# E08-B04 · A deleted message can come back, dated today

## The defect

E05's duplicate check is existence in `messages`:

```dart
// lib/features/messaging/domain/receive_message_use_case.dart:110-116
final existing = await (_db.select(_db.messages)
      ..where((t) => t.id.equals(envelope.id)))
    .getSingleOrNull();
if (existing != null) {
  // Duplicate packet (task file §3.3/EARS-MSG-2)
  return null;
}
```

`RetentionExecutor.deleteMessageItems` removes that row and records nothing
that this check consults. So after a retention pass, a still-circulating
copy of the same message is no longer a duplicate — it is a new message.

Worse than a plain re-insert: the re-inserted row does not carry the
original timestamp.

```dart
// receive_message_use_case.dart:119
final createdAt = DateTime.now().millisecondsSinceEpoch;
```

A message the policy deleted for being 200 days old returns dated **today**,
and sorts to the top of the conversation
(`idx_messages_conversation_created_at`, keyset pagination by `created_at`).
It is then immune to the age policy that removed it, for another 45 days.

## Repro
1. Fresh in-memory `AppDatabase`. Seed 2 `messages`.
2. `RetentionExecutor.deleteMessageItems(['m-00000'])`.
3. Run E05's dedup query for `m-00000` — i.e. what
   `ReceiveMessageUseCase.call` runs before inserting.

## Expected
FR-MSG-003 / EARS-MSG-2 — a duplicate packet is recognized and dropped.
FR-STORE-004 — data the user's policy removed stays removed; a retention
delete is not silently undone by the mesh. If a deleted message *may* legally
return, that is a product decision, and FR-STORE-007's explanation surface
must be able to say so.

## Actual
Reviewer's own probe (`test/core/storage/sweep_probe_test.dart`, scratch,
not committed):

```
dedup lookup for the deleted id returns: null -> treated as a NEW message
```

The packet is accepted, a fresh `messages` row is inserted with
`delivery_state: accepted` and `created_at: now`, and `recordStored` writes
a new `delivery_states` row on top of the orphan one `E08-B03` describes
(same `(message_id, state)` PK, so it merges via the existing `DoUpdate`
rather than failing — the collision is silent).

## Severity
**S3** — genuine cross-epic contract violation and a falsified timeline for
the affected message, but narrow: it needs a manual retention mode active
*and* a peer or relay still holding and re-delivering a message old enough
to have been deleted. Relay payloads are TTL-reclaimed
(`RelayEngine.reclaimPayloads`, E04-B02), which limits how long a copy
survives in the mesh. The blast radius is one message per occurrence, not a
broken feature.

**Reachability note for the 🧍 `bug_priorities` gate:** as with `E08-B01`,
no shipped UI can enable a manual mode today (`E08-T09` is prospective), so
this cannot fire in the current build. Smart Mode never deletes a message
(`OQ-E08-3(a)`), so it cannot trigger this either.

## Fix direction — a product call first, not a code call
Two honest shapes; the human/planner picks:
- **(a) Tombstones.** Record deleted message ids (a small table, or a
  `deleted` flag on a retained stub row) and have `ReceiveMessageUseCase`
  consult it. Correct and durable, but it is a **schema migration** (🧍
  `db_schema_migration`, rule 3) and it trades storage back for the storage
  the deletion reclaimed — which needs to be sized honestly before it is
  chosen, since this is a storage epic.
- **(b) Accept it, and say so.** Declare that a re-delivered message may
  legally return, and record it as a known, disclosed limitation of manual
  retention in the explanation surface — with, at minimum, the `created_at`
  falsification fixed by preserving the envelope's own creation time instead
  of stamping `DateTime.now()`, so a returning message at least lands in the
  right place in the conversation.

Note that `OQ-E08-3`'s original option **(b)** already contemplated
tombstones ("keeping tombstones so E05's dedup, sequence and sync-cursor
guarantees survive") and the human chose **(a)** — Smart Mode excludes
conversation content — which left the tombstone question unanswered for the
manual path rather than settled. This bug is that unanswered half surfacing.

## Regression test (write it first)
Delete a message via `RetentionExecutor`, then drive
`ReceiveMessageUseCase.call` with the same envelope and assert the agreed
behaviour (dropped as duplicate under (a); or re-inserted with the
*original* `created_at` under (b)). Must fail on today's code.

## What this fix does NOT do
- Does **not** change Smart Mode's allow-list, the delivery-state guard, or
  the transactional per-group apply path.
- Does **not** add a schema migration without the 🧍 `db_schema_migration`
  gate cleared first.
- Does **not** touch `SyncCursorService`, sequence-number assignment, or
  `sync_cursors` — a retention delete does not rewind a cursor, and the
  reviewer confirmed that is correct: the backfill path re-requests by
  sequence number and is not affected by this defect.
- Does **not** touch the group receive path or `GroupCryptoService`.
- Does **not** fix the orphan rows — that is `E08-B03`.
