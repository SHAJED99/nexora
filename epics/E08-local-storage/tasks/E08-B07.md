# E08-B07 · `olderThanDays` selects the newest of the aged set, not the oldest

## The defect

`ManualPolicy._planOlderThan` (`manual_policy.dart:121-124`) calls:

```dart
items(kind, olderThanEpochMs: cutoff)   // default limit: 500, ORDER BY created_at DESC
```

with no paging. `itemsOfKind`'s `oldestFirst`/paging support (added by
`E08-B01`/`E08-B02`'s fix) exists on the enumeration itself, but this call
site was never updated to use it — `_planOlderThan` still takes whatever
500 rows come back from a `DESC`-ordered, cutoff-filtered query, which are
the **newest** 500 items that happen to be older than the cutoff, not the
**oldest** 500.

## Repro (reviewer's own probe, from E08-B01/B02's PR review)

1. Seed 1500 messages, all older than a 30-day cutoff, with a spread of
   ages beyond that.
2. `StorageSettingsRepository.setMode(StorageMode.olderThanDays, olderThanDays: 30)`.
3. `StorageManager.runPass(...)` under `olderThanDays`.

```
selected=500 of 1500 aged; min=m-01000 max=m-01499
```

The 500 selected are the newest of the 1500 aged messages — i.e. the ones
*closest* to no longer qualifying — not the oldest, which is what a user
asking to delete "data older than 30 days" would expect to go first.

## Expected

FR-STORE-004 — "delete data older than X days" removes the oldest
qualifying data first, same as `overSizeMb`'s and Smart Mode's corrected
behavior.

## Actual

As above: the newest 500 of the aged set are selected each pass, so the
genuinely-oldest data survives every pass until enough newer aged items
have been removed to bring it into the window.

## Severity

**S3** — under-deletion, not wrong-deletion. Unlike `E08-B01`, this does
not delete the *wrong* items; it deletes *a* qualifying set of items,
just not the chronologically-correct-first ones. It self-corrects over
repeated passes (each pass eats 500 from the newest-aged end, gradually
working backward), and reaches full correctness once the aged set drops
under the page size. Not reachable today by any shipped UI (`E08-T09` is
prospective, same reachability note as `E08-B01`/`E08-B04`).

## Fix direction

Apply the same `oldestFirst` paging `E08-B01`'s fix added to
`itemsOfKind` — call `_planOlderThan`'s `items(...)` with
`oldestFirst: true` (or equivalent) and page until the running byte
total/item count captures what the policy should remove, or the kind
is exhausted. This should be a small, mechanical change reusing
`E08-B01`'s own paging helper/pattern rather than a new algorithm —
`_planOlderThan`'s selection rule ("everything older than X days") is
simpler than `_planOverSize`'s ("oldest-first until under a byte cap"),
since it has no early-termination condition other than exhausting the
aged set.

## Regression test (write it first)

Seed > the default page-size worth of items older than the cutoff and
assert the selected ids are the genuinely-oldest ones among the aged set
(not the newest-of-aged). Must fail on today's code with the
`min=m-01000 max=m-01499`-shaped signature above, and pass after.

## What this fix does NOT do

- Does **not** touch `_planOverSize` (`E08-B01`) or Smart Mode's item
  gathering (`E08-B02`) — both already fixed.
- Does **not** change `itemsOfKind`'s signature or paging mechanics —
  `E08-B01`'s fix already added what this needs; this task only changes
  the call site.
- Does **not** change the `olderThanDays` validation, the 1-day floor, or
  any `StorageSettingsRepository` behavior.
- Does **not** touch `RetentionExecutor`'s invariants, the delivery-state
  guard, or relay payload retention.
- Does **not** build `E08-T09` or make manual modes reachable from any UI.
