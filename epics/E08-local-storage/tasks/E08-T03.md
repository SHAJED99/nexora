# E08-T03 · Access-frequency signals

## 1. Goal
Give `FR-STORE-005`'s *access frequency* factor a real data source, so
Smart Mode can say "rarely accessed" because it observed the item not being
accessed — not because a heuristic guessed.

## 2. Business logic
- **Access frequency is one of the eight factors `FR-STORE-005` names, and
  the current schema records it nowhere.** Without this task the factor can
  only ever be reported *unavailable* (which `E08-T04` handles honestly, and
  which is precisely why this task is `should` rather than `must` — the epic
  degrades correctly without it, it just degrades).
- **An access is a real display, not a query.** The signal is recorded when
  a message is actually shown to the user
  (`ChatController.onMessageDisplayed`, already the delivery-ack read
  trigger) and when a conversation is opened (`ChatController.onInit`).
  Background reads — the conversations list projection, the dashboard's
  three-row preview, a sync pass — are **not** accesses; counting them would
  make every item look equally used and destroy the factor's meaning.
- **NULL means never observed.** `last_accessed_at` stays NULL until a real
  access happens. No backfill, no "assume created_at". A reader that treats
  NULL as "accessed at epoch 0" turns every old message into a deletion
  candidate on day one, which is the failure mode this rule exists to stop.
- **Recording is best-effort and never blocks the UI.** A failed stat write
  is not a user-visible error and never propagates out of the display path —
  the same "a lost ack is not an error" posture `E06-T08` already
  established for acknowledgements.
- **Conversation activity** (a second named factor) is derived at scoring
  time from `messages.created_at` and needs no new signal — this task adds
  nothing for it, deliberately.

## 3. What this task does
- `storage_access_recorder.dart`: `StorageAccessRecorder` with an upsert
  against `storage_item_stats` (bump `access_count`, set
  `last_accessed_at`), plus a batched/debounced write so scrolling a long
  conversation is not one write per bubble per frame.
- Wires two call sites in `ChatController`: `onInit` (conversation opened)
  and `onMessageDisplayed` (a message actually rendered).
- Tests: real in-memory `AppDatabase`, assert upsert semantics, debounce,
  best-effort failure, and that no other read path records.

## 4. What this task does NOT do  ← the scope fence
- **Does not score, rank or delete anything.** It records; `E08-T04` reads.
- **Does not add a call site outside `ChatController`.** Not the
  conversations list, not the dashboard, not `ConversationRepository`, not
  the inbound pipeline. Every extra call site silently redefines what
  "accessed" means.
- **Does not backfill `storage_item_stats` from history.** NULL is the
  correct value for an unobserved item.
- **Does not change `onMessageDisplayed`'s existing behaviour** — the
  `markRead` ack path is untouched; the recorder call is additive and
  independent, and a recorder failure must not break the ack.
- **Does not touch `delivery_states` or the read-receipt semantics.**
  "Displayed" already has an owner (`E06-T08`); this task reuses its trigger
  rather than inventing a second notion of "seen".
- Does not add a dependency, a timer service, or a background isolate.

## 5. Contract

### Functions
```yaml
- signature: "StorageAccessRecorder({required AppDatabase db, Duration flushInterval = const Duration(seconds: 5)})"
  params:
    db: "the app's AppDatabase (injected; never constructed here)"
    flushInterval: "debounce window — accesses coalesce within it, one write per (kind,id) per window"
  returns: "StorageAccessRecorder"
  purpose: "the single writer of storage_item_stats"

- signature: "StorageAccessRecorder.recordAccess(StorageItemKind kind, String itemId) -> void"
  params: { kind: "the item's class", itemId: "its primary key" }
  returns: "void — fire and forget; never throws to the caller"
  purpose: "note that a stored item was really used"

- signature: "StorageAccessRecorder.recordConversationOpened(String conversationId) -> void"
  params: { conversationId: "the opened conversation" }
  returns: "void"
  purpose: "conversation-level access signal, recorded as kind message with the conversation id, so a conversation opened but not scrolled still counts as used"

- signature: "StorageAccessRecorder.flush() -> Future<void>"
  params: {}
  returns: "Future — completes when pending coalesced writes are durable"
  purpose: "deterministic flush for tests and for app pause; never called per-bubble"

- signature: "StorageAccessRecorder.dispose() -> Future<void>"
  params: {}
  returns: "Future — flushes then cancels the timer"
  purpose: "no timer outlives the controller that owns it"
```

### Data
Writes `storage_item_stats` only (created by `E08-T01`). Upsert on
`(item_kind, item_id)`: `access_count = access_count + 1`,
`last_accessed_at = <now>`. No other table is written.

## 6. Risks
- A per-bubble write during fast scrollback is a real performance trap on a
  low-end device; the debounce is the contract, not an optimization.
- `ChatController` is disposed on route pop — an un-flushed debounce window
  loses the last few accesses unless `dispose()` flushes. Test it.
- Injecting the recorder into `ChatController` must not change its
  constructor's existing required parameters in a way that breaks
  `chat_binding.dart` — if it does, the binding is outside this fence and
  the correct move is to make the recorder an optional named parameter
  defaulting to a no-op, not to widen the fence.
- The upsert must be a single statement; a read-then-write races itself
  under the debounce flush.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-STORE-7**: WHEN a stored message is displayed to the user or its
  conversation is opened, the system SHALL record the access against that
  item's stats row. (FR-STORE-005)
- **EARS-STORE-8**: IF an item has never been accessed, THEN the system
  SHALL leave its `last_accessed_at` NULL rather than substituting a
  default, and IF a stat write fails, THEN the display path SHALL continue
  unaffected. (FR-STORE-005)

**Deviations from spec/design:**
- **`StorageItemKind` is a temporary, disclosed duplicate of E08-T02's
  enum.** `storage_tables.dart` (T01) documents `storage_item_stats
  .item_kind` as "a `StorageItemKind.name` string (E08-T02 owns the
  enum)" — but this task's `depends_on` lists only `[E08-T01]`, and T02 was
  dispatched in parallel off the same base commit and has not merged, so
  `lib/core/storage/storage_item.dart` does not exist on this branch, and
  this task's own `files:` fence forbids creating or touching anything
  under `lib/core/storage/` beyond `storage_access_recorder.dart`. This
  task's own §5 contract names `StorageItemKind` directly in
  `recordAccess`'s signature, so the type must exist somewhere for the
  code to compile. Resolution: `storage_access_recorder.dart` declares its
  own `StorageItemKind` enum, copied verbatim (same names, same order) from
  T02's own task file §2, so every `.name` string this recorder writes is
  byte-for-byte what T02's canonical enum will also produce — a drop-in
  seam, not a competing definition. Flagged as `OQ-E08-T03-1` below for the
  planner: once T02 merges, a small follow-up should delete this
  declaration and import the canonical one instead, with no behavior
  change. This is a task-sharding gap (a function signature naming a type
  owned by a sibling task not listed as a dependency), not a spec gap — the
  simplest interpretation that satisfies this task's own acceptance
  criteria without stalling on T02's merge.
- **`chat_binding.dart` is not wired to pass a real recorder.** Task §6
  Risks explicitly names this: injecting the recorder as a `required`
  constructor parameter would break `chat_binding.dart`'s existing call
  site, which is outside this task's `files:` fence. `recorder` is an
  optional named parameter (`StorageAccessRecorder? recorder`), and every
  call site in `chat_controller.dart` is null-safe (`_recorder?....`) — a
  literal `no-op` object was not introduced since a null check is
  functionally identical and adds no extra class. Production wiring (a
  real `StorageAccessRecorder` constructed in `chat_binding.dart` from
  `stack.db`) is therefore out of scope here and remains a follow-up task's
  job — this task proves the recorder and its two call sites work, not
  that they are wired end to end into the running app yet.
- **Test file path.** The task's `files:` list names
  `test/features/chat/chat_controller_test.dart`; the real, existing file
