# E08-T07 · E08 design gap pass

## 1. Goal
Give this epic's two undesigned surfaces — the Storage settings screen and
the expanded state of the dashboard's storage warning — real, human-
approvable derived contracts, so the frontend tasks that build them are
shardable at all (rule 2: no contract, no frontend task).

## 2. Business logic
- **Rule 2, both halves.** The design draws a `Local Storage` card
  (dashboard elements 15-18) and a `Storage` settings row (settings
  elements 29-30, "Local cache, message retention, export"). It draws
  **no** expanded warning and **no** Storage sub-screen. Both journeys are
  required by the spec (`FR-STORE-004`, `FR-STORE-007`), so both are
  *derived* — from the existing screens' own measured primitives, marked
  `source: derived`, and 🧍 human-approved. Never invented freely, never
  silently dropped.
- **`GAP-005` is the governing precedent**, not a special case: a settings
  row that implies a destination screen the design never drew. That entry's
  approved resolution was "a design pass produces the contract, then a task
  builds from it" — this task is that pass for the Storage row.
- **`GAP-011` closes here in spirit and in `E08-T08` in fact.** It deferred
  the Local Storage card's data source "until E08" and explicitly left the
  `Smart Mode - Older than 10 days` line as static copy. This pass decides
  what that line becomes when the policy is real, and adds the expanded
  state behind it.
- **The design's own copy wins over the BRD's example.** `dashboard.md`
  measures the string `Smart Mode - Older than 10 days` character for
  character; BRD §21 shows the same string. The expansion's copy comes from
  BRD §22's worked example, rendered in the design's existing typography —
  not new voice.
- **`L-process-002`: an agent does not approve its own gap.** Every
  `approved by:` line this task writes is deliberately bare. The gate line
  at the top of `design/gaps.md` is left exactly as the human set it — an
  agent neither re-opens nor re-clears it.
- **When nothing is derivable, the honest output is a question**, not a
  proposal — `E06-T13`'s PTT precedent (GAP-017). Copy for a state the BRD
  never wrote is a named fork, not an invention.
- **No new token, colour, radius or spacing value.** Everything comes from
  the union of `dashboard.md` and `settings.md`'s measured token tables.

## 3. What this task does
- Writes `design/screens/settings-storage.md` — a `source: derived`
  contract for the Storage sub-screen: the three-mode selector
  (`FR-STORE-004`), the two manual-policy parameter inputs, the current-
  usage summary, and the decision-explanation list (`FR-STORE-007`), all
  composed from `settings.md`'s row/card primitives and `devices.md`'s list
  primitives, at the same viewport as its parents.
- Adds an expanded-state section to `design/screens/dashboard.md` covering
  the storage warning's expansion (`FR-STORE-006` collapsed →
  `FR-STORE-007` expanded), as a derived state of an already-measured card.
- Appends `GAP-024`…`GAP-027` to `design/gaps.md` (written at sharding by
  the planner and refined here), each citing its spec id, its derived-from
  primitives, its proposal, and a bare `approved by:` line.
- Names, as explicit forks rather than choices: the collapsed warning's
  *threshold copy* when no denominator exists (`OQ-E08-1`), and how a
  category with an `unavailable` factor is worded (`OQ-E08-4`).

## 4. What this task does NOT do  ← the scope fence
- **Writes no Dart, builds no screen, registers no route.** `E08-T08` and
  `E08-T09` build; this task only contracts.
- **Does not fill in any `approved by:` line** and does not touch the gate
  line at the top of `design/gaps.md` (`L-process-002`).
- **Does not re-measure or regenerate `dashboard.md`'s or `settings.md`'s
  existing token tables.** The generated tables are never hand-edited
  (design-fidelity rule 1); the expanded state is appended as a derived
  section, clearly marked, leaving the measured tables byte-unchanged.
- **Does not invent a "Clean Now" button, a confirmation dialog, or any
  forced action** — `EARS-STORE-2` and `FR-STORE-006` say the warning is
  informational. A destructive affordance nobody asked for is the single
  most tempting wrong move on this screen.
- **Does not design an export flow.** The settings row's subtitle says
  "Local cache, message retention, export"; export has no FR in this epic's
  `traces_to:` and no id anywhere in `FR-STORE-*`. It is named as an open
  gap with no proposal, not quietly designed.
- **Does not design a per-conversation or per-item "keep" control** —
  that would decide `OQ-E08-4` (importance) with a widget.
- Does not touch any other screen contract, or `design/sources.yaml` (a
  derived screen has no extractable source; its golden is extracted from
  the build later, as `group-create.md` records).

## 6. Risks
- The strongest pull on this screen is toward a "Clean Now" button, because
  every storage screen the designer has ever seen has one. `FR-STORE-006`
  explicitly says the user does not need to press one. Write the
  prohibition into the contract, not just into this task.
- `settings.md`'s rows are a *menu*; a settings **detail** screen has no
  measured precedent in this design at all. Deriving it from `devices.md`'s
  list rows is the honest reading — say so in the contract's header, with
  the alternative named, rather than presenting it as measured.
- BRD §22's example numbers (820 MB, 620 MB, 310 MB, 50 MB) are
  *illustrative*. Copying them into a contract as if they were design copy
  would put fabricated figures on a screen — the exact defect
  `dashboard_controller.dart`'s header exists to prevent.
- A derived contract with no golden cannot be gated by `make design-verify`
  until the build exists; say so explicitly, as `group-create.md` does, so
  `E08-T09`'s reviewer is not surprised by a missing golden.

**Deviations from spec/design:**
1. **`settings.md` element 6's title colour `rgb(234, 241, 255)` is not used.**
   It is measured on the element but is **absent from settings' own measured
   token table**, so using it would put a value in a derived contract that
   `DOC-STORE-17`'s check cannot find in any source table. `SS3` uses
   `rgb(248, 249, 255)` — in that table, 8 uses, and the colour of every
   `heading:3` on the parent screen. Same reasoning `group-manage.md`
   §Derivation boundary 2 applied to devices' `r4px`. Recorded in
   `settings-storage.md` §Derivation boundary 3.
2. **Devices' row *geometry* is borrowed; devices' row *colours* are not.**
   `devices.md` is a light surface and `settings.md` a dark one —
   `rgb(11, 28, 48)` is text on the first and page fill on the second — so
   carrying devices' colours onto a settings child would put near-black text on
   a near-black page. §Derivation boundary 2.
3. **The parameter field is not derived from an input primitive**, because no
   parent draws one. It is the parent's own card surface (`rgb(33, 49, 69)`,
   `r12px`) with a `JetBrains Mono` numeral. The named alternative —
   `conversations.md`'s search field, which `group-manage.md` GM3 borrowed — is
   rejected only because its light fill belongs to a light screen.
   §Derivation boundary 4.
4. **Three colours appear in `settings-storage.md` that are not tokens of it:**
   `rgb(234, 241, 255)`, `rgb(186, 26, 26)` and `rgb(229, 238, 255)`. Each
   appears **only** inside §Derivation boundary 3/4/5, naming a value
   deliberately *not* used. The §Tokens preamble says so explicitly so a
   mechanical token check reads them correctly.
5. **`arrow_back` is borrowed from `chat.md`**, which is not one of §5's three
   named parents — the same cross-screen navigation borrow `group-manage.md`
   GM2 makes, recorded rather than silent.
6. **Two of `dashboard.md`'s measured strings will report as copy findings**
   once E08 feeds the card: `45% used` → `GAP-026` (`OQ-E08-1`(c)) and
   `Smart Mode - Older than 10 days` → `GAP-011`'s approved resolution. Both
   are disclosed in the new §Derived state, not silently rewritten.
