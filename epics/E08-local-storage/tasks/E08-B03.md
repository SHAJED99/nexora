# E08-B03 · Deleting a message reclaims its ciphertext and leaks two rows

## The defect

The app's only deletion path touches exactly one table:

```dart
// lib/core/storage/retention_executor.dart:375-378
Future<void> deleteMessageItems(List<String> ids) async {
  if (ids.isEmpty) return;
  await (db.delete(db.messages)..where((t) => t.id.isIn(ids))).go();
}
```

`delivery_states` (PK `(message_id, state)`, `message_tables.dart:57-69`)
and `storage_item_stats` (PK `(item_kind, item_id)`,
`storage_tables.dart:24-35`) both key off a message id, neither declares a
foreign key or cascade, and a repo-wide grep finds **no** delete against
either table anywhere in `lib/`. The rows survive their message forever.

Second, related consequence — the one place this epic materializes an
unbounded table:

```dart
// lib/core/storage/storage_manager.dart:177-186
Future<Map<String, ItemAccessStat>> _accessStats() async {
  final rows = await inventory.db.select(inventory.db.storageItemStats).get();
  ...
}
```

Every pass, every 6 hours, loads the entire `storage_item_stats` table into
a Dart `Map` with no limit — a table that only ever grows (one row per
message ever displayed, per `E08-T03`'s recorder, plus one per conversation
opened, and now never pruned). This directly contradicts
`storage_inventory.dart`'s own stated discipline: *"a history large enough
to be worth managing is a history too large to materialize"*.

## Repro
1. Fresh in-memory `AppDatabase`. Seed 3 `messages`, plus one
   `delivery_states` row and one `storage_item_stats` row per message
   (exactly what `MessagingCoordinator.recordStored` and
   `StorageAccessRecorder` write in the real app).
2. `RetentionExecutor.deleteMessageItems(['m-00000','m-00001','m-00002'])`.
3. Count rows in all three tables.

## Expected
FR-STORE-001/005 — a retention pass reclaims the space the removed items
occupied. Per-message bookkeeping for a message that no longer exists is not
data the user asked to keep, and `RetentionOutcome.bytesReclaimed`'s
"real bytes reclaimed, never re-estimated" claim
(`retention_executor.dart:107-110`) should describe what the database
actually gives back.

## Actual
Reviewer's own probe (`test/core/storage/sweep_probe_test.dart`, scratch,
not committed):

```
after delete -> messages: 0, delivery_states: 3, storage_item_stats: 3
```

Two orphan rows per deleted message, permanently. `bytesReclaimed` counts
only the `LENGTH(ciphertext)` freed and overstates the net reclaim by the
orphans' own footprint — small per row, monotonic, and never recovered.

## Severity
**S3** — real and monotonic, but small per occurrence and with no
correctness impact on messaging: nothing reads `delivery_states` by a
message id that no longer exists, and a stale `storage_item_stats` row is
keyed to an id no plan will ever name again. The `_accessStats()` full-table
materialization is the part that scales worst, and it is live **today** on
the default Smart Mode path — it does not need any delete to have happened.

## Fix direction
- Extend the per-group `db.transaction()` in `RetentionExecutor.apply` (it
  already exists, `retention_executor.dart:279-286`) to delete the matching
  `delivery_states` and `storage_item_stats` rows alongside the `messages`
  rows, so the cleanup is atomic with the delete it belongs to and cannot
  half-apply.
- Separately, bound `_accessStats()`: read only the stats rows for the item
  ids the plan is actually scoring (a join or an `IN` over the enumerated
  items), rather than the whole table. This is worth doing regardless of the
  orphan fix, and interacts with `E08-B01`/`E08-B02`'s paging change — do
  them in an order that does not leave a half-paged read against a full-table
  stats map.
- Consider whether `delivery_states` should carry a real FK with
  `ON DELETE CASCADE`. That is a **schema migration** and therefore a 🧍
  rule-3 gate (`db_schema_migration`) — present it as an option, do not take
  it unilaterally.

## Regression test (write it first)
Assert all three tables are empty after a real `apply()` pass deletes a
message that has both a `delivery_states` and a `storage_item_stats` row.
Must fail on today's code with `delivery_states: 3, storage_item_stats: 3`.

## What this fix does NOT do
- Does **not** add a schema migration, a foreign key, or a cascade without
  the 🧍 `db_schema_migration` gate being cleared first.
- Does **not** delete any `messages`, `relay_packets`, `sync_cursors` or
  group row that the current guards protect, and does not weaken the
  delivery-state guard or the relay-payload invariant.
- Does **not** prune `storage_decisions` — that log is append-only by
  design (FR-STORE-007) and pruning it is a separate product question.
- Does **not** change what `StorageAccessRecorder` writes or when
  (`E08-T03`'s contract).
