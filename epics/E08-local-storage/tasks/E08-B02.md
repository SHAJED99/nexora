# E08-B02 · Smart Mode goes blind to old data past 500 items per kind

## The defect

```dart
// lib/core/storage/storage_manager.dart:123-129
final items = <StorageItem>[
  for (final kind in const [StorageItemKind.message,
                            StorageItemKind.relayPayload])
    ...await inventory.itemsOfKind(kind),   // limit: 500, ORDER BY created_at DESC
];
plan = smart.plan(snapshot: snapshot, items: items, ...);
```

No `limit`, no `olderThanEpochMs`, no paging. Smart Mode therefore scores
only the **newest 500** items of each kind — while the factor it exists to
apply (`RetentionReason.olderThan`, age threshold 45 days) selects the
**oldest**. The candidates it is looking for are precisely the ones the
window drops.

This is the **default** mode on every fresh install (`E08-T01`'s default
settings row, `mode: 'smart'`), running on `MessagingCoordinator`'s tick
every 6 hours.

Note also `smart_mode_policy.dart:79-84`'s own doc comment, which already
states the requirement this caller does not meet: *"the caller is
responsible for supplying a representative set (e.g. every `message` item,
not an age-filtered subset) for this factor to mean what its name says."*

## Repro
1. Fresh in-memory `AppDatabase`, default (Smart) mode.
2. Seed N `messages`, all dormant (older than the 14-day conversation-active
   window so the documented activity shield is out of the way), all older
   than the 45-day age threshold, 100 bytes each.
3. `StorageManager.runPass(nowEpochMs: now, apply: false)` and count the
   `olderThan` candidates in the returned plan.

## Expected
EARS-STORE-1 / FR-STORE-005 — Smart Mode determines removal candidates over
the stored data. FR-STORE-006/007 — the dashboard's informational warning
and its explanation describe what is really there. The candidate count
should track the number of genuinely-aged items.

## Actual
Reviewer's own probe (`test/core/storage/sweep_probe_test.dart`, scratch,
not committed):

```
400 msgs  -> olderThan candidates: 400   (correct)
2000 msgs -> olderThan candidates: 500   (capped at the window)
2000 msgs -> messages genuinely older than 90d: 2000
2000 msgs -> plan.totalBytes: 50000      (true removable total: 200000)
```

At 400 items the plan is right. At 2000 it reports 500 items / 50 000 bytes
against a true 2000 / 200 000 — a **4× under-report**, growing worse the
more history the device accumulates. The dashboard Local Storage card
(`dashboard_controller.dart:_decisionsFromGroups`) renders exactly these
numbers, so FR-STORE-006's warning becomes least accurate on the device that
most needs it.

`warningActive: decisions.isNotEmpty` still fires here, so the user is not
told "nothing to remove" outright — but every figure shown is wrong, and
the `age` factor's own score (`agingCandidateCount`) is wrong with them.

## Severity
**S2** — the epic's primary EARS criterion produces materially wrong output
with no workaround available to the user, on any device past 500 messages
(a low bar for a chat app). Not S1: Smart Mode's allow-list is empty
(`OQ-E08-3(a)`), so nothing is deleted and no data is lost — the harm is
wrong information on the user-visible surface, not destroyed data.

## Fix direction
Depends on the same `itemsOfKind` enumeration change as `E08-B01`. Either
page through every kind, or compute the aggregate candidate counts/bytes in
SQL and materialize only what the explanation actually needs to name.
Do **not** simply raise `limit` — that moves the cliff instead of removing
it, and `StorageInventory`'s "bounded by construction" property (task §5,
"a history large enough to be worth managing is a history too large to
materialize") is correct and must survive the fix.

If a bound must remain for a real reason, the plan must say so honestly
rather than silently reporting a truncated figure as complete — an
`Unavailable`/`partial` disclosure in the same spirit as `EARS-STORE-10`'s
null-budget handling, never a fabricated-complete number (E04-B03's standing
prohibition).

## Regression test (write it first)
Seed > `limit` genuinely-aged items and assert the plan's candidate count
and `totalBytes` match the SQL ground truth. It must fail on today's code
with the `500` / `50000` signature above.

## What this fix does NOT do
- Does **not** change the conversation-activity shield
  (`smart_mode_policy.dart:119-123`), the 45/30/7-day thresholds, or any
  `A-004` placeholder value — those are documented, human-owned numbers.
- Does **not** widen Smart Mode's allow-list. `OQ-E08-3(a)` stands: Smart
  Mode still deletes nothing.
- Does **not** fix `overSizeMb`'s wrong-item selection — that is `E08-B01`,
  with its own regression test, even if one shared enumeration change serves
  both.
- Does **not** implement the `storagePressure` or `importance` factors —
  that is `E08-B05`.
- Does **not** reshape any widget or touch the design probe.
