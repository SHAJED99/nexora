# E08-T06 · Retention execution + decision log + composition

> 🟢 **`OQ-E08-3` answered 2026-09-02 (option (a)):** Smart Mode's
> allow-list excludes conversation content entirely; message deletion
> happens only under a manual policy the user explicitly turns on. This
> makes the allow-list **mode-dependent**, which `RetentionExecutor`'s
> original §5 signature could not express — see `OQ-E08-T06-1` below for
> the resulting, orchestrator-amended contract (allow-list moved from the
> constructor to a per-`apply()`-call parameter, supplied by
> `StorageManager` based on which policy produced the plan). Build against
> the amended §5, not the original static-constructor shape.

## 1. Goal
Make the plan real and make it *run*: apply an approved plan, record every
decision with its reason so `FR-STORE-007` has something honest to explain,
and — the part this project has now missed twice — actually compose the
thing into the running app.

## 2. Business logic
- **Plan and apply are separate calls, always.** `planNow()` computes and
  records `outcome: planned` rows; `apply(plan)` deletes and records
  `outcome: applied`. The dashboard's informational warning
  (`EARS-STORE-2`) reads *planned* rows and never triggers `apply` — a
  warning that deletes when you look at it is not informational.
- **Only the classes `OQ-E08-3` authorises may be deleted.** The executor
  takes an explicit allow-list of `StorageItemKind`s, and a candidate group
  outside it is recorded as `outcome: skipped` with its reason preserved —
  visible in the explanation, never silently dropped.
- **Never delete an item that is not yet delivered.** A message whose
  delivery state is `Queued`, `Sent` or `Failed` is in flight; deleting it
  destroys data the user believes they sent. This is an invariant of the
  executor, independent of any policy, and it is asserted before every
  delete.
- **Relay payload retention is not ours.** `RelayEngine.reclaimPayloads()`
  (E04-B02) already owns relay TTL and `MessagingCoordinator` already
  drives it (`E06-T06`). The executor never deletes a `relay_packets` row
  or nulls a payload — if relay bytes appear in a plan they are reported,
  and skipped with the owning mechanism named.
- **Every delete is logged before it happens, in the same transaction.**
  A delete whose decision row failed to write is an unexplainable deletion,
  which is worse than no deletion (`FR-STORE-007`).
- **Composition is this task's own deliverable, not a follow-up.** This
  project has now shipped an unwired controller twice — `OQ-E06-T06-4`
  (`MessagingCoordinator.start()` had no caller) caught it proactively,
  `E07-B03` (`CallMigrationController` never constructed in `lib/`) did
  not, and E07's retro named the pattern explicitly. So `bindings.dart`
  and `messaging_coordinator.dart` are inside **this** task's fence: the
  manager is registered, the tick calls it, and a test proves the wiring
  from the composition root rather than from a hand-built object.
- **The storage pass runs on the existing coordinator tick, not a new
  scheduler.** `MessagingCoordinator` already owns the app's one periodic
  tick; a second timer would be a second answer to "when does background
  work happen".
- **The storage pass is throttled.** A full inventory scan on every tick is
  wasteful; the manager runs at most once per `storagePassInterval` and
  skips (recording nothing) otherwise.

## 3. What this task does
- `storage_decision_log.dart`: `StorageDecisionLog` — append planned/applied/
  skipped rows to `storage_decisions`, and read the most recent pass's rows
  for the explanation surfaces.
- `retention_executor.dart`: `RetentionExecutor.apply(plan, allowedKinds: ...)`
  — transactional, delivery-state guarded, log-before-delete. `allowedKinds`
  is supplied per call by `StorageManager`, mode-dependent (see
  `OQ-E08-T06-1`'s amendment).
- `storage_manager.dart`: `StorageManager` — the facade the app composes:
  reads settings, picks Smart or Manual policy, plans, logs, optionally
  applies, exposes the latest plan for the UI.
- Wires `StorageManager` into `AppBinding` (`Get.put(..., permanent: true)`)
  and calls it from `MessagingCoordinator`'s tick behind the throttle.

## 4. What this task does NOT do  ← the scope fence
- **Does not choose which classes are deletable beyond what `OQ-E08-3`'s
  answer and `OQ-E08-T06-1`'s amendment already state.** The mode-split
  (Smart Mode always empty; Manual Mode may include `message`) is fixed by
  those resolutions — the builder implements exactly that split and does
  not widen it, narrow it, or add a third mode-dependent variant.
- **Does not delete a `relay_packets` row or null a payload** — E04-B02 and
  `E06-T06` own that, and duplicating it would give relay retention two
  owners with different rules.
- **Does not delete a message that is not in a terminal delivered state.**
- **Does not add a second periodic timer, isolate, or background service.**
  `E10` owns background operation; this rides the existing tick.
- **Does not touch `messages` schema, delivery-state semantics, sync
  cursors or dedup state.** If a delete would break E05's dedup or sequence
  guarantees, that is a finding for `OQ-E08-3`, not something to work around
  here.
- **Does not render anything.** No copy, no widget, no controller. `E08-T08`
  and `E08-T09` read from the manager.
- **Does not change `MessagingCoordinator`'s existing tick semantics** —
  no reordering of `processQueue`/`sweepExpired`/`reclaimPayloads`, no
  change to its re-entrancy coalescing (the property `E06-T06`'s reviewer
  falsified). The storage pass is appended, after the existing work, and
  its failure must not abort the tick.

### Data
Writes `storage_decisions`. Deletes rows only from tables named in the
per-call `allowedKinds` set (empty for Smart Mode; `{message}` for Manual
Mode, per `OQ-E08-T06-1`). Reads `storage_policy_settings` through
`E08-T05`'s repository and inventory through `E08-T02`'s.

## 6. Risks
- **A deletion bug here is unrecoverable user data loss** — there is no
  server copy (ADR-0005). Every test that asserts a delete must also assert
  what was *not* deleted; falsification (revert the guard, watch the right
  test fail) is the expected review style.
- `Get.put` ordering in `AppBinding`: the manager depends on `AppDatabase`
  and the messaging stack, both already registered above it. Registering it
  too early yields a `Get.find` failure at startup — exactly the class of
  composition-root defect `E06-B02` was.
- An exception in the storage pass must not abort the coordinator tick, or
  a storage bug silently stops message delivery. Wrap it, count it, keep
  going.
- The throttle must survive process restart or every cold start runs a full
  scan; persist the last pass time (via `storage_decisions.decided_at`,
  which already records it) rather than an in-memory field alone.
- `bindings.dart` is touched by **no other E08 task** — keep it that way; a
  second task editing it would be this epic's merge-pain source.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-STORE-13**: WHEN a retention plan is applied, the system SHALL
  record every candidate group's decision and reason before deleting
  anything, and SHALL delete only items of the classes it was explicitly
  authorised to delete. (FR-STORE-005, FR-STORE-007)
- **EARS-STORE-14**: The system SHALL NOT delete a message that is not in a
  terminal delivered state, and SHALL NOT delete or reclaim a relay packet
  payload. (FR-STORE-005, NFR-PRIV-001)
- **EARS-STORE-15**: WHILE the app is running, the storage manager
  registered by the composition root SHALL be driven by the existing
  coordinator tick, and a failure in the storage pass SHALL NOT prevent the
  tick's messaging work. (FR-STORE-005)

## Open Questions
- **OQ-E08-T06-1 — the deletable-class allow-list.** Inherits epic-level
  `OQ-E08-3`. The executor ships with an empty allow-list until answered;
  populating it is a spec decision, not an implementation choice.
  - **Status:** 🟢 answered, with a contract amendment — inherits the
    epic-level `OQ-E08-3` resolution (option (a), 2026-09-02): **"Smart
    Mode's allow-list excludes conversation content entirely; message
    deletion happens only under a manual policy the user explicitly turns
    on."** Read literally, this makes the allowed classes **mode-dependent**:
    a Smart Mode pass must never delete `message`-kind items; a Manual Mode
    pass (`olderThanDays`/`overSizeMb`, `E08-T05`) is explicitly authorised
    to, since the user chose that specific rule themselves.
    **§5's `RetentionExecutor` constructor signature as originally written
    (one static `Set<StorageItemKind> allowedKinds>` for the whole
    executor's lifetime) cannot express this — it has no way to know which
    policy produced the plan it is asked to apply.** This is a real
    contract gap, not something to paper over by picking one static set.
    **Amendment: `StorageManager.runPass` must select the allow-list per
    pass, based on which policy produced the plan** — e.g. either (i)
    `StorageManager` constructs/reconfigures the kinds it passes to
    `RetentionExecutor.apply` per call (pass `allowedKinds` as a per-call
    parameter to `apply`, not only a constructor field), or (ii)
    `StorageManager` holds two named allow-lists (`smartModeAllowedKinds`
    empty, `manualModeAllowedKinds` = `{message}`) and selects by
    `settings.mode` before calling `apply`. Either shape is acceptable;
    the builder decides the cleaner implementation, but the resulting
    behavior must be: Smart Mode passes never delete `message`-kind items
    regardless of any allow-list value, and a Manual Mode pass under
    `olderThanDays`/`overSizeMb` may delete `message`-kind items the
    user's own chosen rule selected. `relayPayload`/`databaseFile` stay
    excluded from both, per §4's existing, unambiguous fence (owned
    elsewhere). Write a test proving the mode-dependent split explicitly —
    the same plan/candidate shape must be blocked under Smart Mode and
    permitted under Manual Mode.
  - **Answered by:** orchestrator, amending §5's contract to match the
    human's actual `OQ-E08-3` answer (a mechanical fix required to build
    what was approved, not a new product decision).
