# E08-T05 · Manual policies + mode selection

## 1. Goal
Let the user choose a storage management mode and have that choice actually
mean something — the two non-default modes `FR-STORE-004` names, each
producing the same shape of plan Smart Mode produces, so every surface
downstream is mode-agnostic.

## 2. Business logic
- **`FR-STORE-004` names exactly three modes**: Smart Mode (default),
  delete-older-than-X-days, delete-when-over-X-MB. No fourth mode, no
  "off". (If the human wants an explicit "never delete anything" mode, that
  is a spec amendment, not an addition made here — see §4.)
- **Smart Mode is the default and is what a fresh install has**, per
  `E08-T01`'s migration-inserted settings row. This repository never has to
  handle a missing row.
- **A manual policy produces the same `RetentionPlan` type Smart Mode
  produces**, with the corresponding `RetentionReason` (`olderThan`,
  `overSizeLimit`). One plan shape means one explanation surface
  (`FR-STORE-007`) rather than three that drift apart.
- **A manual policy is literal, not clever.** "Older than X days" means
  exactly items whose `createdAt` is older than X days — it does not
  additionally consider access frequency, importance or pressure. The user
  chose a simple rule over Smart Mode precisely to get a simple rule.
- **Changing the mode never deletes anything by itself.** It changes what
  the next plan says. Execution stays `E08-T06`'s single responsibility.
- **Validation is concrete**: `olderThanDays` ≥ 1, `maxBytes` ≥ 1 MiB, and
  the mode's own parameter must be non-null while the other two stay NULL.
  An invalid write is rejected loudly, never coerced to a default.

## 3. What this task does
- `storage_settings_repository.dart`: `StorageSettingsRepository` reading
  and writing the single `storage_policy_settings` row — `watch()` (a
  broadcast stream for the UI), `read()`, `setMode(...)`, `setBudgetBytes(...)`.
- `manual_policy.dart`: `ManualPolicy.plan(...)` producing a `RetentionPlan`
  for `olderThanDays` and `overSizeMb`, using `E08-T04`'s types.
- Tests: persistence round-trip, validation rejections, watch emission on
  change, and both manual policies' candidate selection.

## 4. What this task does NOT do  ← the scope fence
- **Deletes nothing.** Same fence as `E08-T04`: plan only.
- **Does not add a mode the spec does not name** — no "off", no "ask me
  first", no per-conversation override. Each would be a real product
  decision with no id behind it.
- **Does not set `budget_bytes` to a default.** `setBudgetBytes` exists so
  `OQ-E08-1`'s answer has a home; this task leaves it NULL.
- **Does not build the settings UI.** The Storage screen is `E08-T09`,
  against `E08-T07`'s contract. No widget, no route, no copy here.
- **Does not re-implement Smart Mode's factors** for the manual modes. A
  manual mode that quietly scores access frequency is Smart Mode with a
  different label.
- Does not touch `settings_controller.dart` or `settings_view.dart`.

### Data

inventory through the injected callbacks. Writes no other table.

## 6. Risks
- `overSizeMb` needs a rule for *which* items go when the total exceeds the
  cap. Oldest-first, deterministic, tie-broken by id — write it down and
  test it, or two runs disagree and the explanation surface lies.
- A broadcast stream that does not emit its current value on listen makes
  the settings screen render empty on first frame; `E08-T09` will look
  broken and the bug will be blamed on the UI.
- MiB vs MB: `FR-STORE-004` says "MB". The column is bytes. Pick one
  conversion, state it in the doc comment, and never convert twice.
- Rejecting an invalid write loudly is correct, but the UI must not be able
  to *produce* one — `E08-T09` validates before calling; this layer is the
  backstop, not the only guard.

## Open Questions
- **OQ-E08-T05-1 — `overSizeMb`'s item-fetch callback has no paging control,
  so a truncated 500-item window can silently misfire "oldest-first"
  selection.** Found by the round-1 reviewer (F2): §5 fixes the injected
  `items(StorageItemKind, {int? olderThanEpochMs})` callback signature with
  no `limit`/pagination parameter. In production this callback is
  `StorageInventory.itemsOfKind`, whose default `limit = 500` query is
  `ORDER BY created_at DESC LIMIT ?` — **newest 500**, not oldest. With
  more than 500 items in a kind, "oldest-first removal" operates on the
  500 *newest* items, and the genuinely oldest items (the ones that should
  be removed first) are never candidates. `runningBytes` is separately
  seeded from the kind's real SQL-summed total, so the loop can also
  exhaust its truncated list without ever reaching the cap. This is a
  contract gap (§5's signature), not a coding mistake this task can fix
  inside its own `files:` fence — the callback needs a way to page through
  all items oldest-first, or `StorageInventory` needs a dedicated
  oldest-first paged reader.
