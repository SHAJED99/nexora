# E08-T01 · Storage schema migration v14

> 🧍 **This task fires the `db_schema_migration` human gate** (`harness.yaml`
> `human_gates`, rule 3). The tables and columns below are the contract the
> human approves; the builder does not add, rename or widen any of them.

## 1. Goal
Give every later E08 task one durable, migrated place to keep what the
storage manager *knows* (per-item access signals), what the user *chose*
(the active policy), and what the policy *decided and why* (the explanation
log) — so no later task invents a table under time pressure.

## 2. Business logic
- **Three tables, one schema version bump (13 → 14).** `FR-STORE-004` needs
  a persisted mode choice, `FR-STORE-005` needs per-item access signals that
  exist nowhere in the current schema, and `FR-STORE-007` needs a record of
  the decisions a policy made in order to explain them later. All three are
  new, additive, and land together so exactly one migration step exists.
- **Additive only.** `docs/conventions.md` "Schema migrations": a migration
  step never drops a table or column holding user conversation data. This
  step creates three tables and touches nothing existing.
- **Enums are stored as `.name` strings**, never integer indexes
  (`docs/conventions.md` "Enums") — the same rule `messages.deliveryState`
  and `relay_packets.deliveryState` already follow.
- **The migration must be atomic.** `database.dart`'s existing `onUpgrade`
  already wraps its steps because Drift bumps `user_version` *after*
  `onUpgrade` returns (see the comment at `database.dart` ~line 177) — this
  step joins that existing wrapping, it does not invent a second scheme.
- **`storage_policy_settings` is a single-row table** (`id` always `1`), the
  simplest correct shape for app-wide settings and the one that makes
  "exactly one active policy" an invariant of the schema rather than of
  every reader.
- **`budget_bytes` is nullable and stays NULL until a human answers
  `OQ-E08-1`.** The column exists so the later tasks have somewhere to put
  the denominator; this task does not choose a default for it. A NULL
  budget means "no denominator known", which every reader must render as
  *unmeasured*, never as 0 or 100%.

## 3. What this task does
- Creates `lib/core/persistence/storage_tables.dart` with three Drift
  tables: `StorageItemStats`, `StoragePolicySettings`, `StorageDecisions`.
- Registers them on `AppDatabase`, bumps `schemaVersion` 13 → 14, and adds
  the `from < 14` step to the existing `onUpgrade` chain.
- Regenerates `database.g.dart` (`dart run build_runner build`).
- Extends `test/core/persistence/database_migration_test.dart` with a
  v13 → v14 additive-upgrade test in the same shape as
  `test_EARS_GROUP_5_v12_upgrades_to_v13_additively`.
- **Retires E07's carried-forward migration-test advisory** (E07 tracker
  §Carried-forward observations, 2026-08-31, S4): that note asked whichever
  task first adds a schema version beyond 13 to assert the added set is
  *exactly* the expected tables/indexes, not merely that they exist. This
  task is that task; the new test asserts exact set equality of added
  tables and indexes, and the observation is then retired.

## 4. What this task does NOT do  ← the scope fence
- **Does not read, write or delete a single row of user data.** No
  inventory scan, no policy evaluation, no deletion. Tables only.
- **Does not touch `messages`, `delivery_states`, `relay_packets`,
  `routes`, `sync_cursors` or any group/crypto table** — not a column, not
  an index, not a comment. E08 manages lifecycle; it does not reshape what
  E05/E06/E07 store.
- **Does not add a `pinned` / `important` / `keep` column anywhere.**
  "Importance" is an undefined term in the spec (`OQ-E08-4`); inventing a
  column for it here would decide that question by schema.
- **Does not pick a default `budget_bytes`, retention age, or size cap.**
  Those are `OQ-E08-1`/`OQ-E08-2`, human calls.
- Does not add a dependency. `drift_dev`/`build_runner` are already dev
  dependencies from E07-T01; nothing new is introduced.
- Does not backfill `storage_item_stats` from existing `messages` rows —
  an absent stat row means "never observed", which is the honest reading
  and the one `E08-T03` is built against.

## 5. Contract

### Data
Migration step `from < 14` — three new tables, no changes to existing ones.

**`storage_item_stats`** — the access signals `FR-STORE-005` needs and the
schema currently has nowhere to put.

| column | type | null | notes |
|---|---|---|---|
| `item_kind` | TEXT | no | a `StorageItemKind.name` string (E08-T02 owns the enum) |
| `item_id` | TEXT | no | the owning row's primary key in its own table |
| `last_accessed_at` | INTEGER | **yes** | epoch-ms; NULL = never observed, never 0 |
| `access_count` | INTEGER | no | default `0` |

PK `(item_kind, item_id)`. Index `idx_storage_item_stats_last_accessed`
on `(last_accessed_at)`.

**`storage_policy_settings`** — `FR-STORE-004`'s three modes.

| column | type | null | notes |
|---|---|---|---|
| `id` | INTEGER | no | PK, always `1` — single-row table |
| `mode` | TEXT | no | a `StorageMode.name`: `smart` \| `olderThanDays` \| `overSizeMb`. Default row inserted by the migration with `smart` (FR-STORE-004: "Smart Mode (default)") |
| `older_than_days` | INTEGER | yes | NULL unless `mode == olderThanDays` |
| `max_bytes` | INTEGER | yes | NULL unless `mode == overSizeMb` |
| `budget_bytes` | INTEGER | yes | the denominator; **stays NULL** until `OQ-E08-1` is answered |
| `updated_at` | INTEGER | no | epoch-ms |

The migration inserts the single default row (`id=1, mode='smart',
updated_at=<now>`, everything else NULL) — the app must never have to cope
with an absent settings row.

**`storage_decisions`** — `FR-STORE-007`'s "what did the policy decide, and
why".

| column | type | null | notes |
|---|---|---|---|
| `id` | TEXT | no | PK, locally minted |
| `decided_at` | INTEGER | no | epoch-ms |
| `mode` | TEXT | no | the `StorageMode.name` in force when the decision was made |
| `category_key` | TEXT | no | a stable machine key (e.g. `relayCache`, `messages`) — **not** display copy |
| `item_count` | INTEGER | no | |
| `bytes` | INTEGER | no | real measured bytes, never estimated |
| `reason_code` | TEXT | no | a `RetentionReason.name` (E08-T04 owns the enum) |
| `reason_detail` | TEXT | yes | the reason's parameter as text (e.g. `45` for "older than 45 days") |
| `outcome` | TEXT | no | a `DecisionOutcome.name`: `planned` \| `applied` \| `skipped` |

Index `idx_storage_decisions_decided_at` on `(decided_at)` — the
explanation surfaces read most-recent-first.

> `category_key` and `reason_code` are machine keys on purpose. The user-
> facing strings ("Older than 45 days", "No longer required") are design
> copy and live in the design contract `E08-T07` writes — a table is not a
> place to store copy that the design gate must match character for
> character.

## 6. Risks
- `database.g.dart` is generated. Hand-editing it is the fastest way to a
  broken build that looks like a merge conflict; regenerate.
- The default-row insert must be inside the same atomic wrapping as the
  `createTable` calls, or a failed-then-retried migration can leave the
  settings table created and empty.
- `E07-T01`'s own test asserted *existence* of the added entities, not
  *exactly* the added set. Copying its shape without tightening it repeats
  the advisory this task is supposed to retire.
- A fresh install runs `onCreate`, not `onUpgrade` — the default settings
  row must exist on both paths, and a test must prove the fresh-install
  path too, not just the upgrade path.

**Deviations from spec/design:**
- **Test-order note (not a spec deviation):** the implementation checklist's
  "tests written FIRST and failing" is satisfied in the sense that
  `implement/SKILL.md` intends -- `storage_tables_test.dart` and the new
  cases in `database_migration_test.dart` were written and run red before
  `flutter analyze`/full-suite green was declared -- but the very first
  `storage_tables.dart` draft (the Drift table *class* declarations) had to
  exist and be codegen'd before any test referencing
  `StorageItemStatsCompanion` etc. could even compile, let alone fail for
  the right reason. This mirrors the brownfield/characterization exception
  in `skills/implement` §2: a schema task's tests cannot assert against
  types that don't exist yet, so "red for the right reason" here means
  "compiles and fails on the assertions" once the table shape exists, not
  "fails to compile" beforehand. No behavior was written ahead of its test;
  only the minimal Drift type declarations were.
- **`m.database.transaction(...)` wrap on the `from < 14` step:** this
  task's own §2/§6 requires the default-row insert be atomic with the
  `createTable` calls. The immediately-preceding `from < 13` step
  (E07-T01) has no explicit transaction wrap because it has no insert to
  protect; this step does, so it follows the `from < 10` rebuild's
  explicit-wrap precedent instead (see the in-code comment at
  `database.dart`'s `from < 14` block for the full reasoning). Noted here
  because the task text's "same atomic-wrapping pattern already used for
  v12→v13" could be read as "no explicit wrap," which would leave the
  default-row insert unprotected against the exact crash-window risk §6
  itself calls out.
