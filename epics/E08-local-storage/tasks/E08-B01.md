# E08-B01 · `overSizeMb` deletes newer messages and leaves the oldest untouched

## The defect

`StorageInventory.itemsOfKind` is bounded newest-first:

```dart
// lib/core/storage/storage_inventory.dart:129-131, 167
Future<List<StorageItem>> itemsOfKind(StorageItemKind kind,
    {int limit = 500, int? olderThanEpochMs}) async { ... }
// _messageItems: 'ORDER BY created_at DESC LIMIT ?'
```

`ManualPolicy._planOverSize` pools items with **no** `olderThanEpochMs`
pushdown and **no** paging, then sorts that pool oldest-first:

```dart
// lib/core/storage/manual_policy.dart:186
pooled.addAll(await items(classTotal.kind));   // -> newest 500 only
// :188-192  pooled.sort(... a.createdAt.compareTo(b.createdAt) ...)
```

So "oldest first" is applied to *the newest 500 rows*. The genuinely-oldest
items — exactly the ones the user's policy asks to remove first — are never
in the pool at all.

This is the `apply: true` path: `StorageManager.runPass` passes
`allowedKinds: {message}` for a manual mode
(`storage_manager.dart:141`), so `RetentionExecutor` really deletes these
rows.

## Repro
1. Fresh in-memory `AppDatabase`. Seed 600 `messages` in one conversation,
   all delivery-state `stored`, all dormant (older than the 14-day active
   window), 2000 bytes each — ids `m-00000` (oldest) … `m-00599` (newest).
   Total 1 200 000 bytes.
2. `StorageSettingsRepository.setMode(StorageMode.overSizeMb, maxBytes: 1048576)`.
3. `StorageManager.runPass(nowEpochMs: now)`.

## Expected
FR-STORE-004 / `design/screens/settings-storage.md`'s SS11 — "Delete old
data when storage exceeds X MB". The ~76 items removed to get under the cap
must be the **oldest** ones: `m-00000` … `m-00075`.

## Actual
Reviewer's own probe (`test/core/storage/sweep_probe_test.dart`, scratch,
not committed):

```
overSizeMb selected 76 items; oldest id in db is m-00000, newest is m-00599
  min selected id: m-00100  max selected id: m-00175
```

`m-00000`…`m-00099` — the hundred oldest messages, the ones the policy
exists to remove — are not considered at all, and survive. The 101st through
176th oldest are permanently deleted in their place.

The error scales with history size, and the untouched oldest block stays
unreachable across passes until the total row count falls back under 500 —
so each pass eats further into newer messages while the oldest are still
sitting there.

## Severity
**S1** — irreversible deletion of user data the active policy did not
select. This app has no server copy (ADR-0005), so a wrongly-deleted message
is gone. Not merely "the wrong window": the selected set and the correct set
are disjoint.

**Reachability, stated plainly for the 🧍 `bug_priorities` gate:** no
shipped UI can set a manual mode today — `E08-T09` (the storage settings
screen) is prospective and unsharded, and `setMode` has no caller in `lib/`.
The defect is therefore not reachable by a user of the current build. It
becomes reachable the moment T09 ships. That is priority information; the
severity of the code path itself is unchanged.

## Fix direction
Give the enumeration an oldest-first, paged mode rather than widening
`limit` (which just moves the cliff). Two honest shapes:
- **(a)** add an `oldestFirst: bool` (or an explicit `order`) parameter to
  `itemsOfKind`, and page in `_planOverSize` until `runningBytes <= maxBytes`
  or the kind is exhausted. Keeps `StorageInventory`'s "bounded by
  construction" property, which is correct and should not be given up.
- **(b)** push the selection into SQL entirely (`ORDER BY created_at ASC`
  with a running-sum window), so no unbounded Dart list is ever built.

`E08-T05`'s §5 `items()` callback signature is part of the contract and will
need amending either way — that is the contract gap `OQ-E08-T05-1` named.

Also fold in the second half of `OQ-E08-T05-1` recorded at T05 round 2:
`runningBytes` is seeded from the SQL-summed **total** but decremented only
by pooled-item bytes, so the same truncation can exhaust the pool while
still over cap (under-planning), not only select wrong items.

## Regression test (write it first)
A test that seeds > `limit` items across a kind and asserts the selected ids
are the genuinely-oldest ones. It must fail on today's code with the exact
`min selected id: m-00100` signature above, and pass after.

## What this fix does NOT do
- Does **not** change `RetentionExecutor`'s three unconditional invariants,
  the delivery-state guard, or the transactional per-group apply path.
- Does **not** touch Smart Mode's own truncation — that is `E08-B02`, a
  different caller with a different symptom and its own regression test.
  A shared `itemsOfKind` change may make B02's fix trivial; it does not
  close B02 without B02's own test.
- Does **not** build `E08-T09`'s settings screen, or make manual modes
  reachable from the UI.
- Does **not** relax `StorageSettingsRepository`'s validation, or the 1 MiB
  `minMaxBytes` floor.
- Does **not** touch relay payload retention (`RelayEngine.reclaimPayloads`,
  E04-B02) or `lib/features/**`.
