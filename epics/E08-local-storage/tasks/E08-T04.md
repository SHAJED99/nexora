# E08-T04 · Smart Mode — the eight-factor plan

> 🟡 **Two epic-level Open Questions bind this task**: `OQ-E08-1` (the
> storage denominator — the *storage pressure* factor has no input without
> it) and `OQ-E08-4` (*importance* and *temporary status* are undefined
> terms in the spec). Both have advisory recommendations in `epic.md`. This
> task is **dispatchable before they are answered only for the six factors
> that have inputs**; the two that do not must report `unavailable` per
> EARS-STORE-10 rather than be given an invented definition.

## 1. Goal
Turn the inventory into a *plan*: which stored items Smart Mode would
remove, grouped into the categories the user is shown, each carrying a
machine-readable reason — the thing `FR-STORE-007`'s explanation surface
and `EARS-STORE-1`'s eight-factor requirement both need to exist.

## 2. Business logic
- **`EARS-STORE-1` (epic) — the eight factors are named by `FR-STORE-005`
  and all eight are addressed explicitly**, each either scored from a real
  input or reported `unavailable`:

  | # | Factor | Input in this build |
  |---|---|---|
  | 1 | age | `StorageItem.createdAt` (real) |
  | 2 | size | `StorageItem.bytes` (real, measured) |
  | 3 | file type | `StorageItemKind` (real; media kinds have no producer yet) |
  | 4 | access frequency | `storage_item_stats` from `E08-T03` (real; NULL = never observed) |
  | 5 | conversation activity | most recent `messages.created_at` per conversation (derived, real) |
  | 6 | storage pressure | **no input — needs `OQ-E08-1`'s denominator**; reports `unavailable` until then |
  | 7 | temporary status | `StorageItem.isTemporary` per `E08-T02`'s derived definition (relay payload = temporary; message = not) |
  | 8 | importance | **undefined term — `OQ-E08-4`**; reports `unavailable` until answered |

- **A factor without an input is `unavailable`, never a default.** This is
  the same standing prohibition as E04-B03's synthesized measurement: a
  factor silently scored `0.0` reads to every downstream surface as "we
  measured it and it was zero". `FactorScore` is a sum type — `Scored(v)`
  or `Unavailable(reason)` — and the plan carries which factors were
  actually available.
- **The plan is a forecast, not an act.** BRD §20/§22's own worked example
  says "**Will** remove". This task computes candidates and reasons; it
  deletes nothing and writes nothing. Execution is `E08-T06`, behind
  `OQ-E08-3`.
- **Every candidate carries a `RetentionReason`,** because `FR-STORE-007`
  requires the app to explain *why* each category was selected. A candidate
  with no reason is a bug, not a candidate — assert it.
- **Thresholds are declared constants in one place, marked tunable.**
  `NFR-SCALE-001` has no number (`A-002`'s placeholder approach covers
  group size and hop count, *not* storage — see `OQ-E08-2`). Every
  threshold this task needs lives in one `SmartModeThresholds` value object
  with a documented, human-replaceable default, so answering `OQ-E08-2`
  is a one-file change and never a rewrite.
- **Ordering is deterministic and tie-broken explicitly** — the same
  discipline `E06-T09` was reviewed against. Two runs over the same data
  produce the same plan, or the explanation surface is not reproducible.

## 3. What this task does
- `retention_plan.dart`: `RetentionReason` enum (`olderThan`,
  `rarelyAccessed`, `noLongerRequired`, `overSizeLimit`, `storagePressure`),
  `DecisionOutcome` enum (`planned`, `applied`, `skipped`), `FactorScore`
  (scored / unavailable), `RetentionCandidateGroup` (categoryKey, kind,
  itemIds, itemCount, bytes, reason, reasonDetail) and `RetentionPlan`
  (mode, groups, totalBytes, availableFactors, unavailableFactors,
  computedAt).
- `smart_mode_policy.dart`: `SmartModePolicy.plan(snapshot, stats,
  thresholds)` — the pure scoring function, no I/O, no clock reads except
  an injected `now`.
- Tests covering every factor's presence and absence, determinism, and the
  never-a-default rule.

## 4. What this task does NOT do  ← the scope fence
- **Deletes nothing, writes nothing.** Pure function in, plan out. No
  `AppDatabase` write, no file removal, no `storage_decisions` row (that is
  `E08-T06`'s, from the plan this returns).
- **Does not invent a definition for "importance" or a value for the
  storage denominator.** Both report `unavailable` until `OQ-E08-4` /
  `OQ-E08-1` are answered. Filling either in would answer a human question
  in a diff — exactly what rule 1 forbids.
- **Does not build the manual policies.** `olderThanDays` / `overSizeMb`
  are `E08-T05`'s; this file knows only Smart Mode.
- **Does not touch relay TTL.** A `relayPayload` past its own TTL is
  already `RelayEngine.reclaimPayloads`' business (E04-B02, driven by
  `E06-T06`'s coordinator). Smart Mode may *report* relay bytes as a
  category; it must not schedule, shorten or duplicate that reclaim.
- **Does not produce user-facing copy.** `categoryKey` and `reason` are
  machine keys; the strings ("Older than 45 days", "No longer required")
  are design copy owned by `E08-T07`'s contract and rendered by
  `E08-T08`/`E08-T09`. Two sources of one string is the trap `E06-T12` was
  written to avoid.
- Does not read `storage_policy_settings` (that is `E08-T05`'s repository)
  beyond receiving the already-loaded thresholds as a parameter.

## 6. Risks
- **The placeholder thresholds are the most quietly dangerous thing in this
  epic.** Whatever number is written here becomes the app's real deletion
  behaviour. Every one must be a named constant with a comment saying it is
  a placeholder pending `OQ-E08-2`, and none may appear as a literal at a
  use site.
- Scoring across heterogeneous kinds tempts a single composite score. A
  composite score cannot be explained (`FR-STORE-007`), because the reason
  is exactly the thing it collapses. Keep per-factor scores and a named
  dominant reason per group.
- `stats` keyed by a composite string is easy to get subtly wrong (`kind:id`
  vs `id`); a single canonical key helper, tested, avoids a whole class of
  silently-never-matching lookups that would make every item look unaccessed.
- `nowEpochMs` injected, always. A `DateTime.now()` inside the scorer makes
  the determinism test flaky and the explanation surface irreproducible.

**Deviations from spec/design:**
- **`SmartModePolicy.plan()` takes an additional required `items:
  List<StorageItem>` parameter, not named in §5's literal signature.** The
  contract as written (`plan({required StorageInventorySnapshot snapshot,
  required Map<String, ItemAccessStat> stats, required int nowEpochMs, int?
  budgetBytes})`) cannot satisfy the task's own goal or §8 test list:
  `StorageInventorySnapshot` (E08-T02) carries only **class-level
  aggregates** (`StorageClassTotal(kind, itemCount, bytes)` — no per-item
  `createdAt`, `bytes`, or `conversationId`), so age-based, size-based and
  conversation-activity-based candidate selection is structurally
  impossible from `snapshot` alone — there is no age anywhere in a class
  total. `stats` (E08-T03) is `storage_item_stats` only (access signals),
  not item metadata. Per-item detail exists only via
  `StorageInventory.itemsOfKind()`, which this file is contractually
  forbidden to call itself (§5 Data: "No table access at all from this
  file" — a pure function cannot also be the thing that does the async DB
  read). The only way to keep `plan()` pure **and** give it what it needs
  to select real candidates is for the caller to fetch items first (via
  `itemsOfKind`) and pass them in. This reading is also the one the
  dispatching brief pointed at directly — `E08-T02.md`'s `StorageItem` type
  is named as something this task consumes, not just
  `StorageInventorySnapshot`. This is additive (a new parameter, not a
  changed one) and does not touch any table, so it does not widen the "no
  I/O" contract — only the "exact literal signature" one. Flagged as
  `OQ-E08-T04-2` below for the record; not blocking, since the simplest
  correct reading was available and stalling the whole task to ask "should
  `plan()` take an items list" would have wasted the dispatch on a question
  with one clearly-necessary answer.
- **`importance` reports `Unavailable` unconditionally, even though the
  epic-level `OQ-E08-4` is now marked 🟢 answered** (epic.md: option (a),
  derive importance from a Trusted relationship (E02) + a never-delete rule
  for undelivered messages). This task's own body text (§2's factor table,
  §3, §4's explicit "does not invent a definition for 'importance'") was
  never updated to reflect that answer, and this task's `files:` fence
  (`retention_plan.dart`, `smart_mode_policy.dart`, its own test file) does
  not include anything from `E02`'s trust-relationship code, so building
  the derivation here would be scope creep beyond a fence I cannot widen
  unilaterally (rule 6). The task's own binding §4 scope fence — not the
  epic doc's later, unincorporated answer — governs this diff. Also
  consistent with the explicit dispatch instruction for this run: "two
  (storage pressure, importance) have no input in this build and MUST
  report Unavailable". Flagged as `OQ-E08-T04-3` below so the discrepancy
  between the epic doc and this task's own text is visible, not silently
  reconciled by picking one.
- **`RetentionPlan.mode` is a plain `String` (`'smart'`), not an enum
  spanning all three `storage_policy_settings.mode` values.** §4 states
  this file "knows only Smart Mode" and does not build the manual policies
  (`olderThanDays`/`overSizeMb` are `E08-T05`'s) — inventing a
  `StorageMode { smart, olderThanDays, overSizeMb }` enum here would
  pre-empt part of T05's own contract. A bare machine-key string matches
  `storage_tables.dart`'s own column convention (`TextColumn get mode`) and
  needs no shared enum T05 might define differently.
- **`SmartModeFactor` (the eight-factor key enum) and `ItemAccessStat` (the
  `stats` value type) are new types this task defines,** since neither is
  owned by any existing file. `ItemAccessStat` mirrors `StorageItemStatRow`'s
  two data columns exactly (`accessCount`, nullable
  `lastAccessedAtEpochMs`) rather than importing the Drift-generated row
  type directly, keeping this file free of any Drift/`AppDatabase` import
  (task §5 Data).
- **Storage pressure, when scored as "high" (`budgetBytes` supplied and the
  usage ratio at/above `storagePressureRatio`), overrides an
  already-selected `olderThan`/`rarelyAccessed`/`overSizeLimit` reason with
  `storagePressure` rather than adding a second, independent candidate
  pass.** BRD §22's own worked example folds pressure and low usage into
  one "why" together ("Storage pressure is high and these items have low
  recent usage") — read as support for pressure being the *dominant*
  explanation over a plain age/access reason when both are true, not a
  separate selection mechanism. No test in §8 exercises this path directly
  (the only pressure test is the null-budget-unavailable case); documented
  here so a reviewer knows this behaviour exists and is deliberate, not
  incidental.
