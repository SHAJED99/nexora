# E00-B01 · The release build is signed with the debug key

## 1. Goal
`flutter build apk --release` produces a **distributable** artifact when a
keystore is configured, and keeps working unchanged when one is not.

## 2. Findings

1. **`android/app/build.gradle.kts` still carried Flutter's scaffold default**
   — `signingConfig = signingConfigs.getByName("debug")`, under a literal
   `// TODO: Add your own signing config for the release build.` This is the
   generated placeholder; nothing in this project had replaced it.
2. **The consequence is not cosmetic.** An APK signed `CN=Android Debug`
   cannot be uploaded to Google Play, and cannot be updated by a
   differently-signed build later. For this app in particular, "uninstall and
   reinstall to take the update" means destroying the user's device
   cryptographic identity, their Signal sessions and their entire local
   message history (ADR-0001, ADR-0005) — `FR-TRUST-002`, which would have
   softened that, is itself one of the open release-scope gaps.
3. **Release mode itself is healthy** — worth recording, because it was the
   larger suspected risk and it turned out not to be one. The release build
   succeeds in 147.6s cold / 17.2s warm, tree-shakes icons by 99.7%, and
   produces a 62.5MB APK. No R8/minification failure against Drift codegen,
   `libsignal` or the Pigeon bindings, because `isMinifyEnabled` is not set
   and AGP therefore does not shrink. The only build warning is unrelated and
   forward-looking (`sentry_flutter` applies the Kotlin Gradle Plugin;
   "future versions of Flutter will fail to build") — not a release blocker
   now, and not this task's to fix.

## 3. What this task does NOT do
- **Does not create a keystore, a password, an alias, or any other signing
  material.** That is a `secrets_or_env_change` human gate (`harness.yaml`,
  rule 3), and a signing key generated by tooling would be both a security
  error and useless. `docs/release-signing.md` documents what the human
  generates; nothing here executes it.
- Does not wire signing into CI. That would mean putting a keystore into
  repository secrets — a separate `secrets_or_env_change` decision.
- Does not enable minification/shrinking, change `minSdk`/`targetSdk`, or
  touch the version number.
- Does not set up Play Console, the store listing, the privacy policy or the
  data-safety declaration. None of those exist; see `docs/release-signing.md`
  §What is NOT covered.
- Does not address the `sentry_flutter` KGP warning (finding 3).

## 4. Risks
- **Breaking the no-keystore path would break CI**, which has no keystore and
  needs none. Mitigated by making the signing config conditional: it is not
  even declared unless `android/key.properties` exists, so Gradle cannot fail
  on a partially-specified config. Verified both ways in §6.
- **"It built" is not "it was signed."** A release operator reading only
  Gradle's output would see success in both branches. Mitigated by naming
  `apksigner verify --print-certs` as the gate in `docs/release-signing.md`
  step 4, because it reads the artifact rather than the configuration.
  A `printSigningMode` Gradle helper was written and then **removed**: it
  could not be exercised in this environment (`android/gradle/wrapper/
  gradle-wrapper.jar` is git-ignored, so `./gradlew` is not dependable on a
  fresh clone), and documenting an unverified step is the failure mode this
  task is trying to close, not one to add.

## 5. Acceptance criteria
This task asserts no EARS criterion and claims no requirement coverage: it is
build configuration, not product behaviour, and inventing an EARS id for it
would put a false row in the traceability matrix. Its evidence is the
before/after `apksigner` output in §6.

## 6. Evidence

**Before** (`fa85bd7`, no change):
```
$ apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
Signer #1 certificate DN: C=US, O=Android, CN=Android Debug
Signer #1 certificate SHA-256 digest: 72df478c0615b789006c40e28d938d637cd78fe166a750d76cf07550ef265c80
```
(That SHA-256 is the well-known public Android debug certificate, shared by
every Android SDK install on earth. It is not a secret.)

**After, fallback path** — no `android/key.properties`, i.e. exactly what CI
and a fresh clone see:
```
$ flutter build apk --release
√ Built build\app\outputs\flutter-apk\app-release.apk (62.5MB)   [17.2s, exit 0]
```

**After, signed path** — proved with a **throwaway 30-day test keystore
generated in the session scratchpad, never committed and deleted immediately
after the check**. It exists only to prove the Gradle wiring resolves and
signs; it is not a release key and is not proposed as one:
```
$ apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
Signer #1 certificate DN: CN=E00-B01 THROWAWAY TEST KEY, O=NOT FOR RELEASE, C=US
```
Post-check: the keystore and `android/key.properties` were deleted and
`git status` confirmed clean. `git check-ignore -v android/key.properties`
confirmed the path is ignored before the file was ever written.

## Open Questions
- **OQ-E00-B01-1 — the keystore itself.** 🟡 open, and deliberately so. The
  human generates it (`docs/release-signing.md` steps 1–3) and decides whether
  this app enrols in **Play App Signing**. That choice decides whether a lost
  key is recoverable at all, and it is irreversible after the first upload.
  No advisory is offered on the key material itself; step 2 of the runbook
  states the consequence and leaves the decision where it belongs.
