# E05-B01 · The wire envelope has a consumer but no producer

## The defect
`E05-T03.md` §3 defines the wire format and states plainly who writes it:

> this task defines a minimal envelope (id, conversation_id, sequence_number,
> plaintext_payload) **that gets serialized INTO what E03 encrypts on the
> sending side (T02)** and deserialized AFTER E03 decrypts on the receiving
> side (this task)

`receive_message_use_case.dart:40-42` repeats the claim as settled fact in
the source itself ("the sending side (T02) serializes this envelope INTO the
plaintext before encrypting").

**T02 does no such thing.** `send_message_use_case.dart:123` is:

```dart
ciphertext = await _encrypt(recipientDeviceId, plaintext);
```

`plaintext` is the caller's raw bytes, passed straight through. No
`MessageEnvelope` is constructed anywhere in `lib/` outside
`receive_message_use_case.dart`'s own class declaration — `grep -rn
"MessageEnvelope(" lib/` returns only the constructor definition, and every
construction site in the repo is inside
`test/features/messaging/domain/receive_message_use_case_test.dart`, which
fabricates its own envelopes.

So the receive side's dedup key (`envelope.id`) and its ordering key
(`envelope.sequenceNumber`) are recovered from a structure the send side
never emits.

## Why the green suite did not catch it
Both tasks pass their own tests because each stands up its own half of the
seam:
- T02's tests inject an `encrypt` seam and assert sequencing/state
  transitions; the word `Envelope` does not appear in
  `send_message_use_case_test.dart` at all.
- T03's tests build a `MessageEnvelope`, serialize it, hand it to a fake
  `decrypt`, and assert dedup/ordering.

Neither test ever puts T02's output into T03's input. That is the definition
of a seam bug: task-level tests prove tasks, only the sweep proves the epic.

## Repro (reviewer-verified 2026-08-29 on `epic_05` @ `af86907`)
Throwaway probe, deleted after the run. Identity "encryption" is used — the
single most favourable case, where the receiver decrypts bytes *identical*
to what the sender encrypted, so nothing else can be blamed:

1. `SendMessageUseCase(db: <in-memory>, selfDeviceId: 'device-A',
   encrypt: (r, p) async => p, enqueue: (d, payload, pr, ttl) async
   { onTheWire = payload; return 'relay-1'; })`
2. `await useCase.call('conv-1', 'device-B', utf8.encode('hello world'))`
3. Feed `onTheWire` to `MessageEnvelope.deserialize(...)` — exactly what
   `ReceiveMessageUseCase.call` does at `receive_message_use_case.dart:200`
   with the decrypted plaintext.

**Expected** (T03 §3 step 2, FR-MSG-003/FR-MSG-004): the envelope
deserializes, yielding the sender's `id`, `conversationId` and
`sequenceNumber`, so the receiver can dedup and order.

**Actual:** probe output —
```
PROBE wire bytes = [104, 101, 108, 108, 111, 32, 119, 111, 114, 108, 100]
PROBE deserialize threw: FormatException: MessageEnvelope: truncated,
  missing id bytes or conversationId-length header
```
The bytes on the wire are the literal plaintext `hello world`. Every message
this epic can send is unreceivable by this epic's receiver.

## Second, worse failure mode: silent mis-parse
`FormatException` is the *lucky* outcome. `deserialize`
(`receive_message_use_case.dart:108-152`) trusts the first big-endian `u32`
as `idLength` and only length-checks the buffer. A raw payload that happens
to begin with small-valued bytes — entirely plausible for the binary
payloads E06 will actually send (a length-prefixed blob, a protobuf, an
image chunk) — parses "successfully" into a garbage `id`, garbage
`conversationId` and garbage `sequenceNumber`, and is then **inserted as a
real message row** at `:215-227`. Two consequences worth naming:
- a corrupt row with a nonsense conversation/order lands in the store, and
- because dedup is keyed on `messages.id` (`:203-205`), a garbage id that
  collides with an existing row causes a *legitimate* message to be silently
  dropped as a "duplicate".

There is no magic number, no version byte, and no length check that the
declared field lengths sum to the buffer size.

## Severity: S2 (major function broken, no workaround)
The epic's central value — "messages that reliably arrive exactly once, in
order" (`epic.md` §Business goal) — cannot happen at all across the two
components this epic built to do it. EARS-MSG-2 (no duplicates) and
EARS-MSG-3 (logical ordering) are demonstrated only against test-fabricated
envelopes, never against anything the product can produce. There is no
workaround short of writing the missing code.

Not S1: nothing crashes or loses data *today*, because no production caller
wires `SendMessageUseCase` to `ReceiveMessageUseCase` yet (T02 §4, T03 §4 —
transport wiring is deferred). It becomes S1 the moment E06 wires them, via
the silent-mis-parse path above.

Severity is the reviewer's call per `skills/bug-sweep`. **Priority is the
human's** (`bug_priorities` gate, rule 3) — left `TBD-human`. Reviewer's
advisory: fix before E06 starts, because E06's first act is to wire exactly
this seam, and it will otherwise be built on a false comment in
`receive_message_use_case.dart:40-42`.

## Root cause
A contract written in one task about *another* task's behaviour, with no
gate that checks the other task agrees. T03 was sharded and implemented
after T02 was already merged (`ea7c9fb` then `984f83e`), and T03's author
described the sending side's obligation in T03's own file and source. T02's
file — the binding contract for the sending side — never mentions an
envelope: its §3 step 2 says only "calls `CryptoService.encrypt(...)` to get
the ciphertext", and its §5 signature takes an opaque `plaintext`. Neither
reviewer was wrong within their own task's fences; the obligation lived in
neither `files:` list.

## Related gap in the same seam (fix together)
The two halves also disagree on the *type* crossing the transport:
- T02 hands `RelayEngine.enqueue` a `Uint8List`
  (`send_message_use_case.dart:188`).
- T03 accepts a `CiphertextMessage` object
  (`receive_message_use_case.dart:194-197`).

Nothing in the repo converts the relayed bytes back into a
`CiphertextMessage` (`SignalMessage`/`PreKeySignalMessage` reconstruction is
never called anywhere in `lib/`). Whatever fixes the envelope must also
decide, and write down, how the wire bytes are re-typed on arrival —
otherwise the same "no producer" gap simply moves one layer out.

## Proposed fix direction (builder to confirm; not prescriptive)
- Move `MessageEnvelope` out of `receive_message_use_case.dart` into a file
  both sides import, so the wire format has exactly one definition with two
  users rather than one user and a comment. (This changes `files:` for both
  T02 and T03's source — declare it.)
- In `SendMessageUseCase.call`, build the envelope from the id and
  sequence number it already assigns, `serialize()` it, and encrypt *that*.
  Note the ordering constraint this creates: today the sequence number is
  assigned **inside** the transaction at `send_message_use_case.dart:149-170`,
  *after* encryption at `:123` — but the envelope must contain the sequence
  number, so it must be known before encryption. Re-deriving the order
  safely without reintroducing the read-then-write race that T02's §6 and
  L-backend-003 are about is the real work in this fix, and it must not be
  hand-waved: reserve the number inside a transaction first, then encrypt,
  then persist, keeping the critical section free of the crypto call.
- Harden `deserialize` against the silent mis-parse: reject any buffer where
  the declared lengths do not account for the buffer exactly, and consider a
  version/magic byte so a future format change is detectable rather than
  mis-parsed.
- Correct the now-false comment at `receive_message_use_case.dart:40-42` and
  T02's §3/§5 so the contract and the code say the same thing.

- `test_EARS_MSG_2_duplicate_of_a_really_sent_message_is_dropped` — deliver
  the same real wire bytes twice; the second call returns `null` and no
  second row exists. (Today's dedup test proves this only for fabricated
  envelopes.)
- `test_EARS_MSG_3_out_of_order_delivery_of_really_sent_messages_orders_by_sequence`
  — send seq 0 and 1 from the sender, deliver in reverse, assert stored
  order.
- `test_envelope_deserialize_rejects_a_non_envelope_payload` — the silent
  mis-parse case: a raw payload whose leading bytes form plausible small
  lengths must be rejected, not turned into a row.
- The existing T02/T03 suites must stay green.
