# E05-T02 · Offline outgoing message queue

## 1. Goal
Compose a message while offline (or online), have it persist locally as
`Queued` immediately, and transition to `Sent` once E04's relay engine has
genuinely handed it off — using E03's `CryptoService` to encrypt and E04's
`RelayEngine`/`RoutingEngine` to move the bytes, without this task
reimplementing either.

## 2. Business logic
- FR-MSG-001 / EARS-MSG-1: composing a message succeeds and persists
  locally (`Queued`) regardless of connectivity — never blocks on a route
  existing. Sending is a separate, later step this use case also drives,
  but composition itself must be synchronous-feeling and always succeed
  locally.
- FR-MSG-005: the queue must survive app restart — `Queued` messages sit
  in the `messages` table (T01), not in memory, so a restart before
  sending doesn't lose them.
- `Sent` means "durably accepted into this device's relay queue" — i.e.
  `RelayEngine.enqueue()` returned successfully (the row is committed into
  `relay_packets`). It does NOT mean the message left this device, was
  transmitted over any radio, reached a first hop, or was forwarded any
  distance toward the recipient — `enqueue()` is a local, durable INSERT and
  nothing more (E04-T04, `relay_engine.dart`). Actual forwarding happens
  later, asynchronously, inside `RelayEngine.processQueue()`, which this task
  does not call and does not observe the outcome of. `Sent` is emphatically
  NOT "the recipient has it" — that's `Accepted`/`Delivered`, which require
  an ack mechanism this task does not build (E04's relay engine has no ack;
  per its own scope fence, dedup/ack is explicitly E05's job, and this task
  is the *sending* half only — the ack-receiving half, if any, would need
  E04's transport to carry an ack packet back, which is not decided/built
  here — note this honestly as a scope boundary, don't invent an ack
  protocol to fill the gap). See E05-B03: this is the corrected, single
  definition — an earlier draft of this section additionally required "the
  first hop's `processQueue()` attempt succeeded", which was never true of
  the implementation (§3 below) and has been removed as an overclaim, not
  softened.

## 3. What this task does
> **Updated by E05-B01** (the seam bug this task's own §3/§5 caused): this
> task's original text below said "calls `CryptoService.encrypt(...)` to get
> the ciphertext" of the caller's raw `plaintext` and never mentioned an
> envelope, while T03's contract stated as settled fact that this task
> serializes an envelope into the plaintext before encrypting. It didn't;
> nothing this task sent could be deserialized by T03's `ReceiveMessageUseCase`
> (E05-B01.md has the full defect/repro). Steps 1-2 below are corrected to
> state the actual obligation, implemented in `send_message_use_case.dart`
> by E05-B01.
- `SendMessageUseCase.call(conversationId, recipientDeviceId, plaintext) -> Future<Message>`:
  1. Assigns a unique id + reserves the next `sequence_number` for
     `(conversationId, senderDeviceId)` (T01's schema), persisting a
     `Queued` placeholder row in the same transaction as the reservation
     (E05-B01) — this has to happen BEFORE encryption, because step 2 below
     needs the sequence number.
  2. Builds a `MessageEnvelope` (id, conversationId, sequenceNumber,
     payload: plaintext) using `message_envelope.dart` — the wire format
     shared with T03's `ReceiveMessageUseCase` (E05-B01) — `serialize()`s
     it, and calls `CryptoService.encrypt(recipientDeviceId,
     envelope.serialize())` (E03) to get the ciphertext, NOT
     `CryptoService.encrypt(recipientDeviceId, plaintext)` directly. If no
     session exists yet with the recipient, this will throw per E03-T03's
     own contract (`establishSession` must be called first) — this task
     surfaces that as a clear `AppFailure` rather than crashing (transitioning
     the already-reserved row from step 1 to `Failed` first, per E05-B01); it
     does NOT call `establishSession` itself (session establishment needs a
     `PreKeyBundle`, which is a discovery/exchange concern this task doesn't
     own — out of scope, see §4).
  3. Persists the real ciphertext bytes over step 1's placeholder (row
     remains `Queued`; `DeliveryStateMachine` governs every state
     transition, per T01).
  4. Calls `RelayEngine.enqueue(recipientDeviceId, ciphertext,
     priority, ttl)` (E04) to hand it to the relay/transport layer.
  5. On successful enqueue (per §2: durable acceptance into this device's
     relay queue, nothing further), transitions the row to `Sent` via
     `DeliveryStateMachine`. On failure (enqueue throws or returns an
     error), transitions to `Failed`.

## 4. What this task does NOT do
- Does NOT implement X3DH session establishment — if no session exists
  with the recipient, this task surfaces a clear failure; establishing one
  (which needs the recipient's `PreKeyBundle`, itself needing a discovery/
  exchange mechanism not yet built anywhere in this codebase) is out of
  scope and flagged as an Open Question below, not silently worked around.
- Does NOT implement any ack/receipt protocol — `Accepted`/`Delivered`/
  `Stored`/`Read` states exist in T01's schema but nothing in this task
  ever writes them; that requires a receiving-side mechanism this task
  doesn't build (see §2's honest scope-boundary note).
- Does NOT implement retry-on-failure beyond what `RelayEngine` itself
  already does (route-failure retry, per E04-T04) — a `Failed` message
  here is terminal; no separate "retry queue" or exponential backoff is
  built.
- Does NOT implement incoming message handling — that's T03.
- Does NOT touch any UI/screen — that's E06's job.

## 6. Risks
- `sequence_number` assignment must be atomic against concurrent sends in
  the same conversation (two rapid taps) — use the same
  read-then-advance-in-a-transaction discipline established in E03/E04's
  counter bugs (L-backend-003: audit this reader against every other
  writer of the same counter before shipping).
- Noted by E05-T01's review (round 1): T01's `messages` table has no
  uniqueness constraint on `(conversation_id, sender_device_id,
  sequence_number)`. A naive read-then-write (`MAX()+1`) for this task's
  sequence-number assignment is exactly the L-backend-003 failure shape —
  a DB-level `UNIQUE` constraint would turn a race into a caught error
  instead of a silent duplicate/skip. Adding that constraint is a schema
  migration (🧍 human gate) and out of T01's scope, so it wasn't added
  there; consider it here if the transaction discipline alone isn't
  judged sufficient.
- Don't let a `RelayEngine.enqueue()` failure silently leave a message
  stuck at `Queued` forever with no `Failed` transition — every code path
  through this use case must end in a definite state.
- **Added by E05-B01 (review round 2, F2) — undisclosed crash-window
  hazard.** The reserve-then-encrypt-then-update flow E05-B01 introduced
  (reserve sequence number + insert `Queued` row with placeholder
  `ciphertext: Uint8List(0)`, THEN encrypt outside the transaction, THEN
  `UPDATE` the row with real ciphertext) opens a window that did not exist
  before that fix: if the process is killed between the reserve-commit and
  the ciphertext `UPDATE`, a `Queued` row with EMPTY ciphertext persists
  durably, and nothing in today's schema distinguishes it from a normal,
  healthy `Queued` row. Not fixed here — no caller wires this use case to a
  real transport yet, so nothing reads/retries `Queued` rows today — but
  flagged explicitly for whoever builds a retry/outbox scanner (E06, most
  likely): that scanner must treat a `Queued` row with empty/short
  `ciphertext` as "encryption never completed" rather than as a row merely
  awaiting relay delivery. See the header comment in
  `send_message_use_case.dart` for the same disclosure in the source.

- **Constructor shape / dependency wiring (not specified by §5's contract,

  (documented in the typedef's doc comment). This keeps this task's own
  tests focused on sequencing/state-machine/error-surfacing (this file's own
  logic) without needing to stand up a real X3DH session or a real
  `RoutingEngine`/route topology just to exercise this use case — both of
  which already have their own exhaustive test suites in E03-T03/E04-T04.
  No caller is wired to the real classes yet (task file §4: no UI/use-case

  wiring concern, not resolved by this task.** E03-T03's `CryptoService`

  invented or hidden here.
- **`priority`/`ttl` values for `RelayEngine.enqueue`** are not specified by
