# E05-T05 · Conflict resolution — security-restrictive precedence

## 1. Goal
When two devices (this device and a peer, or two of the user's own
devices via sync) disagree about a piece of security-relevant state —
trust, location sharing, membership — resolve the conflict by always
favoring the more restrictive value, never the more permissive one.

## 2. Business logic
- FR-MSG-007 / EARS-MSG-4: exactly four named precedence pairs (epic.md
  §Scope), each independently a security control:
  - `BLOCK` beats `TRUST` (blocking always wins over any trust state)
  - `LOCATION-OFF` beats `LOCATION-ON` (sharing stops if either side
    disagrees)
  - `REVOKED` beats `ACTIVE` (a revoked credential/session stays revoked)
  - `REMOVED` beats `MEMBER` (group removal wins over membership)
  - The epic's own risk note is explicit: don't assume a single generic
    "restrictive wins" rule generalizes correctly to all four pairs
    untested — each pair is its own named test case.

## 3. What this task does
- `ConflictResolver` (or four small typed resolvers, implementer's
  judgment on shape — see §6): a pure function per precedence pair,
  taking two values of that pair's type and returning the more
  restrictive one. E.g.:
  - `resolveTrust(RelationshipState a, RelationshipState b) -> RelationshipState`
    — if either side is `blocked` (E02's existing `RelationshipState`
    enum), the result is `blocked`, regardless of the other side.
  - `resolveLocationSharing(bool a, bool b) -> bool` — `false` (off) wins
    if either is `false`.
  - `resolveMembershipRevocation`/`resolveGroupMembership` — analogous,
    using whatever revoked/removed representations already exist, or
    simple bool/enum types if no richer type exists yet in this codebase
    (session revocation and group membership aren't modeled anywhere yet
    as of E05 — use the simplest honest representation, don't invent a
    richer domain model speculatively ahead of the epics that actually
    own sessions/groups, E12/E07).
- Each resolver is a small, independently testable pure function — no I/O,
  no persistence, no wiring into where conflicts are actually detected
  (that's T04's sync mechanism's job, once the gap-fill protocol exists —
  see T04's Open Question).

## 4. What this task does NOT do
- Does NOT implement conflict *detection* — figuring out that two devices
  disagree about a value in the first place is T04's sync mechanism's job
  (and, per T04's own Open Question, the gap-fill protocol that would
  surface such disagreements isn't built yet either). This task only
  provides the pure resolution function once a conflict is known.
- Does NOT wire into E02's `RelationshipRepository`, E07's future group
  membership model, or E12's future session/revocation model — those
  integrations happen when those systems exist to be wired to. This task
  is deliberately upstream of all of them: a pure, reusable precedence
  function.
- Does NOT add UI or persistence for conflict resolution — no "conflict
  detected" screen, no audit log of resolved conflicts (E13 territory if
  ever wanted).
- Does NOT generalize beyond the four named pairs — no generic
  "more-restrictive-wins" framework applied to arbitrary future state
  types without its own explicit precedence definition.

## 5. Contract

### Functions
```yaml
- signature: "ConflictResolver.resolveTrust(a: RelationshipState, b: RelationshipState) -> RelationshipState"
  purpose: "blocked beats everything; among non-blocked states, use RelationshipState's own existing ordering if E02 already defines one, else document the chosen ordering explicitly here"

- signature: "ConflictResolver.resolveLocationSharing(a: bool, b: bool) -> bool"
  returns: "false if either input is false"
  purpose: "off wins"

- signature: "ConflictResolver.resolveRevocation(a: bool, b: bool) -> bool"
  params: { a: "true = revoked", b: "true = revoked" }
  returns: "true (revoked) if either input is true"
  purpose: "revoked wins"

- signature: "ConflictResolver.resolveMembership(a: bool, b: bool) -> bool"
  params: { a: "true = removed", b: "true = removed" }
  returns: "true (removed) if either input is true"
  purpose: "removed wins"
```

## 6. Risks
- E02's `RelationshipState` has more than two values (trusted/allowed/
  unknown/blocked) — "restrictive wins" needs a real ordering among all
  four, not just a `blocked`-vs-not check, if both inputs are non-blocked
  (e.g. `unknown` vs `allowed` — which wins?). Read E02's existing domain
  model (`lib/features/trust/domain/relationship.dart`) for whether an
  ordering already exists there to reuse, rather than inventing a second,
  possibly-inconsistent one here.
- Resist building a generic/reusable "conflict resolution framework" —
  the epic names exactly four pairs; four small functions are more honest
  and more testable than one generic mechanism speculatively covering
  cases nobody asked for yet.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-MSG-4**: WHEN resolving conflicts, the system SHALL favor the
  more security-restrictive state, for each of the four named precedence
  pairs. (FR-MSG-007)

### Tests
- `test_EARS_MSG_4_block_beats_trust` — all pairwise combinations
  involving `blocked` on either side
- `test_EARS_MSG_4_trust_state_full_ordering` — every pairwise combination
  of E02's four `RelationshipState` values, asserting the documented
  ordering holds both directions (`resolve(a,b) == resolve(b,a)` —
  symmetry is itself worth asserting explicitly)
- `test_EARS_MSG_4_location_off_beats_on`
- `test_EARS_MSG_4_revoked_beats_active`
- `test_EARS_MSG_4_removed_beats_member`

None — pure functions, no observable app behavior changes in this task.
