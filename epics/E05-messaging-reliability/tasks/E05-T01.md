# E05-T01 · Message domain model + delivery-state machine + Drift tables

## 1. Goal
Give every later E05 task (outgoing queue, incoming handling, sync) one
shared, correctly-modeled `Message` entity and delivery-state machine to
build on — the schema and the state-transition rules, with no
transport/crypto wiring yet.

## 2. Business logic
- FR-MSG-002 (`F-032`, per `docs/conventions.md`): delivery state is a
  closed set — `Queued → Sent → Accepted → Delivered → Stored → Read`, or
  `→ Failed` from any pre-terminal state. Stored as the enum's `name`
  string in Drift, never an integer index.
- FR-MSG-003 / EARS-MSG-2: every message has a stable, unique id assigned
  at creation (client-generated, not server-assigned — this app has no
  server) so a duplicate packet can be recognized and dropped by whoever
  receives it (T03's job; this task only makes the id a real unique
  column).
- FR-MSG-004 / EARS-MSG-3: messages need a strictly-increasing logical
  sequence number **per conversation**, independent of arrival order —
  this is what lets T03 reorder messages that arrive out of sequence over
  the mesh. Wall-clock timestamps are NOT sufficient for this (clock drift
  across devices) — the sequence number is a separate, monotonic-per-sender
  counter.
- Keyset pagination per `docs/conventions.md`: message list queries use
  `WHERE created_at < :cursor ORDER BY created_at DESC LIMIT :n`, never
  offset-based.

## 3. What this task does
- `messages` Drift table (per epic.md's Data model): `id TEXT PK`
  (client-generated unique id), `conversation_id TEXT`, `sender_device_id
  TEXT`, `sequence_number INTEGER` (monotonic per `(conversation_id,
  sender_device_id)`), `ciphertext BLOB` (opaque — E03 already encrypted
  it before this layer sees it; this task never touches plaintext),
  `created_at INTEGER`, `delivery_state TEXT` (enum-as-string).
- `delivery_states` Drift table, if the state history itself needs to be
  queryable separately from the message's current state (e.g. "when did
  this become Delivered") — per epic.md's Data model listing it as a
  separate table from `messages`. Keep it minimal: `message_id TEXT`,
  `state TEXT`, `changed_at INTEGER`, one row per transition.
- `Message` (domain entity, `lib/features/messaging/domain/message.dart`):
  immutable value object mirroring the table's shape in domain terms.
- `DeliveryStateMachine`: a pure function/class validating and applying
  state transitions — `canTransition(from, to) -> bool` and
  `transition(current, to) -> DeliveryState` (throws on an illegal
  transition, e.g. `Read → Queued`). This is the single place transition
  legality is decided; T02/T03/T06(future) all call through it rather than
  writing `delivery_state = X` directly.

## 4. What this task does NOT do
- Does NOT implement the outgoing queue, sending, encryption, or transport
  wiring — that's T02.
- Does NOT implement incoming message handling, dedup, or reordering logic
  — that's T03. This task only provides the schema/columns
  (`id`/`sequence_number`) those algorithms will use; it does not
  implement dedup or reorder itself.
- Does NOT implement multi-device sync or `sync_cursors` — that's T04.
- Does NOT implement conflict resolution — that's T05.
- Does NOT decrypt or inspect `ciphertext` — this layer, like E04's relay
  engine, only ever moves/stores opaque bytes.

## 5. Contract

### Data
Migration: new `messages` and `delivery_states` tables (schema version
bump, additive):
- `messages` — `id TEXT PK`, `conversation_id TEXT`, `sender_device_id
  TEXT`, `sequence_number INTEGER`, `ciphertext BLOB`, `created_at
  INTEGER`, `delivery_state TEXT`. Index on `(conversation_id, created_at)`
  for the keyset-paginated query.
- `delivery_states` — `message_id TEXT`, `state TEXT`, `changed_at
  INTEGER`, PK `(message_id, state)` (a state should only be recorded once
  per message in the normal case; revisit if retries prove that wrong,
  don't build retry-state history speculatively here).

### Functions
```yaml
- signature: "DeliveryStateMachine.canTransition(from: DeliveryState, to: DeliveryState) -> bool"
  purpose: "Pure predicate — is this transition legal per the closed-set state graph"

- signature: "DeliveryStateMachine.transition(current: DeliveryState, to: DeliveryState) -> DeliveryState"
  returns: "to, if legal; throws StateError with both states named, if not"
  purpose: "The one call site that mutates delivery state — never write delivery_state directly elsewhere"
```

## 6. Risks
- Getting the state graph wrong (e.g. allowing `Stored → Sent`) silently
  breaks every later task's assumptions — write an exhaustive test matrix
  over every `(from, to)` pair, not just the happy path, so illegal
  transitions are provably rejected, not just untested.
- `sequence_number` must be assignable without a live transport connection
  (T02 needs to assign it at compose time, offline) — don't design it as
  something only a "server" or a connected peer could hand out.
