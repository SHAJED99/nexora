# E05-T03 · Incoming message handling

## 1. Goal
When a ciphertext packet arrives (via E04's `TransportService.incomingData`
or a relay hand-off), decrypt it, recognize and drop duplicates, and store
it so it displays in the correct logical order even if the underlying
packet arrived out of sequence — the receiving-side mirror of T02.

## 2. Business logic
- FR-MSG-003 / EARS-MSG-2: a duplicate packet (same message id already
  stored) must not create a second row or a second visible message.
  Idempotency is keyed on T01's `messages.id` (client-generated at compose
  time, carried through ciphertext metadata — see §5 for exactly what
  travels alongside the ciphertext).
- FR-MSG-004 / EARS-MSG-3: messages display in logical order
  (`sequence_number` per `(conversation_id, sender_device_id)`, T01's
  schema) regardless of the order packets physically arrived in. This
  task's job is to persist correctly; actual UI ordering/display is E06's
  concern, but the data must be queryable in the right order once stored.

## 3. What this task does
- Define the wire envelope this task expects to receive: NOT just raw
  ciphertext bytes — decrypt needs to know the sender's device address
  (already available from `TransportService.incomingData(deviceId)`'s
  stream key) and the message needs its `id`/`conversation_id`/
  `sequence_number` to dedup/order correctly. Since E03's `CryptoService`
  only encrypts/decrypts opaque plaintext bytes (it doesn't define message
  structure), this task defines a minimal envelope (id, conversation_id,
  sequence_number, plaintext_payload) that gets serialized INTO what E03
  encrypts on the sending side (T02) and deserialized AFTER E03 decrypts
  on the receiving side (this task) — encryption still covers the whole
  envelope, so nothing about conversation_id/sequence_number is exposed to
  a relay (FR-ROUTE-003 still holds; only the two encryption endpoints
  ever see the envelope's plaintext fields).
- `ReceiveMessageUseCase.call(senderDeviceId, ciphertext) -> Future<Message?>`:
  1. `CryptoService.decrypt(senderDeviceId, ciphertext)` (E03) →
     plaintext envelope bytes.
  2. Deserialize the envelope → `(id, conversationId, sequenceNumber,
     payload)`.
  3. If `id` already exists in `messages`, return `null` (duplicate,
     dropped) — no second row, no second delivery-state transition.
  4. Otherwise persist a new row: `delivery_state: Accepted` (received and
     decrypted successfully — the receiving-side equivalent of T02's
     `Sent`), using `sequence_number` from the envelope for correct
     ordering, not arrival order.
  5. Return the new `Message`.

## 4. What this task does NOT do
- Does NOT implement `Delivered`/`Stored`/`Read` transitions — those are
  UI/application-level events (E06: message shown in the chat list =
  `Delivered`; user opens the conversation = `Read`; `Stored` may map to
  successful local persistence, arguably achievable here, but is left to
  whichever later task actually defines what "Stored" distinctly means
  beyond "the row exists" — noted as an Open Question below rather than
  guessed at).
- Does NOT implement any transport-layer wiring (subscribing to
  `TransportService.incomingData` for every connected device) — that's a
  scheduler/coordinator concern for whichever epic actually starts the
  app's messaging loop (E06, most likely). This task is a pure use case:
  given sender + ciphertext, produce a `Message?`.
- Does NOT implement group message envelopes/Sender-Keys — 1:1 only,
  matching E03's own scope (Sender-Keys is E07's job).
- Does NOT re-derive or second-guess E04's routing — this task doesn't
  know or care how the bytes arrived, only that they did.

## 5. Contract

### Envelope format (new, minimal — defined by this task)
A simple length-prefixed or JSON-ish binary structure is acceptable;
choose the simplest correct encoding (e.g. a small `MessageEnvelope`
class with a `serialize()`/`deserialize()` pair using fixed-width fields
for id/conversationId/sequenceNumber followed by the payload bytes) —
don't add a general-purpose serialization framework dependency for this.

### Functions
```yaml
- signature: "ReceiveMessageUseCase.call(senderDeviceId: String, ciphertext: CiphertextMessage) -> Future<Message?>"
  returns: "the newly-persisted Message, or null if this id was already stored (duplicate, correctly dropped)"
  purpose: "Decrypt, dedup, and correctly-ordered persistence of one incoming packet"
```

## 6. Risks
- The dedup check (`id` already exists?) and the insert must be atomic
  (a transaction) — two near-simultaneous deliveries of the same duplicate
  packet (plausible if E04's relay hands off the same packet twice under
  some retry path) must not both pass the "not found" check before either
  inserts, or a duplicate slips through. Same class of race this project
  has hit before (L-backend-003's lineage) — be paranoid here specifically.
- Don't assume packets from ONE sender arrive in one connection/stream —
  `sequence_number` ordering must be correct even if two packets from the
  same sender arrive on separate `processQueue()` hand-offs at different
  times, which is the whole point of this task existing.
