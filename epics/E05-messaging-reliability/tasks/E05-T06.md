# E05-T06 · The content-kind discriminator

## 1. Goal

A receiver can tell what a message **contains**. Today both encrypted
envelopes carry an opaque payload that is text purely by convention, and
that convention is the only thing making it readable — so attachments, voice
notes and location-in-chat are unbuildable (ADR-0009 §Context).

This task builds the discriminator **and nothing else**.

## 2. Business logic

ADR-0009 (accepted, human-decided 2026-09-28) settles the design. The two
constraints that shape every line below:

1. **The discriminator must live inside the encrypted envelope.** The
   frame-level `PayloadType` is relay-visible by design, and the control-kind
   byte is read *pre-decrypt* (`inbound_pipeline.dart:1062` does
   `final int controlKind = frame.payload[0];` unconditionally). A content
   type in either position would disclose "this is a voice note" to every
   relay on the path — a direct regression against FR-ROUTE-003/FR-ROUTE-004.
2. **The working text path must produce byte-identical output.** Not merely
   compatible — identical. This is what makes the change safe to ship before
   any attachment feature exists: the only path that runs today never
   executes any new encoding branch.

## 3. What this task does

### Wire layout

The kind byte is inserted immediately after the version byte; every
subsequent field keeps its order and shifts by exactly one.

| | v1 (unchanged) | v2 |
|---|---|---|
| `MessageEnvelope` | `[u8 0xE5]…` | `[u8 0xE6][u8 kind]…` |
| `GroupMessageEnvelope` | `[u8 1]…` | `[u8 2][u8 kind]…` |

The asymmetry is pre-existing and deliberate: `MessageEnvelope`'s version
field is a **magic sentinel** (`0xE5`), not a counter, so its v2 is a second
accepted sentinel `0xE6`. `GroupMessageEnvelope` uses a real monotonic
version, so its v2 is `2`. Both validated with strict `!=` before; both
become a two-value known-set check.

### Kind values

`1 = text` · `2 = image` · `3 = file` · `4 = voice` · `5 = location`

`text` is defined so the decoder is total, but is **never emitted** as a v2
kind byte — a text message is always a v1 envelope.

### The four rules

- **Emit v1 for text** — byte-identical to today.
- **Emit v2 only for non-text.**
- **Decode v1 as text**, unconditionally.
- **Unknown kinds are neither guessed nor silently dropped.** No inference
  from payload shape, filename, magic bytes or MIME sniffing. The envelope
  parses, the raw byte is preserved in `unknownKindWireValue`, and `kind`
  reports `null`. A caller that cannot render it must say so — which copy it
  says is an open Rule-2 decision (§9).

### Local persistence

Additive **v24 → v25**: a nullable `kind` column on `messages`. `null` means
text, covering every existing row. No backfill is attempted or possible.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT emit a v2 envelope from anywhere.** No call site changes. There
  is no non-text sender in this codebase yet; building one is a separate
  task. `SendMessageUseCase` and `SendGroupMessageUseCase` are untouched.
- **Does NOT render anything.** No UI file is in `files:`. The unknown-kind
  placeholder copy is explicitly deferred to a human (§9) and no
  provisional string is invented for it.
- **Does NOT touch `PayloadType`, the control-kind registry, relay
  behaviour, sender-key handling or the Double Ratchet.** ADR-0009's own
  scope fence. The kind byte lives inside already-encrypted plaintext, so
  relays observe nothing new.
- **Does NOT design attachment transfer, chunking, thumbnailing or a media
  store.** Separate decisions, explicitly outside ADR-0009.
- **Does NOT backfill `messages.kind`.** Impossible and unnecessary: `null`
  already means text.
- **Does NOT write `messages.kind` from any producer.** The column exists
  for the writer a future attachment task will add.

## 7. Risks

- **The text path could stop being byte-identical.** This is the risk that
  matters most, because it would change behaviour for every existing peer.
  Pinned by `..._byte_identically_to_v1`, which asserts against a literal
  expected byte list, not against a re-serialization.
- **An unknown kind could be silently treated as text**, which is exactly
  the silent-mis-parse class `E05-B01` already cost this project once.
  Pinned by `..._preserved_not_guessed_and_not_dropped`, which asserts
  `kind` is `null` *and* that the raw byte survives.
- **The migration could be non-additive.** Pinned by the v24→v25 test's
  surviving-row assertion.

     future step alters `messages` unexpectedly.

## 9. Open Questions

- **OQ-E05-T06-1 — the unknown-kind placeholder copy.** 🧍 **Rule-2 human
  decision, deliberately unresolved.** When a receiver decodes a v2 envelope
  whose kind byte it does not recognise, the message is preserved and must be
  rendered as a distinct placeholder. ADR-0009 requires that string to read
  as distinct from both `(unable to decrypt this message)` and
  `Message hidden — contact is blocked`, because all three mean different
  things and conflating them makes the app misreport its own reason. **No
  string is invented here**, and nothing in this task's diff renders one —
  the codec reports `kind == null` plus the raw byte and stops. The options
  and their evidence are in the hand-back that accompanied this task.
