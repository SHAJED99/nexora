# E05-B03 · `Sent` means less than the task file says it means

## The defect
`E05-T02.md` §2 defines the state:

> `Sent` means "handed to E04's relay engine successfully" (i.e.
> `RelayEngine.enqueue()` accepted it **and the first hop's `processQueue()`
> attempt succeeded**)

`E05-T02.md` §3 steps 4–5 define it differently:

> 4. Calls `RelayEngine.enqueue(...)` … 5. **On successful enqueue**,
> transitions the row to `Sent`.

The implementation follows §3, which is correct — §3 is the binding contract
section. But §3's meaning is materially weaker than §2's, and §2 is the
sentence a future reader (E06's UI author, deciding what a checkmark means)
will find first.

`RelayEngine.enqueue` (`relay_engine.dart:106-127`) is a bare Drift INSERT
into `relay_packets`. It consults no route, opens no connection, and touches
no radio. Barring a disk/constraint error it cannot fail. Therefore, at
`send_message_use_case.dart:187-195`:

- **every** message becomes `Sent` — with the device in airplane mode, with
  no peer in range, with no route to the recipient in the `routes` table;
- the `catch` branch that transitions to `Failed` (`:190-195`) is
  **unreachable in production**. Every test that exercises it does so by
  injecting a throwing `enqueue` seam
  (`send_message_use_case_test.dart:152`). No real code path reaches it.

So `messages.delivery_state` has seven values of which the send path can, in
practice, only ever produce one after `queued`, and that one asserts
something that has not happened.

## Why it is a defect and not just wording
Two concrete consequences:

1. **A user-facing lie, one epic away.** E06 renders delivery state. Under
   the current behaviour a message composed on a plane with no peers within
   a kilometre displays as `Sent` the instant it is composed. That is a
   worse failure than showing nothing, because it suppresses the user's
   retry instinct at exactly the moment retrying matters.
2. **A dead failure path is an untested failure path.** The one branch
   responsible for surfacing "this did not work" is proven only against a
   fake. Whatever eventually *can* fail (E05-B02's coordinator, a real
   transport error) will exercise this code for the first time in
   production.

Note the interaction with **E05-B02**: today nothing calls `processQueue()`
at all, so §2's stricter definition is not merely unimplemented — it is
currently unimplementable. These two should be reasoned about together.

## Repro (reviewer-verified 2026-08-29 on `epic_05` @ `af86907`)
1. Construct `SendMessageUseCase` with a real `AppDatabase` and a real
   `RelayEngine` whose `RoutingEngine` has **no routes recorded** and whose
   `send` callback is never reachable (no route ⇒ no forward attempt).
2. `await useCase.call('conv-1', 'device-B', <bytes>)`.

**Expected**, per `E05-T02.md` §2: `Sent` requires "the first hop's
`processQueue()` attempt succeeded". With no route, no first hop succeeded,
so the row must not read `Sent`.

**Actual:** the returned `Message.deliveryState` is `DeliveryState.sent` and
the `messages` row reads `sent`. Traceable statically without a probe:
`enqueue` (`relay_engine.dart:106-127`) performs one INSERT and returns an
id; `send_message_use_case.dart:188-189` awaits it and immediately applies
the `sent` transition. No route lookup occurs on this path — route selection
happens later, inside `processQueue()`, which this path never invokes.

## Severity: S3 (broken, but there is a workaround)
There is a workaround, and it is the honest reading of the delivered code:
treat `Sent` as "accepted into the local relay queue", and do not render it
as a delivery signal until an ack mechanism exists. E06 can be written
correctly against that meaning. Nothing malfunctions, nothing is lost, and
the message does eventually forward once E05-B02 is fixed.

Not S4: it is neither cosmetic nor minor — it is a state-machine value whose
documented meaning and actual meaning differ, in the one part of the system
whose entire purpose is "did this message get there", plus a permanently
dead error branch.

Severity is the reviewer's call per `skills/bug-sweep`. **Priority is the
human's** (`bug_priorities` gate, rule 3) — left `TBD-human`. Reviewer's
advisory: cheapest to settle now, while there is no UI depending on either
reading; the cost of settling it later is a semantics change under a shipped
checkmark.

## Root cause
A task file that defined the same term twice, in two sections, with two
meanings — and a review process that (correctly) checks the implementation
against §3 without also checking §2 and §3 against each other. T02's reviewer
did spot the contradiction and recorded it as observation 1 for this sweep,
which is why it is here rather than lost; the gap is that nothing forced it
to be reconciled before the epic gate.

## Proposed fix direction (builder to confirm; not prescriptive)
🧍 **HUMAN DECISION RECORDED (2026-08-29): Option A.** Sent means "durably
accepted into this device's relay queue" — NOT "left the device" and NOT
"delivered". This is documentation/semantics only; the existing behaviour
(transition to `Sent` on successful `RelayEngine.enqueue()`) is already
correct under this reading and is unchanged by this fix. Options B and C
are explicitly NOT implemented (no coordinator, no new state, no per-packet
forward-outcome reporting).

🧍 **The choice is the planner's/human's, not the builder's** — it decides what
a delivery state means to a user, which is product semantics:

- **Option A — weaken §2 to match §3 and the code (cheapest).** Redefine
  `Sent` as "durably accepted into this device's relay queue". Requires:
  editing §2; renaming nothing; and honestly documenting that no state in
  the current implementation means "left the device". The dead `Failed`
  branch stays as defence for real DB errors, documented as such.
- **Option B — implement §2 as written.** `Sent` is applied only after a
  first-hop forward attempt succeeds. This cannot be done inside
  `SendMessageUseCase.call` as it stands — the forward happens in
  `processQueue()`, asynchronously, and no ack exists (E04-T04 §4, T02 §4).
  It requires the coordinator from E05-B02 to report per-packet forward
  outcomes back to the message row, which is real design work, not an edit.
- **Option C — add an intermediate state.** Keep `Sent` = enqueued, and let
  the coordinator advance to the existing `accepted` (or a new `forwarded`)
  on first-hop success. Note that `DeliveryStateMachine`'s happy path
  (`delivery_state_machine.dart:30-37`) already permits `sent -> accepted`,
  so C may need no state-machine change — but `accepted` is currently the
  receiving side's initial state (`receive_message_use_case.dart:225`), so
  reusing it would overload the term across the two directions. Check that
  before choosing C.

Whichever is chosen, `epic.md` and `E05-T02.md` §2 must end up stating one
definition, and the source comment at `send_message_use_case.dart:38-41`
("every code path ends in a definite `Sent` or `Failed` state") must not
imply a delivery guarantee it does not provide.

## Regression test (required before this closes)
Shape depends on the option chosen:
- **Option A:** `test_sent_means_enqueued_not_delivered` — assert with a real
  `RelayEngine` and an empty routing table that the row reads `sent`, and
  pin the *documented* meaning in the test name so the next reader cannot
  mistake it. Plus a test that the `failed` branch still fires on a genuine
  DB error (not only on an injected seam), or an explicit note that it
  cannot, recorded in T02 §9.
- **Option B/C:** a test that a message with no route does **not** reach the
  delivery-asserting state, and does reach it after a route is recorded and
  one forward pass succeeds. Must fail on `af86907`.
