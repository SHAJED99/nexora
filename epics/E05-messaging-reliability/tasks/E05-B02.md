# E05-B02 · The relay queue has no driver

## The defect
`RelayEngine` (E04-T04) exposes three lifecycle methods that must be called
periodically for the store-and-forward mesh to function: `processQueue()`
(forward one pass of queued packets), `sweepExpired()` (retire past-TTL
packets), and `reclaimPayloads()` (E04-B02: null out third-party ciphertext
past its TTL).

`grep -rn "processQueue\|sweepExpired\|reclaimPayloads" lib/ --include=*.dart`
returns **zero call sites** outside `relay_engine.dart` itself and doc
comments. Nothing in the product ever drives the queue.

This was a known, explicitly-handed-off obligation, not an oversight nobody
saw coming. `E04-B02.md`'s approved review, advisory #2, states it:

> Nothing calls `reclaimPayloads()` in production yet — but nothing calls
> `sweepExpired()` either, and production wiring is explicitly a later epic
> … the retention *mechanism* is delivered and proven, while the retention
> *guarantee* only becomes real **once E05 wires both onto a scheduler**.
> … flagged for the E04→development human gate rather than fixed here.

E05 is that epic. None of E05-T01…T05's `files:` blocks contain a scheduler,
a coordinator, or any caller; none of their §3/§4 sections mention the
obligation. The handoff was written down at one epic's gate and dropped at
the next epic's planning.

## Why it matters inside E05, not just for E04
This is not merely E04's unfinished business. It breaks an **E05 epic-level
EARS criterion**:

> **EARS-MSG-1**: WHEN a message is created offline, the system SHALL queue
> it locally **and send once a route is available**. (FR-MSG-001)

T02 delivers the first half honestly — the message is persisted `Queued`,
survives restart (FR-MSG-005), and is handed to `RelayEngine.enqueue`. The
second half — *and send once a route is available* — is implemented by
`RelayEngine.processQueue()`, which nothing ever calls. A route can come and
go a hundred times and the packet never moves. As merged, E05's messages are
queued forever, by every device, in every condition.

The second consequence is E04's, still unmet: `reclaimPayloads()` is never
called, so the "ephemeral" relay-store guarantee recorded in E04's `epic.md`
§Data model (and the NFR-SEC-001 third-party-ciphertext retention argument
behind it) remains a mechanism with no schedule.

## Repro (reviewer-verified 2026-08-29 on `epic_05` @ `af86907`)
Static, exhaustive, and therefore not flaky:

1. `grep -rn "processQueue\|sweepExpired\|reclaimPayloads" lib/ --include=*.dart`
2. Discard the matches inside `lib/core/routing_engine/relay_engine.dart`
   (the definitions) and the doc-comment mentions in
   `lib/core/persistence/relay_tables.dart`,
   `lib/core/persistence/database.dart`,
   `lib/core/persistence/database.g.dart` and
   `lib/core/routing_engine/routing_engine.dart:205`.

**Expected** (EARS-MSG-1, FR-MSG-001): some production component invokes
`processQueue()` on a schedule and/or on a connectivity/route-change event,
so a queued message is forwarded once a route exists.

**Actual:** nothing remains. There is no caller, no timer, no lifecycle
hook, no stream subscription. The behavioural consequence follows directly
and needs no probe: `relay_packets` rows written by
`send_message_use_case.dart:188` are read by nothing.

## Severity: S2 (major function broken, no workaround)
The epic's headline promise — offline compose, delivery when a route
appears — does not happen. No configuration, no user action, and no existing
code path works around it; the fix is new code. It is not S1 only because
nothing is lost or corrupted: the queued rows are durable and correct, and
they will forward the moment a driver exists.

Severity is the reviewer's call per `skills/bug-sweep`. **Priority is the
human's** (`bug_priorities` gate, rule 3) — left `TBD-human`.

Reviewer's advisory, offered honestly with its counter-argument: a defensible
reading is that a scheduler is application-lifecycle work belonging to E06
(the epic that first has a running messaging loop and a UI to own it), and
that E05 delivering the mechanism is legitimate. What makes this a bug ticket
rather than a carry-forward note is that E04's merge gate already named E05
as the owner, so leaving it unrecorded a second time is how an obligation
gets lost for good. If the human decides E06 owns it, the right outcome is to
close this as deferred **with the owning task named**, not to let it go
unwritten again.

## Root cause
An inter-epic handoff recorded only in a *bug file's review advisory* and in
the E04 merge-gate note — neither of which is an input to E05's sharding.
`skills/task-sharding`'s analyze gate checks that the union of an epic's
tasks is sufficient for *that epic's* stated scope (L-process-005, applied
in E05's own analyze report, which did find two real gaps). It has no step
that asks "what did the previous epic's gate hand to this one?". That gap is
the reusable lesson here, and belongs in the retro.

## Related, same root cause — the sync cursors have no caller either
`SyncCursorService.recordLocalProgress`'s doc comment
(`sync_cursor_service.dart:113-114`) says it is:

> called whenever a message is stored (T02 on send, T03 on receive)

Nothing calls it. `grep -rn "recordLocalProgress" lib/` matches only the
declaration and doc comments; neither `SendMessageUseCase` nor
`ReceiveMessageUseCase` imports `SyncCursorService`. T04 could not have wired
it — T02's and T03's files are outside T04's `files:` fence — so this is not
a T04 defect, and T04's own EARS (MSG-5 monotonicity, MSG-6 never-throws) are
genuinely met by its tests. But the `sync_cursors` table has no writer in
product code, and the comment asserts a wiring that does not exist, exactly
as `receive_message_use_case.dart:40-42` does in E05-B01. Whatever component
ends up driving the messaging loop should advance the cursor at the same
point, and the comment must stop claiming someone already does.

## Proposed fix direction (builder to confirm; not prescriptive)
🧍 **This one needs a human decision before code.** Choosing *when* the queue
runs is an application-architecture question (a periodic timer? a
connectivity/route-change trigger? a foreground service? what interval? what
happens in the background, on Android, with the app killed?) — that is rule 3
territory (architecture + battery/OS-lifecycle policy), not a builder's pick.
Present the options with trade-offs and stop.

Once the human has chosen, the shape is roughly:
- a small coordinator in `lib/features/messaging/` that owns the tick and
  calls `processQueue()` → `sweepExpired()` → `reclaimPayloads()` in that
  order (E04-B02's review established the ordering is correctness-neutral
  but affects reclaim latency by one cycle),
- the same coordinator being the natural place to call
  `SyncCursorService.recordLocalProgress` on store, and the natural home for
  E05-B01's send↔receive wiring — the three findings share one root cause and
  probably one fix location. Sequence E05-B01 first: there is little point
  driving a queue whose payloads no receiver can parse.
- correct `sync_cursor_service.dart:113-114` to describe reality.

## Regression test (required before this closes)
Deferred until the human picks the trigger model, because the test must
assert the chosen contract, not a guessed one. At minimum it must prove, on a
fake clock and with no real radio, that: a message composed with no route
stays `queued` in `relay_packets`; once a route is recorded and one tick
elapses, the packet is forwarded exactly once; and `reclaimPayloads` runs on
the same schedule. The test must fail on `af86907` (it will not compile —
there is nothing to call).

## 🧍 Human decision (2026-08-29)
**Deferred to E06.** E06 is the first epic with a real running app/UI and
foreground presence — the coordinator belongs where app-lifecycle and
Android background policy naturally live, not bolted onto E05's pure domain
layer. This bug closes as deferred with the owning epic named explicitly,
per its own advisory, so the obligation is not lost a second time.
E06's planner must carry this file (and E05-B01's send/receive wiring, and
`SyncCursorService.recordLocalProgress`'s uncalled state) into E06's task
sharding as a named dependency, not rediscover it.
