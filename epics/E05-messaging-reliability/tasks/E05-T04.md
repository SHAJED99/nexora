# E05-T04 · Multi-device sync cursors

## 1. Goal
Let a user's second device figure out *what it's missing* from a
conversation without re-syncing everything — track, per device-pair, the
highest `sequence_number` each side has confirmed seeing, so a reconnect
only needs to request the gap.

## 2. Business logic
- FR-MSG-006: multi-device sync is missing-data-only, not full re-sync —
  a device that's been offline for a week doesn't re-fetch every message
  ever exchanged, only what it hasn't seen.
- FR-FB-002 (non-negotiable, same boundary as E01-T02/E04-B03): Firebase
  may only ever hold sync *metadata* — cursor positions (which
  sequence_number a device has confirmed), never message content or
  ciphertext. This task's Firebase writes are exactly analogous to
  `FirebaseMetadataService`'s existing pattern (best-effort, bounded
  timeout, never blocks local operation, fire-and-forget on failure).
- "Firebase-less operation with reconnect-time sync" (epic.md): the
  primary sync path is mesh-to-mesh (two of the user's own devices
  discovering each other directly, comparing cursors, requesting the gap
  over E04's transport) — Firebase cursor metadata is a best-effort
  assist for cases where the two devices aren't directly reachable, not
  the sync mechanism itself. This task builds the cursor bookkeeping both
  paths need; it does NOT build the actual gap-request/gap-fill protocol
  over the mesh (see §4 — that needs a message type this epic hasn't
  defined, same class of gap as T02's OQ about prekey bundle exchange).

## 3. What this task does
- `sync_cursors` Drift table (epic.md's Data model): per device-pair,
  "what's missing" bookkeeping — `local_device_id`, `remote_device_id`,
  `conversation_id`, `last_confirmed_sequence_number`, `updated_at`.
- `SyncCursorService`:
  - `recordLocalProgress(conversationId, senderDeviceId, sequenceNumber)`
    — called whenever a message is stored (T02 on send, T03 on receive) to
    advance this device's own high-water mark for that conversation.
  - `cursorFor(conversationId, remoteDeviceId) -> SyncCursor?` — reads the
    last known confirmed position for a given remote device.
  - `writeCursorToFirebase(uid, cursor)` — best-effort RTDB write of this
    device's cursor metadata (sequence numbers + conversation/device ids
    only — no content), following `FirebaseMetadataService`'s exact
    pattern (bounded timeout, catch-and-log, never throws to the caller).
  - `readRemoteCursorFromFirebase(uid, remoteDeviceId, conversationId) ->
    SyncCursor?` — best-effort read of another of the user's own devices'
    last-known cursor, for computing the gap.

## 4. What this task does NOT do
- Does NOT implement the actual gap-fill protocol — requesting specific
  missing messages by sequence-number range over E04's transport, and the
  receiving device responding with them. That needs a new message
  type/envelope this epic hasn't defined anywhere yet (flagged as an Open
  Question, same shape as T02's prekey-bundle gap). This task only
  produces the cursor data a gap-fill mechanism would need to know *what*
  is missing.
- Does NOT implement conflict resolution — that's T05. Sync cursors
  concern message *position*, not trust/security *state* conflicts.
  T05's precedence rules are a separate mechanism.
- Does NOT write message content, ciphertext, or anything beyond
  sequence-number/device-id/conversation-id bookkeeping to Firebase — any
  additional field needs its own FR-FB-001/002 justification, per
  `FirebaseMetadataService`'s own established convention.
- Does NOT implement any UI or "syncing..." indicator.

## 5. Contract

### Data
Migration: new `sync_cursors` table — `local_device_id TEXT`,
`remote_device_id TEXT`, `conversation_id TEXT`,
`last_confirmed_sequence_number INTEGER`, `updated_at INTEGER`, PK
`(local_device_id, remote_device_id, conversation_id)`.

### External services & flags
Firebase Realtime Database, same project/instance as
`FirebaseMetadataService` (E01-T02) — write path:
`users/$uid/sync_cursors/$localDeviceId/$conversationId` (or similar,
implementer's call on exact path shape, consistent with the existing
`users/$uid/devices/$deviceId` convention). No new external service, no
new dependency — reuses `firebase_database`, already in `pubspec.yaml`.

### Functions
```yaml
- signature: "SyncCursorService.recordLocalProgress(conversationId: String, senderDeviceId: String, sequenceNumber: int) -> Future<void>"
  purpose: "Advances this device's local high-water mark for a conversation"

- signature: "SyncCursorService.cursorFor(conversationId: String, remoteDeviceId: String) -> Future<SyncCursor?>"
  purpose: "Local read of the last known cursor for a device-pair"

- signature: "SyncCursorService.writeCursorToFirebase(uid: String, cursor: SyncCursor) -> Future<void>"
  returns: "void — never throws; failures caught and logged, same pattern as FirebaseMetadataService.registerDevice"
  purpose: "Best-effort cursor metadata publish"

- signature: "SyncCursorService.readRemoteCursorFromFirebase(uid: String, remoteDeviceId: String, conversationId: String) -> Future<SyncCursor?>"
  returns: "null on any failure (offline, not found, timeout) — never throws"
  purpose: "Best-effort cursor metadata read, to compute the local-vs-remote gap"
```

## 6. Risks
- Mirror E01-T02's L-backend-002 lesson exactly: any Firebase read/write
  here must have a bounded timeout — an unbounded await on a Realtime
  Database call that's queued offline must never hang a caller.
- `recordLocalProgress` must only advance the high-water mark, never move
  it backward (a delayed/out-of-order call with an older sequence number
  must not regress the cursor) — same "counter must be monotonic, audit
  every writer" discipline as this project's recurring counter lessons.
