# E15-T06 · Security Center screen

## 1. Goal
Show the user what this device has actually recorded about its own security —
revocations, trusted identities, blocks, rate-limit denials — without exposing
a single byte that `FR-DIAG-002` forbids.

## 2. Business logic

Implements `FR-DIAG-003` against `design/screens/settings-security-center.md`
(`GAP-034`). Four read-only sections over four tables that already ship:
`DeviceRevocations` (`E12`), `SignalTrustedIdentities` (`E03`), `Relationships`
filtered to blocked (`E02`), `RateLimitCounters` (`E13-T02`).

**`FR-DIAG-002` binds absolutely, and this is the most likely screen in the
product to violate it.** A record renders as *what happened, to which device
id, and when* — never *what was in it*. No key material, no session material,
no message content, no location. Not truncated, not "just the first eight
bytes", not behind an expand affordance, not in a debug build. The one
identifier that may appear is a **device id**, which is already public:
`E11-B06` made it the hex of the device's own identity **public** key, and
`devices.md` already displays device identifiers on a shipped screen.

**This screen takes no action.** No unblock, no re-trust, no revoke, no
clear-log. `EARS-DIAG-5` makes that a criterion, not a preference. Blocking and
trust decisions have exactly one home (`devices.md`); an audit surface that can
also change security state has quietly become an unreviewed control panel.

**A `SecurityRecordsRepository` exists so the SQL lives in one reviewable
place** and the controller cannot reach a raw table. It is a read-only
repository: no write method, at all.

## 3. What this task does
- Builds `SecurityRecordsRepository` — four read methods, each returning a
  narrow view model carrying **only** the fields the contract renders.
- Builds `SecurityCenterController` + `SecurityCenterView` composing
  `E15-T03`'s scaffold, rendering SC1-SC21.
- Adds its own probe test, verifies, and commits the first clean dump as the
  golden.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT render key material, session material, message content or
  location data.** Not partially, not hashed, not truncated, not behind a tap.
  The view models must not even *carry* those fields — if they are not in the
  model, they cannot leak into a widget later.
- **Does NOT offer any action.** No unblock button, no "trust again", no
  revoke, no clear-log, no swipe action, no long-press menu. A security log
  with a button is the specific wrong move this task invites.
- **Does NOT add export, share, or copy-to-clipboard.** Each is an obvious
  addition to a log screen and each is a route by which `FR-DIAG-002`-protected
  content leaves the device.
- **Does NOT build a certificates section.** The hub row's subtitle promises
  one; **this app has no certificate concept** — `ADR-0003` is a
  Signal-protocol design with identity keys, not X.509. `GAP-034` carries the
  fork with **no proposal**, and its option (b) — relabelling identity-key
  fingerprints as "certificates" — was already considered and rejected there:
  it makes the copy true by making the concept false.
- **Does NOT build a "network audits" section.** Same subtitle, same fork;
  `settings-network.md` already owns everything this app knows about its
  network.
- **Does NOT add a severity colour, a badge, a count on the hub row, or an
  alert.** `settings.md` measures no red and no badge, and `devices.md`'s
  `rgb(186, 26, 26)` carries destructive/blocked semantics a *record* does not.
- **Does NOT add filtering, sorting or search.**
- **Does NOT touch `lib/app/routes.dart`, `settings_controller.dart`,
  `settings_binding.dart` or `test/design/design_probe_test.dart`** — all four
  are `E15-T11`'s alone.
- **Does NOT change any Drift table, or `RateLimiter`, or
  `DeviceRevocationService`.**

## 5. Contract

### UI
- **Design contract:** `design/screens/settings-security-center.md`.
- Route: `/settings/security-center` (registered by `E15-T11`).
- States: `default` · `loading` · **`empty` — the expected state**, not an edge
  case: on a healthy install all four lists are empty and that is the good
  outcome; each section shows its own SC7/SC11/SC15/SC20 line independently and
  an all-empty screen must not read as broken · `error` (SC21 replaces the
  affected section's list only).
- Gate: `make design-verify SCREEN=settings-security-center --impl-probe build/design-probe/settings-security-center.json` green before the PR. Derived
  screen — golden extracted from the first clean dump (`design-fidelity` §3).

### Functions
```yaml
- signature: "SecurityRecordsRepository.revocations() -> Future<List<SecurityRecord>>"
  returns: "device id, record type, timestamp — and nothing else"
  purpose: "FR-DIAG-003 over DeviceRevocations, FR-DIAG-002-safe by construction."

- signature: "SecurityRecordsRepository.trustedIdentities() -> Future<List<SecurityRecord>>"
  returns: "device id, record type, first-seen timestamp. NEVER the identity key bytes"
  purpose: "The section most likely to be implemented wrongly; the return type
            is the guard."

- signature: "SecurityRecordsRepository.blockedPeers() -> Future<List<SecurityRecord>>"
  returns: "device id, record type"
  purpose: "Relationships filtered to blocked. Read only — blocking stays on devices.md."

- signature: "SecurityRecordsRepository.rateLimitDenials() -> Future<List<SecurityRecord>>"
  returns: "limit name, count in the current window"
  purpose: "FR-ABUSE-001's user-visible half."
```

`SecurityRecord` carries exactly: a display identifier, a record type, an
optional timestamp, an optional count. **It has no field that could hold key
material.** That is the design, not an implementation detail.

### External services & flags
None.

## 6. Risks
- **`SignalTrustedIdentities` holds the identity key.** Reading the row and
  passing it into a view model "for later" is how this screen leaks. Project
  the columns in the query; do not select the row and drop the field in the
  widget.
- **Empty looks broken.** Four empty sections on a healthy install is correct.
  The copy must make that obvious (`No device has been revoked.` reads
  differently from a bare blank).
- **Rate-limit counters are per-window.** Displaying a lifetime total would be
  wrong and is not what the table holds (`E13-B01` is about the eviction
  window). Render what the row says.
- **`fail()` in a seam is swallowed** — use call counters for the
  "no action is possible" tests.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-DIAG-4**: This screen SHALL render only device identifiers, record types and timestamps, and SHALL NOT render key material, session material, message content or location data. (FR-DIAG-003, FR-DIAG-002)
- **EARS-DIAG-5**: This screen SHALL offer no action that changes trust, block or revocation state. (FR-DIAG-003)
- **EARS-UI-9**: WHERE a Settings row's subtitle names a capability the application does not implement, the sub-screen SHALL state the absence and SHALL NOT present a control or a value for it. (FR-UI-007)
- **EARS-UI-11**: IF a read fails, THEN the system SHALL show that section's failure line and leave every other section unchanged. (FR-UI-007, NFR-REL-001)

### Tests
- `test_EARS_DIAG_4_trusted_identity_row_never_renders_key_bytes` → seeds a
  trusted identity with a **recognisable key pattern**, renders, and asserts
  that pattern appears nowhere in the widget tree. This is the falsification
  test for this screen's whole reason to exist.
- `test_EARS_DIAG_4_record_model_has_no_key_field` → a structural assertion on
  `SecurityRecord`.
- `test_EARS_DIAG_5_no_action_affordance_is_rendered` → asserts no button,
  no dismissible, no long-press menu in any of the four sections.
- `test_EARS_DIAG_5_screen_performs_no_write` → **call counters** on the
  repository seams, `expect(writes, 0)` after interacting with every row.
- `test_EARS_UI_9_no_certificates_section_is_present`
- `test_EARS_UI_11_one_section_failing_leaves_the_other_three_rendered`
- `test_EARS_DIAG_4_all_four_sections_empty_renders_their_own_empty_lines`

### Manual
1. Fresh install → four empty sections, four distinct empty lines, nothing red.
2. Block a peer on `/devices` → it appears here, with no way to unblock it here.
