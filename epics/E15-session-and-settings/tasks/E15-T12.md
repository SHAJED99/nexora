## 1. Goal
Give `SignOutUseCase` a real, non-blocking best-effort remote device-revoke
call and a real GetX-aware teardown closure in production — closing the gap
between what `Q-SEC-009`(b)/`Q-FUNC-010` answered and what the code actually
does on sign-out.

## 2. Business logic
Implements the human's answer to `Q-SEC-009`(b) (`spec/questions.md`): on
sign-out, call `DeviceRevocationService.revoke(uid, deviceId)` — best-effort,
non-blocking, never allowed to leave the local wipe half-done or fail the
sign-out itself. Left undone, `Q-SEC-009`(b) silently degrades to option (a)
(the outcome the human explicitly rejected), and `Q-FUNC-010`'s answer ("(a)
falls out of (b) for free") stops being true, since it depends on the remote
row actually being gone.

Also implements `FR-AUTH-006`/`FR-AUTH-008`'s teardown ordering
(`sign_out_use_case.dart`'s own doc comment, corrected during this task's own
implementation to: "best-effort revoke -> teardown -> wipe -> best-effort auth
clear" — see §9 Deviations for why the original "teardown -> wipe -> revoke"
ordering was a contract defect, not a design choice) for real: the
`AppDatabase`/`MessagingStack` singletons and their registered repositories
must be closed/unregistered from GetX before `LocalDataWipeService.wipe()`
deletes the database file out from under them, and `revoke` must run while
that same database connection is still live.

## 3. What this task does
- Add an optional `revoke: Future<void> Function()?` constructor seam to
  `SignOutUseCase`, defaulting to a no-op (same shape as the existing
  `teardown` seam) — called BEFORE `teardown` (corrected during this task's
  own implementation, see §9 Deviations), wrapped in the same best-effort
  `try`/`catch`/log pattern the auth clear already uses (never propagates,
  never blocks, never delays navigation).
- In `settings_binding.dart`, when registering the production
  `SignOutConfirmController`, construct its `SignOutUseCase` with:
  - `teardown`: a real closure that closes/unregisters `AppDatabase` and
    `MessagingStack` (and any repository singleton holding a database handle)
    from GetX, in an order that does not throw if a dependency was never
    resolved (nothing has necessarily been visited yet in this session).
  - `revoke`: a closure that calls
    `DeviceRevocationService.revoke(uid, deviceId)` for the current session's
    uid/device id.
- Extend `sign_out_use_case_test.dart` to prove: (a) `revoke` is called
  exactly once, after the wipe and before/alongside the auth clear; (b) a
  throwing `revoke` closure does not propagate and does not prevent
  `call()` from completing; (c) the default (no closure given) behaves exactly
  as today — a no-op, `call()` succeeds identically.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT touch any screen's widget, controller, view, or copy.** Not
  `account_controller.dart`, not `sign_out_confirm_controller.dart`, not any
  `_view.dart`. This is domain + binding wiring only.
- **Does NOT change `SignOutUseCase.call()`'s existing auth-clear error
  handling, or the teardown -> wipe -> auth-clear relative sequence.** Only
  adds the new `revoke` seam and calls it. (§9 Deviations: `revoke`'s
  position relative to `teardown` was corrected mid-task — from after the
  wipe to before `teardown` — after discovering this was a contract-ordering
  defect, not a scope change; `teardown` still runs before `wipe`, and `wipe`
  still runs before the auth clear.)
- **Does NOT add a new route, a new UI affordance, or any user-visible
  change.** This closes a silent gap; nothing about the screen changes.
- **Does NOT touch `bindings.dart`** (the app-level global binding) — the
  production `SignOutUseCase` construction lives in `settings_binding.dart`,
  scoped to the Settings feature, matching where `SignOutConfirmController`
  itself is registered.
- **Does NOT retry a failed revoke, queue it, or persist it for a later
  attempt.** Best-effort means best-effort — a fire-and-log failure, exactly
  like the existing auth-clear catch. A retry/queue mechanism is out of scope
  and would need its own task if ever wanted.
- **Does NOT change `DeviceRevocationService`'s own API.** `revoke(uid,
  deviceId)` already exists (built for `E09`'s device-enrollment work) —
  this task only calls it from a new call site.

## 5. Contract

### Functions
```yaml
- signature: "SignOutUseCase({LocalDataWipeService? wipeService, GoogleAuthService? authService, Future<void> Function()? teardown, Future<void> Function()? revoke})"
  purpose: "Adds the `revoke` seam alongside the existing `teardown` seam.
            Both default to a no-op; the constructor shape for existing
            callers (E15-T07's SignOutConfirmController, this task's own
            production wiring) is otherwise unchanged."

- signature: "SignOutUseCase.call() -> Future<void>"
  purpose: "Corrected ordering (§9 Deviations): best-effort revoke ->
            teardown -> wipe -> best-effort auth clear. `revoke` moved to
            run BEFORE teardown/wipe (the original contract placed it after
            the wipe) because `DeviceRevocationService.revoke()`'s
            production implementation needs a live `AppDatabase` connection
            for its own unconditional local-first write, and `teardown`
            closes that connection. `revoke`'s failure is caught and logged
            exactly like the existing auth-clear catch — never propagates,
            never blocks."
```

### External services & flags
- `DeviceRevocationService.revoke(uid, deviceId)` — already built, no API
  change. Called from `settings_binding.dart`'s production closure only.

## 6. Risks
- **A `revoke` call that throws must not become a visible sign-out failure.**
  The whole point of `Q-SEC-009`(b)'s "best-effort, non-blocking" answer is
  that a flaky network must never turn a successful local wipe into an error
  screen. Test this by making the double throw and asserting `call()` still
  completes normally.
- **Teardown ordering matters more here than it looks.** If the real teardown
  closure closes `AppDatabase` in a way that the wipe's own file-delete then
  races against (a lingering open handle on some platforms), the wipe could
  fail. Confirm the close is awaited and fully synchronous-complete before
  `wipeService.wipe()` runs (this is already the ordering `call()` enforces —
  just confirm the real closure respects it and doesn't fire-and-forget).
- **`uid`/`deviceId` must be read before teardown, not after.** Once
  `AppDatabase` is closed, nothing that reads local identity from it will
  resolve. Capture both before constructing/invoking the `revoke` closure.

**Deviations from spec/design:**
1. **§8's fourth named test
   (`test_teardown_closure_runs_and_completes_before_wipe_is_invoked`) was not
   added as a new, separately-named test.** The pre-existing
   `test_EARS_AUTH_5_teardown_runs_before_wipe_and_wipe_before_auth_clear`
   (E15-T01) already asserts exactly this — `calls == ['teardown', 'wipe',
   'authClear']` via a recording closure — and remains green, unchanged,
   after this task's edits. Adding a byte-for-byte duplicate under a new name
   seemed like noise rather than coverage; flagging the substitution here
   rather than silently treating the §8 list as satisfied by a test that
   doesn't exist under that name.
2. **RESOLVED — the original ordering was a contract defect, fixed within
   this same task rather than left as an open finding.** Round 1 of this
   task's own implementation placed `revoke` strictly AFTER
   `wipeService.wipe()` (per §5's original text) and disclosed, but did not
   fix, that this made `DeviceRevocationService.revoke()`'s unconditional
   local database write (its very first statement, no try/catch around it)
   throw on every single production sign-out — because `teardown` (which
   runs before the wipe) had already closed the shared `AppDatabase`
   connection that write needs. The throw was caught by
   `SignOutUseCase.call()`'s own best-effort wrapper around `revoke` (so
   sign-out itself never visibly failed), but the practical effect was that
   the call never reached the Firebase push at all — `Q-SEC-009`(b)'s actual
   point silently never happened.

   On review of this disclosure, the fix was to reorder `call()` to
   **revoke -> teardown -> wipe -> auth clear** (was: teardown -> wipe ->
   revoke). This is a reordering of two calls this task's own `files:` fence
   already owns (`sign_out_use_case.dart`'s `call()` body) — not a scope
   violation, and not a change to `DeviceRevocationService`'s own API/file
   (§4's fence on that file is respected; only the CALL ORDER `SignOutUseCase`
   uses changed). `teardown` still runs before `wipe` (E15-T01's original
   reasoning holds: other singletons must release their database handle
   before the file is deleted); `revoke` simply moves to the front, so it
   runs while the database connection is still live. `revoke`'s own
   "local write survives next launch" design (a legitimate property of
   `DeviceRevocationService` on its own terms) is irrelevant in this specific
   call path regardless, since the whole database is wiped moments later —
   there is no "next launch" with that local row intact either way.

   §5/§7/§9's own text above, and `sign_out_use_case.dart`/
   `settings_binding.dart`'s doc comments, are updated to describe the
   corrected order; the previously-disclosed "unresolved limitation" is
   removed here rather than left standing alongside the fix. Regression
   tests added and falsified against the pre-fix ordering — see Run log.
