# E15-T13 · Reconcile `settings.md`'s golden against a real Flutter build

## The defect
`design/screens/settings.md`'s golden was extracted from the HTML design
source (`source: ui`, genesis, 2026-08-26) — before
`test/design/flutter_probe_dumper.dart` (E06-T01) existed. It had never been
compared against a real Flutter build via `--impl flutter` until E15-T11
added the screen's first-ever `design-probe` block (the hub itself was never
one of the probe dumper's registered screens before that task). The result:
`node design/tools/verify.mjs --screen settings --impl flutter` reads
❌ **33.8% match (25/74)**, independently reproduced by both E15-T11's
implementer and its round-1 reviewer (isolated via `git stash` to confirm it
predates and is unrelated to E15-T11's own routing changes).

The report's findings are two genuinely different classes:
1. **Missing icon-name map entries** in `flutter_probe_dumper.dart`'s
   `_iconNames` (`account_circle`, `policy`, `wifi_tethering`, `sd_storage`,
   `chevron_right`, `battery_full_alt`) — every other currently-gated screen
   either doesn't use these icons or had them added to that map by whichever
   task built it.
2. **Structural DOM-wrapper/role elements with no Flutter equivalent** —
   `generic <body>`, `generic <header>`, four `button <button>` elements,
   and a role mismatch on every row title/subtitle (`heading:3`/`generic` in
   the golden vs whatever the Flutter walk actually reports). A
   Scaffold-scoped Flutter widget-tree walk has no equivalent for an
   HTML page's own `<body>`/`<header>` wrapper — this is a documented
   "honest limit" (`docs/design-gate-flutter.md §6`).

## Expected
`design-verify SCREEN=settings IMPL=flutter` passes at or near 100%, the way
every other currently-gated screen does (all nine E15 sub-screens: 100%
each), so the hub's own gate is meaningful again on every future PR that
touches it.

## Actual
Red at 33.8%, for reasons unrelated to whatever any given PR changes —
`design-verify SCREEN=settings` cannot currently distinguish "this PR broke
something" from "the golden was never reconciled with this tool."

## Severity
**S3.** Not a shipped UI defect — the hub's actual behavior and appearance
are correct and unchanged. The design gate itself is what's broken for this
one screen, and it will silently pass every review that doesn't independently
re-run `--impl flutter` (as this epic's reviewers have done throughout).

## Fix direction — a planner call between two real options, not a builder guess
1. **Extend `flutter_probe_dumper.dart`'s icon/role handling** to cover this
   screen's icon set and reconcile its `<body>`/`<header>`/`<button>`
   role handling against what an HTML-extracted golden expects — the more
   invasive option, since it changes shared tooling every other gated
   screen also depends on.
2. **Re-extract `settings.md`'s golden from the shipped Flutter build**
   (`make design-extract SCREEN=settings`, then human-approve the diff),
   matching how all nine E15 sub-screens' own goldens are `source: derived`
   — the narrower option, but changes what counts as "the design law" for
   an already-shipped, human-approved screen (`E02-T03`), so it needs the
   same human sign-off any golden change would.

This task's own `files:` fence intentionally leaves the choice open — do not
guess at (1) vs (2) without first re-reading `design/screens/settings.md`'s
own frontmatter/history and confirming which option the human/planner
actually wants for a screen this old and already shipped.

## What this fix does NOT do
- Does NOT change `settings_view.dart`, `settings_controller.dart`, or any
  other product code — the shipped hub is correct; only the gate's own
  golden/tooling needs reconciling.
- Does NOT touch any of the nine sub-screens' own goldens — all nine
  already pass at 100% and are untouched by this task.
