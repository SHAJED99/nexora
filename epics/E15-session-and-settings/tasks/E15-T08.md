# E15-T08 · Network and Battery settings screens

> **Two screens, one task.** Both are read-only status lists over shipped
> services, both compose the same shell, both have the same four states and
> **neither has a write path at all**. Split apart, their combined non-shared
> content is about one screen's worth. Sized `M` on that basis and named here
> so the Analyze gate's Size row is checkable rather than asserted.

## 1. Goal
Put the technical truth about this device's mesh and its background life one
tap away — which is exactly where `FR-UI-004` says it belongs, and nowhere
else.

## 2. Business logic

Implements `FR-ROUTE-010` against `design/screens/settings-network.md`
(`GAP-036`) and `FR-PLAT-004` against `design/screens/settings-battery.md`
(`GAP-037`). Both read-only, both over services that already ship:
`TransportService` and `RoutingEngine` (`activeRouteFor`, `LinkQuality`) for
Network; `PowerState` and `BackgroundPolicy`/`BackgroundPlan` for Battery.

**`FR-UI-004` is why the Network screen exists at all.** The dashboard says
"You're connected"; the route, transport and latency detail is required to be
*one tap away, not shown by default*. This is that tap.

**Two rules do the real work here, and they are the same rule twice:**

1. **An unavailable signal renders as unavailable, never as a value**
   (`FR-ROUTE-010`, `EARS-ROUTE-13`). `FR-ROUTE-007`'s cost formula is still
   `[NEEDS FORMULA]` (`Q-ARCH-004`), and `RouteCostCalculator` already reports
   some factors as unavailable rather than defaulting them — the discipline
   `E08-T04` established for the eight storage factors and `EARS-ROUTE-12`
   enforces in `link_quality_feed.dart` ("reject loudly rather than substitute
   a default"). **A zero on this screen means measured zero.** `0 ms` for
   "never measured" is the one bug these screens exist to not have.
2. **An unreported OS restriction is `Unknown`, not `Off`** (`EARS-PLAT-15`).
   A platform that does not report Doze is not the same as Doze being off, and
   the difference matters to a user wondering why messages are late.

**Neither screen offers a control.** `FR-DISC-003` explicitly forbids
permanently restricting a transport to one feature, nothing in `spec/` gives
the user a routing knob, and `FR-PLAT-004` explicitly forbids reimplementing
the OS's battery settings. `EARS-ROUTE-14` and `EARS-PLAT-16` make both
criteria.

## 3. What this task does
- Builds `NetworkSettingsController` + `NetworkSettingsView` rendering
  NW1-NW15: a Transports card and an Active-routes card, both read-only.
- Builds `BatterySettingsController` + `BatterySettingsView` rendering
  BT1-BT13: background-operation state, the three `FR-PLAT-002` restrictions,
  and the current `BackgroundPlan`.
- Adds two probe tests, verifies both, commits both first clean dumps as
  goldens.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT add any control to either screen.** No transport enable/disable,
  no "prefer Wi-Fi", no relay toggle, no manual route pin, no power-saving mode
  switch, no "restart background service". A settings screen invites settings;
  these two report.
- **Does NOT substitute a default for a missing measurement.** No `0 ms`, no
  `100%`, no `—` standing in for a number. `Not measured` and `Unknown` are the
  contract's own strings.
- **Does NOT render `1 hops`.** NW12's `Direct` and `N hops` are both fixed
  copy for exactly this reason.
- **Does NOT add data-usage metering or a proxy control.** The hub row's
  subtitle promises both; **nothing in `lib/` meters bytes and this app has no
  proxy concept at all.** `GAP-036` carries the fork with **no proposal**;
  metering is a feature with its own FR, not a display problem.
- **Does NOT add a chart, graph, sparkline or latency history.** No measured
  contract in this design draws one; `dashboard.md`'s connectivity treatment is
  textual.
- **Does NOT add a per-factor route-cost breakdown.** `FR-ROUTE-007`'s weighting
  is unresolved (`Q-ARCH-004`); publishing it would present an unfinished
  decision as a fact.
- **Does NOT add relay statistics.** `FR-ROUTE-004`'s relay data is about other
  people's packets and carries a privacy question nobody has asked for.
- **Does NOT add a polling timer, a periodic refresh, or an animated counter.**
  `NFR-BATT-001` is not served by a settings screen that spins the radio. Bind
  to the engines' own updates.
- **Does NOT add the OS battery-settings deep link (BT12) unless `GAP-037`'s
  fork is answered as (a).** It needs a platform call the Pigeon boundary does
  not have (`ADR-0004`), and adding one is a native-boundary change, not a row.
- **Does NOT show a battery percentage, charge state or time-remaining.** Every
  one duplicates a system UI the user already has, and none is in any `FR-*`.
- **Does NOT change `TransportService`, `RoutingEngine`, `PowerState`,
  `BackgroundPolicy`, or any Pigeon schema.**
- **Does NOT touch `lib/app/routes.dart`, `settings_controller.dart`,
  `settings_binding.dart` or `test/design/design_probe_test.dart`** — all four
  are `E15-T11`'s alone.

## 5. Contract

### UI
- **Design contracts:** `design/screens/settings-network.md` (primary, in
  frontmatter) **and** `design/screens/settings-battery.md` (the second screen
  this task builds — named here because the frontmatter field holds one path).
- Routes: `/settings/network`, `/settings/battery` (both registered by
  `E15-T11`).
- **Network** states: `default` · `loading` · **`empty` — the ordinary state on
  a device that is alone**: NW7 and/or NW14, independently; a user in a room
  with no peers correctly sees an empty route list · `error` (NW15 replaces the
  affected card's list only).
- **Battery** states: `default` · `loading` · `error` (BT13). **No `empty`** —
  both cards render fixed sets.
- Gates: `make design-verify SCREEN=settings-network …` and
  `SCREEN=settings-battery …`, **both green before the PR**. Derived screens —
  goldens extracted from the first clean dumps (`design-fidelity` §3).

### Functions
```yaml
- signature: "NetworkSettingsController.transports -> RxList<TransportStatus>"
  returns: "one entry per transport TransportService reports, each Available or Unavailable"
  purpose: "FR-DISC-001's user-visible half. No entry is synthesised for a
            transport the platform did not report."

- signature: "NetworkSettingsController.routes -> RxList<RouteSummary>"
  returns: "destination id, hop count, and latency/loss OR an explicit
            not-measured marker — never a substituted number"
  purpose: "FR-ROUTE-010. The not-measured marker is a type-level distinction,
            not a magic value, so a widget cannot render it as 0."

- signature: "BatterySettingsController.backgroundRunning -> RxBool"
  purpose: "FR-PLAT-001's user-visible half."

- signature: "BatterySettingsController.restrictions -> RxList<RestrictionStatus>"
  returns: "exactly three entries — Doze, Battery Saver, Background restricted —
            each On | Off | Unknown"
  purpose: "FR-PLAT-002's three names, no more and no fewer. Unknown is a real
            value, not a failure."

- signature: "BatterySettingsController.plan -> Rx<String?>"
  returns: "BackgroundPlan's own rendering, one line"
  purpose: "The 'why is the app doing less right now' answer — the only
            question this screen is really for."
```

### External services & flags
None. **BT12's deep link would be a new platform call — 🧍 rule 3 territory,
gated by `GAP-037`. Do not add it unilaterally.**

## 6. Risks
- **The default-substitution reflex.** `latencyMs ?? 0` is one keystroke and
  destroys this screen's whole purpose. Model "not measured" in the type
  (`int?` surfaced as a distinct UI state), not as a sentinel.
- **`RoutingEngine.activeRouteFor` is per-destination.** There is no
  "all routes" accessor; the controller must enumerate destinations it knows
  about. Do not add one to `RoutingEngine` — it is not in `files:`.
- **Subscribing to link-quality updates can be chatty.** Bind, do not poll, and
  dispose cleanly (`NFR-BATT-001`).
- **Two screens, one task, one review.** Keep the two controllers genuinely
  independent — no shared mutable state, no cross-import — so a later split
  costs nothing.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-ROUTE-13**: The Network screen SHALL present each transport and each active route from the shipped `TransportService`/`RoutingEngine` state, and SHALL present an unmeasured signal as unmeasured rather than as a numeric value. (FR-ROUTE-010, FR-ROUTE-007)
- **EARS-ROUTE-14**: The Network screen SHALL offer no control that changes transport selection or routing. (FR-ROUTE-010, FR-DISC-003)
- **EARS-PLAT-15**: The Battery screen SHALL present whether background operation is running and which of Doze, Battery Saver and background-execution restriction are in effect, reporting an unreported restriction as unknown. (FR-PLAT-004, FR-PLAT-002)
- **EARS-PLAT-16**: The Battery screen SHALL offer no control that purports to change an operating-system power restriction. (FR-PLAT-004)
- **EARS-UI-11**: IF a read fails, THEN the system SHALL show that section's failure line and leave every other section unchanged. (FR-UI-007, NFR-REL-001)

### Tests
- `test_EARS_ROUTE_13_unmeasured_link_renders_not_measured_not_zero` → the
  falsification test for this task. Seed a route with no measurement; assert
  `Not measured` is rendered and `0` is not.
- `test_EARS_ROUTE_13_single_hop_renders_direct`
- `test_EARS_ROUTE_13_not_measured_renders_as_text_not_zero` → renders the
  actual view (not just controller state) and asserts `find.text('Not
  measured')` exists while `find.textContaining('0 ms')` does not — added on
  review to close the gap where only sealed-type state, never rendered text,
  was ever asserted.
- `test_EARS_ROUTE_14_no_control_is_rendered` → walks the rendered element
  tree and counts every hit-testable gesture surface (`GestureDetector`,
  `InkWell`/`InkResponse`, `Listener` with a pointer callback, `Semantics`
  with `onTap`/`onLongPress`), asserting the total is exactly 1 (the shared
  shell's own back affordance) — rewritten on review after a widget-type
  denylist was proven defeatable by a raw `Listener`.
- `test_EARS_PLAT_15_initial_loading_state_renders_unknown_before_first_read`
  → renamed on review from
  `test_EARS_PLAT_15_unreported_restriction_renders_unknown`: it proves the
  synchronous loading-state initial value is `unknown`, NOT that a
  genuinely-unreported-by-the-platform restriction can be distinguished from
  a reported-off one after a `PowerState` read completes (see Deviations).
- `test_EARS_PLAT_15_exactly_three_restrictions_are_listed`
- `test_EARS_PLAT_15_unknown_renders_as_text_not_off` → renders the actual
  view before any `PowerState` arrives and asserts `find.text('Unknown')`
  finds 3 widgets while `find.text('Off')` finds none — added on review to
  close the same rendered-text gap as the Network test above.
- `test_EARS_PLAT_16_no_control_is_rendered` → same rewritten gesture-surface
  count as `test_EARS_ROUTE_14_no_control_is_rendered` above, asserting
  exactly 1.
- `test_EARS_UI_11_transport_read_failure_leaves_the_routes_card_rendered`
- `test_EARS_ROUTE_13_no_polling_timer_is_started` → **call counter** on the
  service seam over a pumped duration; the count must not grow.
