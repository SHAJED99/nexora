# E15-T05 · Privacy & Security settings screen

## 1. Goal
One screen that answers "what does this app protect, and what does it share?"
— and lets the user turn the sharing off.

## 2. Business logic

Implements `FR-SEC-005` against `design/screens/settings-privacy.md`
(`GAP-033`). Three cards, one writable.

- **Encryption (read-only).** PV7/PV8 state the protocol actually in force per
  `ADR-0003` — `X3DH + Double Ratchet` for direct messages, `Sender Keys` for
  groups. This is a **statement of fact about an accepted architectural
  decision**, not a preference. A control here would imply the user could
  choose, and they cannot (`FR-SEC-001` is unconditional).
- **Notification privacy (read-only, links out).** PV11 shows the current
  level; PV12 navigates to `/settings/notifications`. **One setting, one
  writer** — `E15-T04` owns it. Two screens writing one preference is the
  "state defined in two documents" trap that cost this project `E05-B03`.
- **Location (writable).** `LocationSettingsRepository` (`E09-T01`) is the sole
  source of truth: `watchGlobalEnabled` / `writeGlobalEnabled`,
  `readAllPeerEnabled` / `writePeerEnabled`.

**PV17 is load-bearing copy, not decoration.** `FR-LOC-003` makes location
availability an **AND** over four conditions — connected, authorized, global
on, per-peer on. A user who does not know that reads a per-person "on" row as
a promise the global switch silently overrides.

## 3. What this task does
- Builds `PrivacySettingsController` bound to
  `LocationSettingsRepository.watchGlobalEnabled()` and a per-peer read, plus a
  read-only `privacyLevel()` from `NotificationSettingsRepository`.
- Builds `PrivacySettingsView` composing `E15-T03`'s scaffold, rendering
  PV1-PV21 exactly as the contract specifies.
- Adds its own probe test, verifies, and commits the first clean dump as the
  golden.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT write the notification privacy level.** PV11 reads; PV12
  navigates. If the diff contains `setPrivacyLevel`, it is wrong.
- **Does NOT build an app lock, a PIN, a biometric gate, or a placeholder for
  one.** The hub row's subtitle promises "app lock" and `ADR-0005`'s
  consequences mention a local lock mechanism — **no FR requires one and none
  exists in `lib/`.** `GAP-033` carries it as a fork with **no proposal**.
  Building one from a subtitle plus an ADR consequence is inventing scope; a
  greyed-out control for it is worse.
- **Does NOT build a permissions screen or list.** Same fork, same reason;
  Android already owns that UI.
- **Does NOT add a block/unblock control.** Blocking lives on `devices.md` and
  keeps exactly one home.
- **Does NOT show location history, a map, a coordinate or a timestamp of a
  fix.** `FR-LOC-004` forbids a permanent location store; displaying a history
  would imply one exists.
- **Does NOT offer a protocol choice, a "re-key" button, or a key-rotation
  control.**
- **Does NOT touch `lib/app/routes.dart`, `settings_controller.dart`,
  `settings_binding.dart` or `test/design/design_probe_test.dart`** — all four
  are `E15-T11`'s alone.
- **Does NOT change `LocationSettingsRepository` or any Drift table.**

## 5. Contract

### UI
- **Design contract:** `design/screens/settings-privacy.md`.
- Route: `/settings/privacy` (registered by `E15-T11`).
- States: `default` · `loading` (values unpopulated, no spinner) · `empty` (the
  per-person list only — PV20; **the ordinary state on a new install**, not an
  error) · `error` (PV21 replaces the affected card's values; **the global
  location switch is never cleared by a failed read of something else**).
- Gate: `make design-verify SCREEN=settings-privacy --impl-probe build/design-probe/settings-privacy.json` green before the PR. Derived screen — golden
  extracted from the first clean dump of the build (`design-fidelity` §3).

### Functions
```yaml
- signature: "PrivacySettingsController.globalLocationEnabled -> RxBool"
  returns: "bound to LocationSettingsRepository.watchGlobalEnabled()"
  purpose: "FR-LOC-001's switch state, streamed not polled."

- signature: "PrivacySettingsController.setGlobalLocation(bool enabled) -> Future<void>"
  returns: "void — delegates to writeGlobalEnabled"
  purpose: "FR-LOC-001's write path. The only write on this screen besides per-peer."

- signature: "PrivacySettingsController.setPeerLocation(String peerDeviceId, bool enabled) -> Future<void>"
  returns: "void — delegates to writePeerEnabled"
  purpose: "FR-LOC-002's write path."

- signature: "PrivacySettingsController.notificationPrivacyLabel -> Rx<String>"
  returns: "`Hidden` | `Sender only` | `Full` — READ ONLY"
  purpose: "PV11. There is deliberately no setter here (see §4)."
```

None.

## 6. Risks
- **The obvious wrong convenience.** Adding a privacy-level selector here
  "since the user is already in Privacy" is exactly the duplication §2 forbids.
- **`readAllPeerEnabled()` returns a map, not a stream.** Re-read after any
  per-peer write; do not maintain a parallel local map.
- **Peer identity display.** PV19 shows a device id (public, already shown on
  `devices.md`). It must not show anything else about the peer.
- **`location_on` is flagged `[glyph — pending human confirmation]`** in the
  contract — it is the one glyph on this screen not measured anywhere. Do not
  quietly substitute a different one; if the human has not confirmed it by
  build time, raise it.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-SEC-4**: WHEN the global location switch is turned off, the system SHALL persist it through `LocationSettingsRepository` and location SHALL be unavailable to every peer regardless of per-peer state. (FR-SEC-005, FR-LOC-001, FR-LOC-003)
- **EARS-SEC-5**: This screen SHALL present the notification privacy level as a read-only value linking to the Notifications screen, and SHALL NOT write it. (FR-SEC-005, FR-NOTIFY-002)
- **EARS-UI-9**: WHERE a Settings row's subtitle names a capability the application does not implement, the sub-screen SHALL state the absence and SHALL NOT present a control or a value for it. (FR-UI-007)
- **EARS-UI-11**: IF a read fails, THEN the system SHALL show that section's failure line and leave every other section, and every user-chosen setting, unchanged. (FR-UI-007, NFR-REL-001)

### Tests
- `test_EARS_SEC_4_global_switch_persists_through_the_repository`
- `test_EARS_SEC_4_global_off_overrides_peer_on` → a peer with location on,
  global off; asserts the screen states unavailability (`FR-LOC-003`'s AND).
- `test_EARS_SEC_5_privacy_level_is_read_only` → **call counter** on
  `setPrivacyLevel`, `expect(calls, 0)` after interacting with PV11/PV12.
- `test_EARS_UI_9_no_app_lock_control_is_present`
- `test_EARS_UI_9_no_permissions_control_is_present`
- `test_EARS_UI_11_peer_read_failure_leaves_the_global_switch_intact`

### Manual
1. Turn global location off, force-quit, relaunch → still off.
2. Tap the notification-privacy row → lands on Notifications, level unchanged.
