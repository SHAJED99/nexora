> ✅ **UNBLOCKED 2026-09-08.** `Q-SEC-009` ((b) revoke best-effort via
> `DeviceRevocationService.revoke()`) and `Q-FUNC-010` ((a) fix the
> enrollment gate, accept the rate limit as-is) are both answered in
> `spec/questions.md`. See this task's own §Open Questions and §Deviations

> task's own `files:`/Functions contract.

## 1. Goal
Give this app the sign-out it has never had: one call that permanently erases
every trace of this device's identity and history, so that the next sign-in
starts from nothing.

## 2. Business logic

Implements `FR-AUTH-006` (what is erased), `FR-AUTH-008` (what the next
sign-in sees), `FR-AUTH-009` (an interrupted erase), and the mechanism
`FR-AUTH-007`'s confirmation screen (`E15-T07`) sits in front of.

**What "everything" means is already enumerated** — in
`docs/impact/IMP-003`'s table, walked file by file against `ADR-0001` and
`ADR-0005`. It is not open for re-interpretation here. The short form:

1. **The Drift database file is deleted, not emptied.** `<app documents>/nexora.sqlite`
   (`database.dart`'s `_openConnection`), together with its `-wal` and `-shm`
   sidecars if present. Deleting rows leaves the file, its write-ahead log and
   its freelist pages carrying recoverable ciphertext and key material —
   `NFR-PRIV-001` is not satisfied by a `DELETE FROM`.
2. **The Firebase Authentication session is terminated** and **the cached
   Google credential is cleared.** `ADR-0005` makes these a thin account
   pointer, independent of device identity — so they are dropped as their own
   act, never derived from the database wipe and never blocking it.
3. **Every in-memory singleton holding a handle to that file is closed and
   unregistered before the file is deleted.** This is the ordering that keeps
   the app from crashing, and it is the most likely defect in this task.

**What is NOT wiped:** anything remote. See §5 Remote.

**The E13 carried-forward observation is satisfied by this design, and the
implementer must not undo it.** `epics/E13-abuse-diagnostics/tracker.md`
carries T07's reviewer note that `SignInUseCase.call` matches on `deviceId`
only, never on account. After this wipe there is **no** `DeviceIdentities` row,
so `existingDeviceId()` returns `null`, `_deriveDeviceIdFromLocalIdentity()`
derives a *new* id from a *new* keypair (the old one went with the file), and
`call()`'s returning-device branch is correctly not taken — the next sign-in
registers as a genuinely new device and **is** counted by the rate limiter.
That is the intended behaviour, verified in `IMP-003`. **Do not add a
"remember this device across logout" shortcut** to make the rate limiter
happier; that would silently restore the exact hole E13 flagged.

## 3. What this task does
- Adds `LocalDataWipeService` (`lib/core/session/`) with three operations:
  arm-and-erase, ask whether an erase is pending, and complete a pending one.
- Adds a **sentinel file** next to the database, written *before* the first
  delete and removed *after* the last, so an interrupted erase is detectable.
  It cannot live in the database — the database is what is being destroyed.
- Adds `GoogleAuthService.signOut()` (the class has only `signIn()` and
  `signInAndGetAccountUid()` today) covering both the Firebase Auth session
  and the cached Google credential.
- Exposes the database file location from `AppDatabase` as a named,
  independently callable function, so the wipe service targets **the same
  path** `_openConnection` opens rather than re-deriving it.
- Adds `SignOutUseCase` — the one call `E15-T07`'s confirm button makes:
  tear down singletons → wipe → clear auth. It performs no navigation.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT delete rows.** Not as a fallback, not "for the tables that
  matter", not if file deletion throws. See §2.1 and §6.
- **Does NOT navigate anywhere.** `SignOutUseCase` returns; `E15-T07` decides
  what screen comes next. A use case that calls `Get.offAllNamed` is
  untestable and owns a decision that is not its own.
- **Does NOT build any UI, confirmation, dialog or snackbar.** The whole
  confirmation journey is `E15-T07` (`design/screens/sign-out-confirm.md`).
- **Does NOT change `SignInUseCase`, `LoginController`, `main.dart` or
  `bindings.dart`.** None is in `files:`. The launch-side half — completing a
  pending wipe and routing afterwards — is **`E15-T02`**, deliberately, so the
  erase mechanism and the launch decision are reviewed separately.
- **Does NOT add a "sign out but keep my identity" path.** The human
  explicitly rejected it on 2026-09-08. There is one sign-out.
- **Does NOT add an export, backup or "download my data" step.** `GAP-027`
  already established this app has no export; offering one on the way out
  would be the worst possible place to promise it.
- **Does NOT touch `schemaVersion` or add a migration.** There is no schema
  change here — the schema is being deleted.
- **Does NOT delete the Firebase account itself.** Signing out of an account
  is not deleting it.

## 5. Contract

### Data
**No migration. No new table. No `schemaVersion` bump.** The only new
persistent artifact is a zero-byte sentinel file beside the database.

### Functions
```yaml
- signature: "AppDatabase.databaseFile() -> Future<File>"
  params: {}
  returns: "File — the same path `_openConnection` opens: <app documents>/nexora.sqlite"
  purpose: "One source of truth for where the database lives. A wipe that
            re-derives the path is a wipe that will one day miss the file."

- signature: "GoogleAuthService.signOut() -> Future<void>"
  params: {}
  returns: "void — completes when both the Firebase Auth session and the cached
            Google credential are cleared"
  purpose: "ADR-0005's account-pointer half of sign-out. Never throws out: a
            failure here is logged via ObservabilityService and swallowed —
            the local erase is the part that must not be blocked by a network."

- signature: "LocalDataWipeService.isWipePending() -> Future<bool>"
  params: {}
  returns: "true when the sentinel file exists — an erase was started and not
            finished"
  purpose: "FR-AUTH-009's detection half. Read by E15-T02 at launch."

- signature: "LocalDataWipeService.wipe() -> Future<void>"
  params: {}
  returns: "void — completes only when the sentinel has been removed"
  purpose: "FR-AUTH-006. Writes the sentinel, closes and unregisters every
            handle, deletes the database file and its -wal/-shm sidecars,
            removes the sentinel. Idempotent: safe to call when nothing exists."

- signature: "LocalDataWipeService.completePendingWipe() -> Future<void>"
  params: {}
  returns: "void"
  purpose: "FR-AUTH-009. No-op when no sentinel exists; otherwise re-runs the
            delete half and clears the sentinel. Called by E15-T02 at launch,
            BEFORE any routing decision."

- signature: "SignOutUseCase.call() -> Future<void>"
  params: {}
  returns: "void — completes when the local erase is done"
  purpose: "FR-AUTH-006/008. Teardown -> wipe -> auth clear, in that order.
            The auth clear is best-effort and never fails the call; the wipe
            is not, and its failure propagates as an AppFailure."
```

### Ordering — binding, not advisory
`teardown → sentinel → delete → sentinel removed → auth clear`.
The teardown closes and unregisters `AppDatabase`, `MessagingStack` and every
repository singleton **before** the file is touched. A live `AppDatabase` on a
deleted path is this epic's most likely crash (epic §Risks, row 1). Deleting
first and closing after "works" in a test and fails on a device with an open
WAL.

### External services & flags
`FirebaseAuth.signOut()` and `GoogleSignIn.signOut()` — both already
dependencies (`firebase_auth`, `google_sign_in` in `pubspec.yaml`). **No new
dependency, no new secret, no flag.** If either looks necessary, stop: that is
a 🧍 human gate (rule 3), not a judgement call.

### Remote — 🟡 UNRESOLVED, `Q-SEC-009`
`users/$uid/devices/<deviceId>` in the Realtime Database is **not local** and
survives this wipe. Whether sign-out should also revoke it (via the existing
`DeviceRevocationService.revoke(uid, deviceId)`), delete it, or do nothing, is
`Q-SEC-009` — **blocking, unanswered**. Whatever the answer, it must be
best-effort and non-blocking: a network write inside a destructive local
operation may never be allowed to leave the erase half-done. **Do not
implement any remote behaviour until the answer is recorded in
`spec/questions.md`.**

## 6. Risks
- **The obvious wrong fix.** File deletion fails (a locked handle on Android),
  and the implementer "helpfully" falls back to deleting rows. That leaves key
  material in the file and reports success. **A failed delete is a failure** —
  propagate it, leave the sentinel in place, and let `completePendingWipe()`
  retry at next launch.
- **Sidecars.** SQLite in WAL mode leaves `nexora.sqlite-wal` and
  `nexora.sqlite-shm`. Deleting only the main file leaves recent writes
  recoverable. Delete all three; absent sidecars are not an error.
- **Teardown ordering** — see §5. Get this backwards and the crash appears
  only on a real device.
- **Idempotency.** `completePendingWipe()` runs on a device where the file may
  already be gone. Every delete must tolerate "already absent".
- **Test isolation.** `AppDatabase.forTesting(NativeDatabase.memory())` has no
  file at all. The file-path tests need a real temp directory; the service
  must take its paths through an injected seam rather than calling
  `getApplicationDocumentsDirectory()` inline, or none of this is testable.
- **`fail()` in an injected seam is swallowed** by a broad catch and proves
  nothing — use a call counter and assert the count (`L-testing`, and this
  task has three best-effort catches).

## 8. Acceptance criteria (EARS) + test plan

- **EARS-AUTH-5**: WHEN sign-out is confirmed, the system SHALL delete the local database file and clear the Firebase Authentication session and cached Google credential, leaving no local device cryptographic identity. (FR-AUTH-006, FR-AUTH-008)
- **EARS-AUTH-6**: IF a sign-out is interrupted before the erase completes, THEN the system SHALL complete the erase before presenting any signed-in state. (FR-AUTH-009)
- **EARS-AUTH-11**: WHEN a device signs in after a completed sign-out, the system SHALL create a new device cryptographic identity rather than reusing any prior one. (FR-AUTH-008)

### Tests
- `test_EARS_AUTH_5_wipe_deletes_database_file_and_sidecars` → seeds a real
  file-backed database plus `-wal`/`-shm`, wipes, asserts **all three are
  absent**. Absence of the file, not emptiness of a table.
- `test_EARS_AUTH_5_wipe_clears_auth_session` → call-counter seam on
  `GoogleAuthService.signOut`, asserts it ran exactly once.
- `test_EARS_AUTH_5_auth_failure_does_not_prevent_local_erase` → seam throws;
  the file is still gone and `call()` still completes.
- `test_EARS_AUTH_6_sentinel_present_after_interrupted_wipe` → delete seam
  throws mid-run; asserts the sentinel **remains** and `isWipePending()` is true.
- `test_EARS_AUTH_6_complete_pending_wipe_finishes_the_erase` → from that
  state, `completePendingWipe()` leaves no file and no sentinel.
- `test_EARS_AUTH_6_complete_pending_wipe_is_a_noop_without_a_sentinel`
- `test_EARS_AUTH_11_fresh_database_after_wipe_has_no_device_identity` →
  re-opens a new `AppDatabase` on the same path and asserts
  `latestDeviceIdentity()` is `null` **and** the schema is at the current
  version (a fresh create, not a survivor).

### Manual
1. Sign in on a device → confirm `nexora.sqlite` exists.
2. Trigger `SignOutUseCase.call()` → file, `-wal`, `-shm` and sentinel all gone.
3. Relaunch and sign in → a **different** device id is registered.
