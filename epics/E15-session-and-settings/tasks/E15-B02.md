# E15-B02 · `_sendAndRestoreOnFailure` writes to a disposed `TextEditingController`

## The defect
`_ComposerState._sendAndRestoreOnFailure` (`chat_view.dart`) does:
```dart
await widget.controller.send(trimmed);
if (widget.controller.sendError.value.isNotEmpty) {
  _textController.text = trimmed;   // <- crash site, pre-fix
  Get.snackbar(...);
}
```
If the user navigates away from the chat (taps the header's back arrow,
`Get.back<void>()`) while `send()` is still resolving, `_ComposerState.dispose()`
runs and disposes `_textController` before the pending future completes. When
`send()` later resolves with a failure, this method resumes and writes to the
already-disposed controller.

## Repro
Hit live on a physical device: sent a message to the wrong peer by mistake,
backed out of that chat before the send resolved, opened the correct chat.
The first send's failure surfaced afterward via logcat:
```
Unhandled Exception: A TextEditingController was used after being disposed.
#6  _ComposerState._sendAndRestoreOnFailure (chat_view.dart:390:23)
```
Reproduced deterministically in a widget test using an unreachable peer (no
relationship row, so `send()` goes down `PrekeyExchange.ensureSession`'s real
20s-timeout path instead of the fast synchronous `messaging.peer_blocked`
rejection) with `tester.pump(Duration)` fake-time control: advance partway,
tap back, `pumpAndSettle` to let the route actually pop and dispose the
composer, advance past the timeout — exact same error text and stack shape.

## Expected
Navigating away from a chat while a send is still resolving must never
crash, regardless of whether that send eventually succeeds or fails.

## Actual
Hard crash, `A TextEditingController was used after being disposed`.

## Severity
**S1.** Deterministic hard crash on ordinary use (send a message, immediately
navigate away — no special timing needed from the user's side, only from an
in-flight async op).

## Fix (implemented)
Added `if (!mounted) return;` immediately after the `await`, before any use
of `_textController` or `Get.snackbar`.

## What this fix does NOT do
- Does **NOT** change `ChatController.send`'s own failure semantics, the
  optimistic-bubble-drop behavior, or `sendError`'s contract.
- Does **NOT** attempt to still show the "Message not sent" snackbar after
  the user has navigated away — the composed text is unrecoverable either
  way once the composer is gone, and an unexplained snackbar on an unrelated
  screen would be worse UX, not better (recorded as a reviewer observation,
  not required to change).
- Does **NOT** touch `_submit`'s synchronous, pre-`unawaited` code path,
  which was never at risk (it only touches `_textController` before the
  async call begins).
