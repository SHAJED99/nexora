# E15-T04 · Notifications settings screen

## 1. Goal
The human's own first priority: make the Notifications row lead somewhere, so a
user can decide which alerts this device shows and how much they reveal.

## 2. Business logic

Implements `FR-NOTIFY-003` — the user-facing surface for `FR-NOTIFY-001`'s
categories and `FR-NOTIFY-002`'s privacy level — against
`design/screens/settings-notifications.md` (`GAP-032`).

**The data layer already ships.** `NotificationSettingsRepository`
(`lib/core/notifications/`, `E10-T02`) is the sole source of truth:
`isEnabled` / `setEnabled` / `watchEnabled` per category, `privacyLevel` /
`setPrivacyLevel`. This screen holds **no** second copy of a preference and
**no** defaulting rule of its own — the repository's asymmetric defaults
(a missing category row is **enabled**, a missing/unknown privacy level is
**hidden**) are deliberate and documented in `notification_tables.dart`'s
header. Do not re-derive, mirror or "correct" them here.

Two rules from the contract that are the actual work:

1. **Nine categories, not ten.** `NotificationCategory.backgroundService` is
   **absent by contract**: Android requires that notification whenever the
   foreground service runs, so it is not a user preference and `E10-T02` seeds
   no row for it. A tenth row would be a control that cannot work.
2. **`full` privacy is offered as a value, not as a working feature.** It has
   no supported mechanism today — plaintext is decrypted only in the screen
   layer, and a background dispatcher cannot reach it. `FR-UI-007` and
   `EARS-NOTIFY-17` require NT21 to say so.

## 3. What this task does
- Builds `NotificationSettingsController` bound to
  `NotificationSettingsRepository`'s **streams**, and
  `NotificationSettingsView` composing `E15-T03`'s scaffold.
- Renders NT1-NT22 exactly as `settings-notifications.md` specifies, with the
  nine category rows in the contract's stated order and copy.
- Adds its own probe test (`test/design/probe_settings_notifications_test.dart`)
  producing `build/design-probe/settings-notifications.json`, runs
  `make design-verify SCREEN=settings-notifications --impl-probe …`, and
  commits the first clean dump as this screen's golden.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT use a `Switch`, `Checkbox`, `Radio` or any Material toggle.** This
  design measures none, anywhere. On/off is SH12 —
  `radio_button_checked` / `radio_button_unchecked` — the treatment
  `settings-storage.md` SS14-16 already uses and the human already approved.
  "It's Material 3, `FR-UI-001` allows it" is the specific wrong argument this
  fence exists to pre-empt: `FR-UI-001` picks a design *system*, it does not
  license a primitive the design never draws.
- **Does NOT add a tenth category row** for `backgroundService`.
- **Does NOT hide, disable-and-grey, or remove the `full` privacy option.** It
  is shown with NT21's disclosure copy.
- **Does NOT add an LED control or a silent-mode control.** `GAP-032` carries
  that fork with **no proposal** and the default disposition is `GAP-027`'s
  approved (c) — no control, disclosed absence. Building one from the hub row's
  subtitle would be inventing scope from copy.
- **Does NOT add per-conversation muting, quiet hours, a sound picker, a
  vibration setting, or a "send a test notification" button.** None is in
  `FR-NOTIFY-*`; the first belongs on `chat.md` if it is ever specified, and
  Android's own notification channels already own the rest.
- **Does NOT post, build, suppress or decrypt any notification.** This screen
  writes preferences. `E10-T03` is the consumer that acts on them.
- **Does NOT touch `lib/app/routes.dart`, `settings_controller.dart`,
  `settings_binding.dart` or `test/design/design_probe_test.dart`.** All four
  are **`E15-T11`'s alone**. This screen is unreachable in the app until T11
  lands, and that is intended — the epic branch integrates as a whole.
- **Does NOT change `NotificationSettingsRepository` or any Drift table.**

## 5. Contract

### UI
- **Design contract:** `design/screens/settings-notifications.md` — build from
  this, not from `settings.md`'s row.
- Route: `/settings/notifications` (registered by `E15-T11`).
- States required: `default` · `loading` (frame + cards render, row states
  unpopulated — **no spinner**) · `error` (NT22 replaces the affected card's
  rows only, the other card unchanged). **No `empty` state** — both lists are
  fixed sets.
- Gate: `make design-verify SCREEN=settings-notifications --impl-probe build/design-probe/settings-notifications.json` **green before the PR** (rule 2).
  **This screen has no design source**, so its golden is extracted from the
  first clean dump of the build itself, per `design-fidelity` §3 and exactly as
  `E12-B06` records for `device-enrollment`. The gate is a **regression** gate
  from that commit onward; first-build fidelity is proven by the reviewer
  reading the contract's element and copy tables.

### Functions
```yaml

  returns: "the nine user-facing values, in settings-notifications.md's order"
  purpose: "One place the nine-not-ten rule is expressed."

- signature: "NotificationSettingsController.toggle(NotificationCategory category) -> Future<void>"
  params: { category: "the row that was tapped" }

- signature: "NotificationSettingsController.selectPrivacy(NotificationPrivacyLevel level) -> Future<void>"
  params: { level: "hidden | senderOnly | full" }
  returns: "void — delegates to setPrivacyLevel"

            the same as honouring it (E10-T02's own header)."
```

## 6. Risks
- **Read-once instead of watch.** `watchEnabled` is a stream. A `Future`-based
  render goes stale the moment anything else writes, and the bug is invisible
  in a single-screen test.
- **Nine `watchEnabled` subscriptions.** One per category is correct and cheap;
  make sure they are disposed with the controller.
- **The copy is compared character for character.** Twenty-plus strings in
  §Copy, including the em dash in NT19's `Neither who nor what — "New message".`
  and the straight double quotes inside it. Copy them, do not retype them.
- **`full`'s row must still be tappable-looking enough to read but must not
  write.** Decide once, in the controller, and test it (`EARS-NOTIFY-17`).

## 8. Acceptance criteria (EARS) + test plan

- **EARS-NOTIFY-16**: WHEN a notification category is switched on this screen, the system SHALL persist that choice through `NotificationSettingsRepository` and SHALL reflect the persisted value on the next read. (FR-NOTIFY-003, FR-NOTIFY-001)
- **EARS-NOTIFY-17**: WHERE the `full` privacy level has no supported mechanism, this screen SHALL state that it is unavailable rather than presenting it as a working option. (FR-NOTIFY-003, FR-NOTIFY-002, FR-UI-007)
- **EARS-UI-9**: WHERE a Settings row's subtitle names a capability the application does not implement, the sub-screen SHALL state the absence and SHALL NOT present a control or a value for it. (FR-UI-007)
- **EARS-UI-11**: IF a read fails, THEN the system SHALL show that section's failure line and leave every other section unchanged. (FR-UI-007, NFR-REL-001)

### Tests
- `test_EARS_NOTIFY_16_toggling_a_category_persists_through_the_repository` →
  real in-memory `AppDatabase`, toggles, re-reads through the repository.
- `test_EARS_NOTIFY_16_screen_reflects_an_external_write` → writes via the
  repository directly, asserts the view updates (proves the stream binding).
- `test_EARS_NOTIFY_16_background_service_category_is_absent` → asserts exactly
  nine rows and that no row corresponds to `backgroundService`.
- `test_EARS_NOTIFY_17_full_privacy_row_shows_the_unavailable_copy`
- `test_EARS_NOTIFY_17_selecting_full_does_not_write` → **call counter** on the
  repository seam, `expect(calls, 0)`. Not `fail()` inside the seam — a broad
  catch swallows it (`L-testing`).
- `test_EARS_UI_9_no_led_control_is_present`
- `test_EARS_UI_11_category_read_failure_leaves_the_privacy_card_intact`

### Manual
1. Toggle three categories, force-quit, relaunch → all three persist.
2. Tap `Full` → nothing changes, the disclosure copy is visible.
