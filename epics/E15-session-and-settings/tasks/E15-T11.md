# E15-T11 · Settings hub wiring: eight routes, eight rows, probe consolidation

> **This task is the single owner of every file the eight screen tasks share.**
> That is not a convenience — it is what makes those eight tasks
> collision-free and parallelisable. `lib/app/routes.dart`,
> `settings_controller.dart`, `settings_binding.dart` and
> `test/design/design_probe_test.dart` appear in **no other E15 task's**
> `files:`, and this one owns all four outright.
>
> It is also the task without which none of the other seven screens is
> reachable. Every one of them says so in its own §4; this file is where that
> obligation is actually met.

## 1. Goal
Turn the Settings screen from a menu that acknowledges taps into a menu that
navigates — all eight rows, all at once — and fold the eight ad-hoc probe
dumps into the one fixture `make design-probe` actually runs.

## 2. Business logic

Implements `FR-UI-006` (every row navigates; **no row responds with a
non-navigating acknowledgement**) and `FR-UI-008` (back returns to the hub),
closing `EARS-UI-8` and `EARS-UI-10`.

`SettingsController.openRow(String title)` today shows the same
`Get.snackbar(title, 'Coming soon')` for all eight rows — correct when
`E02-T03` wrote it (none of the destinations existed, and navigating to a
fabricated screen would have been worse), and wrong the moment they do.

**Eight routes, eight rows, and the mapping between them is where this task
fails if it fails.** A single copy-pasted route constant sends two rows to one
screen, and every individual screen task still passes its own gate. That is
what §8's per-row test exists to catch.

**`design/sources.yaml` already has all eight entries** — `E15-T03` registered
them so every screen task could gate itself against its own dump. This task
does not touch that file; it consolidates the **probe fixture** so
`make design-probe` dumps all eight in one run and CI keeps gating them
(`L-design-002`: disclosing a fixture gap is correct, leaving it for the next
task to rediscover is not).

## 3. What this task does

### The eight routes (`lib/app/routes.dart`)
Eight constants and eight `GetPage` entries, each with its screen's binding,
each doc-commented with its design contract exactly as every existing constant
in that file is:

| constant | path | view |
|---|---|---|
| `settingsAccount` | `/settings/account` | `AccountView` (T07) |
| `settingsSignOutConfirm` | `/settings/sign-out-confirm` | `SignOutConfirmView` (T07) |
| `settingsPrivacy` | `/settings/privacy` | `PrivacySettingsView` (T05) |
| `settingsSecurityCenter` | `/settings/security-center` | `SecurityCenterView` (T06) |
| `settingsNetwork` | `/settings/network` | `NetworkSettingsView` (T08) |
| `settingsStorage` | `/settings/storage` | `StorageSettingsView` (T09) |
| `settingsBattery` | `/settings/battery` | `BatterySettingsView` (T08) |
| `settingsNotifications` | `/settings/notifications` | `NotificationSettingsView` (T04) |
| `settingsAbout` | `/settings/about` | `AboutSettingsView` (T10) |

(Nine constants — eight hub rows plus the sign-out confirmation, which is
reached from the Account screen rather than from a row.)

### The eight rows (`settings_controller.dart`, `settings_view.dart`)
- Replace `openRow(String title)`'s snackbar with navigation. The row identity
  becomes a **closed enum**, not a display string — routing on a title string
  breaks silently the moment the design copy changes, and the design gate
  compares that copy character for character.
- `settings_view.dart` passes the enum value per row; the eight row labels and
  subtitles are **unchanged** (`settings.md`'s copy is law).
- `settings_binding.dart` registers the eight sub-screen controllers lazily.

### The probe fixture (`test/design/design_probe_test.dart`)
- Add nine `dumpScreenProbe` blocks (eight screens + sign-out confirmation),
  each reusing the fixture data its own screen task's widget test already
  builds — the one-block pattern `docs/design-gate-flutter.md` §"Adding a
  screen" documents.
- Delete the nine ad-hoc `test/design/probe_*_test.dart` files the screen tasks
  created. Their goldens stay; only the runners are folded in.

### Documentation
- `docs/routes.md` gains the nine routes.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT change any screen's own widget, controller, copy, layout or
  behaviour.** Not "one small fix while I'm here". Every screen file belongs to
  its own task and is not in `files:`. A defect found in one is a **bug task**
  against that task, not an edit here.
- **Does NOT change `settings.md`'s eight row labels or subtitles.** Including
  `Version 2.4.1, release notes, diagnostic logs` — see `E15-T10` §4. The hub's
  own design gate is green and must stay green.
- **Does NOT add a ninth row, reorder the eight, add a badge, a count, a
  chevron the design does not draw, or a section divider.** The hub is a
  measured, shipped screen.
- **Does NOT change the bottom navigation bar** (`settings.md` elements 48-59)
  or any other tab's routing.
- **Does NOT route on a display string.** See §3.
- **Does NOT add a route guard, a redirect, a middleware or a
  `Get.routingCallback`.** Launch routing is `E15-T02`'s and nothing else
  decides where the app starts.
- **Does NOT keep a "Coming soon" fallback for an unmapped row.** After this
  task there is no unmapped row; a fallback would let a future missing mapping
  fail silently instead of failing at compile time. That is what the closed
  enum is for.
- **Does NOT delete any golden.** Only the nine ad-hoc probe *runners*.
- **Does NOT touch `main.dart`, `bindings.dart`, or `design/sources.yaml`.**

## 6. Risks
- **The mapping is eight near-identical lines.** Copy-paste drift here is the
  single most likely defect, and it is invisible to every other task's gate.
  §8's per-row test is not optional.
- **Bindings resolve lazily.** A screen whose controller needs a dependency
  `AppBinding` never registered will throw on first navigation, not at startup
  — and only for that one row. Navigate to all nine in the tests.
- **The consolidated probe fixture needs each screen's fixture data.** Copy it
  from each screen task's own widget test rather than re-deriving; a fixture
  that seeds different data than the screen task used produces a red gate that
  looks like a regression and is not (`L-design-002`'s exact shape).
- **`settings_view.dart` is a shipped, gated screen.** The only change is which
  value each row passes to `openRow`. If the diff touches a string, a padding
  or a colour there, it is out of scope.
- **This task depends on eight others.** Dispatch it only when all eight are
  merged to `epic_15`; a partial wiring task is a merge conflict waiting to
  happen.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-UI-8**: WHEN any Settings row is tapped, the system SHALL navigate to that row's sub-screen; no Settings row SHALL respond with a non-navigating acknowledgement. (FR-UI-006)
- **EARS-UI-10**: WHEN the back affordance is used on any Settings sub-screen, the system SHALL return to the Settings hub. (FR-UI-008)

### Tests
- `test_EARS_UI_8_each_row_navigates_to_its_own_route` → **parameterised over
  all eight rows**, asserting a *distinct* route per row. The duplicate-mapping
  test; a copy-paste that sends two rows to one screen fails here and nowhere
  else.
- `test_EARS_UI_8_no_row_shows_a_snackbar` → **call counter** on the snackbar
  seam across all eight taps, `expect(calls, 0)`.
- `test_EARS_UI_8_every_registered_route_resolves_to_a_page` → navigates to all
  nine and asserts each builds, catching an unregistered binding.
- `test_EARS_UI_10_back_from_each_sub_screen_returns_to_settings` →
  parameterised over all eight.
- `test_EARS_UI_8_settings_row_copy_is_unchanged` → guards §4's "does not
  change the eight labels".

### Manual
1. Tap all eight rows in turn; each lands on its own screen, each backs out to
   Settings.
2. Account → Sign out → the confirmation screen; cancel returns to Account.
3. `make design-probe && make design-verify SCREEN=settings IMPL=flutter` green.
