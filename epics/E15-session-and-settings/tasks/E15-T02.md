# E15-T02 · Session-aware launch routing, composed after the mandatory-update gate

> 🛑 **BLOCKED via `E15-T01`** on `Q-SEC-009` / `Q-FUNC-010`. It also depends
> on `E15-T01`'s `completePendingWipe()` existing. Do not start before both.

## 1. Goal
A returning user opens the app and is *in* it — no welcome screen, no
"Continue with Google" tap they have already done — without weakening the
mandatory-update block by a single condition.

## 2. Business logic

Implements `FR-AUTH-010` (skip when an identity exists), `FR-AUTH-012` (welcome
when it does not), `FR-AUTH-011` (never ahead of the update block), and the
launch half of `FR-AUTH-009` (finish an interrupted wipe first).

**`FR-AUTH-011` is the whole reason this is a task and not a one-line edit.**
`lib/app/main.dart` already computes a launch route:
`initialRouteFor(versionState)` returns `Routes.versionUpdateRequired` when the
state is `updateRequired`, else `Routes.welcome`. That function is already
tested (`test_EARS_VER_10_update_required_routes_to_mandatory_screen`) and
already carries `E14-B01`/`E14-B06`'s history. **Extend it; do not add a
second routing decision beside it.** Two functions deciding one route is how
`FR-VER-006`'s block gets bypassed by the one that runs first.

The evaluation order is fixed and binding:

1. **Complete any pending wipe** (`LocalDataWipeService.completePendingWipe()`).
   Nothing else may be decided against a half-erased device — `FR-AUTH-009`
   says "before presenting any signed-in state", and a routing decision *is*
   presenting one.
2. **`updateRequired` → `/version-update-required`.** Returns here. The local
   identity is not consulted at all — not read, not awaited.
3. **A local device identity exists → `/dashboard`.**
4. **Otherwise → `/welcome`.**

**The existing enrollment branch is untouched.** `LoginController._signIn`
routes to `/device-enrollment` when another device is registered to the
account (`E12-T03`). That branch runs *inside* the login flow. Skipping to
`/dashboard` means a returning device never reaches it — which is correct for
a device that is already enrolled, and is exactly what `Q-FUNC-010` is asking
the human about for the *post-logout* case. **Do not replicate the enrollment
check here.**

## 3. What this task does
- Adds `resolveInitialRoute(...)` — a pure function of `(VersionState, bool
  hasLocalIdentity)` implementing the four-step order above, in the same
  independently-testable shape `initialRouteFor` already is and for the same
  stated reason (it can be asserted without booting Firebase, `AppDatabase` or
  `MessagingStack`).
- Wires it into `main()`: `completePendingWipe()` first, then the existing
  version evaluation, then this function, then `runApp`. `main()` already
  reads `db.latestDeviceIdentity()` to seed `selfDeviceId` — **reuse that same
  read**; do not issue a second one.
- Updates `test/widget_test.dart`'s F1 regression test for the changed route.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT bypass, weaken, reorder or "optimise" the mandatory-update
  check.** `initialRouteFor`'s existing `updateRequired` branch keeps
  precedence, and `blockCommunication` keeps being threaded from the same
  `versionState`. If a change here makes `EARS-VER-10`'s test easier to pass,
  it is wrong.
- **Does NOT delete or weaken `test/widget_test.dart`'s F1 regression test.**
  Its *route* changes; its *subject* does not. It exists because a returning
  device was being denied by the per-account registration rate limiter — an
  S1. **The rate-limiter seeding, the 5-prior-registrations setup, and the
  final "exactly 6 rows, no 7th" assertion must all survive.** Only the
  navigation path it asserts changes. Rewriting it into a simpler test is a
  changes-requested.
- **Does NOT touch `LoginController`, `SignInUseCase`, or the
  `/device-enrollment` branch.** None is in `files:`.
- **Does NOT add a mid-session re-check, a timer, or a route guard.**
  `E14-T04`'s fence deliberately kept this launch-time-only and `E14-B06`
  already owns the reconnect re-check. Do not add a third trigger.
- **Does NOT add a local session/lock, PIN or biometric gate.** `ADR-0005`
  mentions a local lock mechanism as a consequence; **no FR requires one** and
  `GAP-033` carries it as an unanswered fork. "An identity exists" is the
  entire condition.
- **Does NOT implement the wipe.** `E15-T01` owns `LocalDataWipeService`
  entirely; this task calls `completePendingWipe()` and nothing else.
- **Does NOT change `AppBinding` or `bindings.dart`.**

## 5. Contract

### Functions
```yaml
- signature: "resolveInitialRoute({required VersionState versionState, required bool hasLocalIdentity}) -> String"
  params:
    versionState: "the value main()'s existing evaluateVersionStateAtLaunch() returned"
    hasLocalIdentity: "true when db.latestDeviceIdentity() returned non-null —
                       the SAME read main() already performs to seed selfDeviceId"
  returns: "Routes.versionUpdateRequired | Routes.dashboard | Routes.welcome"
  purpose: "FR-AUTH-010/011/012 as one pure, order-fixed decision. Pure so the
            precedence of the update block is provable without a device."
```

`main()`'s call order becomes:
`completePendingWipe()` → `evaluateVersionStateAtLaunch()` → `latestDeviceIdentity()`
(already there) → `resolveInitialRoute(...)` → `runApp(...)`.

## 6. Risks
- **The one-line-edit trap.** `initialRouteFor` is a tempting place to write
  `state == updateRequired ? x : (hasIdentity ? dashboard : welcome)` inline
  and skip the pending-wipe step entirely, because that step is `async` and
  the function is not. Do the wipe completion in `main()` before calling the
  pure function; do not make the function `async` to hide it.
- **A returning device with a *corrupt* identity row.** `latestDeviceIdentity()`
  can throw. A throw must not route to `/dashboard` — treat an unreadable
  identity as **no identity** (welcome), log it, and never crash the launch.
  That is the same fail-direction `login_controller.dart`'s own best-effort
  reads already take.
- **`test/widget_test.dart` is a shared, load-bearing file.** It holds several
  unrelated tests. Change only the F1 test's navigation expectations.
- **Ordering vs `MessagingStack.create`.** `main()` builds the stack from
  `selfDeviceId` *before* `runApp`. `completePendingWipe()` must run **before**
  the `AppDatabase` is opened, or the wipe re-creates the file it just deleted.
  This is the subtlest failure in the task.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-AUTH-8**: WHILE a local device cryptographic identity exists, WHEN the application launches, the system SHALL present the dashboard without presenting the welcome or login screens. (FR-AUTH-010)
- **EARS-AUTH-9**: IF the launch-time version evaluation is UPDATE_REQUIRED, THEN the system SHALL present the mandatory-update screen regardless of whether a local device identity exists. (FR-AUTH-011, FR-VER-006)

   `initialRouteFor(versionState)`** rather than re-implementing the

   Delegating means the exact same, already-tested function
   (`test_EARS_VER_10_update_required_routes_to_mandatory_screen`) decides
   that branch, unmodified, rather than a second copy of the same check that
   could drift from it. `initialRouteFor` itself is untouched — still

2. **`test_EARS_AUTH_6_pending_wipe_completed_before_routing`
   (`resolve_initial_route_use_case_test.dart`) proves the wipe-before
   -routing ORDER via a literal mirror of `main.dart`'s own call sequence

   exercising `main()` itself.** `main()` cannot be unit-tested directly
   without booting Firebase — none of `evaluateVersionStateAtLaunch`,
   `initialRouteFor`, or `readInstalledBuildNumber` (this file's existing
   precedent, E14-T02/T04) are tested through real `main()` either; each is
   pulled out and tested as a piece. This task's own Functions contract
   names only the pure `resolveInitialRoute`, so no new production
   composition function was added purely to make this order "really"
   testable end-to-end (that would itself be a second thing deciding —
   or appearing to decide — the route, which task §2 explicitly warns
   against). The test instead uses the REAL `LocalDataWipeService` (not a
   fake) over a temp-dir sentinel/db file, asserts the sentinel and db file
   are genuinely gone afterward (the wipe actually ran, not merely was
   called), and asserts the call order matches `main.dart`'s own literal
   source order — cross-referenced by comment at both ends. `main.dart`'s
   own ordering is additionally verifiable by inspection (§7's own checklist
   item, `main.dart:50` vs `main.dart:55`).
3. **The identity-read failure path (`try`/`catch` around
   `db.latestDeviceIdentity()`) logs via
   `ObservabilityService.instance.logError('session.local_identity_read_failed',

   caught exception object, never any row content).
