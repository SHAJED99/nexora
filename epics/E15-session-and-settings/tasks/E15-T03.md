# E15-T03 · Settings sub-screen shell widget and design-gate registration

## 1. Goal
Build the frame all eight Settings sub-screens compose, once — so that eight
agents cannot each derive their own from the same parent and arrive at eight
slightly different ones, each of which passes its own gate.

## 2. Business logic

Implements `design/screens/settings-shell.md` (`GAP-031`), which is the
contract for `FR-UI-006`'s destinations, `FR-UI-007`'s honesty rule and
`FR-UI-008`'s back behaviour.

Every value in that contract is already measured in `design/screens/settings.md`
or already derived and **human-approved** in `design/screens/settings-storage.md`
(`GAP-024`, ✅ 2026-09-02). **Nothing here is a new visual decision.** If the
implementation needs a colour, radius, size or glyph that appears in neither of
those two files, that is a finding to raise, not a value to pick.

Two of the shell's rules are the ones that will actually be tested by
temptation:

- **SH3's heading colour is `rgb(248, 249, 255)`, not `settings.md`'s measured
  `rgb(234, 241, 255)`.** The measured value does not appear in `settings.md`'s
  own token table, so a derived screen using it carries a value the token check
  cannot find in any source table. `settings-storage.md` §Derivation boundary 3
  made this exact call and the human approved it.
- **There is no bottom navigation bar on a sub-screen.** `settings.md` draws
  one (elements 48-59) because `/settings` is a top-level tab. A sub-screen is
  pushed on top of that tab, not a peer of it.

## 3. What this task does
- Builds `SettingsSubScreenScaffold` — the SH1-SH4 frame (back button,
  `arrow_back`, heading, subtitle) plus the SH5-SH13 vocabulary exposed as
  small composable pieces (section card, section heading, body line, row with
  leading glyph, state label, machine value, selection glyph, empty/error line).
- Registers **all eight** sub-screen ids in `design/sources.yaml` as
  `source: derived`, `design_path: n/a`, `impl_path` per the epic's Screens
  table, `viewports: [390x844]`, `states: [{ name: default }]` — following the
  exact shape `E12-B06` used for `device-enrollment` / `device-enrollment-approval`.
  **This is why every later screen task can run `make design-verify
  SCREEN=<id>` against its own fenced probe dump without touching a shared
  file.**
- Adds a widget test proving the scaffold renders every frame element and that
  the back affordance pops.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT build any of the eight screens.** Not even a stub, not even an
  empty one, not "just to make the route work". `E02-T03` correctly refused to
  navigate to a fabricated screen; this task does not create eight of them.
- **Does NOT register any route or wire any Settings row.** `lib/app/routes.dart`
  and `settings_controller.dart` are **`E15-T11`'s alone** and are not in
  `files:`.
- **Does NOT touch `test/design/design_probe_test.dart`.** That file is
  `E15-T11`'s alone — this is `E08`'s own recorded collision warning being
  honoured ("T09 must not be given the probe fixture… T08 now owns that file").
- **Does NOT change `design/screens/settings.md` or the built `/settings`
  screen.** The hub's own gate is green and stays green.
- **Does NOT invent a switch, a dialog, a spinner, a skeleton, an error colour
  or a new glyph.** `settings-shell.md` §"What this shell deliberately does NOT
  contain" lists all six with the reason for each.
- **Does NOT add a design token that is not already in `lib/core/design/`.**
  If one is genuinely missing, raise it — do not inline a literal.

## 5. Contract

### UI
- **Design contract:** `design/screens/settings-shell.md` — build from this.
- Route: none. This is a widget, not a screen.
- States required: the shell renders identically in all of them; `loading`
  means the *content* slot is unpopulated, never a spinner.
- Gate: **not runnable for this task** — a shell has no screen id and no probe
  dump of its own. Its fidelity is proven by the eight screens that compose it,
  starting with `E15-T04`. The reviewer checks the widget against the
  contract's element table by reading, which is what a contract is for.

### Functions
```yaml
- signature: "SettingsSubScreenScaffold({required String title, required String subtitle, required List<Widget> children})"
  params:
    title: "SH3 — the sub-screen's own heading string, from its own contract"
    subtitle: "SH4 — the sub-screen's own one-line subtitle"
    children: "the screen's own content sections"
  returns: "Widget — the SH1-SH4 frame wrapping children"
  purpose: "One frame, composed eight times, forkable by nobody."
```

### External services & flags
None.

## 6. Risks
- **Eight screens will want to fork this.** The scaffold must be flexible
  enough (a `children` slot, not a fixed layout) that no screen has a reason
  to. If a later screen genuinely cannot compose it, that is a contract
  amendment to `settings-shell.md`, not a local copy.
- **`design/sources.yaml` entries with a wrong id are invisible until a later
  task fails.** `SCREEN=<id>` filters on exactly these; a typo means
  `E15-T06`'s gate silently has nothing to verify. Cross-check all eight ids
  against the eight contract files' own `id:` frontmatter.
- **`impl_path` for a screen with no route yet.** Register the route string the
  epic's Screens table names, even though `E15-T11` is what makes it real —
  `verify.mjs` never reads it on the `impl_flutter` path (`E12-B06`'s own note).
