# E15-T10 · About / Updates screen

## 1. Goal
Answer "what am I running, is it still supported, and what has gone wrong
lately?" — from the components `E14` already shipped, without inventing a
second version story.

## 2. Business logic

Implements `FR-VER-012` against `design/screens/settings-about.md`
(`GAP-038`). Three read-only cards over shipped code: `PackageInfo` via
`readInstalledBuildNumber` (`lib/app/main.dart`),
`VersionPolicyService.cached()`, `EvaluateVersionStateUseCase`, and
`ObservabilityService`'s local log.

**`Version 2.4.1` is a disclosed copy artifact on the HUB row, and it stays
there.** `settings.md` element 46 measures the literal string
`Version 2.4.1, release notes, diagnostic logs`, and the gate compares it
character for character. The real build number is not 2.4.1 and never will be.
`E02-T03` already built that row and it already passes its gate. **This
sub-screen shows the real version; the hub row keeps the design's literal
copy.** Same class of artifact as `GAP-027`'s "export".

**`FR-DIAG-002` binds the log section absolutely.** `ObservabilityService`
already logs **codes** (`version.installed_build_read_failed`,
`recovery.device_identity_read_failed`, …) rather than content. This screen
renders those codes and their timestamps — **and does not expand an entry into
its `cause` object**, because a cause object is exactly where a stack trace
carrying real data would be.

**AB13 states the fail-open default, and that is deliberate.** When no policy
is cached, `EvaluateVersionStateUseCase` treats the build as supported —
`E14-B01`'s whole subject. A user looking at an empty policy card deserves to
know which way the app fails rather than guessing.

## 3. What this task does
- Builds `AboutSettingsController` reading the installed version/build, the
  evaluated `VersionState`, the cached policy and its fetch time, and the local
  log; and `AboutSettingsView` composing `E15-T03`'s scaffold, rendering
  AB1-AB18.
- Adds its own probe test, verifies, and commits the first clean dump as the
  golden.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT change the hub row's `Version 2.4.1` copy.** Doing so reds the
  already-green `settings` design gate for a screen this epic is not otherwise
  touching. This is the specific wrong move this task invites.
- **Does NOT add a "check for updates" button.** `FR-VER-008` already
  re-evaluates on reconnect (`VersionReconnectWatcher`, `E14-B06`) and
  `E14-T04` already evaluates at launch. A third trigger would need an
  in-flight state this design has no spinner for.
- **Does NOT add an update action.** `FR-VER-006`/`FR-VER-007`'s Play in-app
  update flow belongs to `version-update-required.md` and only to it.
  `Update available` at AB8 is a status word, not a button — a dismissible
  `UPDATE_AVAILABLE` nudge is explicitly out of scope per `GAP-029`.
- **Does NOT render a log entry's `cause` object, stack trace, or any expanded
  detail.** Codes and timestamps only.
- **Does NOT add log export, share, copy-to-clipboard, a level filter or a
  clear-log control.** The first three are routes by which
  `FR-DIAG-002`-protected content leaves the device; the last is a state change
  on an audit surface.
- **Does NOT add release notes, a Play Store link, licences, credits, a privacy
  policy or terms.** `GAP-038` carries the release-notes fork with **no
  proposal**; the other four are conventional, unspecified, and three of them
  point at documents this project does not have.
- **Does NOT call `VersionPolicyService.refresh()`.** `main.dart` owns that
  call (`E14-B01`). Reading `cached()` is this screen's whole job.
- **Does NOT touch `lib/app/routes.dart`, `settings_controller.dart`,
  `settings_binding.dart`, `test/design/design_probe_test.dart`, `main.dart` or
  any `E14` component.**

## 6. Risks
- **`readInstalledBuildNumber()` returns `null` on two distinct failures** — a
  `PackageInfo` platform-channel error, and a non-numeric `buildNumber`.
  `E14-B03` deliberately collapsed both to `null` rather than a sentinel.
  Render `null` as AB18, never as `0`.
- **The hub-row copy trap** — see §4, first bullet.
- **`DiagnosticEntry` must not carry `cause`.** Same structural guard as
  `E15-T06`'s `SecurityRecord`: if the field is not in the model, it cannot
  leak into a widget later.
- **`cached()` is a `Future` over a Drift read** that can legitimately return
  `null`. `null` is AB13, not AB18 — an absent policy is not an error.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-VER-18**: This screen SHALL present the installed version and build number, the cached version policy, and the evaluated version state, all read from the shipped `E14` components. (FR-VER-012, FR-VER-005, FR-VER-008)

- **EARS-UI-9**: WHERE a Settings row's subtitle names a capability the application does not implement, the sub-screen SHALL state the absence and SHALL NOT present a control or a value for it. (FR-UI-007)
- **EARS-UI-11**: IF a read fails, THEN the system SHALL show that section's failure line and leave every other section unchanged. (FR-UI-007, NFR-REL-001)
