# E15-T07 · Account screen and sign-out confirmation

> **Two screens, one task, deliberately.** They are one journey — the Account
> screen's only action leads to the confirmation, and the confirmation's copy
> must name exactly what the Account screen has just been showing. Splitting
> them puts the loss list and the thing it describes in two contracts that can
> drift.

## 1. Goal
Give the user a place to see who they are signed in as and what this device's
identity is — and the one honest, fully-explained way out.

## 2. Business logic

Implements `FR-AUTH-013` (the Account screen) and `FR-AUTH-007` (the
confirmation) against `design/screens/settings-account.md` (`GAP-035`) and
`design/screens/sign-out-confirm.md` (`GAP-039`).

**AC14 navigates. It does not sign out.** Tapping Sign out goes to
`/settings/sign-out-confirm` and nothing else happens. `FR-AUTH-006` destroys
every key on the device; a one-tap path to that from a settings list is the
worst affordance this product could ship. AC15 (`Erases everything on this
device.`) sits under the row so a user learns it is destructive **without
tapping the destructive thing**.

**AC7 and AC11 are not filler.** `FR-AUTH-002` (account identity ≠ device
identity) and `ADR-0005` are the least intuitive facts in this product, and
this is the only screen where both are visible at once. A user who does not
read them here will read the confirmation as "sign out of Google".

**SO6 calls `E15-T01`'s `SignOutUseCase.call()` and nothing else.** This task
contains no persistence logic, no `AppDatabase` handle, no file deletion and no
auth call of its own. After the use case completes it navigates with a
**stack-replacing** `Get.offAllNamed(Routes.welcome)` — so no screen holding a
controller with a handle to the now-deleted database survives (epic §Risks,
row 1).

**`sign-out-confirm` is a full screen, not a dialog.** This design draws no
dialog or bottom-sheet primitive anywhere — `GAP-025` established it and
`GAP-029` acted on it for the mandatory-update block. The most destructive
action in the product gets no less.

## 3. What this task does
- Builds `AccountController` + `AccountView` rendering AC1-AC17: the signed-in
  account identifier (`DeviceIdentities.accountUid`), this device's identity
  fingerprint (`identity_key_hex.dart`), the linked-device list
  (`FirebaseMetadataService.readOwnDeviceIds`), and the Sign out row.
- Builds `SignOutConfirmController` + `SignOutConfirmView` rendering SO1-SO7,
  composing **`welcome.md`'s** centred single-focus layout — **not**
  `E15-T03`'s settings scaffold (see §4).
- Wires SO6 → `SignOutUseCase.call()` → `Get.offAllNamed(Routes.welcome)`, and
  SO7/back → pop.
- Adds two probe tests, verifies both, commits both first clean dumps as
  goldens.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT sign out from AC14.** One tap on a settings row must never destroy
  a device. AC14 navigates.
- **Does NOT implement any part of the wipe.** `LocalDataWipeService`,
  `GoogleAuthService.signOut()`, the sentinel file and the teardown order are
  **`E15-T01`'s alone** and none of its files is in `files:` here.
- **Does NOT use a dialog, an `AlertDialog`, a bottom sheet, or a snackbar with
  an action** for the confirmation. Forbidden by `sign-out-confirm.md`
  §Prohibition 1, on `GAP-025`/`GAP-029`'s already-recorded finding.
- **Does NOT compose the settings scaffold on `sign-out-confirm`.** That screen
  is `welcome.md`-shaped, exactly as `version-update-required.md` is. Using the
  settings frame would make a blocking, destructive decision look like a
  settings page.
- **Does NOT add a typed confirmation phrase, a second confirmation, a
  countdown, an undo window, or a progress/spinner state.** All five are named
  and rejected in `sign-out-confirm.md` §Derivation boundary; the last is
  impossible anyway (`FR-AUTH-009` resumes an interrupted wipe rather than
  watching it).
- **Does NOT add an "export before you go" affordance.** `GAP-027` established
  this app has no export; offering one here would be the cruellest place to
  promise it.
- **Does NOT add a second destructive action** — no delete-account, no
  reset-keys, no unlink-device, no per-row remove on the linked-device list.
  `FR-AUTH-013` names exactly one action, and the remote half is `Q-SEC-009`'s
  open subject.
- **Does NOT add "switch account".** Explicitly rejected by the human on
  2026-09-08.
- **Does NOT assert a destructive colour.** `GAP-035`/`GAP-039` share one
  **unanswered** fork, inherited from `GAP-021`. AC14 and SO6 are built in the
  neutral treatment until the human answers. Picking a red is settling a parked
  design decision by taste.
- **Does NOT add an avatar, display name or profile section.** No profile
  entity exists.
- **Does NOT touch `lib/app/routes.dart`, `settings_controller.dart`,
  `settings_binding.dart` or `test/design/design_probe_test.dart`** — all four
  are `E15-T11`'s alone.

## 5. Contract

### UI
- **Design contracts:** `design/screens/settings-account.md` (primary, in
  frontmatter) **and** `design/screens/sign-out-confirm.md` (the second screen
  this task builds — named here because the frontmatter field holds one path).
- Routes: `/settings/account`, `/settings/sign-out-confirm` (both registered by
  `E15-T11`).
- **Account** states: `default` · `loading` · `empty` (the linked-device list
  only — AC16, the ordinary state for a single-phone user; **the sign-out row
  is unchanged**) · `error` (AC17 replaces the affected card's values; **the
  sign-out row is never hidden by a failed read** — a user must always be able
  to reach the confirmation, especially when something is wrong).
- **Sign-out confirm** states: `default` only. Every string is static; there is
  nothing to load, be empty, or fail.
- Gates: `make design-verify SCREEN=settings-account …` and
  `make design-verify SCREEN=sign-out-confirm …`, **both green before the PR**.
  Both are derived screens with no design source — goldens extracted from the
  first clean dumps (`design-fidelity` §3).

### Functions
```yaml
- signature: "AccountController.accountUid -> Rx<String?>"
  returns: "DeviceIdentities.accountUid for this device's latest identity"
  purpose: "AC6. Null renders AC17's failure line, never a blank."

- signature: "AccountController.deviceFingerprint -> Rx<String?>"
  returns: "hexEncodeIdentityKey of this device's own identity public key"
  purpose: "AC10. Uses the SAME encoding device ids already use
            (identity_key_hex.dart) — not a second representation."

- signature: "AccountController.linkedDevices -> RxList<String>"
  returns: "FirebaseMetadataService.readOwnDeviceIds(uid); best-effort, empty on failure"
  purpose: "AC13. A network failure shows AC16/AC17, never blocks the screen."

- signature: "SignOutConfirmController.confirm() -> Future<void>"
  returns: "void — calls SignOutUseCase.call(), then Get.offAllNamed(Routes.welcome)"
  purpose: "FR-AUTH-006's single entry point from the UI. Contains no
            persistence logic of its own."

- signature: "SignOutConfirmController.cancel() -> void"
  returns: "void — pops back to /settings/account"
  purpose: "SO7. The cancel path is the default outcome, not the exceptional one."
```

### External services & flags
`FirebaseMetadataService.readOwnDeviceIds` (existing, best-effort). Nothing new.

## 6. Risks
- **A surviving controller after the wipe.** If `confirm()` pops rather than
  replacing the stack, `/settings/account` is still mounted holding a
  repository over a deleted file. Use `Get.offAllNamed`.
- **A failed sign-out leaves the user on the confirm screen.** That is correct:
  `SignOutUseCase` propagates a wipe failure, and the screen must show it
  rather than navigating to `/welcome` as if it had worked. **Do not swallow
  it.** `E15-T01` leaves the sentinel in place so the next launch finishes the
  job.
- **The loss list is long and exact.** Eleven verbatim strings in
  `sign-out-confirm.md` §Copy. Every phrase maps to a real surface in
  `FR-AUTH-006`'s enumeration; do not paraphrase, shorten or reorder.
- **The `Signing back in creates a brand-new identity…` line is the one people
  drop.** Without it a user reasonably assumes signing back in restores what
  they had — which is exactly what `FR-AUTH-008` says will not happen.
- **`readOwnDeviceIds` is a network call on screen load.** Best-effort, and it
  must not gate the sign-out row.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-AUTH-7**: WHEN the user reaches the sign-out confirmation, the system SHALL name every category of data that will be destroyed and SHALL state that it is unrecoverable, before any destructive action is possible. (FR-AUTH-007, FR-RECOVER-002)
- **EARS-AUTH-12**: WHEN the Account screen is shown, the system SHALL present the signed-in account identifier, this device's own identity fingerprint, and the other devices registered to the account. (FR-AUTH-013)
- **EARS-UI-10**: WHEN the back affordance is used, the system SHALL return to the Settings hub (Account) or to the Account screen (confirmation). (FR-UI-008)
- **EARS-UI-11**: IF a read fails, THEN the system SHALL show that section's failure line and leave every other section — including the sign-out row — unchanged. (FR-UI-007, NFR-REL-001)

### Manual
1. `/settings/account` → account id, fingerprint, device list, Sign out row.
2. Tap Sign out → the confirmation screen, full-screen, no dialog, with the

4. Confirm → welcome screen; relaunch → still welcome, new identity on sign-in.
