# E15-B03 · A second `BackgroundService()` hijacks the shared native event registration

## The defect
`lib/app/bindings.dart:276` constructs a `BackgroundService()` inline for
`BackgroundLifecycleObserver` — a permanent, app-lifetime observer — but never
registers that instance as a findable singleton (`Get.put<BackgroundService>`
is never called). `lib/features/settings/presentation/settings_binding.dart`
(E15-T11, line 151) constructs a **second, independent** `BackgroundService()`
for `BatterySettingsController`. `BackgroundService`'s constructor calls
`BackgroundEventsApi.setUp(...)` on the SAME default (empty-suffix) platform
channel every time (`background_service.dart`'s own header documents that
distinct suffixes are what let multiple instances coexist without clobbering
each other's handler) — and Pigeon's generated `setUp` calls
`setMessageHandler` on that channel name unconditionally, so the second
registration silently **replaces** the first.

`BatterySettingsView` is a `GetView<BatterySettingsController>`, so simply
navigating to Settings → Battery resolves the lazy factory and permanently
steals `onServiceStateChanged`/`onPowerStateChanged` from
`BackgroundLifecycleObserver` for the rest of the process — with no
workaround short of an app restart.

## Repro
1. Launch the app (this registers `BackgroundLifecycleObserver`'s handler,
   the one production code actually depends on for background lifecycle
   management).
2. Navigate to Settings → Battery (constructs the second `BackgroundService`,
   silently replacing the handler).
3. Background/foreground the app, or trigger any native background-service
   state change. `BackgroundLifecycleObserver.onServiceStateChanged`/
   `onPowerStateChanged` no longer fire — the app's real background-service
   lifecycle management (`FR-PLAT-001`/`FR-PLAT-002`/`FR-PLAT-003`,
   `EARS-PLAT-11`) has silently stopped working.

## Expected
Exactly one `BackgroundService` instance exists for the process, shared by
`BackgroundLifecycleObserver` and any screen (like Battery settings) that
also needs to read its state.

## Actual
Two independent instances are constructed, and the second one silently wins
the shared platform channel — a native-event handler hijack with no error,
no log, and no visible symptom until background-lifecycle management stops
working.

## Severity
**S2.** Not a crash, but a silent, deterministic regression in a core
lifecycle mechanism this messaging app depends on to keep the mesh
transport alive in the background — triggered by simply opening one Settings
sub-screen.

## Fix direction
`AppBinding` should register its shared instance as a findable, permanent
singleton keyed on the **`BackgroundControl` interface, not the
`BackgroundService` concrete type** — `lib/app/bindings.dart:67,102,276`
deliberately keeps a `BackgroundControl? backgroundControl` injection seam
that tests fill with `BackgroundStub`; a literal
`Get.put<BackgroundService>(...)` would bypass that seam and break every
stub-based test relying on it. The correct registration is
`Get.put<BackgroundControl>(_backgroundControl ?? BackgroundService(),
permanent: true)`, constructed once alongside `BackgroundLifecycleObserver`.
Then `settings_binding.dart`'s `BatterySettingsController` registration
should resolve it via `Get.find<BackgroundControl>()` instead of
constructing a second instance — the same "shared singleton, not a fresh
instance per screen" pattern this app already uses for `AppDatabase`,
`MessagingStack`, and every repository singleton.

## What this fix does NOT do
- Does NOT change `BackgroundService`'s own API or constructor signature.
- Does NOT change `BackgroundLifecycleObserver`'s own logic.
- Does NOT touch any other `settings_binding.dart` registration — every
  other sub-screen controller registration in that file is unaffected.
- Does NOT add a new channel suffix or otherwise change the platform
  channel contract — the fix is sharing one instance, not partitioning two.
