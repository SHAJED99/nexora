# E13-B01 · the eviction sweep is O(table) on every `allow()`, and the table is attacker-growable

## The defect

This is a **seam between E13-T01 and E13-T07**, owned by neither task's
own review.

`E13-T01` chose the schema and wrote the reasoning into both
`abuse_tables.dart:26-29` and the `from < 18` migration
(`database.dart:570-572`):

> "No index needed: the only local access pattern is a point lookup by
> `bucketKey`, which the PK's own implicit index already serves."

That was true when T01 landed. **`E13-T07` then invalidated the premise
and did not revisit it.** To close `OQ-E13-T01-1` (unbounded counter-row
growth) it added an opportunistic eviction at the top of `allow()`:

```dart
// rate_limiter.dart:74-79
await (_db.delete(_db.rateLimitCounters)..where(
      (t) => t.windowStartMs.isSmallerThanValue(
        nowMs - _staleRowMaxAge.inMilliseconds,
      ),
    ))
    .go();
```

`windowStartMs` is not indexed. So **every single admission decision in
the app** — every relayed frame (twice: the `relay:` count gate and the
`storage_volume:` byte gate, `inbound_pipeline.dart:477` and `:510`),
every connection-request evaluation, every group create/add, every
device registration — now performs a full scan of `rate_limit_counters`
before doing its point lookup.

The table's size is attacker-controlled. `relay:${frame.source}` and
`storage_volume:${frame.source}` are keyed on the unverified, claimed
wire `frame.source` (T03's own accepted limitation), so an attacker
rotating claimed source ids adds **two new rows per frame**, each of
which survives for `_staleRowMaxAge` (2 days). Each added row makes
every subsequent `allow()` — the attacker's and every legitimate
caller's — measurably more expensive. The work is quadratic in the
number of frames the attacker sends.

That inverts the purpose of `FR-ABUSE-001`, whose own list explicitly
includes battery/network-exhaustion attacks: the mechanism built to bound
what a flooder can force this device to do is itself the thing doing
increasing work per flooded frame.

## Repro (measured, not reasoned)

Reviewer-authored probe against `AppDatabase.forTesting(NativeDatabase
.memory())` and the real `RateLimiter`, 10,000 rotated bucket keys per
batch:

```
batch 0: table now 10000 rows, 10000 allows took  2766ms
batch 1: table now 20000 rows, 10000 allows took  4204ms
batch 2: table now 30000 rows, 10000 allows took  6184ms
batch 3: table now 40000 rows, 10000 allows took  8008ms
batch 4: table now 50000 rows, 10000 allows took 13109ms
```

0.28 ms/call at 10k rows -> 1.31 ms/call at 50k rows: a 4.7x slowdown for
a 5x table, i.e. per-call cost tracking table size linearly, exactly as
an unindexed scan predicts. This is an in-memory SQLite on a desktop CPU;
a real device on disk-backed storage is strictly worse.

Steps to reproduce:
1. Open an in-memory `AppDatabase` and a `RateLimiter` over it.
2. Call `allow('relay:a-$i', maxCount: 60, window: 1 min)` for
   i = 0..50000, timing each block of 10000.
3. Observe per-call latency rising monotonically with row count.

## Expected

`FR-ABUSE-001` — an admission check bounds what an attacker can force
this device to do. Per-decision cost must be O(1) in the number of
distinct bucket keys the attacker has touched, not O(N).

## Actual

Per-decision cost is O(N) with N attacker-growable to ~345,000 rows
(2-day retention x ~1 relayed frame/second x 2 buckets per frame), paid
by every rate-limited path in the app, not just the relay path.

## Secondary finding (same root cause, bookkeeping)

The tracker records `OQ-E13-T01-1` as "resolved". More precisely: it is
**bounded, not resolved**. Verified both directions by probe:

- Rows older than `_staleRowMaxAge` (2 days) **are** evicted — 50
  three-day-old rows plus one `allow()` leaves exactly 1 row. The
  mechanism works as designed.
- Within the retention window nothing is bounded: 500 rotated
  `storage_volume:` keys still produce **500 permanent rows and zero
  denials** — byte-for-byte the same result E13-T02's reviewer originally
  filed `OQ-E13-T01-1` for.

So the eviction converts "unbounded forever" into "unbounded across a
rolling 2 days". That is a real improvement and worth keeping; it is not
what "resolved" implies, and the difference is exactly what makes the
scan cost above reachable. The tracker line should say bounded-to-2-days.

## Severity

**S3.** No crash, no data loss, no security hole — degraded performance
and battery drain under a sustained attack, with no user-side workaround.
Not S2 because it requires an attacker sustaining a rotating-source flood
within radio range for hours to reach the row counts where the slowdown
bites; not S4 because the degradation is real, attacker-triggered,
affects every rate-limited path in the app rather than only the flooded
one, and directly undercuts a `FR-ABUSE-001` goal.

Priority is the human's call (`bug_priorities` gate).

## Fix direction

Cheapest correct fix is one line of schema: add
`@TableIndex(name: 'idx_rate_limit_counters_window_start', columns: {#windowStartMs})`
to `RateLimitCounters`, bump `schemaVersion` to 19, and create the index
in a `from < 19` step (`createIndex`, additive, no backfill). That makes
the eviction's range delete an index scan over only the rows it will
actually delete, restoring O(1)-ish per-call cost.

Worth considering alongside it (not instead of): only run the eviction on
a sampled fraction of calls (e.g. when `nowMs % 64 == 0`) rather than
every call. The sweep is opportunistic housekeeping, not part of the
admission decision's correctness — `allow()`'s verdict is identical
whether or not a stale row was deleted first — so it does not need to run
on the hot path every time. Note the current code deliberately runs it
inside the same transaction; a sampled sweep keeps that property on the
calls where it fires.

Whichever is chosen, the stale "No index needed" comments in
`abuse_tables.dart:26-29` and `database.dart:570-572` must be corrected —
they are now actively wrong and are what let this through.

## What this fix does NOT do

- Does **not** change `_staleRowMaxAge`, the eviction policy's semantics,
  or when a row becomes stale. The 2-day bound is a deliberate T07
  decision with its own documented reasoning; this bug is about the cost
  of enforcing it, not the value.
- Does **not** attempt to close the rotating-`frame.source` evasion
  itself. That is E13-T03's explicitly accepted limitation, consistent
  with this codebase's TOFU posture (same class as `E09-B09`), and needs
  a protocol-level source-authentication decision (rule 3), not an index.
- Does **not** touch any `RateLimiter` caller: no bucket key scheme, no
  limit number, no window duration, and no call site in
  `inbound_pipeline.dart`, `evaluate_connection_request_use_case.dart`,
  `device_identity_repository.dart`, `group_membership_service.dart` or
  `sign_in_use_case.dart` changes.
- Does **not** change `allow()`'s public signature or its return
  semantics; a denied call must still not increment.
- Does **not** add an index to any other table, or revisit any other
  table's own "no index needed" reasoning.
