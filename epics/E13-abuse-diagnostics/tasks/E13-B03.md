# E13-B03 · `SentryFlutter.init()` hangs in a VM test — root cause, not a test-seam gap

## Re-scoped 2026-09-07 (by the E13-B02 reviewer's own recommendation)

**This bug's original headline claim is now false.** `E13-B02`
(`lib/core/observability/observability_service.dart`) added
`ObservabilityService.debugOverrideInstanceClientForTesting` — a real,
`@visibleForTesting`-guarded seam that lets a test substitute the client
backing the shared `.instance` singleton, with a restore closure
registered via `addTearDown` (LIFO-safe, and even a leaked override only
degrades to "logs dropped", never "reaches the real Sentry client" — see
`E13-B02`'s own reviewer verdict for the full safety analysis). This
resolves this bug's own §Expected ("a documented, safe way to do so")
and its first §Suggested direction bullet.

**What's left, and the only reason this bug still exists**: the SECOND
§Suggested direction bullet was never addressed — `SentryFlutter.init()`
itself still hangs (not throws, not completes) when called for real
inside a `flutter test` VM with no platform/engine binding. The seam
means nothing production-facing needs to call `.instance.init()` for
real in a test anymore, so this is now a narrower, lower-priority
question: is the hang itself worth fixing at the source (e.g. does
`SentryObservabilityClient.init()` need to skip native bootstrap when
the DSN is empty, rather than attempting it and hanging), purely so that
a FUTURE test author who ISN'T aware of the new seam doesn't rediscover
the same hang the hard way. Downgraded from S3/P2 to S4/P3 accordingly —
the seam already closes the practical, load-bearing gap this bug was
filed to protect against.

## The defect (original, still accurate for what remains)

`ObservabilityService.instance` (`lib/core/observability/observability_service.dart:145`)
is a `static final` singleton, constructed once with the real
`SentryObservabilityClient()` as its default client:

```dart
ObservabilityService._({ObservabilityClient? client})
    : _client = client ?? SentryObservabilityClient();

static final ObservabilityService instance = ObservabilityService._();
```

The only test-facing seam, `ObservabilityService.withClient(fakeClient)`
(used correctly by `observability_service_test.dart`), constructs a
**separate** instance — it cannot substitute the client backing the shared
`.instance` singleton. Any production call site (like `LoginController`,
which calls `ObservabilityService.instance.logError(...)` directly, with
no injected `ObservabilityService`/`ObservabilityClient` parameter) can
therefore only be observed in a test by exercising the REAL client.

## Repro (confirmed)

An isolated probe — a single `testWidgets` calling only
`await ObservabilityService.instance.init().timeout(Duration(seconds: 5), onTimeout: () => print('TIMED OUT'))` —
never printed "TIMED OUT" and never completed even after several minutes
inside a plain `flutter test` run (no `--platform chrome`, no real device).
Since this is a `.timeout()`-wrapped `Future`, an ordinary slow-but-
eventually-completing async operation would still have fired the timeout
callback; the fact that it did not strongly suggests a genuinely blocking,
non-cancellable native/network call inside `SentryFlutter.init()` — likely
attempting to bootstrap the native Sentry platform-channel integration
with no real engine/platform binding present to answer it.

## Expected

A test should be able to exercise `ObservabilityService.instance`'s real
call sites (production code that hardcodes `.instance`, not an injected
client) without risking an indefinite hang, OR there should be a
documented, safe way to do so.

## Actual

Calling `ObservabilityService.instance.init()` for real, inside a `flutter
test` VM environment, hangs indefinitely with no timeout, no error, no
diagnostic — the test run itself must be killed externally.

## Severity

**S3** — no production impact (this never manifests outside a test
process), but it silently removed real test coverage: `E12-B08`'s own
regression test had to have its log-content assertion removed at this
merge (see `login_controller_enrollment_gate_test.dart`'s own comment on
`test_EARS_AUTH_3_device_identity_read_failure_falls_through_to_dashboard`)
because there was no other safe way to verify it. Any FUTURE test wanting
to verify a log message from a production call site hardcoding
`ObservabilityService.instance` will hit the same wall.

## Suggested direction (not binding, builder's call at dispatch)

- **This is the only remaining direction** (the seam bullet above is
  DONE, delivered by `E13-B02`): investigate why `SentryFlutter.init()`
  specifically hangs rather than completing quickly or throwing when no
  DSN is configured and no platform binding exists — if there's a
  legitimate fix inside `SentryObservabilityClient.init()` itself (e.g.
  skipping native bootstrap entirely when the DSN is empty, rather than
  attempting it and hanging), that closes the root cause. If the
  investigation concludes this is an unfixable `sentry_flutter` SDK
  behavior (not something this app's own wrapper can control), document
  that finding and close this bug rather than leaving it open
  indefinitely for something outside this codebase's control.

## What this fix does NOT do
- Does NOT restore the specific log-content assertions removed from
  `login_controller_enrollment_gate_test.dart` — a real seam now exists
  (`E13-B02`); restoring those specific assertions with the new seam is
  a natural, separate follow-up if ever wanted, not part of this task.
- Does NOT change any of `SentryObservabilityClient`'s privacy-conscious
  configuration (`ADR-0006`, `E13-T06`) — this is a root-cause
  investigation, not a behavior change.
- Does NOT re-implement or modify `debugOverrideInstanceClientForTesting`
  (`E13-B02`'s own seam) — that part of this bug's original scope is
  already done and reviewed.

## Run log
- **Setup**: `git worktree add ../wt-E13-B03 -b epic_13_bug_03
  origin/development`, HEAD at `55dcad9`.
- **Investigation, step 1 — reproduce with a bare `test()`**: wrote the
  regression test as a plain `test()` first, calling
  `SentryObservabilityClient().init()` directly with the default empty
  DSN, wrapped in `.timeout(Duration(seconds: 5))`. This test PASSED
  immediately even on the unmodified pre-fix code — it did not
  reproduce the bug. This matters: it means a bare `flutter test`
  `test()` (no `testWidgets`, no active `TestWidgetsFlutterBinding`) is
  NOT sufficient to reproduce this hang, because `flutter_test`'s
  automatic platform-channel mocking (present once any Flutter test
  binding is active) answers unmocked channel calls with a
  `MissingPluginException` right away rather than leaving them
  unanswered.
- **Investigation, step 2 — reproduce with `testWidgets`**: rewrote two
  disposable hand-probes (not committed) — one calling
  `ObservabilityService.instance.init()`, one calling
  `SentryObservabilityClient().init()` directly, both inside a
  `testWidgets` callback, both wrapped in
  `.timeout(Duration(seconds: 8), onTimeout: () => fail('TIMED OUT'))`.
  Both hung for the full ~57s until `flutter test`'s own outer per-test
  timeout killed them with "did not complete" — critically, the INNER
  8s `.timeout()` never fired either, meaning the underlying `Future`
  genuinely never completes (not merely "slower than 8s"). This exactly
  reproduces the original bug's own repro description. Confirms the
  bug requires a real widget-test binding, not just any `flutter test`
  process.
- **Investigation, step 3 — read `sentry_flutter` 8.14.2 source**
  (`$PUB_CACHE/hosted/pub.dev/sentry_flutter-8.14.2/lib/src/sentry_flutter.dart`):
  `SentryFlutter.init()` always builds a default integration list
  (`_createDefaultIntegrations`) regardless of DSN — including
  `WidgetsFlutterBindingIntegration`, and (because
  `PlatformChecker.hasNativeIntegration` returns `true` for every
  desktop/mobile platform, `platform_checker.dart:44-50` — this app's
  Windows dev/CI host included) the native SDK binding plus
  `NativeAppStartIntegration`/`FramesTrackingIntegration`/
  `ReplayIntegration`, and unconditionally `LoadReleaseIntegration`
  (which awaits `package_info_plus`'s `PackageInfo.fromPlatform()`, a
  platform-channel call). `SentryFlutter.init()` then calls
  `package:sentry`'s `Sentry.init()`
  (`$PUB_CACHE/hosted/pub.dev/sentry-8.14.2/lib/src/sentry.dart:79-81`),
  whose ONLY DSN guard is `if (sentryOptions.dsn == null) throw
  ArgumentError(...)` — an EMPTY string (this app's actual default,
  `String.fromEnvironment('SENTRY_DSN')` with no dart-define set) is
  not null, so it passes this guard and `_callIntegrations`
  (`sentry.dart:183-190`) runs the ENTIRE default integration list
  unconditionally, with no public `SentryFlutterOptions` flag to skip
  it while the DSN is unset. There is no way for this app's wrapper to
  ask `SentryFlutter.init()` itself to skip that pipeline for an empty
  DSN — confirmed by reading the full public surface of
  `SentryFlutterOptions` (`autoInitializeNativeSdk` only gates the
  native-crash-handler's own native-binding init call, not
  `WidgetsFlutterBindingIntegration`/`LoadReleaseIntegration`/the
  binding's mere construction).
- **Conclusion**: this narrows to "why does one of those integrations
  hang under `testWidgets` specifically" (most likely a default
  integration awaiting a widget frame callback that only fires once a
  frame is pumped, which `init()`'s caller never does and has no reason
  to) — but the task's own §Suggested direction only asks whether
  `SentryObservabilityClient.init()` can avoid triggering the pipeline
  at all when there's no DSN, not to fully instrument sentry_flutter's
  internals to name the exact integration. Since an empty DSN means
  there is nothing to send in the first place, skipping the call
  entirely is both a legitimate production fix (not a test workaround)
  and sufficient to close this without needing to pinpoint the exact
  integration.
