# E13-T03 · Rate-limit message flooding and relay abuse at RelayEngine admission

## 1. Goal
Close three more of `FR-ABUSE-001`'s eight named vectors: a sender flooding
this device with messages, a peer abusing this device as a relay for
someone else's traffic, and — as a direct consequence of bounding both —
the "network-resource abuse" and "battery-exhaustion" vectors, whose
concrete mechanism in this codebase is repeated inbound relay/message
traffic forcing this device to do expensive work (decrypt, re-route,
radio wake) on demand. No separate admission point for battery/network
abuse was found in this codebase's mesh/routing layer beyond this one and
`E13-T02`'s connection-request gate (`RouteCostCalculator` is a pure local
computation, not something a remote peer invokes directly) — if a genuinely
distinct battery/network-drain mechanism is later found, it needs its own
task, not a silent extension of this one; recorded as an epic-level Open
Question, not assumed solved here.

## 2. Business logic
`FR-ABUSE-001`. `RelayEngine.enqueue` (per `relay_engine.dart:~119`) accepts
any packet handed to it and queues it (`RelayDeliveryState.queued`),
governed only by priority tier and TTL/expiry — never by how often ONE
sender has already enqueued something. The file's own header (`~53-59`)
already anticipates this: "diagnostics (§3, later E13 needs)."

**Superseded by `Q-E13-T03-1`'s resolution (see Open Questions below).**
`RelayEngine.enqueue` turned out to have no sender-identity parameter or
column to gate on at all, and no existing rejection path — adding one would
have meant a schema migration and six call-site changes, all outside this
task's original `files:` fence. The human's resolution moves the gate to
`InboundPipeline`'s forward branch instead (`inbound_pipeline.dart`'s
`!isForUs` case) — the one caller that already has a candidate sender
identity in scope (`frame.source`) before `enqueue` is ever called. A
sender over its limit is denied there: the packet never reaches
`enqueue`, never enters the relay queue, never counts against
`RelayEngine`'s existing priority/TTL bookkeeping — this is admission
control, not a queue-eviction policy; `RelayEngine` itself (including its
expiry sweep, `~371-378`) is untouched by this task, exactly as originally
intended.

## 3. What this task does (as actually implemented — corrected per `Q-E13-T03-1`)
- `InboundPipeline` gains a constructor-injected `RateLimiter` dependency
  (`RateLimiter? rateLimiter`, defaulting to `RateLimiter(stack.db)` —
  matches this codebase's established "optional named param with a real
  default, overridable for tests" DI pattern, e.g.
  `MessagingStack.create`'s own `transport`/`store`/`cryptoService`
  params).
- `_handleBuffer`'s forward branch (`!isForUs`, `inbound_pipeline.dart`)
  calls `_rateLimiter.allow('relay:${frame.source}', maxCount: 60, window:
  1 minute)` BEFORE `RelayEngine.enqueue`. Denied ⇒ `counters.rateLimited++`
  and an early `return` — `enqueue` is never called, `counters.forwarded`
  is never incremented.
- One bucket key per claimed sender identity (`frame.source`), not per
  (sender, priority) or per (sender, destination) — a flooding sender is
  throttled regardless of which priority tier or destination it targets,
  matching `FR-ABUSE-001`'s framing ("message flooding", "relay abuse") as
  sender-scoped, not route-scoped.
- Concrete limit: `maxCount: 60`, `window: 1 minute` (~1/sec sustained) —
  reasoning and the accepted `frame.source`-is-unverified limitation are in
  the Run log below.

## 4. What this task does NOT do
- Does **not** change `RelayEngine`'s existing priority tiers,
  TTL/expiry sweep, or delivery-state machine — only what happens at
  `enqueue`'s very entry, before any of that existing logic runs.
- Does **not** distinguish 1:1 messages from group/relay traffic at the
  rate-limit layer — `FR-ABUSE-001` names "message flooding" and "relay
  abuse" together, and `RelayEngine` is the one shared admission point for
  both per this task's own investigation; if execution reveals these are
  NOT the same admission point after all, STOP and raise an Open Question
  rather than silently building two separate gates under one task.
- Does **not** touch `group_membership_service.dart`'s own `handleWireFrame`
  — group-invite-specific abuse is `E13-T04`'s task, not this one, even
  though both ultimately touch inbound wire traffic.
- Does **not** add a queue-size cap (a distinct mitigation from per-sender
  rate limiting) — out of scope unless a later bug names it as insufficient.

## 6. Risks
- `RelayEngine.enqueue`'s exact current signature and return/rejection
  shape were not fully verified at task-sharding time (survey found the
  method and its queueing behavior, not its complete type signature) —
  the executing agent must read the file in full before writing this
  contract's implementation; if the rejection shape genuinely doesn't
  exist yet (every packet today is unconditionally accepted), that is a
  bigger seam than a one-line contract change and should be flagged as a
  Deviation, not silently designed around.
- A single global per-sender bucket cannot distinguish "one sender flooding
  many different peers via relay" from "one sender messaging one peer a
  lot" — both are folded into the same `relay:$senderId` key by this task's
  design (§3); acceptable per `FR-ABUSE-001`'s own framing, not a gap to
  silently expand scope to fix.
