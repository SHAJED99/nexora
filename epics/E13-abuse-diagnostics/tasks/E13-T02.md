# E13-T02 · Rate-limit connection-request spam and device-registration abuse

## 1. Goal
Close two of `FR-ABUSE-001`'s eight named vectors: a device id that spams
connection requests, and an account that spams new-device registrations.

## 2. Business logic
`FR-ABUSE-001`. Today, `EvaluateConnectionRequestUseCase.call` (per
`E02-T0x`'s own contract, unchanged by this task) is a pure lookup: it reads
whatever `RelationshipState` is already stored for a `deviceId` and defaults
to `unknown` if none exists — nothing throttles how OFTEN it may be called
for the same or many device ids. `DeviceIdentityRepository.createDeviceIdentity`
is likewise an unthrottled write.

This task adds an admission check BEFORE each of those two existing
operations, using `E13-T01`'s `RateLimiter`, and denies (rather than
silently dropping) when a caller is over its limit — the caller (whichever
UI/controller invokes these) decides what "denied" looks like to a user;
this task's own contract is the boolean gate only.

Bucket keys (this task's own decision, per `E13-T01` §4): 
`"connection_request:<deviceId>"` for connection requests,
`"device_registration:<accountUid>"` for device registration — keyed by the
REMOTE device id in the first case (limits how often any single peer can be
evaluated) and by the LOCAL account uid in the second (limits how many
devices one account can register in a window), matching each vector's own
actual abuse shape.

## 3. What this task does
- `EvaluateConnectionRequestUseCase.call` gains a `RateLimiter` dependency
  (constructor-injected, matching this codebase's existing DI pattern for
  every other use case) and calls `allow('connection_request:$deviceId',
  maxCount: <chosen>, window: <chosen>)` before doing its existing lookup;
  returns a deny-shaped result (mirroring the existing `blocked`/`unknown`
  result shape, not a thrown exception — a rate-limited caller is not a
  programming error) when denied.
- `DeviceIdentityRepository.createDeviceIdentity` gains the same dependency
  and the same admission check keyed by `accountUid`, called before its
  existing `_db.createDeviceIdentity` write; throws (or returns a mapped
  failure, matching `sign_in_use_case.dart`'s existing error-mapping
  convention — follow whatever that file already does, do not invent a new
  error shape) when denied.
- Concrete limit numbers and window durations: this task's own decision at
  implementation time, informed by realistic legitimate use (a user
  reasonably re-requesting a connection a few times after a mesh dropout;
  a user reasonably registering 2-3 devices in a sitting) — document the
  chosen numbers and the reasoning in the Run log, not silently guessed.

## 4. What this task does NOT do
- Does **not** change `RelationshipRepository`, `RelationshipState`, or any
  trust/block semantics — this task only gates HOW OFTEN the existing
  lookup runs, never WHAT it returns when it does run.
- Does **not** change what a UI/controller does when denied — that is
  whichever screen calls these (out of this task's `files:` fence); this
  task only makes "denied" a reachable outcome these callers must now
  handle (flag as a Deviation if a caller's existing exhaustive
  switch/error-mapping breaks because of the new outcome — do not silently
  swallow it into an existing case).
- Does **not** implement device-registration abuse via Firebase (i.e. does
  not touch `FirebaseMetadataService`/`database.rules.json`) — this is a
  purely LOCAL admission check before the local Drift write; a
  Firebase-side registration-abuse control (if ever wanted) is a distinct,
  separate task and not silently folded in here.
- Does **not** add any UI copy, error screen, or design contract — no
  `layer: frontend` surface is touched.

## 5. Contract

### Functions
```yaml
- signature: "EvaluateConnectionRequestUseCase.call(deviceId: String) -> Future<ConnectionRequestResult>"
  params: { deviceId: "the remote peer's device id being evaluated" }
  returns: "unchanged result type; gains a rate-limited/denied outcome as a new reachable case, exact shape matching this task's existing result type's convention"
  purpose: "adds a RateLimiter.allow('connection_request:$deviceId', ...) gate before the existing lookup logic"
- signature: "DeviceIdentityRepository.createDeviceIdentity(deviceId: String, accountUid: String) -> Future<int>"
  params: { deviceId: "the new device id being registered", accountUid: "the authenticated account creating it" }
  returns: "unchanged on success; throws/maps to a failure (match sign_in_use_case.dart's existing convention) when the accountUid is over its registration-rate limit"
  purpose: "adds a RateLimiter.allow('device_registration:$accountUid', ...) gate before the existing write"
```
Note: `createDeviceIdentity`'s current signature (per `lib/features/login/data/device_identity_repository.dart`) takes only `deviceId` — verify at execution time whether `accountUid` is already available at this call site (via `sign_in_use_case.dart`) or needs threading through; do not invent a global/singleton account-uid lookup if it isn't already passed down this call chain.

## 6. Risks
- `EvaluateConnectionRequestUseCase`'s current callers (find them via a
  repo-wide reference search before starting) may assume this call never
  fails/never returns anything but the existing states — a new
  rate-limited outcome is a breaking change to every exhaustive `switch` on
  its result type. Audit every call site, don't just add the case and hope.
- Fixed-window counting means a legitimate burst right at a window boundary
  (e.g. 2 requests just before rollover + 2 just after) can total more than
  `maxCount` within a short real-time span even though each window
  individually stayed under it — acceptable per `E13-T01`'s own scope (task
  §2, "simplest correct primitive"), not a defect to fix here.
