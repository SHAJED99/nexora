# E13-T01 · Generic rate-limiter primitive (fixed-window counter, Drift-backed)

## 1. Goal
Give every later E13 task (connection requests, device registration, message/
relay flooding, group invites, storage-exhausting inbound data, battery/
network-draining request floods) ONE shared, already-tested "is this bucket
over its limit right now" primitive, instead of five ad hoc reimplementations
of the same counting logic — the same reason `FirebaseBoundary`/
`FirebasePaths` (E11-T01) centralized a cross-cutting concern instead of
letting five wrappers each invent their own shape.

## 2. Business logic
Implements the mechanism `FR-ABUSE-001` requires, but declares no policy
itself (no specific limit numbers, no specific bucket keys) — those are each
consuming task's own decision, informed by their own subsystem's realistic
traffic shape. This task is deliberately policy-free.

A **fixed window** counter (not sliding window, not token bucket): simplest
correct primitive that satisfies "bound the rate of X per identity" without
needing a background sweep/decay process. Given `bucketKey` (a caller-chosen
string identifying what is being limited AND who it's being limited against,
e.g. `"connection_request:<deviceId>"`), a window duration, and a max count:
increments the bucket's counter by `increment` (default 1 — a caller
limiting a raw event COUNT never passes this; a caller limiting a
cumulative QUANTITY, e.g. `E13-T05`'s byte-volume storage-abuse check,
passes the size of the thing being admitted); if the window has elapsed
since it was last reset, resets to `increment` and allows; otherwise allows
only while `count + increment <= maxCount`, then denies (without
incrementing further — a denied call must not itself count toward ever
un-denying). This one generalization (increment amount, not just implicit
+1) is why a single primitive covers both "N requests per window" (T02/T03/
T04/T06) and "N bytes per window" (T05) without two different tables or
two different classes.

## 3. What this task does
- A new Drift table (`RateLimitCounters` in `abuse_tables.dart`, following
  `location_tables.dart`/`notification_tables.dart`'s established per-concern
  file split): `bucketKey TEXT PRIMARY KEY`, `windowStartMs INTEGER`,
  `count INTEGER`. Added via a new `from < 18` migration step in
  `database.dart`'s `onUpgrade` (current `schemaVersion` is **17** as of this
  writing — verify against `origin/development` at execution time, not this
  hardcoded number: `E09`/`E10`/`E11` each independently claimed the same
  next version against a stale baseline this session and had to be
  renumbered at their `development` merge; check the real current value
  before writing this step, per task §6 Risks).
- `RateLimiter` class (`lib/core/abuse/rate_limiter.dart`), constructed with
  an `AppDatabase`:
  ```dart
  Future<bool> allow(String bucketKey, {required int maxCount, required Duration window, int increment = 1})
  ```
  Returns `true` (and increments by `increment`) if under the limit, `false`
  (no increment) if admitting `increment` would exceed it. Single method —
  every consuming task calls this once per admission decision, whether
  counting events (`increment: 1`, the default) or a cumulative quantity
  like bytes (`increment: <size>`).
- No wiring into any real subsystem — that is every later task's own job.

## 4. What this task does NOT do
- Does **not** decide any real limit number, window duration, or bucket-key
  naming scheme for connection requests, device registration, messages,
  relay, group invites, storage, or battery/network — every one of those is
  `E13-T02`..`E13-T06`'s own decision, informed by their own subsystem.
- Does **not** wire this primitive into `evaluate_connection_request_use_case.dart`,
  `device_identity_repository.dart`, `relay_engine.dart`,
  `group_membership_service.dart`, `storage_manager.dart`, or
  `background_policy.dart` — zero call sites change in this task.
- Does **not** add a background sweep/cleanup job for stale `RateLimitCounters`
  rows (a bucket that is never checked again just sits there, unbounded row
  growth over very long device lifetimes) — flagged as an Open Question
  below, not solved here; premature to design a cleanup cadence before any
  real bucket-key volume exists.
- Does **not** add sliding-window or token-bucket semantics — fixed window
  is the deliberate, simpler choice (task §2); do not "improve" this without
  a real task naming why fixed window is insufficient for its specific case.
- Does **not** touch `ObservabilityService` or add any logging — `E13-T07`'s
  own scope.

## 5. Contract

### Data
Migration step `from < 18` (verify the real next version at execution time,
per §3/§6): additive only, one new table, no backfill (no bucket exists for
any identity yet — nothing to seed). `docs/conventions.md`'s "Schema
migrations" rule applies: `IF NOT EXISTS` for any index this task adds (none
needed — the PK's own implicit index already serves the only access pattern,
a point lookup by `bucketKey`, same reasoning `revocation_migration_test.dart`'s
own precedent already documents for `device_revocations`).

### Functions
```yaml
- signature: "RateLimiter.allow(bucketKey: String, {required int maxCount, required Duration window, int increment = 1}) -> Future<bool>"
  params:
    bucketKey: "caller-chosen identity string, e.g. 'connection_request:<deviceId>' -- this task assigns no naming scheme, only documents that one is expected"
    maxCount: "the maximum cumulative total allowed within one window, caller's choice"
    window: "the fixed window duration, caller's choice"
    increment: "how much this call adds toward the total if allowed -- 1 for event counting (the default), a byte size for cumulative-quantity limiting (E13-T05)"
  returns: "true and increments the stored count by `increment` if the result would stay <= maxCount for the current window (or if the window just rolled over); false (no increment) if admitting `increment` would exceed maxCount"
  purpose: "the one shared admission check every E13 subsystem task calls"
```

## 6. Risks
- **schemaVersion collision.** This session's own E09/E10/E11 merge required
  renumbering three independently-claimed version bumps into one chain
  (v15→v16→v17) because each task was written against a stale baseline.
  Check `origin/development`'s CURRENT `int get schemaVersion` at the moment
  this task starts, not the `18` written above — if another task has since
  claimed it, renumber this step, not the other one, unless this task
  merges first.
- **Clock skew / `DateTime.now()` vs monotonic time**: fixed-window counting
  by wall-clock time is coarser than a monotonic clock, but this codebase's
  existing patterns (`storage_decisions.decidedAt`, `location_fixes.capturedAt`)
  already use wall-clock epoch-ms throughout — consistent with precedent, not
  a new risk this task introduces.
- A caller that reuses the SAME `bucketKey` for two logically different
  limits (e.g. one task using `"peer:<id>"` for two different purposes) would
  silently share one counter — each consuming task must choose a bucket-key
  scheme specific enough to avoid this; not this task's job to prevent by
  construction (a string key, not a typed enum, mirrors `FirebaseNodeKind`'s
  own "simplest thing that is greppable" reasoning, not the stronger
  compile-time guarantee an enum would give — a deliberate simplicity
  trade-off worth revisiting if a collision is ever actually found).

## 8. Acceptance criteria (EARS) + test plan
- **EARS-ABUSE-1**: WHEN `allow` is called for a bucket under its configured
  max within the current window, THE system SHALL increment the counter and
  return `true`. (FR-ABUSE-001)
- **EARS-ABUSE-2**: WHEN `allow` is called for a bucket AT its configured
  max within the current window, THE system SHALL NOT increment the counter
  and SHALL return `false`. (FR-ABUSE-001)
- **EARS-ABUSE-3**: WHEN the configured window has elapsed since a bucket's
  `windowStartMs`, THE system SHALL reset the counter to `increment` and
  return `true`, regardless of the count at window-end. (FR-ABUSE-001)
- **EARS-ABUSE-3b**: WHEN `allow` is called with `increment > 1` and the
  resulting total would exceed `maxCount`, THE system SHALL deny without
  partially incrementing. (FR-ABUSE-001)
