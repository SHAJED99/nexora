# E13-T05 · Byte-volume admission control against storage-exhausting inbound data

## 1. Goal
Close `FR-ABUSE-001`'s "storage exhaustion" vector as an ADVERSARIAL
concern (a peer deliberately sending excessive data at this device to fill
its disk), distinct from `E08`'s own storage-management scope.

## 2. Business logic
`FR-ABUSE-001`. `E08`'s `StorageManager`/`RetentionExecutor` +
`StorageDecisionLog` already enforce a QUOTA on already-accepted local
data — periodically inventorying what is stored and evicting per policy
(smart/manual mode). That is retention management, not admission control:
it runs on data already written to disk, after the fact. Nothing today
throttles HOW MUCH inbound data one peer may cause to be written in the
first place.

This task adds a byte-volume admission check, using `E13-T01`'s
`RateLimiter` with `increment` set to the size (bytes) of the inbound item
being admitted, keyed by the SENDING peer's identity — BEFORE that item is
handed off to whatever local write path eventually persists it. This task
runs strictly after `E13-T03` (`depends_on:` above) and adds its check at
the SAME call site T03 already gates for per-message COUNT — a second,
independent `RateLimiter.allow` call with a distinct bucket key and
`increment: sizeBytes`, alongside (never replacing) T03's own count check;
both must pass for admission.

**Execution-time correction (resolves `OQ-E13-T05-1`):** the paragraph
above, and this file's original `files:` fence, assumed that shared call
site was `RelayEngine.enqueue`. It is not — `RelayEngine.enqueue` has no
sender-identity parameter or column to gate on at all, exactly the
discovery `E13-T03` already made and disclosed for its own count-based gate
(see that task's Run log and `Q-E13-T03-1`). The real, confirmed call site
is `InboundPipeline._handleBuffer`'s forward branch
(`lib/core/messaging/inbound_pipeline.dart`), keyed by `frame.source`,
immediately after T03's own `relay:` bucket check. This is a disclosed
correction mirroring T03's own, not silent scope creep — `files:` above has
been updated accordingly.

## 3. What this task does
- Locate the real entry point where inbound data destined for local
  storage is first accepted — confirmed at execution time to be
  `InboundPipeline._handleBuffer`'s forward branch
  (`lib/core/messaging/inbound_pipeline.dart`), the same call site `E13-T03`
  already gates, NOT `RelayEngine.enqueue` (see the correction above).
- Add a second `RateLimiter.allow('storage_volume:${frame.source}', maxCount:
  <chosen bytes-per-window>, window: <chosen>, increment: <item size in
  bytes>)` check there, independent of any per-message COUNT check T03
  added — a sender could send few but huge messages (fails this task's
  check, passes T03's) or many small ones (passes this task's check, fails
  T03's); both checks matter and neither substitutes for the other.
- Concrete byte/window numbers: this task's own decision, informed by
  `E08`'s own existing `storage_policy_settings` defaults (read them for
  context — do not blindly reinvent a number unrelated to what the app
  already considers a reasonable storage budget) — document the chosen
  numbers and reasoning in the Run log.

## 4. What this task does NOT do
- Does **not** change `StorageManager`, `RetentionExecutor`,
  `StorageDecisionLog`, or any eviction/retention policy — `E08`'s
  scope is completely untouched; this task only adds a check BEFORE data
  reaches that layer at all.
- Does **not** duplicate `E13-T03`'s per-message-count relay rate limit —
  reuses the same admission point, adds an independent byte-volume check
  alongside it, never replaces it.
- Does **not** distinguish message content types (text vs. media/
  attachment) for the byte-volume calculation — every byte counts the
  same; a finer-grained policy (e.g. a looser cap for one content type) is
  a distinct, later decision if ever needed, not this task's default.

## 5. Contract

### Functions
No new public function signature of its own — this task calls
`E13-T01`'s existing `RateLimiter.allow(..., increment: sizeBytes)` from
inside whatever call site is confirmed at execution time (§3). If the
confirmed call site requires a NEW wrapper function to read the item's
size before calling `allow`, name and document it here as a Deviation
during implementation rather than leaving this section silently wrong.

  verified at task-sharding time (see `E13-T03`'s own §6 Risks — same

  way T03's own §6 already flagged as possible — the real call site is
  `InboundPipeline._handleBuffer`'s forward branch, not `RelayEngine` at
  all. See the correction in §2/§3 above and `OQ-E13-T05-1`'s resolution.
- Both this task and `E13-T03` touch `inbound_pipeline.dart`'s forward
  branch — `depends_on: [E13-T01, E13-T03]` above serializes this task
  strictly after `E13-T03` lands, so this task's own edit is the second gate
  added at that call site, never a parallel edit racing T03's (the
  anti-collision matrix must be empty; this dependency is what keeps it
  that way).
