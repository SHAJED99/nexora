# E13-T06 · Real observability client (Sentry-or-equivalent) replacing the console-log stub

## 1. Goal
Give the team actual field visibility into crashes/errors (`ADR-0006`,
`NFR-REL-001`), replacing the genesis stub that only `print()`s in debug
builds and reports nothing in production.

## 2. Business logic
`FR-DIAG-001`/`FR-DIAG-002`, `ADR-0006` (accepted: a dedicated,
privacy-conscious crash/error tool, e.g. Sentry; no analytics/usage
tracking for v1). `ObservabilityService` (`lib/core/observability/
observability_service.dart`, 23 lines) is the ONE existing call surface
every other service in this codebase already calls (`logError`,
`log(LogLevel, code, {cause})`) — this task swaps what happens INSIDE
`init()`/`log()`, it does not change either method's signature, so no
other file's call site changes.

`ADR-0006` explicitly leaves the specific vendor (Sentry vs. an
equivalent) as an implementation detail for this task, not a new
foundational choice — but adding ANY new SDK dependency is still a 🧍
rule-3 `new_dependency` gate at `pubspec.yaml` (`docs/conventions.md`'s own
"requires a human-approved addition" rule). This task's own `files:` list
already includes `pubspec.yaml` — the gate is a real precondition on
merging this task, not a blocker on sharding it.

## 3. What this task does
- Pick a concrete vendor (Sentry is the ADR's own named example; `sentry_flutter`
  is the standard Flutter package) — this task's own decision, subject to
  the pubspec 🧍 gate at merge time, not before.
- `ObservabilityService.init()` initializes the real client (DSN from a
  build-time config, never hardcoded — follow whatever config-injection
  convention this codebase already uses for other secrets/keys, verify at
  execution time before inventing one).
- `ObservabilityService.log(LogLevel, code, {cause})` forwards to the real
  client's error/breadcrumb API instead of (or in addition to, for debug
  builds) the existing `print()`.
- Record the vendor pick in `docs/conventions.md`, per `ADR-0006`'s own
  closing line ("`docs/conventions.md` (T02) can record the pick").
- Every existing call site (`logError` used throughout `lib/core/services/`,
  `lib/features/`, etc. — dozens of them, unchanged) keeps working
  unmodified, since neither public method's signature changes.

## 4. What this task does NOT do
- Does **not** add usage/behavior analytics — `ADR-0006`'s decision is
  crash/error reporting only, explicitly not analytics for v1.
- Does **not** change `LogLevel`'s enum values or `logError`'s signature —
  every existing call site across the codebase must compile unmodified.
- Does **not** audit every existing `logError`/`log` call site's `cause`
  argument for FR-DIAG-002 compliance (no plaintext/keys/voice/location) —
  that is a separate, cross-cutting audit this task does not scope-creep
  into; flag as a follow-up bug if a violation is noticed in passing, don't
  silently fix call sites outside this task's `files:` fence.
- Does **not** decide self-hosted vs. managed hosting for the chosen
  vendor — `ADR-0006`'s own closing line leaves this as a `docs/
  conventions.md` implementation note, this task's own call, not a new
  rule-3 decision, but still document the choice made.
- Does **not** wire crash reporting into native (Kotlin) code — Dart-side
  `ObservabilityService` only; a native crash reporter (if ever wanted) is
  a distinct, separate task.

### External services & flags

## 6. Risks
- A crash/error SDK's own instrumentation (network requests, native
  hooks) must itself never transmit anything FR-DIAG-002 forbids — verify
  the chosen SDK's default breadcrumb/context collection doesn't
  auto-capture something like device location or clipboard content by
  default; disable any such default collection explicitly rather than
  assuming it's off.
- Every existing `logError`/`log` call site across the codebase already
  assumes calls are fire-and-forget and never throw — the new
  implementation must preserve this (never let a network failure from the
  observability SDK itself propagate as an exception to a caller that
  didn't expect one).

## 8. Acceptance criteria (EARS) + test plan
- **EARS-DIAG-1**: THE system SHALL never log message plaintext, private/
  session keys, voice content, or sensitive personal/location data, via
  `ObservabilityService` or the chosen vendor's own default instrumentation.
  (FR-DIAG-002 — the epic-level criterion this task is the one place it
  becomes mechanically checkable: every OTHER file's own `logError`/`log`
  call sites already existed before this task and are each individually
  responsible for what they pass as `cause` — task §4 explicitly does not
  audit them — but §6 Risks' vendor-default-collection check IS this
  task's own new surface area, and is where this criterion is tested here.)
- **EARS-DIAG-2**: WHEN `ObservabilityService.log` is called with
  `LogLevel.error`, THE system SHALL forward the event to the configured
  crash/error client. (FR-DIAG-001)
- **EARS-DIAG-3**: IF the observability client itself fails (e.g. network
  error sending the event), THEN `log`/`logError` SHALL NOT throw to the
  caller. (FR-DIAG-001, matches every existing best-effort pattern in this
  codebase)
