# E13-B02 · the observability sink changed under call sites that were written for a console

## The defect

A **seam owned by no single task.** Before `E13-T06`,
`ObservabilityService` was a genesis stub that printed to the debug
console. Every `logError(code, cause: e)` call site in the codebase was
written against that stub, where the `cause` argument never left the
device. `E13-T06` replaced the sink with a real vendor
(`SentryObservabilityClient`) that ships `cause` to a third-party
service:

```dart
// observability_service.dart:133-137
if (cause is Object && cause is! String) {
  Sentry.captureException(cause, hint: Hint.withMap({'code': code}));
} else {
  Sentry.captureMessage(code, level: sentryLevel);
}
```

`captureException` serializes the exception's message/`toString()` as the
event value. T06 correctly and thoroughly hardened everything the *SDK*
collects on its own (`sendDefaultPii`, screenshots, view hierarchy,
interaction/print breadcrumbs, session tracking, tracing — three of those
were themselves found by T06's own review). What it did not do — and no
task's `files:` fence covered — is re-audit the ~13 pre-existing
`cause:` payloads that are now vendor-bound.

At least one of them puts a device identifier in the message body:

```dart
// device_directory_service.dart:273-278
ObservabilityService.instance.logError(
  'firebase.device_directory_lookup_identity_mismatch',
  cause: StateError(
    'directory/$deviceId: identityPublicKey field disagrees with '
    'the identity key embedded in prekeyBundle',
  ),
);
```

`FR-DIAG-002` forbids logging "sensitive personal data". In an app whose
whole premise is that identity is local and unlinkable (ADR-0005) and
that ships no usage analytics in v1 (ADR-0006), a stable device
identifier egressing to a third-party vendor is at minimum a decision
that should be made deliberately rather than inherited from a stub's call
site.

## Reachability — why this is S4 and not higher

The one **proven** site is currently unreachable in production:
`DeviceDirectoryService` is never constructed anywhere in `lib/`
(`grep -rn "DeviceDirectoryService(" lib/` matches only its own
declaration) — the same fact `E11-B01` already recorded. Nothing in the
running app reaches line 274 today. This is a trap armed for whoever
wires the first real consumer, not a live leak.

A **second, reachable variant is suspected but unproven** and is the
reason this should be an audit rather than a one-line edit:
`firebase_metadata_service.dart:70-74` logs
`'firebase.device_registration_failed'` with `cause: e`, where `e` is
whatever `_registerDevice(uid, deviceId)` threw. That path runs on every
real sign-in (`SignInUseCase.call`). A `FirebaseException` raised against
`users/$uid/devices/$deviceId` plausibly carries that path — and
therefore the account uid and the device id — in its own message, which
`captureException` would then ship verbatim. Verifying this needs a real
Firebase failure against a live/emulated backend; it is recorded here as
suspected, not as established fact. The same shape applies to every
`cause: e` site that wraps a vendor exception (Drift/SQLite statements
and bound variables, Firebase paths).

## What was checked and is CLEAN

The sweep's specific question was whether rate-limit denials leak
identifiers. They do not:

- `InboundPipeline`'s two gates, `GroupMembershipService`'s gate and
  `EvaluateConnectionRequestUseCase`'s gate increment an in-memory
  counter and return. None of them calls `ObservabilityService` at all.
  No bucket key, no `frame.source`, no device id reaches Sentry.
- The single denial that does reach Sentry is the device-registration
  one, via `LoginController._signIn`'s catch
  (`login_controller.dart:86-89`). It logs
  `AppFailure('device.registration_rate_limited')`, whose `toString()` is
  `'AppFailure(device.registration_rate_limited)'`
  (`google_auth_service.dart:26`) and whose own `cause` field is `null`
  at that throw site (`device_identity_repository.dart:50` —
  `throw const AppFailure('device.registration_rate_limited')`). No uid,
  no device id, no bucket key. **PASS.**

## Expected

`FR-DIAG-002` / `EARS-DIAG-1`: the system never logs sensitive personal
data. With a real vendor sink, "log" now means "send to a third party",
and every `cause:` payload is in scope for that rule.

## Actual

`cause:` payloads inherited from the console-stub era were never
re-examined when the sink changed; at least one interpolates a device id
into the captured message.

## Severity

**S4.** The proven site is unreachable in the running app today, and the
identifier involved is pseudonymous rather than content. Not dismissed as
a non-issue because (a) `EARS-DIAG-1` is called out in the epic's own
§Acceptance criteria as non-negotiable, (b) the reachable variant is
plausible and unverified, and (c) the failure mode is silent — nothing
about this surfaces until someone reads Sentry events in production.

Priority is the human's call (`bug_priorities` gate).

## Fix direction

1. Audit every `ObservabilityService.log`/`logError` call site's `cause:`
   argument against `FR-DIAG-002`. There are ~13; `grep -rn "cause:" lib/`
   plus following each `e` back to what can throw it is the whole job.
2. Fix `device_directory_service.dart:274-277` by dropping `$deviceId`
   from the message (the stable `code` already says which failure this
   is; the id adds nothing a reader of a privacy-scoped error report
   needs).
3. Consider making the rule structural rather than per-site: a
   `beforeSend` hook on `SentryFlutterOptions`, or scrubbing inside
   `SentryObservabilityClient.capture`, so a future call site cannot
   reintroduce this by writing a normal-looking interpolated message. A
   test asserting that a `cause` containing a known identifier does not
   appear in what the client would send would then guard it mechanically
   — the current `observability_service_test.dart` asserts the SDK
   options, not the payloads.
4. Record the outcome in `docs/conventions.md` next to the existing
   third-party-dependency note, so "what may go in a `cause:`" is a
   written convention rather than each author's judgement.

## What this fix does NOT do

- Does **not** revisit ADR-0006's choice of vendor, or `E13-T06`'s
  `SentryFlutterOptions` hardening — that work is correct and this bug
  does not challenge any of it.
- Does **not** remove or weaken any log site. Every `code` stays exactly
  as it is; only what rides along in `cause` is in scope. Diagnostics
  that stop being diagnostic are not a fix.
- Does **not** touch any `RateLimiter` call site or any E13 abuse gate —
  those were checked and are clean (see above).
- Does **not** wire `DeviceDirectoryService` into production, or resolve
  `E11-B01`'s "never constructed" state. If that changes, this bug's
  reachability changes with it; that is the follow-up's problem, not
  this one's.
- Does **not** add a new dependency (a `beforeSend` hook uses the already
  human-approved `sentry_flutter`).

- **Suspected site investigation — `firebase_metadata_service.dart:70-74`
  (`firebase.device_registration_failed`, runs on every real sign-in)**:
  `sentry_flutter`'s `Sentry.captureException` ships whatever the caught
  exception's own `toString()` produces. For a Firebase Realtime Database
  failure that is a `FirebaseException`, whose `toString()`
  (`firebase_core_platform_interface-6.0.3/lib/src/firebase_exception.dart:69-77`)
  is exactly `'[$plugin/$code] $message'` -- so the question reduces to
  "does the Realtime Database SDK's `message` for a write failure to
  `users/$uid/devices/$deviceId` ever contain the uid or deviceId".
  Verified against a REAL backend, not just documentation: started a
  local `firebase-tools` Realtime Database emulator (`firebase
  emulators:start --only database --project nexora-b3a97`), loaded this
  project's actual `database.rules.json` into it (the emulator's default
  config didn't auto-load it; deployed via the admin REST endpoint,
  `PUT /.settings/rules.json` with `Authorization: Bearer owner`), then
  issued the exact write shape `registerDevice`/`FirebaseMetadataService`
  performs against `users/$uid/devices/$deviceId`:
  - Unauthenticated write (no ID token) -> `401`, body
    `{"error":"Permission denied"}`.
  - Write with a mismatched `auth.uid` override (`someone-else` against
    `users/testuid123/...`) -> `401`, same generic body.
  - Write with the correct uid but data that fails this project's own
    `.validate` rule (a `deviceId` field that disagrees with the path
    segment) -> `401`, same generic body.
  In all three cases the response is the flat, generic string
  `"Permission denied"` -- **neither the uid nor the device id is echoed
  back anywhere in the error payload.** This is the server-side wire
  format the native Android/iOS RTDB SDKs receive and then surface as
  `DatabaseError.message`/`FirebaseException.message`; it corroborates
  Firebase's own publicly documented generic error strings for this error
  class (e.g. "Client doesn't have permission to access the desired
  data.").

  validation-failure failure modes**, which are the realistic ways this
  specific write can fail (the account is real, the path is well-formed,

  well-documented as generic, connection-level messages with no
