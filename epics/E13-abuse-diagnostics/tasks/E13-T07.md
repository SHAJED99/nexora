# E13-T07 · Wire the rate limiter into production

## 1. Goal
`E13-T02` built and tested a real admission-check mechanism for
connection-request spam and device-registration abuse — and its own
cross-model reviewer confirmed both mechanisms are correct and
falsifiable in isolation, then flagged that **neither is reachable in
the running app**: every real construction site was left outside that
task's own `files:` fence by design (`OQ-E13-T02-1`), so both `RateLimiter?`
parameters default to `null` and the gates silently no-op. `EARS-ABUSE-4`
and `EARS-ABUSE-5` are currently **false** in production. This task closes
that gap — this is the `L-process-007` "unwired capability" shape
(previously seen in E09-B02/B06), named now with an owning task so it
does not sit unresolved through the rest of this epic the way it did
across eight tasks in E06.

## 2. Business logic
`FR-ABUSE-001`. Four real construction sites need a real `RateLimiter`
threaded through, per `OQ-E13-T02-1`'s own text plus one site its own
Open Question missed (found by `E13-T02`'s reviewer):

1. `lib/core/messaging/messaging_stack.dart` — construction site for
   `EvaluateConnectionRequestUseCase(RelationshipRepository(db))` needs
   `rateLimiter: RateLimiter(db)` added.
2. `lib/features/devices/presentation/devices_controller.dart` — its
   own default-fallback construction of `EvaluateConnectionRequestUseCase`
   needs a `db` (or a pre-built `RateLimiter`) threaded into
   `DevicesController`'s own constructor to build a real default.
3. `lib/features/login/domain/sign_in_use_case.dart` — the existing
   `createDeviceIdentity(deviceId)` call needs `accountUid: accountUid`
   added (the value is already in scope one line earlier).
4. **`lib/app/bindings.dart:90`** (the site `OQ-E13-T02-1` did not name —
   confirmed by `E13-T02`'s reviewer via direct construction-site audit):
   `DeviceIdentityRepository(Get.find<AppDatabase>())` needs a
   `rateLimiter:` argument too. Wiring site 3 alone, without this one,
   leaves `EARS-ABUSE-5` still inert — the singleton
   `DeviceIdentityRepository` the app actually resolves through `Get.find`
   is built here, not at the call site `sign_in_use_case.dart` merely
   invokes.

**Precondition, not a follow-up**: `E13-T01`'s own `OQ-E13-T01-1` (no
eviction/cleanup policy for stale `RateLimitCounters` rows) must be
resolved as PART OF this task, not after it. `E13-T02`'s reviewer probed
this directly: 500 requests with a rotating, attacker-chosen `deviceId`
produced 500 permanent database rows and zero denials — because
`connection_request:$deviceId` is keyed on a value the remote peer
controls, with no cap on distinct keys. Wiring the gate live, without
addressing this first, converts a currently-unreachable storage-
exhaustion vector into a reachable one — trading one open `FR-ABUSE-001`
gap for a different one.

## 3. What this task does
- Threads a real `RateLimiter` into the four sites above.
- Resolves `OQ-E13-T01-1`: adds a bound on `RateLimitCounters` row count
  or a periodic/lazy eviction of expired-window rows (your own
  implementation choice — a simple approach: evict rows whose
  `windowStartMs + window` has already passed, on some natural trigger
  this codebase already has rather than a new polling timer — e.g.
  piggy-back on `allow()`'s own write path, matching the "no new driver"
  discipline `E08-T06`/`E10-T08` established).
- Resolves the UI-conflation finding from `E13-T02`'s review: a
  rate-limited peer currently renders identically to a user-blocked peer
  in `devices_view.dart` (both are `RelationshipState.blocked`). Decide
  and implement a fix — either a distinct outcome the UI can
  distinguish, or an explicit, documented decision that this conflation
  is acceptable (if so, say why in the Run log; do not silently leave it
  unaddressed now that it's reachable).
- Decides the partial-auth-state question `E13-T02`'s review also named:
  `sign_in_use_case.dart` signs in, then writes the device row, then
  calls `markSignedIn` — once the gate is live, a denial between steps 1
  and 3 leaves a user Google-authenticated with no local device identity.
  Decide what happens (retry guidance, a specific error state, etc.) and
  implement it.

## 4. What this task does NOT do
- Does **not** change `RateLimiter.allow`'s core semantics (fixed window,
  the `increment` parameter) — only adds eviction/bounding on top of the
  existing table.
- Does **not** change `EvaluateConnectionRequestUseCase`'s or
  `DeviceIdentityRepository.createDeviceIdentity`'s own gate logic —
  `E13-T02` already built and tested both; this task only supplies real
  arguments at construction time.
- Does **not** re-litigate `RelationshipState.blocked`'s reuse as the
  rate-limit-denial outcome — that decision stands; this task only fixes
  what the UI does with it, if a fix is chosen.
- Does **not** touch any other E13 task's files (T01/T03/T04/T05/T06 are
  all independently scoped and unaffected).

### Data
If eviction requires a schema-visible change (e.g. an index for an
efficient "expired rows" query) — 🧍 `db_schema_migration` gate. If a
purely query-time eviction (delete-then-read, no new column/index)
suffices, no migration is needed; prefer the simpler shape unless a real
performance concern forces the migration.

## 6. Risks
- Getting the `bindings.dart` site wrong (or missing it again) makes this
  task repeat its own reason for existing — audit EVERY construction site
  of both `EvaluateConnectionRequestUseCase` and `DeviceIdentityRepository`
  yourself with a fresh grep, don't trust this task's own enumeration as
  exhaustive without checking.
- An eviction policy that runs too aggressively could evict a bucket
  mid-window and reset a legitimate limit — verify eviction only touches
  rows whose window has genuinely already elapsed.
