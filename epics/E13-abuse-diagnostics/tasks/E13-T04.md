# E13-T04 · Rate-limit group-invitation spam

## 1. Goal
Close `FR-ABUSE-001`'s "group-invitation spam" vector: a device that creates
groups or adds members faster than any legitimate use would.

## 2. Business logic
`FR-ABUSE-001`. `GroupMembershipService.createGroup` (`~264`) sends invites
to every member of `memberList` with no throttle on how often one caller may
create a group or add a member; `addMember` (`~309`) is likewise
unthrottled. `_perform` (`~363`) is the shared apply/send helper both funnel
through.

This task adds an admission check at the shared `_perform` helper (not
duplicated separately in `createGroup` and `addMember` — one gate, both
callers benefit, matching this file's own existing "one shared helper"
shape), using `E13-T01`'s `RateLimiter`, keyed by the LOCAL device id doing
the inviting (this device is the one whose behavior is being bounded, not
the invitee).

## 3. What this task does
- `_perform` (or whichever of `createGroup`/`addMember` is confirmed at
  execution time to be the actual single funnel point) gains a `RateLimiter`
  dependency and calls `allow('group_invite:$localDeviceId', maxCount:
  <chosen>, window: <chosen>)` before its existing send logic.
- Denial surfaces through `GroupMembershipCounters` (`~128`)'s existing
  outcome-tracking shape — add a new counter value there (matching its
  existing pattern like `groupUnauthenticated`) rather than inventing an
  unrelated result type, since that struct already exists precisely to
  report "why didn't this succeed" to callers.
- Concrete limit numbers/window: this task's own decision, informed by
  realistic legitimate use (a user creating a handful of groups or adding a
  handful of members in one sitting) — document in the Run log.

## 4. What this task does NOT do
- Does **not** change `handleWireFrame` (`~565`) or any INBOUND
  decrypt/verify logic — this task only throttles OUTBOUND
  create/invite/add actions this device itself initiates, not what it
  receives. (Spamming this device with unwanted GROUP MEMBERSHIP WIRE
  FRAMES from elsewhere, if that turns out to be a distinct real vector, is
  a separate concern for `E13-T03`'s relay-layer admission control, not
  this task.)
- Does **not** change `membership_epoch`, group-event ordering, or any
  cryptographic membership-rotation logic (`ADR-0003`'s sender-keys scheme)
  — this task is purely a rate gate in front of unchanged existing logic.
- Does **not** add UI copy or a design contract for what a user sees when
  denied — no `layer: frontend` surface.

## 5. Contract

### Functions

```yaml
- signature: "GroupMembershipService._perform(...) -> <existing return/outcome type, gains a rate-limited case>"
  params: "unchanged (verify exact signature at execution time)"
  returns: "unchanged on success; a new GroupMembershipCounters outcome value (e.g. rateLimited) when the local device id is over its group-invite rate limit"
  purpose: "adds a RateLimiter.allow('group_invite:$localDeviceId', ...) gate shared by createGroup and addMember"
```
Verify at execution time whether `_perform` really is the single funnel both
`createGroup` and `addMember` go through, per this file's own structure —
if it is not, gate each caller individually instead of forcing a shared

## 6. Risks
- If `createGroup`'s invite fan-out counts each invitee as a separate
  `_perform` call, a legitimate group of N members could itself trip a
  naively-chosen limit — size the chosen `maxCount` around GROUPS/ADDS per
  window, not per-invitee-within-one-group, or key the bucket at the
  `createGroup`/`addMember` call boundary rather than inside the per-invitee
  loop (verify exactly where `_perform` is called from before choosing).

**Deviations from spec/design:**
1. **`_perform` is NOT the single funnel `createGroup` and `addMember` both
   go through** (task file §5's own explicit verification requirement).
   Reading `group_membership_service.dart` in full shows `createGroup`
   (`~264`) builds its own `GroupControlFrame` and fans out directly — it
   never calls `_perform`. Per the task file's own stated fallback ("if it
   is not, gate each caller individually instead of forcing a shared choke
   point that doesn't actually exist, and note the deviation"), the
   admission check is duplicated at both real call sites: inside `_perform`
   (scoped to `action == GroupAction.addMember` only — see point 2) and at
   the top of `createGroup`. Both share one bucket key
   (`group_invite:$localDeviceId`) so one device's combined create+add rate
   draws from a single budget, matching §6's risk note.
2. **The `_perform` gate is scoped to `GroupAction.addMember` only, not
   unconditional.** `_perform` is the shared helper for eight actions
   (`rename`, `addMember`, `removeMember`, `grantAdmin`, `revokeAdmin`,
   `transferOwnership`, `deleteGroup`, `leave`), but `FR-ABUSE-001`/
   EARS-ABUSE-8 name only "group-invitation spam" (create/add). Gating
   unconditionally would have silently throttled unrelated group
   management (rename, admin changes, deletion) that this task was never
   asked to bound. Verified by a dedicated test
   ("the rate-limit gate never rate-limits an unrelated `_perform` action
   like rename") that `rename` still succeeds with the shared bucket
   exhausted.
3. **`createGroup` signals denial by throwing `AppFailure`, not by
   returning a nullable failure.** Every `_perform`-backed method returns
   `Future<AppFailure?>`; `createGroup`'s own return type is `Future<String>`
   (the new group id), and changing that signature is outside this task's
   `files:`-fenced contract (no caller/route file is listed). Throwing
   `AppFailure` on failure already has a precedent in this codebase
   (`google_auth_service.dart`'s documented "Throws AppFailure ... on any
   failure" methods), so this is not a new pattern introduced by this task.
4. **Process note on §7's first item:** the source change and the test file
   were both written together rather than tests-first — the tests were not
   observed failing against pre-change code in a separate step. To
   compensate, after the real implementation was green, the `createGroup`
   gate was locally disabled (`if (false) { ... }` in place of the real
   `_rateLimiter.allow(...)` check, uncommitted) and
   `group_membership_rate_limit_test.dart` re-run: 2 of 5 tests
   (`test_EARS_ABUSE_8_create_group_over_limit_is_denied` and the
   shared-bucket test) failed for the right reason (an `Actual: <null>`
   assertion mismatch where an `AppFailure('group.rate_limited')` was
   expected), confirming the tests really do exercise the gate rather than
   passing vacuously. The real implementation was then restored verbatim
   (matches commit `a772f36` exactly — confirmed via `git diff`) and the
   full suite re-run green before this handoff.
