# E14-B06 · `FR-VER-008` reconnect re-evaluation is unimplemented

## The defect

`FR-VER-008` requires: on reconnect, the app shall fetch the current version
policy and re-evaluate. `E14-B01`'s fix (launch-time `refresh()` call in
`lib/app/main.dart`) correctly and explicitly left this out of its own scope
— there is no connectivity-change signal wired anywhere in this codebase that
could trigger a re-fetch mid-session. A user who launches the app while
offline (or before an emergency policy update is published), then later
reconnects without relaunching, never sees the updated policy or gets routed
to `/version-update-required` until their next cold start.

## Expected

`FR-VER-008`: reconnect (real network restoration during a live session)
triggers a fresh `VersionPolicyService.refresh()` and re-evaluation via
`EvaluateVersionStateUseCase`, re-routing to the mandatory-update screen if
the result changes to `updateRequired`.

## Actual

No connectivity-change hook exists in `lib/` that could drive this. Launch-
time evaluation (`E14-B01`) is the only trigger.

## Severity

**S3** — a real gap against a named FR, but narrower than `E14-B01`/`B02`:
`FR-VER-010`'s emergency-enforcement lever still works on next launch (most
messaging apps are relaunched at least daily), and this does not regress any
existing protection. Not blocking `E14`'s own `epic_14 -> development` merge
on its own, but should not be silently dropped — `FR-VER-008` must not be
marked satisfied until this lands.

## What this fix does NOT do

- Does NOT change `E14-B01`'s launch-time refresh or its fence.
- Does NOT invent a new connectivity primitive if one already exists
  elsewhere in the mesh/transport stack for a different purpose — check
  `TransportService`/`LinkQualityFeed`/`BackgroundObserver` first for an
  existing reconnect signal before adding a new one.
- Does NOT require polling; a reconnect *event* is sufficient, not a timer.

## Investigation

Checked `TransportService`/`LinkQualityFeed`/`BackgroundObserver`
(`BackgroundLifecycleObserver`, `lib/app/bindings.dart`) per this task's own
fence, before writing anything new:

- `TransportService.connectionState`/`connect()` (`lib/core/transport/
  transport_service.dart`) report per-peer-device mesh transport link state
  (Bluetooth/WiFi-Direct-style, via Pigeon) — a completely different signal
  from "can this app reach the Firebase project". `VersionPolicyService
  .refresh()` reads `config/version_policy` from Firebase Realtime Database,
  not from any mesh peer, so a mesh reconnect has no bearing on whether a
  fresh policy is fetchable.
- `LinkQualityFeed` is downstream of the same mesh `TransportService`
  signal, same conclusion.
- `BackgroundLifecycleObserver` tracks app lifecycle (foreground/background)
  and device power state (Doze/battery saver) — not connectivity at all.

Read `FR-VER-008` verbatim in `spec/srs.md:161`: *"The system shall cache
the last known valid version policy locally for offline use; on reconnect
it shall fetch the current policy and re-evaluate."* `VersionPolicyService
.refresh()` (the only fetch this FR could mean) reads exclusively from
Firebase Realtime Database (`lib/core/services/version_policy_service.dart`),
so "reconnect" here is reconnection to Firebase/the internet — not a mesh
transport concept, confirming neither existing signal above is the right
one to reuse.

No existing internet-connectivity signal exists anywhere in `lib/`
(confirmed by grep — no `connectivity_plus`, no `.info/connected` usage, no
`ConnectivityResult`). Rather than adding a new dependency (a 🧍
`new_dependency` gate), this fix reuses Firebase Realtime Database's own
built-in `.info/connected` special path — already available via the
`firebase_database` package this app already depends on, and it is
literally the connection state of the exact channel `refresh()` reads from.
See `FirebasePaths.infoConnected()`'s own doc comment.

## Fix

- `FirebasePaths.infoConnected()` — new registry entry for Firebase's
  built-in `.info/connected` path (`lib/core/services/firebase_paths.dart`).
- `VersionReconnectWatcher` (`lib/features/version/domain/
  version_reconnect_watcher.dart`) — new, injectable, event-driven class:
  subscribes to a `Stream<bool>` connectivity signal, tracks the previous
  value, and on a genuine `false -> true` transition (never on the first
  event a fresh subscription ever sees, so it never re-fires `E14-B01`'s own
  launch-time check) calls `VersionPolicyService.refresh()` then composes
  `EvaluateVersionStateUseCase` exactly the way `main.dart`'s own
  `evaluateVersionStateAtLaunch` already does, invoking an injected
  `onUpdateRequired` callback if the result is `VersionState.updateRequired`.
  No `Timer`, no polling — driven entirely by stream events.
- `lib/app/main.dart` — after `runApp`, constructs one
  `VersionReconnectWatcher` reusing the SAME `versionPolicyService`/
  `_readInstalledBuildNumber` `main()` already built for the launch-time
  check (never a second `VersionPolicyService`), wired to the real
  `FirebaseDatabase.instance.ref(FirebasePaths.infoConnected()).onValue`
  stream, and navigates via `Get.offNamed(Routes.versionUpdateRequired)` on
  `updateRequired` — the same forced-navigation shape
  `LoginController._signIn` already uses (`Get.offNamed`,
  `login_controller.dart:58`), adapted for a mid-session re-route rather
  than `initialRouteFor`'s launch-time initial-route return.
