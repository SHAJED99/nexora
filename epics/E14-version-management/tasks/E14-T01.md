# E14-T01 · Version-policy Firebase schema, boundary registration, and local offline cache

## 1. Goal
Claim `OQ-E11-2`'s reserved `config/version_policy` node — E11's own
sharding named this epic as the one to pick it up — and give every later
E14 task a locally-cached, offline-usable copy of the remote policy.

## 2. Business logic
`FR-VER-005` (version states driven by a remotely configurable minimum-
build policy), `FR-VER-008` (cache the last known valid policy locally
for offline use; on reconnect, fetch and re-evaluate), `FR-VER-010`
(emergency minimum-version enforcement — retroactively marking all
builds below a new minimum unsupported is just "the policy value
changed," no special mechanism beyond re-fetching it).

`docs/firebase-schema.md` already reserves `config/version_policy` with
no fields, no rule, and no owner. This task gives it both, following
`E11-T01`'s own registry pattern exactly: a `FirebasePaths.versionPolicy()`
path function, a new `FirebaseNodeKind.versionPolicy` allow-list entry in
`FirebaseBoundary`, and a `database.rules.json` rule — `.read: "auth !=
null"` (every authenticated account needs this, it is not per-account
data; `config/` is a sibling of `users/` and `directory/`, not nested
under any uid), `.write: false` for every client (this is server/ops-
published policy, never client-written — see `E14-T02`'s own note on
who actually publishes it, out of this task's own build).

## 3. What this task does
- `FirebasePaths.versionPolicy() -> 'config/version_policy'`.
- `FirebaseNodeKind.versionPolicy` allow-list:
  `{minimumSupportedBuild, currentBuild, updateAvailableBuild, signature,
  updatedAt}` — exact field set this task's own read path parses; no
  write path exists in this build (see task §4).
- `database.rules.json`: `config/version_policy` gets `.read: "auth !=
  null"`, `.write: false`, `.validate` requiring the fields above, `$other`
  deny — matching every other node's structural shape. `docs/firebase-
  schema.md`'s row flips from `reserved` to `live`.
- A new Drift table, `VersionPolicyCache` (single row, id always `1`,
  same "exactly one settings row" shape as `StoragePolicySettings`/
  `LocationSettings`/`NotificationPreferences`): the last successfully
  read policy, cached for offline use.
- `VersionPolicyService`: `Future<void> refresh()` — best-effort read of
  `config/version_policy`, bounded timeout, catch-and-log
  (`ObservabilityService`), never throws; on success, writes the cache
  row. `Future<VersionPolicy?> cached()` — reads the local cache row,
  returns `null` if never successfully fetched.

## 4. What this task does NOT do
- Does **not** implement the version STATE MACHINE
  (UP_TO_DATE/UPDATE_AVAILABLE/UPDATE_REQUIRED) — `E14-T02`'s own pure
  domain logic, consuming this task's `cached()` output.
- Does **not** implement signature verification (`FR-VER-011`) —
  `E14-T05`'s own task; this task stores whatever `signature` field the
  policy carries, unverified, as raw data only.
- Does **not** implement WHO publishes `config/version_policy` (an ops/
  release process, not client code) — this task's `.write: false` rule
  makes that explicit: no client, including this build, ever writes this
  node. Publishing is a human/ops step outside this repo's own CI, same
  precedent `docs/firebase-schema.md`'s "Deployment" section already
  states for `database.rules.json` itself.
- Does **not** add a polling driver — `refresh()` has no caller yet in
  this task (that's `E14-T02`'s wiring); when wired, the caller decides
  the cadence (e.g. on reconnect, per `FR-VER-008`), not a new
  always-on timer this task invents.

  purpose: "the one Firebase read, best-effort, matching every other wrapper's exact pattern"
- signature: "VersionPolicyService.cached() -> Future<VersionPolicy?>"
  params: {}
  returns: "the last successfully cached policy, or null if none has ever been fetched"
  purpose: "the offline-usable read E14-T02's state machine consumes"

## 6. Risks
- `config/version_policy`'s `.write: false` means there is no way to test
  a real write through this app's own boundary guard — `FirebaseBoundary
  .assertAllowedFields` still applies to whatever payload the READ path
  parses into, but there is no `.set()` call to boundary-check the way
  every other wrapper in this codebase has one. Do not add one just to
  exercise the guard; a read-only node legitimately has no write side.
- schemaVersion collision risk — same standing note as `E13-T01`'s own
  §6: check the real current value before writing the migration step.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-VER-3**: WHEN `refresh()` succeeds, THE system SHALL cache the
  policy locally, overwriting any previous cache. (FR-VER-008)
- **EARS-VER-4**: IF `refresh()` fails or times out, THEN the system
  SHALL leave the existing cache untouched and never throw. (FR-VER-008)
- **EARS-VER-5**: WHEN `cached()` is called before any successful
  `refresh()`, THE system SHALL return `null`, never throw. (FR-VER-008)
