# E14-B03 · An unreadable build number silently disables version enforcement

## The defect

`lib/app/main.dart:113-127`:

```dart
Future<int> _readInstalledBuildNumber() async {
  try {
    final info = await PackageInfo.fromPlatform();
    return int.parse(info.buildNumber);
  } catch (e) {
    ObservabilityService.instance.logError(
      'version.installed_build_read_failed', cause: e);
    return 1 << 62;
  }
}
```

`1 << 62` is above any plausible `minimumSupportedBuild`, so
`EvaluateVersionStateUseCase.call()` takes neither of its guard branches and
returns `upToDate`. Any failure inside that `try` — a platform-channel error,
a plugin-registration failure, a `PackageInfo` cache miss, or an
`int.parse` `FormatException` on a non-numeric `buildNumber` — therefore
**disables version enforcement entirely** for that launch, silently apart
from one observability log line.

The `int.parse` path is the concrete one: `PackageInfo.buildNumber` is a
`String`. On Android it is `versionCode` and is numeric, so the happy path
holds — but the value is not guaranteed numeric by the plugin's contract, and
a non-numeric build number would fail open rather than being handled.

**The fail-open is justified in the comment by an analogy that does not
transfer.** `EvaluateVersionStateUseCase`'s no-cached-policy fail-open is
specced: `EARS-VER-9`, traced to `FR-VER-008`'s offline-use framing — "we have
never heard a policy, so we cannot claim this build is unsupported" is a
sound inference. "We could not read our own build number" is a different
statement, and no FR covers it. Under `FR-VER-010` (an emergency bump
published because the running build is unsafe), a device that cannot read its
own build number is precisely the device that should not be given the benefit
of the doubt.

## Repro

1. In a test, inject an `InstalledBuildProvider` that throws — or point
   `_readInstalledBuildNumber` at a `PackageInfo` whose `buildNumber` is
   `"1.0.3"` (a valid `CFBundleVersion` shape).
2. Seed a policy with `minimumSupportedBuild: 100`.
3. Evaluate.

## Expected

The spec is silent, which is itself the finding — `FR-VER-010`'s intent
(retroactively marking builds unsupported cannot be sidestepped) argues for
`updateRequired`, or at minimum a distinct, non-silent outcome. This needs a
one-line answer, not a builder's guess: **raise it as an Open Question
(`OQ-E14-B03-1`) before writing the fix.**

## Actual

`VersionState.upToDate`, `initialRoute: /welcome`, one log line. Enforcement
off.

## Severity

**S3** — broken, but conditional on a failure mode that should be rare on the
target platform, and a workaround exists (the next launch that reads
successfully re-enforces). Not S2: it does not fire on the normal path.

## Suggested fix shape (not binding)

Once `OQ-E14-B03-1` is answered: narrow the `catch` to the cases actually
intended to fail open, and make the "I do not know my own build" case its own
explicit branch rather than a sentinel value smuggled through an `int`. A
sentinel of `1 << 62` inside a normal-looking `int` return is what let this
land unnoticed — an `int?` or a small result type says what happened.

## Regression test (required before close)

A test asserting the chosen behaviour for a throwing `InstalledBuildProvider`
against a seeded `minimumSupportedBuild`, and a second asserting the
non-numeric `buildNumber` string case. Both must fail on today's HEAD.

## What this fix does NOT do

- Does NOT change `EvaluateVersionStateUseCase`'s own `EARS-VER-9`
  no-cached-policy fail-open — that one IS specced and stays exactly as it is.
- Does NOT change the `package_info_plus` dependency, its pin, or add any new
  dependency.
- Does NOT add retry logic or a second read attempt.
- Does NOT touch `E14-B01`'s missing `refresh()` call site or `E14-B02`'s
  communication blocking.
