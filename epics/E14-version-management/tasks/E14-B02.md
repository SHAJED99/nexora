# E14-B02 · The mandatory-update screen blocks the UI but not communication

## The defect

`FR-VER-006` (`spec/srs.md:159`) has two clauses:

> When the installed version is UPDATE_REQUIRED, the system shall **block
> application communication** *and* present a non-dismissible mandatory
> update prompt directing the user to Google Play.

The epic's own `EARS-VER-1` repeats both. `E14-T04` implemented the second
clause (verified — see the sweep's own falsification below). **Nothing in
this epic implements the first.**

`main.dart:130-138` passes the version-derived `initialRoute` into
`GetMaterialApp`, but `initialBinding: AppBinding(...)` sits right beside it
and GetX runs `initialBinding.dependencies()` at app construction,
**independent of which route is shown**. That method starts everything:

- `bindings.dart:130` — `messagingStack.coordinator.start()`, which
  (`messaging_coordinator.dart:281`) calls `_inbound.start()`, subscribing
  the inbound pipeline to live transport data and starting the queue's
  `Timer.periodic`.
- `bindings.dart:154-160` — `LinkQualityFeed(...).start()`.
- `bindings.dart:224` — `backgroundObserver.start()`.
- `bindings.dart:342` — `notificationDispatcher.start()`.

So on a device pinned to `/version-update-required`, the app is still
routing, relaying, decrypting inbound frames, holding transport links open
and dispatching notifications. The user cannot *see* a conversation; the
device is nonetheless a fully participating mesh node running an
explicitly-unsupported build.

This matters most for exactly the case `FR-VER-010` exists to serve: an
emergency minimum-version bump published *because* the old build's protocol
or crypto handling is unsafe. Blocking only the UI leaves the unsafe code
paths running.

## Repro

Because `E14-B01` currently makes the update screen unreachable, reproduce
against the composition rather than a live device:

1. Check out `epic_14`.
2. Read `lib/app/main.dart:139-146` — `initialBinding` and `initialRoute` are
   independent arguments to the same `GetMaterialApp`; there is no branch on
   `initialRoute` anywhere in `AppBinding`.
3. `grep -n "\.start()" lib/app/bindings.dart` — four unconditional starts,
   none gated on `VersionState`.
4. Or, after `E14-B01` is fixed: seed the cache with a `minimumSupportedBuild`
   above the installed build, launch, and observe the mandatory-update screen
   while `messagingStack.coordinator` is running.

## Expected

`FR-VER-006` / `EARS-VER-1`: under `UPDATE_REQUIRED`, application
communication is blocked — the messaging coordinator / inbound pipeline /
relay engine / background service are not started (or are started and
immediately stopped), and no frames are sent or processed.

## Actual

All four subsystems start unconditionally at app construction, whatever the
version state. `AppBinding` has no knowledge that `VersionState` exists.

## Severity

**S2** — a specced, security-relevant control is entirely absent, with no
workaround. Not S1: it is currently latent behind `E14-B01` (the screen is
unreachable at all today), and it is a missing mitigation rather than an
active exploit.

## Suggested fix shape (not binding)

Pass the evaluated `VersionState` (or a plain `bool blockCommunication`) from
`main.dart` into `AppBinding`, and gate the four `start()` calls on it.
Construction should stay unconditional — `MessagingStack.create`'s "does NOT
start anything" contract and the single-instance discipline in
`messaging_stack.dart:11-23` both depend on the composition root running
normally; only the *starts* should be suppressed. Note that
`initialRouteFor` in `main.dart` is already the pure, tested decision point,
so the same value can drive both.

## Regression test (required before close)

A widget/composition test that builds `NexoraApp` with
`VersionState.updateRequired`, and asserts the messaging coordinator's inbound
pipeline is **not** started (a call counter on the transport-data
subscription, per `L-feedback` on `fail()` inside injected seams — assert
`calls == 0`, never `fail('must not be called')`, which a broad catch would
swallow). Plus the mirror-image assertion under `upToDate` that it **is**
started, so the test cannot pass by breaking startup generally. Both must
fail on today's `epic_14` HEAD in the right direction.

## What this fix does NOT do

- Does NOT change `VersionUpdateView`, `VersionUpdateController`,
  `EvaluateVersionStateUseCase` or `VersionPolicyService`.
- Does NOT change `MessagingStack.create`'s "does NOT start anything"
  contract, nor construct anything conditionally — construction stays
  unconditional; only the lifecycle `start()` calls are gated.
- Does NOT add a mid-session re-check or a way to un-block without a relaunch.
- Does NOT change what `UPDATE_AVAILABLE` does — that state is explicitly
  non-blocking (`FR-VER-005`) and must keep starting everything.
- Does NOT fix `E14-B01`; this fix is only observable once that one lands.
