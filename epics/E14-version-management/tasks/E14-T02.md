# E14-T02 · Version state machine

## 1. Goal
Turn `E14-T01`'s cached policy plus the installed build number into the
one of three states `FR-VER-005` names, deciding nothing about UI or
enforcement — pure domain logic, the same "policy layer decides, UI layer
renders" split every other feature in this codebase already uses
(`location_visibility_policy.dart`, `notification_policy.dart`).

## 2. Business logic
`FR-VER-005`: `UP_TO_DATE`, `UPDATE_AVAILABLE`, `UPDATE_REQUIRED`, driven
by comparing the installed build number against the cached policy's
`minimumSupportedBuild` and `updateAvailableBuild`. `FR-VER-010`
(emergency retroactive enforcement) needs no special code here — the
policy value itself changing (a fresh `minimumSupportedBuild` published
and re-fetched via `E14-T01`'s `refresh()`) is what makes a previously
`UP_TO_DATE` build re-evaluate as `UPDATE_REQUIRED` on the next
evaluation; this task's own logic is stateless and re-derives the answer
every time it's called, so "retroactive" falls out of it for free.

State rule (exact precedence, in order):
1. installed build < `minimumSupportedBuild` → `UPDATE_REQUIRED`
2. installed build < `updateAvailableBuild` → `UPDATE_AVAILABLE`
3. otherwise → `UP_TO_DATE`

No cached policy at all (`E14-T01.cached()` returns `null` — e.g. a
fresh install that has never reached Firebase) → `UP_TO_DATE`. A
fail-open default is deliberate: refusing service because a policy was
never fetched would make every offline first-run unusable, which
`FR-VER-008`'s own "offline use" framing forbids.

## 3. What this task does
- `VersionState` enum: `upToDate`, `updateAvailable`, `updateRequired`
  (stored by `.name` per `docs/conventions.md` "Enums", though this is an
  in-memory-only value with no persistence in this task — noted for
  whichever later task, if any, ever stores it).
- `EvaluateVersionStateUseCase.call() -> Future<VersionState>`: reads the
  installed build number (from `pubspec.yaml`'s own build number via
  whatever package-info mechanism this codebase already uses — verify at
  execution time whether one exists, e.g. `package_info_plus`, before
  adding a new dependency; if none exists, adding one is a 🧍
  `new_dependency` gate, flag it rather than silently picking a package),
  calls `E14-T01`'s `cached()`, and applies the precedence rule above.

## 4. What this task does NOT do
- Does **not** call `refresh()` — this use case only reads the already-
  cached policy; refreshing it (and deciding when) is `E14-T04`'s own
  wiring concern.
- Does **not** render any UI or decide what happens in each state —
  `E14-T04`'s own job.
- Does **not** implement signature verification — this task treats
  whatever policy `E14-T01` cached as already trustworthy input; `E14-T05`
  decides what happens to an UNVERIFIED or invalid-signature policy,
  which may mean this task's own contract gains a guard later (flagged
  as a dependency for `E14-T05` to resolve, not invented here).
- Does **not** persist `VersionState` anywhere — it is derived fresh on
  every call, by design (§2, "stateless").

## 5. Contract

### Functions
```yaml
- signature: "EvaluateVersionStateUseCase.call() -> Future<VersionState>"
  params: {}
  returns: "upToDate | updateAvailable | updateRequired, per the precedence rule in §2; upToDate when no policy has ever been cached"
  purpose: "the one pure decision point FR-VER-005 needs"
```

## 6. Risks
- Verify whether an installed-build-number reader already exists in this
  codebase before adding a new dependency for it — a duplicate mechanism
  is worse than a missing one, and a new dependency is its own 🧍 gate
  regardless.
- Build-number comparison must be numeric, not lexicographic (`"9" <
  "10"` is false as strings) — parse to `int` before comparing.

  `minimumSupportedBuild`, THE system SHALL evaluate `UPDATE_REQUIRED`.

  evaluate `UP_TO_DATE`. (FR-VER-005, FR-VER-008)
