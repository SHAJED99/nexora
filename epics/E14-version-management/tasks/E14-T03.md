# E14-T03 · Verify the version policy's signature before trusting it

## 1. Goal
`FR-VER-011`: "where appropriate, version policy shall be
cryptographically signed and verified by the application, to protect
against unauthorized modification."

## 2. Why this had `side: blocked` and an empty `files:` fence
**Update 2026-09-06: `OQ-E14-T03-1` is now resolved (see §9 Open
Questions) — asymmetric signing, option (b).** `side` is now
`unblocked`. This section is kept as-written (below) for the historical
record of what the decision actually needed to resolve; it is no longer
a live blocker. A concrete task-sharding pass (files:, functions:, EARS
criteria in §7/§8) still needs to happen before this is dispatchable —
notably, the exact signing LIBRARY (no Ed25519-capable dependency exists
in `pubspec.yaml` today, confirmed by grep) is its own, separate 🧍
`new_dependency` gate, not resolved by this decision.

This task could not be written concretely without a human decision this
session had no basis to make unilaterally (rule 3 — new cryptographic
infrastructure, plus a secrets/key-distribution question):

- **What signs the policy?** A private key held by whoever publishes
  `config/version_policy` (an ops/release process, per `E14-T01` §4's
  "no client ever writes this node") — but WHERE that private key lives,
  who can access it, and how it's rotated if compromised is an
  operational decision with no existing precedent in this codebase.
  `ADR-0003` (Signal Protocol) governs message/session cryptography
  between mesh peers, not app-to-ops policy signing — a different trust
  relationship entirely, and reusing Signal Protocol machinery for it
  would be a category error, not a reuse.
- **What verifies it, and with what bundled key?** The app needs a public
  key baked into the binary at build time to verify against. Which
  algorithm (Ed25519 is the obvious fit if a signing library is already a
  dependency — verify at execution time whether one exists before adding
  a new one, itself a 🧍 `new_dependency` gate either way) and how that
  public key gets into the app (a literal constant? a build-time
  config injection, matching whatever secrets pattern `E14-T01`'s own DSN-
  style config uses?) are both foundational choices.
- **What happens on a verification FAILURE?** Reject the whole policy
  read (fail closed — but then a single bad signature could make
  `EvaluateVersionStateUseCase` fall back to its own "no cached policy →
  UP_TO_DATE" default, which is fail-OPEN in the opposite direction from
  what signing was meant to protect) or something else. This is a real
  security-posture decision, not an implementation detail.

`FR-VER-011`'s own "where appropriate" qualifier is doing real work here:
it explicitly permits deciding this is not appropriate for v1's threat
model (the same class of call `ADR-0006` made for observability's
scope) — that is itself one of the options the human should see, not an
assumption this task makes for them.

## 4. What this task does NOT do
- Does **not** invent a signing scheme, a key format, or a bundled public
  key value — every one of those is the open decision above.
- Does **not** change `E14-T01`'s or `E14-T02`'s contracts — both already
  ship without signature verification (`E14-T01`'s `refresh()` stores
  whatever `signature` field the policy carries, unverified, as raw
  data), and this task does not retroactively require either to change
  before this decision is made.

## 6. Risks
Leaving `config/version_policy` unverified means anyone who can write to
that node (today: nobody, per `E14-T01`'s `.write: false` rule — the
actual risk surface is a Firebase project-level compromise, not a client-
side one) could push an arbitrary policy. `E14-T01`'s rule already
narrows this to "whoever has ops/Firebase-console access," which may be
judged sufficient without app-level signing at all — exactly the
"where appropriate" call above.

## Open Questions
- **OQ-E14-T03-1 — is policy signing appropriate for v1, and if so,
  with what key infrastructure?** Three options, advisory only:
  (a) skip it for v1 — `FR-VER-011`'s own "where appropriate" qualifier
  permits this; the write-side rule already restricts who can publish
  the node; revisit if a real incident ever demonstrates the gap
  matters. (b) a build-time-embedded Ed25519 public key (or whatever
  algorithm a library already in `pubspec.yaml` supports, checked before
  adding a new dependency), verifying a signature over the policy's own
  fields, fail-CLOSED on mismatch (a verification failure is treated as
  "no valid policy," same as `E14-T01`'s own "no cached policy" case —
  fail open toward `UP_TO_DATE`, consistent with `E14-T02`'s existing
  fail-open default, not a stricter new failure mode). (c) something
  else the human has in mind for how release signing already works in
  this project outside this repo (e.g. reusing whatever key already
  signs the Android release build, if one exists).
  - **Status:** ✅ resolved
  - **Answer:** Option (b) — asymmetric signing. A private key (held
    offline by whoever runs the ops/release process that publishes
    `config/version_policy`; the exact custody/rotation procedure is an
    operational runbook, not something this task builds) signs each
    policy payload. The app ships only the corresponding PUBLIC key,
    embedded at build time — never the private key, never a shared
    secret. Algorithm: Ed25519 if a signing-capable library already
    exists in `pubspec.yaml` (check `cryptography`/`pointycastle`/etc.
    before adding anything new — this is still a 🧍 `new_dependency` gate
    if none does). Verification failure is fail-CLOSED at the signature
    check itself (an invalid/missing signature is never trusted as a
    valid policy), but this composes with `E14-T01`/`E14-T02`'s EXISTING
    fail-open default (no valid cached policy → `UP_TO_DATE`) rather than
    inventing a new, stricter failure mode — the net effect is: a bad
    signature is treated exactly like "no policy fetched yet," not like
    "force everyone to update."
  - **Answered by:** human
