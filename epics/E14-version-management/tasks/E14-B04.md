# E14-B04 · The migration-safety suite's own sample skips the only destructive migration step

## The defect

`test/core/persistence/migration_safety_regression_test.dart:762-766`:

```dart
final representativeVersions = <int, void Function(sqlite3.Database)>{
  11: _createV11Tables,
  13: _createV13Tables,
  16: _createV16Tables,
};
```

The comment above it (lines 754-761) justifies each choice honestly — v11 is
where `messages` is introduced, v13 adds the group model, v16 is the fullest
intermediate schema. But the one step in the whole chain that *drops a
table* — v9→v10's `relay_packets` `DROP TABLE` — is never entered, because
no sampled start version is below 10.

This is a test-coverage gap, not a product defect. The drop itself **is**
covered, by `relay_retention_migration_test.dart` (E08's own file), and the
sweep confirms that file still passes. `EARS-VER-16`'s own frame — the one
whose stated job is "a representative sample of intermediate versions a real
install could plausibly resume from" — simply does not include the version
that makes the sample interesting.

Filed rather than left in the tracker so the observation has a reader, per
`skills/bug-sweep`'s own rule on unread carry-forwards (`L-process-008`).

## Repro

1. Read `migration_safety_regression_test.dart:762-766`.
2. Confirm no key is `< 10`.
3. `grep -n "relay_packets" test/core/persistence/migration_safety_regression_test.dart` — the drop step is never reached from any sampled start version.

## Expected

`EARS-VER-16` / `FR-VER-009`: the suite's representative sample exercises
every migration shape a real paused-mid-upgrade install could resume through,
destructive steps included.

## Actual

v9 is absent; the `relay_packets` drop is exercised only by a different
epic's test file.

## Severity

**S4** — a completeness gap in a test's own sample. No product behaviour is
wrong and the underlying migration is covered elsewhere. It is worth closing
because this suite is the artifact the epic points at to prove `FR-VER-009`,
and a proof that routes around its own hardest case is weaker than it looks.

## Suggested fix shape (not binding)

Add `9: _createV9Tables` to `representativeVersions`, with a `_createV9Tables`
builder in the same style as `_createV11Tables`, seeding a `relay_packets`
row alongside the existing device/message rows and asserting the message and
identity rows survive the drop.

## Regression test (required before close)

The added v9 case is itself the regression test. Falsify it: temporarily make
the v9→v10 step drop `messages` instead of `relay_packets` and confirm the new
case fails for that reason, then restore verbatim.

## What this fix does NOT do

- Does NOT change any migration in `lib/core/persistence/database.dart` — the
  migrations are correct; only the test's sample is incomplete.
- Does NOT change or duplicate `relay_retention_migration_test.dart`.
- Does NOT add every intermediate version 1..18 — the sample stays a sample;
  this adds exactly the one version that covers a shape the others cannot.
- Does NOT touch the E14 version-policy pipeline (`E14-B01`/`B02`/`B03`).
