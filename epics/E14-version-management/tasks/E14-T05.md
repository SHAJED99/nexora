# E14-T05 · Extend the relay frame's version check to reject incompatible peers gracefully

## 1. Goal
`FR-VER-001`/`FR-VER-002`: this codebase already has ONE piece of version
negotiation — `relay_packet_frame.dart`'s `frameVersion` byte, checked and
rejected on read (`relayFrameVersion = 1`, `deserialize` throws
`RelayPacketFrameException` on an unknown version, per
`relay_packet_frame.dart:~182-183`). This task confirms/hardens that this
IS the negotiation mechanism `FR-VER-001` asks for, rather than a
half-measure that needs a second, separate one built alongside it.

## 2. Business logic
`FR-VER-001` ("communication protocols shall include version information
... devices shall negotiate compatible communication features"),
`FR-VER-002` ("if a protocol is no longer compatible or secure, the
system may reject the connection").

Read `relay_packet_frame.dart` in full before writing anything: confirm
exactly what `deserialize` does today on an unknown `frameVersion` (throws
— verify this is caught somewhere upstream and treated as "drop this
frame, don't crash the relay pipeline," not an uncaught exception that
takes down `RelayEngine`). This task's own job is narrower than it might
first look: prove the EXISTING mechanism handles version mismatch
gracefully end-to-end (frame received → version check → graceful
rejection, no crash, no silent data corruption from misinterpreting a
newer frame layout as the old one), and extend the version byte's own
semantics if `FR-VER-001`'s fuller list (app version, build, protocol
version, **crypto version**, **database version**) needs more than the
one `frameVersion` byte already carries.

## 3. What this task does
- Confirm (via test, not assumption) that a frame with an unknown
  `frameVersion` is caught by whatever calls `deserialize` and results in
  the frame being dropped, not an uncaught exception propagating out of
  `RelayEngine`'s own processing loop.
- If `frameVersion` alone cannot express `FR-VER-001`'s crypto-version/
  db-version negotiation (verify: does anything about session
  establishment, E03's Signal Protocol handshake, already carry its own
  version marker independently? If so, `FR-VER-001` may already be
  satisfied by the SUM of `relayFrameVersion` + whatever E03 already
  does, and this task's own scope shrinks to "confirm and document,"
  not "add a new field"), extend the frame header with the additional
  version fields this task's own investigation finds missing — additive
  to the existing header layout, a new `relayFrameVersion` bump of its
  own if the header shape changes.

## 4. What this task does NOT do
- Does **not** touch `E03`'s Signal Protocol session establishment or key
  exchange — if that layer already carries its own version negotiation,
  this task documents it, never re-implements it.
- Does **not** change `RelayEngine`'s priority/TTL/expiry logic —
  `E13-T03`'s own scope fence, unaffected here.
- Does **not** add a NEW rejection reason distinct from what
  `deserialize` already throws — this task hardens/confirms the existing
  mechanism's end-to-end behavior, not a parallel one.
- Does **not** implement `FR-VER-003`'s migration-safety guarantee —
  `E14-T06`'s own task.

## 5. Contract

### Functions
No new public function signature guaranteed yet — this task's exact
shape depends on its own investigation (§3). If the header genuinely
needs new fields, the contract is: bump `relayFrameVersion`, add the new
field(s) additively to the existing serialize/deserialize pair, matching
`relay_packet_frame.dart`'s own existing length-prefixed field
conventions exactly (cited in that file's own header comment).

## 6. Risks
- This task could turn out to be nearly a no-op (the existing mechanism
  already satisfies `FR-VER-001`/`FR-VER-002` in full) or could require a
  real wire-format change (a new `relayFrameVersion`) — the investigation
  in §3 decides which, and the task's own size estimate assumes the
  former; if the latter, flag it as a Deviation rather than silently
  absorbing a bigger change into an `S`-sized task.
