# E14-T05 · Extend the relay frame's version check to reject incompatible peers gracefully

## 1. Goal
`FR-VER-001`/`FR-VER-002`: this codebase already has ONE piece of version
negotiation — `relay_packet_frame.dart`'s `frameVersion` byte, checked and
rejected on read (`relayFrameVersion = 1`, `deserialize` throws
`RelayPacketFrameException` on an unknown version, per
`relay_packet_frame.dart:~182-183`). This task confirms/hardens that this
IS the negotiation mechanism `FR-VER-001` asks for, rather than a
half-measure that needs a second, separate one built alongside it.

## 2. Business logic
`FR-VER-001` ("communication protocols shall include version information
... devices shall negotiate compatible communication features"),
`FR-VER-002` ("if a protocol is no longer compatible or secure, the
system may reject the connection").

Read `relay_packet_frame.dart` in full before writing anything: confirm
exactly what `deserialize` does today on an unknown `frameVersion` (throws
— verify this is caught somewhere upstream and treated as "drop this
frame, don't crash the relay pipeline," not an uncaught exception that
takes down `RelayEngine`). This task's own job is narrower than it might
first look: prove the EXISTING mechanism handles version mismatch
gracefully end-to-end (frame received → version check → graceful
rejection, no crash, no silent data corruption from misinterpreting a
newer frame layout as the old one), and extend the version byte's own
semantics if `FR-VER-001`'s fuller list (app version, build, protocol
version, **crypto version**, **database version**) needs more than the
one `frameVersion` byte already carries.

## 3. What this task does
- Confirm (via test, not assumption) that a frame with an unknown
  `frameVersion` is caught by whatever calls `deserialize` and results in
  the frame being dropped, not an uncaught exception propagating out of
  `RelayEngine`'s own processing loop.
- If `frameVersion` alone cannot express `FR-VER-001`'s crypto-version/
  db-version negotiation (verify: does anything about session
  establishment, E03's Signal Protocol handshake, already carry its own
  version marker independently? If so, `FR-VER-001` may already be
  satisfied by the SUM of `relayFrameVersion` + whatever E03 already
  does, and this task's own scope shrinks to "confirm and document,"
  not "add a new field"), extend the frame header with the additional
  version fields this task's own investigation finds missing — additive
  to the existing header layout, a new `relayFrameVersion` bump of its
  own if the header shape changes.

## 4. What this task does NOT do
- Does **not** touch `E03`'s Signal Protocol session establishment or key
  exchange — if that layer already carries its own version negotiation,
  this task documents it, never re-implements it.
- Does **not** change `RelayEngine`'s priority/TTL/expiry logic —
  `E13-T03`'s own scope fence, unaffected here.
- Does **not** add a NEW rejection reason distinct from what
  `deserialize` already throws — this task hardens/confirms the existing
  mechanism's end-to-end behavior, not a parallel one.
- Does **not** implement `FR-VER-003`'s migration-safety guarantee —
  `E14-T06`'s own task.

## Run log
- **Investigation conclusion: near-no-op, confirm-and-document (the §6
  "former" branch, not the "latter").** No wire-format change was needed.
- **What `deserialize` actually does on an unknown version** (read in
  full): `relay_packet_frame.dart:182-188` throws `FormatException` (not
  its own `RelayPacketFrameException` type — no such type exists in this
  file; the task file's §1 misnamed it) naming the got/expected version.
  Every other malformation (truncation, bad length prefix, unknown
  `payloadType`) throws the same `FormatException` type, consistent with
  the file's own documented contract.
- **Who actually catches it, and whether it can reach `RelayEngine`
  uncaught** (read `relay_engine.dart` in full, per `required_context`):
  `RelayEngine` never imports or calls `RelayPacketFrame` at all — it only
  ever `enqueue()`s/forwards `payload` as opaque `Uint8List` bytes
  (FR-ROUTE-003), and its own `_attempt()`'s only try/catch wraps the
  transport `_send` call, not any parsing. So `RelayEngine`'s processing
  loop was never at risk from this exception in the first place — it
  simply never touches the type that can throw it. The task file's own §2
  wording ("caught somewhere upstream ... not an uncaught exception that
  takes down `RelayEngine`") assumed the wrong call site. The REAL call
  site is `InboundPipeline._handleBuffer`
  (`inbound_pipeline.dart:348-355`), which already wraps
  `RelayPacketFrame.deserialize(bytes)` in `try { ... } on FormatException
  { counters.malformed++; return; }` — confirmed by an existing test
  (`inbound_pipeline_test.dart`'s `test_EARS_COMM_10_malformed_packet_does_
  not_stop_the_loop`, using an empty-buffer malformation) and now also by
  this task's own `test_EARS_VER_13_unknown_frame_version_is_dropped_not_
  crashed`, which drives the SPECIFIC unknown-`frameVersion` case (not
  truncation/empty-buffer) through the real `InboundPipeline` +
  transport-pigeon boundary and confirms: the bad-version frame is
  dropped (`counters.malformed == 1`), never stored/forwarded
  (`relayPackets` table stays empty, `counters.forwarded == 0`), and the
  receive loop stays alive — a subsequent legitimate encrypted message from
  the same peer still delivers (`counters.delivered == 1`).
- **Whether E03's session establishment carries its own version marker**
  (searched `lib/core/crypto/`): yes —
  `prekey_bundle_codec.dart:56-59` declares `preKeyBundleCodecVersion`,
  checked and rejected the same way (`deserialize` throws
  `FormatException` on an unknown `codecVersion`) on the X3DH prekey-bundle
  handshake artifact, independent of `relayFrameVersion`. So the SUM of
  `relayFrameVersion` (transport frame layout) + `preKeyBundleCodecVersion`
  (crypto handshake artifact layout) already covers `FR-VER-001`'s fuller
  list (protocol version + crypto version) without a combined field.
  `FR-VER-001`'s "app version"/"build"/"database version" items are outside
  this task's `files:` fence (no wire artifact here carries those, and
  none was added, per §4/§6 — flagged for the planner as a possible gap
  for a future task, not resolved here since it would require touching
  files outside this task's contract).
- **EARS-VER-14** (compatibility determinable without a full message
  exchange): proven directly — byte 0 of a serialized frame predicts
  `deserialize`'s accept/reject outcome with no session, no decrypt, no
  reply required. See `test_EARS_VER_14_version_compatibility_is_
  determinable_from_the_header_alone`.
