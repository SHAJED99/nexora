# E14-B07 · the shipped release cannot actually be built for Android

## The defect

Two independent, stacked build failures, both discovered running `flutter
run -d 21121119SG` against the `v0.1.0` tag (a real physical device, the
first actual Gradle/native Android build attempted since `sentry_flutter`
and `package_info_plus` were both added):

### Failure 1 — obsolete Kotlin `languageVersion` (worked around, not fixed)
`sentry_flutter` 8.14.2's own `android/build.gradle` hardcodes:
```groovy
kotlinOptions {
    jvmTarget = JavaVersion.VERSION_1_8
    languageVersion = "1.6"
}
```
This project's Kotlin Gradle Plugin (`2.3.20`, `android/settings.gradle.kts`)
no longer supports compiling with `languageVersion 1.6` at all:
```
e: Language version 1.6 is no longer supported; use version 2.0 or greater instead.
FAILURE: Execution failed for task ':sentry_flutter:compileDebugKotlin'.
```
**Worked around** (not committed, tried in a throwaway worktree) by forcing
every Kotlin compile task project-wide onto `languageVersion`/`apiVersion
2.0` via a `subprojects { tasks.withType<KotlinCompile>() { ... } }` block
in the root `android/build.gradle.kts` — this resolved failure 1 cleanly
with no dependency version change.

### Failure 2 — `sentry_flutter` vs `package_info_plus` AAR metadata conflict (NOT resolved)
Once failure 1 was worked around, the build proceeds further and hits:
```
FAILURE: Execution failed for task ':sentry_flutter:checkDebugAarMetadata'.
An issue was found when checking AAR metadata:
  1. Dependency ':package_info_plus' requires libraries and applications
     that depend on it to compile against version 36 or later of the
     Android APIs.
     :sentry_flutter is currently compiled against android-34.
```
`sentry_flutter` 8.14.2's own `android/build.gradle` hardcodes
`compileSdkVersion 34`. `package_info_plus` (whatever version this
project's `pubspec.lock` currently resolves — check at fix time) declares
an AAR metadata requirement of API 36+, and Gradle's AAR metadata check
enforces that every consumer in the same dependency graph (including
sibling library subprojects like `sentry_flutter`) meets that floor.

**Four attempted workarounds, all failed, none committed:**
1. Setting `:app`'s own `compileSdk = 36` in `android/app/build.gradle.kts`
   — does not touch `sentry_flutter`'s own, separately-declared
   `compileSdkVersion 34`. No effect on the error.
2. `subprojects { plugins.withId("com.android.library") { extensions
   .configure<com.android.build.gradle.LibraryExtension> { compileSdk = 36
   } } }` — Kotlin DSL script compilation error: `LibraryExtension` is
   deprecated in this AGP version's Kotlin DSL surface and
   `BaseAppModuleExtension` is unresolved.
3. Same, using `com.android.build.api.dsl.CommonExtension<*, *, *, *, *,
   *>` instead — different Kotlin DSL script compilation error: this
   AGP's `CommonExtension` is not generic in this resolved version
   (`No type arguments expected`).
4. Same, using untyped Groovy dynamic property access
   (`extensions.getByName("android").withGroovyBuilder { setProperty
   ("compileSdk", 36) } }`) wrapped in `afterEvaluate` — script compiles,
   but Gradle now reports `compileSdk` is READ synchronously as soon as
   each subproject's own `android {}` block finishes evaluating, before
   `afterEvaluate` ever fires: `"It is too late to set compileSdk. It has
   already been read to configure this project. Consider ... using the
   variant API."` Scoping the override to skip `:app` (to dodge a
   separate `evaluationDependsOn(":app")`-induced "project already
   evaluated" error) did not change this outcome for the library
   subprojects either.

**No root-Gradle-script-level override of a dependency subproject's own
hardcoded `compileSdk` was found to work.** This appears to be a genuine
AGP constraint, not a syntax issue — `compileSdk` is read too early in a
subproject's own configuration for a parent/root script to safely override
it after the fact.

## Expected

The released app builds and installs on a real Android device.

## Actual

`flutter run` fails at the Gradle `assembleDebug` step, on a real physical
device, for the tagged `v0.1.0` release. **The app has never actually run
on a device with both `sentry_flutter` and `package_info_plus` present
together** — every prior review of `E13-T06`/`E14-T04` individually only
ran `flutter test` (VM-only, does not invoke Gradle) and `flutter analyze`,
neither of which builds the native Android artifact at all.

## Severity

**S1** — the release does not build for its primary target platform
(Android). This blocks any real-device verification of the whole project,
not just these two features.

## Suggested direction (not binding, builder's call at dispatch — likely
needs a 🧍 human decision first, see below)

Since no build-script-level override was found to work, the real fix is
almost certainly one of:
- **Bump `sentry_flutter`'s pinned version** to one that compiles against
  a newer SDK (check its changelog for when `compileSdkVersion` was raised
  past 34, and whether a newer version's own Kotlin module also fixes
  failure 1's `languageVersion 1.6` problem natively, making that
  workaround unnecessary too).
- **Pin `package_info_plus` to an older version** that doesn't carry the
  API 36 AAR metadata requirement (check its own changelog for when that
  requirement was introduced).
- Some combination of both, chosen for minimal version drift from what
  was originally human-approved.

**Either of these changes a human-approved pinned dependency version** —
per `AGENTS.md` rule 3, this is carved out as human-only even under the
2026-09-06 extended autonomy grant ("new dependencies" and version
changes to already-approved ones read the same way). Present the specific
version options with trade-offs at dispatch time; do not silently pick
one.

## What this fix does NOT do
- Does NOT touch `minSdk`/`targetSdk` — only `compileSdk`-level
  compilation compatibility is at issue.
- Does NOT change `ADR-0006`'s Sentry privacy configuration
  (`SentryObservabilityClient.configurePrivacyOptions`) or `E14-T04`'s
  `in_app_update`/Play Store integration behavior — this is a build-
  toolchain compatibility issue, not a behavior change to either feature.
- Does NOT re-attempt the four failed root-Gradle-script workarounds
  above — they are recorded here so the next attempt doesn't repeat them,
  not because they need to be tried again with different code.
