# E14-B01 · The version-policy cache is never written, so the whole epic is inert at runtime

## The defect

Three tasks each fenced the `refresh()` call site out to a *different* one of
the other two. The fences are individually defensible and collectively leave
a hole no task's tests could see:

- `lib/core/services/version_policy_service.dart:12-14` — *"It does NOT add a
  polling driver -- [refresh] has no caller in this task; when wired, the
  caller decides the cadence."*
- `lib/features/version/domain/evaluate_version_state_use_case.dart:15-17` —
  *"this use case does NOT call `refresh()` — only the already-cached policy
  is read; deciding when to refresh is `E14-T04`'s own wiring concern."*
- `lib/app/main.dart:64-67` — *"Only `.cached()` is consulted here:
  `.refresh()` has no caller in this task … this task wires the consumer, not
  a new remote-fetch trigger."*

Grep confirms it: across all of `lib/`, `refresh()` appears only in its own
declaration (`version_policy_service.dart:86`) and in three comments. There
is **no call site**.

Consequence chain, all of it mechanical:

1. `version_policy_cache` is never written outside tests.
2. `VersionPolicyService.cached()` (`version_policy_service.dart:133-137`)
   returns `null` — the row does not exist.
3. `EvaluateVersionStateUseCase.call()`
   (`evaluate_version_state_use_case.dart:99-101`) hits its documented
   fail-open branch: `if (policy == null) return VersionState.upToDate;` —
   and never even reads the installed build number.
4. `initialRouteFor(state)` (`main.dart:100-102`) therefore always returns
   `Routes.welcome`.
5. `VersionUpdateView` is registered in `appPages` (`routes.dart:117-121`)
   but has no reachable entry point.

`FR-VER-006`, `FR-VER-010` and the epic's own headline `EARS-VER-1` are
therefore satisfied only inside unit tests that inject a policy directly.
`FR-VER-008`'s *"on reconnect it shall fetch the current policy and
re-evaluate"* has no implementation at all — there is no reconnect hook and
no fetch.

Every per-task test passes because every one of them supplies the cached
policy itself: `evaluate_version_state_use_case_test.dart` passes a
`CachedPolicyProvider` stub, and `version_update_controller_test.dart` tests
`initialRouteFor` against a `VersionState` value handed to it directly.
Neither ever composes `VersionPolicyService.cached` against a real database
the way `main.dart` does.

## Repro

From a clean checkout of `epic_14`:

1. Add this test file and run `flutter test`:

```dart
final db = AppDatabase.forTesting(NativeDatabase.memory());
final svc = VersionPolicyService(database: db);
// main.dart:68-72's exact composition:
final useCase = EvaluateVersionStateUseCase(
  cachedPolicyProvider: svc.cached,
  installedBuildProvider: () async => 1, // an ancient, unsupported build
);
print(await useCase.call());
print(initialRouteFor(await useCase.call()));
```

2. Observe the output.

## Expected

`FR-VER-005` / `FR-VER-006`: a build below the published
`minimumSupportedBuild` evaluates `UPDATE_REQUIRED` and is routed to the
mandatory-update screen.

## Actual (reviewer's own probe, 2026-09-06, worktree off `origin/epic_14`)

```
PROBE1 state with build=1 and no refresh(): VersionState.upToDate
PROBE1 initialRoute: /welcome
```

The control probe proves the rest of the pipeline is correct and the missing
`refresh()` call is the *only* broken link — writing the cache row directly
and re-running the identical composition gives:

```
PROBE2 state: VersionState.updateRequired -> /version-update-required
```

## Severity

**S2** — major function broken, no workaround. The epic's entire enforcement
mechanism is inert in any shipped build. Argued up toward S1 on the grounds
that `FR-VER-010` (emergency minimum-version enforcement — the lever for
forcing users off a build with a known vulnerability) is the mechanism that
is inert; argued down from S1 because nothing crashes, no data is lost, and
no *existing* protection regresses. Left at S2; the human sets priority.

## Suggested fix shape (not binding)

`main.dart` already constructs `versionPolicyService`. The minimal honest fix
is to `await versionPolicyService.refresh()` **before** the
`evaluateVersionState.call()` at `main.dart:73` — `refresh()` is already
best-effort, timeout-bounded and never-throwing (`EARS-VER-4`), so a launch
with no network degrades to exactly today's behaviour rather than a hang.
`FR-VER-008`'s "on reconnect … re-evaluate" half is a larger question (there
is no connectivity hook wired for it) and may warrant its own follow-up task
rather than being smuggled into this fix.

## Regression test (required before close)

A test that composes `VersionPolicyService.cached` against a **real**
`AppDatabase.forTesting`, seams the remote read (`readVersionPolicyData`, the
existing test seam) to return an `updateRequired`-triggering payload, runs
the same launch sequence `main()` runs, and asserts `initialRouteFor` returns
`Routes.versionUpdateRequired`. It must fail on today's `epic_14` HEAD.

## What this fix does NOT do

- Does NOT add a polling timer, a periodic refresh, or a mid-session
  re-check. Launch-time only, matching `E14-T04`'s own existing fence.
- Does NOT implement `FR-VER-008`'s reconnect-triggered re-evaluation — that
  needs a connectivity signal this fix does not wire.
- Does NOT change `EvaluateVersionStateUseCase`, `VersionPolicyService`,
  `VersionUpdateView` or `VersionUpdateController` — all four are correct as
  written; only the composition root is missing a call.
- Does NOT block application communication on the update screen — that is
  `E14-B02`'s own defect and its own fix.
- Does NOT touch `VersionPolicy.signature` verification (`FR-VER-011`,
  `E14-T03`, still blocked on `OQ-E14-T03-1`).
