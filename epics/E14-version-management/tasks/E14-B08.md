# E14-B08 · re-audit `configurePrivacyOptions` against `sentry_flutter` 9.x's changed defaults

## The defect

`E14-B07` bumped `sentry_flutter` 8.14.2 → 9.29.0 (human-approved, to fix
a real Android build failure — unrelated to this bug). That major version
bump changed two things `configurePrivacyOptions`
(`lib/core/observability/observability_service.dart`) does not currently
address:

1. **`SentryFlutterOptions.anrEnabled` default flipped from `false` to
   `true`.** Confirmed by reading both versions' own source directly:
   `sentry_flutter-8.14.2/lib/src/sentry_flutter_options.dart:72` vs.
   `sentry_flutter-9.29.0/lib/src/sentry_flutter_options.dart:71`. ANR
   (Application Not Responding) detection is native, automatic capture —
   the same category of "capture more than this app ever intends to send"
   that `configurePrivacyOptions`'s own header comment already explicitly
   disables `enableAutoNativeBreadcrumbs` for, on exactly that reasoning.
2. **Session Replay (screen-recording capture) GA'd in 9.x** — did not
   exist as a shipping feature in the pinned 8.14.2. Confirmed currently
   OFF by default (`sentry_replay_options.dart:83` — `isEnabled` requires
   `sessionSampleRate`/`onErrorSampleRate` > 0, both `null` by default),
   but `configurePrivacyOptions` does not explicitly pin it off the way it
   explicitly pins `attachScreenshot`/`attachViewHierarchy` off — it is
   silently relying on the SDK's own default staying conservative, which
   is precisely the trust `configurePrivacyOptions`'s own existing code
   comments say this file deliberately does NOT extend to Sentry's
   defaults.

## Why this is blocked, not just todo

**No DSN is currently configured anywhere in this project** — `init()`
early-returns before `SentryFlutter.init()` ever runs
(`E13-B03`'s fix, already merged). So there is currently zero real-world
exposure: nothing captures ANR events or replay data because Sentry never
initializes at all. Deciding exactly which flags to pin, and to what
values, is more naturally scoped alongside whoever configures a real DSN
for the first time (an operational/business decision — when/whether this
project ever turns on real crash reporting) rather than guessed at now
against a feature set with zero current runtime relevance. Filed now so
the finding isn't lost (rule 8), `status: blocked` on that future trigger,
not because of a missing technical decision.

## Expected

`configurePrivacyOptions` explicitly sets `anrEnabled` and every Session
Replay-relevant option to the project's own intended default (whatever ADR-
0006's privacy stance concludes for each), rather than depending on
whatever `sentry_flutter`'s own next major version happens to default to.

## Actual

Both are left at the SDK's own default, undocumented by this file, and
un-pinned against a future SDK upgrade silently changing them again.

## Severity

**S4** — zero current runtime exposure (no DSN configured, `init()` never
reaches the SDK). Correctness/future-proofing only.

## Suggested direction (not binding, builder's call once unblocked)
- Read `ADR-0006`'s actual privacy stance and decide, for each of
  `anrEnabled` and the `SentryReplayOptions` fields, whether this
  project's intended posture is "off" (matching the rest of
  `configurePrivacyOptions`'s existing all-off defaults) or something
  else — then set it explicitly, with a comment citing this bug and the
  version this default changed at (so a future upgrade's changelog is
  the thing to re-check, not a silent re-drift).
- Do NOT wait for a real DSN to exist before doing this — the fix itself
  (explicit flags) is safe and free to ship regardless of whether Sentry
  is actually initialized anywhere; the "blocked" status above is about
  WHEN this is worth prioritizing, not a technical dependency on a DSN
  existing.

## What this fix does NOT do
- Does NOT configure or add a real Sentry DSN anywhere — that is a
  separate, human-owned operational decision (secrets, per rule 3),
  entirely independent of this bug.
- Does NOT change any other `configurePrivacyOptions` setting already
  pinned (tracing, `attachScreenshot`, `attachViewHierarchy`,
  `enableAutoNativeBreadcrumbs`, etc.) — those are unaffected by this
  version bump per `E14-B07`'s own review.
- Does NOT re-litigate whether bumping `sentry_flutter` to 9.29.0 was the
  right call — that's `E14-B07`, already reviewed and merged.
