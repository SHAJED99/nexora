# E14-T06 · Migration-safety regression suite

## 1. Goal
`FR-VER-003`/`FR-VER-009`: prove, as one standing regression suite rather
than scattered per-task assertions, that every migration step in
`database.dart`'s `onUpgrade` from schemaVersion 1 to the current version
is additive-only and never destroys a pre-existing row.

## 2. Business logic
`FR-VER-003` ("application updates shall migrate database schema, local
configuration, cryptographic structures, communication protocol, and
synchronization metadata without intentionally destroying existing local
conversations"), `FR-VER-009` ("mandatory application updates shall not
delete local messages, voice messages, call recordings, attachments,
user settings, or conversation history").

`docs/conventions.md`'s "Schema migrations" rule already mandates
additive-only steps, and every task from `E01` through `E13` has
individually followed it (each migration test file --
`database_migration_test.dart` and its per-task siblings -- already
proves ITS OWN step is additive, in isolation). What does not exist yet
is ONE suite that walks the FULL chain end to end -- v1 all the way to
the current version -- seeding realistic data at v1 (messages,
conversations, settings) and asserting every one of those rows survives
verbatim after every subsequent step runs, which is a stronger and more
direct statement of `FR-VER-003`/`FR-VER-009` than "each step is additive
in isolation" already gives.

## 3. What this task does
- One new test file that: builds a raw v1 schema (reuse
  `database_migration_test.dart`'s own earliest fixture-building function
  as the starting point, do not re-derive it), seeds representative rows
  in the tables that exist at v1 (at minimum: `device_identities`,
  `messages` -- the two `FR-VER-009` names explicitly and this codebase
  has from the start), snapshots them, opens the handle at the CURRENT
  `schemaVersion` (triggering the full migration chain), and asserts
  every seeded row is still present with byte-identical field values.
- Runs this same proof for every intermediate `schemaVersion` a real
  install could plausibly resume from (not just v1 -- a device paused
  mid-upgrade-chain at any prior version must also survive), reusing the
  "open at v13/v14/etc." pattern every existing per-task migration test
  file already establishes.

## 4. What this task does NOT do
- Does **not** change any migration step itself -- this is a proof
  suite, not a fix. If it finds a real destructive step, that is a NEW
  bug, filed separately (do not fold a fix into this task's own `files:`
  fence).
- Does **not** duplicate every existing per-task migration test file's
  own narrower assertions -- this suite is additive, a stronger
  end-to-end statement layered on top of what already exists, not a
  replacement for any of them.
- Does **not** cover crypto-structure or protocol-version migration
  (`FR-VER-003`'s other named categories) beyond what `database.dart`'s
  own migration chain touches -- `signal_identity`/`signal_sessions`
  table survival is covered by the same generic "every v1-onward table's
  seeded rows survive" proof, but this task does not separately exercise
  E03's own session-state semantics beyond row presence.

## 5. Contract
No new production code -- test-only task, no `Functions`/`Data`/`UI`
sections apply.

## 6. Risks
- The full migration chain (v1→current) will only grow longer over
  time -- this suite's own runtime cost grows with it. Acceptable; a
  slow-but-thorough regression test is the correct trade here, not a
  reason to sample a subset of versions.
- `schemaVersion` at execution time may have moved past whatever this
  task assumes while writing it -- verify the real current value, same
  standing note as every other task this session that touches
  `database.dart`.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-VER-15**: WHEN a database is migrated from schema v1 to the
  current version, THE system SHALL preserve every pre-existing message
  and device-identity row, byte-identical. (FR-VER-003, FR-VER-009)
- **EARS-VER-16**: WHEN a database is migrated from any intermediate
  schema version to the current version, THE system SHALL preserve every
  pre-existing row from that version's own tables. (FR-VER-003)

### Tests
- `test_EARS_VER_15_v1_to_current_preserves_seeded_rows_byte_identical`
- `test_EARS_VER_16_intermediate_version_to_current_preserves_rows`
  (parameterized/repeated across a representative sample of versions)

None — no UI surface, test-only task.
