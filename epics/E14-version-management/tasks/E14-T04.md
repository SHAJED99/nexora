# E14-T04 · Mandatory-update screen and Google Play in-app update integration

## 1. Goal
Close `FR-VER-006`/`FR-VER-007`: when `E14-T02`'s state machine evaluates
`UPDATE_REQUIRED`, block app use and route the user to Google Play's
in-app update flow, non-dismissibly.

## 2. Business logic
`FR-VER-006` (block communication, present a non-dismissible mandatory
prompt), `FR-VER-007` (use Google Play's in-app update mechanism —
specifically the Immediate Update flow, never a silently-downloaded
arbitrary APK), `FR-VER-009` (the update itself must not delete local
data — already true by construction, since Play's in-app update
mechanism updates the installed package in place and never touches app
data directories; this task's own copy states that property per
`design/screens/version-update-required.md`'s own contract, it does not
need to newly guarantee it).

A NEW dependency is required here — the Google Play in-app update API
has no first-party Flutter binding in this project today (verify at
execution time; `in_app_update` is the commonly-used package for this on
pub.dev, but the exact package choice is this task's own decision,
subject to the `pubspec.yaml` 🧍 gate below, same as `E13-T06`'s own
observability-vendor precedent).

## 3. What this task does
- `lib/app/main.dart` (or wherever this codebase's own app-lifecycle
  entry point already runs a startup check — verify the real structure
  before assuming one) calls `E14-T02`'s `EvaluateVersionStateUseCase`
  once at launch; if `updateRequired`, routes to
  `/version-update-required` instead of continuing the normal
  startup→login/dashboard flow.
- `VersionUpdateController`/`VersionUpdateView` implementing
  `design/screens/version-update-required.md`'s single state: the
  `Update now` button starts the platform in-app update's Immediate
  Update flow.
- Add the chosen package to `pubspec.yaml` — 🧍 human gate, per
  `docs/conventions.md`'s "requires a human-approved addition, recorded
  as a one-line note here with the approving human gate."
- **Non-dismissible, structurally**: no back-button handling added that
  pops this route, no close affordance in the view, and the route is
  reached in a way that leaves no previous route on the navigation stack
  to pop back to (verify GetX's own route-replacement mechanism, e.g.
  `Get.offAll`, rather than a plain push).

## 4. What this task does NOT do
- Does **not** implement `UPDATE_AVAILABLE`'s own (non-blocking,
  dismissible) UI — out of `GAP-029`'s own scope (its own boundary note),
  and out of this task's.
- Does **not** re-check the version state mid-session on any new timer —
  a launch-time check is this task's own scope; a mid-session interrupt
  (per `design/screens/welcome.md`'s own Journey gap note, "at launch
  and/or mid-session, a behavioral decision for whichever task builds
  it") is deliberately picked here as launch-time-only, simplest correct
  behavior for a first build of this screen; extending to mid-session
  is a follow-up if ever needed, not silently added now.
- Does **not** implement `E14-T03`'s signature verification — this task
  consumes `E14-T02`'s state machine as-is, unverified per that task's
  own current scope.
- Does **not** touch `LoginController`, `/dashboard`, or any other
  existing route beyond the one new launch-time branch point.

## 5. Contract

### External services & flags
Service: Google Play in-app update API (via the chosen Flutter package)
— 🧍 new dependency, human gate at `pubspec.yaml`. No new secret/env var
(the API works against the app's own Play Store listing, no key needed
client-side).

### Functions
```yaml
- signature: "VersionUpdateController.startImmediateUpdate() -> Future<void>"
  params: {}
  returns: "launches the platform's Immediate Update flow; failure is logged (ObservabilityService), the screen stays -- there is nothing else for the user to do but retry the same button"
  purpose: "the mandatory screen's one action"
```

### UI

- Route: `/version-update-required` · reached at launch when

## 6. Risks
- **Getting "non-dismissible" wrong is this task's single most important
  risk.** A `WillPopScope`/`PopScope` that silently allows a pop under
  some untested condition, or a route pushed atop an existing stack
  (leaving something to pop back to), both defeat `FR-VER-006`'s entire
  point. Test the back gesture/button explicitly, not just the happy
  path.
- Google Play in-app update APIs are Android-only in practice (no iOS
  equivalent exists in the same shape) — confirm at execution time what
  this codebase's actual target platform(s) are and what the chosen
  package does on a platform without the API (verify it degrades safely
  rather than crashing, per the package's own documented behavior).
