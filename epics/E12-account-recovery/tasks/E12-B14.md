# E12-B14 · device row order is non-deterministic when `updatedAt` ties

## The defect

```dart
// lib/features/trust/data/relationship_repository.dart:43
..orderBy([(t) => OrderingTerm.desc(t.updatedAt)])
```

No secondary sort key. When two or more rows share the same `updatedAt`
(e.g. seeded in one test tick, or any real-world case of two devices
updated in the same millisecond), SQLite's tie-break order is unspecified —
different runs can return the same rows in different orders.

## Why this matters beyond a flaky test

The `devices` screen's design-verify probe (`E12-B12`) upserts its 4 fixture
device rows in one tick, so this repository read is exactly the kind of tie
this bug describes. `design/tools/compare.mjs`'s element-matching pass pairs
elements by nearest position, so a reordered render mispairs rows against
the golden and produces phantom copy/color findings that have nothing to do
with real fidelity — confirmed in `E12-B12`'s own review run (a device's
"Last seen: 5d ago" text reported as both missing and a copy mismatch on a
sibling row, consistent with a swapped pair). **This makes `devices`' own
design-verify score non-reproducible by a few points from run to run**,
which undermines any threshold decision made against it.

Beyond the test/gate context, this is also a real production concern: any
UI relying on stable device-row ordering (screen-reader announcement order,
scroll-position preservation across refreshes) could see rows silently
reorder between renders with no underlying data change.

## Expected

Identical underlying data always renders in the identical row order,
run to run.

## Actual

Rows with tied `updatedAt` values can render in a different order between
runs.

## Fix

Add a secondary sort key, e.g.:
```dart
..orderBy([
  (t) => OrderingTerm.desc(t.updatedAt),
  (t) => OrderingTerm.asc(t.deviceId),
])
```
`deviceId` is already unique and stable, making the sort fully deterministic.

## Severity

**S3** — no data loss or security issue, but genuinely undermines design-
verify's own reliability (the gate meant to catch real drift), plus a minor
real-world UX consistency gap.

## What this fix does NOT do
- Does NOT change `RelationshipRepository`'s primary sort criterion
  (`updatedAt desc` stays the main ordering).
- Does NOT touch `devices_view.dart`, `DevicesController`, or any other
  E12-B12-adjacent file — this is a one-line query fix in the repository
  layer only.
- Does NOT re-run or re-triage `devices`' own design-verify score — that's
  a natural follow-up once this lands, not part of this task.
