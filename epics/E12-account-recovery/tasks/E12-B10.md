# E12-B10 · a self-authored enrollment grant is not rejected at the rules level

## The defect

`database.rules.json`'s `device_enrollment_grants/$newDeviceId` node allows
any authenticated write for the account's own `$uid` with an
`approvedByDeviceId` field validated only as a non-empty string ≤128 chars.
Nothing requires it to differ from `$newDeviceId`, or to name a device that
actually exists under `users/$uid/devices/`.

No in-app code path reaches this today — `writeEnrollmentGrant` is only
called from `verify()` behind an existing pending-enrollment check — so this
is defense-in-depth, not a reachable exploit via the current client.

## Severity

**S4** — no reachable path through the shipped app; a client that could
write an arbitrary self-grant already controls its own `checkApproval()`
read, so the practical value is limited. Still worth tightening since this
is an authorization-relevant rule.

## Suggested fix (not binding)

Tighten the rule's `.validate` to also require:
```
newData.val() !== $newDeviceId &&
root.child('users').child($uid).child('devices').child(newData.val()).exists()
```
so the writer must name a real, already-registered device other than the
target.

## What this fix does NOT do
- Does NOT change the write/read call sites in `devices_controller.dart` or
  `device_enrollment_controller.dart` — this is rules-only.
- Does NOT add a new emulator-backed test suite; extend the existing
  structural assertions in `firebase_rules_test.dart`.
