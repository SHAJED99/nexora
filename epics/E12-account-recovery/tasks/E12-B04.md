# E12-B04 · a stale or failed own-device-id read is cached forever

## The defect

```dart
// lib/features/devices/presentation/devices_controller.dart:~245
Future<Set<String>> _ownDeviceIds() {
  return _ownDeviceIdsFuture ??= () async {
    final String? uid = await _currentAccountUid();
    return uid == null
        ? const <String>{}
        : await _firebaseMetadataService.readOwnDeviceIds(uid);
  }();
}
```

`_ownDeviceIdsFuture` is memoised for the controller's entire lifetime with no
invalidation path — not on `load()`, not on `discover()`, not on a manual
refresh. Two consequences:

**1. Ordering.** The enrollment journey is inherently "open Devices on the
trusted phone, *then* bring the new device up". But `readOwnDeviceIds` is
resolved on the first discovery event. If the trusted device's Devices screen
resolved that future before the new device completed `registerDevice`, the
cached set does not contain the new device's id, `_classifyDiscoveredDevice`
returns `normal`, and the new device is rendered as an ordinary Unknown
stranger with a generic "Verify" button instead of an Approve/Deny enrollment
row — for as long as the screen stays open.

**2. Fail-open, cached.** `readOwnDeviceIds` swallows every Realtime Database
error and timeout and returns `const {}` (`firebase_metadata_service.dart:~200`).
That empty set is then cached identically to a real answer. A single transient
network blip at the moment of first discovery permanently disables enrollment
detection for that controller's lifetime, with no telemetry distinguishing it
from "this account genuinely has no other devices".

## Repro

1. Trusted device: open Devices, tap Discover (with no other device nearby).
   → `_ownDeviceIdsFuture` resolves to the current registry.
2. New device: sign in on the same account (`registerDevice` adds its id).
3. Trusted device, same screen still open: the new device is discovered.
4. Observe: rendered as an Unknown stranger row, not "Awaiting your approval".

## Expected

`EARS-RECOVER-5`/`EARS-RECOVER-6`: a discovered device that is one of this
account's own registered devices with no local relationship is classified as a
pending enrollment.

## Actual

Classified `normal`, because the cached set predates its registration.

## Severity

**S3** — there is a workaround (leave the Devices screen and return, disposing
the controller and clearing the cache), and the user is not blocked from
anything else. But the workaround is undiscoverable, and step 1→2 is the
*natural* order a user performs this task in.

## Suggested direction

Re-resolve on each `discover()` invocation (cheap, user-initiated, bounded), or
cache only successful non-empty reads and retry on a classification miss.
Preserve E12-T02's actual concern — the in-flight-`Future` de-duplication that
its own reviewer verified — which is about concurrent discovery events within
one cycle, not about caching across cycles.

## What this fix does NOT do

- Does **not** remove the in-flight `Future` de-duplication (regression test
  `readOwnDeviceIds is fetched at most once per controller lifetime` will need
  its scope re-stated to "per discovery cycle", not deleted).
- Does **not** add a polling/refresh timer — E10's one-tick discipline stands.
- Does **not** change `readOwnDeviceIds`'s own fail-open contract.
- Does **not** touch `devices_view.dart` or the row rendering.

  anyway, matching the existing `_evaluatingIds` precedent).
