# E12-T01 · Read back this account's own device list from Firebase

## 1. Goal
Give `E12-T02`/`E12-T03` the one fact both need: which device ids already
exist under this account's own Firebase device registry — the mechanism
`FR-RECOVER-001`'s "existing trusted device shall authorize enrollment"
turns out to need no new backend protocol at all, only a way to read data
that already exists.

## 2. Business logic
`FR-RECOVER-001`. `FirebaseMetadataService.registerDevice` (E01-T02)
already writes every device this account has ever signed in from to
`users/$uid/devices/$deviceId`; `FirebasePaths.devices(uid)` (E11-T01)
already names the parent path. Nothing reads the whole list back —
`FirebaseMetadataService.readDeviceMetadata` reads exactly one device's
node, and the only existing whole-subtree reader,
`DeviceRevocationService.readDevicesData` (E11-T04), is scoped to that
class's own revocation-flag extraction, not a general list.

This task adds the analogous whole-list reader to
`FirebaseMetadataService` itself (the class that already owns
`users/$uid/devices` writes), mirroring
`DeviceRevocationService.readDevicesData`'s exact seam-splitting pattern
(a raw-read method plus a pure extraction function) rather than adding a
second, competing whole-subtree reader elsewhere.

## 3. What this task does
- `FirebaseMetadataService.readOwnDeviceIds(String uid) ->
  Future<Set<String>>`: reads `users/$uid/devices` once (best-effort,
  bounded timeout, catch-and-log via `ObservabilityService` — this
  class's own existing pattern for every other method), and returns the
  set of device id keys present. Absent/malformed data reads as an empty
  set, never a thrown error — this is a best-effort hint, not a source of
  truth anything blocks on.
- A private, pure extraction function (mirrors
  `DeviceRevocationService._extractRevocationFlags`'s shape) that turns
  the raw snapshot value into the `Set<String>`, testable without a
  Firebase call.

## 4. What this task does NOT do
- Does **not** change `registerDevice`, `readDeviceMetadata`, or any
  existing write path — purely additive, one new method.
- Does **not** call this new method from anywhere — that is `E12-T02`'s
  and `E12-T03`'s own job. This task has no caller yet.
- Does **not** distinguish "revoked" or "stale" devices in the returned
  set — every key present under `users/$uid/devices` is returned, exactly
  as stored. Filtering (e.g. excluding a revoked device from being
  treated as a valid enrollment authority) is whichever consuming task's
  own concern, informed by `E11-T04`'s existing revocation data if it
  turns out to matter.
- Does **not** add a new Firebase path or rule — `FirebasePaths.devices`
  and its existing `.read`/`.write` rules (owner-only, `users/$uid`'s own
  scope) are unchanged and already sufficient; this task only adds a
  reader on the Dart side.

## 5. Contract

### Functions
```yaml
- signature: "FirebaseMetadataService.readOwnDeviceIds(uid: String) -> Future<Set<String>>"
  params: { uid: "the authenticated account's own uid -- never a foreign account's" }
  returns: "the set of device id keys present under users/$uid/devices; empty on any failure, timeout, or absent data"
  purpose: "the one whole-list read E12-T02/E12-T03 both need"
```

## 6. Risks
- This is a best-effort, eventually-consistent hint (same as every other
  Firebase read in this codebase) — a device that registered moments ago
  on a flaky connection may not yet appear. Consuming tasks must treat an
  empty/small result as "couldn't confirm," never as "definitely no other
  devices exist," and must never block indefinitely on this call
  succeeding.
