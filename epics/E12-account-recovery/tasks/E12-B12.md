# E12-B12 · `devices` is now visibly, measurably red

## The defect

`node design/tools/verify.mjs --screen devices --impl flutter` now runs
cleanly (per `E12-B05`'s fix) and reports:

```
❌ FAIL devices/default@390x844 — match 62.3% (38/61)
  ❌ 23 missing element(s)   ❌ 26 copy mismatch(es)
  ❌ 103 style delta(s)      ❌ 4 off-palette token(s)   ⚠️ 34 layout delta(s)
```

Full report: `design/reports/devices/default@390x844/report.md`.

Before `E12-B05`, this screen's gate had been reporting `renderError: true`
for an unknown period — a broken fixture, not a real 0%. Now that the probe
renders correctly, the real number is visible for the first time, and it is
red. This is not new drift caused by this epic (`devices_view.dart` has zero
diff in `E12-B04`/`E12-B05`'s fix) — it is pre-existing drift that was
simply unmeasured until now.

## Expected

`devices` matches `design/screens/devices.md` within the project's
configured threshold (per `skills/design-fidelity`).

## Actual

62.3% (38/61) — well below threshold, with missing elements, copy
mismatches, style deltas, and off-palette tokens.

## Severity

**S3** — a real, shipping screen with visible drift, but no crash and no
data-safety concern. The design gate itself is the value here: this bug
existing and being tracked is the whole point of fixing `E12-B05`'s probe
in the first place.

## What this fix does NOT do
- Does NOT relax `thresholds.yaml` to make 62.3% pass (rule 2 — that is the
  `design_threshold_relaxation` human gate, a separate decision).
- Does NOT touch `E12-B05`'s probe fixture again — that fix is confirmed
  correct and unrelated to this drift.
- Is not, by itself, evidence of what specifically changed — read
  `design/reports/devices/default@390x844/report.md`'s full element-by-

  `lib/features/devices/presentation/devices_view.dart` (the build), and the
  full report side by side. Root-caused each finding bucket before touching
  code — several turned out NOT to be `devices_view.dart` defects at all,
  but structural limits of `test/design/flutter_probe_dumper.dart` (the
  Flutter-side probe engine, out of this bug's fence and shared by every
  screen — see §Deviations):
  - The dumper never emits a `heading:N` role — every `Text` dumps as
    `generic` (confirmed against its own EARS-UI-1 test, which asserts
    `title['role'] == 'generic'` for a plain heading `Text`). The contract's
    `heading:1` "NEXORA", `heading:2` "Network Nodes" and four `heading:3`
    device-name rows can never match on role, regardless of what
    `devices_view.dart` does.
  - Any `Icon`/`Text` nested inside an interactive ancestor (`InkWell`,
    `PopupMenuButton`/`IconButton`, and `OnProcessButtonWidget`'s own
    internal gesture handling) is swallowed by `_walk`'s
    `insideInteractive` guard and never dumped as a separate element. This
    is why the bottom nav's `dashboard`/`Dashboard`/`chat`/`Conversations`/
    `settings`/`Settings` glyph+label pairs, the kebab menu's `more_vert`
    glyph, and the `Discover`/`Verify` buttons' own icon+label text all
    report as missing/absent or empty — not because the screen doesn't
    render them (it does — confirmed via a raw dump of
    `build/design-probe/devices.json`), but because the probe cannot see
    inside an accessible tap target. Per `skills/design-fidelity` rule 5,
    this is the tool's own documented limitation (the same shape as
    `L-frontend-001`), not something to route around by reshaping the
    widget tree (that would trade away real gesture-arena/accessibility
    behaviour for a score, exactly what rule 5 forbids).
  - The `button` role in the dumper never records `color`/`fontSize`/
    `fontFamily` (only `background`/`radius`/`borderWidth`/`borderColor`
    from a decoration), and never reads `OnProcessButtonWidget.borderRadius`
    at all (only `.backgroundColor`). Every `button`-role style delta in the
    report (icon-button tint, `Discover`/`Verify`'s radius/fontSize/
    fontFamily) is this same gap, not a devices_view style bug.
  - A `Color`'s alpha channel is an 8-bit int internally; `0.1` opacity has
    no exact `x/255` representation, so it always resolves to `≈0.102`. The
    4 "off-palette" `rgba(…, 0.102)` findings (background/border fills) are
    this rounding, not an invented colour.
  - The remaining `<nav>`/`<a>`/`<header>` "missing" rows are DOM-only
    wrapper elements from the design's own web export with no Flutter
    layout-tree equivalent (Flutter has no anchor/nav tag); their
    constituent content is separately captured (or, per the point above,
    swallowed) but the wrapper itself has nothing to match.
  - The genuinely real, fixable devices_view.dart defect found: every
    device row rendered a fixed `Icons.devices` glyph regardless of
    `RelationshipState`, which collided (case-insensitively, in the
    matcher's own text key) with the bottom nav's "Devices" tab label —
    that collision, not a real style bug, was producing several of the
    report's more confusing findings (a nav label "matching" a device row's
    icon and inheriting its colour/size).

## Deviations
- **Full pass not reached; genuinely blocked by tooling this bug's own
  fence excludes, not by `devices_view.dart`.** `design/thresholds.yaml`
  requires 0 missing / 0 copy / 0 style / 0 off-palette to pass — every
  hard-failure bucket still has real findings after this fix, but the
  large majority trace to `test/design/flutter_probe_dumper.dart`'s own
  documented capability gaps (see Run log): no `heading:N` role ever
  emitted; icon/text nested inside ANY interactive ancestor (`InkWell`,
  `IconButton`/`PopupMenuButton`, `OnProcessButtonWidget`'s internal
  gesture handling) swallowed and never dumped separately; the `button`
  role never records `color`/`fontSize`/`fontFamily` and never reads
  `OnProcessButtonWidget.borderRadius`; an 8-bit alpha channel cannot
  represent a literal `0.1` opacity exactly (~0.102 is the closest
  possible value); the design's own DOM-only `<nav>`/`<a>`/`<header>`
  wrapper elements have no Flutter layout-tree equivalent. Per
  `skills/design-fidelity` rule 5, these are the gate's own limitations to
  fix in the probe (or record as a known cause, as done here) — never the
  shipped UI's problem to route around by reshaping the widget tree (that
  is the exact `L-frontend-001` anti-pattern the rule names). Fixing the
  dumper itself is out of this bug's fence (shared by every screen's
  probe, not scoped to `devices`) and explicitly excluded a second time by
  `E12-B05`'s own precedent ("does NOT touch E12-B05's probe fixture
  again"). Recommend a follow-up bug against
  `test/design/flutter_probe_dumper.dart` if closing these buckets for
  real is wanted project-wide.
- **`Wi-Fi Direct`/`Bluetooth LE`/`Mesh Proximity` subtitle copy left
  unchanged (still the fixed `'Paired locally'` placeholder).** This is
  `design/gaps.md GAP-003` (already approved, pre-existing, called out in
  this same file's own top-of-file comment before this bug): no transport-
  type metadata exists in `RelationshipRepository` pre-E04 discovery.
  Fabricating a fixed one of the contract's three transport-type strings
  per row would be actively misleading (a real device's real transport has
  nothing to do with which of the four example rows it happens to render
  as), not a fidelity improvement — left as the same honest, already-
  documented gap, only the row's font family was corrected.
- **Nav-bar tab labels (`Dashboard`/`Conversations`/`Devices`/`Settings`)
  and the header's own icon/text `fontSize`/`fontFamily` deltas left
  unresolved.** Both are the swallowed-by-interactive-ancestor and
  Icon-widget-has-no-font-metadata dumper limitations above, not
  devices_view defects — see Run log root-cause notes.
