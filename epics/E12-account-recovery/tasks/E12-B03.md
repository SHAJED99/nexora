# E12-B03 · a remote approval is discarded by the conflict resolver

## The defect

`DeviceEnrollmentController.checkApproval()` is built entirely on
`pull()`-then-read-local:

```dart
// lib/features/recovery/presentation/device_enrollment_controller.dart:137
Future<bool> checkApproval() async {
  await _relationshipSyncService.pull(_accountUid);
  final relationship = await _relationshipRepository.get(_thisDeviceId);
  final peerState = relationship?.state;
  return peerState == RelationshipState.trusted ||
      peerState == RelationshipState.allowed;
}
```

`pull()` merges each remote state with the local one through
`ConflictResolver.resolveTrust`, which implements `FR-MSG-007` —
**the more restrictive state wins**:

```dart
// lib/features/messaging/domain/conflict_resolver.dart:50
static const List<RelationshipState> _trustRestrictiveness = [
  RelationshipState.blocked,   // rank 0
  RelationshipState.unknown,   // rank 1
  RelationshipState.allowed,   // rank 2
  RelationshipState.trusted,   // rank 3
];
// resolveTrust: aRank <= bRank ? a : b   -> lower rank wins
```

An enrolling device has **no local relationship row** — by definition, and
enforced on the other side too (`_classifyDiscoveredDevice` only classifies
a peer as `pendingEnrollment` when `_repository.get(deviceId) == null`).
`pull` therefore treats the local side as `unknown` (rank 1), and:

`resolveTrust(unknown, allowed)` → **`unknown`**

`merged == localState`, so `pull` does not even write a row. The approval is
silently dropped. `checkApproval()` returns `false` forever.

## Repro

Reviewer probe — a real in-memory `RelationshipRepository` with no local rows,
`pull()` against a relationships subtree holding three already-decided peers:

```
dev-1 (remote allowed): null
dev-2 (remote trusted): null
dev-3 (remote blocked): RelationshipState.blocked
resolveTrust(unknown, allowed) = RelationshipState.unknown
```

`blocked` propagates. `allowed` and `trusted` are discarded. `pull()` is a
**restriction-only** channel.

## Expected

`EARS-RECOVER-1`: an existing trusted device's authorization reaches the
enrolling device.

## Actual

It cannot, by construction. Even with `E12-B02` fixed and the node correctly
written, `checkApproval()` returns `false` on every poll and the screen
times out to `denied`.

## Severity

**S1** — same total blocker as `E12-B02`, from an independent cause. Fixing
either one alone changes nothing.

## This is a spec conflict, not just a coding error — route via the planner

`FR-MSG-007`'s "more restrictive wins" is correct for reconciling two devices'
*independent opinions* about a third-party peer. An enrollment approval is not
an opinion to be reconciled — it is an **authorization grant** from a trusted
device to a specific new device. Running it through the conflict resolver is a
category error introduced when T03 chose `pull()` as its transport.

Options for the planner (rule 3 — do not pick one unilaterally):
- a dedicated enrollment-approval node/path, not `relationships/*`, read
  directly rather than merged;
- an explicit "grant" merge rule that is allowed to raise trust when the
  writer is one of the account's own registered devices;
- keeping `pull` restriction-only and giving enrollment its own channel.

Each has a different `ADR-0008` / `FR-MSG-007` blast radius. Recommend an
`IMP-nnn` via `skills/change-impact` before the fix task is sharded.

**🧍 Human decision (2026-09-06):** dedicated enrollment-approval node/path
(option 1) — a new Firebase path, read directly, never merged through
`ConflictResolver`. Does not touch `FR-MSG-007` or `resolveTrust` at all;
mirrors `E14-T01`'s own precedent of a dedicated reserved node
(`config/version_policy`) for a value that isn't an ordinary peer-trust
opinion. The fix task should pair this with `E12-B02` (the write side) —
both ends of the same new channel — rather than fixing either in
isolation.

## What this fix does NOT do

- Does **not** loosen `ConflictResolver.resolveTrust` for the general
  peer-relationship case — `FR-MSG-007` stays binding there, and `blocked`
  must keep winning everywhere.
- Does **not** change `pull`'s Firebase read seam or its best-effort
  error handling.
- Does **not** address the missing write side (`E12-B02`).
- Does **not** change the enrollment screen's three UI states.
