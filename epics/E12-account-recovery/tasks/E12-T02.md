# E12-T02 · Detect and surface a pending new-device enrollment request

## 1. Goal
Close `FR-RECOVER-001`'s "existing trusted device shall authorize the new
device's enrollment" half — the existing device's side of the journey.

## 2. Business logic
`FR-RECOVER-001`. `DevicesController._onDeviceDiscovered`
(`devices_controller.dart:~150`) already evaluates every newly-discovered
peer via `EvaluateConnectionRequestUseCase`, which defaults an
never-seen device to `RelationshipState.unknown` — the SAME treatment
whether the peer is a stranger or this account's own new device
enrolling. This task adds one more check before that default applies:
if the discovered device id is in `E12-T01`'s `readOwnDeviceIds(uid)`
result AND has no local relationship entry yet
(`RelationshipRepository.get(deviceId) == null`), it is this account's
own device enrolling, not an unknown stranger — render it as a pending
enrollment request (`design/screens/device-enrollment-approval.md`),
not the generic unknown-peer treatment.

Approving or denying reuses `DevicesController`'s OWN EXISTING methods —
`verify(deviceId)` (promotes to trusted/allowed, already wired to
`RelationshipRepository.upsert` via `RelationshipSyncService.push`) and
`block(deviceId)` — no new trust-recording logic. This task is UI
classification + a design contract's row, not a new backend mechanism.

## 3. What this task does
- `DevicesController` gains a way to know "is this discovered device id
  one of my own account's registered devices with no relationship yet" —
  calling `E12-T01`'s `readOwnDeviceIds` once per discovery cycle (cache
  the result for the session; it is a best-effort hint, not something to
  re-fetch on every single discovery event) and cross-referencing against
  `RelationshipRepository.get`.
- `device-enrollment-approval.md`'s row (device platform icon + name +
  short code, `Awaiting your approval` status label, `Approve`/`Deny`
  buttons) renders at the TOP of the existing device list for any device
  classified as a pending enrollment request — `devices_view.dart` gains
  this row rendering, `devices.md`'s own generated element table and
  every other row are unchanged (design-fidelity rule 1: never hand-edit
  a generated contract to accommodate a new row; this contract's row is
  read from `device-enrollment-approval.md` instead).
- `Approve` calls the controller's existing `verify(deviceId)`; `Deny`
  calls the existing `block(deviceId)`. Both already exist; this task
  only adds the classification that decides WHEN to show this row instead
  of the ordinary unknown-peer treatment, and wires the two existing
  buttons to it.

## 4. What this task does NOT do
- Does **not** add any new trust-recording mechanism — `verify`/`block`
  and everything under them (`RelationshipRepository`,
  `RelationshipSyncService`) are completely unchanged.
- Does **not** send any notification (push or otherwise) about a pending
  request — `design/gaps.md` GAP-028 explicitly deferred this; a request
  is only visible while the Devices screen is open and discovery is
  active.
- Does **not** change `EvaluateConnectionRequestUseCase` or
  `evaluate_connection_request_use_case_test.dart` — this task's
  classification happens in `DevicesController`, before that use case's
  own unrelated evaluation is even reached for a device classified as a
  pending enrollment.
- Does **not** touch `E12-T03`'s side (the new device's own waiting
  screen) — this task is the existing/trusted device's screen only.
- Does **not** change what a normal `Unknown`/`Verify` row looks like or
  does for an actual stranger peer — only devices classified as "my own
  account's device, no relationship yet" get the new treatment.

## 5. Contract

### Functions
```yaml
- signature: "DevicesController._classifyDiscoveredDevice(deviceId: String) -> _DeviceClassification"
  params: { deviceId: "a newly-discovered peer's device id" }
  returns: "a new internal enum/class distinguishing pendingEnrollment from the existing unknown/known handling -- exact shape is this task's own implementation choice, verify DevicesController's existing structure before naming it"
  purpose: "the one new decision point this task adds before the existing evaluation logic runs"
```

### UI
- **Design contract:** `design/screens/device-enrollment-approval.md`
- Route: none — a row on the existing `/devices` route.
- States required: the contract's own single `pending` state, rendered
  per discovered device classified as a pending enrollment; absent
  otherwise (no empty/loading/error state of its own — this row simply
  doesn't render when there is no pending request).
- Gate: `make design-verify SCREEN=devices` must stay green — this row is
  NOT part of `devices.md`'s own measured contract (design-fidelity's own
  documented shape for a derived addition to a measured screen); expect
  it to be invisible to that gate, exactly as `dashboard.md`'s
  `warning-expanded` derived state documents for itself. Read the
  collapsed/base screen against `devices.md`'s generated table as usual.

## 6. Risks
- `readOwnDeviceIds` is best-effort and can return an empty/incomplete
  set on a flaky connection — a real enrolling device might briefly NOT
  be classified as one and fall through to the ordinary unknown-peer
  treatment. This is an acceptable degraded case (task §2's own framing:
  `FR-RECOVER-001` says "where possible"), not a bug to engineer around
  with retries/polling loops in this task.
- Caching `readOwnDeviceIds`'s result per session risks staleness if a
  device is added to the account mid-session — acceptable for the same
  "where possible" reason; do not add a refresh timer (`E10`'s one-tick
  discipline — no new polling driver for a best-effort hint).
- Read `E06-B01` before laying out the new row — a trailing
  button-pair-after-a-name is exactly the `RenderFlex` overflow shape
  that bug fixed elsewhere in this codebase; the name must stay the
  flexible/ellipsis child, the button pair fixed-width.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-RECOVER-5**: WHEN a discovered device id is present in this
  account's own device list AND has no local relationship entry, THE
  system SHALL classify it as a pending enrollment request rather than an
  unknown peer. (FR-RECOVER-001)
- **EARS-RECOVER-6**: WHEN a discovered device id is NOT in this
  account's own device list, THE system SHALL classify it exactly as
  before this task (unchanged unknown-peer treatment). (FR-RECOVER-001)
- **EARS-RECOVER-7**: WHEN the pending-enrollment row's `Approve` is
  tapped, THE system SHALL call the existing `verify(deviceId)` path;
  `Deny` SHALL call the existing `block(deviceId)` path. (FR-RECOVER-001)

### Tests

- `test_EARS_RECOVER_6_foreign_device_id_unaffected`

### Manual
1. Sign in on a second physical/emulated device with the same test
   account, keep it discoverable → confirm the first device's Devices
   screen shows the pending-enrollment row, not an `Unknown` row.
2. Tap `Approve` → confirm the row disappears and the device appears as a
   normal trusted row.
