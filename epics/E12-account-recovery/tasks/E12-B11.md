# E12-B11 · the account's own devices no longer sync ordinary trust decisions with each other

## The defect

`RelationshipSyncService.push`/`pull` were built (E11-T05) to let an
account's own devices propagate ordinary peer-relationship decisions
(trusted/blocked/etc.) to each other via `users/$uid/relationships/*`. `push`
had no production caller even before this epic (`E12-B02`'s original
finding). `E12-B03`'s fix — correctly, per the human-decided dedicated
enrollment-grant channel — removed `DeviceEnrollmentController`'s call to
`pull`, which was `RelationshipSyncService`'s only remaining production
caller.

`FR-TRUST-007` ("the account's own devices SHALL agree on relationship
state") is named in both `E12-B02.md`'s and `E12-B03.md`'s own `traces_to`,
and now has no production wiring anywhere satisfying it.

## Why this is not a defect in either fix
The human decision for `E12-B03` explicitly chose a dedicated channel over
reusing `relationships/*` for enrollment approval — correctly, since running
an authorization grant through a restrictive-wins conflict resolver was the
root cause of `E12-B03`'s bug. Removing `pull`'s only caller was the correct
consequence of that decision, not a new mistake. This bug exists to make
sure `FR-TRUST-007`'s now-total lack of wiring isn't silently forgotten.

## Severity

**S3** — no regression (this capability was never fully wired before this
epic either — `push` never had a caller), but a named FR is now completely
unimplemented and undiscoverable without this bug file.

## Suggested direction (not binding, planner call)
- Wire `push`/`pull` into a real multi-device-sync trigger for ordinary
  peer-relationship changes (a genuinely new feature, not this epic's
  scope), or
- Formally descope `FR-TRUST-007` if multi-device relationship sync is not
  actually needed given how thin this app's multi-device model is elsewhere
  (per `ADR-0005`, device identity/session is already independent per
  device) — a spec decision, not a coding one.

## The decision (human, 2026-09-06) — direction 2

The human took the second of the two directions above: **formally descope
`FR-TRUST-007` and delete the dead code.** Recorded in full, with the blast
radius walk, as `docs/impact/IMP-002-descope-fr-trust-007.md`.

Reasoning, in short: `ADR-0005` already makes device identity and session
state independent per device, and each device evaluates authorization for
itself (`FR-TRUST-003`/`FR-TRUST-005`) — no product behaviour depends on an
account's own devices agreeing on peer-relationship state. The one case that
genuinely needed a device-to-device signal was enrollment approval, and
`E12-B03` moved that onto a dedicated grant channel. `push` never had a
production caller; `pull`'s last one went with `E12-B03`'s correct fix.

**Nothing supersedes `FR-TRUST-007`.** The id and its text are retained in
`spec/srs.md`, marked ⛔ DESCOPED (tasks trace to it, so it is never deleted).
Reviving own-account relationship sync needs a new FR id and a fresh human
decision.

## What this fix does NOT do
- Does NOT touch the enrollment-grant channel (`E12-B02`/`E12-B03`) at all.
- Does NOT touch `ConflictResolver.resolveTrust` or `FR-MSG-007` — the
  restrictive-wins rule is untouched and still covered by
  `test/features/messaging/domain/conflict_resolver_test.dart`.
- Does NOT delete `FR-TRUST-007` or `EARS-FB-14`/`EARS-FB-15` — they are
  **marked** descoped/retired, never removed, because `E11-T05`, `E12-B02`,
  `E12-B03`, `E12-B09` and `E12-B10` all trace to them.
- Does NOT edit `E11-T05`'s contract — that task file is the historical
  record of correct work against the spec as it then stood. A `## Descoped
  after completion` note is appended at its end, changing no frontmatter or
  contract field.
- Does NOT remove the `relationships` node from `database.rules.json`, nor
  `EARS-FB-16`, nor `FirebasePaths.relationship`/`relationships`, nor
  `FirebaseNodeKind.relationship`. Removing a **deployed security rule** is an
  operational change, not a code cleanup, and is a rule-3 call the 2026-09-06
  decision does not cover. Each is marked in place as unused with a pointer to
  `IMP-002`, and carried as `IMP-002` follow-up 2.
- Does NOT re-point `E12-B10`'s `traces_to:` (its only trace is now a
  descoped id). Retargeting another open bug's contract is outside this
  fence — carried as `IMP-002` follow-up 1, owned by the planner at that
  bug's dispatch.
- Does NOT fix the one pre-existing `annotate_overrides` analyzer info in
