# E12-B11 · the account's own devices no longer sync ordinary trust decisions with each other

## The defect

`RelationshipSyncService.push`/`pull` were built (E11-T05) to let an
account's own devices propagate ordinary peer-relationship decisions
(trusted/blocked/etc.) to each other via `users/$uid/relationships/*`. `push`
had no production caller even before this epic (`E12-B02`'s original
finding). `E12-B03`'s fix — correctly, per the human-decided dedicated
enrollment-grant channel — removed `DeviceEnrollmentController`'s call to
`pull`, which was `RelationshipSyncService`'s only remaining production
caller.

`FR-TRUST-007` ("the account's own devices SHALL agree on relationship
state") is named in both `E12-B02.md`'s and `E12-B03.md`'s own `traces_to`,
and now has no production wiring anywhere satisfying it.

## Why this is not a defect in either fix
The human decision for `E12-B03` explicitly chose a dedicated channel over
reusing `relationships/*` for enrollment approval — correctly, since running
an authorization grant through a restrictive-wins conflict resolver was the
root cause of `E12-B03`'s bug. Removing `pull`'s only caller was the correct
consequence of that decision, not a new mistake. This bug exists to make
sure `FR-TRUST-007`'s now-total lack of wiring isn't silently forgotten.

## Severity

**S3** — no regression (this capability was never fully wired before this
epic either — `push` never had a caller), but a named FR is now completely
unimplemented and undiscoverable without this bug file.

## Suggested direction (not binding, planner call)
- Wire `push`/`pull` into a real multi-device-sync trigger for ordinary
  peer-relationship changes (a genuinely new feature, not this epic's
  scope), or
- Formally descope `FR-TRUST-007` if multi-device relationship sync is not
  actually needed given how thin this app's multi-device model is elsewhere
  (per `ADR-0005`, device identity/session is already independent per
  device) — a spec decision, not a coding one.

## What this fix does NOT do
- Does NOT touch the enrollment-grant channel (`E12-B02`/`E12-B03`) at all.
- Does NOT delete `RelationshipSyncService` unilaterally — that is a
  separate call once the direction above is decided.
