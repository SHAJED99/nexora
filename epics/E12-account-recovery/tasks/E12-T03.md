# E12-T03 · New-device enrollment waiting screen, login-flow gate, and the "no recovery" notice

## 1. Goal
Close `FR-RECOVER-001`'s new-device half and `FR-RECOVER-002`'s "no
recovery" disclosure — the new device's own journey between signing in
and reaching the dashboard.

## 2. Business logic
`FR-RECOVER-001`, `FR-RECOVER-002`. `LoginController._signIn()`
(`login_controller.dart`) today unconditionally calls
`Get.offNamed('/dashboard')` once `SignInUseCase` completes — no branch
point exists. This task inserts one: after sign-in, call `E12-T01`'s
`readOwnDeviceIds(uid)`; if it returns any device id OTHER than the one
just created, route to `/device-enrollment` instead of `/dashboard` (this
account has other devices, so enrollment vouching is at least possible);
otherwise this genuinely is the first device on the account and the
existing unconditional `/dashboard` redirect is correct and unchanged.

`/device-enrollment` (`design/screens/device-enrollment.md`) then
attempts to detect approval by calling
`RelationshipSyncService.pull(uid)` (E11-T05) and checking whether THIS
device's own local relationship (`RelationshipRepository.get(thisDeviceId)`)
has become `trusted`/`allowed` — `pull` already reads
`users/$uid/relationships/*` for the whole account, which structurally
includes whatever a trusted device's `push(uid, thisDeviceId, ...)`
(`E12-T02`) already wrote; no new Firebase mechanism, only a new local
consumer of one that already exists.

## 3. What this task does
- `LoginController._signIn()` gains the branch described above, calling
  `E12-T01`'s reader before the existing `Get.offNamed` line.
- A new route, `/device-enrollment` (`lib/app/routes.dart`), and a new
  `DeviceEnrollmentController`/`DeviceEnrollmentView` implementing
  `design/screens/device-enrollment.md`'s three states (`waiting`,
  `denied`, `no-recovery-notice`) — GetX MVC, matching every other
  feature's structure (`ADR-0002`).
- `waiting`: polls (or listens to, if `RelationshipSyncService` exposes a
  stream — verify at execution time; if not, a single bounded-interval
  poll loop is acceptable, mirroring how a first-run/no-history case is
  handled elsewhere, but must stop polling once resolved or the screen is
  left) for this device's own relationship state to become
  trusted/allowed; on success, navigates to `/dashboard` (no new screen —
  falls through to the existing redirect, per the contract's own note).
  "Continue without history" is reachable from the first frame, never
  gated behind the poll/timeout.
- `denied`/timeout: the contract's own restated state, same single
  button.
- `no-recovery-notice`: reached from "Continue without history" (either
  prior state); states `FR-RECOVER-002`'s property per the contract's own
  copy; "Continue" proceeds to `/dashboard`.

## 4. What this task does NOT do
- Does **not** change `SignInUseCase`, `FirebaseMetadataService`, or
  anything about how the FIRST device on an account signs in — the
  branch this task adds only fires when other device ids already exist.
- Does **not** implement `E12-T02`'s side (the existing device's approval
  UI) — this task only consumes what that task's `push` already writes,
  via the pre-existing `pull` mechanism. `E12-T02`/`E12-T03` may build in
  either order or in parallel (disjoint files, no `depends_on` between
  them — both depend only on `E12-T01`).
- Does **not** add a new Firebase path, rule, or service method beyond
  `E12-T01`'s reader — `RelationshipSyncService.pull` already does
  everything this task's detection needs.
- Does **not** change `RelationshipRepository`, `RelationshipSyncService`,
  or `ConflictResolver` — read-only consumers of all three.
- Does **not** add a "resend"/"retry enrollment" affordance beyond
  routing back through the same waiting state — `denied`'s own button is
  the retry path (re-enters `waiting`), no separate mechanism.

  params: {}

### UI
- **Design contract:** `design/screens/device-enrollment.md`
- Route: `/device-enrollment` · navigation from `/login`'s own sign-in

- States required: `waiting`, `denied`, `no-recovery-notice` (per the

## 6. Risks
- Polling `RelationshipSyncService.pull` too frequently is a new
  driver this codebase's one-tick discipline (`E08-T06`/`E10-T08`)
  explicitly guards against — pick a bounded interval (a handful of
  seconds, not sub-second) and stop entirely once resolved or the screen
  is disposed; do not leave a `Timer.periodic` running past this
  controller's own lifecycle.
- `readOwnDeviceIds`'s best-effort nature (task §6 of `E12-T01`) means a
  genuinely-first device could, on a bad connection, wrongly see a stale
  cached id and route to `/device-enrollment` unnecessarily — acceptable
  degraded behavior (the "Continue without history" button is always
  one tap away), not a case to special-case around.

  practice, `verify.mjs`/`extract.mjs` both filter on
  `design/sources.yaml`'s `screens:` list (`design/tools/verify.mjs`:
