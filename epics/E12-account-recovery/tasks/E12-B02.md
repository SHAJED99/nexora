# E12-B02 · the approval is recorded locally and never mirrored

## The defect

`E12-T02` §2 states, as established fact:

> Approving or denying reuses `DevicesController`'s OWN EXISTING methods —
> `verify(deviceId)` (promotes to trusted/allowed, **already wired to
> `RelationshipRepository.upsert` via `RelationshipSyncService.push`**)

**That premise is false.** `verify()` calls the repository directly:

```dart
// lib/features/devices/presentation/devices_controller.dart:150
Future<void> verify(String deviceId) async {
  await _repository.upsert(deviceId, RelationshipState.allowed);
  pendingEnrollments.removeWhere((d) => d.id == deviceId);
  await load();
}
```

There is no `RelationshipSyncService` in that file, and grepping the whole
production tree, `RelationshipSyncService` is **constructed in exactly one
place in `lib/`** — `DeviceEnrollmentController` (the *reading* side,
E12-T03). `push(...)` has **no production caller at all**; it has been dead
code since E11-T05 shipped it behind an explicit "does NOT decide when to
call push/pull" scope fence.

So a trusted device's "Approve" tap writes one local Drift row and stops.
`users/$uid/relationships/$newDeviceId` is never written, and the enrolling
device — which polls exactly that subtree — has nothing to find.

The builder was correct to ship this: T02 §4 forbids adding "any new
trust-recording mechanism". The defect is in the task contract's false
premise, not the implementation. That makes this a **sharding defect worth a
retro lesson** (`skills/retro`) as well as a fix.

## Repro

1. Device A (trusted, signed in). Device B signs in on the same account.
2. On A: open Devices, tap Discover, see B as "Awaiting your approval", tap **Approve**.
3. Inspect `users/$uid/relationships` in the Realtime Database.

Reviewer probe composing the real `DevicesController` and the real
`DeviceEnrollmentController` over one shared relationships subtree:

```
PROBE store after verify(): {}
PROBE new device sees approval: false
```

(Local trust on A was correctly recorded — `repoA.get(newDeviceId).state == allowed`.)

## Expected

`EARS-RECOVER-1` / `EARS-RECOVER-7`: approving on the trusted device makes the
approval visible to the enrolling device. `FR-TRUST-007` also requires the
account's own devices to agree on relationship state.

## Actual

Nothing leaves device A. The enrolling device polls to timeout and shows
`denied`.

## Severity

**S1** — the epic's headline requirement (`FR-RECOVER-001`, "an existing
trusted device SHALL authorize a new device's enrollment") is non-functional
in the running app, with both task suites green.

## Note

Fixing this alone is **not sufficient**: `E12-B03` shows the read side
discards the approval even when the node is present. Both must land before
the journey works. Filed separately because they are two defects in two
files with two distinct regression tests.

## What this fix does NOT do

- Does **not** change `RelationshipSyncService.push`'s own implementation or
  its Firebase path — it is correct and already tested; it simply has no caller.
- Does **not** change `_classifyDiscoveredDevice` or the pending-enrollment
  row rendering in `devices_view.dart`.
- Does **not** change `ConflictResolver` (that is `E12-B03`'s territory).
- Does **not** add notifications for a pending request (GAP-028, still deferred).
