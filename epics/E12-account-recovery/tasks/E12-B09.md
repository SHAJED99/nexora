# E12-B09 · an enrollment grant outlives the trust decision that created it

## The defect

`DeviceEnrollmentController.checkApproval()` reads
`users/$uid/device_enrollment_grants/$newDeviceId` directly and nothing ever
deletes that node. Reviewer's own probe: approve `dev-X`, then call
`block('dev-X')` on the approving device (the same handler `Deny` uses) —
the enrolling device's `checkApproval()` still returns `true` and the grant
node is still present.

Under the previous (broken) design, at least `blocked` propagated through
`ConflictResolver` because everything shared one channel. The new dedicated
channel is correct for the *approval* case (that was the whole point of
`E12-B03`), but nothing revokes a grant when the approving device later
changes its mind, or when `E11-T04`'s own device-revocation mechanism fires
for that device id.

## Repro

1. Device A approves device B's enrollment (`device_enrollment_grants/B`
   written).
2. Device B has not yet polled/completed enrollment.
3. Device A blocks/denies device B, or B is revoked via
   `users/$uid/devices/B/revocation`.
4. Device B's `checkApproval()` still reads the stale grant and proceeds.

## Expected

A later block/deny/revocation of the same device id should make a pending
or already-consumed enrollment grant for that device ineffective.

## Actual

The grant is permanent; nothing observes revocation events.

## Severity

**S3** — narrows to the window between grant and the enrolling device's
next successful poll, and this journey gate does not touch cryptographic
identity/session material (Signal Protocol keys are unaffected regardless).
Not blocking `E12`'s own merge, but a real gap worth closing before this is
considered feature-complete.

## Suggested direction (not binding)

Either (a) delete the grant node when `verify()`'s sibling `block()`/`deny()`
handlers fire for the same device id, or (b) have `checkApproval()` also
check the current `relationships/$deviceId` state is not `blocked` before
trusting the grant (cheap, reuses existing data, does not require deleting
anything). Do not resurrect `ConflictResolver`/`pull()` for this — that was
the source of `E12-B03`'s original bug.

## What this fix does NOT do
- Does NOT change the grant's write path (`E12-B02`) or its schema.
- Does NOT reintroduce merging the grant read through `ConflictResolver`.
