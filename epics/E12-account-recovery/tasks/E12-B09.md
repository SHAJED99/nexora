# E12-B09 · an enrollment grant outlives the trust decision that created it

## The defect

`DeviceEnrollmentController.checkApproval()` reads
`users/$uid/device_enrollment_grants/$newDeviceId` directly and nothing ever
deletes that node. Reviewer's own probe: approve `dev-X`, then call
`block('dev-X')` on the approving device (the same handler `Deny` uses) —
the enrolling device's `checkApproval()` still returns `true` and the grant
node is still present.

Under the previous (broken) design, at least `blocked` propagated through
`ConflictResolver` because everything shared one channel. The new dedicated
channel is correct for the *approval* case (that was the whole point of
`E12-B03`), but nothing revokes a grant when the approving device later
changes its mind, or when `E11-T04`'s own device-revocation mechanism fires
for that device id.

## Repro

1. Device A approves device B's enrollment (`device_enrollment_grants/B`
   written).
2. Device B has not yet polled/completed enrollment.
3. Device A blocks/denies device B, or B is revoked via
   `users/$uid/devices/B/revocation`.
4. Device B's `checkApproval()` still reads the stale grant and proceeds.

## Expected

A later block/deny/revocation of the same device id should make a pending
or already-consumed enrollment grant for that device ineffective.

## Actual

The grant is permanent; nothing observes revocation events.

## Severity

**S3** — narrows to the window between grant and the enrolling device's
next successful poll, and this journey gate does not touch cryptographic
identity/session material (Signal Protocol keys are unaffected regardless).
Not blocking `E12`'s own merge, but a real gap worth closing before this is
considered feature-complete.

## Suggested direction (not binding)

Either (a) delete the grant node when `verify()`'s sibling `block()`/`deny()`
handlers fire for the same device id, or (b) have `checkApproval()` also
check the current `relationships/$deviceId` state is not `blocked` before
trusting the grant (cheap, reuses existing data, does not require deleting
anything). Do not resurrect `ConflictResolver`/`pull()` for this — that was
the source of `E12-B03`'s original bug.

## What this fix does NOT do
- Does NOT change the grant's write path (`E12-B02`) or its schema.
- Does NOT reintroduce merging the grant read through `ConflictResolver`.

## Run log
- 2026-09-06 — Investigated the suggested direction (b) ("check
  `relationships/$deviceId` state is not blocked") against the actual state
  of the codebase and found its premise does not hold: `block()`
  (`BlockUseCase.call`) only ever writes `RelationshipState.blocked` to the
  LOCAL Drift repository — `RelationshipSyncService.push`, the only thing
  that could mirror that to `users/$uid/relationships/$deviceId`, still has
  zero production callers (confirmed by grep across `lib/`), exactly as
  `E12-B02`'s own finding described for `verify()` before its fix. Checking
  a Firebase path nothing ever writes would be a vacuous check, not "cheap,
  reuses existing data" as the suggested direction assumed. Implemented
  option (a) instead for the block/deny case: `DevicesController.block()`
  now also deletes the grant node
  (`FirebaseMetadataService.deleteEnrollmentGrant`, new method mirroring the
  existing `writeEnrollmentGrant`'s exact best-effort/timeout/catch-log
  shape, a `.remove()` at the unchanged `FirebasePaths
  .deviceEnrollmentGrant` path — no rules.json change needed, since RTDB's
  `.write` rule at the `$uid` ancestor already governs a removal the same
  as a set). Deliberately unconditional on `pendingEnrollments` membership:
  by the time a previously-approved device is later blocked, `verify()` has
  already cleared that tracking (EARS-RECOVER-7), so gating on it the way
  `verify()`'s own `wasPendingEnrollment` does would silently miss exactly
  the repro's own timing. A delete for a deviceId with no grant at all (the
  common "Block" of an ordinary stranger) is a harmless no-op.
  For the device-revocation case (`E11-T04`'s own mechanism, a genuinely
  separate trigger from block/deny — it never calls `DevicesController
  .block()`), found the opposite: zero new plumbing needed at all.
  `DeviceRevocationService.revoke` already writes a `revocation` child
  under the SAME `users/$uid/devices/$deviceId` node
  `FirebaseMetadataService.readDeviceMetadata` already reads whole. Added
  `isDeviceRevoked` as a thin wrapper reusing that existing read (mirrors
  `DeviceRevocationService._extractRevocationFlags`'s own extraction
  shape) and wired it into `checkApproval()` as a second, independent
  condition after the existing grant read. Neither addition touches
  `relationships/*`, `RelationshipSyncService`, or `ConflictResolver` at
  all — both checks stay squarely inside `E12-B03`'s "a dedicated node,
  read directly" precedent, just adding a second dedicated read for the
  revocation case and a delete for the block/deny case.
