# E12-B01 · a returning user can never reach their own dashboard

## The defect

`LoginController._signIn()` mints a **brand-new random device id on every
single launch**:

```dart
// lib/features/login/presentation/login_controller.dart:113
final deviceId = generateSecureDeviceId();
```

`SignInUseCase.call` then registers that fresh id under the account's own
Firebase device registry (`sign_in_use_case.dart:50`,
`registerDevice(accountUid, deviceId)`), which is additive — ids accumulate,
one per launch.

E12-T03's new gate then asks whether any *other* id exists:

```dart
// lib/features/login/presentation/login_controller.dart:136
routeToEnrollment = otherDeviceIds.any((id) => id != deviceId);
```

On the **second and every subsequent launch of the same physical device**,
the registry already holds the previous launch's id, so `any((id) => id !=
deviceId)` is unconditionally `true` and the user is sent to
`/device-enrollment` — a screen that tells them to go approve this device
from another device they may not own.

## Repro

1. Fresh install. Launch the app, sign in with Google. → reaches `/dashboard`. ✅
2. Close the app. Launch it again, on the **same device, same account**.
3. Observe: the app lands on `/device-enrollment` ("Waiting for approval…").

Reviewer probe (composed the real `LoginController` against a registry that
accumulates ids the way `registerDevice` does), output:

```
launch 1 -> [/dashboard]        registry=1
launch 2 -> [/device-enrollment] registry=2
```

## Expected

`EARS-RECOVER-9` gates enrollment on *another* device existing. A user's own
single device relaunching is not another device — it must reach `/dashboard`,
which is the unchanged pre-E12 behaviour (`FR-AUTH-001`).

## Actual

Every launch after the first routes to `/device-enrollment`. Because
`E12-B02`/`E12-B03` make approval unreachable, the screen then polls for
8 × 4s ≈ 32s and settles on `denied`, and the only way out is
"Continue without history" — which is a lie: the history is still on this
device, locally, untouched.

## Severity

**S1** — total blocker on the primary launch path for every returning user,
and it degrades into a false "your history is gone" message.

## Overlap with E13-T07 — do not fix both sides independently

`E13-T07` (P1, mid-fix, branch `docs_e13_t07_and_progress`) is addressing the
same root cause from the other end — sign-in minting a new identity per launch
instead of reusing the existing one, which was independently found to cause
rate-limit lockouts. Its `files:` fence lists
`lib/features/login/domain/sign_in_use_case.dart` and `lib/app/bindings.dart`
but **not** `lib/features/login/presentation/login_controller.dart`, where
`generateSecureDeviceId()` is actually called (line 113).

If T07 makes sign-in reuse a stable device id, this bug is resolved as a side
effect and the fix here reduces to a regression test. **Sequence T07 first**,
then re-verify this repro. Do not patch `login_controller.dart:113`
independently while T07 is in flight — two fixes to the same identity-minting
path will conflict.

## What this fix does NOT do

- Does **not** change `E12-T03`'s enrollment-gate *condition* itself
  (`otherDeviceIds.any(...)`) — the condition is correct; its input is wrong.
- Does **not** fix the approval propagation break (`E12-B02`/`E12-B03`) — a
  genuinely-new device still cannot be approved after this fix.
- Does **not** touch `DeviceEnrollmentController` or the enrollment view.
- Does **not** change `readOwnDeviceIds` or `registerDevice`.
