# E12-B08 · two small defects in the new login branch

Filed together: same method, same file, same one-line shape, both S4.

## Defect 1 (tracker C5) — a new way for sign-in to fail

```dart
// lib/features/login/presentation/login_controller.dart:123-124
final deviceIdentityRepository = _resolveDeviceIdentityRepository();
final identity = await deviceIdentityRepository?.latestDeviceIdentity();
```

This read sits **inside** `_signIn()`'s `try`. If `latestDeviceIdentity()`
throws — a Drift error, a corrupt row, disk pressure — it falls into the outer
`catch` and is reported to the user as a mapped **sign-in failure**, even
though sign-in fully succeeded and the local identity was already written.
Before E12-T03, no such read existed on this path and the flow went straight
to `/dashboard`.

Narrow: it is a local read immediately after the successful local write that
produced the very row being read. But it converts a succeeded sign-in into a
visible failure, which is the wrong direction for a best-effort hint. Every
other collaborator in this feature (`readOwnDeviceIds`, `pull`,
`_resolveDeviceIdentityRepository`) is explicitly best-effort; this one read
is not.

**Fix:** wrap the identity read (and the `readOwnDeviceIds` call it feeds) in
its own try/catch that logs and falls through to `/dashboard` — the same
degraded case the task's own §6 Risks already sanctions for an unresolvable
repository.

## Defect 2 (tracker F1) — the one unlogged catch

```dart
// lib/features/login/presentation/login_controller.dart:97-101
try {
  return Get.find<DeviceIdentityRepository>();
} catch (_) {
  return null;
}
```

This is the **only** best-effort failure path in the whole feature that does
not log via `ObservabilityService`. Every sibling does —
`readOwnDeviceIds` (`firebase.read_own_device_ids_failed`), `pull`
(`firebase.relationship_sync_pull_failed`), `push`
(`firebase.relationship_sync_push_failed`), and `_signIn`'s own outer catch.

Consequence: in production, a genuine DI misconfiguration is
**indistinguishable from a legitimate first-device case**, and emits no
telemetry at all. Given `E12-B01` shows this branch already misroutes users,
the absence of any signal here directly slowed diagnosis.

**Fix:** one line —
`ObservabilityService.instance.logError('recovery.device_identity_repository_unresolved', cause: e)`
(and `catch (e)` instead of `catch (_)`).

## Repro

Both are read-and-reason findings on an error path; neither has a natural user
repro. Defect 1 is provable by injecting a `DeviceIdentityRepository` whose
`latestDeviceIdentity()` throws and asserting the controller lands on an error
state rather than `/dashboard`. Defect 2 is provable by asserting a log call
with an unregistered repository.

## Severity

**S4** for both — narrow error paths, no happy-path impact.
