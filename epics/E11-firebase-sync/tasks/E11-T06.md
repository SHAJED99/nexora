# E11-T06 · Public device directory

## 1. Goal
Build exactly what `ADR-0008` (option 2, accepted 2026-09-04) authorised: a
`directory/$deviceId` node that publishes a device's public identity key,
current prekey bundle and revocation flag, readable by any authenticated
account **only if it already knows the exact device id** — no listing, no
enumeration. This is the mechanism, not the consumer: it does not by
itself fix the TOFU gap in `E07` or give `E06-T07` its fallback, it makes
both fixable.

## 2. Business logic
- **`ADR-0008` is binding, not advisory, for this task.** Read it in full
  before writing rules. The two properties that make option 2 acceptable
  are both structural, and both are this task's job to prove:
  (a) a read at `directory` (the parent) must be denied — only a read at
  `directory/$deviceId` (an exact, known id) may succeed; (b) nothing
  published here is anything other than public-by-construction material
  (a public key, a public prekey bundle, a boolean-shaped revocation
  timestamp) — never a private key, never session state, never anything
  `ADR-0005` reserves to local storage.
- **What gets published, and where it comes from:**
  - `identityPublicKey` — `IdentityService`'s own identity key pair holds
    this; only the **public** half ever leaves the device. Never call
    anything that returns the private key.
  - `prekeyBundle` — `PrekeyBundleCodec.serialize(IdentityService.
    getLocalPreKeyBundle())`, base64-encoded for the RTDB string field.
    Reuses `E06-T07`'s wire codec verbatim; does not re-derive the format.
  - `revokedAt` — read from `E11-T04`'s local revocation table
    (`isRevoked`/the underlying row's timestamp), *this device's own*
    revocation status as recorded on this account. `null`/absent when not
    revoked.
- **Publish is triggered by rotation, not polled.** Whenever
  `IdentityService` rotates the signed prekey or replenishes one-time
  prekeys (`ensureSignedPreKey`, `replenishOneTimePreKeys`), and whenever
  `DeviceRevocationService.revoke` runs, the directory entry is
  republished. This task adds the publish call at those existing call
  sites; it does not change what those functions do.
- **Lookup is exact-id, single-shot.** `lookupDevice(deviceId)` returns the
  entry for one named id or `null` if absent — never a list, never a
  query, never a "nearby devices" or "all known devices" read. That
  distinction is not a style preference; it is the entire privacy argument
  `ADR-0008` makes for option 2, and it must be provably true of the rules
  file, not just the client code.

## 3. What this task does
- Adds `directory/$deviceId` to the Firebase schema — path in
  `firebase_paths.dart`, allowed-field set (`identityPublicKey:String`,
  `prekeyBundle:String`, `revokedAt:int?`, `ownerUid:String`) in
  `firebase_boundary.dart`, and the row in `docs/firebase-schema.md`
  (status `live`, superseding its `not-decided` placeholder from
  `E11-T01`).
- Adds `.validate`/`.read`/`.write` rules to `database.rules.json`:
  - `.write` — only the authenticated account matching the stored
    `ownerUid` (or, on first publish, the authenticated caller writing
    their own uid into `ownerUid`) may write `directory/$deviceId`.
  - `.read` at `directory/$deviceId` — any authenticated user.
  - `.read`/`.write`/`.indexOn` at the `directory` parent node — **absent**,
    which under RTDB's default-deny means no listing is possible; the
    rules test must assert this by attempting a parent-level read and
    expecting denial, not by inspecting the rules JSON for absence.
- Adds `DeviceDirectoryService`:
  - `publish(uid, deviceId)` — assembles the three fields from
    `IdentityService`/`PrekeyBundleCodec`/`E11-T04`'s revocation query and
    writes `directory/$deviceId`; best-effort, never throws to its caller.
  - `lookupDevice(deviceId)` — reads `directory/$deviceId` by exact id,
    decodes `prekeyBundle` back through `PrekeyBundleCodec.deserialize`,
    returns a typed result or `null`.
- Wires `publish` into `IdentityService.ensureSignedPreKey`,
  `IdentityService.replenishOneTimePreKeys` and
  `DeviceRevocationService.revoke` (the three existing events that change
  what should be published) — additive calls only, no change to those
  functions' own return values or error behaviour.
- Extends `firebase_rules_test.dart`: exact-id read succeeds for any
  authenticated user; parent-level (`directory`) read is denied; write by a
  non-owning uid is denied.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT change `DriftSignalProtocolStore.isTrustedIdentity` or
  anything in `E07`.** This task publishes and exposes a lookup; consuming
  it to close the TOFU gap is `E07`'s own file, outside this fence
  (`ADR-0008` Consequences names this explicitly).
- **Does NOT wire `lookupDevice` into `PrekeyExchange` or any E06 file.**
  Same shape: this task is the publisher, not the consumer. `E06-T07`'s
  Firebase fallback, if built, is E06's own task.
- **Does NOT publish a private key, a session key, or any Signal session
  state.** Only `IdentityService`'s public-key accessors and
  `PreKeyBundle`'s own public-material getters (the same set
  `PrekeyBundleCodec` already restricts itself to) may be called.
- **Does NOT add polling, a background sync, or a scheduled republish.**
  Publish is event-triggered only (§2); no new `Timer`, no second driver
  (same one-tick invariant `E08-T06`/`E10-T08` already established).
- **Does NOT implement `relationships/$peerDeviceId`** — that is `E11-T05`,
  a same-account node with different data and different rules.
- **Does NOT add a UI or settings screen.**
- **Does NOT change `PrekeyBundleCodec`'s wire format or version.**

## 5. Contract

### Data — the Realtime Database node
| Path | Fields | Read | Write |
|---|---|---|---|
| `directory/$deviceId` | `identityPublicKey:String` (base64), `prekeyBundle:String` (base64, `PrekeyBundleCodec` v1), `revokedAt:int?`, `ownerUid:String` | any authenticated user, **exact id only** | only the account matching `ownerUid` |
| `directory` (parent) | — | denied to everyone (no rule granted; RTDB default-deny) | denied to everyone |


## 6. Risks
- **The single highest-value thing a reviewer must verify by hand**: attempt
  a read at `directory` (no child segment) against the deployed rules and
  confirm denial. A rules file that accidentally grants `.read` one level
  too high turns "look up one device" into "list every device this project
  has ever seen" — the exact failure mode `ADR-0008` spent its whole
  Options section ruling out.
- `ownerUid` must be set exactly once, at first publish, and never
  overwritten by a later `publish` call from a different (compromised or
  buggy) caller — otherwise the write-ownership rule can be defeated by
  whoever publishes first winning a race that should not be a race. Write
  the rule so `ownerUid` is immutable after first write (`!data.exists() ||
  data.child('ownerUid').val() === newData.child('ownerUid').val()` or
  equivalent), and test it.
- `prekeyBundle` staleness: this task republishes on rotation events, but a
  bundle read by a peer between rotations could be one that has since had
  its one-time prekey consumed elsewhere. `E06-T07`'s existing
  `bundleUnavailable` handling already exists for the "no bundle" case;
  this task does not need to solve "stale bundle" beyond documenting it as
  a known limitation in Run log.

**How the parent-level `directory` read denial was verified, by hand, not
just by a passing test:** RTDB's actual server-side read algorithm walks a
requested path from the root down to (and including) the target node,
OR-ing every `.read` rule it finds on the way — a grant at any level makes
the read succeed for that node and everything below it; a rule *below* the
requested path is never consulted, and a grant never flows back up to an
ancestor. I read `database.rules.json` top to bottom with exactly that
algorithm in mind, once for each path a caller could request:
- **Root** (`rules`): no bare `.read` key. The only rules at this level are
  `.read`/`.write` nested one level down, under `users`, `directory`, and
  `$other` — none of those is evaluated for a request that stops at the
  root itself.
- **`directory`** (the parent, no child segment): I opened the `directory`
  object in `database.rules.json` and confirmed by eye that it contains
  exactly one key, `$deviceId` — no `.read`, no `.write`, no `.validate` at
  this level. Since neither the root nor `directory` itself carries a
  `.read`, and the algorithm never looks past the requested path (i.e.
  never descends into `$deviceId` to find its `.read` and apply it
  upward), a request for `directory` with no child segment is denied by
  RTDB's default deny — not because some `.validate: false`/`$other` deny
  rule fires (there is none needed here), but because **no rule anywhere
  from root to `directory` ever says `true`.**
- **`directory/$deviceId`**: one level deeper, `.read: "auth != null"` is
  present. Any authenticated caller's request that names an exact
  `$deviceId` reaches this rule and is granted.

I did not stop at reading the JSON, because task §3 is explicit that an
absence-check is not sufficient evidence: `firebase_rules_test.dart` now
contains `_cascadingReadGranted`, a small function that mechanically
executes the same walk I just did by hand (root → each path segment,
checking `.read` at every step, matching a `$`-prefixed wildcard child when
the concrete segment isn't found), rather than checking whether a `.read`
key is merely absent at one specific node. Two tests exercise it against
the actual parsed `database.rules.json`: one asserts the walk to `directory`
returns `false`, the other asserts the same walk one segment deeper (to
`directory/<any-id>`) returns `true` — proving the denial above is caused
by an absent grant, not by the helper itself being unable to reach that
part of the tree (a helper that always returned `false` would make the
first assertion pass for the wrong reason; the second assertion rules that
out). This is still not a live Firebase-emulator read (`OQ-E11-T02-1`,
unresolved — see Deviations), but it is a real execution of RTDB's
documented cascade semantics against this file's actual JSON, not a
structural absence check.

3. **`DeviceRevocationService.revoke` only republishes the directory entry
   when the revoked `deviceId` equals `localDeviceId`.** `revoke(uid,
   deviceId)` may name *another* device on the account (`FR-AUTH-004`), but
   `DeviceDirectoryService.publish` can only ever assemble a bundle from
   THIS process's own `IdentityService` — it has no key material for any
   other device. Publishing this device's own identity/prekey bundle under
   a different device's `directory/$deviceId` entry would corrupt that
   entry with the wrong identity key, so the call is skipped for that case
   (`test_EARS_FB_17...does NOT republish when the revoked deviceId is a
   DIFFERENT device`). The other device republishes its own entry (with its
   own now-current `revokedAt`) the next time its own `IdentityService`/
   `revoke` runs — not solved by this task, not a regression either, since
   nothing before this task republished any directory entry at all.
4. **`ensureSignedPreKey`/`replenishOneTimePreKeys` only fire the publish
   hook when they actually changed something**, not on their existing
   idempotent no-op branches (a second `ensureSignedPreKey()` call, or a
   `replenishOneTimePreKeys()` call when the pool is already at/above
   `minimum`). Task §2 says publish triggers on rotation/replenishment;
   a no-op is neither.
5. **`publish` consumes one one-time prekey per call**, because task §2
   explicitly names `IdentityService.getLocalPreKeyBundle()` as the source
   of `prekeyBundle`, and that method's own contract (E03-B02) issues a
   *distinct*, cursor-advanced one-time prekey on every call — the same
   behaviour as handing a bundle to a real peer. Every `publish` call this
   task wires in (rotation, replenishment, revocation) therefore also
   consumes one one-time prekey, on top of whatever the pool's own
   replenishment logic maintains. Not actioned in code (same as the task's
   own documented "stale bundle" limitation in §6) — flagged here for the
   reviewer and for whoever tunes `replenishOneTimePreKeys`'s
   `minimum`/`batch` defaults later.

## Open Questions
- `OQ-E11-T02-1` carries forward unresolved (see Deviations #1) — not a new
  question opened by this task, but this task is the second of the two the
  original answer named as the point to bring in the Firebase emulator, and
  it still wasn't brought in. Whoever next touches a rules-bearing node
  should either bring it in or explicitly re-defer it again.
- **OQ-E11-T06-1 — first-publish squatting.** The cross-model review found
  that `directory/$deviceId`'s immutable-`ownerUid` rule means whichever
  account writes an id *first* owns it permanently — including a hostile
  account publishing a forged identity key under an id it doesn't
  legitimately hold, before the real device ever publishes. `E07`/`E06-T07`
  (the future consumers of `lookupDevice`) must not treat a directory hit as
  unconditionally authoritative on a never-before-contacted peer; this is
  additional context for whatever TOFU-replacement logic those tasks build,
  not a defect in this task's own contract.
  - **Status:** 🟡 open — not blocking this task; blocking a naive
    "directory always wins" design in whichever task consumes it
  - **Owner:** whoever next shards E07's TOFU fix or E06-T07's fallback
- **OQ-E11-T06-2 — one-time-prekey reuse across readers.** `lookupDevice`
  returns the same currently-published one-time prekey to every caller who
  reads it before the next rotation — there is no single-use consumption
  semantics at the directory layer (unlike the mesh-based prekey exchange,
  which this directory is explicitly a fallback for). A consumer using this
  as a first-contact bootstrap should treat the returned bundle's freshness
  conservatively.
  - **Status:** 🟡 open — not blocking; a property of the publish/lookup
    design to be aware of, not a bug in it
  - **Owner:** whoever builds the consuming task (E06-T07 fallback)
- **OQ-E11-T06-3 — no delete path for a directory entry.** A null/empty
  write fails the `.write` rule's `hasChildren` shape (implicitly, via the
  boundary guard), so once published, a `directory/$deviceId` entry is
  effectively permanent — there's no way to un-publish. Not assessed as a
  defect (this task's own §4 didn't scope removal), but worth naming
  explicitly rather than leaving as a silent property.
  - **Status:** 🟡 open — not blocking
  - **Owner:** unassigned; revisit if account/device deletion is ever
    scoped (E12's territory)
