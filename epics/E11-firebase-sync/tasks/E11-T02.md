# E11-T02 · Security rules that structurally enforce the FR-FB-002 boundary

## 1. Goal
Make the Firebase boundary hold even when the client is wrong, hostile, or a
future version of itself: today `database.rules.json` lets an authenticated
user write *anything at all* under their own subtree, so `FR-FB-002` is
enforced by client code only.

## 2. Business logic

- **This is the inherited obligation from `E01-T02`'s review**, carried to
  E11 verbatim in `epics/E01-identity-access/retro.md` §Open follow-ups:
  *"no `.validate` rule structurally enforcing the FR-FB-002 field boundary"*
  — the boundary "is enforced by client code only, not structurally by the
  rules."
- **`FR-FB-002`/`EARS-FB-1`** is the epic's non-negotiable constraint and the
  epic states it is *"testable by schema review"*. A `.validate` rule turns
  "reviewable" into "rejected by the server".
- **`FR-FB-001`** supplies the allow-list; `E11-T01` already wrote it down
  once in `docs/firebase-schema.md` and once in `firebase_boundary.dart`.
  This task adds the third and authoritative copy — the rules file — and the
  test in §8 exists specifically to keep the three from drifting apart.
- **Ownership stays per-account.** `auth.uid === $uid` is unchanged; this
  task narrows what the owner may write, it does not widen who may read.
  Any cross-account read is `ADR-0008`'s decision and is out of scope.
- **Default deny.** Every node not named gets `".read": false, ".write": false`
  — the existing `$other` catch-all is kept and extended to unknown children
  *inside* `users/$uid` too, which today are wide open.

## 3. What this task does

- Rewrites `database.rules.json` so that, under `users/$uid`:
  - only the child names `devices` and `sync_cursors` are writable at all
    (a `$other` deny sibling inside `$uid`);
  - `devices/$deviceId` accepts exactly the four keys from
    `docs/firebase-schema.md` and no others (`.validate` +
    `"$other": { ".validate": false }`), each with a type check;
  - `sync_cursors/$writer/$conversation/$about` accepts exactly its five
    keys, typed, with `lastConfirmedSequenceNumber` required to be a
    non-negative number;
  - string fields carry a length ceiling (a rule that permits a 10MB string
    permits smuggling ciphertext through a field named `deviceId`).
- Adds a **Dart structural test** (`firebase_rules_test.dart`) that parses
  `database.rules.json` and asserts, for every node in
  `docs/firebase-schema.md` marked `live`: the node exists, its `.validate`
  names exactly the documented key set, unknown children are denied, and no
  node anywhere grants a read or write outside `auth.uid === $uid`.
- Updates `docs/firebase-schema.md` with a "Rules enforcement" column stating,
  per node, whether the boundary is enforced structurally (rules) or by the
  client guard only.
- Deploys nothing. Deployment is called out in §4.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT run `firebase deploy --only database`.** Publishing rules changes
  a live backend and can lock out devices already in the field — that is a
  human action at the merge gate, exactly as `E01-T02` deliberately did not
  deploy Firestore rules. Write the rules, prove them, and say in the PR that
  deployment is pending.
- **Does NOT add the emulator or `@firebase/rules-unit-testing`.** A
  behavioural rules test needs the Firebase emulator and a new dev dependency
  — 🧍 a rule 3 human gate. The structural Dart test is this task's required
  deliverable; the behavioural test is recorded as `OQ-E11-T02-1`, not
  smuggled in.
- **Does NOT declare rules for any reserved or not-decided node**
  (`push`, `config/version_policy`, `directory/`). Those stay denied by the
  catch-all until their owner exists. A rule written ahead of its schema is a
  hole with a comment next to it.
- **Does NOT change any path, field name, or client code.** If a rule and the
  client disagree, the client is right and the *rule* is the bug — `E11-T01`
  fixed the paths already.
- **Does NOT widen read access to another account** (that is `ADR-0008`).
- **Does NOT touch `firestore.rules`** — this project has no Firestore
  (E01-T02 pivoted to RTDB because Firestore now requires the Blaze plan and
  the human declined billing).

## 5. Contract

### Data — the rules shape (structure is binding; exact JSON is the builder's)

```
rules
├── users
│   └── $uid                       .read/.write : auth != null && auth.uid === $uid
│       ├── devices
│       │   └── $deviceId          .validate: has children [deviceId, createdAt, lastSeenAt, platform]
│       │       ├── deviceId       .validate: isString && length <= 128 && val === $deviceId
│       │       ├── createdAt      .validate: isNumber
│       │       ├── lastSeenAt     .validate: isNumber && >= createdAt
│       │       ├── platform       .validate: isString && length <= 32
│       │       └── $other         .validate: false
│       ├── sync_cursors
│       │   └── $writer/$conversation/$about
│       │       ├── localDeviceId                .validate: isString && length <= 128
│       │       ├── remoteDeviceId               .validate: isString && length <= 128
│       │       ├── conversationId               .validate: isString && length <= 128
│       │       ├── lastConfirmedSequenceNumber  .validate: isNumber && >= 0
│       │       ├── updatedAt                    .validate: isNumber
│       │       └── $other                       .validate: false
│       └── $other                 .validate: false      ← new: unknown subtrees denied
└── $other                         .read: false, .write: false
```

`lastSeenAt >= createdAt` is stated because `E11-T03` is about to make those
two values differ; today they are always equal and the rule holds either way.

### Functions
No production Dart. The test file exposes no public API.

### External services & flags
Firebase Realtime Database rules for `nexora-b3a97-default-rtdb`. No new
dependency, no new secret. **Deployment is a human step** (§4).

## 6. Risks

- **RTDB `.validate` does not run on delete**, and `.write` at `users/$uid`
  cascades: a `.validate: false` on `$other` blocks writing unknown children
  but does not retroactively remove any that exist. State that in the PR.
- `newData.hasChildren([...])` makes every listed field **required**. A
  partial update (`update()` rather than `set()`) then fails. Both existing
  writers use `.set()` with the full map — confirm before shipping, because
  `E11-T03` and `E11-T04` will want partial writes and will have to say so.
- Rules are validated as a whole file by Firebase; a syntax error is only
  caught at deploy time, which this task does not run. `firebase database:rules:get`
  / a JSON parse in the test is the cheap substitute — a malformed file must
  fail the Dart test, not the human's deploy.
- The structural test must read `docs/firebase-schema.md`, not restate the key
  lists inline — a test that duplicates the thing it is checking passes even
  when both are wrong together.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-FB-4**: The system's Firebase security rules SHALL reject any write to a documented node carrying a field outside that node's `FR-FB-001` allow-list. (FR-FB-002)
- **EARS-FB-5**: The system's Firebase security rules SHALL deny read and write on every path not documented in `docs/firebase-schema.md`. (FR-FB-002, NFR-PRIV-001)
- **EARS-FB-6**: The system's Firebase security rules SHALL grant read and write only to the authenticated owner of the subtree. (FR-FB-001, ADR-0005)

  files; for each `live` node asserts the `.validate` key set equals the

- `test_EARS_FB_5_undocumented_paths_are_denied` → asserts a top-level

- `test_EARS_FB_6_no_cross_account_access` → asserts every `.read`/`.write`
