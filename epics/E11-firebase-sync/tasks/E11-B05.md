# E11-B05 · documented Firebase containers can be overwritten with an arbitrary blob

## The defect

`database.rules.json` (pre-fix) declared `.validate` on every documented
*leaf* field (`deviceId`, `platform`, `state`, ...) and on the innermost
wildcard node of each container (`devices/$deviceId`,
`relationships/$peerDeviceId`, `sync_cursors/$writer/$conversation/$about`)
— but never on the container nodes themselves: `users/$uid`, `devices`,
`relationships`, `sync_cursors`, `sync_cursors/$writer`,
`sync_cursors/$writer/$conversation`.

RTDB's `.validate` check runs at every level of the hierarchy a write
touches. A container with no `.validate` of its own imposes no shape
requirement, so a write like:

```
set(ref('users/<own-uid>/devices'), '<arbitrary base64 blob>')
```

is accepted: `.write` at `users/$uid` grants it (own uid), and no level
between there and `devices` declares a `.validate` that would reject a
non-object value. The `$deviceId` wildcard rule is never reached (there
is no child to validate against — the write IS the leaf), and `$other`
never fires (it only denies an unknown *child name*, and there is no
child here at all).

This is exactly the gap `EARS-FB-5`/`FR-FB-002` exist to close, one level
up from where the existing rules already close it for individual fields:
any FR-FB-002-forbidden payload (plaintext, keys, location data) can be
parked at a documented, previously "safe" path.

## Severity

**S3** — the rules have never been deployed (`database.rules.json` is
merged to `epic_11` but `firebase deploy --only database` has not run),
so nothing is exploited in production today. Not S2: no live system is
affected yet. Not S4: this is the exact property the task exists to
guarantee, and every later task (`T04`/`T05`/`T06`) and
`docs/firebase-schema.md`'s "Rules enforcement" column build on the
(currently false) assumption that it already holds.

## Fix direction

Add `.validate": "newData.hasChildren()"` at every documented container
node: `users/$uid`, `users/$uid/devices`, `users/$uid/relationships`,
`users/$uid/sync_cursors`, `users/$uid/sync_cursors/$writer`,
`users/$uid/sync_cursors/$writer/$conversation`. `hasChildren()` with no
argument requires the node to be a non-empty object — it forces every
level to be a container, never a leaf, without constraining which
children it must have (that's still the deeper, field-specific
`.validate`'s job). Deletion is unaffected (`.validate` is skipped when
`newData` doesn't exist); a normal write to one field under the container
is unaffected (the container still has children after the write).

## What this fix does NOT do

- Does **not** change any existing leaf-level `.validate` expression —
  all already correct and covered by the existing FB-4/FB-13/FB-16
  test groups.
- Does **not** touch `directory/$deviceId` or anything under it — that
  node already declares its own container-level `.validate`
  (`newData.hasChildren([...])`) from `E11-T06`; it was never missing
  this property. (Separate, unrelated findings on `directory` are
  tracked as `E11-B06`.)
- Does **not** deploy the rules — `firebase deploy --only database` is
  still the human's action at the epic→`development` merge gate
  (`OQ-E11-T02-1`), unaffected by this fix.
- Does **not** add a Firebase emulator dependency — this fix, like the
  rest of the rules file, is verified by this repo's own JSON-structural
  simulator (`test/core/services/firebase_rules_test.dart`), not a live
  RTDB instance.

## Regression test (write it first)

`test_EARS_FB_5_documented_containers_reject_a_leaf_overwrite` — asserts
the exact string `.validate: "newData.hasChildren()"` is present at each
of the six container paths above. Must fail on pre-fix rules (it does —
confirmed by stashing the fix and re-running) and pass after.
