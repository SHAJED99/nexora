# E11-B06 · directory-entry squatting and cross-account `ownerUid` readability

## The defect

Two findings on `directory/$deviceId`, both distinct from `E11-B05`
(which was about `users/**`'s missing container-level `.validate`).

**1. Directory-entry squatting (S2).** `database.rules.json`'s write rule:

```
".write": "auth != null && newData.child('ownerUid').val() === auth.uid
           && (!data.exists() || data.child('ownerUid').val() === auth.uid)"
```

is first-writer-wins: whoever publishes to a given `$deviceId` first owns
it forever after (`data.exists()` then requires the SAME uid to write
again). Nothing binds `$deviceId` cryptographically to the
`identityPublicKey`/`prekeyBundle` being published under it.
`ADR-0008` itself notes device ids "leak wherever they are shared" —
i.e. to every mesh peer a device has ever contacted. Any authenticated
user who learns a device id can publish their OWN identity key under it
before the real owner ever does, and the true owner is then permanently
locked out. `E11-B02`'s fix (binding `identityPublicKey` to the key
embedded in `prekeyBundle`) only proves internal self-consistency — a
squatter's entry is perfectly self-consistent and passes that check.
Consumers doing `lookupDevice` on that id get an attacker's identity key
for a victim's device, which is exactly the impersonation `ADR-0008`'s
option 2 was chosen to close.

**2. Cross-account `ownerUid` readability (S3).** `directory/$deviceId`'s
`.read": "auth != null"` grants read on the WHOLE node, `ownerUid`
included. Any authenticated user holding two device ids can read both
entries' `ownerUid` and learn whether they belong to the same Firebase
account — device-linkage/account-correlation, a distinct privacy surface
`ADR-0008`'s cost analysis (`"one public key + revocation flag per
device id"`) never priced in. `ownerUid` is a write-ownership marker;
nothing in `lookupDevice` reads it back.

**3. No unpublish path (S4, likely intentional, undocumented).** The
write rule denies deletion (on delete, `newData.child('ownerUid').val()`
is null, never equal to `auth.uid`) — only a `revokedAt` update is
possible. Flagged so it is a documented decision, not an oversight.

## Why this is not currently exploitable

Per `E11-B01` (already filed, `won't-fix-in-E11`): `DeviceDirectoryService`
is never constructed anywhere in `lib/` — nothing in the running app
publishes to or reads from `directory/` in production yet. All three
findings here require a real caller to exist before they mean anything
concrete. `E11-B01`'s own resolution deferred exactly this kind of
consequence to "the first real consumer (E07 TOFU replacement or E06-T07
prekey fallback)" — this bug is that deferred consequence, named now so
it has a reader when that consumer gets built, rather than discovered
again from scratch.

## Severity

**S2** for finding 1 (a real identity-impersonation vector once wired,
matching the class of exploit `ADR-0008` was written to prevent) · **S3**
for finding 2 (a real but narrower privacy leak, cross-account
correlation not cross-account content access) · **S4** for finding 3
(a plausible intentional gap, needs a documented answer not a fix).

## Fix direction (for whoever wires the first consumer, not this bug)

- **Finding 1** needs an actual binding between `$deviceId` and the
  identity being published — e.g. requiring `$deviceId` to be derived
  from (or signed by) the identity key itself, so squatting a specific
  id without controlling its corresponding private key becomes
  infeasible. This is close to `ADR-0008`'s own territory (a protocol
  design choice, not a rules tweak) and should go back through rule 3 if
  it isn't already covered by the ADR's existing text.
- **Finding 2** is fixable within the rules file alone: move `ownerUid`
  to a separate, owner-only-readable node (e.g. `directory_private/
  $deviceId/ownerUid`), written in the same client-side call as the
  public entry, with `.read` restricted to `auth.uid === $deviceId`'s
  owner. `lookupDevice`'s current callers don't read `ownerUid` at all,
  so this is additive, not a breaking schema change to existing readers.
- **Finding 3**: a human decision — either document "revoke, don't
  delete" as final, or add an owner-only delete path if unpublishing is
  actually wanted.

## What this bug does NOT do

- **Finding 1 remains unfixed and `status: blocked`.** The human chose a
  direction (derive `$deviceId` from the identity key -- see `ADR-0008`'s
  2026-09-05 addendum) but implementing it needs either a Cloud Function
  (a new dependency, its own rule-3 call) or a bootstrap-sequencing
  change spanning `E01`/`E03` (RTDB security rules have no hash/signature
  primitive, so a rules-only enforcement of this binding is not
  possible) -- neither is this bug's own scope until that follow-up is
  concrete enough to shard as a task.
- Does **not** revisit `ADR-0008`'s core decision (public directory,
  option 2) — these are gaps within that decision's implementation, not
  a challenge to the decision itself.
- Does **not** claim `E11-B02`'s fix (identity/prekey self-consistency)
  is wrong — it does exactly what it says; this bug documents what it
  was never meant to catch.
- The finding-2/3 fix does **not** touch `lookupDevice` or any of its
  future consumers (`E07`, `E06-T07`) — `ownerUid` was never read by
  `lookupDevice`, so moving it to its own node changes nothing about
  what a reader sees.

- 2026-09-05 (round 2) — **Cross-model review (Opus) found the round-1
  fix's `.write` expression -- `root.child('directory_private/'+$deviceId+
  '/ownerUid').val() === auth.uid` -- was itself broken**: `root` in a
  Realtime Database multi-location `update()` reflects the PRE-write
  snapshot, never a sibling path written in the SAME update, so a brand
  new device's very first publish (when `directory_private/$deviceId/
  ownerUid` does not exist yet) would be denied FOREVER --
  `DeviceDirectoryService.publish` swallows the resulting
  `PERMISSION_DENIED` (best-effort, catch-and-log), so this would have
  failed silently in production. The reviewer verified this against a
  real Firebase RTDB emulator (`@firebase/rules-unit-testing`), not by
  reasoning alone, and proposed the Firebase-documented remedy:
  `newData.parent().parent().child('directory_private').child($deviceId)
  .child('ownerUid')` (walking up from the rule's own location through
  the merged multi-location update to reach the same sibling).
  - **I independently re-verified the proposed remedy** (not merely
    applying it on the reviewer's word) using the same emulator tooling:
    a 6-case test suite (fresh-device first publish; a second account's
    squat attempt on an existing entry, denied; the true owner's own
    re-publish/rotation, still succeeds; an unauthenticated write, denied;
    the private node's own immutability in isolation; reading `ownerUid`
    as a different account, denied) — all 6 pass against the exact
    `database.rules.json` content in this worktree, on a real emulator, not
    the JSON-structure-only checks `firebase_rules_test.dart` itself is
    limited to (its own header already documents this limitation).
  - Applied the fix: `database.rules.json`'s `.write` expression,
    `firebase_rules_test.dart`'s two exact-string assertions for it,
    `docs/firebase-schema.md`'s prose, and
    `device_directory_service.dart`'s doc comment (which had overstated
    the atomicity requirement as "crash-safety" when it is actually
    REQUIRED for the rule to see the sibling write at all, not merely
