# E11-T03 · Device registry semantics — real createdAt, refreshed lastSeenAt

## 1. Goal
Make the device registry answer the question it exists to answer — *which of
this account's devices are real, and when was each last seen* (`FR-AUTH-004`)
— by giving `createdAt` a first-seen meaning it does not currently have.

## 2. Business logic

- **This is the inherited obligation from `E01-T02`'s review**, carried to E11
  verbatim in `epics/E01-identity-access/retro.md` §Open follow-ups and in
  `E01-T02.md` §Run log: *"`createdAt`/`lastSeenAt` are always equal since
  both use `ServerValue.timestamp` on every `.set()` — `createdAt` currently
  carries no real 'first seen' information."*
- **`FR-AUTH-004`**: multiple devices per account, each with its own local
  state. The registry is the only place the account can enumerate them, and a
  registry where every device claims to have been created just now cannot
  distinguish a long-standing device from one that appeared this morning —
  which is exactly the signal a future revocation or abuse decision needs.
- **`FR-FB-001`**: device registry metadata is permitted. The field set does
  not change; only *when each field is written* changes.
- **`ADR-0005`**: still a best-effort, additive account↔device pointer.
  `registerDevice` must keep never throwing, keep its bounded timeout, and
  keep being irrelevant to local sign-in success. A registry refresh that can
  block or fail sign-in is a worse bug than the one being fixed.

## 3. What this task does

- Splits the single `.set()` into the two writes the data actually needs:
  - `createdAt` written **only when the node does not yet exist**, via a
    write that cannot clobber an existing value;
  - `lastSeenAt` (and `platform`, `deviceId`) written on every registration.
- Keeps the whole operation inside the existing best-effort envelope: one
  bounded `.timeout(_timeout)` budget across the whole sequence, every failure
  caught and logged through `ObservabilityService`, never rethrown.
- Keeps the public API (`registerDevice(uid, deviceId)`) unchanged so
  `SignInUseCase` and its tests are untouched.
- Extends `writeDeviceMetadata` (or adds a sibling seam) so tests can still
  observe the exact payloads without a live platform channel — the existing
  `_CapturingFirebaseMetadataService` test double pattern must keep working.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT change `SignInUseCase` or its tests.** The caller keeps calling
  one fire-and-forget method. If the signature has to change to make this
  work, stop — that is a sharding error, raise it as an Open Question.
- **Does NOT add a field.** No `appVersion`, no `model`, no `lastIp`, no
  "might be useful for the device list screen". Every field needs its own
  `FR-FB-001` justification, and adding one changes `E11-T02`'s rules, which
  this task's `files:` does not include.
- **Does NOT add a retry queue or offline write queue.** Still explicitly
  out of scope, as it was in `E01-T02` §4.
- **Does NOT read the registry back into local state.** `ADR-0005`: Firebase
  never feeds local device identity or session. There is no "sync devices to
  Drift" step here.
- **Does NOT build a device-list UI.** `ui_surface: []` for this epic.
- **Does NOT implement revocation** — that is `E11-T04`, which owns the
  `revocation` node and will touch a *different* file for exactly this reason.

## 5. Contract

### Data
Node `users/$uid/devices/$deviceId`, field set unchanged from `E11-T01`'s
schema: `deviceId`, `createdAt`, `lastSeenAt`, `platform`.

Write semantics after this task:

| Field | Written when | Value |
|---|---|---|
| `deviceId` | every registration | the local device id |
| `platform` | every registration | `'android'` |
| `lastSeenAt` | every registration | `ServerValue.timestamp` |
| `createdAt` | **first registration only** | `ServerValue.timestamp`, never overwritten afterwards |

`E11-T02`'s rule `lastSeenAt >= createdAt` must continue to hold — it is
satisfied by construction here, and a test must assert the ordering claim
rather than assume it.

The mechanism for "first only" is the builder's choice between (a) a
`runTransaction` on the node that preserves an existing `createdAt`, or
(b) a `.get()` on `createdAt` followed by a child `.set()` only when absent.
Both are acceptable; (a) is race-free and (b) is simpler and testable through
the existing seam. **Whichever is chosen, document why in §9 Deviations if it
is (b), and note the benign race** (two devices cannot race on the same node;
the same device racing itself would at worst re-stamp `createdAt` once).

### Functions

  returns: "Future<void> — completes always; never throws, never propagates a Firebase error"

## 6. Risks

- **The timeout budget is per-operation, not per-call.** Two sequential
  awaits each with `_timeout` doubles the worst case that
  `E01-T02`'s review bug fix deliberately bounded. Bound the *whole*
  sequence, and keep the existing hanging-write regression test green — that
  test exists because `registerDevice` once could hang sign-in indefinitely.
- `ServerValue.timestamp` reads back as an `int`, but writes as a sentinel
  map. An existence check comparing the two directly will always disagree.
- A `runTransaction` on a node whose rules require `hasChildren([...])` fails
  mid-transaction when the node is absent — check `E11-T02`'s rules shape
  before choosing (a).
- The existing tests subclass the service and override the write seam. Adding
  a *second* seam without updating those doubles silently bypasses them: the
  test passes and the new code path is never exercised. Assert on both.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-FB-7**: WHEN a device registers for the first time, the system SHALL record `createdAt` and `lastSeenAt` in the device registry. (FR-FB-001, FR-AUTH-004)
- **EARS-FB-8**: WHEN a device that is already registered registers again, the system SHALL refresh `lastSeenAt` and SHALL NOT overwrite `createdAt`. (FR-FB-001, FR-AUTH-004)
- **EARS-FB-9**: IF any Firebase operation in registration fails, times out, or the device is offline, THEN the system SHALL log the failure and complete normally without throwing. (ADR-0005)

### Tests
- `test_EARS_FB_7_first_registration_writes_both_timestamps`
- `test_EARS_FB_8_second_registration_preserves_created_at` → capturing double
  reports an existing node; asserts the emitted payload has no `createdAt` key
  (or a transaction that preserves the prior value).
- `test_EARS_FB_8_last_seen_never_precedes_created_at`
- `test_EARS_FB_9_read_failure_does_not_block_registration` → the existence
  read throws; registration still completes and `lastSeenAt` is still written.
- `test_EARS_FB_9_hanging_write_still_bounded` → the existing regression test,
  extended to cover the two-write sequence.

### Manual
1. Sign in on a device, note `createdAt` in the Firebase console.
2. Sign out, sign in again → `lastSeenAt` moves, `createdAt` does not.
