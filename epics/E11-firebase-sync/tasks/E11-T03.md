# E11-T03 · Device registry semantics — real createdAt, refreshed lastSeenAt

## 1. Goal
Make the device registry answer the question it exists to answer — *which of
this account's devices are real, and when was each last seen* (`FR-AUTH-004`)
— by giving `createdAt` a first-seen meaning it does not currently have.

## 2. Business logic

- **This is the inherited obligation from `E01-T02`'s review**, carried to E11
  verbatim in `epics/E01-identity-access/retro.md` §Open follow-ups and in
  `E01-T02.md` §Run log: *"`createdAt`/`lastSeenAt` are always equal since
  both use `ServerValue.timestamp` on every `.set()` — `createdAt` currently
  carries no real 'first seen' information."*
- **`FR-AUTH-004`**: multiple devices per account, each with its own local
  state. The registry is the only place the account can enumerate them, and a
  registry where every device claims to have been created just now cannot
  distinguish a long-standing device from one that appeared this morning —
  which is exactly the signal a future revocation or abuse decision needs.
- **`FR-FB-001`**: device registry metadata is permitted. The field set does
  not change; only *when each field is written* changes.
- **`ADR-0005`**: still a best-effort, additive account↔device pointer.
  `registerDevice` must keep never throwing, keep its bounded timeout, and
  keep being irrelevant to local sign-in success. A registry refresh that can
  block or fail sign-in is a worse bug than the one being fixed.

## 3. What this task does

- Splits the single `.set()` into the two writes the data actually needs:
  - `createdAt` written **only when the node does not yet exist**, via a
    write that cannot clobber an existing value;
  - `lastSeenAt` (and `platform`, `deviceId`) written on every registration.
- Keeps the whole operation inside the existing best-effort envelope: one
  bounded `.timeout(_timeout)` budget across the whole sequence, every failure
  caught and logged through `ObservabilityService`, never rethrown.
- Keeps the public API (`registerDevice(uid, deviceId)`) unchanged so
  `SignInUseCase` and its tests are untouched.
- Extends `writeDeviceMetadata` (or adds a sibling seam) so tests can still
  observe the exact payloads without a live platform channel — the existing
  `_CapturingFirebaseMetadataService` test double pattern must keep working.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT change `SignInUseCase` or its tests.** The caller keeps calling
  one fire-and-forget method. If the signature has to change to make this
  work, stop — that is a sharding error, raise it as an Open Question.
- **Does NOT add a field.** No `appVersion`, no `model`, no `lastIp`, no
  "might be useful for the device list screen". Every field needs its own
  `FR-FB-001` justification, and adding one changes `E11-T02`'s rules, which
  this task's `files:` does not include.
- **Does NOT add a retry queue or offline write queue.** Still explicitly
  out of scope, as it was in `E01-T02` §4.
- **Does NOT read the registry back into local state.** `ADR-0005`: Firebase
  never feeds local device identity or session. There is no "sync devices to
  Drift" step here.
- **Does NOT build a device-list UI.** `ui_surface: []` for this epic.
- **Does NOT implement revocation** — that is `E11-T04`, which owns the
  `revocation` node and will touch a *different* file for exactly this reason.

## 5. Contract

### Data
Node `users/$uid/devices/$deviceId`, field set unchanged from `E11-T01`'s
schema: `deviceId`, `createdAt`, `lastSeenAt`, `platform`.

Write semantics after this task:

| Field | Written when | Value |
|---|---|---|
| `deviceId` | every registration | the local device id |
| `platform` | every registration | `'android'` |
| `lastSeenAt` | every registration | `ServerValue.timestamp` |
| `createdAt` | **first registration only** | `ServerValue.timestamp`, never overwritten afterwards |

`E11-T02`'s rule `lastSeenAt >= createdAt` must continue to hold — it is
satisfied by construction here, and a test must assert the ordering claim
rather than assume it.

The mechanism for "first only" is the builder's choice between (a) a
`runTransaction` on the node that preserves an existing `createdAt`, or
(b) a `.get()` on `createdAt` followed by a child `.set()` only when absent.
Both are acceptable; (a) is race-free and (b) is simpler and testable through
the existing seam. **Whichever is chosen, document why in §9 Deviations if it
is (b), and note the benign race** (two devices cannot race on the same node;
the same device racing itself would at worst re-stamp `createdAt` once).

### Functions

```yaml
- signature: "FirebaseMetadataService.registerDevice(String uid, String deviceId) -> Future<void>"
  params: { uid: "Firebase Auth account uid", deviceId: "local device identity id" }
  returns: "Future<void> — completes always; never throws, never propagates a Firebase error"
  purpose: "unchanged public contract; internals now write createdAt once"

- signature: "FirebaseMetadataService.readDeviceMetadata(String uid, String deviceId) -> Future<Object?>"
  params: { }
  returns: "Object? — the raw node value, or null on any failure/timeout"
  purpose: "the test seam for the existence check; never throws (mirrors SyncCursorService.readCursorData)"
```

### External services & flags
Firebase Realtime Database, unchanged instance. No new dependency, no flag.

## 6. Risks

- **The timeout budget is per-operation, not per-call.** Two sequential
  awaits each with `_timeout` doubles the worst case that
  `E01-T02`'s review bug fix deliberately bounded. Bound the *whole*
  sequence, and keep the existing hanging-write regression test green — that
  test exists because `registerDevice` once could hang sign-in indefinitely.
- `ServerValue.timestamp` reads back as an `int`, but writes as a sentinel
  map. An existence check comparing the two directly will always disagree.
- A `runTransaction` on a node whose rules require `hasChildren([...])` fails
  mid-transaction when the node is absent — check `E11-T02`'s rules shape
  before choosing (a).
- The existing tests subclass the service and override the write seam. Adding
  a *second* seam without updating those doubles silently bypasses them: the
  test passes and the new code path is never exercised. Assert on both.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-FB-7**: WHEN a device registers for the first time, the system SHALL record `createdAt` and `lastSeenAt` in the device registry. (FR-FB-001, FR-AUTH-004)
- **EARS-FB-8**: WHEN a device that is already registered registers again, the system SHALL refresh `lastSeenAt` and SHALL NOT overwrite `createdAt`. (FR-FB-001, FR-AUTH-004)
- **EARS-FB-9**: IF any Firebase operation in registration fails, times out, or the device is offline, THEN the system SHALL log the failure and complete normally without throwing. (ADR-0005)

**Deviations from spec/design:**
1. **Mechanism: chose (b)**, the `.get()`-then-conditional-write existence
   check, over (a) `runTransaction` — per §5's explicit permission. Reasoning:
   `E11-T02`'s `.validate` rule on the `$deviceId` node requires
   `newData.hasChildren(['deviceId','createdAt','lastSeenAt','platform'])`
   (`database.rules.json`) — a `runTransaction` that only supplies a partial
   update when the node already exists would need to merge in the untouched
   fields itself before returning from the transaction callback to keep that
   `.validate` rule satisfied, which is exactly what `.update()` already does
   for free at the client-library level; (b) also stays inside the existing
   test-seam pattern this task's §3 requires ("the existing
   `_CapturingFirebaseMetadataService` test double pattern must keep
   working") without inventing a second live-platform-channel shape for
   transactions, which flutter tests can't drive without a real
   `FirebaseDatabase`.
   **Benign race, as anticipated by §5**: two different devices never share a
   `$deviceId` node, so they cannot race on the same existence check. The same
   device calling `registerDevice` twice concurrently (not a real call
   pattern — `SignInUseCase` calls this once per sign-in, fire-and-forget) at
   worst has both calls read "does not exist" and both write `createdAt` —
   harmless, since `ServerValue.timestamp` resolves to whichever write the
   server orders last, and either value is a legitimate "first seen" moment
   for that device.
2. **The write moved from `.set()` to `.update()`** (not named as a required
   change in §5's Contract, but required by (b)'s mechanics): `.set()`
   replaces the whole node, so a repeat registration's payload (which
   deliberately omits `createdAt`) would have deleted the field from the
   server entirely, which is a worse defect than the one being fixed.
   `.update()` merges the given fields into any existing node (and still
   creates the node, with just the given fields, when none exists) — exactly
   the semantics both the first and every later registration need. No field
   in the allow-list changed; `FirebaseBoundary.assertAllowedFields` still
   runs before every write in both branches.
3. **[Corrected in round 2 — the original version of this deviation was
   wrong.]** On a failed/throwing existence read, `registerDevice` treats
   existence as "**first**" (writes `createdAt`) — and, as of round 2,
   the same treatment applies when the read *succeeds* but returns a node
   that exists yet is missing `createdAt` (the leftover shape of exactly
   this failure case, from before the round-2 fix, or any other path that
   ever created an incomplete node).
   **Original (round-1) reasoning, since falsified by cross-model review**:
   the first cut treated a failed read as "not first" (omit `createdAt`),
   reasoned to be "the safer of the two wrong guesses" because guessing
   wrong the other way "risks re-clobbering an existing value." That
   framing was backwards. `.update()` merges — an *existing* device with a
   real `createdAt` is never at risk from including it again (its own
   value is what would be written back, or `.update()` simply leaves an
   omitted field alone in the successful-read path, which is unaffected by
   this branch). The actual risk was on the **other** side: a genuinely
   first-ever registration whose existence read happens to fail would
   create a node with **no `createdAt` at all**, and every subsequent
   registration would then see a non-null (but incomplete) node and repeat
   the same omission forever — a **permanent** loss, not a one-registration
   delay as originally claimed. Guessing "first" trades that permanent
   loss for a narrow, self-correcting cost: an *already-existing* device
   whose read happens to fail gets `createdAt` **re-stamped** with a fresh
   timestamp that registration (a one-time "first seen" inaccuracy), which
   cannot recur once a later read succeeds. Caught by cross-model (Opus)
   review on PR #43 round 1; fixed and regression-tested in round 2
   (`test_EARS_FB_8_incomplete_existing_node_still_gets_created_at`,
   falsified against the pre-fix code).
4. **A `FirebaseBoundaryViolation` from `assertAllowedFields` is now caught
   by `registerDevice`'s single outer catch-all**, rather than propagating
   uncaught as the pre-T03 code's structure allowed (`registerDevice`
   previously called the guard directly in its own body, before entering any
   try/catch). This task's own §2 explicitly elevates "never throwing" to an
   unconditional requirement for the whole method ("`registerDevice` must
   keep never throwing... A registry refresh that can block or fail sign-in
   is a worse bug than the one being fixed") to make room for the new
   read-decide-write sequence sharing one timeout budget (§6's "per-operation
   timeout doubles the worst case" risk) — bounding read+write together in
   one shared `.timeout()`/catch was not compatible with also keeping the
   guard call outside every catch, since the read that decides the payload
   now sits between the guard-eligible payload construction and any
   individually-scoped catch. No test in this codebase asserts the old
   propagate-vs-swallow distinction for this guard (checked: none of the 5
   pre-existing tests constructs an out-of-allow-list payload), and the
   payload is always built from this method's own two hardcoded literal
   field sets, so it cannot violate the boundary in practice — logging it via
   `ObservabilityService.logError('firebase.device_registration_failed', ...)`
   still surfaces a real violation, it just no longer crashes the caller.
   Flagging this explicitly rather than silently reinterpreting the original
   inline comment's intent.
