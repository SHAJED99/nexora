# E11-B04 · the guard-ordering tests never actually exercise the guard

## The defect

`E11-T01`'s whole runtime deliverable is `FirebaseBoundary.assertAllowedFields`
sitting *before* the real write call in both `FirebaseMetadataService
._registerDevice` and `SyncCursorService.writeCursorToFirebase`. Three
tests claim to prove this ordering; none can fail if it breaks:

- `firebase_boundary_test.dart`'s `test_EARS_FB_2_unknown_key_rejected
  _before_write` builds its own local `fakeWrite` function and calls the
  guard against it — exercising code the test itself wrote, never the
  production service.
- `firebase_metadata_service_test.dart`'s
  `test_EARS_FB_2_registerDevice_asserts_allowed_fields_before_the_write`
  and its `sync_cursor_service_test.dart` equivalent both compare the
  *captured payload's key set* against the allow-list. Both real call
  sites build their payload entirely from hardcoded, already-safe field
  names (`deviceId`, `lastSeenAt`, `platform`, `createdAt` / the
  `SyncCursor` fields) — there is no path through the public API that
  could ever produce a payload with a forbidden key. The comparison is
  therefore true whether the guard call exists, was deleted, or never
  ran at all.

Confirmed by inspection (not by mutating the file, which this session's
own permission classifier blocks for a security-guard call — see
`L-infra-003`): deleting the `FirebaseBoundary.assertAllowedFields(...)`
line from either `_registerDevice` or `writeCursorToFirebase` changes
nothing any of these three tests observe.

## Severity

**S3** — the shipped behavior is correct (both guard calls are genuinely
present and in the right place); this is a missing regression guard, not
a live defect. Not S2: nothing is exploitable today, since neither real
call site can produce a bad payload. Not S4: this is the one property
`EARS-FB-2` exists to hold in place, and the next task or refactor that
touches either write path has no test failing if it accidentally moves
or removes the guard.

## Fix direction

Extract the guard-then-write sequence in each service into its own
small, `@visibleForTesting`-annotated method that takes the payload as a
parameter (`guardedWriteDeviceMetadata` / `guardedWriteCursorData`),
called by the real production path exactly as before. A test can then
invoke that method directly with a deliberately-forbidden key and assert
both that `FirebaseBoundaryViolation` is thrown and that the real write
seam (`writeDeviceMetadata` / `writeCursorData`) was never reached.

## What this fix does NOT do

- Does **not** change `FirebaseBoundary.assertAllowedFields`'s own logic
  or allow-lists — already correct, per the passing FB-1 tests.
- Does **not** change what data either service actually writes in
  production; the new methods wrap the exact same two lines
  (guard call, then write call) that existed before, just under a
  callable name instead of inlined.
- Does **not** touch `firebase_boundary_test.dart`'s FB-1 tests (device/
  syncCursor forbidden-field rejection) — those are real, unit-level
  tests of `assertAllowedFields` itself and are correctly scoped.

- 2026-09-04 — **Round 2 (Opus review, real finding):** the round-1 fix
  for `SyncCursorService` silently inverted EARS-FB-2's own contract --
  moving `guardedWriteCursorData`'s call site outside `writeCursorToFirebase`'s
  `try` meant a genuine write-layer exception (not a boundary violation)
  thrown synchronously by the write seam (this repo's own
  `_ThrowingWriteSyncCursorService` test fixture does exactly this) would
  also escape the `try` uncaught -- swapping "guard violation swallowed"
  for "write failure not swallowed," the opposite defect from what round
  1 fixed. `FirebaseMetadataService` was unaffected (its guard was already
  inside `_registerDevice`, itself already inside `registerDevice`'s own
  try/catch). Fixed by moving the `try`/`catch` INSIDE
  `guardedWriteCursorData` itself, wrapping only the write call -- the
  guard's synchronous throw still precedes the `try`'s dynamic extent
  (true even in an `async` function: code before a `try` still throws
  before that `try` begins), so both halves of the contract hold at once.
  Re-verified: `flutter test test/features/messaging/domain/
  sync_cursor_service_test.dart` 14/14 (both the guard-ordering test and
  the pre-existing write-failure-caught test now pass together). Full
  suite: 899/899. `flutter analyze`: clean.
