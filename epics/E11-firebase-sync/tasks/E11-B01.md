# E11-B01 · the public device directory is never written in production

## The defect

`E11-T06` §3 states, as a deliverable:

> Wires `publish` into `IdentityService.ensureSignedPreKey`,
> `IdentityService.replenishOneTimePreKeys` and
> `DeviceRevocationService.revoke` (the three existing events that change
> what should be published).

What actually shipped is the *hook points*, not the wiring. `DeviceDirectoryService`
is **never constructed anywhere in `lib/`**. Grepping the whole production tree, the
only mentions outside its own file are a nullable constructor parameter and doc
comments:

```
lib/core/services/device_revocation_service.dart:48:    DeviceDirectoryService? directoryService,
lib/core/services/device_revocation_service.dart:74:  final DeviceDirectoryService? _directoryService;
lib/core/services/device_revocation_service.dart:134:      await _directoryService?.publish(uid, deviceId);
```

`_directoryService` is null in every production construction, because there is no
production construction of `DeviceRevocationService` either.

The one production construction of `IdentityService` passes no hook at all:

```dart
// lib/core/messaging/messaging_stack.dart:491
final identityService = IdentityService(db, resolvedStore);   // no onKeyMaterialChanged
```

so `_onKeyMaterialChanged` is null and `_notifyKeyMaterialChanged()` returns
immediately (`identity_service.dart:68`).

The trigger events themselves *do* fire in production — `messaging_stack.dart:497-499`
calls `ensureLocalIdentity()`, `ensureSignedPreKey()`, `replenishOneTimePreKeys()`
on every stack init. So the "WHEN" of EARS-FB-17 happens on every launch and the
"SHALL publish" never does.

**Consequence:** the `directory/` node is empty in every deployed database.
`ADR-0008`'s entire deliverable — the thing the ADR was written to unblock — does
not exist at runtime. The two future consumers the ADR names (`E07`'s TOFU fix,
`E06-T07`'s prekey fallback) would each be built against a directory that is
permanently empty, and `lookupDevice` would return `null` for every peer.

**Why this is not the same as T04/T05's disclosed no-caller state.** `E11-T04` §4
and `E11-T05` §4 both explicitly declare shipping "with no caller yet" as an
in-fence decision ("this task ships the service, proven, with no caller yet, the
same shape `E11-T04` shipped `isRevoked` in"). `E11-T06` §4 makes no such
statement, and §3 affirmatively claims the wiring as delivered. This is an
undisclosed gap, not a disclosed deferral.

## Repro
1. Check out `epic_11`. Grep the production tree:
   `grep -rn "DeviceDirectoryService(" lib/` → only the class's own declaration
   at `device_directory_service.dart:100`.
2. `grep -rn "onKeyMaterialChanged" lib/` → only `identity_service.dart`'s own
   declaration; no call site supplies it.
3. Read `lib/core/messaging/messaging_stack.dart:491` — `IdentityService(db, resolvedStore)`,
   two positional args, no named hook.
4. Therefore every `ensureSignedPreKey()` / `replenishOneTimePreKeys()` in the
   shipped app takes the `if (_onKeyMaterialChanged == null) return;` branch.

## Expected
**EARS-FB-17** — "WHEN a device's signed prekey rotates, its one-time prekeys are
replenished, or it is revoked, the system SHALL best-effort publish the
corresponding `directory/$deviceId` entry without exposing any private key
material." (FR-FB-001, FR-FB-002)

## Actual
No `directory/$deviceId` entry is ever written by the running application. EARS-FB-17
is satisfied only by `device_directory_service_test.dart`, which constructs the
service directly and injects the callback by hand.

## Severity
**S2** — a headline epic deliverable is inert in production, with no workaround
available to a consumer (the node is simply never populated). Not S1: nothing
regresses for a user today, no data is lost or exposed, and there is no consumer
yet to be misled — the directory is empty rather than wrong.

## Why this is `blocked`, owner `planner` — not a scoped code fix

The obvious "just wire it up" fix does not survive contact with the lifecycles:

- `publish(uid, deviceId)` requires an **authenticated Firebase uid**.
- The trigger (prekey rotation) fires inside `MessagingStack.create`, which has
  **no auth context at all** — `grep -n "uid\|FirebaseAuth\|currentUser" lib/core/messaging/messaging_stack.dart`
  returns nothing.
- `ADR-0005` makes this deliberate: Firebase is a *thin account pointer* and device
  identity/session is *fully local*. The app is offline-first; key material is
  generated and rotated for a device that may never have signed in.

So there is a genuine unanswered design question, and it is rule 3's, not a
builder's:

1. When does a device publish, if its keys rotate while signed out — on next
   sign-in? On every sign-in? Never?
2. Does a device that never signs in publish at all (and if not, is the directory
   simply absent for the offline-first majority, which would weaken `ADR-0008`'s
   premise)?
3. Which component owns the composition — `sign_in_use_case` (has the uid, does not
   have the key-rotation events) or `MessagingStack` (has the events, has no uid)?

The alternative resolution is equally a planner call: **amend EARS-FB-17** to the
publisher-only shape `E11-T04`/`E11-T05` used, so the criterion honestly describes
what E11 ships, and hand the wiring to whichever epic builds the first consumer.

Either way the decision precedes the code, which is why this is filed `blocked` /
`owner_agent: planner` rather than as a scoped fix.

## Regression test (write it first, once the direction is decided)
A test at the composition root — not at `DeviceDirectoryService` — asserting that
building the real app graph and completing a sign-in results in a
`directory/$deviceId` write through a captured seam. It must fail on today's code
(no write is ever attempted) and pass after. A test that constructs
`DeviceDirectoryService` directly cannot catch this class of defect and is what
allowed it through T06's own review.

## What this fix does NOT do
- Does **not** wire `lookupDevice` into `E07`'s `DriftSignalProtocolStore` or
  `E06-T07`'s `PrekeyExchange` — those remain the consumers' own tasks, per
  `E11-T06` §4 and `ADR-0008` Consequences. This is about the *publisher* only.
- Does **not** change `database.rules.json`, the `directory` node's shape, or its
  allowed-field set.
- Does **not** add polling, a scheduled republish, or a second driver — the
  one-tick invariant (`E08-T06`/`E10-T08`) still binds whatever wiring is chosen.
- Does **not** resolve `E11-B02` (the identity-consistency gap in `lookupDevice`),
  which is a separate defect on the read path with its own regression test.
- Does **not** give `DeviceRevocationService` or `RelationshipSyncService` a
  production caller — those are disclosed deferrals (`OQ-E11-5`, `E11-T05` §4),
  not defects.
