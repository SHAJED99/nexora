# E11-T05 · Own-account relationship-config mirror

## 1. Goal
Let a user's trust/block decision about one peer device show up on their
*other* devices — `FR-TRUST-007`'s "relevant relationship configuration
shall synchronize", read narrowly (per `ADR-0008`) as **a user's own
devices agreeing with each other**, not one account learning another
account's relationship state.

## 2. Business logic
- **`ADR-0008`'s declined-option-3 boundary is binding here.** This task
  does **not** read or write anything under another account's uid. It
  mirrors `users/$uid/relationships/$peerDeviceId` — `$uid` is always the
  authenticated caller's own account. Cross-account relationship exchange
  (`OQ-E09-T02-1`'s original ask) stays an accepted, permanent limitation
  per `ADR-0008`'s Consequences.
- **The merge rule already exists and must be reused, not reinvented.**
  `ConflictResolver.resolveTrust(RelationshipState a, RelationshipState b)`
  (`conflict_resolver.dart:60`) picks the more restrictive of two states
  (`_trustRestrictiveness`, more restrictive wins) — this is `FR-MSG-007`'s
  own ordering and is exactly the semantics two of a user's devices
  disagreeing about a peer need: if one device already blocked someone,
  a second device that never heard about it must not un-block them by
  silently overwriting. `E06`'s retro named this function as built and
  uncalled since E05; this task is one of its two intended callers
  (`E11-T04` is the other, for revocation).
- **Local-first, same shape as `E11-T04`.** A relationship change is
  authoritative locally the instant `RelationshipRepository.upsert` returns;
  the Firebase mirror is best-effort and never blocks or reverses a local
  decision.
- **`RelationshipState` has four values** (`trusted`, `allowed`, `unknown`,
  `blocked`) — the Firebase field is the enum's `.name` string, per
  `docs/conventions.md` §Enums, never an index.

## 3. What this task does
- Adds `users/$uid/relationships/$peerDeviceId` to the Firebase schema — the
  path in `firebase_paths.dart`, the allowed-field set (`state:String`,
  `updatedAt:int(ServerValue)`) in `firebase_boundary.dart`, the
  `.validate` rules in `database.rules.json` restricting `state` to the
  four known enum-name strings, and the row in `docs/firebase-schema.md`
  (status `live`, superseding its `reserved` placeholder from `E11-T01`).
- Adds `RelationshipSyncService`:
  - `push(uid, deviceId, RelationshipState state)` — writes locally via
    `RelationshipRepository.upsert` first, then best-effort mirrors to
    Firebase; a Firebase failure is logged and swallowed, never surfaced to
    the caller of a trust/block action.
  - `pull(uid)` — reads every `relationships/$peerDeviceId` node under the
    caller's own uid, merges each remote `state` with the corresponding
    local one through `ConflictResolver.resolveTrust`, and persists the
    merged result via `RelationshipRepository.upsert` only when it differs
    from what is already stored.
- Extends `firebase_rules_test.dart` with the new node's assertions
  (own-uid read/write only; a peer's uid must not be able to read or write
  `users/<other-uid>/relationships/...`).

## 4. What this task does NOT do  ← the scope fence
- **Does NOT let one account read another account's relationships.** Every
  path this task touches is `users/$uid/relationships/...` for the caller's
  own `$uid`. `ADR-0008`'s directory (`E11-T06`) is a completely separate
  node (`directory/$deviceId`) with different data and different rules;
  this task does not touch it.
- **Does NOT call `ConflictResolver` for revocation** — that is `E11-T04`,
  already built and merged before this task starts (`depends_on`).
- **Does NOT decide *when* to call `push`/`pull`.** Wiring these into
  `EvaluateConnectionRequestUseCase` or the Devices/Trust screen's actions
  is a caller's decision outside this task's `files:` fence — this task
  ships the service, proven, with no caller yet, the same shape `E11-T04`
  shipped `isRevoked` in.
- **Does NOT add a UI, a settings toggle, or a sync-status indicator.**
- **Does NOT change `RelationshipState`'s values, `_trustRestrictiveness`'s
  ordering, or any file under `lib/features/trust/domain/`.**
- **Does NOT touch `firebase_metadata_service.dart` or the revocation
  node/table** — those are `E11-T03`/`E11-T04`'s files.

## 5. Contract

### Data — the Realtime Database node
| Path | Fields | Notes |
|---|---|---|
| `users/$uid/relationships/$peerDeviceId` | `state:String` (one of `trusted`/`allowed`/`unknown`/`blocked`), `updatedAt:int(ServerValue)` | own-uid only; `$peerDeviceId` is the remote device id, not a foreign uid |

### Functions
```yaml
- signature: "RelationshipSyncService.push(String uid, String deviceId, RelationshipState state) -> Future<void>"
  params: { uid: "the caller's own Firebase Auth uid", deviceId: "the peer device id this relationship is about" }
  returns: "void; never throws — a Firebase failure is logged and swallowed"
  purpose: "mirror a local trust/block decision to the account's other devices, best-effort"

- signature: "RelationshipSyncService.pull(String uid) -> Future<void>"
  params: { uid: "the caller's own Firebase Auth uid" }
  returns: "void; merges every remote relationship into local storage via ConflictResolver.resolveTrust"
  purpose: "reconcile relationship state written by another of this account's devices"
```

### External services & flags
Firebase Realtime Database, same instance as `E11-T01`/`T04`. No new
package, no new permission.

## 6. Risks
- **Merge direction matters.** `resolveTrust(a, b)` must be called with
  *(local, remote)* or *(remote, local)* consistently — since the function
  is commutative in outcome (more-restrictive wins regardless of argument
  order) this is lower-risk than `E11-T04`'s cursor-argument-order risk, but
  test it explicitly rather than assuming commutativity without proof.
- **`pull` must not thrash writes.** Only call `RelationshipRepository.upsert`
  when the merged state actually differs from the stored one, or every
  `pull` call generates a spurious `updatedAt` bump and a redundant
  `push`-shaped write-amplification loop if a caller ever chains the two.
- A device with no local relationship for a peer that Firebase has one for
  must merge as if the local side were `unknown` (the domain default), not
  crash on a missing row.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-FB-14**: WHEN a relationship's state changes locally, the system
  SHALL persist it locally first and best-effort mirror it to the account's
  own Firebase relationship node, without blocking or reversing the local
  change on a Firebase failure. (FR-TRUST-007)
- **EARS-FB-15**: WHEN a remote relationship state disagrees with the local
  one for the same peer device, the system SHALL resolve to the more
  restrictive of the two via `ConflictResolver.resolveTrust`. (FR-MSG-007)
- **EARS-FB-16**: The system's Firebase security rules SHALL grant read and
  write on `users/$uid/relationships/*` only to the authenticated owner of
  `$uid`. (FR-FB-001, ADR-0005, ADR-0008)
