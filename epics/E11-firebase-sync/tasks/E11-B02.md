# E11-B02 · a directory entry can carry two different identities and `lookupDevice` won't notice

## The defect

`directory/$deviceId` carries the device's identity key **twice**, in two
independently-decoded fields:

- `identityPublicKey` — the bare serialized `IdentityKey`
- `prekeyBundle` — a `PreKeyBundleCodec` blob which *also* contains an identity key
  (`prekey_bundle_codec.dart:70`, `bundle.getIdentityKey().serialize()`)

`publish` derives both from one bundle, so an honest publisher is always
self-consistent:

```dart
// lib/core/services/device_directory_service.dart:164-165
final serializedBundle = base64Encode(PreKeyBundleCodec.serialize(bundle));
final identityPublicKey = base64Encode(bundle.getIdentityKey().serialize());
```

`lookupDevice` decodes the two fields **independently and never compares them**:

```dart
// lib/core/services/device_directory_service.dart:223-230
final preKeyBundle   = PreKeyBundleCodec.deserialize(base64Decode(prekeyBundleRaw));
final identityPublicKey = IdentityKey.fromBytes(base64Decode(identityPublicKeyRaw), 0);
...
return DirectoryEntry(identityPublicKey: identityPublicKey, preKeyBundle: preKeyBundle, ...);
```

The bytes being decoded come from `directory/$deviceId` — a node readable *and*
writable across accounts by design (`ADR-0008` option 2). `database.rules.json`
cannot help here: RTDB `.validate` can check that both fields are strings of
bounded length (`database.rules.json:90-95`) but cannot parse base64 or a codec
blob to check that two opaque strings agree. This is exactly the check that has to
live in the client.

The class doc comment asserts the invariant that the code does not enforce
(`device_directory_service.dart:82-86`): "decoded from the same bytes
`[PreKeyBundleCodec]` would also carry inside `[preKeyBundle]`". True of `publish`;
merely hoped-for on read.

**Why it matters.** `ADR-0008` created this node for exactly two consumers, and they
read *different halves* of it:

- `E07`'s TOFU replacement resolves "is this the identity I trust" from
  `entry.identityPublicKey` — `DirectoryEntry`'s own doc comment says so verbatim
  ("a caller resolving 'is this the identity I already trust' (`E07`'s own future
  consumer) needs it without first deserializing the whole prekey bundle").
- `E06-T07`'s prekey fallback establishes a Signal session from `entry.preKeyBundle`.

So a forged entry makes one consumer *verify* identity A while the other
*establishes a session keyed to* identity B. That is an identity-substitution
primitive handed to the consumers, and it defeats the precise gap `ADR-0008` was
written to close. Combined with `OQ-E11-T06-1` (first-publish squatting), an
attacker who claims an unpublished device id can serve exactly this entry.

This is the E11 instance of the pattern the sweep was asked to look for. Note the
*write* side is clean: `ownerUid` is anchored to Firebase's server-authenticated
`auth.uid` by `database.rules.json:88`, and `publish`'s caller-supplied `uid` is
rejected server-side if it lies — verified independently. The unauthenticated
claim being trusted here is not the owner, it is the **binding between the two key
fields inside the payload**.

## Repro
Reviewer's own probe (`test/zz_reviewer_probe2_test.dart`, scratch, not committed):

1. Build two independent identities A and B (`IdentityService.ensureLocalIdentity`
   + `ensureSignedPreKey` + `replenishOneTimePreKeys` against two in-memory
   `AppDatabase`s). Assert their identity keys differ.
2. Construct a forged raw node:
   ```dart
   {
     'identityPublicKey': base64Encode(bundleA.getIdentityKey().serialize()),
     'prekeyBundle'    : base64Encode(PreKeyBundleCodec.serialize(bundleB)),
     'ownerUid'        : 'attacker-uid',
   }
   ```
3. Return it from the `readDirectoryData` seam and call
   `lookupDevice('victim-device-id')`.

## Expected
`lookupDevice` treats a self-inconsistent entry the same way it already treats a
malformed one — log and return `null`. The file's own stated policy
(`device_directory_service.dart:237-239`) is that "a malformed entry (bad base64,
undecodable codec bytes) is treated as 'not found' … the caller cannot do anything
more useful with a half-decoded entry than with a missing one." An entry asserting
two different identities is strictly worse than half-decoded, and the same
reasoning applies with more force.

## Actual
The entry is accepted. The probe printed:

```
identityPublicKey field  : BeJoHmGilPheMbS7KaCgk9RNJ6nlUPiPnx+5hvjWoXZn
prekeyBundle identity key: BeMK5kdFTek99EH72NyZgImwkMVb7QQcyTgjbfDgipBg
```

`lookupDevice` returned a non-null `DirectoryEntry` from which two different
identities can be read. No log, no signal to the caller.

## Severity
**S2** — the identity-attestation function of the one cross-account node is
unsound, and a consumer has no workaround short of performing the check itself
(which is precisely the mistake the directory exists to prevent them from having
to get right). Not S1: `E11-B01` means the node is never populated in production
and there is no consumer wired yet, so this is not reachable in the shipped build
today. That is priority information; the soundness of the code path is unchanged.

## Fix direction
In `lookupDevice`, after both decodes succeed, compare
`identityPublicKey.serialize()` against `preKeyBundle.getIdentityKey().serialize()`
byte-for-byte; on mismatch log a distinct reason
(e.g. `firebase.device_directory_lookup_identity_mismatch`) and return `null`,
matching the existing malformed-entry path. Constant-time comparison is not
required — both values are public.

Prefer this over "trust the bundle and drop the bare field": `DirectoryEntry`'s
two-field shape is deliberate and documented, and silently preferring one source
would leave the same ambiguity for the next reader.

## Regression test (write it first)
The probe above, committed as a real test: assert `lookupDevice` returns `null` for
a mismatched entry, and — as the falsification control — that it still returns a
populated `DirectoryEntry` for a genuinely consistent one, so the test cannot pass
by rejecting everything. It must fail on today's code (which returns a non-null
entry) and pass after.

## What this fix does NOT do
- Does **not** address `OQ-E11-T06-1` (first-publish squatting). A consistent entry
  published by a squatter is still a squatter's entry; that remains the consuming
  task's problem, per its recorded owner.
- Does **not** wire any consumer (`E07` TOFU, `E06-T07` fallback) — still out of
  E11's fence per `E11-T06` §4.
- Does **not** fix `E11-B01` (the publisher is never constructed) — separate defect,
  separate owner, and this fix is worth making regardless of how B01 is resolved.
- Does **not** change `database.rules.json`, the node's allowed-field set, or
  `PreKeyBundleCodec`'s wire format or version.
- Does **not** add single-use consumption semantics for one-time prekeys
  (`OQ-E11-T06-2`) or a delete path (`OQ-E11-T06-3`).
