# E11-T01 · Firebase data-boundary schema, path registry and wrapper reconciliation

## 1. Goal
Give the project **one** written, machine-checkable definition of everything
Firebase is allowed to hold — and make the two wrappers that already write to
Firebase go through it, so `FR-FB-002` stops being a promise in a comment and
starts being a guard that fails a test.

## 2. Business logic

- **`FR-FB-001`** enumerates exactly what Firebase *may* store: authentication
  information, user identity, device registry metadata, device public identity
  information, trust metadata, block metadata, user configuration, revocation
  information, push notification information, application version policy. That
  list is closed — nothing outside it goes to Firebase.
- **`FR-FB-002`** is the epic's non-negotiable constraint (`EARS-FB-1`):
  never message plaintext, voice recordings, call recordings, private keys,
  session keys, or permanent private location history. `FR-LOC-004` restates
  the location half; `FR-SEC-002` restates the plaintext half.
- **`NFR-PRIV-001`**: central services store only what authentication, device
  management, synchronization, configuration, security and notifications
  actually require. A field that is merely "useful later" fails this.
- **Reconciliation, not replacement** (epic §Risks): two wrappers already
  exist and both work. `FirebaseMetadataService` (E01-T02) writes
  `users/$uid/devices/$deviceId`; `SyncCursorService` (E05-T04) writes
  `users/$uid/sync_cursors/$writerDeviceId/$conversationId/$aboutDeviceId`.
  Both invented their own path string and their own copy of the
  best-effort/timeout/catch-and-log pattern. This task centralises **the paths
  and the allowed-field sets**; it deliberately does not rewrite their
  behaviour.
- **`ADR-0005`**: Firebase stays a thin account pointer. Nothing here may feed
  back into local device identity or session state, and a Firebase failure
  must never affect an offline-first local flow.
- **`ADR-0008` (✅ accepted, option 2)**: every path this task declares
  lives under `users/$uid/…`. The schema doc **reserves** the cross-account
  `directory/` subtree for `E11-T06`, which builds it; this task declares
  no rules or code for it.

## 3. What this task does

- Writes **`docs/firebase-schema.md`** — the complete Realtime Database tree
  the project is allowed to use: every node, its owner (task/epic), its exact
  field list with types, its `FR-FB-001` justification clause, and its status
  (`live` · `reserved` · `not-decided`). Reserved slots are declared for
  `push notification information` and `application version policy` — the two
  `FR-FB-001` categories E11 does **not** own the behaviour of (see §4).
  The doc also carries the forbidden list verbatim from `FR-FB-002`.
- Adds **`lib/core/services/firebase_paths.dart`** — pure functions producing
  every Realtime Database path the app uses. No `FirebaseDatabase` import, no
  I/O, trivially testable. The two existing services call these instead of
  building path strings inline.
- Adds **`lib/core/services/firebase_boundary.dart`** — the allowed-field
  registry: for each node kind, the closed set of permitted keys, plus
  `assertAllowedFields(FirebaseNodeKind, Map<String, Object?>)` which throws
  on any key not in the set. Both services route their write payload through
  it immediately before `.set()`.
- Rewires `FirebaseMetadataService.writeDeviceMetadata` and
  `SyncCursorService.writeCursorData`/`readCursorData` to use the path
  registry and the boundary guard. **The RTDB paths produced must be
  byte-identical to today's** — this is a refactor, not a migration.
- Extends both services' existing tests for the new seam, and adds tests for
  the two new files.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT change `database.rules.json`.** The structural `.validate`
  enforcement of this schema is `E11-T02`, deliberately separated so the
  schema is agreed before rules are written against it.
- **Does NOT add, remove or rename a single Firebase field or path.** If the
  schema doc and the code disagree, the *code* is the current truth and the
  doc records it as-is; propose the change as an Open Question. A refactor
  that quietly "improves" a live path breaks every device already writing it.
- **Does NOT fix `createdAt`/`lastSeenAt` always being equal** (E01-T02's
  carried review note) — that is `E11-T03`, which owns the semantics change.
- **Does NOT implement the reserved push-token or version-policy nodes.**
  They are declared in the schema and reserved in prose only; no client code,
  no rules, no reads, no writes. Their behaviour belongs to E10/E14
  (`OQ-E11-2`).
- **Does NOT introduce a shared base class, mixin or "FirebaseClient"
  abstraction over the two services.** Tempting, and wrong here: they have
  different lifetimes, different owners and different test seams, and the
  duplication that matters (paths, allowed fields) is exactly what this task
  centralises. Extracting the retry/timeout/log pattern too is a bigger,
  separately-reviewable change.
- **Does NOT touch `lib/features/messaging/domain/conflict_resolver.dart`**,
  the Drift schema, or anything under `lib/features/trust/`.
- **Does NOT add a dependency.**

## 5. Contract

### Data — the Realtime Database tree this task declares

`docs/firebase-schema.md` must document exactly this and nothing more:

| Path | Status | Fields | `FR-FB-001` clause | Owner |
|---|---|---|---|---|
| `users/$uid/devices/$deviceId` | live | `deviceId:String`, `createdAt:int(ServerValue)`, `lastSeenAt:int(ServerValue)`, `platform:String` | device registry metadata | E01-T02 |
| `users/$uid/sync_cursors/$writerDeviceId/$conversationId/$aboutDeviceId` | live | `localDeviceId:String`, `remoteDeviceId:String`, `conversationId:String`, `lastConfirmedSequenceNumber:int`, `updatedAt:int` | synchronization metadata (`NFR-PRIV-001`) | E05-T04 |
| `users/$uid/devices/$deviceId/revocation` | reserved | — declared by `E11-T04` | revocation information | E11-T04 |
| `users/$uid/relationships/$peerDeviceId` | reserved | — declared by `E11-T05` | trust metadata, block metadata | E11-T05 |
| `users/$uid/push/$deviceId` | reserved (no owner) | — | push notification information | ⏳ `OQ-E11-2` |
| `config/version_policy` | reserved (no owner) | — | application version policy | ⏳ `OQ-E11-2` |
| `directory/$deviceId` | reserved | — declared by `E11-T06` | device public identity information | `E11-T06` (`ADR-0008` accepted, option 2) |

Forbidden anywhere in the tree, restated verbatim from `FR-FB-002`: message
plaintext · voice recordings · call recordings · private keys · session keys ·
permanent private location history.

### Functions

```yaml
- signature: "FirebasePaths.device(String uid, String deviceId) -> String"
  params: { uid: "Firebase Auth account uid", deviceId: "local device identity id (E01-T01)" }
  returns: "String — 'users/<uid>/devices/<deviceId>'"
  purpose: "the one place the device-registry path is spelled"

- signature: "FirebasePaths.syncCursor(String uid, String writerDeviceId, String conversationId, String aboutDeviceId) -> String"
  params: { writerDeviceId: "device that produced the cursor", aboutDeviceId: "device the cursor tracks progress against" }
  returns: "String — 'users/<uid>/sync_cursors/<writer>/<conversation>/<about>'"
  purpose: "replaces SyncCursorService._cursorPath, argument order preserved exactly"

- signature: "FirebaseBoundary.allowedFields(FirebaseNodeKind kind) -> Set<String>"
  params: { kind: "the node being written" }
  returns: "Set<String> — the closed permitted key set for that node"
  purpose: "the FR-FB-001 allow-list, in one place, greppable"

- signature: "FirebaseBoundary.assertAllowedFields(FirebaseNodeKind kind, Map<String, Object?> data) -> void"
  params: { data: "the exact map about to be passed to DatabaseReference.set()" }
  returns: "void — throws FirebaseBoundaryViolation naming the offending key(s)"
  purpose: "EARS-FB-1's runtime half: an unlisted key never reaches the wire"
```

`FirebaseNodeKind` is an enum (`device`, `syncCursor`), stored/compared by
`.name` per `docs/conventions.md` §Enums. `FirebaseBoundaryViolation` extends
`Error` (a programming error, not a runtime condition) and its message must
name the kind and every offending key — never the *values*, which is how a
guard against leaking plaintext ends up logging plaintext.

### External services & flags
Firebase Realtime Database, project `nexora-b3a97`, instance
`nexora-b3a97-default-rtdb`. No new service, no new env var, no new flag.
Note from `E01-T02` §9: provisioning a *first* RTDB instance needs the
Firebase console — irrelevant here, the instance exists.

## 6. Risks

- **The path strings are live data.** Devices in the field already wrote to
  today's paths. Diff the produced strings character by character; the
  `syncCursor` argument order (`writer, conversation, about`) is easy to
  transpose and the bug is silent — a read simply returns null forever.
- `assertAllowedFields` must run **before** `.set()`, not inside the existing
  `try`/`catch`, or a boundary violation gets swallowed as "just another
  Firebase error" and logged instead of failing the build's tests.
- `ServerValue.timestamp` is a sentinel `Map`, not an `int`. The guard checks
  *keys*, not value types — don't accidentally reject it.
- `sync_cursor_service.dart` belongs to E05 and has a live test suite. Run it;
  don't reshape its public API to make the refactor tidier.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-FB-1**: The system SHALL NOT write message plaintext, voice/call recordings, private/session keys, or location history to Firebase. (FR-FB-002)
- **EARS-FB-2**: WHEN any Firebase write is prepared, the system SHALL reject a payload containing a key outside that node's `FR-FB-001` allow-list, before the write is issued. (FR-FB-001, FR-FB-002)
- **EARS-FB-3**: The system SHALL produce every Realtime Database path from a single path registry, and those paths SHALL be identical to the paths in use before this task. (FR-FB-001)

### Tests
- `test_EARS_FB_1_no_forbidden_field_is_writable` → for each node kind,
  asserts that a payload carrying `plaintext`/`privateKey`/`sessionKey`/
  `latitude` throws `FirebaseBoundaryViolation`.
- `test_EARS_FB_2_unknown_key_rejected_before_write` → a fake
  `writeDeviceMetadata` seam records whether `.set()` was reached; asserts it
  was not.
- `test_EARS_FB_2_allowed_payload_passes` → today's exact four-field device
  payload and five-field cursor payload pass unchanged.
- `test_EARS_FB_3_paths_unchanged` → asserts the two live path strings
  literally, with hard-coded expected values (not by calling the same
  function twice).

   path in the code appears in the doc, and vice versa.
