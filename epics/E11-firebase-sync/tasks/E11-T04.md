# E11-T04 · Device revocation records and own-account propagation

## 1. Goal
Let a user revoke one of their own devices and have every *other* device on
that account learn about it — the "revocation information" half of
`FR-FB-001`, which no epic has built and three have assumed exists.

## 2. Business logic

- **`FR-FB-001`** permits Firebase to hold revocation information. This task
  is the first and only thing in the project that writes it.
- **`FR-MSG-007`** is binding on the merge: *REVOKED > ACTIVE*. A conflict
  between "this device says revoked" and "that device says active" resolves
  to revoked, always, in both directions. `ConflictResolver.resolveRevocation`
  (E05-T05, `a || b`) already implements exactly this and **must be the
  function called** — this task is one of the callers `E06`'s retro recorded
  as missing (*"`ConflictResolver` has no caller … Owner: E11"*).
- **`FR-AUTH-004`**: devices on one account are independent. Revocation is
  therefore *account-scoped state about a device*, not a change to that
  device's own local identity — a revoked device is not asked to cooperate,
  and must not be trusted to.
- **Revocation is monotonic and irreversible in v1.** There is no un-revoke.
  A cleared revocation is a security downgrade, and `FR-MSG-007`'s ordering
  makes it unrepresentable anyway: any device still holding `revoked` would
  immediately re-win the merge. If un-revoke is wanted, that is a new
  requirement, not a flag.
- **Scope is own-account only.** A *peer* learning that someone else's device
  was revoked requires a cross-account read — decided by `ADR-0008`
  (accepted, option 2) and built by `E11-T06`, not this task. This task
  writes only `users/$uid/devices/$deviceId/revocation`, never
  `directory/$deviceId`.

## 3. What this task does

- Adds the `device_revocations` Drift table (schema **v15**, additive) —
  local, authoritative-on-this-device record of which device ids this account
  has revoked, plus when and where the knowledge came from.
- Adds `users/$uid/devices/$deviceId/revocation` to the Firebase schema: the
  path in `firebase_paths.dart`, the allowed-field set in
  `firebase_boundary.dart`, the `.validate` rules in `database.rules.json`,
  and the row in `docs/firebase-schema.md` (status `live`).
- Adds `DeviceRevocationService`:
  - `revoke(uid, deviceId)` — writes locally first, then best-effort to
    Firebase (local-first: a revocation that only succeeded remotely is a
    revocation this device forgets on next launch);
  - `pullRevocations(uid)` — reads the account's device nodes, merges each
    remote revocation flag with the local one through
    `ConflictResolver.resolveRevocation`, and persists the merged result;
  - `isRevoked(deviceId)` — the single local query point later epics call.
- Extends `firebase_rules_test.dart` with the new node's assertions.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT enforce revocation anywhere.** Nothing in this task blocks a
  session, tears down a Signal session, refuses a connection, or deletes a
  key. `isRevoked` is a query with no callers yet, deliberately — enforcement
  spans E03's crypto and E04's transport and is not sharded (`OQ-E11-5`).
  Building half an enforcement path is worse than none: it reads as protection
  and isn't.
- **Does NOT propagate revocation to peers or other accounts.** Cross-account
  reads are `ADR-0008` (`OQ-E11-1`). No `directory/` node, no peer lookup.
- **Does NOT implement un-revoke** (§2).
- **Does NOT add a revocation UI, settings toggle, or device-list screen.**
- **Does NOT touch `firebase_metadata_service.dart`** — `E11-T03` owns that
  file this wave, and the revocation node is written by its own service.
- **Does NOT drop, rename, or backfill any existing column.** Migration is
  additive only, per `docs/conventions.md` §Schema migrations and
  `FR-VER-003`.
- **Does NOT call `ConflictResolver` for trust state** — that is `E11-T05`.

## 5. Contract

### Data — Drift migration `v15` 🧍 **human gate `db_schema_migration`**

```dart
@DataClassName('DeviceRevocationRow')
class DeviceRevocations extends Table {
  TextColumn get deviceId => text()();
  DateTimeColumn get revokedAt => dateTime()();
  TextColumn get source => text()();          // 'local' | 'firebase' (.name, per conventions)
  @override Set<Column> get primaryKey => {deviceId};
}
```

Additive: `schemaVersion` 14 → 15, `onUpgrade` gains
`if (from < 15) await m.createTable(deviceRevocations);`, `onCreate` needs no
seed row. Reversible in the sense that matters: nothing existing is altered,
so a downgrade loses only this table. **No backfill.**

### Data — Firebase node `users/$uid/devices/$deviceId/revocation`

| Field | Type | Meaning |
|---|---|---|
| `revokedAt` | int (`ServerValue.timestamp` on write) | when the revocation was recorded |
| `revokedByDeviceId` | String (≤128) | which of the account's devices issued it |

`FR-FB-001` clause: *revocation information*. Rules: both fields required,
`$other` denied, `.read`/`.write` still `auth.uid === $uid` only.
**Note for `E11-T02`'s `hasChildren` rule on the parent `devices/$deviceId`
node:** `revocation` is a new *child* of that node — confirm the parent's
`$other: {.validate: false}` is amended to permit exactly this child, or the
write fails. This is the first real test of that rule and it will bite.

### Functions

```yaml
- signature: "DeviceRevocationService.revoke(String uid, String deviceId) -> Future<void>"
  params: { deviceId: "the device being revoked — may be this device or another of the account's" }
  returns: "Future<void> — completes after the local write; the Firebase write is best-effort and never throws"
  purpose: "the only way a revocation is created"

- signature: "DeviceRevocationService.pullRevocations(String uid) -> Future<int>"
  params: { uid: "Firebase Auth account uid" }
  returns: "int — number of local rows changed; 0 on any failure/offline (never throws)"
  purpose: "merge remote revocations into local state via FR-MSG-007 precedence"

- signature: "DeviceRevocationService.isRevoked(String deviceId) -> Future<bool>"
  params: { }
  returns: "bool — true iff a local revocation row exists"
  purpose: "the one local query point; no callers in this task, by design (§4)"
```

Firebase Realtime Database, same instance. No new dependency. Rules change is
**not deployed** by this task (same as `E11-T02` §4) — human step.

## 6. Risks

- **`pullRevocations` must never un-revoke.** `resolveRevocation(a, b) = a || b`
  gives that for free *only if* a missing remote node is read as `false`, not
  as "unknown → overwrite". A read failure must leave local state untouched;
  write the test for the offline case first.
- The parent-node `hasChildren` rule (§5) is the most likely reason this task
  fails at deploy rather than in tests — the structural test only checks what
  the rules file says, not what the server does (`OQ-E11-T02-1`).
- `database.dart` is the highest-traffic shared file in the repo. Touch only
  the `@DriftDatabase` table list, `schemaVersion`, and one `onUpgrade` block.
  Regenerate `database.g.dart` with `dart run build_runner build` — never hand-
  edit it.
- Local-first ordering matters: if the Firebase write is awaited *before* the
  local insert and the app is killed in between, the account has a revocation
  the revoking device does not know about.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-FB-10**: WHEN a device is revoked, the system SHALL record the revocation locally and SHALL best-effort publish it to the account's Firebase device registry. (FR-FB-001)
- **EARS-FB-11**: WHEN local and remote revocation state for one device disagree, the system SHALL resolve to revoked. (FR-MSG-007 — REVOKED > ACTIVE)
- **EARS-FB-12**: IF the Firebase read or write fails or the device is offline, THEN the system SHALL keep the local revocation state unchanged and complete without throwing. (ADR-0005, NFR-REL-001)
- **EARS-FB-13**: The revocation node SHALL carry only `revokedAt` and `revokedByDeviceId`, and the security rules SHALL reject any other field. (FR-FB-001, FR-FB-002)
