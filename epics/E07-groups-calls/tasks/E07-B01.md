# E07-B01 · A group row's tap lands on a screen that cannot do groups

## The defect

`E07-T08` made group rows tappable and routed them to `/chat/:conversationId`
with the group id — exactly what its own §3 Contract instructed, and the route
is registered (`lib/app/routes.dart:44`), so the journey is live in the app:

```dart
// lib/features/conversations/presentation/conversations_view.dart:458
onTap: () => controller.openConversation(row.conversationId),
// -> conversations_controller.dart:377  Get.toNamed('/chat/$conversationId');
```

The destination treats the conversation id as a **peer device id**:

```dart
// lib/features/chat/presentation/chat_controller.dart:119-122
/// The peer's device id — this schema's only conversation shape is 1:1,
/// with `conversationId == peerDeviceId` ...
String get _peerDeviceId => conversationId;
```

so `send()` runs `ensureSession(<groupId>)` and
`_send.call(<groupId>, <groupId>, bytes)` — a 1:1 X3DH handshake and a
Double-Ratchet send addressed to a device id that is really a group id.

`E07-T08` §4 correctly says it does **not** build the group thread view
(that is GAP-020, still gated on `OQ-E07-13`). The gap is that the tap
shipped anyway.

## Repro
1. From a clean install, have at least one group with ≥1 message
   (`groups` + `group_members` + a `messages` row on the group id).
2. Open `/conversations`. The group appears under the `Groups` heading.
3. Tap the group row.
4. Type any text and send.

## Expected
FR-COMM-002 — group communication via text. Either the group thread renders
group messages and sends via the group path, or the affordance does not
exist yet. A tap that navigates must not land on a screen that structurally
cannot serve the conversation it was given.

## Actual
Reviewer's own probe against the real `ChatController` + `MessagingStack`
(scratch, not committed):

```
PROBE C messages rendered=1 error=""
PROBE C sendError="Could not send this message. Try again."
PROBE C msg={id: m1, conversation_id: g:team, sender_device_id: device-a, delivery_state: accepted}
```

- The group's message rows **are** loaded into the thread, but decrypted by
  the 1:1 `CryptoService`, which holds no sender-key chain for them — so
  they render via the undecryptable-bubble path, not as their real content.
- `send()` fails closed (no message row, no relay packet — **no forged
  frame is emitted and nothing leaks**, which is why this is S2 and not S1),
  but reports the *generic retryable* copy: "Could not send this message.
  Try again." Retrying can never succeed. The user is told to retry a thing
  that is structurally impossible.

## Severity
**S2** — a major function (opening a group) is broken with no workaround,
and the error text actively misleads. Not S1: fails closed, no data loss,
no confidentiality break.

## Fix direction (for the planner — this is a product call, not a code call)
Two honest options; **the human/planner picks, the fixer does not**:
- **(a)** Make the group row non-navigating until GAP-020 ships. Cheapest,
  and consistent with rule 2 (do not invent a journey the design has not
  approved) — but a visibly inert row.
- **(b)** Ship a minimal group thread: render via `GroupCryptoService` and
  send via `MessagingStack.sendGroupMessage` (both already built and wired,
  E07-T06/T14). This is GAP-020's build, which is gated on `OQ-E07-13`
  (blocked-member rendering) — so it needs that question resolved first.

Either way an honest, non-retryable error string is required if any group
send path can still fail.

## What this fix does NOT do
- Does **NOT** resolve `OQ-E07-13` (whether a blocked member's messages are
  dropped, hidden or placeholdered in a group thread) — that is a product
  question and stays the human's.
- Does **NOT** build per-sender attribution lines or membership event lines
  beyond whatever the chosen option strictly needs — the rest of GAP-020
  stays prospective.
- Does **NOT** add group creation or management affordances (GAP-018/019).
- Does **NOT** change `ConversationRepository`'s projection or any file
  under `lib/core/`.
- Does **NOT** widen `ChatController` to a general multi-party controller —
  only whichever of (a)/(b) is chosen.
