# E07-T12 · E07 design gap pass

## 1. Goal
Give this epic's undesigned journeys — creating a group, managing a group,
and the call surfaces — real, human-approvable derived contracts, so the
frontend tasks that build them are shardable at all (rule 2: no contract,
no frontend task).

## 2. Business logic
- **Rule 2 in both directions.** A journey the design omits is *derived*
  from the spec, marked `source: derived`, built from the existing
  design's own primitives, and 🧍 human-approved. It is never invented
  freely and never silently dropped. `E06-T13` is the worked precedent —
  including its most important behaviour: when nothing derivable exists,
  the honest output is a question (GAP-017/PTT), not a proposal.
- **The gap entries themselves are written by the planner at sharding**
  (GAP-018…GAP-022, appended to `design/gaps.md` in the same pass that
  produced this task). This task's job is the *contracts* those approved
  gaps imply, plus any further gaps the contract-writing surfaces.
- **Derivation sources, named per screen** — every token, spacing value and
  component shape must come from a screen that already has a measured
  golden, and the contract must say which:
  - group create / manage → `conversations.md` (list rows, section
    headings, search field) + `devices.md` (the per-device row with a
    trailing action, the closest existing "manage a list of peers" shape)
  - call surfaces → `chat.md` (header with peer identity, the 24px icon
    button treatment) + `dashboard.md` (the status-card treatment for
    connection state, which GAP-014 already borrowed once)
- **No new visual language.** If a required element cannot be built from an
  existing primitive — as PTT could not — that is a question with an owner,
  not an invention. Say so in the entry and stop.
- **This task self-approves nothing.** `L-process-002`'s standing rule: the
  `approved by:` lines stay bare, and `design_contract_approval` is the
  human's. `E06-T13`'s reviewer verified exactly this and it is checked
  again here.

## 3. What this task does
- Writes three hand-written, `source: derived` screen contracts in the same
  shape the generator produces (frontmatter, element checklist, verbatim
  copy, token table), each naming its derivation source per §2:
  - **`design/screens/group-create.md`** — name field, member picker over
    the trusted-contact list, create action, empty/loading/error states.
  - **`design/screens/group-manage.md`** — group name (editable by
    Owner/Admin per E07-T02's matrix), member list with role labels,
    per-member actions gated by that same matrix, leave/delete, and the
    **role-forbidden state** (a Member sees the list and no actions).
  - **`design/screens/call.md`** — the three coherent states of one
    surface: outgoing (ringing), incoming (accept/decline), in-call
    (duration, mute, hangup, connection quality), plus the failure state
    `NullCallMediaTransport` produces today.
- Reviews GAP-018…GAP-022 as written at sharding, corrects them against
  what contract-writing actually reveals, and adds any further gap the pass
  surfaces.
- Records, for each contract, the **route** it binds to and adds it to
  `docs/routes.md`'s pending list — without registering a route in code
  (that is the building task's).

## 4. What this task does NOT do
- Does **NOT** build any screen, controller, binding or route. Docs only.
- Does **NOT** approve its own gaps or contracts. Every `approved by:` line
  ships bare (`L-process-002`).
- Does **NOT** hand-edit any *generated* contract's tables
  (`design-fidelity` Rule 1) — `conversations.md`, `chat.md`,
  `dashboard.md`, `devices.md` are read-only inputs here.
- Does **NOT** loosen `design/thresholds.yaml` (Rule 2 — a 🧍 gate of its
  own).
- Does **NOT** propose a PTT contract. `GAP-017` is decided-and-parked and
  `E07-T13` owns reopening it once `OQ-E07-3` is answered. Proposing one
  here would answer a human's open question by drawing it.
- Does **NOT** design group *thread* rendering beyond naming the gap
  (GAP-020) — per-sender attribution and membership-event lines need
  `OQ-E07-10`'s blocked-in-group answer first.
- Does **NOT** extract a golden. Derived screens get their golden extracted
  **after** they are built (`design-fidelity` §3's note), not before.

## 5. Contract

### UI
The three contracts must each carry, in the generated shape:
`id` · `impl_path` · **`source: derived`** · `states` · `viewports:
[390x844]` (matching every existing contract) · an element checklist with
role, copy and measured-or-derived style per element · the verbatim copy
list · the token table, **every value of which already appears in the
source screen's own token table** — an off-palette value in a derived
contract is an invented value.

Each contract ends with a `## Derivation` section naming: the source
screen(s), the specific elements borrowed, and the spec id each screen
serves (`FR-GROUP-002` for manage, `FR-CALL-001` for call, etc.).

### External services & flags
None.

## 6. Risks
- The call contract is the one most likely to over-reach: it is tempting to
  draw a rich in-call experience (speaker toggle, video button, add
  participant) that no spec id requires. Every element must trace to
  FR-CALL-001/002/003 or to a state the state machine (E07-T09) can
  actually be in. A button for a capability that does not exist is a
  promise the build will have to keep.
- `group-manage` must render *differently per role*, and the role-forbidden
  state is the one that gets forgotten. It is a required state, not an
  edge case — E07-T02's matrix is what it renders.
- Deriving from `devices.md` means inheriting its known issues, including
  the RenderFlex overflows `E06-B01` fixed. Read that bug before borrowing
  the row shape.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-UI-5**: WHEN a journey in this epic has no design source, the
  system's design record SHALL carry a derived contract traced to a spec id
  and to the existing design primitives it was built from, or an explicit
  question with a named owner. (FR-UI-004, rule 2)
- **EARS-UI-6**: The derived contracts SHALL introduce no token, colour or
  spacing value absent from the source screens' measured token tables.
  (rule 2)

### Tests
Docs task — the checks are mechanical, not a Dart suite:
- `test_EARS_UI_5_every_new_gap_traces_to_a_spec_id` — grep each new
  GAP entry for an `FR-`/`UC-` id.
- `test_EARS_UI_6_derived_contracts_use_only_source_tokens` — a script
  comparing each derived contract's token table against the union of its
  named source screens' tables; any value not present is a failure.
- `test_no_approved_by_line_is_filled` — every new `approved by:` is bare
  (`L-process-002`, the check `E06-T13`'s reviewer ran).

### Manual
1. Human reads the three contracts and GAP-018…GAP-022, then clears or
   amends 🧍 `design_contract_approval` in `design/gaps.md`.
