# E07-T07 · Read model widened to groups

## 1. Goal
Let the Conversations screen ask one repository for both its sections, so
the Groups list is the same projection as the Personal list rather than a
second, subtly different one.

## 2. Business logic
- **This is the widening E06-T09 planned for.** That task fixed
  `conversationId == peerDeviceId` for 1:1 and wrote, verbatim: *"Group
  conversations (E07) will need a different id space; that is E07's problem
  and this task's `conversationId` is documented as opaque to callers so
  E07 can widen it without rewriting the screens."* This task performs that
  widening — it is a named inherited obligation, not new scope.
- **One query, two kinds.** `ConversationSummary` gains a `kind`
  (`personal | group`) and the group-only fields the design's Groups rows
  need (`design/screens/conversations.md` elements 21-33 draw a title, a
  preview prefixed with the sender's name — `David Chen:` — and status
  glyphs). The repository must still return the whole list in **one grouped
  query**, exactly as E06-T09's `test_EARS_COMM_17_list_is_a_single_query`
  requires; widening the projection must not reintroduce the N+1 that test
  exists to prevent.
- **Blocking applies asymmetrically and deliberately.** A blocked peer's
  1:1 conversation is excluded from the list (FR-BLOCK-001, unchanged). A
  *group* containing a blocked peer is **not** excluded — the group is
  still yours. `spec/feature-list.md`'s "Blocked users are mutually
  invisible within a shared group" is the rule that applies inside the
  thread, and it belongs to whichever task renders group messages; this
  task records the obligation rather than silently deciding the thread's
  behaviour. See `OQ-E07-10`.
- **A deleted group leaves the list.** `groups.is_deleted` excludes it,
  while its rows are retained (E07-T01 §2).
- **The preview is still metadata, and the ciphertext is still opaque
  here** — E06-T09's §2 rule holds unchanged. The repository does not
  decrypt, does not import `CryptoService`, and `ConversationSummary`
  still has no `previewText` field. The sender-name prefix the design draws
  is assembled in the screen layer, from the group member list this
  projection exposes.

## 3. What this task does
- **`ConversationSummary` gains:** `kind` (`ConversationKind.personal |
  .group`), `groupName` (null for personal), `memberCount` (null for
  personal), `lastMessageSenderDeviceId` (already implied by
  `lastMessageIsMine`, now explicit so the screen can render the
  `<name>:` prefix without a second query). `peerDeviceId` and
  `relationshipState` become nullable for the group case — a group has no
  single peer and no single relationship state, and faking one would be a
  lie the screen would then render.
- **`listConversations()` / `watchConversations()`** extended: the same
  single grouped query, `UNION`-ing the personal projection with a group
  projection over `groups` ⋈ `messages` ⋈ `group_members`, blocked *peers*
  still excluded, deleted groups excluded, ordered `lastMessageAt DESC`
  across both kinds.
- **`watchConversations()` also re-emits on group-table changes** — a
  rename or a membership change must move the list without a message
  arriving.
- `messagesPage` / `watchConversation` / `unreadCount` need **no signature
  change**: they already take an opaque `conversationId`, and a group id
  is one. Assert that with a test rather than assuming it.

## 4. What this task does NOT do
- Does **NOT** decrypt, and does **NOT** add `previewText` (E06-T09 §2,
  restated because this is exactly the task where "just for the Groups
  rows" becomes tempting).
- Does **NOT** write. Read model only.
- Does **NOT** add a table, column, index or migration. If the group
  projection genuinely cannot be written against E07-T01's tables, stop and
  raise it — do not add an index here.
- Does **NOT** filter blocked members' messages inside a group thread
  (`OQ-E07-10` — the obligation is recorded, the owner is named, the
  behaviour is not guessed here).
- Does **NOT** implement search, mute, pin, or archive.
- Does **NOT** touch any UI file. E07-T08 consumes this.
- Does **NOT** modify `GroupRepository` or anything under
  `lib/features/groups/`.

## 6. Risks
- The single-query property is the one thing most likely to be lost here.
  E06-T09's `test_EARS_COMM_17_list_is_a_single_query` must still pass
  **unmodified**, and a new assertion must show that growing the group
  count does not grow the query count either. If the union genuinely
  requires two round trips, that is a finding to record, not to hide.
- `watchConversations` now watches three tables. E06-T09's coalescing
  window already exists; widening the watch without widening the coalesce
  turns a membership burst into a query storm — the exact risk E06-T09 §6
  named and tested.
- Nullable `peerDeviceId` will make every existing call site a compile
  error. That is the point — each one is a place that assumed 1:1. Fix them
  in `files:`-declared files only; if a call site outside the fence breaks,
  that is a fence amendment to raise, not to quietly widen.
