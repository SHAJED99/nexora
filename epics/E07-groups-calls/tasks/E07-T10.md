# E07-T10 · Real-time profile + call priority

## 1. Goal
Make FR-CALL-002 true where it is checkable today: a third traffic profile
that weights latency far above battery and hop count, and a relay queue
that drains call traffic before synchronization traffic.

## 2. Business logic
- **FR-CALL-002: "Calls shall receive higher network priority than
  non-real-time synchronization."** Two distinct mechanisms are needed and
  this task builds both:
  1. **Route selection** — a `TrafficProfile.realtime` weight set. E04's
     `RouteCostCalculator` already parameterises cost by profile
     (`interactive`, `bulk`); this adds the third rather than special-casing
     calls inside the engine.
  2. **Queue ordering** — `RelayEngine` already stores a `priority` on
     every queued packet (`relay_packets.priority`, and `RelayPacketFrame`
     carries it on the wire). Call traffic is enqueued at a strictly higher
     priority band than messaging or sync, and the drain order must respect
     it. A priority field nothing sorts by is decoration; check whether
     `processQueue` currently orders by it, and if it does not, that is
     this task's central change.
- **The weights are tunable and explicitly marked so**, in the style
  `route_cost_calculator.dart` already uses for `_interactive`/`_bulk`
  ("TUNABLE: these starting values are a task-sharding implementation
  detail, not a locked-in constant"). Proposed starting point: latency
  weight ~4× `interactive`'s, hop-count weight ~2×, battery weight ~0.25×.
  A call would rather burn battery on a two-hop path than be smooth-free on
  a five-hop one; a sync would rather wait.
- **Priority bands, named once:** `realtime = 200`, `interactive = 100`,
  `bulk = 0`. Integers with gaps so a future band fits between without
  renumbering. Existing enqueues keep their current effective priority —
  this task must not silently re-prioritise E05/E06 traffic. Verify the
  current default (`_defaultPriority = 0` in `messaging_stack.dart`) and
  either map it explicitly onto a band or leave it untouched and say which.
- **Higher priority must not mean starvation.** A device in a long call
  must still eventually drain its message queue. The drain takes call
  packets first *within a bounded budget per cycle* — never an unbounded
  "drain all realtime before anything else" loop. A messaging queue that
  never drains during a 40-minute call is a worse bug than a slightly
  choppy call.
- **This task moves no audio.** It prepares the routing and queueing
  behaviour that a real-time media path will use, and the only traffic it
  can actually mark `realtime` today is **call signaling** (E07-T09). That
  is a genuine, testable improvement — an invite that queues behind a large
  sync backlog is a call that never rings — and it is the honest limit of
  what is buildable before `OQ-E07-3` is answered.

## 3. What this task does
- `TrafficProfile.realtime` + its weight set in `RouteCostCalculator`,
  marked TUNABLE.
- `RelayPriority` band constants and the enqueue-site plumbing.
- `RelayEngine.processQueue` ordering by `(priority DESC, created_at ASC)`
  with a bounded per-cycle budget, plus the starvation guard.
- `CallSignaling._sendFrame` computes every outgoing signaling frame's
  route with `TrafficProfile.realtime`, stamps the wire frame's
  `priority` field `RelayPriority.realtime`, and then **dispatches on the
  computed route — a hybrid, not an unconditional enqueue**:
  - **direct or unknown route** (`computeRoute` returns `null`, or a route
    whose `hops.length <= 1` — the peer is this device's direct neighbor,
    or is assumed reachable): the frame goes **straight to
    `transport.send`**. No `relayEngine.enqueue`, no `relay_packets` row,
    no priority band involved on this device at all — the `realtime`
    profile still governs the route computation, and the frame's own
    `priority` field still travels on the wire for any downstream relay.
  - **known multi-hop route** (`hops.length > 1`): the frame goes through
    `relayEngine.enqueue(peerDeviceId, serialized, RelayPriority.realtime,
    _controlFrameTtl)`, immediately followed by an explicit
    `relayEngine.processQueue()` call so the attempt happens now rather
    than at the messaging coordinator's next periodic tick (60s default,
    longer than the 45s ring timeout).
  This is the ratified rule — see §5 §Dispatch rule for why it is the
  contract rather than a deviation from it.
- Tests that pin the *ordering behaviour*, not the weight numbers — a test
  asserting a specific cost value would freeze a constant the file itself
  marks tunable.

## 4. What this task does NOT do
- Does **NOT** add media, audio, codecs or a dependency.
- Does **NOT** change `interactive` or `bulk` weights, or re-prioritise any
  existing E05/E06 enqueue.
- Does **NOT** implement mid-call migration — `E07-T11`.
- Does **NOT** add QoS at the native transport layer, a new Pigeon method,
  or a second queue. One queue, ordered.
- Does **NOT** touch `routing_engine.dart`'s route computation, migration
  thresholds, or `considerMigration`. This task adds a profile; it does not
  retune the engine.
- Does **NOT** write `RelayDeliveryState.failed` (`OQ-E06-T06-3`).
- Does **NOT** add a table, column or migration. `relay_packets.priority`
  already exists.

## 5. Contract

### Functions
```yaml
- signature: "enum TrafficProfile { interactive, bulk, realtime }"
  purpose: "third value appended -- appended, not reordered, because the enum is persisted nowhere but is switched on in several places and a reorder is a silent behaviour change"

- signature: "abstract final class RelayPriority { static const int realtime = 200; static const int interactive = 100; static const int bulk = 0; }"
  purpose: "named bands, gapped so a future band needs no renumbering"

- signature: "RelayEngine.processQueue({int? maxPacketsPerCycle}) -> Future<int>"
  returns: "packets attempted this cycle"
  purpose: "drains (priority DESC, created_at ASC) within a bounded budget; the budget is what prevents realtime traffic starving the message queue (§2)"
```

**Weight set (TUNABLE — the ratios are the contract, the numbers are not):**
`realtime` weights latency ≈4× `interactive`, hop count ≈2×, battery
≈0.25×, unreliability ≈2×.

### Dispatch rule — `CallSignaling._sendFrame` (ratified 2026-09-01)

Binding, in the same sense as `files:` and `functions:`. `_sendFrame`
computes `routingEngine.computeRoute(peerDeviceId, TrafficProfile.realtime)`
once, and branches on the result:

| Computed route | Dispatch | Priority band | Delivery evidence |
|---|---|---|---|
| `null`, or `hops.length <= 1` | `transport.send(peerDeviceId, serialized)` directly — bypasses `RelayEngine` and `relay_packets` entirely | none on this device (the wire frame still carries `priority: RelayPriority.realtime` for downstream relays) | `transport.send`'s own boolean return |
| `hops.length > 1` | `relayEngine.enqueue(..., RelayPriority.realtime, _controlFrameTtl)` then an immediate `relayEngine.processQueue()` | `RelayPriority.realtime` in the shared queue | real evidence that the send was **attempted** — never an unconditional `true` (see below) |

Failure on either branch raises `AppFailure('call.unreachable')`, exactly
as E07-T09 specified. **The multi-hop branch must not assume success**: a
frame that was enqueued but whose drain provably never attempted a send
has not been delivered, and `call.unreachable` must still be able to
fire. The honest ceiling on this branch is "handed off to the next hop" —
matching `RelayEngine`'s own `forwarding`/`delivered` semantics, never
"the end recipient's app confirmed receipt" — so the branch is satisfied
by evidence of a real send attempt, not by reaching the end of the
`enqueue` call. The code fix implementing this is being made by the
builder in the same PR (#10) alongside F1/F2/F6; **this contract states
the intended behaviour, and verifying that the code matches it is the
reviewer's job on the next review round** — the planner has not verified
it here.

**Why the hybrid is the contract and not a deviation.** The original §3
line ("`CallSignaling` enqueues at `RelayPriority.realtime`") read
literally as *always enqueue* cannot be met as written, and the round-1
review (`tracker.md`, "E07-T10 — 2026-09-01 — 📋 CHANGES", F3/F4)
independently verified both halves of why:

1. **An unconditional enqueue silently no-ops every send in the existing
   `call_signaling_test.dart` suite.** `RelayEngine._attempt` needs
   `RoutingEngine` graph state that suite never populates, so
   `computeRoute` returns `null` throughout it and nothing would ever
   route — every invite/accept/decline/hangup/ringing/busy/cancel would
   go permanently dark. That suite is E07-T09's, is not in this task's
   `files:`, and must not be touched.
2. **Bypassing the queue on the direct path is what actually delivers
   EARS-CALL-6's guarantee.** The sync backlog lives only in
   `relay_packets`; a direct `transport.send` does not touch that
   structure, so a call invite on the common path genuinely cannot get
   stuck behind a queued sync backlog. The multi-hop branch achieves the
   same property the other way — it enters the same one queue as
   everything else (§4: "one queue, ordered") at the top band, and drains
   immediately.

Under rule 1 this should have been raised as an Open Question and stopped
on rather than reinterpreted in flight; the outcome was nonetheless
correct, so the contract is amended to match the code rather than the
code reverted to match the contract. Recorded here so future reviewers do
not re-litigate whether the hybrid was legitimate: it is ratified, dated
2026-09-01.

## 6. Risks
- **Check before you build:** if `processQueue` already orders by priority,
  half this task is a test that proves it and a plumbing change at the
  enqueue site. If it does not, changing the drain order touches the
  behaviour every E05/E06 test depends on. Read `relay_engine.dart` fully
  and run the existing suite before and after; an unexplained change in an
  E05 test is a finding, not noise to fix.
- The starvation guard is the part most likely to be skipped because
  nothing fails without it. Test it explicitly: 50 queued messages + a
  continuous realtime stream ⇒ the messages still drain.
- A test that pins a cost *number* will break the moment anyone tunes the
  weights, and the fix will be to change the test, which makes the test
  worthless. Assert orderings and comparisons only.

3. **`CallSignaling`'s delivery path is a hybrid, not a full switch to

   "enqueues at `RelayPriority.realtime`"; a literal unconditional read of
   that (replace every send with `relayEngine.enqueue`) was tried and
   rejected after two concrete findings: (a) `RelayEngine._attempt` requires
   `RoutingEngine` to already have graph knowledge of the destination
   (`computeRoute` returning a route) before it will attempt a send at
   all — none of `call_signaling_test.dart`'s existing scenarios ever
   populate that graph (they rely on `CallSignaling`'s original
   direct-neighbor `transport.send`), so an unconditional switch would make
   every existing invite/accept/decline/hangup/ringing/busy/cancel frame in

   `files:` list and must not be touched; (b) `messaging_coordinator.dart`'s

   directly contradicts FR-CALL-002's purpose. The implemented design:

   immediate `processQueue()` call (so it is not left to the periodic tick);

   `call_signaling_test.dart` suite never populates `RoutingEngine`'s
   link graph for its test peer ids, so `computeRoute` returns `null` there

   the top band zero slots at very small budgets.** `_applyStarvationGuard`
   reserves at least one slot per lower band (`perBandReserve`, at minimum
   1) before the top band gets anything (see Step 1/Step 2 in
   `relay_engine.dart`). With 3 live bands (`realtime`, `interactive`,
   `bulk`) and `maxPacketsPerCycle` of 1 or 2, the two lower-band reserves
   alone can consume the *entire* budget, leaving `remaining <= 0` when
   Step 2 tries to give the top band its share — so `realtime` (the band
   this whole task exists to prioritize) can receive 0 slots that cycle,
   a priority inversion. This is **not reachable in production today**:
   both current callers of `processQueue()` — `call_signaling.dart`'s
   post-`enqueue()` call and `messaging_coordinator.dart`'s periodic tick —
   invoke it with no `maxPacketsPerCycle` (unbounded), so the
   `_applyStarvationGuard` codepath that has this inversion never runs for
   either of them. Recorded here per round-2 review instruction as a known,
   currently-unreachable edge case for whoever eventually adds a bounded
   caller.

7. **Round-1 finding F5 (S4, non-blocking, previously dropped): per-destination
   route-profile contamination.** `RoutingEngine._lastProfile` is keyed
   per-destination and is never reset once set. `CallSignaling._sendFrame`
   computes routes under `TrafficProfile.realtime` for a given peer; if
   that peer is later the target of an ordinary (non-call) messaging send
   that fails and falls back to route recomputation, the fallback inherits
   the `realtime` profile that call signaling left behind for that
   destination, rather than the `interactive`/`bulk` profile the messaging
   path actually intends. In other words, a peer you've called at least
   once can have its subsequent messaging traffic silently routed under
   call-grade weights (favoring latency/hops over battery) instead of its
   own traffic's profile. This was identified in round 1's review but was
   never recorded anywhere with a permanent home — not here, not in the
   tracker's Carried-forward observations — until round 2 named that gap
   explicitly (the L-process-008 failure mode: a finding with no reader).
   It is non-blocking (S4): no test or EARS criterion depends on
   per-destination profile isolation across traffic kinds, and the effect
   is "slightly wrong route weighting," not incorrect delivery. Left as a
   known limitation for a future task to decide whether `_lastProfile`
   should be reset after a call ends, or made non-sticky across profiles
   entirely.
