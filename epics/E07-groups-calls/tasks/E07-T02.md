# E07-T02 · Group role permission matrix

## 1. Goal
One pure, total function that answers "may this role perform this action on
this group?", so that the protocol layer (E07-T03), the fan-out layer
(E07-T06) and any future UI all enforce the *same* answer instead of three
similar ones.

## 2. Business logic
- **FR-GROUP-002 enumerates the Owner's powers exactly:** rename the group,
  add members, remove members, assign administrators, transfer ownership,
  delete the group. That list is the spec; it is not a starting point to
  extend.
- **FR-GROUP-003 is deliberately vague** — "Admins shall be able to perform
  permitted group-management actions; Members shall participate in normal
  communication." The spec does not enumerate which management actions an
  Admin gets, so this task does not invent a generous answer. The matrix
  below takes the *narrow, reversible* reading — an Admin may do the things
  a wronged Owner can trivially undo (add a member, remove a non-admin
  member, rename), and may not do the things that are irreversible or
  self-elevating (grant/revoke admin, transfer ownership, delete the
  group). Recorded as `OQ-E07-5` so the human can widen it cheaply; a
  narrow matrix that is later widened is a one-line change, a wide matrix
  that is later narrowed is a security incident.
- **Every rule is evaluated against the acting device's *current* role in
  *that* group**, never against a cached role from another group and never
  against a role a control frame claims for itself. The permission decision
  is always made locally against local state (E07-T03 §2).
- **Self-actions are distinct from actions on another member.** Leaving a
  group is not "removing a member"; every role may leave. An Owner may not
  leave without transferring ownership first — otherwise the single-owner
  invariant E07-T01 enforces in the index becomes unsatisfiable.
- **A removed member has no role and therefore no permission at all**, not
  even to read. `removed_at_epoch IS NOT NULL` is a hard `false` for every
  action.

## 3. What this task does
- **`GroupAction`** — one enum value per FR-GROUP-002/003 action:
  `rename`, `addMember`, `removeMember`, `removeAdmin`, `grantAdmin`,
  `revokeAdmin`, `transferOwnership`, `deleteGroup`, `leave`, `sendMessage`.
- **`GroupPermissions.allows({required GroupRole actorRole, required
  GroupAction action, GroupRole? subjectRole})`** — a pure, total, `const`-
  friendly function returning `bool`. No I/O, no database, no clock.
- **`GroupPermissions.check(...)`** — the same decision returning a typed
  `AppFailure('group.forbidden')` instead of a bare `false`, for callers
  that need to surface a reason (`docs/conventions.md`'s single error
  envelope, the one E06-T02's taxonomy established).
- The matrix as an explicit, readable table in the source, with a test that
  asserts **every** `(role × action × subjectRole)` combination — a matrix
  with an untested cell is a matrix with a guess in it.

## 4. What this task does NOT do
- Does **NOT** read or write the database. This is a pure function over
  roles; the caller loads the roles. A permission function that queries is
  a permission function nobody can test exhaustively.
- Does **NOT** enforce anything. E07-T03 calls it; this task provides it.
- Does **NOT** widen `GroupRole` or add a fourth role.
- Does **NOT** decide the Admin matrix beyond the narrow reading in §2 —
  widening is `OQ-E07-5`, a human call, not an implementer's judgement.
- Does **NOT** touch trust/blocking (E02). Whether a *blocked* peer may be
  added to a group is E07-T03's composition of this matrix with
  `RelationshipRepository`, not a new role here.
- Does **NOT** add a `GroupRepository`, a controller, or a UI affordance.

## 5. Contract

### Functions
```yaml
- signature: "enum GroupAction { rename, addMember, removeMember, removeAdmin, grantAdmin, revokeAdmin, transferOwnership, deleteGroup, leave, sendMessage }"
  purpose: "one value per FR-GROUP-002/003 action; removeMember and removeAdmin are separate because the Admin matrix distinguishes them"

- signature: "bool GroupPermissions.allows({required GroupRole actorRole, required GroupAction action, GroupRole? subjectRole})"
  params:
    actorRole: "the acting device's CURRENT role in THIS group, loaded by the caller"
    subjectRole: "the target member's current role, for member-directed actions; null for group-directed ones"
  returns: "true iff the matrix permits it. Total — never throws, never returns null"
  purpose: "the single source of truth for FR-GROUP-002/003"

- signature: "AppFailure? GroupPermissions.check({required GroupRole actorRole, required GroupAction action, GroupRole? subjectRole})"
  returns: "null when allowed; AppFailure('group.forbidden') otherwise"
  purpose: "the same decision in the project's error envelope, for callers that surface a reason"
```

## 6. Risks
- The tempting shortcut is `if (role == owner) return true;` at the top.
  Do not: the Owner's `leave` is a deliberate `false`, and a blanket
  owner-allows-everything line silently deletes that row from the matrix.
- `removeMember` with `subjectRole == null` is a programming error, not a
  permission decision. Assert loudly rather than defaulting to `false` —
  a silent `false` here reads at the call site as "not permitted" and
  hides the bug.
- Exhaustive testing means `GroupRole.values × GroupAction.values ×
  (GroupRole.values + null)` = 120 cells. Generate them in a loop against
  a literal expectation table; do not hand-write 120 `expect`s and do not
  test only the interesting ones.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-GROUP-6**: WHEN an Owner performs any of rename, add member,
  remove member, grant/revoke admin, transfer ownership or delete, the
  system SHALL permit it. (FR-GROUP-002)
- **EARS-GROUP-7**: IF a Member or an Admin attempts an action the matrix
  reserves for a higher role, THEN the system SHALL deny it with
  `group.forbidden`. (FR-GROUP-003)

## Open Questions
- **OQ-E07-5 — how much may an Admin actually do?** FR-GROUP-003 says
  "permitted group-management actions" without enumerating them, so the
  spec is genuinely silent and this task takes the narrow reading (§2).
  Options: **(a) narrow** — Admin may rename, add, and remove *members*
  only (this task's matrix); **(b) medium** — Admin may additionally grant
  admin, but not revoke it or transfer ownership; **(c) broad** — Admin may
  do everything except delete the group and transfer ownership.
  *Advisory: **(a)**.* Widening later is a one-line matrix change plus a
  test; narrowing later means telling users a capability they had is gone,
  and any Admin who used it in the meantime has already made irreversible
  changes.
