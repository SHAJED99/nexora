# E07-T03 · Group membership control protocol

## 1. Goal
Make the six FR-GROUP-002 actions real end to end: performed locally
against the permission matrix, encoded as a control frame, delivered to
every current member over their existing pairwise Signal session, and
applied on receipt with the same permission check the sender ran.

## 2. Business logic
- **Membership control frames are authenticated by the Signal session
  they arrive in, never by `frame.source`.** `E06-B04` proved
  `RelayPacketFrame.source` is unauthenticated at the transport layer, and
  the human deferred *signing transport frames* to E11. This task must not
  inherit that weakness: a forged `frame.source` on a membership frame
  would let any device on the mesh remove any member of any group. So a
  group control frame is carried as an **encrypted `PayloadType.control`
  payload inside the pairwise Double Ratchet session** with the sending
  device (the same channel `E06-T07`'s prekey exchange and `E06-T08`'s
  acks already established), and the acting device id is taken **from the
  decrypting session's address**, not from the frame header. If the
  payload does not decrypt under a session with the claimed actor, the
  frame is dropped and counted. This is a design decision *within*
  accepted ADR-0003, recorded here rather than assumed; see `OQ-E07-6`.
- **The permission check runs twice, and both times locally.** The sender
  checks before emitting (fail fast, good UX); every receiver checks again
  before applying, against its *own* copy of the membership table. A
  receiver that trusts the sender's claim of authority is a receiver with
  no authority model at all. `GroupPermissions.check` (E07-T02) is the only
  implementation of that check on either side.
- **Every applied change bumps `groups.membership_epoch` by exactly one
  and appends one `group_events` row, in a single transaction.** Epoch and
  event log must never disagree; that is what makes rotation (E07-T05)
  deterministic.
- **Application is idempotent and ordered by epoch.** A frame whose
  `epoch` is `<= groups.membership_epoch` is already applied — drop and
  count, do not re-apply. A frame whose epoch is more than one ahead means
  this device missed a change: it is **not** applied speculatively; it is
  parked and counted as `groupOutOfOrder`. Filling that hole is
  `OQ-E07-7`, not this task.
- **Blocked peers cannot be added (FR-BLOCK-001, E02).** `addMember`
  composes the permission matrix with `RelationshipRepository` — a device
  the local user has blocked is refused locally with
  `group.blocked_member`, and an incoming `memberAdded` naming a blocked
  device is applied to the table (the group really does contain them) but
  their messages stay filtered by the existing block path. Blocking is a
  local view, not a group-wide veto — a member cannot silently rewrite
  another member's group.
- **Creation is a local act.** `createGroup` writes the local rows and then
  emits `memberAdded` frames to the invitees; there is no server to
  register with (ADR-0005).
- **Deleting a group deletes it locally for everyone who applies the
  frame**, marking `groups.is_deleted`. Rows are retained (E07-T01 §2), and
  `E07-T05` must still rotate/discard key state on delete.

## 3. What this task does
- **`GroupControlFrame`** (`group_control.dart`) — the serialized control
  payload: `version`, `kind` (`GroupEventKind`), `groupId`, `epoch`,
  `actorDeviceId`, `subjectDeviceId?`, `name?` (for `renamed`/`created`),
  `memberList?` (for `created`, so an invitee learns the roster),
  `createdAtMs`. Deterministic binary encoding, length-prefixed strings —
  the same shape `relay_packet_frame.dart` already establishes; **not**
  JSON.
- **Control kind `3`** — a new `kControlKindGroupControl = 3`, registered
  on `InboundPipeline`'s keyed control-handler dispatch (the seam
  `OQ-E06-T08-2` retrofitted, currently holding `1` = prekey exchange and
  `2` = delivery ack). Registration happens in `MessagingStack`'s
  constructor, exactly like the other two — this is the established
  pattern, not a new one.
- **`GroupRepository`** — the durable read/write surface over E07-T01's
  four tables: `createGroup`, `currentMembers`, `roleOf`, `applyEvent`
  (transactional: member mutation + epoch bump + event row),
  `watchGroups`, `eventsFor`.
- **`GroupMembershipService`** — the six FR-GROUP-002 actions as methods,
  each of which: checks permission → applies locally in one transaction →
  fans the control frame out to every current member over
  `PrekeyExchange.ensureSession` + `CryptoService.encrypt` +
  `RelayEngine.enqueue`. And `handleControlFrame`, the receive half.
- Counters on the inbound path for `groupForbidden`, `groupReplayed`,
  `groupOutOfOrder`, `groupUnauthenticated` — the same
  `InboundCounters` style E06-T05 established, so a dropped frame is
  observable rather than silent.

## 4. What this task does NOT do
- Does **NOT** encrypt group *messages* or touch sender keys. Membership
  frames ride pairwise sessions only. Group message encryption is
  E07-T04/T05/T06.
- Does **NOT** rotate keys. It bumps the epoch; `E07-T05` watches the epoch
  and rotates. Do not add a key operation here even though it looks
  adjacent — that split is deliberate and is what keeps both tasks at M.
- Does **NOT** sign transport frames or otherwise fix `E06-B04`. That is
  E11's. This task routes *around* the weakness (§2) rather than fixing it.
- Does **NOT** implement gap-fill for a missed epoch (`OQ-E07-7`), and
  does **NOT** speculatively apply an out-of-order frame.
- Does **NOT** write `RelayDeliveryState.failed` — `OQ-E06-T06-3`'s
  standing constraint (whoever first writes `failed` must extend
  `reclaimPayloads`'s reclaim set in the same change) stays untriggered by
  this epic.
- Does **NOT** build any UI, controller, or route. Group create/manage
  screens are prospective and blocked on their design contracts.
- Does **NOT** modify `PrekeyExchange`, `DeliveryAckService`,
  `InboundPipeline` or `relay_packet_frame.dart`. It *registers on* the
  existing seam; it does not reshape it. If registration turns out to
  require changing `inbound_pipeline.dart`, stop — that is a fence
  amendment, not a quiet edit.

## 6. Risks
- The fan-out loop is where an epic-sized bug hides: sending to N members
  means N `ensureSession` calls, each of which may need a prekey bundle and
  may take seconds on first contact (E06-T11's review found exactly this
  latency shape). Do the local transaction **first**, then fan out
  best-effort and asynchronously — never hold the local write behind N
  network round trips.
- One failed member send must not roll back the local change or abort the
  other sends. A group where a change applies to four of five devices is
  the normal, recoverable state (that member catches up via
  `OQ-E07-7`); a group where the change applied to nobody because the
  fifth device was off is not.
- `transferOwnership` and `removeMember(owner)` interact with E07-T01's
  single-owner partial unique index. Transfer must demote the old owner
  and promote the new one **inside one transaction**, or the index will
  reject the intermediate state. This is the most likely place to hit a
  constraint violation at hour three.
- Reading the actor from the decrypting session's address (rather than the
  frame) is the security property of this whole task. It is also easy to
  lose during a refactor — assert it with a test that forges a frame whose
  `actorDeviceId` disagrees with the session address and confirms the
  frame is dropped.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-GROUP-8**: WHEN an Owner performs a membership action, the system
  SHALL apply it locally in one transaction, increment the group's
  membership epoch by one, append a group event, and emit the change to
  every current member. (FR-GROUP-002)
- **EARS-GROUP-9**: WHEN a membership control frame is received, the
  system SHALL evaluate the sender's permission against local membership
  state and SHALL NOT apply a change the sender's role does not permit.
  (FR-GROUP-003)
- **EARS-GROUP-10**: IF a membership control frame's claimed actor differs
  from the identity of the Signal session it decrypted under, THEN the
  system SHALL discard it. (FR-GROUP-002, FR-SEC-001)
- **EARS-GROUP-11**: IF a membership control frame's epoch is not exactly
  one greater than the local epoch, THEN the system SHALL discard it as
  replayed or out-of-order without applying it. (FR-GROUP-004)

**Deviations from spec/design:**

1. **The `grep -n "frame.source"` self-review check cannot literally read
   zero, and this is disclosed rather than routed around.** §2's security
   property is "never read the acting device id from `frame.source`" — that
   is upheld: `group_membership_service.dart`'s `handleControlFrame` derives
   the acting identity ONLY from `sourceDeviceId`, the parameter documented
   (and enforced by its own doc comment) to be "the address of the SIGNAL
   SESSION the payload decrypted under — NOT `frame.source`". But
   `handleWireFrame` — the method that actually receives a raw
   `RelayPacketFrame` off the wire, one layer below `handleControlFrame` —
   must pass *some* `SignalProtocolAddress` into
   `CryptoService.decrypt(address, ciphertext)` to select which session's
   ratchet state to attempt decryption with; libsignal's API offers no way
   to decrypt without first naming a candidate address. `frame.source` (the
   outer, unauthenticated claim) is the only candidate this device has, so
   `handleWireFrame` reads it once, at `group_membership_service.dart:423`,
   purely as *which session to try* — never as a trusted identity claim. The
   security property holds regardless: if `frame.source` is a lie, decrypt
   either fails outright (wrong/no session → `groupUnauthenticated`) or, in
   the pathological case where a real session for that claimed address
   exists but the bytes were actually produced by someone else's session,
   decryption still cannot produce a plaintext that both parses AND carries
   an `actorDeviceId` matching that address unless the claimed party's own
   ratchet keys actually produced the ciphertext — which only that party can
   do. This is not a new pattern invented for this task: `inbound_pipeline.dart:349`
   (`_stack.receiveMessage.call(frame.source, ciphertextMessage)`, unmodified
   by this task) already uses `frame.source` exactly this way for every
   ordinary encrypted chat message in this codebase, and E06-B04's own
   finding was scoped specifically to the **unencrypted** control channel
   (`PrekeyExchange`/`DeliveryAck`), never to this already-accepted
   decrypt-as-authentication pattern. `test_EARS_GROUP_10_forged_actor_id_is_discarded`
   is the falsification proving the property holds in practice: a frame
   whose plaintext `actorDeviceId` claims Owner, but which is genuinely
   encrypted through the Member's own session, is discarded
   (`groupUnauthenticated == 1`, table unchanged) — the forged claim inside
   the plaintext never survives the check against the address that actually
   decrypted it. Flagging this explicitly for the reviewer rather than
   deleting the two remaining code comments that mention `frame.source` (at
   `group_control.dart`'s and `group_membership_service.dart`'s own file
   headers) to force the grep to read zero — that would hide the reasoning,
   not remove the dependency.
2. **`old owner → admin` on `transferOwnership`, not `old owner → member`.**
   §5's contract does not specify what role the outgoing Owner receives.
   Demoting to Admin (rather than plain Member) was chosen as the least
   disruptive default — the group is not left with one fewer Admin as a side
   effect of a transfer — and is exercised by
   `test_EARS_GROUP_8_transfer_ownership_is_atomic`
   (`group_repository_test.dart`), which also proves a second, later
   transfer back still succeeds (the single-owner index is genuinely intact,
   not merely unused).
3. **`GroupMembershipService.createGroup` is not in §5's literal function
   list** (which names only the eight per-action methods plus
   `handleControlFrame`), but §2/§3's own prose ("`createGroup` writes the
   local rows and then emits ... frames to the invitees") describes exactly
   this behaviour, and `GroupControlFrame.memberList`'s own documented
   purpose ("for `created`, so an invitee learns the roster") is otherwise
   unreachable code — nothing else in this task's contract ever sends a
   `created` frame. Implemented as the natural pairing of
   `GroupRepository.createGroup` (§5's contract) with the same
   permission-free-by-construction fan-out shape every other action uses,
   and covered by `GroupRepository`'s own `test_EARS_GROUP_...` bootstrap
   test plus the service-level `createGroup` code path exercised
   transitively by the "a genuine rename fans out..." two-stack test's own
   `applyEvent(created ...)` seed. §2's own text says "emits `memberAdded`
   frames to the invitees" verbatim, while §3's `memberList` field
   description implies `created`; this implementation sends `created`
   (the only kind whose payload plausibly carries `memberList`) — logged
   here as the interpretation taken, in case the reviewer reads it the
   other way.
4. **`GroupAction.removeAdmin` has no `GroupMembershipService` entry
   point.** §5 lists no `removeAdmin` method (only `rename`, `addMember`,
   `removeMember`, `grantAdmin`, `revokeAdmin`, `transferOwnership`,
   `deleteGroup`, `leave`) even though `GroupAction.removeAdmin` exists
   (E07-T02). Read this as intentional: E07-T02's own matrix distinguishes
   `removeMember`(subject=admin) → always `false` from `removeAdmin`
   (Owner-only), so the only reachable path to fully removing an Admin is
   `revokeAdmin` (demote to Member) followed by `removeMember` — two calls,
   never one. `_kindFor` throws `UnsupportedError` if this action is ever
   reached, so a future caller that tries to wire it gets a loud failure,
   not a silent no-op.

## Open Questions
- **OQ-E07-6 — membership frames ride pairwise Signal sessions, and that
  is a security posture worth your confirmation.** The alternative designs
  are (a) this task's: carry every membership frame inside the pairwise
  Double Ratchet session, authenticated by the ratchet, N sends per change;
  (b) sign the frame with the sender's Signal identity key and broadcast it
  once, cheaper on the wire but a new signing scheme not covered by
  ADR-0003; (c) wait for E11's transport-frame signing (E06-B04) and use
  `frame.source` until then — cheapest, and forgeable by anyone on the mesh
  in the meantime. *Advisory: **(a)**.* It costs bandwidth this app does
  not have a shortage of, adds no new cryptographic construction, and is
  the only option that is secure the day it ships. Recorded rather than
  silently chosen because it is a security decision, even though it sits
  inside accepted ADR-0003.
