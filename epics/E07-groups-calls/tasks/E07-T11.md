# E07-T11 · Make-before-break migration

> ⛔ **This task owns the epic's `EARS-CALL-1` and it has a hard boundary.**
> The *control* of make-before-break — evaluate, establish, validate,
> switch, tear down — is fully buildable and testable today against
> `RoutingEngine` and the `CallMediaTransport` seam. The *media* half —
> actually carrying two audio paths at once during the overlap — cannot be
> built until `OQ-E07-3` (real-time transport) is answered by the human.
> This task builds the control and drives a media transport through the
> seam; it does not invent the transport. See `OQ-E07-12`.

## 1. Goal
FR-CALL-003, mechanically: when a better connection appears mid-call, the
system evaluates it, establishes and validates it, migrates the call onto
it, and only then terminates the old route — so the call does not drop.

## 2. Business logic
- **FR-CALL-003 names four ordered steps and the order is the
  requirement:** *evaluate → establish and validate → migrate → terminate
  the old route*. "Make-before-break" is precisely the claim that step 4
  happens after step 3. A controller that tears down first and reconnects
  fast is break-before-make and does not satisfy this requirement no matter
  how short the gap is.
- **Evaluation is already built and must not be re-implemented.**
  `RoutingEngine.considerMigration(destinationId, profile)` (E04-T02)
  returns `MigrationDecision.stay()` or `.migrateTo(route)`, already
  applying the ≥20% improvement threshold and the 10-consecutive-sample
  stability rule (both TUNABLE constants owned by E04). This controller
  drives it on a timer with `TrafficProfile.realtime` (E07-T10) and acts on
  its answer. **Do not add a second migration heuristic**, and do not tune
  E04's constants from here.
  - Note the sampling contract: `kMigrationStabilityTicks` counts
    `considerMigration` *calls*, not wall-clock time (the engine reads no
    clock). The controller's tick interval therefore sets the real-world
    stability window, and it is an injected value, never a literal.
- **Validate means "a packet made the round trip on the candidate route",
  not "the route was computed".** A computed route whose first hop has
  silently dropped is exactly the case E04-B01 distinguishes
  `noteAttemptedRoute` from `setActiveRoute` for. The controller sends a
  probe over the candidate, waits for its echo within a bounded timeout,
  and only on success calls `setActiveRoute`. A failed probe means: stay,
  do not tear anything down, and do not mark the candidate active.
- **The old route is torn down only after the media transport reports the
  new one carrying.** The controller asks the `CallMediaTransport`
  (E07-T09's seam) to attach the new route, waits for `CallMediaHealth`
  to report it live, and only then detaches the old. With
  `NullCallMediaTransport` this step reports "no media" and the controller
  **stays on the old route** — the correct behaviour for an unbuilt media
  path is to change nothing, never to migrate blind.
- **A migration is never allowed to end the call.** Every failure mode —
  probe timeout, media attach failure, candidate lost mid-switch — resolves
  to "stay on the current route", counted and logged. That is the whole
  point of FR-CALL-003, and it is the invariant the tests must attack
  hardest.
- **Route failure is distinct from route improvement.**
  `RoutingEngine.onRouteFailure` (FR-ROUTE-009) already handles "the
  current route died" — that is break-then-make by necessity, and this
  controller must call it rather than reimplementing recovery. Migration
  (this task) is the optional, opportunistic path; failure recovery is the
  mandatory one. Conflating them is how an opportunistic optimisation ends
  up in the crash path.

## 3. What this task does
- **`CallMigrationController`** — started when a `CallSession` reaches
  `active`, stopped on `ending`:
  - a `Timer.periodic` (injected interval, default 1 s) calling
    `considerMigration(peerDeviceId, TrafficProfile.realtime)`
  - on `.migrateTo(route)`: `noteAttemptedRoute` → send a
    `CallSignalKind.pathProbe` frame over the candidate → await its echo
    within a bounded timeout → `setActiveRoute` → `media.attach(newRoute)`
    → await `CallMediaHealth.live` → `media.detach(oldRoute)`
  - any failure at any step: abandon, stay, increment a counter, leave the
    active route exactly as it was
  - on a route failure signal: delegate to `RoutingEngine.onRouteFailure`,
    not to the migration path
- **`CallSignalKind.pathProbe` / `.pathProbeEcho`** added to E07-T09's
  frame — the probe is an ordinary signaling frame at the `realtime` band,
  so validation uses the same authenticated channel as everything else.
- **`CallSession` gains an observable `activeRoute` and a
  `migrations` event stream** (`attempted`, `validated`, `completed`,
  `abandoned(reason)`), so the (prospective) call UI and any future
  diagnostics read one source of truth.
- Counters: `callMigrationAttempted`, `callMigrationProbeTimeout`,
  `callMigrationMediaFailed`, `callMigrationCompleted`,
  `callMigrationAbandoned`.

## 4. What this task does NOT do
- Does **NOT** implement, choose, or add a real-time media transport
  (`OQ-E07-3`, 🧍 human). Does **NOT** add an audio/codec/WebRTC
  dependency.
- Does **NOT** carry two live audio paths simultaneously — that is the
  media half, and it belongs to whatever implements
  `CallMediaTransport`. This task defines and drives the sequence the
  implementation must satisfy (`OQ-E07-12`).
- Does **NOT** modify `RoutingEngine`, `RouteCostCalculator`,
  `RelayEngine`, or E04's TUNABLE thresholds. It is a caller.
- Does **NOT** add a second migration heuristic, a hysteresis of its own,
  or a "force migrate" API.
- Does **NOT** handle route failure recovery — it delegates to
  `onRouteFailure`.
- Does **NOT** migrate non-call traffic. Messaging already routes
  per-packet; migration is a *session* concept and applies only to calls.
- Does **NOT** add a table, column or migration.

```yaml
  purpose: "both durations injected, never literals at a call site (the MessagingStack.coordinatorTickInterval pattern)"

- signature: "CallMigrationController.stop() -> Future<void>"
  purpose: "cancels the timer and every in-flight probe; safe to call twice"

- signature: "CallMigrationController.evaluateOnce() -> Future<MigrationOutcome>"
  returns: "stayed | probeFailed | mediaFailed | migrated(Route) -- exposed so tests drive the sequence deterministically instead of waiting on a timer"

- signature: "enum MigrationOutcome { stayed, probeFailed, mediaFailed, migrated }"

- signature: "CallSession.activeRoute -> Route?"
- signature: "CallSession.migrations -> Stream<CallMigrationEvent>"
  purpose: "attempted | validated | completed | abandoned(reason)"
```

**The ordered sequence is contractual (FR-CALL-003) and an implementation
may not reorder it:**
`considerMigration → noteAttemptedRoute → probe → echo received →
setActiveRoute → media.attach(new) → health live → media.detach(old)`

## 6. Risks
- **The single most likely defect is tearing down early.** Write
  `test_EARS_CALL_1_old_route_is_still_attached_until_the_new_one_is_live`
  first, with a media transport that records the exact order of
  attach/detach calls, and make it fail for the right reason before
  writing the controller.
- `considerMigration` requires an *active* route to migrate away from
  (`_activeRoutes[destinationId]`), and it returns `stay()` when there is
  none. The controller must therefore `setActiveRoute` once when the call
  becomes `active`, or migration will never trigger and every test will
  pass. This is a silent-no-op trap: assert that the first evaluation of a
  call with a better alternative actually attempts.
- A probe echo arriving *after* its timeout must be ignored, not applied
  late. A late echo applied after the controller moved on will switch the
  route out from under a completed decision.
- Timer + async probe + media futures is three concurrency sources on one
  session. Serialise: at most one migration in flight, and a tick during an
  in-flight migration is dropped, not queued.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-CALL-1** *(epic-level)*: WHEN a better route becomes available
  mid-call, the system SHALL migrate without dropping the call
  (make-before-break). (FR-CALL-003)
- **EARS-CALL-9**: WHEN a candidate route is selected, the system SHALL
  validate it with a round-trip probe before making it active.
  (FR-CALL-003)
- **EARS-CALL-10**: IF validation or media attachment on the candidate
  route fails, THEN the system SHALL remain on the existing route and the
  call SHALL NOT end. (FR-CALL-003, FR-CALL-001)
- **EARS-CALL-11**: WHEN the active route fails outright, the system SHALL
  use route-failure recovery rather than the migration path.
  (FR-ROUTE-009)

## Open Questions
- **OQ-E07-12 — the media half of make-before-break needs the transport
  decision first.** This task proves the *control* sequence: evaluate,
  probe, validate, switch, tear down, and never drop the call. What it
  cannot prove is that audio actually keeps flowing across the switch,
  because carrying two paths concurrently is a property of the media
  transport, and no media transport exists (`OQ-E07-3`, 🧍 human). The
  three shapes the answer takes, depending on that decision:
  **(a)** a datagram-style transport over the existing mesh — the
  controller simply addresses frames to the new next hop and the overlap is
  free (a few duplicated packets); **(b)** a connection-oriented native
  channel — the overlap requires holding two native connections open,
  which is a Pigeon API change (`ADR-0004`) and a real platform-side cost;
  **(c)** WebRTC — ICE restart handles this internally and the controller
  becomes a thin driver over someone else's migration logic.
  *Advisory: settle `OQ-E07-3` first; this task's seam is deliberately
  shaped so all three plug in without changing the sequence.* The media
  half is listed as a prospective task in `epic.md` §Tasks, not sharded.
