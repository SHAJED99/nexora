# E07-B04 · `group_events.id` is not actually unique

## The defect

```dart
// lib/features/groups/data/group_repository.dart:63-66
int _eventIdCounter = 0;

String _nextEventId() =>
    'ge:${_clock().microsecondsSinceEpoch}-${_eventIdCounter++}';
```

The counter is **per-`GroupRepository`-instance**, and the class's own doc
comment (`:53-55`) says *"One instance per `AppDatabase` — cheap to
construct"* — which invites exactly the pattern that breaks it. Two
instances against one database each start at `0`; if both write an event in
the same microsecond, they generate the identical id and the second insert
throws.

`DateTime.now().microsecondsSinceEpoch` does not have true microsecond
resolution on Windows, which is why this reproduces readily rather than
theoretically.

## Repro
```
$ flutter test test/features/groups/domain/group_key_rotation_service_test.dart
```
Run it repeatedly. Observed by this sweep: **2 failures in ~35 runs**
(first at run 5 of a batch of 6, then at run 11 of a batch of 25), all the
same test and the same exception:

```
two-device: EARS-GROUP-2 / EARS-GROUP-15 (real crypto)
  test_EARS_GROUP_15_removed_member_is_not_a_distribution_recipient [E]
SqliteException(1555): UNIQUE constraint failed: group_events.id
  INSERT INTO "group_events" ("id", ...) VALUES (?, ...),
  parameters: ge:1788321577489944-0, g:5cbcf0..., 1, memberRemoved, device-a, device-c, ...
```

Note the id suffix: `-0`. Both colliding writes were the **first** event
from their respective repository instance — the test constructs a fresh
`GroupRepository(a.db)` per operation (lines 150, 192, 576, 666, 724, 810).

## Expected
FR-GROUP-002/003 — a membership change is recorded exactly once. An id
generator's uniqueness must not depend on clock resolution or on how many
repository instances a caller happens to build.

## Actual
`SqliteException(1555)` propagates out of the event write, aborting the
operation.

## Severity
**S3.** In `lib/` today all three `_nextEventId()` writers
(`group_repository.dart:109, 224, 274`) are reached only through
`GroupMembershipService._repository` — a single instance built at
`messaging_stack.dart:308` — whose counter is monotonic, so **production is
currently safe by the accident of single-writer ownership**, not by design.
The two `GroupRepository(_stack.db)` instances in
`inbound_pipeline.dart:487,567` are read-only (`groupRow`, `roleOf`) and do
not contribute.

Not S4: it makes the epic's suite non-deterministic today, and it becomes
S1/S2 the moment any second writer instance appears — which the class's own
doc comment actively encourages.

## Fix direction
Make the id independent of instance-local state and of clock resolution —
e.g. a random/UUID suffix, or a counter seeded from `MAX(id)`, or a database
-side identity. Prefer the option that needs no schema migration (rule 3:
a migration is a human call).

**Regression test first:** two `GroupRepository` instances over one
`AppDatabase`, each writing an event under a frozen `clock` that returns a
constant `DateTime` — must produce two distinct ids and two rows. That test
fails deterministically before the fix, rather than 1 run in 10.

## What this fix does NOT do
- Does **NOT** add or alter a schema migration, or change `group_events`'
  columns — rule 3 makes migrations a human call, and the fix should not
  need one.
- Does **NOT** change `newGroupId()` or any other id scheme in the file
  beyond `_nextEventId()`.
- Does **NOT** change `GroupMembershipService`'s transaction boundaries or
  event semantics.
- Does **NOT** refactor the tests' fresh-instance-per-call pattern into a
  shared instance — that would hide the defect rather than fix it.
- Does **NOT** touch `messaging_stack.dart`'s composition.
