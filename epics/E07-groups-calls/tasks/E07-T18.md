# E07-T18 · The group thread

## 1. Goal
`FR-COMM-002` — group communication via text. The group backend has been
complete since `E07-T06`/`T14` and nothing rendered it. This builds the
screen, and with it the journey: **create → open → send → read**.

## 2. The decisions this implements
Both were the human's, both 2026-09-25:

- **`GAP-045`, option (b)**, verbatim: `Message hidden — contact is blocked`,
  with the instruction *"Do not describe it as undecryptable, failed to load,
  or otherwise imply a cryptographic/decryption failure."*
- **`GAP-020` event-line typography reconciled to the measured contract:**
  `12px` `w500`, *not* the `14px` GAP-020's own approved prose said, *"Record
  the reconciliation honestly; do not alter measurements to conceal it."*

## 3. Contract
- **Route `/groups/:id`** — a new route and a new controller, **not** a mode
  on `ChatController`. `E07-B01` (human, P1, 2026-09-02) and `E07-B05` (this
  session) both exist because a group id reached the 1:1 controller, and
  `E07-B01` §What this fix does NOT do explicitly forbids widening it.
- `GroupThreadController` renders a single ordered list of **bubbles and
  event lines merged by timestamp**.
- Sender attribution (G9) on incoming bubbles only; never on this device's
  own (GAP-020: *"the design never labels the user to themselves"*).
- A blocked sender's bubble renders G10's copy **in place of the body**, and
  keeps its attribution.
- `ConversationsController.openGroup` navigates here instead of showing
  `E07-B01`'s interim "Coming soon".
- `GroupCreateController`'s success path lands here instead of
  `/conversations` (`E07-B05`'s interim).

## 4. What this task does NOT do
- Does **NOT** widen `ChatController` or touch `/chat/:id`.
- Does **NOT** build attachments, voice, PTT, location or calls in a group
  thread — each has its own contract and gap.
- Does **NOT** build group membership management (`group-manage.md`), and
  therefore renders **no** `more_vert` overflow button: an affordance with
  nothing behind it is the `E07-B01` mistake.
- Does **NOT** implement read receipts or delivery ticks in the group thread;
  `chat.md`'s tick elements belong to the 1:1 contract and GAP-020 does not
  derive them for groups.
- Does **NOT** add optimistic local bubbles (`ChatController`'s
  `_pendingOptimistic`); the stream re-emits on insert.
- Does **NOT** touch E04 or E01-B01's OQ-1.

## 5. Acceptance criteria (EARS)
- **EARS-GROUP-22**: WHEN a group row is tapped, the system SHALL open that
  group's thread. (`FR-COMM-002`)
- **EARS-GROUP-23**: WHERE a group message was sent by another device, the
  system SHALL render a sender attribution line; WHERE it was sent by this
  device, it SHALL NOT. (`FR-GROUP-002`, GAP-020)
- **EARS-GROUP-24**: WHERE a group message's sender is blocked, the system
  SHALL render `Message hidden — contact is blocked` in place of the body
  and SHALL NOT render the body. (`FR-TRUST-004`, GAP-045)
- **EARS-GROUP-25**: WHEN a membership event exists for the group, the
  system SHALL render it as a centred event line. (`FR-GROUP-003`, GAP-020)
- **EARS-GROUP-26**: WHEN the user sends into a group thread, the system
  SHALL send via the group path and SHALL NOT invoke the 1:1 send path.
  (`FR-COMM-002`, `E07-B01`)

## 6. Test strategy
`E07-B05`'s lesson is binding here: **navigation-critical tests exercise the
real destination.** The route tests assert against `Get.currentRoute` and
against the real `appPages` table, never only an injected spy.

The blocked-member test asserts both halves — the placeholder **is** present
**and** the real body string is **absent** — because asserting only the first
would pass even if the body rendered underneath it.

## 8. The design gate, and why its number is worthless today

```
design: PASS chat-group/default@390x844 — match 100% (17/17)
```

**Ignore that 100%.** `chat-group` is `source: derived`, and a derived
screen's golden is *extracted from the build* (`design-fidelity` §3). The
golden is this build's own probe dump, so the first run compares the build
to itself and cannot fail. It is a tautology, not evidence.

What it IS worth: from the next commit onward the screen is regression-gated
like every other one, and any drift shows up as a real diff.

The evidence that actually means something is in the probe assertions, which
read the rendered widget tree:

- `Message hidden` **is** present (GAP-045 option (b))
- `PROBE-BLOCKED-BODY-MUST-NOT-RENDER` is **absent** — the blocked sender's
  real body never reaches the widget tree at all
- `unable to decrypt` is **absent** — the human's instruction was to not
  imply a cryptographic failure

## 9. A bug the probe found that reasoning did not

`render` is async — it awaits the group row, the blocked set and every
body — so two renders can be in flight and the one that **started first can
finish last**. The first probe draft came back with a single row because a
subscription created before the database was seeded emitted an empty list,
and that render's awaits resolved *after* the seeded one had already
published four rows.

In the app the same shape is reachable whenever a message arrives while an
earlier render is still resolving bodies: the thread would visibly flicker
back to a stale list. Fixed with a render-generation guard. Cancelling the
subscription is **not** a fix — the in-flight render is not part of the
subscription.

## 10. A self-inflicted near-miss, recorded

While editing `design_probe_test.dart` I ran an unanchored global string
replace for `controller.onClose();` — intending to remove **one** line from
my own new test. It removed **six**, across five unrelated probe groups.

The symptom was maximally misleading: a single failure in the
**`device-enrollment`** test, reporting *"A Timer is still pending even
after the widget tree was disposed"* — a test I had never touched, failing
for a reason with no visible connection to my change. It survived being run
in isolation, which made it look environmental rather than self-inflicted.

What found it: comparing `git diff development...HEAD` for deleted lines
rather than reading the failure. What fixed it: rebuilding the file from
`development`'s version plus only my three additions, then asserting
`git diff development -- <file>` contains **zero** deletions.

The general rule, which is not new but was not applied: **a string replace
in a file I did not write needs an anchor unique to the site I mean**, and
an edit intended to be purely additive should be verified as additive.
