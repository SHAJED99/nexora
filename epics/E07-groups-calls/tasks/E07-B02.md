# E07-B02 · The sticky route profile leaks the wrong way

## The defect

`RoutingEngine` remembers the last traffic profile used per destination and
reuses it when recovering from a route failure:

```dart
// lib/core/routing_engine/routing_engine.dart:121
final Map<String, TrafficProfile> _lastProfile = {};
// :220 and :233 — written by computeRoute() and considerMigration()
// :297 — read by onRouteFailure()
final profile = _lastProfile[destinationId] ?? TrafficProfile.interactive;
```

The epic tracker carried this forward as "a call leaves `realtime` behind and
a later *message* send recovers under it". **That direction is not
reachable** — `RelayEngine._attempt` calls
`computeRoute(row.destinationId, _profile)` at `relay_engine.dart:315`,
immediately before `onRouteFailure(...)` at `:360`, so the messaging path
always rewrites `_lastProfile` with its own profile first.

The **reverse** direction is real and has a concrete in-`lib/` trigger. While
the Dashboard screen is mounted, every discovery / link-quality event runs:

```dart
// lib/features/dashboard/presentation/dashboard_controller.dart:232
if (_links.routing.computeRoute(peerId, TrafficProfile.interactive) != null)
```

for **every known peer**, including one on an active call. That overwrites
`_lastProfile[peer] = interactive`. `CallMigrationController.notifyRouteFailure()`
(`call_migration_controller.dart:197`) then calls `onRouteFailure(peer)`
with no profile of its own, so the call's replacement route is chosen under
the interactive weighting instead of `realtime` — silently discarding
exactly what E07-T10 exists to provide (FR-CALL-002).

The two profiles genuinely disagree (`route_cost_calculator.dart:59-87`:
realtime weights latency 4x and hop count 2x, battery 0.25x).

## Repro
Reviewer's own probe against the real `RoutingEngine` (scratch, not
committed). Graph from `self` to `peer`: an active direct link, plus two
2-hop alternatives — `x` (10ms/hop, high battery) and `y` (200ms/hop, no
battery).

1. `computeRoute('peer', realtime)` → `setActiveRoute(...)` — the call's route.
2. `computeRoute('peer', interactive)` — the Dashboard's connectivity poll.
3. `onRouteFailure('peer')` — the call's route fails.

```
PROBE D realtime    -> [x, peer]
PROBE D interactive -> [y, peer]
PROBE E control  recovered = [x, peer]   (no dashboard poll — correct)
PROBE E leaked   recovered = [y, peer]   (with dashboard poll — WRONG)
PROBE F messaging recovered = [y, peer]  (the recorded direction — correctly interactive, no leak)
```

## Expected
FR-CALL-002 / FR-ROUTE-009 — a call's route-failure recovery selects the
replacement route under the `realtime` profile. The chosen route must not
depend on whether an unrelated screen happens to be open.

## Actual
The call recovers onto `[y, peer]` — a 400ms path instead of the available
20ms one — purely because the Dashboard was mounted.

## Severity
**S3.** Latent today: `CallMigrationController` is the only caller of
`notifyRouteFailure` and it is not constructed anywhere in `lib/` (see
`E07-B03`), so this path is currently unreachable at runtime. It becomes
live the moment `E07-B03` is fixed. Not S2: the recovered route is valid and
the call continues — the cost is audio quality, not function.

## Fix direction
The durable fix is to stop `onRouteFailure` reading sticky state and take
the profile from its caller, who always knows it — but that changes an
E04-owned public signature with two call sites
(`relay_engine.dart:360`, `call_migration_controller.dart:197`). Coordinate
with `E07-B03`, whose owner (the real-time media-path task) already has to
reshape this seam for O2.

**Regression test:** assert at the `RoutingEngine` level that a
`computeRoute(dest, interactive)` between `setActiveRoute` and
`onRouteFailure` does not change the route a `realtime` caller recovers onto.
This needs no wired controller — PROBE D/E above is already the shape.

## What this fix does NOT do
- Does **NOT** retune any weight in `RouteCostCalculator` — those are
  TUNABLE by E04's own note and changing them is not this fix's call.
- Does **NOT** change the improvement-ratio or stability-window constants,
  nor add any second migration heuristic.
- Does **NOT** wire `CallMigrationController` into the app — that is `E07-B03`.
- Does **NOT** touch `DashboardController`'s connectivity reading: polling
  `computeRoute` there is correct; the defect is that `onRouteFailure`
  depends on who called last.
- Does **NOT** touch `RelayEngine`'s own profile handling, which is correct.

## Fix (implemented)

Took the durable fix direction verbatim: `RoutingEngine.onRouteFailure`
now takes an explicit `TrafficProfile profile` parameter instead of
reading a sticky `_lastProfile[destinationId]` map. That map is removed
entirely (`computeRoute`/`considerMigration` no longer write to it — it
had no other reader). Both production call sites updated to pass their
own, always-known profile: `RelayEngine._attempt` passes its own
`_profile` field; `CallMigrationController.notifyRouteFailure` passes
`TrafficProfile.realtime` explicitly.

`DashboardController`'s own `computeRoute(peerId, interactive)` polling
is untouched — it was never the defect; the defect was `onRouteFailure`
trusting shared, caller-agnostic state instead of asking its own caller.
