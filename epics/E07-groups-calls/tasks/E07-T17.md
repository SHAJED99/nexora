# E07-T17 · The group-thread contract

## 1. Goal
`GAP-020` was approved on 2026-08-31 with its build gated on `OQ-E07-13`, and
it deliberately left the contract unwritten:

> "Whoever writes that contract inherits this paragraph and answers
> `OQ-E07-13` first."

The human answered `OQ-E07-13` on **2026-09-25**. This task writes the
contract, so `E07-T18` can build the thread.

## 2. The answer this contract encodes
Human, 2026-09-25, verbatim: *"In a group thread, a blocked member's messages
should remain represented as placeholders rather than being silently dropped
or rendered as normal readable messages."*

Encoded as state 3 (`bubble-blocked-placeholder`) with three rules: the
message is represented, its body is not readable, and it keeps its sender
attribution.

## 3. Contract
`design/screens/chat-group.md`, `source: derived`, `derived_from: [chat,
conversations]`, five states. Every token cited by name from an already
measured table; **no new colour, size, radius or font**.

Two things are derived rather than copied, and both are named in the file:
- **the group avatar.** `chat.md` element 3 is a 38×38 per-person image and a
  group has no single person. `conversations.md` element 22 already solved
  this with the `dns` glyph; reused, not invented.
- **the route.** `/groups/[id]`, not `/chat/[id]` — see §4.

## 4. Why a separate route
`ChatController` is structurally 1:1: it treats `conversationId` as a Signal
**peer device id**. `E07-B01` measured what a group id does there and the
human closed that route to group ids (2026-09-02, P1, direction (a));
`E07-B05` re-closed a second door into it this session. `E07-B01`'s own
§What this fix does NOT do forbids widening `ChatController` into a
multi-party controller. A separate route keeps that invariant instead of
eroding it.

## 5. The two things this contract could not derive

### 5a. The blocked-member placeholder copy
The human decided the **behaviour**; no source supplies the **words**, and the
existing `(unable to decrypt this message)` primitive would be **false** here
— a blocked member holds a valid sender key, so the message decrypts; it is
withheld by policy, not by failure.

Rule 2 requires a derived element to be human-approved **before** it is built,
so the contract invents no string. It took **two review rounds** to get this
right, and both corrections are worth recording:

1. The first draft proposed a string and directed `E07-T18` to build it
   unapproved, reasoning that the human had said *"proceed to build the
   complete group-thread journey"*. The reviewer called that a rule-2
   violation dressed as pragmatism. Correct.
2. The second draft swung to an **empty bubble body** — no invented words,
   all three of the human's rules technically satisfied. The reviewer pointed
   out what that actually renders: the measured inbound bubble is a filled
   surface, so a name and a timestamp over an empty body reads as *a message
   that failed to load*. That is a different claim about the app than "this
   sender is blocked", and arguably worse than the
   `(unable to decrypt this message)` string this contract already rejects as
   false. There is no honest interim.

3. The third draft said state 3 was blocked but left the *runtime* behaviour
   unstated. The reviewer's answer to "so what does the app render today?"
   exposed the last error: a thread with states 1, 2, 4 and 5 but no state 3
   renders a blocked member's message as an **ordinary readable bubble** —
   precisely what the human's answer forbids. Shipping four of five states is
   not a partial win; it is a regression against a decision already taken.

**Conclusion: `E07-T18` — the whole thread build — is gated on `GAP-045`,
not just state 3.** One string, three candidates, one human answer. Until
then the app keeps the behaviour it already ships and already reviewed: a
group row tap is non-navigating and acknowledges itself
(`ConversationsController.openGroup`, `E07-B01` direction (a), 2026-09-02).

Three review rounds to reach that, and each round the error was the same
shape: preferring a shippable-looking outcome over an honest one.

### 5b. G11's `14px` + `rgb(70, 69, 85)` pairing
`GAP-020`'s human-approved text specifies the event line as *"`chat.md`'s own
secondary-text treatment (14px `rgb(70, 69, 85)`)"*. In `chat.md`'s measured
table that colour appears **only at 12px**; 14px appears at `rgb(11, 28, 48)`.
**The pair does not exist in the parent contract.**

The contract writes GAP-020's approved wording and **discloses the
discrepancy inline** rather than silently normalising to 12px — normalising
would quietly contradict an approved gap, which is the worse of the two
errors. If the human wants 12px instead, that is a one-value change; it is
listed in the decision package.

## 6. What this task does NOT do
- Does **NOT** build anything. No `lib/` or `test/` file is touched.
- Does **NOT** hand-edit `chat.md` or `conversations.md` — both are measured
  and generated (`design-fidelity` rule 1).
- Does **NOT** cover attachments, voice, PTT, location or calls inside a
  group thread; each has its own contract and its own gap.
- Does **NOT** cover group membership management (`group-manage.md`).
- Does **NOT** approve `GAP-045`, and does **NOT** build its copy. The
  `approved by:` line is left pending, never signed by an agent
  (`L-process-002`).
