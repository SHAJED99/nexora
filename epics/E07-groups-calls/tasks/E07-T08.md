# E07-T08 · Groups section, populated

## 1. Goal
Turn the Conversations screen's `Groups` heading from an empty-state
placeholder into the three-row treatment the design actually draws —
closing the one design gap E06 explicitly deferred to this epic.

## 2. Business logic
- **This closes `GAP-006`.** That entry reads: *"E06 renders the `Groups`
  heading exactly as the contract measures it, with a single centered
  subtitle line in place of the three rows… The three group rows are
  recorded here as knowingly-absent **until E07 populates them**"*, and its
  `built:` line says *"rows deferred to E07"*. This is that task, and it is
  a named inherited obligation, not new scope. GAP-006's status flips from
  ⚪ deferred to built when this merges.
- **The design already specifies the group row** (`design/screens/
  conversations.md`, elements 21-33): the `Groups` `heading:2` at 22px
  w500 `rgb(234, 241, 255)`; per row a leading transport/status glyph
  (`dns`, `group_off`), the group name at w500 `rgb(11, 28, 48)`, a
  timestamp at 12px w500 `rgb(70, 69, 85)`, a preview at 14px
  `rgb(70, 69, 85)`, an optional **sender-name prefix** at 14px w500
  `rgb(11, 28, 48)` (`David Chen:`), an optional `cloud_off`, and a
  trailing `lock`. No element of that is invented here — every one is
  measured, and every one must appear.
- **The sender-name prefix is assembled in this layer, not in the read
  model.** `ConversationSummary` deliberately carries no `previewText`
  (E06-T09 §2, restated by E07-T07 §2). The controller decrypts the last
  message for display and prefixes the sender's display name — exactly the
  division E06-T10 already implements for the Personal section.
- **The empty state stays.** A user with no groups still sees the `Groups`
  heading and GAP-006's approved copy, `"No groups yet"`. Rendering the
  heading only when groups exist would delete a measured design element,
  which rule 2 and design-fidelity rule 3 both forbid.
- **The delivery-glyph mapping is GAP-009's, shared, not re-derived.**
  `E06-B03` was filed precisely because this screen built its own glyph
  mapping before Chat had one. Import the same mapping; do not write a
  second `switch`.
- **Groups are not filtered by block state** (E07-T07 §2). A blocked
  contact being in a group does not hide the group.

## 3. What this task does
- `ConversationsController`: consume `ConversationKind` from the widened
  `watchConversations()`, split into `personal` and `groups` lists, expose
  `groupRows` with the fields the design's row needs (name, timestamp,
  preview, sender prefix, connectivity glyph, delivery glyph).
- `ConversationsView`: replace the `GAP-006` empty subtitle with the real
  row list when `groups.isNotEmpty`, keeping the empty treatment for the
  zero case, and keeping the `Groups` heading unconditionally.
- Tapping a group row navigates to `/chat/:conversationId` with the group
  id — the same route the Personal rows already use, since a group
  conversation id is an ordinary conversation id (E07-T07 §2). The *thread*
  rendering differences a group needs (per-sender attribution, membership
  event lines) are **GAP-020's**, not this task's.
- The design gate re-run and its report recorded verbatim in the Run log,
  as every E06 UI task did.

## 4. What this task does NOT do
- Does **NOT** build the group thread view, per-sender attribution inside
  the thread, or membership-event system lines — GAP-020, prospective.
- Does **NOT** build group creation or management UI — GAP-018/GAP-019,
  prospective, blocked on `design_contract_approval`. **Do not add a
  "create group" affordance**, not even a disabled one: the design draws
  none on this screen, and inventing one is exactly the rule-2 violation in
  the "never silently invent" direction.
- Does **NOT** re-derive the delivery-glyph mapping (§2, `E06-B03`).
- Does **NOT** swap any `InkWell`/`GestureDetector` for a raw `Listener`
  to score better against the probe — `design-fidelity` **Rule 5**
  (L-frontend-001), promoted after `E06-T10` did exactly that and lost
  gesture-arena and accessibility behaviour. If a correct widget costs gate
  score, record the cause; do not reshape the tree.
- Does **NOT** touch the Chat or Dashboard screens, `routes.dart`, or any
  file under `lib/core/` or `lib/features/messaging/`.
- Does **NOT** fix the known delivery-tick **colour**-token divergence
  across chat/dashboard/conversations (E06 retro §5) — out of fence, a
  future S4 chore.

## 5. Contract

### UI
- **Design contract:** `design/screens/conversations.md` — elements 21-33
  are this task's; build from the contract, not from the screenshot.
- **Route:** `/conversations` (existing). Navigation: group row →
  `/chat/:conversationId`.
- **States required:** data (≥1 group) · empty (`"No groups yet"`, GAP-006's
  approved copy) · loading (the existing shared treatment) · error (the
  existing shared treatment).
- **Gate:** `make design-verify SCREEN=conversations` run and its report
  recorded **before the PR**. The score must not regress below E06-B03's
  last recorded 21.1% (12/57); every remaining finding must trace to a
  named known cause (the T01 probe-dumper icon-swallowing, `OQ-E06-T01-1`'s
  font gap) or to an approved `design/gaps.md` entry.

## 6. Risks
- The gate score is dominated by known, already-attributed causes. Read
  `E06-T10`'s and `E06-B03`'s Run logs before running it, so a
  pre-existing finding is not re-diagnosed as a new one (three E06 reviews
  lost time to exactly this).
- Decrypting the last message per group row on the UI thread will stutter a
  long list. E06-T10 already solved this shape for Personal; reuse its
  approach rather than inventing a second one.
- The `Groups` heading must render in **both** states. The easy mistake is
  to wrap heading + rows in one conditional, which silently deletes a
  measured element in the empty case and fails the gate for a reason that
  looks like a data problem.

  SHALL still render the `Groups` heading with the approved empty
