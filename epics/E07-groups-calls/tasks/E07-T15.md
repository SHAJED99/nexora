# E07-T15 · Group create screen — build `/groups/new` against its approved contract

> **Why this task exists at all.** `E07-T12` (a `layer: docs` task) wrote
> `design/screens/group-create.md` and was correctly marked done. No build task
> was ever created for it, and E07 then closed as `status: done`. The
> 2026-09-24 product-completeness audit found the result: the group backend is
> complete and **nothing renders it** — a person cannot create a group at all.
> See `docs/product-completeness-audit.md`.

## 1. Goal
A person with at least one trusted contact can name a group, pick members, and
create it — landing in the new group's thread — so that `FR-GROUP-001`'s roles
and `FR-GROUP-002`'s Owner powers have a group to apply to.

## 2. Business logic
Implements `FR-GROUP-001` (a group with roles must first exist),
`FR-GROUP-002` (the Owner's powers presuppose a group someone created) and
`FR-COMM-002` (group communication).

- The member list is the **trusted** relationships only —
  `RelationshipRepository.listAll()` filtered to `RelationshipState.trusted`.
  Trust is read, never assigned here.
- `Create group` is **disabled until a non-empty name AND ≥1 selected member
  exist**. `FR-GROUP-002` presupposes a named group with members; the contract
  states this as the `default` state's rule.
- Creation calls `GroupMembershipService.createGroup(name:, memberDeviceIds:)`,
  which returns the new group id. **It throws `AppFailure`** rather than
  returning a nullable failure — documented at
  `group_membership_service.dart:352`. Catch it.
- On success, navigate to `/chat/<groupId>` (the contract's "Leads to").
- On failure, render state `error` and **do not clear the entered name or the
  selection** — the contract says so explicitly.
- The creator becomes Owner. That is `E07-T03`'s doing. **This screen renders
  no role.**
- Whether a *blocked* peer may be added is `E07-T03`'s composition of
  `GroupPermissions` with `RelationshipRepository`. Never re-decided in a
  widget.

## 3. What this task does
- Adds `GroupCreateController` — trusted-contact load, selection state, name
  state, the derived `canCreate`, and the create/failure path.
- Adds `GroupCreateView` — all 16 contract elements GC1–GC16 across the four
  contract states (`default`, `empty`, `loading`, `error`).
- Adds `GroupCreateBinding`.
- Registers `Routes.groupCreate = '/groups/new'` in `lib/app/routes.dart` and
  adds its row to `docs/routes.md`'s table.
- Registers the screen in `test/design/design_probe_test.dart` so
  `make design-probe` dumps it and `make design-verify SCREEN=group-create
  IMPL=flutter` can gate it.
- Unit tests for the controller, named by EARS id.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT add any affordance to `conversations.md` or its view.** The
  create-group entry point is `group-create.md` §Open, explicitly **⏳ awaiting
  the human** and **not** covered by GAP-018's clearance. Until it is approved,
  `/groups/new` is reachable only by direct navigation. Adding a header button
  here would forge that clearance. This is the single most tempting wrong move
  in this task.
- **Does NOT edit `design/screens/group-create.md`**, `conversations.md`,
  `devices.md`, `design/gaps.md` or `design/thresholds.yaml`. Rule 2:
  contracts are law, never edited to fit a build.
- **Does NOT touch `lib/core/design/tokens.dart`.** Every value comes from
  this contract's own measured token table, declared locally in the view —
  the same convention `conversations_view.dart` documents at its head.
- Does NOT build `/groups/:id` (group-manage) — that is `E07-T16`.
- Does NOT add a search field over the member list — the contract's §Notes
  forbids it; it would be a second instance of GC5's primitive with no spec id.
- Does NOT change `GroupMembershipService`, `GroupRepository`,
  `RelationshipRepository` or any backend file.
- Does NOT add a spinner or skeleton for `loading` — the design draws none
  anywhere, so the contract defines that state as the frame with an
  unpopulated list.
- Does NOT invent an error colour. The contract refuses one; the failure is
  carried by the words (GC16).

## 6. Risks
1. **`E06-B01`'s `RenderFlex` trap, in exactly this row shape.** A trailing
   widget after a `Spacer()` with no width bound overflowed by 57px and hung
   the test harness for its full 10-minute timeout. The contract calls the row
   layout "load-bearing, not cosmetic". The trailing slot (GC12–GC14) is
   fixed-width; the name (GC9) is the flexible child with an ellipsis overflow
   policy. A contact name is user-supplied and arbitrarily long.
2. **`createGroup` throws, it does not return a failure.** Every sibling
   method on that service returns `Future<AppFailure?>`. Writing the usual
   `final f = await ...; if (f != null)` here compiles and silently never
   catches. `group_membership_service.dart:352` documents the exception.
3. **The disabled primary button must not invent a token.** The contract
   specifies the *same* button with its label at `rgb(119, 117, 135)` — no
   opacity, no new fill.
4. **`empty` must keep the `Members` heading.** Deleting a measured element to
   satisfy the data layer is a design-fidelity rule-3 violation; `empty`
   differs from `default` only in the list area's content.

## 8. Acceptance criteria (EARS) + test plan

- **EARS-GROUP-17**: WHEN the screen loads, the system SHALL present every
  trusted relationship as a selectable member row, and no untrusted one.
  (`FR-GROUP-002`)
- **EARS-GROUP-18**: WHILE either the group name is empty or no member is
  selected, the system SHALL keep the create action disabled.
  (`FR-GROUP-001`, `FR-GROUP-002`)
- **EARS-GROUP-19**: WHEN the create action is invoked with a name and ≥1
  member, the system SHALL create the group with exactly the selected members
  and navigate to that group's thread. (`FR-GROUP-001`, `FR-COMM-002`)
- **EARS-GROUP-20**: IF creation fails, THEN the system SHALL present the
  failure and SHALL preserve the entered name and the member selection.
  (`FR-GROUP-002`)

### Tests
- `test_EARS_GROUP_17_only_trusted_relationships_become_member_rows` → seeds
  trusted + allowed + blocked + unknown; asserts only the trusted ones appear.
- `test_EARS_GROUP_18_create_disabled_until_name_and_member` → asserts
  `canCreate` across the four combinations of (name empty/non-empty) ×
  (0/1 selected).
- `test_EARS_GROUP_19_create_passes_selected_members_and_navigates` → asserts
  the exact `memberDeviceIds` passed to the service and the route pushed.
- `test_EARS_GROUP_20_failure_preserves_name_and_selection` → makes
  `createGroup` throw `AppFailure`; asserts `failed` is set and that name and
  selection are unchanged.

### Manual
1. Launch → navigate to `/groups/new` directly (no entry point exists yet —
   see §4) → expect the `New Group` frame.
2. With no trusted contacts → expect `No trusted contacts yet`, `Members`
   heading still present, create disabled.
3. With trusted contacts → type a name, select one → create enables → tap →
   lands in the group thread.
