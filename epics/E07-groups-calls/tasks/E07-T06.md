# E07-T06 · Group message send/receive

## 1. Goal
Make FR-COMM-002 real for text: a member composes a message, it is
encrypted once with the group's sender chain, delivered to every other
current member over the existing relay/routing stack, and stored on each
receiving device in the same `messages` table the 1:1 path already uses.

## 2. Business logic
- **Encrypt once, address N times.** The Sender-Keys property is that one
  `SenderKeyMessage` is produced per message regardless of member count
  (E07-T04). Fan-out happens at the *routing* layer: one
  `RelayPacketFrame` per recipient, each carrying the *same* payload
  bytes, each with its own `destination`. This is what makes groups
  cheaper than N pairwise encryptions and it is the reason ADR-0003 chose
  this family.
- **The group's `conversationId` is the group id** (E07-T01 §2, widening
  E06-T09's documented-opaque field). Group messages are ordinary
  `messages` rows: same table, same `delivery_state` machine, same keyset
  pagination. **No parallel message table.**
- **`sequenceNumber` stays monotonic per `(conversationId,
  senderDeviceId)`** — exactly `message_tables.dart`'s existing contract,
  which already accommodates a group because the pair is per-sender, not
  per-conversation. Do not invent a group-wide sequence; there is no
  authority to mint one (ADR-0005: no server).
- **A group message carries its epoch on the wire.** The receiver must
  know which chain to try, and must not guess. `GroupMessageEnvelope` =
  `{groupId, epoch, senderDeviceId, messageId, sequenceNumber,
  createdAtMs, body}`, encrypted as a unit by
  `GroupCryptoService.encryptForGroup`. An epoch mismatch is a hard,
  explicit failure (`group.no_chain`), never a fallback to another epoch —
  falling back is how FR-GROUP-005 dies quietly.
- **The relay/forward path never decodes a group payload** (FR-ROUTE-003,
  the confidentiality boundary E06-T05 asserts with a test that fails if
  `decrypt` is called on the forward branch). A group frame addressed to
  someone else is forwarded as opaque bytes, identically to a 1:1 frame.
- **Delivery state for a group message is per-message, not per-recipient,
  in v1.** `Sent` means "durably enqueued locally" (E05-B03's human
  resolution). Per-recipient `Delivered`/`Read` for groups would need an
  N-way ack aggregation that the design draws nothing for and that
  FR-COMM-002 does not require — explicitly out of scope, recorded in §4
  rather than half-built.
- **Non-members and removed members are refused at send time** via
  `GroupPermissions.allows(sendMessage)` plus a current-membership check,
  and their *inbound* group messages are dropped and counted rather than
  stored — a message from a device the local table does not list as a
  current member is not a group message, whatever it claims.

## 3. What this task does
- **`GroupMessageEnvelope`** — deterministic binary encode/decode, same
  length-prefixed style as `MessageEnvelope` and `RelayPacketFrame`.
- **`SendGroupMessageUseCase.send({required String groupId, required
  Uint8List body})`:**
  1. permission + current-membership check
  2. reserve `sequenceNumber` and mint the message id (reusing the same
     transactional reservation shape `SendMessageUseCase` already uses —
     **call it, do not re-implement it**, and if it cannot be called from
     here, stop and raise it rather than copying the logic)
  3. `encryptForGroup(groupId, currentEpoch, envelope.serialize())`
  4. persist one `messages` row (`conversationId = groupId`, state
     `Queued` → `Sent` per the existing state machine)
  5. one `RelayEngine.enqueue` per current member except self, all sharing
     the one payload
- **Inbound handling** in `InboundPipeline`: a decrypted payload whose
  envelope is a `GroupMessageEnvelope` is routed to the group path —
  membership check → `decryptFromGroup(groupId, epoch, sender, …)` →
  dedupe by `messageId` → persist → emit on the existing `delivered`
  stream so `DeliveryAckService` and the read model behave unchanged.
- New `InboundCounters` fields: `groupNotAMember`, `groupNoChain`,
  `groupEpochUnknown` — a dropped group message is observable.

## 4. What this task does NOT do
- Does **NOT** add per-recipient delivery/read state for groups (§2). The
  existing single `delivery_state` column is what a group message gets.
- Does **NOT** implement typing indicators, reactions, replies, mentions,
  or group voice/PTT/attachments/location. FR-COMM-002 names PTT, voice
  calls, attachments and group events; **this task covers text and the
  membership events E07-T03 already produces**, and the rest are
  explicitly other tasks or other epics. Do not opportunistically add a
  media branch.
- Does **NOT** touch `SendMessageUseCase`, `ReceiveMessageUseCase`,
  `RelayEngine`, `RoutingEngine`, `relay_packet_frame.dart` or
  `messaging_stack.dart`.
- Does **NOT** decrypt anything on the forward branch (FR-ROUTE-003).
- Does **NOT** write `RelayDeliveryState.failed` (`OQ-E06-T06-3`'s
  standing constraint stays untriggered).
- Does **NOT** add a table, column or migration.
- Does **NOT** build UI. The Groups list is E07-T07/T08; a group *thread*
  view is prospective and blocked on its design contract (GAP-020).

## 6. Risks
- **The dedupe key must be `messageId`, not `(sender, sequenceNumber)`.**
  In a group, the same message arrives once per route, and with multi-hop
  relaying it can arrive more than once from different neighbours. The
  existing 1:1 dedupe already keys on the message id; reuse it rather than
  writing a group-specific one.
- Reusing `SendMessageUseCase`'s sequence-reservation transaction from a
  different use case is the likeliest place to hit a private-member wall
  (E06-T03 hit exactly this shape with `_localSignalDeviceId`). If the
  reservation is not reachable, **raise it as an Open Question** — copying
  the transaction is how two writers of one counter appear, which is
  L-backend-003's whole subject.
- One payload, N frames: it is tempting to serialize the frame once and
  mutate `destination` per recipient. `RelayPacketFrame` is immutable by
  construction; build N frames sharing one `payload` reference. Mutating a
  serialized buffer in place is how one recipient's frame ends up
  addressed to another.
- A member who has not yet received the current epoch's distribution will
  fail every inbound message with `group.no_chain` until it lands. That is
  correct (E07-T05 §2) and it will look like a bug in manual testing. Make
  the counter and the failure code distinct enough that it is diagnosable.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-29**: WHEN a member sends a group message, the system SHALL
  encrypt it once with the group's current-epoch chain and enqueue one
  frame per other current member. (FR-COMM-002)
- **EARS-COMM-30**: WHEN a group message is received from a current
  member, the system SHALL decrypt it with that sender's chain for the
  message's epoch and store it under the group's conversation id.
  (FR-COMM-002, FR-MSG-002)
- **EARS-COMM-31**: IF a group message arrives from a device that is not a
  current member of that group, THEN the system SHALL discard it without
  storing it. (FR-GROUP-005)
- **EARS-COMM-32**: IF the same group message arrives more than once, THEN
  the system SHALL store it exactly once. (FR-MSG-003)
