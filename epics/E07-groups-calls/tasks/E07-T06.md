# E07-T06 · Group message send/receive

## 1. Goal
Make FR-COMM-002 real for text: a member composes a message, it is
encrypted once with the group's sender chain, delivered to every other
current member over the existing relay/routing stack, and stored on each
receiving device in the same `messages` table the 1:1 path already uses.

## 2. Business logic
- **Encrypt once, address N times.** The Sender-Keys property is that one
  `SenderKeyMessage` is produced per message regardless of member count
  (E07-T04). Fan-out happens at the *routing* layer: one
  `RelayPacketFrame` per recipient, each carrying the *same* payload
  bytes, each with its own `destination`. This is what makes groups
  cheaper than N pairwise encryptions and it is the reason ADR-0003 chose
  this family.
- **The group's `conversationId` is the group id** (E07-T01 §2, widening
  E06-T09's documented-opaque field). Group messages are ordinary
  `messages` rows: same table, same `delivery_state` machine, same keyset
  pagination. **No parallel message table.**
- **`sequenceNumber` stays monotonic per `(conversationId,
  senderDeviceId)`** — exactly `message_tables.dart`'s existing contract,
  which already accommodates a group because the pair is per-sender, not
  per-conversation. Do not invent a group-wide sequence; there is no
  authority to mint one (ADR-0005: no server).
- **A group message carries its epoch on the wire.** The receiver must
  know which chain to try, and must not guess. `GroupMessageEnvelope` =
  `{groupId, epoch, senderDeviceId, messageId, sequenceNumber,
  createdAtMs, body}`, encrypted as a unit by
  `GroupCryptoService.encryptForGroup`. An epoch mismatch is a hard,
  explicit failure (`group.no_chain`), never a fallback to another epoch —
  falling back is how FR-GROUP-005 dies quietly.
- **The relay/forward path never decodes a group payload** (FR-ROUTE-003,
  the confidentiality boundary E06-T05 asserts with a test that fails if
  `decrypt` is called on the forward branch). A group frame addressed to
  someone else is forwarded as opaque bytes, identically to a 1:1 frame.
- **Delivery state for a group message is per-message, not per-recipient,
  in v1.** `Sent` means "durably enqueued locally" (E05-B03's human
  resolution). Per-recipient `Delivered`/`Read` for groups would need an
  N-way ack aggregation that the design draws nothing for and that
  FR-COMM-002 does not require — explicitly out of scope, recorded in §4
  rather than half-built.
- **Non-members and removed members are refused at send time** via
  `GroupPermissions.allows(sendMessage)` plus a current-membership check,
  and their *inbound* group messages are dropped and counted rather than
  stored — a message from a device the local table does not list as a
  current member is not a group message, whatever it claims.

## 3. What this task does
- **`GroupMessageEnvelope`** — deterministic binary encode/decode, same
  length-prefixed style as `MessageEnvelope` and `RelayPacketFrame`.
- **`SendGroupMessageUseCase.send({required String groupId, required
  Uint8List body})`:**
  1. permission + current-membership check
  2. reserve `sequenceNumber` and mint the message id (reusing the same
     transactional reservation shape `SendMessageUseCase` already uses —
     **call it, do not re-implement it**, and if it cannot be called from
     here, stop and raise it rather than copying the logic)
  3. `encryptForGroup(groupId, currentEpoch, envelope.serialize())`
  4. persist one `messages` row (`conversationId = groupId`, state
     `Queued` → `Sent` per the existing state machine)
  5. one `RelayEngine.enqueue` per current member except self, all sharing
     the one payload
- **Inbound handling** in `InboundPipeline`: a decrypted payload whose
  envelope is a `GroupMessageEnvelope` is routed to the group path —
  membership check → `decryptFromGroup(groupId, epoch, sender, …)` →
  dedupe by `messageId` → persist → emit on the existing `delivered`
  stream so `DeliveryAckService` and the read model behave unchanged.
- New `InboundCounters` fields: `groupNotAMember`, `groupNoChain`,
  `groupEpochUnknown` — a dropped group message is observable.

## 4. What this task does NOT do
- Does **NOT** add per-recipient delivery/read state for groups (§2). The
  existing single `delivery_state` column is what a group message gets.
- Does **NOT** implement typing indicators, reactions, replies, mentions,
  or group voice/PTT/attachments/location. FR-COMM-002 names PTT, voice
  calls, attachments and group events; **this task covers text and the
  membership events E07-T03 already produces**, and the rest are
  explicitly other tasks or other epics. Do not opportunistically add a
  media branch.
- Does **NOT** touch `ReceiveMessageUseCase`, `RelayEngine`,
  `RoutingEngine`, `relay_packet_frame.dart` or `messaging_stack.dart`.
- **`SendMessageUseCase`: amended 2026-09-01 (planner, resolving
  `OQ-E07-T06-1`).** Originally excluded outright. Now permits **exactly
  one** change and nothing else: moving its phase-1 sequence-reservation
  transaction body verbatim into `MessageSequenceReserver` and calling that
  instead. Its behaviour, ordering, public API and error handling are
  unchanged. Every other part of that file stays untouched.
- Does **NOT** decrypt anything on the forward branch (FR-ROUTE-003).
- Does **NOT** write `RelayDeliveryState.failed` (`OQ-E06-T06-3`'s
  standing constraint stays untriggered).
- Does **NOT** add a table, column or migration.
- Does **NOT** build UI. The Groups list is E07-T07/T08; a group *thread*
  view is prospective and blocked on its design contract (GAP-020).

### Data
**None.** Group messages are rows in the existing `messages` table.

## 6. Risks
- **The dedupe key must be `messageId`, not `(sender, sequenceNumber)`.**
  In a group, the same message arrives once per route, and with multi-hop
  relaying it can arrive more than once from different neighbours. The
  existing 1:1 dedupe already keys on the message id; reuse it rather than
  writing a group-specific one.
- Reusing `SendMessageUseCase`'s sequence-reservation transaction from a
  different use case is the likeliest place to hit a private-member wall
  (E06-T03 hit exactly this shape with `_localSignalDeviceId`). If the
  reservation is not reachable, **raise it as an Open Question** — copying
  the transaction is how two writers of one counter appear, which is
  L-backend-003's whole subject.
- One payload, N frames: it is tempting to serialize the frame once and
  mutate `destination` per recipient. `RelayPacketFrame` is immutable by
  construction; build N frames sharing one `payload` reference. Mutating a
  serialized buffer in place is how one recipient's frame ends up
  addressed to another.
- A member who has not yet received the current epoch's distribution will
  fail every inbound message with `group.no_chain` until it lands. That is
  correct (E07-T05 §2) and it will look like a bug in manual testing. Make
  the counter and the failure code distinct enough that it is diagnosable.

**Deviations from spec/design:**
1. **The sequence-number reservation seam (`ReserveGroupSequenceFn`) is
   declared and injected, but left UNBOUND in production — `OQ-E07-T06-1`,
   below.** `SendMessageUseCase.call`'s own reservation transaction
   (`send_message_use_case.dart:201-227`) is inlined over private fields
   (`_db`, `_selfDeviceId`) and a private id generator, with no smaller
   public entry point exposing just that phase, and `call()` itself cannot
   be reused wholesale either (it does a single-recipient pairwise encrypt
   and a single enqueue, both wrong for a group send). This is exactly the
   "private-member wall" the task's own §3/§6 anticipated and instructed:

   stop and raise it rather than copying the logic." Rather than either (a)
   duplicating the read-MAX-then-insert transaction inside this task's own
   file (L-backend-003's subject — two independent writers of the same kind
   of invariant, even though the `groupId`/1:1-`conversationId` keyspaces
   are disjoint in practice) or (b) touching `send_message_use_case.dart`
   itself (protected, outside this task's `files:` fence), the reservation
   is exposed as an injected, function-typed seam
   (`ReserveGroupSequenceFn`) — the same DI pattern `SendMessageUseCase`
   itself already uses for `MessageEncryptFn`/`MessageEnqueueFn` rather than
   depending on concrete classes directly. Every other step of `send()` is
   fully implemented and exercised against a REAL `AppDatabase` via a
   test-only fake implementing the exact same atomic shape
   (`send_group_message_use_case_test.dart`'s `reserveSequenceFake`) — only
   the seam's PRODUCTION binding (wherever `SendGroupMessageUseCase` is
   eventually constructed for real, which is outside this task's scope
   since `messaging_stack.dart` is not in `files:`) is left for whoever
   resolves `OQ-E07-T06-1`.
   <br>**Resolution (planner, 2026-09-01):** the seam is now BOUND. The
   reservation transaction was extracted from `SendMessageUseCase.call` into
   `MessageSequenceReserver` and both use cases call it — one implementation,
   two call sites. `ReserveGroupSequenceFn` became optional and defaults to
   it. Full reasoning, rejected alternatives, fence amendment and test
   evidence: `OQ-E07-T06-1`'s answer. The *composition-root* half of the
   deviation's last sentence remains open and is now tracked separately as
   `OQ-E07-T06-2`.
2. **No change to `messaging_stack.dart` at all — controlKind 5
   (`kControlKindGroupMessage`) is self-registered inside
   `InboundPipeline`'s own constructor**, not wired externally the way
   T07/T08/T03/T04's control handlers were (each via a
   `messaging_stack.dart` call site). This task's `files:` fence updates
   `inbound_pipeline.dart` directly and does not touch
   `messaging_stack.dart`, so there is no external composition-root call
   site available the way those four tasks each had. The registered
   handler is a closure (`(frame) => _handleGroupMessageWireFrame(frame)`),
   not an eager tear-off, so it never dereferences `_stack.groupCryptoService`
   at construction time — avoiding the exact `LateInitializationError`
   ordering hazard E07-T05's own §9 Deviation 2 already documented for the
   identical constructor-ordering reason.
3. **A second wire structure, `GroupMessageRoutingHeader`, was added to
   `group_message_envelope.dart` beyond §5's literal two-function/one-class
   list.** `GroupCryptoService.decryptFromGroup(groupId, epoch,
   senderDeviceId, bytes)` (E07-T04, protected — not in this task's
   `files:`) needs `groupId`/`epoch` BEFORE it can attempt a decrypt, to
   select which `SenderKeyName` chain to try — but per §2's own wording,
   `GroupMessageEnvelope` (carrying `groupId`/`epoch` internally) is itself
   what gets encrypted as a unit via `encryptForGroup(groupId, epoch,
   envelope.serialize())`, so those fields are NOT available in the clear
   pre-decrypt from the envelope alone. `GroupMessageRoutingHeader` is the
   minimal clear wrapper (`groupId`, `epoch`, opaque `ciphertext`) carried
   in the control frame's payload alongside the controlKind byte, read by
   `InboundPipeline` before it can call `decryptFromGroup` at all. This
   mirrors `GroupCryptoService`'s own private `_KeyDistributionEnvelope`
   (E07-T04's own §9 Deviation: "an implementation necessity of the
   documented contract, not a scope addition") — the only difference is
   this one must be public, since the sending half
   (`send_group_message_use_case.dart`) and the receiving half
   (`inbound_pipeline.dart`) are two different files and a shared wire
   format needs exactly one definition (the same discipline
   `message_envelope.dart`'s own header names E05-B01 as a defect for not
   having). `senderDeviceId` is deliberately NOT part of this header —
   `RelayPacketFrame.source` (already clear on every wire frame) is an
   equally-good routing candidate, so duplicating it would only add a
   second unauthenticated copy of the same non-authoritative hint.
4. **Receive-side step ordering deviates from §3's literal prose** ("a
   decrypted payload ... membership check → decryptFromGroup(...) →
   dedupe... "; §3's own bullet list literally reads "membership check"
   before "decryptFromGroup"). Read literally that would require checking
   membership BEFORE decrypt, but the only identity available pre-decrypt
   is `frameSourceDeviceId` — not the AUTHORITATIVE `envelope.senderDeviceId`
   §5's own contract insists the membership check must use ("regardless of
   what the envelope claims", §2). Performing the real, security-relevant
   membership check against an unauthenticated candidate would defeat the
   exact property that instruction protects (E06-B04). Implemented instead
   as: (1) a cheap, identity-free CLEAR `(groupId, epoch)` recognition check
   against this device's own `groups.membershipEpoch` (`groupEpochUnknown`
   — no crypto needed, nothing to authenticate yet); (2) decrypt, candidate-
   keyed by `frameSourceDeviceId` (mirrors `GroupMembershipService.
   handleWireFrame`'s own established treatment of `frame.source` as a
   decrypt-selection candidate only); (3) the REAL, authoritative
   membership check against `envelope.senderDeviceId` post-decrypt; (4)
   dedupe by `messageId`; (5) persist. Every EARS criterion this task names
   is satisfied by this order, and the more specific, safety-critical
   "never frameSourceDeviceId" rule is treated as taking precedence over
   the prose's literal step sequence — documented in `inbound_pipeline.dart`'s
   own header rather than silently reordered.
5. **A real production gap found and fixed during test development:**
   `GroupCryptoService.decryptFromGroup` (E07-T04, protected) does not map
   libsignal's `DuplicateMessageException` — thrown when a group-cipher
   message key has already been consumed, exactly the case a genuinely
   re-arriving wire packet (task file §6: multi-hop relaying can deliver
   the same message down two routes) produces on its second decrypt
   attempt — to any `AppFailure`; it `rethrow`s the raw library exception.
   Since that file is outside this task's `files:` fence, the mapping is
   done at the call site in `inbound_pipeline.dart` instead: matched by
   `runtimeType` name (mirroring `crypto_failures.dart`'s own
   `mapSignalException` discipline, for the identical reason — the type
   isn't exported from `libsignal_protocol_dart`'s public barrel) and
   counted as `counters.duplicate`, the SAME counter FR-MSG-003's existing
   1:1 dedup signal already uses, never `undecryptable`. Found by
   `test_EARS_COMM_32_duplicate_delivery_stores_once` genuinely failing
   (`duplicate: 0` instead of `1`) against the first version of this file's
   receive branch, which only mapped `AppFailure`/generic exceptions to
   `undecryptable` — confirmed the right root cause by re-running with a
   temporary debug print of every counter before writing the fix, removed
   before commit.
