# E07-T04 · Sender-key store + distribution

> ⛔ **Read `OQ-E07-8` (this file) before writing code.** ADR-0003 accepted
> the Sender-Keys *family* and explicitly deferred "how it layers on the 1:1
> protocol" to this epic's sharding. That layering is specified below; the
> one part that is genuinely a human call — the schema it persists into —
> lives in `E07-T01`'s `OQ-E07-4`, which must read 🟢 first.

## 1. Goal
Give the group message path a real Sender-Keys layer: this device's own
outbound group chain, every peer's inbound chain, both persisted durably,
and a distribution mechanism that hands a member the chain key they need
without ever putting it on the wire in the clear.

## 2. Business logic
- **The layering, concretely (ADR-0003's deferred design).**
  `libsignal_protocol_dart` 0.8.2 already ships the group primitives —
  `GroupCipher`, `GroupSessionBuilder`, `SenderKeyName`,
  `SenderKeyRecord`, and the abstract `SenderKeyStore` that
  `drift_signal_store.dart`'s own header names as *"explicitly out of
  scope — that belongs to E07"*. This task is that. Nothing is hand-rolled:
  the ratchet is libsignal's, and this task provides only the durable store
  and the distribution channel around it. **Rolling a custom group ratchet
  is out of scope and forbidden** (ADR-0003 §Options, option 3).
- **`SenderKeyDistributionMessage` travels inside the pairwise Double
  Ratchet session, one per recipient.** This is the join between the two
  schemes and it is the whole reason ADR-0003's Sender-Keys layer works at
  all: the group chain key is a secret that must reach exactly the current
  members, and the only authenticated confidential channel this app has to
  each member is the 1:1 session E03 built and E06-T07 learned to
  establish. `PrekeyExchange.ensureSession` is reused unchanged.
- **The epoch is carried in the store key, not in `SenderKeyName`.**
  libsignal's `SenderKeyName` is `(groupId, sender)` — two parts, no epoch.
  E07-T01's table is keyed `(groupId, senderDeviceId, membershipEpoch)`.
  The mapping is one line and must be written once, here:
  `SenderKeyName('<groupId>@<epoch>', SignalProtocolAddress(senderDeviceId, 1))`.
  Embedding the epoch in the *group id half* of the name means libsignal
  treats each epoch as a distinct group — which is exactly the property
  FR-GROUP-005 needs, because a chain for epoch N is then structurally
  incapable of decrypting a message sent at epoch N+1. Getting this wrong
  in either direction (epoch in the sender half, or no epoch at all) turns
  rotation into an overwrite race; see `E07-T01` §2.
- **The store never returns another group's or another epoch's record**,
  and `loadSenderKey` for an unknown name returns a *fresh empty*
  `SenderKeyRecord` (libsignal's own contract), never null and never a
  neighbouring record.
- **Distribution is idempotent per `(group, epoch, recipient)`.** Sending
  the same distribution message twice must not advance or reset a chain.
- **A member is never given a distribution message for an epoch below
  their `joined_at_epoch` (FR-GROUP-006, `OQ-E07-1`).** This task enforces
  the check at the send site; E07-T05 enforces it again at rotation. The
  human's 2026-08-26 decision — v1 has no exception path for historical
  access — is encoded here as a hard refusal, not a policy flag.
- **Key material never leaves this device unencrypted and is never
  logged.** The store's blobs are opaque; a log line may name a group id
  and an epoch, never a record, a key, or a chain index.

## 3. What this task does
- **`DriftSenderKeyStore implements SenderKeyStore`** — `storeSenderKey` /
  `loadSenderKey` over `group_sender_keys`, with the `SenderKeyName ↔
  (groupId, epoch, senderDeviceId)` mapping in §2 as the single named
  encode/decode pair (`senderKeyNameFor` / `parseSenderKeyName`).
- **`GroupCryptoService`:**
  - `ensureOwnChain(groupId, epoch)` — creates this device's own sender
    key for the epoch via `GroupSessionBuilder.create` if absent, returns
    the `SenderKeyDistributionMessage` bytes.
  - `distributeTo(groupId, epoch, recipientDeviceIds)` — for each
    recipient: refuse if `joined_at_epoch > epoch`; `ensureSession`;
    encrypt the distribution message as a `PayloadType.control` payload of
    kind `kControlKindGroupKeyDistribution = 4`; enqueue.
  - `acceptDistribution(sourceDeviceId, plaintext)` — the receive half:
    `GroupSessionBuilder.process`, keyed by the *session* address (same
    rule as E07-T03 §2 — never `frame.source`).
  - `encryptForGroup(groupId, epoch, plaintext) -> Uint8List` and
    `decryptFromGroup(groupId, epoch, senderDeviceId, bytes) -> Uint8List`
    — thin `GroupCipher` wrappers, the surface E07-T06 consumes.
  - `discardChains(groupId, {required int belowEpoch})` — deletes sender-key
    rows; used by E07-T05, provided here so the store's delete path is
    tested alongside its write path.
- **Control kind `4`** registered on `InboundPipeline`'s keyed dispatch in
  `MessagingStack`'s constructor, alongside `1`/`2`/`3`.

## 4. What this task does NOT do
- Does **NOT** decide when to rotate. It provides `ensureOwnChain`,
  `distributeTo` and `discardChains`; **E07-T05** is the only thing that
  calls them in response to an epoch change. Do not add an epoch listener
  here.
- Does **NOT** send or receive group *messages* — E07-T06.
- Does **NOT** implement a ratchet, a KDF, a cipher, or a padding scheme.
  Every cryptographic operation is a libsignal call. If a primitive
  appears to be missing from the port, **stop and raise it** — do not
  substitute one.
- Does **NOT** modify `DriftSignalProtocolStore`, `CryptoService`,
  `IdentityService`, `PrekeyExchange` or `InboundPipeline`. It composes
  them.
- Does **NOT** add a table, column, index or migration — E07-T01 owns all
  four tables and the version bump.
- Does **NOT** add a dependency.
- Does **NOT** fix the one-time-prekey pool leak (`OQ-E06-T07-2`,
  inherited from E03) even though this task sharpens its trigger — see
  `OQ-E07-9`.

  params: { sourceDeviceId: "the decrypting Signal session's address -- never frame.source" }

- signature: "GroupCryptoService.encryptForGroup({required String groupId, required int epoch, required Uint8List plaintext}) -> Future<Uint8List>"
  returns: "SenderKeyMessage bytes; throws AppFailure('group.no_chain') when this device has no chain for the epoch"

  returns: "plaintext; throws AppFailure('group.no_chain') when no chain for that sender/epoch is held -- which is the FR-GROUP-006 case for a message predating this device's membership, and it must fail LOUDLY, never silently return empty"

  returns: "rows deleted"
  purpose: "E07-T05's rotation primitive, provided and tested here"

## 6. Risks
- **The `SenderKeyName` mapping is the task.** If the epoch ends up in the
  sender half, two epochs share a chain and FR-GROUP-005 silently fails
  with every test still green. Write the round-trip test
  (`parseSenderKeyName(senderKeyNameFor(x)) == x`) first, and write the
  cross-epoch isolation test before any distribution code exists.
- `loadSenderKey` returning a *fresh empty record* for an unknown name is
  libsignal's contract and is also indistinguishable, at the call site,
  from "I have a chain but it is empty". `decryptFromGroup` must therefore
  fail explicitly rather than letting libsignal produce a confusing
  `InvalidMessageException` — E03-B03's exception-taxonomy work (landed via
  E06-T02) is what to map onto.
- Group fan-out multiplies first-contact prekey consumption by the member
  count. A 20-member group's first distribution can consume 19 one-time
  prekeys at once, and E03's pool has no reclaim policy
  (`OQ-E06-T07-2`). Do not fix it here; do assert the consumption in a
  test so the number is visible rather than surprising (see `OQ-E07-9`).
- Two `MessagingStack`s in one test process share `CryptoService.instance`
  unless constructed with `CryptoService.withStore` — E06-T07's
  `prekey_exchange_test.dart` already solved this; reuse that helper shape
  rather than rediscovering it.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-GROUP-12**: WHEN a device needs to send to a group at an epoch,
  the system SHALL create or reuse exactly one sender chain for that
  `(group, epoch)` and SHALL persist it durably. (FR-GROUP-004, FR-SEC-002)
- **EARS-GROUP-13**: WHEN a group chain key is distributed, the system
  SHALL transmit it only inside an established pairwise Signal session
  with each recipient, and SHALL NOT transmit it to a device whose
  `joined_at_epoch` is greater than that epoch. (FR-SEC-001, FR-GROUP-006)
- **EARS-GROUP-14**: IF a group message is decrypted with a chain from a
  different epoch or a different group, THEN the system SHALL fail
  explicitly rather than returning any plaintext. (FR-GROUP-005)
