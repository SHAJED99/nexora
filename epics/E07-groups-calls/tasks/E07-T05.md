# E07-T05 · Rotation on membership change

## 1. Goal
Make the epic's two headline guarantees true and provable: when membership
changes the group's keys rotate (EARS-GROUP-1), and neither a removed
member nor a newly added one can read communication they are not entitled
to (EARS-GROUP-2, FR-GROUP-005/006).

## 2. Business logic
- **Rotation is triggered by the epoch, not by the action.** E07-T03's
  `applyEvent` is the only writer of `membership_epoch`; this task hooks
  that one seam. Every action that bumps the epoch rotates, with no
  per-action list to keep in sync — a list is how `renamed` ends up
  rotating and `memberRemoved` ends up not.
  - Consequence, stated deliberately: a **rename** also rotates. That is
    slightly wasteful and exactly right, because FR-GROUP-004 says "when
    group membership changes" and the cheap, safe reading is "whenever the
    epoch moves". Recorded as a documented choice, not an oversight.
- **Rotation is: mint a new chain at the new epoch, distribute it to the
  new current member set, then discard chains below the new epoch.** In
  that order. Discarding first would leave a window with no chain at all;
  distributing to the *old* member set would hand the removed member the
  new key, which is the entire defect FR-GROUP-005 exists to prevent.
- **FR-GROUP-005 (a removed member cannot decrypt future communication)**
  falls out of two facts together, and needs both: the removed device is
  not in the recipient list of the new distribution, *and* the new chain is
  keyed at a new epoch so their retained epoch-N chain is structurally
  unable to decrypt an epoch-N+1 message (E07-T04 §2). Neither alone is
  sufficient — a retained chain with no epoch in its name would still
  decrypt.
- **FR-GROUP-006 (a new member gets no historical access)** is enforced as
  a *refusal to distribute*, per `OQ-E07-1`'s human decision of 2026-08-26:
  **v1 has no exception path.** A member added at epoch N is distributed
  the chain for epoch N and never for N−1 or below. There is no flag, no
  admin override, and no "share history" affordance — and this task must
  not leave a hook for one, because a hook is how the decision quietly
  reverses.
  - The user-visible consequence is that a new member's view of the thread
    begins at their join. Older messages are present on other devices and
    are simply undecryptable here; they must fail explicitly (E07-T04's
    `group.no_chain`), never render as empty or corrupted bubbles.
- **Rotation is best-effort per recipient and never blocks the local
  change.** A member who is offline when the epoch moves does not receive
  the new chain until they are reachable; their outbound sends still work
  (their own chain is theirs to mint), their inbound reads of others' new
  messages fail with `group.no_chain` until distribution lands. That is the
  honest degraded state, and it is the one E07-T06's UI must be able to
  represent.
- **On `deleteGroup`, and on this device leaving, every chain for the group
  is discarded** — all epochs, not just below the current one. A deleted
  group leaves no decryptable material behind.

## 3. What this task does
- **`GroupKeyRotationService.onEpochApplied({required String groupId,
  required int newEpoch, required GroupEventKind kind})`** — the single
  entry point, called by `GroupMembershipService` immediately after
  `applyEvent` succeeds, inside neither the transaction nor the fan-out
  loop:
  1. `ensureOwnChain(groupId, newEpoch)` (E07-T04)
  2. `distributeTo(groupId, newEpoch, currentMembers − self)` — refusing
     any member whose `joined_at_epoch > newEpoch`, which E07-T04 already
     enforces and this task asserts again
  3. `discardChains(groupId, belowEpoch: newEpoch)`
  4. for `deleted` / self-`leave`: `discardChains(groupId, belowEpoch:
     newEpoch + 1)` — i.e. everything
- **`GroupKeyRotationService.onRemoteEpochApplied(...)`** — the receive
  side: a device that *applies* someone else's membership frame also
  rotates its own outbound chain to the new epoch and discards its old
  ones. Every device rotates; rotation is not the actor's job alone.
- The one-line wiring into `GroupMembershipService` (both the local-action
  path and `handleControlFrame`'s apply path).
- A **rotation ledger assertion** in tests, not a new table: after any
  epoch change, `group_sender_keys` contains no row with
  `membership_epoch < groups.membership_epoch` for that group. This is the
  invariant the whole task exists to hold, and it is one query.

## 4. What this task does NOT do
- Does **NOT** implement any cryptography, store, or distribution
  mechanism — all four operations it calls are E07-T04's, already tested.
  This task is sequencing and policy.
- Does **NOT** add a "share history with new members" path, a flag, a
  setting, or an extension point for one. `OQ-E07-1` is decided; a hook is
  a reversal in waiting.
- Does **NOT** re-key on message send, on reconnect, on a timer, or on
  anything except an epoch change.
- Does **NOT** implement catch-up for a member who missed a rotation
  (`OQ-E07-7`, owner E11). A `group.no_chain` failure is the correct,
  honest outcome until then.
- Does **NOT** touch `messages`, the relay queue, or the inbound pipeline.
- Does **NOT** send group messages — E07-T06.
- Does **NOT** add a table, column or migration.

## 5. Contract

### Functions
```yaml
- signature: "GroupKeyRotationService({required GroupRepository groups, required GroupCryptoService crypto, required String selfDeviceId})"

- signature: "GroupKeyRotationService.onEpochApplied({required String groupId, required int newEpoch, required GroupEventKind kind}) -> Future<Map<String, AppFailure?>>"
  returns: "per-recipient distribution outcome; never throws -- a failed recipient is a reported outcome, not an aborted rotation"
  purpose: "the ONLY rotation trigger in the codebase (§2). Order is mint -> distribute -> discard, and that order is load-bearing"

- signature: "GroupKeyRotationService.onRemoteEpochApplied({required String groupId, required int newEpoch, required GroupEventKind kind}) -> Future<Map<String, AppFailure?>>"
  purpose: "same, for an epoch this device applied from someone else's frame -- every device rotates, not just the actor"

- signature: "GroupKeyRotationService.discardAllFor(String groupId) -> Future<int>"
  purpose: "group deleted, or this device left: no decryptable material remains"
```

### Data
**None.** No migration; reads/writes only through `GroupRepository` and
`GroupCryptoService`.

## 6. Risks
- **Order is the bug.** Discarding before distributing, or distributing to
  the pre-change member list, both produce a system whose tests pass and
  whose guarantee is void. Write the removed-member test first, and make it
  fail for the right reason before writing the service.
- Rotation on every epoch bump means a rapid burst of membership changes
  (adding five people one at a time) triggers five rotations and five
  fan-outs. Correct, and potentially slow. Do **not** "optimise" it by
  coalescing here — coalescing rotation is a correctness change disguised
  as a performance change, and it is precisely how a removed member ends up
  inside the coalesced window.
- The invariant query in §3 is cheap and catches almost every mistake this
  task can make. Assert it after *every* rotation in the tests, not once.
- `leave` by the last remaining member, and `deleteGroup`, both end with no
  current members. `distributeTo` with an empty recipient list must be a
  no-op success, not an error and not a crash.

**Deviations from spec/design:**
1. **`onEpochApplied`/`onRemoteEpochApplied` are fired, not awaited, from
   `GroupMembershipService`.** §3's own wording ("called by
   `GroupMembershipService` immediately after `applyEvent` succeeds") does
   not explicitly say whether the call must be awaited before `_perform`/
   `handleControlFrame` return. Awaiting it turned out to reintroduce
   exactly the regression `test_EARS_GROUP_8_local_write_is_not_blocked_by_a_failing_member_send`
   (E07-T03) exists to catch: `GroupCryptoService.distributeTo`'s own
   `ensureSession` call (E07-T04) uses a hardcoded, non-configurable ~20s
   timeout per recipient — unlike this file's own membership-frame fan-out,
   whose bound (`_fanOutSessionTimeout`) is test-overridable. Discovered
   during development: that exact test failed at 20.08s against a 5s bound
   once the awaited call was wired in (see Run log). Fired-and-forgotten
   instead (with an internal `catchError` so a genuine bug can never surface
   as an unhandled Future rejection), which also directly satisfies task
   file §2's own words: "rotation is best-effort per recipient and never
   blocks the local change." A `lastRotationForTest` field on
   `GroupMembershipService` (not part of §5's contract, not annotated
   `@visibleForTesting` — that would need `package:meta` added as a direct
   dependency, a 🧍 `new_dependency` gate this one testing seam does not
   justify) lets this file's OWN existing test suite await the fired-off
   rotation deterministically where needed; it is never read by production
   code.
2. **`GroupKeyRotationService` is constructed lazily inside
   `GroupMembershipService`, from `_stack.groupCryptoService`, rather than
   being passed in as a new constructor parameter.** `MessagingStack`'s own
   constructor (out of this task's `files:` fence) builds
   `groupMembershipService` BEFORE `groupCryptoService` — an eager
   `_stack.groupCryptoService` read inside `GroupMembershipService`'s own
   constructor throws `LateInitializationError` on every real app boot. A
   lazy getter (`_rotation`), built on first use (well after `MessagingStack`
   finishes constructing), avoids the ordering hazard entirely without
   touching `messaging_stack.dart`.
3. **The "self-leave" branch of step 4 (discard everything) is
   operationalized as "this device's own `roleOf` lookup returns null
   immediately after the event"**, not by inspecting the frame's actor/
   subject — the task's own §5 contract signature for
   `onEpochApplied`/`onRemoteEpochApplied` carries only `(groupId, newEpoch,
   kind)`, no actor or subject id, so that is the only test this code can
   even perform. This also (safely) covers "this device was removed by
   someone else", not only a voluntary `leave` — both produce a
   `memberRemoved` event and both leave this device with no legitimate
   reason to retain any old chain for a group it is no longer in; treating
   them identically is never less correct than the narrower reading and is
   the only reading this signature can express.
