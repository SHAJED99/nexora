# E07-T14 · Compose the group send path into `MessagingStack`

> **Why this task exists.** `OQ-E07-T06-2`, raised by the planner while
> resolving `OQ-E07-T06-1` and answered by the human on 2026-09-01:
> `grep -rn "SendGroupMessageUseCase" lib/` returns only its own
> definition. E07-T06 built and tested the whole group send path against
> real databases and real Signal sessions — and nothing in the running app
> ever constructs it, because `messaging_stack.dart` sits outside every
> E07 task's `files:` fence (T06 §4 excludes it explicitly; T07 is the read
> model, T08 the Conversations screen, T09–T13 calls/design/PTT). This is
> an **obligation-ownership gap**: every task correctly stayed inside its
> fence, and the composition step fell between all of them. This task is
> the missing step, and nothing else.

## 1. Goal
A `MessagingStack` built by `MessagingStack.create(...)` exposes a real,
fully-wired `SendGroupMessageUseCase`, so FR-COMM-002's send guarantee —
which E07-T06 proved against fakes — is true in the app a user runs.

## 2. Business logic
- **This task adds no behaviour.** Every rule about who may send, what gets
  encrypted, how many frames go out and what a `messages` row looks like is
  E07-T06's, already specified, already tested. The only thing missing is a
  construction. If this task finds itself reasoning about group semantics,
  it has left its lane.
- **One instance per stack, built in the composition root, never
  lazily.** `messaging_stack.dart`'s own header states the invariant this
  file exists to hold (E06-T03 §2): two of anything the stack owns — two
  `AppDatabase`s, two id generators, two writers of one counter — is a
  correctness defect, not a style question. `SendGroupMessageUseCase` joins
  the same discipline as `sendMessage`, `groupMembershipService`,
  `groupCryptoService` and `callSignaling`.
- **The reservation seam stays unbound at the call site.**
  `SendGroupMessageUseCase`'s `reserveSequence:` parameter is optional and
  defaults to `MessageSequenceReserver` — the one shared transaction
  `SendMessageUseCase` also uses (`OQ-E07-T06-1`'s resolution). Production
  composition **must omit it**. Passing anything there from
  `messaging_stack.dart` would reintroduce, at the composition root, the
  exact second-writer-of-one-counter shape L-backend-003 is about.
- **Construction order is load-bearing, not incidental.**
  `groupCryptoService` is a `late final` assigned in `MessagingStack`'s
  constructor **body** (`messaging_stack.dart:321`), not in the initializer
  list — because it needs a fully-constructed `this`. A
  `SendGroupMessageUseCase` that reads it must therefore also be built in
  the constructor body, *after* that line. Building it in `create()`
  alongside `sendMessage` is impossible for the same reason and must not be
  attempted: there is no `groupCryptoService` yet at that point in the
  program's life. E07-T05 §9 Deviation 2 and E07-T06 §9 Deviation 2 both
  document this same hazard from the other side; this is its third
  appearance and the first one that has to solve it rather than route
  around it.
- **`GroupRepository` is a thin, stateless wrapper over the shared
  `AppDatabase`.** `groupMembershipService` is already handed a fresh
  `GroupRepository(db)` (`messaging_stack.dart:307`), so a second instance
  here is consistent with the established pattern and carries no shared
  mutable state — the *database* is the singleton that matters, and it is
  the same `db` either way. Do not refactor the existing one into a shared
  field; that is a change to a line this task has no reason to touch.
- **`GroupPermissions` is a pure static matrix**, not an injectable
  collaborator — `SendGroupMessageUseCase` calls it directly. Nothing to
  wire.

## 3. What this task does
- Adds a `late final SendGroupMessageUseCase sendGroupMessage;` field to
  `MessagingStack`, dartdoc'd in the same shape as its `groupCryptoService`
  / `callSignaling` neighbours (which task built it, what it is, and the
  ordering constraint above).
- Constructs it in the constructor body **after** `groupCryptoService` is
  assigned, with its real dependencies:
  `db` (the stack's own `AppDatabase`), `selfDeviceId`,
  `groups: GroupRepository(db)`, `crypto: groupCryptoService`,
  `enqueue: relayEngine.enqueue` (a tear-off — `GroupMessageEnqueueFn`'s
  arity, order and return type already match `RelayEngine.enqueue`
  exactly, the same tear-off `sendMessage` uses; **verify this, do not
  assume it, and if an adapter turns out to be needed, say so in §9 rather
  than inventing one silently**), and **no** `reserveSequence:` argument.
- Adds the wiring proof to `messaging_stack_test.dart`: two real
  `MessagingStack`s, a real group, a real key distribution, a real group
  message sent through `stack.sendGroupMessage` — the composed object, not
  a locally-constructed one — and really received on the other stack.

## 4. What this task does NOT do
- Does **NOT** change `SendGroupMessageUseCase`, `GroupCryptoService`,
  `GroupRepository`, `InboundPipeline`, `MessageSequenceReserver`,
  `SendMessageUseCase`, `RelayEngine` or anything under
  `lib/features/groups/`. If the wiring reveals a defect in any of them,
  that is an Open Question with a named owner, not a fix in this diff.
- Does **NOT** touch `lib/app/bindings.dart`. Checked, not assumed:
  `bindings.dart:76-100` registers `messagingStack` itself plus the five
  members a *screen* currently resolves directly; `groupMembershipService`,
  `groupCryptoService` and `callSignaling` are all reached via
  `Get.find<MessagingStack>()` and none of them has its own registration.
  There is no group-send UI consumer yet (a group thread view is
  prospective, blocked on GAP-020), so a `Get.put` here would be a
  registration nothing resolves — added on speculation, in a file this task
  otherwise has no reason to open. The task that builds the first consumer
  adds it, if it wants one.
- Does **NOT** normalize `kControlKindGroupMessage`'s registration.
  E07-T06 self-registers that handler inside `InboundPipeline`'s own
  constructor (T06 §9 Deviation 2) instead of externally in
  `messaging_stack.dart` the way kinds 1–5 are wired, because no external
  call site existed inside T06's fence. This task creates one — so the
  question is live and was deliberately answered **no**:
  1. It buys this task's own EARS criterion nothing. T14 is proven by "a
     real composed stack really sends"; where the *receive* handler is
     registered does not move that needle.
  2. It is not a composition change, it is a refactor of
     `inbound_pipeline.dart` — deleting the self-registration, promoting
     `_handleGroupMessageWireFrame` to public, re-registering it — in a
     file E07-T06 has just rewritten and whose group branch is protected by
     tests that construct `InboundPipeline` directly. A silently
     unregistered handler kills group receive with a green suite, which is
     precisely the failure class that deserves its own falsification test
     and its own review, not a rider on an S-sized wiring task.
  3. T06's form is safe as written: the handler is registered as a closure,
     not an eager tear-off, so it never dereferences
     `_stack.groupCryptoService` at construction time (T06 §9 Deviation 2).
     The inconsistency is a readability cost, not a defect.
  Recorded in `tracker.md` §Carried-forward observations with a named owner
  so it has a reader — not dropped.
- Does **NOT** add per-recipient delivery/read state, a group thread view,
  a controller, a route, or any UI. Does **NOT** add a table, column or
  migration. Does **NOT** add a dependency.
- Does **NOT** start anything. `MessagingStack.create`'s standing contract
  ("does NOT start anything", that file's header) is unchanged — this is a
  construction, and it holds no timer, stream subscription or handler slot.

## 6. Risks
- **Check the control-kind numbering before writing a line.** E07-T06
  branched off `epic_07` at `182c6e6`, *before* E07-T09 merged, and assigns
  `kControlKindGroupMessage = 5`
  (`group_message_envelope.dart:58`) — the same slot E07-T09's
  `kControlKindCallSignaling = 5` (`call_signaling.dart:95`) already
  occupies on `epic_07`. `InboundPipeline.registerControlHandler` rejects a
  duplicate slot, so if T06 merges unrenumbered, **every**
  `MessagingStack.create` throws and this task cannot run at all. That is
  T06's to resolve at its merge, not this task's to patch — but confirm it
  is resolved on your branch point before starting, and read the constant's
  merged value rather than hardcoding a number anywhere.
- **The `late final` ordering hazard is the one way to get this wrong.**
  Constructing `SendGroupMessageUseCase` before `groupCryptoService = ...`
  at `messaging_stack.dart:321`, or moving it into `create()` for symmetry
  with `sendMessage`, throws `LateInitializationError` — and it throws in
  `create()`, which every existing stack test calls, so the failure is loud
  rather than subtle. Loud is the good case; do not "fix" it by making the
  field nullable or by capturing `groupCryptoService` inside a lazy
  closure, either of which trades a loud failure for a quiet one.
- **A test that constructs its own `SendGroupMessageUseCase` proves
  nothing here.** T06 already did that, thoroughly, and it is exactly why
  this gap existed for a whole task cycle: everything was tested except
  whether anything builds it. The test for this task must reach the object
  through `stack.sendGroupMessage` and nowhere else — the same discipline
  `OQ-E07-T06-1`'s own
  `test_group_send_reserves_a_real_sequence_number_without_a_fake_seam`
  established when it proved the reservation seam by *omitting* it.
- **Two stacks in one process need `CryptoService.withStore(store)`**, not
  `CryptoService.instance` — `messaging_stack_test.dart`'s existing
  `_RemoteParty` helper and `create()`'s own `cryptoService:` override
  exist for this. Reuse the established helper rather than a second
  `create()` call; the header of that test file explains why.
- **The receiving half needs a real key distribution first.** E07-T06's own
  run log records two false-alarm `group.no_chain` failures caused by a
  harness that skipped `ensureOwnChain` / `distributeTo` + `processQueue`.
  Mirror `send_group_message_use_case_test.dart`'s `sendAndDeliver` helper
  shape rather than rediscovering this.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-35**: WHEN the messaging stack is composed, the system SHALL
  provide a group-message send path wired to the stack's own database,
  group repository, group crypto service, sequence reserver and relay
  engine, such that a group message sent through it is received and stored
  by another device with no test-supplied seam. (FR-COMM-002)

### Tests
- `test_EARS_COMM_35_composed_stack_sends_a_real_group_message` — two real
  `MessagingStack`s (`_RemoteParty` shape), a real group with both devices
  as current members, a real `ensureOwnChain` + `distributeTo` +
  `processQueue`, then `stack.sendGroupMessage.send(groupId: …, body: …)`
  returns `null` and the message is decrypted, stored under the group's
  conversation id and emitted on the receiver's `delivered` stream. Nothing
  in this test constructs a `SendGroupMessageUseCase`, a
  `GroupRepository`, a `GroupCryptoService` or a reservation function
  itself.
- `test_composed_send_group_message_uses_the_stack_database_and_identity` —
  the row written lands in the stack's own `db` with
  `senderDeviceId == stack.selfDeviceId`, and the reserved
  `sequenceNumber` is a real, dense number from the shared reserver (the
  same property `test_group_send_reserves_a_real_sequence_number_without_a_fake_seam`
  asserts, here through the composition root).
- `test_send_group_message_is_the_same_instance_on_every_read` — the
  `late final` is assigned once; two reads are identical, mirroring
  `test_EARS_COMM_6_stack_is_a_single_instance`'s discipline.

### Manual
1. Two devices in one group; A sends from the running app's stack (not a
   test harness) — B stores and renders it. **Expected caveat:** there is no
   group thread UI yet (GAP-020), so "renders" here means the message is
   observable in the Conversations projection once E07-T07/T08 land, or via
   a direct database read before then. State that plainly in the run log
   rather than claiming a screen exists.
