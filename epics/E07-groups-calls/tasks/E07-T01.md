## 1. Goal
Give every later E07 task one durable, migrated place to keep what a group
*is* — its identity, its members and their roles, and the per-sender group
key state the Sender-Keys layer needs — so that no later task invents a
table under time pressure.

## 2. Business logic
- **A group is a first-class conversation, and its id lives in the same id
  space as a 1:1 conversation's.** E06-T09 fixed `conversationId ==
  peerDeviceId` for 1:1 and documented the field as *opaque to callers*
  specifically so this epic could widen it (`E06-T09.md` §2). This task
  widens it: a group's `conversationId` is its `groups.id`, a locally
  minted, globally unique, **non-device-shaped** id. It must be
  distinguishable from a device id by construction — prefix `g:` — so that
  no reader ever has to guess which kind of conversation it is holding, and
  so an attacker cannot mint a group id that collides with a real peer's
  device id.
- **Roles are Owner / Admin / Member (FR-GROUP-001)**, stored as the enum
  value's `.name` string per `docs/conventions.md` "Enums" — never an
  integer index. Exactly one Owner per group is an invariant enforced by a
  partial unique index, not by application code that someone will forget to
  call.
- **Membership is versioned (FR-GROUP-004).** Every membership change bumps
  `groups.membership_epoch`. The epoch is what key rotation keys off — a
  monotonically increasing integer is the only thing that makes "was this
  message encrypted before or after Ahmed was removed?" answerable after
  the fact. `E07-T05` rotates on epoch change; this task only guarantees
  the epoch exists and is monotonic.
- **Sender-key state is per `(groupId, senderDeviceId, membershipEpoch)`,
  not per `(groupId, senderDeviceId)` (FR-GROUP-005/006).** This is the
  single most important shape decision in the table set. libsignal's
  `SenderKeyName` is `(groupId, sender)` only; if this app stored records
  under that key alone, a rotation would have to *overwrite* the old
  record, and there is then no way to hold a removed member's old chain
  and the new chain apart during the window where both exist in flight.
  The epoch in the key makes FR-GROUP-005 ("a removed member shall not
  decrypt future communication") a delete of one row set rather than a
  race. See `E07-T04` §2 for how the composite key maps back onto
  libsignal's two-part `SenderKeyName`.
- **A newly added member gets no historical access (FR-GROUP-006, per
  `OQ-E07-1`, decided by the human 2026-08-26: v1 has no exception path).**
  The schema encodes this rather than leaving it to policy: a member row
  carries `joined_at_epoch`, and nothing in this project ever hands a
  member a sender-key record for an epoch below their own `joined_at_epoch`.
  `E07-T05` enforces it; this table is what makes the enforcement
  checkable.
- **This task stores no plaintext and no group message bodies.** Group
  messages live in the existing `messages` table with the group's
  `conversation_id` (E07-T06), ciphertext still opaque, exactly as
  `message_tables.dart` already requires.

## 3. What this task does
- **`lib/core/persistence/group_tables.dart`** — four Drift tables:
  - `Groups` — `id` (PK, `g:`-prefixed), `name`, `createdAt`,
    `createdByDeviceId`, `membershipEpoch`, `isDeleted`.
  - `GroupMembers` — PK `(groupId, deviceId)`; `role` (a `GroupRole.name`
    string), `joinedAtEpoch`, `removedAtEpoch` (nullable — a removed member
    is marked, never deleted, so FR-GROUP-005 stays auditable).
  - `GroupSenderKeys` — PK `(groupId, senderDeviceId, membershipEpoch)`;
    `record` (an opaque libsignal `SenderKeyRecord` blob), `updatedAt`.
  - `GroupEvents` — PK `id`; `groupId`, `epoch`, `kind` (a
    `GroupEventKind.name` string), `actorDeviceId`, `subjectDeviceId`
    (nullable), `createdAt`. The append-only membership-change log
    FR-GROUP-002's actions produce and E07-T06's in-thread system messages
    render from.
- **Indexes:** `(groupId, removedAtEpoch)` on `GroupMembers` for "current
  members" (the query every fan-out runs); `(groupId, epoch)` on
  `GroupEvents`; a **partial unique index** on `GroupMembers` for
  `role = 'owner' AND removed_at_epoch IS NULL`.
- **Migration `12 → 13`** in `database.dart`'s existing `MigrationStrategy`
  — create the four tables and their indexes, touching no existing table.
  Additive only: no column of any E01–E06 table is altered, renamed or
  dropped.
- Regenerate `database.g.dart` with `drift_dev` (the file is checked in;
  regeneration is not a hand edit).

## 5. Contract

### Data
Migration `13_groups` — additive, forward-only, no backfill required (a
pre-E07 install has no groups, so every new table is legitimately empty).

```
groups(
  id                    TEXT PRIMARY KEY,      -- 'g:' + 32 hex chars
  name                  TEXT NOT NULL,
  created_at            INTEGER NOT NULL,      -- epoch ms
  created_by_device_id  TEXT NOT NULL,
  membership_epoch      INTEGER NOT NULL DEFAULT 0,
  is_deleted            INTEGER NOT NULL DEFAULT 0
)

group_members(
  group_id          TEXT NOT NULL,
  device_id         TEXT NOT NULL,
  role              TEXT NOT NULL,             -- GroupRole.name
  joined_at_epoch   INTEGER NOT NULL,
  removed_at_epoch  INTEGER,                   -- NULL = current member
  PRIMARY KEY (group_id, device_id)
)
CREATE INDEX idx_group_members_current ON group_members(group_id, removed_at_epoch);
CREATE UNIQUE INDEX idx_group_single_owner ON group_members(group_id)
  WHERE role = 'owner' AND removed_at_epoch IS NULL;

group_sender_keys(
  group_id          TEXT NOT NULL,
  sender_device_id  TEXT NOT NULL,
  membership_epoch  INTEGER NOT NULL,
  record            BLOB NOT NULL,             -- opaque SenderKeyRecord
  updated_at        INTEGER NOT NULL,
  PRIMARY KEY (group_id, sender_device_id, membership_epoch)
)

group_events(
  id                 TEXT PRIMARY KEY,
  group_id           TEXT NOT NULL,
  epoch              INTEGER NOT NULL,
  kind               TEXT NOT NULL,            -- GroupEventKind.name
  actor_device_id    TEXT NOT NULL,
  subject_device_id  TEXT,
  created_at         INTEGER NOT NULL
)
CREATE INDEX idx_group_events_group_epoch ON group_events(group_id, epoch);
```

🧍 **Schema change — human gate. See `OQ-E07-4`.**

```yaml
- signature: "String newGroupId({Random? random})"
  returns: "'g:' + 32 lowercase hex chars"
  purpose: "the one place a group id is minted; the 'g:' prefix is what keeps the widened conversationId space unambiguous against device ids (§2)"

- signature: "enum GroupRole { owner, admin, member }"

  purpose: "FR-GROUP-002's action list, one enum value per action, so the event log and the permission matrix (E07-T02) cannot drift apart"
```

## 6. Risks
- `database.g.dart` is generated and checked in. Regenerate it; do **not**
  hand-edit it, and do not let an IDE reformat the whole file — a
  thousand-line noise diff makes the review of an actual schema change
  impossible.
- Drift's partial-index support: if `@TableIndex`'s annotation form cannot
  express the `WHERE role = 'owner' AND removed_at_epoch IS NULL` predicate
  on this drift version, add it as raw SQL inside the migration step rather
  than dropping the constraint. **A single-owner invariant enforced only in
  Dart is not enforced.** If neither route works, stop — that is an Open
  Question, not a quiet downgrade.
- The 12→13 upgrade path must be tested against a database created at
  version 12, not only against a fresh version-13 database. E05-T01's
  review found exactly this class of bug (an index that existed on fresh
  installs and not on upgraded ones); do not repeat it.
- `membership_epoch` starting at `0` and a member's `joined_at_epoch`
  also starting at `0` is correct for the founding members and is the case
  most likely to be got wrong by an off-by-one at creation time. Test it
  explicitly.

## Open Questions
- **OQ-E07-4 — the group schema migration (12 → 13).** Rule 3 names schema
  migrations as a human call. The DDL above is the proposal; three things
  in it are genuine forks worth your eye rather than mine:
  1. **`group_sender_keys` keyed by `(group, sender, epoch)` rather than
     libsignal's own `(group, sender)`.** Costs one extra column and a
     slightly awkward mapping onto `SenderKeyName`; buys a clean delete for
     FR-GROUP-005 instead of an overwrite race. *Advisory: keep the epoch
     in the key.*
  2. **Removed members are retained with `removed_at_epoch` rather than
     deleted.** Costs unbounded row growth on a churny group; buys an
     auditable membership history and makes FR-GROUP-006 checkable.
     *Advisory: retain — the volumes here are tiny and a deleted row cannot
     prove anything later.*
  3. **`group_events` as a persistent table** rather than synthesising
     system messages into `messages`. Costs a fourth table; buys not
     putting non-message rows into a table whose every row is currently
     assumed to have ciphertext. *Advisory: keep it separate.*
  - **Status:** 🟢 resolved
  - **Answer:** All three advisories accepted as proposed: (1) `group_sender_keys`
    keyed by `(group, sender, epoch)`, epoch in the primary key; (2) removed
    members retained with `removed_at_epoch`, not deleted; (3) `group_events`
    as its own persistent table, not synthetic rows in `messages`.
    `schemaVersion` may now bump to 13 against the DDL as drafted in this
    file (subject to any changes needed to make it compile/migrate cleanly —
    that part remains the builder's normal implementation latitude, not a
    reopening of this decision).
