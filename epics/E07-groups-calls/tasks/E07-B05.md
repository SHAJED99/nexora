# E07-B05 · Creating a group lands the user in a screen that cannot do groups

## The defect

`E07-B01` established — and the human decided at the `bug_priorities` gate on
2026-09-02, **P1, fix direction (a)** — that a group id must never reach
`ChatController`:

> `openConversation`'s doc comment, `conversations_controller.dart:386-390`:
> "**Personal rows only** (E07-B01). … A group id reaching this method drives
> that handshake against a group id instead — undecryptable bubbles in, a
> non-retryable send failure out."

`E07-T15` (#325, `a06131b`) built `/groups/new` and routed its **success**
path to precisely that destination:

```dart
// lib/features/groups/presentation/group_create_controller.dart:98-100
static Future<void> _defaultOpenThread(String groupId) async {
  await Get.toNamed<dynamic>('/chat/$groupId');
}
```

`/chat/:id` is registered (`lib/app/routes.dart:217-221`), so this is live.
The conversations-list door was closed by `E07-B01`; the create-group door
was opened four weeks later and leads to the same room.

## Why review did not catch it

The controller test injects the navigation seam and asserts against the
injected spy:

```dart
// test/features/groups/group_create_controller_test.dart:132-167
'test_EARS_GROUP_19_create_passes_selected_members_and_navigates'
  final opened = <String>[];
  final c = build(openedThreads: opened, …);
```

Every assertion is about the seam. `_defaultOpenThread` — the destination the
user actually reaches — is never exercised by any test. The seam that made the
controller testable also made the real destination invisible. This is the same
shape as `E07-B01`'s original test, which asserted the buggy behaviour and
therefore protected it.

## Second finding, surfaced by writing the test

The navigation future was **awaited**:

```dart
await Get.toNamed<dynamic>('/chat/$groupId');
```

`Get.toNamed`/`Get.offNamed` complete when the route they push is **popped**,
not when the navigation happens. So `create()` suspends indefinitely, its
`finally` never runs, and `submitting` never returns to `false` — the create
button is disabled for the remaining life of that controller.

This was invisible for the same reason as the first finding: the injected
seam (`openThread: (id) async => openedThreads?.add(id)`) completes
immediately, so no test ever held the real future. The test written for this
bug hung for the full ten-minute `flutter test` timeout on its first run,
which is how it was found.

The fix is `unawaited(...)`, and the regression assertion is
`expect(c.submitting.value, isFalse)` after a successful create.

## Repro
1. Have ≥1 trusted relationship.
2. Navigate to `/groups/new`, enter a name, select a member, tap create.
3. The group is created (a real `groups` row), and the app pushes
   `/chat/<groupId>`.
4. Type any text and send.

## Expected
`FR-COMM-002` — group communication via text. Either the group thread renders
group messages and sends via the group path, or the app does not navigate
there. A successful create must not deposit the user in a screen that
structurally cannot serve the conversation it was given.

## Actual
Identical to `E07-B01`'s measured behaviour: existing group messages render
through the undecryptable-bubble path (the 1:1 `CryptoService` holds no
sender-key chain for them), and `send()` fails closed but reports the
**generic retryable** copy "Could not send this message. Try again." Retrying
can never succeed.

## Severity
**S2 / P1** — same classification the human set for `E07-B01`, same defect,
and here it is the *terminal step of the create-a-group journey*, so every
user who creates a group hits it.

## Fix
Direction **(a)**, already chosen by the human for this exact defect on
2026-09-02 and applied here rather than re-decided: do not navigate into the
1:1 chat with a group id. This bug's fix does **not** re-open that choice and
does **not** make a new product decision.

`Get.offNamed('/conversations')` replaces the create screen with the
Conversations screen, whose `Groups` section now shows the new group. That is
a **built, real** destination; the created group is visible there; and it
needs **no new copy**, so nothing is invented. `Get.back()` was rejected: the
route is reachable only by direct navigation today (`routes.dart:90-95`), so
there is not always a page beneath it to pop to.

## The design contract disagrees, and that is a separate, human item

`design/screens/group-create.md:34` says:

> **Leads to:** `/chat/:id` for the new group's thread on success.

That line was written by `E07-T12` on **2026-08-31**; the human's `E07-B01`
decision closing that destination to group ids came **2026-09-02**. The
contract is stale with respect to a later human decision, and the destination
it names does not exist in a usable form — the group thread is `GAP-020`,
still gated on `OQ-E07-13`.

This bug does **not** edit the contract (rule 2: an agent does not rewrite a
measured contract to match its code). The correction is carried to the human
as part of **D5** — "how does anyone reach a group thread?" — together with
`GAP-020`/`OQ-E07-13`.

## What this fix does NOT do
- Does **NOT** resolve `OQ-E07-13` or build `GAP-020`'s group thread.
- Does **NOT** edit `design/screens/group-create.md` or any design contract.
- Does **NOT** add a create-group entry point (that is `GAP-018`'s open
  entry-point decision, still awaiting the human).
- Does **NOT** touch `ChatController`, `ConversationsController`, or the
