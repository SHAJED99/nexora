# E01-T02 · Minimal Firebase account/device metadata wrapper

> **Pivoted from Firestore to Realtime Database mid-task** (2026-08-26,
> human decision): Firestore requires the project to be on the Blaze
> (pay-as-you-go) billing plan just to provision a database at all, even
> within its free-tier quota. The human explicitly declined enabling
> billing. Realtime Database has no such requirement and covers this
> task's needs (one small JSON object per device, direct key lookup only,
> no queries). Every "Firestore" reference below that predates the pivot
> is corrected inline; see the Run log for the full story.

## 1. Goal
Write the account-id ↔ device-id mapping to Firebase Realtime Database so
a user's devices are discoverable under their account — strictly within
the boundary FR-FB-001/002 already lock (metadata only, never
content/keys).

## 2. Business logic
- FR-FB-001: Firebase may store device registry metadata, device public
  identity info, user config.
- FR-FB-002: Firebase must NOT store plaintext, recordings, private/session
  keys, or permanent location history — this task's schema has none of those
  fields, by construction.
- FR-AUTH-004: multiple devices per account — this is what makes that
  queryable across devices/sessions.

## 3. What this task does
- `firebase_metadata_service.dart`: one function writing
  `/users/{uid}/devices/{deviceId}` with `{ deviceId, createdAt,
  lastSeenAt, platform: 'android' }` — no other fields.
- Firestore security rules restricting read/write to the authenticated
  owner (`request.auth.uid == uid`).
- Called from `SignInUseCase` (E01-T01) after the local device row is
  written — best-effort: a Firestore write failure must not block local
  sign-in (offline-first constitution).

## 4. What this task does NOT do
- Does NOT implement E11's fuller scope (revocation, push tokens, version
  policy) — this is the minimal slice E01 needs, nothing more.
- Does NOT sync trust/relationship data (E02's job).
- Does NOT retry failed writes with a queue — best-effort fire-and-forget
  for this task; a real offline-write-queue is E05's job if it turns out
  to be needed here too.

## 5. Contract

### Data
Realtime Database node `users/{uid}/devices/{deviceId}` — fields: `deviceId`
(string), `createdAt` (`ServerValue.timestamp`), `lastSeenAt`
(`ServerValue.timestamp`), `platform` (string, literal `"android"` for v1
per C-001). No other fields.

### Functions
```yaml
- signature: "FirebaseMetadataService.registerDevice(uid: String, deviceId: String) -> Future<void>"
  params: { uid: "Firebase Auth uid", deviceId: "the local device identity's id" }
  returns: "void — swallows and logs (via ObservabilityService) any Realtime Database error rather than throwing, since this must never block local-first sign-in"
  purpose: "Best-effort registration of this device under the account for FR-AUTH-004 multi-device visibility"
```

### External services & flags
Firebase Realtime Database, same project (`nexora-b3a97`, instance
`nexora-b3a97-default-rtdb`, created via the Firebase console since
programmatic RTDB-instance creation isn't exposed by the `firebase` MCP
server or scriptable through the CLI's interactive-only `init database`
wizard). No new secrets — same `google-services.json` as E01-T01.

## 6. Risks

  own FR-FB-001 justification, not "might be useful later."
