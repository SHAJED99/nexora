# E01-B02 · A failed Google sign-in is a dead end

## 1. Goal
A user whose first sign-in attempt fails — for the most ordinary reason
there is, no network yet — can see that it failed and try again, without
force-stopping the app.

## 2. Business logic

`EARS-AUTH-3` requires a failed sign-in to be surfaced as a mapped failure,
never a crash. `LoginController` already did the mapping and the logging
correctly. The screen was the problem: `login_view.dart` rendered the
heading as a `const Text('Signing in with Google...')`, so the only thing
`signingIn` controlled was whether a spinner or a `SizedBox` was drawn.

On failure the controller set `signingIn = false`. The spinner vanished.
The heading — being `const` — kept asserting that sign-in was in progress.
There was no third state, and nothing to tap.

**Why this is S1, not cosmetic.** It is not a mislabelled screen; it is a
terminal state. A device in it has no identity, so it has no app: no
conversations, no devices, no settings. The only exit is force-stopping,
which is a developer action. `design/screens/login.md` declares
`states: [default]` — one state — so there was nowhere for a failure to go.

## 3. What this task does

1. `LoginController` gains `signInFailed` and `retry()`. The flag is cleared
   at the **start** of every attempt, so the heading can never claim to be
   both signing in and failed. `retry()` is a no-op while an attempt is in
   flight, so a double tap cannot start two concurrent sign-ins.
2. `LoginView`'s heading becomes reactive. On failure it reads
   **`Couldn't sign in. Try again.`**
3. The spinner's slot becomes a **`Try again`** action that re-runs sign-in
   and returns the screen to its in-progress state.
4. `design/screens/login.md` and `design/gaps.md` record the new state as
   **GAP-047b**, with the copy line left pending human confirmation.

### Why a plain `TextButton`

The retry action deliberately does **not** use `OnProcessButtonWidget`, the
widget every other button in this app uses. That widget begins its tap
handler with `if (isRunning != OnProcessButtonStatus.stable) return;`, so an
instance whose internal state is not `stable` silently swallows every tap.
This button is the only exit from a dead end; it must not be able to do
that. This is a local, defensive choice — **not** a claim that the widget is
defective, which is a separate open question (see §9).

## 4. What this task does NOT do  ← the scope fence

- **Does NOT distinguish failure causes** (offline vs cancelled vs rejected).
  One honest line, one action. Telling them apart is a product decision.
- **Does NOT touch `SignInUseCase`, `GoogleAuthService` or
  `FirebaseMetadataService`.** The mapping already worked.
- **Does NOT change any other screen's use of `OnProcessButtonWidget`.**
- **Does NOT hand-edit `login.md`'s generated tables** (`source: ui`); only
  the hand-written sections below the generator's marker.
- **Does NOT invent an error colour.** `GAP-009`'s precedent: the failure is
  carried by the words.
