# E01-B01 · Cold-start onboarding shows a placeholder code and a stale, self-clearing dead end

## 1. Goal
A user who signs in on a device with no prior session reaches a working app
without being shown placeholder text, and without having to restart to escape
a state the app has already left.

## 2. Findings (three, one flow)
All three were observed in a single uninterrupted sequence on hardware; each
is independently fixable, which is why they are enumerated rather than merged.

1. **Literal placeholder rendered to the user.** The trusted-device screen
   reads `Code: [pairing code]`. Whatever supplies the code is either unset at
   paint time or never substituted. A user asked to read this code aloud to
   another device has nothing to read.
2. **`Continue without history` appears to dead-end.** After the
   start-fresh confirmation, the shell renders with
   `Messaging is unavailable: no local device identity yet (sign in required)`
   and no visible remedy. Sign-in *had* completed -- that is what produced the
   trusted-device screen in the first place -- so the message is also
   misleading about its own cause.
3. **The dead end is stale state.** A force-stop and relaunch produced a fully
   working Dashboard with no additional sign-in, proving the local identity had
   in fact been provisioned. So (2) is a UI state that never recomputed after
   provisioning completed, not a genuine failure. This is the most serious of
   the three: a real user has no reason to try restarting, and would
   reasonably conclude the app is broken.

> Note (2026-09-18): this task originally carried `design_contract: design/screens/onboarding.md`,
> a path that was invented and does not exist. No design contract covers these onboarding
> screens yet. If one is authored later, point this field at it.

## 3. What this task does NOT do
- Does not change the auth strategy or ADR-0005's local-identity model; the
  identity provisioning itself works (finding 3 proves it).
- Does not redesign the onboarding screens or their design contract.
- Does not touch the trusted-device *protocol*; only the code's display.
- Does not address the Bluetooth transport work in E04.

## 4. Risks
- **Findings 2 and 3 may share one root cause** (a provisioning future whose
  completion never notifies the view). Fixing the refresh may resolve both;
  the fix must not stop at hiding the message while leaving the race.
- **Ordering, not absence.** Treating finding 2 as "identity missing" and
  adding a sign-in prompt would be wrong: the identity exists moments later.

## 5. Acceptance criteria (EARS)
- **EARS-AUTH-x1**: WHERE a pairing code is displayed, the system SHALL render
  the actual code and SHALL NOT render a placeholder token. (FR-AUTH-001)
- **EARS-AUTH-x2**: WHEN local device identity provisioning completes, the
  system SHALL update any "identity unavailable" state without requiring an
  app restart. (FR-AUTH-001, FR-UI-004)

## Open Questions

Both findings were traced to their exact cause on 2026-09-18 and then **stopped
at a gate**, rather than fixed. Neither stop is a shrug: each names the rule
that reserves the decision, with options and an advisory recommendation.

- **OQ-E01-B01-1 — what IS the pairing code?** (finding 1, the literal
  `[pairing code]` on screen)
  - **Status:** 🟡 open — **rule 1 (spec is law): the spec is silent, so this stops here.**
  - **Evidence:** `device_enrollment_view.dart:106` renders the string
    `'Code: [pairing code]'` literally. `grep -rn` across the whole of
    `lib/features/recovery/` returns **exactly that one line** — there is no
    code generator, no code field, nothing in
    `device_enrollment_controller.dart`. And
    `design/screens/device-enrollment.md` §Copy specifies
    `Ask a trusted device nearby to approve this one. Code: [pairing code]`
    **verbatim**, under a heading that calls it "proposed copy". So the
    implementation copied the contract faithfully; the contract never decided
    what the code is.
  - **Why I did not just fix it:** an enrolment code is the shared secret that
    lets one device vouch for another. Choosing its format, length, entropy,
    lifetime and comparison rule is device-trust design — rule 3 territory, and
    ADR-0005 owns local identity/session. Inventing one to remove an ugly
    string would be the worst possible reason to design a security primitive.
  - **Advisory:** the cheapest honest interim is to render **no code line at
    all** in the `waiting` state until the scheme exists, so the screen stops
    showing a placeholder as if it were data. That is still a copy change
    against a design contract, so it needs the 🧍 `design_contract_approval`
    gate on `design/screens/device-enrollment.md`.

- **OQ-E01-B01-2 — how should the app notice that identity arrived
  mid-session?** (findings 2 and 3, which share one cause)
  - **Status:** 🟡 open — **rule 3: this is an architecture call inside ADR-0005's area.**
  - **Root cause, fully traced:** `main.dart:98` reads
    `db.latestDeviceIdentity()` **once at launch**; `main.dart:106` collapses a
    missing identity to `selfDeviceId = ''`; `MessagingStack.create` then stamps
    `status = unavailable('no local device identity yet (sign in required)')`
    (`messaging_stack.dart:669`). `MessagingStackStatus` is a **sealed immutable
    value** — no stream, no notifier — and the stack is registered
    `Get.put(messagingStack, permanent: true)` (`bindings.dart:159`), so it is
    never rebuilt. Both `dashboard_controller.dart:304` and
    `conversations_controller.dart:315` read it once in `onInit`, set
    `errorMessage`, and `return`. `LoginController` writes the identity row
    *after* all of this. Nothing re-reads it, so the error persists for the life
    of the process — and a restart re-runs `main.dart:98`, which is exactly why
    force-stop + relaunch cleared it on **both** phones.
  - **Options:**
    (a) **Re-create the stack once sign-in completes.** Precedent already
        exists: `settings_binding.dart:121` does
        `Get.delete<MessagingStack>(force: true)`. `LoginController` already
        holds a `MessagingStack?` and finds the singleton by lookup, so it is
        the natural trigger point.
    (b) Make `status` observable and have both controllers listen — changes a
        sealed value class's contract and touches every caller.
    (c) Re-check on app resume via `bindings.dart:576`'s existing
        `AppLifecycleState.resumed` branch — **weakest**, because sign-in
        typically happens without ever backgrounding the app, so the common
        case would still not recover.
  - **Advisory:** **(a)**, on the strength of the existing precedent and because
    it fixes the cause rather than papering the symptom. Whichever is chosen,
    the regression test is the one this bug already describes: provision
    identity *after* first paint and assert the UI recovers without a restart.
