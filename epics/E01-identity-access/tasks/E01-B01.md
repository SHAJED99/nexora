# E01-B01 · Cold-start onboarding shows a placeholder code and a stale, self-clearing dead end

## 1. Goal
A user who signs in on a device with no prior session reaches a working app
without being shown placeholder text, and without having to restart to escape
a state the app has already left.

## 2. Findings (three, one flow)
All three were observed in a single uninterrupted sequence on hardware; each
is independently fixable, which is why they are enumerated rather than merged.

1. **Literal placeholder rendered to the user.** The trusted-device screen
   reads `Code: [pairing code]`. Whatever supplies the code is either unset at
   paint time or never substituted. A user asked to read this code aloud to
   another device has nothing to read.
2. **`Continue without history` appears to dead-end.** After the
   start-fresh confirmation, the shell renders with
   `Messaging is unavailable: no local device identity yet (sign in required)`
   and no visible remedy. Sign-in *had* completed -- that is what produced the
   trusted-device screen in the first place -- so the message is also
   misleading about its own cause.
3. **The dead end is stale state.** A force-stop and relaunch produced a fully
   working Dashboard with no additional sign-in, proving the local identity had
   in fact been provisioned. So (2) is a UI state that never recomputed after
   provisioning completed, not a genuine failure. This is the most serious of
   the three: a real user has no reason to try restarting, and would
   reasonably conclude the app is broken.

## 3. What this task does NOT do
- Does not change the auth strategy or ADR-0005's local-identity model; the
  identity provisioning itself works (finding 3 proves it).
- Does not redesign the onboarding screens or their design contract.
- Does not touch the trusted-device *protocol*; only the code's display.
- Does not address the Bluetooth transport work in E04.

## 4. Risks
- **Findings 2 and 3 may share one root cause** (a provisioning future whose
  completion never notifies the view). Fixing the refresh may resolve both;
  the fix must not stop at hiding the message while leaving the race.
- **Ordering, not absence.** Treating finding 2 as "identity missing" and
  adding a sign-in prompt would be wrong: the identity exists moments later.

## 5. Acceptance criteria (EARS)
- **EARS-AUTH-x1**: WHERE a pairing code is displayed, the system SHALL render
  the actual code and SHALL NOT render a placeholder token. (FR-AUTH-001)
- **EARS-AUTH-x2**: WHEN local device identity provisioning completes, the
  system SHALL update any "identity unavailable" state without requiring an
  app restart. (FR-AUTH-001, FR-UI-004)

## Run log
- 2026-09-18, filed. Observed on a Pixel 8 Pro at 01:39-01:46 while restoring
  a signed-out phone for E04-B36's live re-run; screenshots were taken at each
  step. The sequence and the restart's effect are recorded above exactly as
  seen. Note the app was driven via adb by the agent, not by the device's
  owner, for every step except the Google account selection.
- **2026-09-18 05:44-05:47, finding 3 reproduced on a SECOND, different device**
  (Redmi 10 2022, `21121119SG`), after a `flutter install -r` upgrade signed it
  out. Same sequence, same result: Google sign-in completed -> trusted-device
  screen -> "No trusted device responded" -> "Continue without history" ->
  "You're starting fresh" -> Continue -> shell renders with
  `Messaging is unavailable: no local device identity yet (sign in required)`
  and no visible remedy. Force-stop + relaunch cleared it with no further
  sign-in, exactly as on the Pixel.
  This raises finding 3 from a single-device oddity to a **reproducible defect
  in the start-fresh path on independent hardware**, and raises its practical
  severity: two of two devices that took this path landed in a state a real
  user would read as "the app is broken", with no hint that restarting fixes
  it. Finding 1 (the literal `[pairing code]` placeholder) was also seen again
  on the Redmi at 05:44.
