# E01-T01 · Real Google Sign-In + device identity

## 1. Goal
Replace genesis's stubbed 1-second-delay "sign-in" with a real Firebase
Auth + Google Sign-In flow, and replace the stub device-id generator with
a cryptographically-secure one — the first real identity in the app.

## 2. Business logic
- FR-AUTH-001: Google Authentication via Firebase Auth is the sign-in mechanism.
- FR-AUTH-002/003: device cryptographic identity is independent of account
  identity — generated locally, never derived from or dependent on the
  Firebase Auth session.
- FR-AUTH-004: multiple devices per account are independent rows, not one
  shared record — proven by running this on two devices signed into the
  same Google account.
- FR-AUTH-005: welcome screen offers no auth path other than Google.

## 3. What this task does
- Add `firebase_core`, `firebase_auth`, `google_sign_in` to `pubspec.yaml`
  (direct implementation of already-accepted ADR-0005 / BRD §5 — not a new
  foundational choice).
- Apply the Google Services Gradle plugin so `google-services.json`
  (already present from Firebase provisioning) actually takes effect.
- `Firebase.initializeApp()` in `main.dart` before `runApp`.
- `GoogleAuthService` (`core/auth/`): wraps `google_sign_in` +
  `firebase_auth`'s `signInWithCredential` — returns the signed-in
  Firebase `User` (or throws a mapped `AppFailure`).
- `SignInUseCase` calls the real service instead of `Future.delayed`.
- Device id generation switches from `Random()` to `Random.secure()` (the
  TODO already left in `login_controller.dart` — this task resolves it).
  This is a random device identifier, not a full asymmetric keypair — the
  crypto *protocol* (X3DH keys) is E03's job (OQ-E03-1 still open); this
  task only needs a unique, cryptographically-random device id per FR-AUTH-003.
- Extend the `DeviceIdentities` Drift table (if needed) with an
  `account_uid` column linking to the Firebase Auth uid, so multiple
  devices under one account are queryable.

## 4. What this task does NOT do
- Does NOT implement the X3DH/Double-Ratchet crypto protocol (E03) — device
  id here is a random token, not a keypair.
- Does NOT implement the Firebase account↔device metadata document/collection
  (E01-T02) — this task only gets Auth working and the device row locally.
- Does NOT touch the welcome screen's UI/copy — `continueWithGoogle()`'s
  call site stays the same; only what happens after changes.
- Does NOT add sign-out, account switching, or session-refresh handling —
  first-run sign-in only. Note as a gap if it comes up, don't build it here.
- Does NOT add error-state UI beyond mapping failures to `AppFailure` and
  logging via `ObservabilityService` — a full error screen is out of scope
  unless the design contract already has one to build against.

## 5. Contract

### Functions
```yaml
- signature: "GoogleAuthService.signIn() -> Future<UserCredential>"
  params: {}
  returns: "Firebase UserCredential on success; throws AppFailure('auth.google_sign_in_failed') on any failure (cancelled, network, etc.)"
  purpose: "Wraps google_sign_in + firebase_auth into one call the use case invokes"

- signature: "SignInUseCase.call(deviceId: String) -> Future<void>"
  params: { deviceId: "Random.secure()-generated device identifier" }
  returns: "void — writes the device identity row (with account_uid) via DeviceIdentityRepository"
  purpose: "Orchestrates real Google sign-in + local device-identity persistence"
```

### Data
Drift migration: add `account_uid TEXT NULL` to `device_identities` (additive,
schema version bump per `docs/conventions.md`'s migration rule — reversible,
no backfill needed since this is pre-release).

### External services & flags
Firebase Auth (Google provider) — already enabled + deployed on project
`nexora-b3a97` (see `epics/E01-identity-access/epic.md` OQ-E01-1). No new
secrets: `google-services.json` already present.

## 6. Risks
- Google Sign-In on an emulator/WSA-style device without Play Services can
  fail in ways unrelated to this code — test on the physical/Wi-Fi device
  (`192.168.0.145:5555`), not WSA.
- `Random.secure()` alone is not a substitute for a real device keypair —
  don't let the naming ("cryptographic device identity") tempt inventing
  E03's protocol early. Keep it to a random token.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-AUTH-1**: WHEN a user taps "Continue with Google", the system SHALL authenticate via Firebase Auth. (FR-AUTH-001)
- **EARS-AUTH-2**: The system SHALL generate a device identity independent of the account identity. (FR-AUTH-003)
- **EARS-AUTH-3**: IF sign-in is cancelled or fails, THEN the system SHALL surface an `AppFailure` rather than crash or hang. (FR-AUTH-001, error path)

### Tests
- `test_EARS_AUTH_1_signs_in_via_firebase` — mocks `GoogleAuthService`, asserts `SignInUseCase` writes a device row with a non-null `account_uid`
- `test_EARS_AUTH_2_device_id_is_secure_random` — asserts device id generation uses `Random.secure()` (not the old `Random()`), distinct across calls
- `test_EARS_AUTH_3_signin_failure_maps_to_app_failure` — mocked service throws, use case surfaces `AppFailure`, does not crash

### Manual
1. Run on the Wi-Fi device → tap "Continue with Google" → real Google account picker appears → select account → lands on `/home`.
2. Repeat on a second device (or after clearing app data) with the same Google account → confirm a second, independent device-identity row.
