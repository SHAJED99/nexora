# E09-B11 · the identity-poisoning exploit needs a protocol decision, not a patch

## The defect

`E09-B09` fixed `location_share_service.dart` to require
`getIdentity(address) != null` before decrypting a location frame. The
round-2 cross-model review of that fix found two things, both confirmed by
independent probes against the fixed code:

**1. The exploit is not closed — it costs one extra frame.**
`getIdentity != null` proves only that *some* write happened to that
identity slot, not that the write was authenticated. `SessionBuilder
.process` (invoked from every one of the four sibling decrypt call sites
below) calls `saveIdentity` unconditionally under trust-on-first-use
whenever no prior identity is recorded. An attacker sends **one** forged
`PreKeySignalMessage` through any sibling path first — a regular message,
a call-signaling frame, a group-membership frame, or a group message —
which poisons `(victimAddress, 1)` with the attacker's key exactly as
`E09-B09`'s original repro did. The **second**, identical forged location
frame then finds `getIdentity != null` (it is not null — it is the
attacker's own key, written a moment ago) and sails through the new gate.
`location_fixes` is populated with the forged coordinate exactly as before;
the real victim's genuine identity is still permanently overwritten.

Confirmed call sites sharing the same unguarded shape:
- `lib/features/messaging/domain/receive_message_use_case.dart:107`
- `lib/core/calls/call_signaling.dart:608`
- `lib/core/messaging/group_membership_service.dart:500`
- `lib/core/messaging/group_crypto_service.dart:389`

**2. The fix also breaks legitimate first-time location sharing.**
`E09-B09`'s fix comment asserted "a location share is never a legitimate
first contact... cannot regress any real use case." Both halves are false:
E02's pairing/trust flow has zero crypto-store side effect (relationship
state and Signal session state are entirely independent — trusting someone
in E02 does not exchange any Signal message), and `ensureSession`'s prekey
exchange saves the identity only on the **sender's own store**
(`prekey_exchange.dart:445`) — the **responder's** store gets its record of
the sender's identity only from processing an inbound prekey message,
which is exactly the code path `E09-B09`'s gate now blocks unconditionally.
Net effect: two devices that are mutually `trusted` in E02, sharing
location for the genuinely first time with no prior Signal session in
either direction, now have their location share **silently and
permanently dropped** by `E09-B09`'s own gate. Latent today only because
`LocationShareService` has no UI caller yet.

## Why this is not a per-file fix

The actual defect is `isTrustedIdentity`'s unconditional trust-on-first-use
policy (`drift_signal_store.dart:144-148`) combined with there being **no
authenticated first-contact mechanism anywhere in this app** — nothing
verifies that the identity key received on first contact with a peer
genuinely belongs to that peer, for *any* feature (messaging, calls,
groups, or location). `E09-B09`'s gate is a location-specific workaround
that (a) doesn't close the hole, because the store it queries is shared
and unguarded everywhere else, and (b) actively regresses a legitimate
flow that depended on the exact behavior it now blocks.

Closing this for real requires one of:
- **A genuine authenticated first-contact mechanism** — e.g. an
  out-of-band verification step (safety-number/QR-code comparison, the
  Signal-app precedent), or a server-mediated identity attestation via
  `E11`'s device directory (`ADR-0008`) treated as authoritative for
  first-contact identity resolution instead of TOFU.
- **A deliberate, disclosed acceptance of TOFU's risk profile app-wide**,
  with `E09-B09`'s location-specific gate reverted (since it doesn't help)
  and the location-forgery risk accepted as a known, documented limitation
  alongside the *same* risk that already exists, unaddressed, in messages,
  calls and groups.
- **Some third option the human sees that this bug file doesn't.**

**This is `ADR-0003`'s territory** (the crypto protocol decision), not an
agent's call, per rule 3 and `E09-B09`'s own "does NOT do" list ("Does not
change ... `isTrustedIdentity`'s trust-on-first-use policy. TOFU is
ADR-0003 territory and a rule-3 human call"). The scope now provably spans
every epic that decrypts anything (E05, E06, E07, E09 at minimum), not
just location sharing — this is why `owner_agent` is `planner`, not
`builder`, and `status` is `blocked`.

## Severity
**S1**, unchanged from `E09-B09` — the exploit remains live app-wide, not
merely un-fixed in one file. The location-specific instance is the
*discovered* instance, not the *only* one.

## What happens to `E09-B09`'s existing fix
Not reverted by this bug. It is inert-but-harmless against the exploit
(closes nothing, per finding 1) and does regress a legitimate flow (finding
2) — whether to revert it, keep it as one layer of defense-in-depth once a
real fix exists, or replace it is part of the human decision this bug
raises, not decided here.

## What this bug does NOT do
- Does **not** choose a fix direction. Three shapes are named above; the
  choice is `ADR-0003`'s human gate, per rule 3.
- Does **not** modify any code. This bug is the escalation and the record;
  implementation is a fresh, properly-scoped task (or tasks, likely
  cross-epic) sharded only after the human decides.
- Does **not** claim the four sibling call sites are exploitable via THIS
  bug's own probes beyond what E09-B05's earlier re-review already flagged
  as unverified for calls/groups (`epics/E09-location-sharing/tracker.md`
  §Carried-forward observations) — the messaging path
  (`receive_message_use_case.dart:107`) is the one directly probed and
  confirmed in this bug's own review; calls/groups share the identical
  code shape and are assessed as very likely vulnerable by the same
  mechanism, not independently reproduced end-to-end in this pass.
