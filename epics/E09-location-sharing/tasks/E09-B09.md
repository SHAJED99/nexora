# E09-B09 · `frame.source` IS trusted as an identity claim on the location receive path

## The defect

`E09-T03` §2 states the invariant in bold: *"The claimed sender is whichever
Signal session decrypted the body, never `frame.source`."* §6 calls trusting
`frame.source` *"the single highest-severity mistake available here
(E06-B04)."* `location_share_service.dart:357-362` carries a comment asserting
the invariant holds:

```dart
// The address that decrypted this frame IS the authenticated sender
// ... decrypt only succeeds because the session bound to that address
// actually produced this ciphertext.
final peerDeviceId = wireFrame.source;
```

**That assertion is false for a `PreKeySignalMessage`.** The X3DH responder
path does not decrypt *under an existing session bound to the address* — it
**creates** one from the identity key carried inside the attacker's own
message. `CryptoService.decrypt` (`crypto_stub.dart:138-140`) hands a
`PreKeySignalMessage` straight to `SessionCipher.decrypt`, which runs
`SessionBuilder.process`, which gates only on
`DriftSignalProtocolStore.isTrustedIdentity` — and that returns
**`true` on trust-on-first-use** when no identity is yet recorded for the
address (`drift_signal_store.dart:144-148`):

```dart
final previous = await getIdentity(address);
if (previous == null) {
  // Trust-on-first-use: nothing recorded yet.
  return true;
}
```

So for any peer the device has *not yet exchanged a Signal message with*,
`decrypt(SignalProtocolAddress(frame.source, 1), ct)` succeeds for a
ciphertext produced by **anyone**. `frame.source` — a field any mesh node can
set to anything (E06-B04) — becomes the stored peer identity.

## Repro

Reviewer probe, run against `epic_09` @ `18d658e`, **failed**:

1. Stack `bob`; stack `mallory`. Bob has a `trusted` `RelationshipState` for
   `alice`, global sharing on, per-peer sharing on for `alice`. Bob has
   **never established a Signal session with `alice`** (pairing/trust is
   E02's; it does not imply a session).
2. Mallory calls `establishSession(SignalProtocolAddress('bob', 1), bobBundle)`
   and encrypts a fabricated `LocationShareFrame(latitudeE7: 511111111,
   longitudeE7: -1111111)`. The result is a `PreKeySignalMessage` (probe
   printed `PROBE A ciphertext type: PreKeySignalMessage`).
3. Wrap it: `RelayPacketFrame(payloadType: control, destination: 'bob',
   source: 'alice', payload: encodeCiphertextControlBody(ct))`.
4. `bob.locationShareService.handleWireFrame(wireFrame)`.
5. `LocationFixRepository(db: bob.db).readFix('alice')`.

## Expected
`null`. `FR-LOC-004` / `E09-T03` §2/§6: an unauthenticated sender claim must
never become a stored peer identity, and a device must not be able to write a
row into `location_fixes` under someone else's name.

## Actual
```
PROBE A stored fix for alice: 51.1111111,-0.1111111
LocationFixRow(peerDeviceId: alice, latitude: 51.1111111,
               longitude: -0.1111111, capturedAt: 1000, receivedAt: ...)
```
Bob's device now shows Mallory's chosen coordinates as Alice's position, and
the receive-side `LocationVisibilityPolicy` gate passes it because it is
evaluated against **`alice`'s** relationship, not the real sender's.

**Second-order damage:** `SessionBuilder.process` also calls `saveIdentity`,
so Mallory's identity key is persisted as `alice`'s. Every subsequent genuine
message from the real Alice then fails `isTrustedIdentity` — a persistent,
remotely-triggerable denial of service against that peer, seeded by one
unsolicited frame.

## Severity
**S1** — security hole (forged-sender data injection into an
`FR-LOC-004`-protected store) plus persistent identity-store poisoning. No
workaround: the receive path has no other identity source, and the frame
requires no prior contact with the victim device.

Priority is the human's (`bug_priorities` gate); severity is the reviewer's.

## Fix direction (options — the choice is not the reviewer's)

The receive path needs an identity that is bound to the *session*, not to the
frame header. Three shapes, cheapest first:

**(a) Require a pre-existing, previously-authenticated session.** Before
`decrypt`, assert the store already holds an identity for
`SignalProtocolAddress(frame.source, 1)` (`getIdentity(address) != null`) and
drop otherwise. A location share is never a legitimate first-ever contact with
a peer whose relationship is already `trusted`/`allowed`. Smallest diff,
confined to this file, and does not touch the crypto layer. Closes the probe.

**(b) Reject `PreKeySignalMessage` on this control kind outright** — the
location sub-protocol always has `share()`'s own `ensureSession` behind it on
the sending side, so an inbound prekey message on kind 7 is anomalous by
construction. Needs a type check the current `CryptoService.decrypt` seam does
not expose; may need a narrow crypto-layer accessor (rule 3 territory).

**(c) Carry an authenticated sender id in the plaintext frame** and cross-check
it — the `GroupControlFrame.actorDeviceId` / `CallSignalingFrame.fromDeviceId`
shape `location_share.dart`'s own header notes is deliberately absent here.
This alone is **not** sufficient (the plaintext is the attacker's too) unless
paired with (a) or (b), and it is a wire-format change.

## Regression test (write it first)
The probe above, verbatim, as
`test_EARS_LOC_12_prekey_message_with_forged_source_dropped` in
`location_share_service_test.dart`. It must **fail on today's tree** (it
does — evidence above) and pass after the fix. It is the case the existing
`test_EARS_LOC_12_undecryptable_frame_dropped` explicitly declined to cover.

## What this fix does NOT do
- Does **not** change `crypto_stub.dart`, `drift_signal_store.dart`, or
  `isTrustedIdentity`'s trust-on-first-use policy. TOFU is ADR-0003 territory
  and a rule-3 human call; this fix makes the *location* receive path not
  depend on TOFU for identity.
- Does **not** change the wire format, `PayloadType`, `kControlKindLocationShare`,
  or `InboundPipeline`.
- Does **not** touch `share()`, the send-side gate, `LocationFixRepository`,
  `LocationVisibilityPolicy`, or `pruneFixesForNonVisiblePeers`.
- Does **not** audit or fix the same pattern in `call_signaling.dart`,
  `group_membership_service.dart` or `inbound_pipeline.dart`'s group-message
  handler. Each of those uses the same "decrypt under `frame.source`" shape and
  may share this defect — that is a separate cross-cutting sweep item, recorded
  in the E09 tracker's §Carried-forward observations, not this fix's fence.
- Does **not** write `RelayDeliveryState.failed` (`OQ-E09-T03-2` stands).

  confirms the fix, per the reviewer's own repro, not a paraphrase of it.

  fix's risk is in the pre-existing-identity gate accidentally firing on a
  real first share. Traced why it cannot: `E09-T03`'s own contract has

  SEND side before every encrypt — the sender always establishes a session
  first. On the recipient's side, that session establishment is exactly
  what runs `SessionBuilder.process`/`saveIdentity` for the sender's
  address as a side effect of receiving the *first* message of any kind

  `establishMutualSessions(alice, bob)` before any `handleWireFrame`, and
  all four still pass unmodified after the fix — the new `getIdentity`
  check is a no-op on every path that already has a real session, and only
  bites the exact forged-first-contact shape the bug file targets.
