# E09-B13 · a literal "--" inside an XML comment fails an existing regression test on `development`

## The defect

`android/app/src/main/AndroidManifest.xml`, the comment E09-T05 added above
the unrestricted location-permission declaration, reads (in part):

```
android:maxSdkVersion="30" to an unrestricted declaration -- this is
```

XML comments may not contain `--` anywhere in their body (only as the
closing `-->` delimiter). `test/core/background/background_service_test.dart`
already has a dedicated regression test for exactly this class of mistake —
`test_no_manifest_comment_contains_a_literal_double_hyphen` (added by an
earlier E10 task) — and it fails against the manifest as merged:

```
Expected: false
  Actual: <true>
comment body contains an illegal "--":  E09-T05 (OQ-E09-T05-2(a), human-approved 2026-09-04): lifted from
         and...
```

## Repro

1. `git checkout origin/development`.
2. `flutter test test/core/background/background_service_test.dart`.

## Expected

All tests pass — the manifest has no comment containing a literal `--`.

## Actual

`test_no_manifest_comment_contains_a_literal_double_hyphen` fails. Confirmed
on a clean `origin/development` checkout (commit `387a3fd`, "Merge pull
request #76 from SHAJED99/epic_09"), independent of any other epic's
changes — this is not something E10 or E11 introduced or can fix by
proxy, since neither epic's `files:` list touches the Android manifest.

## Severity

**S3** — test-only failure with no runtime impact: Android's manifest
parser is far more permissive than strict XML and does not reject this
comment in practice (the app builds and runs). What's broken is the
regression guard itself sitting red on `development`, which means any
*next* manifest edit's CI run inherits a pre-failing suite and can't tell
a new regression from this pre-existing one.

## Fix direction

Rewrite the comment to avoid every literal `--` (there appear to be several
in the same block, per the file's grep — not just the one line quoted
above). Replace with a different punctuation choice (e.g. em dash `—`, or
just a comma/period) at each site. No change to any non-comment manifest
content; the permission declaration itself is correct and out of scope.

## Regression test (write it first)

The existing `test_no_manifest_comment_contains_a_literal_double_hyphen`
already is the regression test — no new test needed. Falsify by
temporarily reintroducing one `--` after the fix, confirming the test goes
red again, then reverting.

## What this fix does NOT do

- Does **not** touch the permission declaration itself, its scoping, or
  any other manifest content — only the comment text.
- Does **not** re-open `E09-T05`'s own OQ-E09-T05-2(a) decision — the
  human-approved unrestricted-declaration choice stands; this is a
  comment-formatting defect introduced while writing it up.
- Does **not** get bundled into the E11 -> development merge that
  discovered it — E11's `files:` list does not include the manifest, and
  this bug predates and is independent of that merge (confirmed present on
  `origin/development` before E11 lands).
