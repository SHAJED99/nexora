# E09-B01 · a blocked peer stays visible on the live read path

## The defect

`LocationVisibilityPolicy.evaluate` takes **four** inputs. `read()` fetches
all four and is correct. `watch()` subscribes to only **two** of them:

```dart
// lib/features/location/domain/location_read_model.dart:271-286
subscriptions
  ..add(_fixes.watchFix(peerDeviceId).skip(1).listen(...))
  ..add(_settings.watchGlobalEnabled().skip(1).listen(...))
  ..add(_settings.watchPeerEnabled(peerDeviceId).skip(1).listen(...));
```

There is no subscription to the peer's `RelationshipState` — the input that
carries `blocked` and `notAuthorized`, i.e. the two most
security-restrictive reasons in the policy's own precedence order
(`location_visibility_policy.dart:41`). `RelationshipRepository` exposes no
stream at all, so `watch()` currently *cannot* observe the transition even
in principle.

Consequence: a surface that subscribes once (which is exactly what
`watch()`'s emit-on-listen contract invites, and what `E06-T18` is
contracted to do — `epics/E06-personal-chat/epic.md:110`) keeps rendering
`LocationAvailable` for a peer the user has just **blocked**, until some
*unrelated* fix-row or settings change happens to fire a recompute.

The method's own doc comment (`location_read_model.dart:230-235`) discloses
the *time*-based limitation (`OQ-E09-T04-2`, answered with `staleAt`). It
does not disclose this one, and `staleAt` does not mitigate it: a freshly
captured fix stays `live` for the full two-minute window regardless.

## Repro
1. In-memory `AppDatabase`. `relationships.upsert('peer-1', trusted)`;
   `settings.writeGlobalEnabled(true)`; `settings.writePeerEnabled('peer-1', true)`.
2. `fixes.upsertFix(peerDeviceId: 'peer-1', latitude: 12.0, longitude: 34.0,
   capturedAtMs: now, receivedAtMs: now)`.
3. `model.watch('peer-1').listen(events.add)`; await the emit-on-listen event.
   `events.last` is `LocationAvailable`.
4. `relationships.upsert('peer-1', RelationshipState.blocked)` — the user
   blocks the peer.
5. Await 400 ms. Read `events.last`.

## Expected
`FR-LOC-003` / **EARS-LOC-1** ("visible only when connected AND authorized
AND global-on AND per-user-on ALL hold") and **EARS-LOC-14** ("WHEN the
visibility policy does not hold for a peer, the system SHALL report
unavailable with the policy's reason **regardless of whether a fix is
stored**"). Step 5 must yield `LocationUnavailable(blocked)`.

## Actual
Reviewer's own probe (`test/sweep_probe_test.dart`, scratch, not committed):

```
PROBE events after block: 1 -> LocationAvailable(freshness: LocationFreshness.live,
  capturedAt: 2026-01-01 18:00:00.000, staleAt: 2026-01-01 18:02:00.000)

Expected: <Instance of 'LocationUnavailable'>
  Actual: LocationAvailable:<...>
```

One event total — the emit-on-listen one. Blocking produced no re-emit.
`await model.read('peer-1')` in the same test correctly returns
`LocationUnavailable`, which isolates the defect to `watch()`, not to the
policy.

## Severity
**S2** — the epic's headline security gate is not enforced on the live read
path, and there is no workaround available to the consumer: `E06-T18` cannot
know when to re-read, because the event that should trigger the re-read is
the one nothing emits. Not S1: nothing is transmitted to the blocked peer,
no data is lost, and `read()` is authoritative and correct.

**Reachability, stated plainly for the 🧍 `bug_priorities` gate:** no shipped
UI consumes `watch()` today — `E06-T18` is prospective and unsharded, and
`LocationReadModel` is not constructed in any composition root
(`messaging_stack.dart` wires `LocationShareService` only). The defect is
not reachable by a user of the current build. It becomes reachable the
moment `E06-T18` ships, and `E06-T18` is precisely the task this epic exists
to unblock. That is priority information; the severity of the path is
unchanged.

## Fix direction
Two honest shapes:
- **(a)** Add a `watch(peerDeviceId)` / `watchState(peerDeviceId)` stream to
  `RelationshipRepository` (Drift `watchSingleOrNull()`, the same
  emit-on-listen shape `watchPeerEnabled` already uses) and add it as a
  fourth `skip(1)` subscription. Correct and complete, but the new method
  lands in `lib/features/trust/` — **E02's file** — so the fix's `files:`
  fence must name it explicitly and the reviewer must check E02's own
  contract is not otherwise disturbed.
- **(b)** Keep the fix inside `lib/features/location/` by having
  `LocationReadModel` subscribe to the `relationships` table through its own
  Drift query. Narrower fence, at the cost of a second place that knows the
  table's shape.

**(a) is advisory** — a repository that cannot be observed is the actual
gap, and B01 is unlikely to be the last reader that wants it.

Whichever is chosen, also **update `watch()`'s doc comment**: it currently
enumerates "every stored-fix or settings change" as the complete trigger
set, and that enumeration is what made the omission invisible in review.

## Regression test (write it first)
`test_EARS_LOC_14_watch_re_emits_unavailable_when_the_peer_is_blocked` —
the repro above, asserting `events.last is LocationUnavailable` with reason
`blocked`. It must **fail on today's code** with the exact
`Actual: LocationAvailable` signature above, and pass after. Add the
mirrored case for a `trusted → unknown` de-authorization
(`LocationUnavailableReason.notAuthorized`), which fails identically today.

## What this fix does NOT do
- Does **not** delete the stored fix on block — that is **`E09-B02`**, a
  different defect with a different fix site and its own regression test.
  A relationship-state subscription may make B02's fix convenient; it does
  not close B02 without B02's own test.
- Does **not** add a timer, a poll, or any time-based re-emit —
  `OQ-E09-T04-2` was answered with `staleAt` and that answer stands.
- Does **not** change `LocationVisibilityPolicy`'s logic, its precedence
  order, or its `remoteState` single-sided limitation (`OQ-E09-T02-1`).
- Does **not** add a user-facing string, a timestamp format, or any
  rendering — still `design/screens/chat-location.md`'s and `E06-T18`'s.
- Does **not** touch the send or receive wire path
  (`location_share_service.dart`), the codec, or the schema.
- Does **not** build `E06-T18`.
