# E09-B08 · the privacy sweep only runs at startup, not on the block itself

## The defect

`E09-B06` wired `LocationShareService.pruneFixesForNonVisiblePeers()` to run
once, at `MessagingStack.create()`. That closes `E09-B02`'s original S2
finding down to: every *observable* surface (`LocationReadModel.read()`/
`watch()`) already re-evaluates the visibility policy live and correctly
reports `LocationUnavailable` for a blocked peer from the instant of the
block — but the underlying row in `location_fixes` is not physically
deleted until the app next restarts.

`RelationshipRepository` (`lib/features/trust/data/relationship_repository.dart`)
exposes only a per-peer `watchState(deviceId)` stream (`E09-B01`), not a
table-wide "any relationship changed" stream — so `E09-B06` had no in-fence
way to trigger the sweep reactively, and stopped rather than expanding
scope into E02's file.

## Expected
A blocked peer's stored coordinate is deleted promptly, not deferred to the
next process start.

## Actual
The row survives on local disk (plaintext SQLite, per E03's still-unowned
carry-forward on at-rest encryption) for the remainder of the app session
after a block, readable by anything with device storage access. Not
readable through this app's own UI/API by that point (E09-B01/B06 already
close that surface), but present on disk.

## Severity
**S3** — real, but bounded and workaround-able. The reviewer's own
assessment (PR #49 round 1): "bounded by process lifetime, workaround
exists" (restarting the app). Not S2: no live surface in the app can
observe or transmit the stale row; it is purely a data-at-rest residue.

## Fix direction
Add a table-wide watch stream to `RelationshipRepository` — e.g.
`Stream<void> watchAnyChange()` or similar, mirroring `watchState`'s
`watchSingleOrNull()`-based emit-on-listen shape but over
`select(relationships).watch()` (any row, any column) rather than one row.
Subscribe to it in `MessagingStack` and call
`pruneFixesForNonVisiblePeers()` on each emission (debounced/coalesced if a
bulk import or multi-row change would otherwise fire the sweep once per
row — check whether `RelationshipRepository.upsert` is ever called in a
loop before assuming this needs guarding).

## What this fix does NOT do
- Does **not** change `pruneFixesForNonVisiblePeers()`'s own logic — already
  correct and tested (`E09-B02`).
- Does **not** add a `Timer` or poll — event-driven off the new stream only.
- Does **not** touch `LocationReadModel`/`LocationVisibilityPolicy` — the
  live-read gate is already correct and unaffected by this bug.

## Regression test (write it first)
`test_EARS_LOC_5_blocking_a_peer_deletes_their_fix_immediately_not_at_next_launch`
— seed a visible peer's fix, construct `MessagingStack` once, THEN block the
peer via `RelationshipRepository.upsert(...)` without restarting the stack,
and assert the row is gone shortly after (await the sweep's own completion
signal or a short delay), with no second `MessagingStack.create()` call in
the test.

## Run log
- 2026-09-04 — Attempted the fix direction exactly as specified: added
  `RelationshipRepository.watchAnyChange()` (a table-wide `Stream<void>`
  over `.select(relationships).watch()`, mirroring `watchState`'s shape)
  and subscribed to it in `MessagingStack.create()`, re-running
  `pruneFixesForNonVisiblePeers()` on each emission. Both regression tests
  named in this bug file passed
  (`test_EARS_LOC_5_blocking_a_peer_deletes_their_fix_immediately_not_at_next_launch`
  in `messaging_stack_test.dart`, plus two direct `watchAnyChange` unit
  tests in `relationship_repository_test.dart`) — confirmed failing
  without the fix (fix survived on disk after a same-session block) and
  passing with it.
- **Discovered while running the full suite: this fix hangs unrelated
  widget tests.** `flutter test` (no filter) stalled indefinitely; bisected
  to `test/features/chat/presentation/chat_view_test.dart`,
  `conversations_view_test.dart`, `conversations_groups_test.dart`, and
  `dashboard_view_test.dart` — each timed out after the runner's own
  10-minute cap on `tester.pumpAndSettle()`. Root-caused with a minimal
  repro: a widget test that constructs a real `MessagingStack` (all four
  above do, via GetX bindings) hangs in `pumpAndSettle()` the moment
  `MessagingStack.create()` holds a **live Drift `.watch()` subscription**
  against `NativeDatabase.memory()` — confirmed by reducing the
  subscription's callback to a no-op `(_) {}` and reproducing the exact
  same hang, so this is not this bug's own callback logic (verified
  `pruneFixesForNonVisiblePeers()` only reads `relationships`/
  `location_fixes` and writes `location_fixes` — no write-back to
  `relationships` that could explain a self-triggering loop). Also tried
  cancelling the subscription explicitly in `MessagingStack.dispose()`
  (rather than relying on `db.close()` alone) — did not help, because the
  hang occurs **inside** the test body's own `pumpAndSettle()` call, before
  `tearDown`/`dispose()` is ever reached.
- **Reverted.** All production and test changes rolled back to
  `origin/epic_09`'s baseline (verified: `git status --short` clean,
  `chat_view_test.dart`'s previously-hanging test passes in <1s on the
  reverted tree). Shipping a fix for a P3, bounded, workaround-able
  data-at-rest issue at the cost of hanging an unbounded number of
  present and future widget tests is not a trade this session's delegated
  authority covers — this is now a real technical obstacle, not a scoped
  implementation choice.
- **Re-blocked, escalated.** This needs one of: (a) a different reactive
  trigger that isn't a live Drift `.watch()` stream held open across a
  widget test's lifetime (e.g. a plain `Stream`/`StreamController` the
  block use case pushes into directly, sidestepping Drift's reactive query
  machinery entirely — `RelationshipRepository.upsert`'s two callers are
  known and few), or (b) confirmation from someone with deeper
  Drift/`flutter_test` internals knowledge that a specific stream-teardown
  order avoids the hang (this session tried the obvious one — cancel in
  `dispose()` — and it didn't). Neither is a rule-3 foundational decision;
  this is squarely re-scoping an implementation approach, but it is beyond
  what this session was able to root-cause further without risking the
  same "ship something that looks done" mistake `L-process-015`-adjacent
  lessons warn against. Left `status: blocked`, not `done` and not
  silently reverted-and-forgotten — this Run log entry is the record.
