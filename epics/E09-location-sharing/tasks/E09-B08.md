# E09-B08 · the privacy sweep only runs at startup, not on the block itself

## The defect

`E09-B06` wired `LocationShareService.pruneFixesForNonVisiblePeers()` to run
once, at `MessagingStack.create()`. That closes `E09-B02`'s original S2
finding down to: every *observable* surface (`LocationReadModel.read()`/
`watch()`) already re-evaluates the visibility policy live and correctly
reports `LocationUnavailable` for a blocked peer from the instant of the
block — but the underlying row in `location_fixes` is not physically
deleted until the app next restarts.

`RelationshipRepository` (`lib/features/trust/data/relationship_repository.dart`)
exposes only a per-peer `watchState(deviceId)` stream (`E09-B01`), not a
table-wide "any relationship changed" stream — so `E09-B06` had no in-fence
way to trigger the sweep reactively, and stopped rather than expanding
scope into E02's file.

## Expected
A blocked peer's stored coordinate is deleted promptly, not deferred to the
next process start.

## Actual
The row survives on local disk (plaintext SQLite, per E03's still-unowned
carry-forward on at-rest encryption) for the remainder of the app session
after a block, readable by anything with device storage access. Not
readable through this app's own UI/API by that point (E09-B01/B06 already
close that surface), but present on disk.

## Severity
**S3** — real, but bounded and workaround-able. The reviewer's own
assessment (PR #49 round 1): "bounded by process lifetime, workaround
exists" (restarting the app). Not S2: no live surface in the app can
observe or transmit the stale row; it is purely a data-at-rest residue.

## Fix direction
Add a table-wide watch stream to `RelationshipRepository` — e.g.
`Stream<void> watchAnyChange()` or similar, mirroring `watchState`'s
`watchSingleOrNull()`-based emit-on-listen shape but over
`select(relationships).watch()` (any row, any column) rather than one row.
Subscribe to it in `MessagingStack` and call
`pruneFixesForNonVisiblePeers()` on each emission (debounced/coalesced if a
bulk import or multi-row change would otherwise fire the sweep once per
row — check whether `RelationshipRepository.upsert` is ever called in a
loop before assuming this needs guarding).

## What this fix does NOT do
- Does **not** change `pruneFixesForNonVisiblePeers()`'s own logic — already
  correct and tested (`E09-B02`).
- Does **not** add a `Timer` or poll — event-driven off the new stream only.
- Does **not** touch `LocationReadModel`/`LocationVisibilityPolicy` — the
  live-read gate is already correct and unaffected by this bug.

## Regression test (write it first)
`test_EARS_LOC_5_blocking_a_peer_deletes_their_fix_immediately_not_at_next_launch`
— seed a visible peer's fix, construct `MessagingStack` once, THEN block the
peer via `RelationshipRepository.upsert(...)` without restarting the stack,
and assert the row is gone shortly after (await the sweep's own completion
signal or a short delay), with no second `MessagingStack.create()` call in
the test.
