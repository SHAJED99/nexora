# E09-B06 · the privacy sweep exists and nothing calls it

## The defect

`LocationShareService.pruneFixesForNonVisiblePeers()` (`lib/features/
location/domain/location_share_service.dart`) is implemented, tested, and
proven correct by E09-B02's own regression suite. It has exactly one
reference in `lib/` — its own declaration:

```
$ grep -rn "pruneFixesForNonVisiblePeers" lib/
lib/features/location/domain/location_share_service.dart:<line>:  Future<void> pruneFixesForNonVisiblePeers() async {
```

`E09-B02`'s own reviewer required this fast-follow explicitly rather than
letting the fix stay "closable, not closed": B02 does not actually
discharge the S2 finding until this method is reachable at runtime. Both
of the pieces this wiring needs now exist on `epic_09`:
- `messaging_stack.dart` already constructs `LocationShareService` and is
  the project's one composition root for this kind of wiring (the same
  place `E09-T05` wired the real `LocationSource` in).
- `RelationshipRepository.watchState(deviceId)` (`E09-B01`, merged) gives a
  per-peer relationship-change stream to trigger an immediate sweep from,
  rather than only a coarse startup pass.

## Expected
`FR-LOC-004`/`FR-LOC-003` (via `E09-B02`): a blocked/de-authorized/globally-
disabled peer's stored fix is actually deleted at runtime, not merely
deletable by a method nothing calls.

## Actual
The sweep is dead code from the perspective of every real user journey.
Blocking a peer today still leaves their coordinate in `location_fixes`
until the app happens to receive another (now-rejected) frame from them —
`E09-B02`'s original defect, unchanged in practice.

## Severity
**S2** — unchanged from `E09-B02`. The fix exists; the defect does not care
that a fix exists if nothing runs it.

## Fix direction
Two calls, both in `messaging_stack.dart`:
1. **At startup**, after `LocationShareService` is constructed, call
   `pruneFixesForNonVisiblePeers()` once — closes the exposure window down
   to "at most until next launch" for every relationship change that
   happened while the app was closed.
2. **Reactively**, subscribe to a merged/any-peer view of
   `RelationshipRepository.watchState` (or, simpler and sufficient: listen
   for *any* relationship upsert — check whether `RelationshipRepository`
   already exposes a table-wide change stream before adding a new one) and
   call `pruneFixesForNonVisiblePeers()` on each change. This closes the
   exposure window to "immediately."

If a table-wide relationship-change stream does not exist yet, (1) alone
is an acceptable, disclosed partial fix for this bug — ship it and open a
new, explicitly-scoped Open Question for (2) rather than block on adding
new repository surface under a bug-fix fence. Prefer (1)+(2) if the stream
already exists or is trivial to add without touching `lib/features/trust/`
again.

## Regression test (write it first)
`test_EARS_LOC_5_sweep_runs_at_composition_root_startup` — construct
`MessagingStack` with a `location_fixes` row for a peer who is `blocked`
(or otherwise non-visible) at construction time, and assert the row is
gone after `create()`/startup completes, with **no message received**
in the test. Add the reactive case if (2) is implemented.

## What this fix does NOT do
- Does **not** change `pruneFixesForNonVisiblePeers()`'s own logic — it is
  already correct and tested (`E09-B02`).
- Does **not** add a new `Timer` or poll — the reactive trigger (if built)
  is event-driven off an existing/near-existing stream, not a schedule.
- Does **not** touch `lib/features/trust/` unless a table-wide watch
  stream must be added and doing so is genuinely trivial (mirrors
  `watchState`'s existing shape) — if it requires anything more, stop and
  ship (1) alone with an Open Question for (2), per Fix direction above.

## Open Questions
- **Fix direction (2), the reactive trigger, is not implemented.**
  `RelationshipRepository` currently exposes only `E09-B01`'s per-peer
  `watchState(deviceId)` — no table-wide/any-peer change stream exists.
  Adding one (even mirroring `watchState`'s shape exactly) means editing
  `lib/features/trust/data/relationship_repository.dart`, which is outside
  this bug's `files:` fence (`messaging_stack.dart` and its test only), so
  per the bug file's own instruction this is left unbuilt rather than
  silently expanding scope. Today's exposure window after this fix is "at
  most until next app launch" (startup sweep only), not "immediately."
  Suggested next: a small fast-follow task, scoped to touch
  `relationship_repository.dart`, that (a) adds a table-wide
  `watchAnyChange()`-style stream and (b) subscribes
  `LocationShareService.pruneFixesForNonVisiblePeers()` to it from
  `messaging_stack.dart`.
