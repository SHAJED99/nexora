# E09-B03 · the manifest claims a verification the task file says never happened

## The defect

`android/app/src/main/AndroidManifest.xml`, closing line of the E09-T05
comment block:

```xml
<!-- ... this permission now simply also existing on
     API 31+ for a DIFFERENT feature (location sharing) does not change
     what that scan itself asserts or needs. Re-verified per manual
     steps 4/5 (task file §8); recorded honestly, not assumed, in §9. -->
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
```

"**Re-verified** per manual steps 4/5 … recorded honestly, not assumed, in
§9" reads as a completed past-tense action. `E09-T05.md` §9 says the exact
opposite:

> **§8 manual steps 4/5 (E04 Bluetooth regression) and the on-device fix
> acquisition were not performed** — no physical Android device or running
> emulator was available in this execution environment.

and leaves both §7 checklist boxes and the DoD box unticked, deliberately:

> Left unchecked here deliberately: this box's own text is the standing
> finding this task must not violate by ticking it anyway.

The task file does everything right. The manifest then undoes it, in the one
place the claim is load-bearing.

## Repro
1. Open `android/app/src/main/AndroidManifest.xml`.
2. Read the E09-T05 comment above `ACCESS_FINE_LOCATION` without also
   opening `epics/E09-location-sharing/tasks/E09-T05.md` §9.
3. Ask: was E04's Bluetooth discovery regression-checked on a real API ≤30
   and API 31+ device before this cap was lifted?

## Expected
Rule 7 ("Done means proven … 'Looks right' is not evidence") and E04's own
retro precedent for on-device gaps: absence of measurement is stated, never
implied. A source comment about an unperformed check must say it is
**pending**, and name who closes it.

## Actual
The comment asserts it was re-verified. A maintainer at step 3 concludes
"yes, checked" and stops. The single most consequential unverified change in
this epic — lifting `maxSdkVersion="30"` on the permission E04's transport
posture is built around — is the one the comment mislabels.

## Severity
**S3** — no runtime behaviour is wrong; the manifest change itself is
correct as far as static analysis can establish (see below). The defect is
that it disarms the tripwire on a real, disclosed risk, and there is a
workaround: cross-reading `E09-T05.md` §9. Not S4: this is not a typo, it is
an incorrect factual claim about a safety check, sitting in the file whose
whole purpose is to be read on its own.

**What static verification *does* support** (recorded so the fix's new
comment can say something true rather than merely hedged, and so this
finding is not read as doubting the change itself):
- `geolocator_android-5.0.2`'s own library manifest declares no
  `ACCESS_FINE_LOCATION`, so no merger conflict — re-confirmed this sweep.
- `BLUETOOTH_SCAN`'s `android:usesPermissionFlags="neverForLocation"` is
  byte-identical to its pre-E09 form — re-confirmed by diff against
  `cc4baff` this sweep.
- `neverForLocation` is an assertion about what the *Bluetooth scan*
  derives. E09 derives position from the location provider, so the assertion
  remains true, and E04's `BluetoothPermissions.kt` still branches on
  `SDK_INT` and never requests `ACCESS_FINE_LOCATION` for a scan on API 31+.
- The permission merely *existing* on API 31+ does not change what a
  Bluetooth Classic discovery requests or asserts.

None of that is a substitute for manual steps 4/5. It is a reason to
describe the risk as **low and unmeasured**, which is the honest wording.

## Fix direction
Replace the final sentence of the comment block with a forward-looking one
that matches §9 — e.g. *"NOT yet re-verified on hardware: manual steps 4/5
(task file §8) were not performed (no device available); see `E09-T05.md`
§9 Deviations item 1. Static checks only, listed above. Whoever runs the
🧍 `verified` gate must run them first."* One line. No XML element, attribute
or permission changes.

## Regression test (write it first)
None is possible or appropriate — this is a comment, and no test can assert
prose is true. This is the "where no test could ever fail for the claim"
case in `skills/review` §2: the evidence is the diff itself plus
`E09-T05.md` §9, and the reviewer re-reads both. Stated rather than a
token test invented to fill the row.

## What this fix does NOT do
- Does **not** change any `<uses-permission>` element, attribute, or
  `maxSdkVersion`/`usesPermissionFlags` value. Comment text only — the diff
  must contain no non-comment line.
- Does **not** perform, simulate, or claim to substitute for manual steps
  4/5. Those stay open and human-owned (see the epic's §Bug sweep merge-gate
  condition).
- Does **not** tick `E09-T05`'s two unticked §7 boxes or its unticked DoD
  box. They stay unticked until real hardware says otherwise.
- Does **not** touch `pubspec.yaml`, `geolocator`'s version pin,
  `platform_location_source.dart`, or any Kotlin/Bluetooth source.
- Does **not** add iOS configuration (still out of scope, `OQ-E09-T05-1`).
