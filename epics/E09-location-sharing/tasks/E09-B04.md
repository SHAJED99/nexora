# E09-B04 · the epic's own status artefacts still say nothing has started

## The defect

At `epic_09`@`cd643f0` — five tasks merged, 895/895 tests green —
`epics/E09-location-sharing/tracker.md` opens with:

> **Status:** **sharded 2026-09-04 — 5 tasks, awaiting the 🧍
> `analyze_report` gate before any dispatch.** … **Started:** — ·
> **Completed:** — · **Progress:** 0/5

Its task table lists `E09-T01`–`T04` as `todo` and `E09-T05` as **`blocked`**.
Its §Event log's last entry is the sharding pass. `epic.md`'s §Tasks table
has the same five `todo` rows (T05's reading `todo (unblocked 2026-09-04…)`).

Meanwhile `epic.md`'s §ANALYZE REPORT records the `analyze_report` gate as
**✅ cleared**, and every task file records `status: done`, a review
outcome, and a merge. The two halves of the epic's own bookkeeping
contradict each other.

Compare `epics/E08-local-storage/tracker.md`, which carries per-task
`done · builder (sonnet) → reviewer (opus) · APPROVE · squash-merged
<hash> (PR #nn)` rows, real `Started:`/`Completed:` dates, a running
progress count, and an event-log entry per landing.

## Repro
1. `git checkout epic_09` at `cd643f0`.
2. Open `epics/E09-location-sharing/tracker.md`. Read the Status block and
   the task table.
3. Run `make next`, or ask "what is left to do in E09?".

## Expected
Rule 7 and the tracker discipline E07/E08 both follow: the tracker is the
artefact the human reads at the merge gate and the orchestrator reads when
dispatching. It must state what actually happened — five merged tasks, their
reviewers, their PRs, their merge hashes.

## Actual
It states that nothing has been dispatched and that T05 is blocked on two
unanswered rule-3 questions — both of which were answered on 2026-09-04 and
are recorded as 🟢 in `E09-T05.md`. A human clearing the epic→`development`
gate on this document alone would conclude the epic had not started.

## Severity
**S3** — no product code is affected and the ground truth is fully
recoverable from the git log and the five task files, so there is a
workaround. Not S4: this is the document the 🧍 human merge gate is read
from, and it is wrong in the direction that understates completion — which
in a harness whose scheduler reads these files is a dispatch hazard, not a
cosmetic one.

## Fix direction
Bring both files up to E08's closure shape: task rows carrying
`done · <builder> → <reviewer> · <outcome> · squash-merged <hash> (PR #nn)`,
real `Started:`/`Completed:`/`Progress:` values, an event-log entry per
landing, and the §Bug sweep section this sweep produces.

## Regression test (write it first)
None possible — these are prose artefacts. The systemic answer is not a test
but a **process lesson**, and it belongs in `skills/retro`: E09 is the first
epic in this project whose tracker went un-stamped across every task, and
the reason is visible in the git log — each merge commit *did* carry a
`docs(E09): T0n merged` message, so the stamping habit fired on the commit
message and stopped there. Recommend a retro entry (`L-process-*`) and, if
it recurs, a `make health` check that flags an epic whose task files say
`done` while its tracker says `todo`. Recorded here rather than invented as
a token test row.

## Resolution
Fixed as part of the E09 bug sweep commit itself (the sweep had to rewrite
both files anyway to record its own findings — see `skills/bug-sweep` step
2). Filed rather than silently corrected so the miss has an id, a severity
and a retro hook instead of disappearing into the diff that repaired it.

## What this fix does NOT do
- Does **not** touch any file under `lib/`, `test/`, `android/` or
  `pubspec.*`. Documentation only.
- Does **not** alter any task file's `status:`, `reviewed_by:`,
  `review_outcome:` or Run log — those are already correct and are the
  source of truth this fix copies *from*, not to.
- Does **not** tick `E09-T05`'s unticked on-device boxes, or change any
  `verified` state. The human owns those.
- Does **not** re-open, re-answer or re-status any Open Question.
- Does **not** update `epics/E06-personal-chat/epic.md:110`'s `E06-T18` row
  (still "needs E09's permission model existing", now satisfied) — that is
  E06's file and is recorded instead as a carried-forward observation in
  the tracker's §Bug sweep, with a named owner.
