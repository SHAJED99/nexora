# E09-B02 · a blocked peer's coordinates stay on disk forever

## The defect

`location_fixes` has exactly one delete path in the whole codebase:

```dart
// lib/features/location/domain/location_share_service.dart:364-372
final visibility = await _evaluateVisibility(peerDeviceId);
if (!visibility.isVisible) {
  await _fixes.deleteFix(peerDeviceId);
  return;
}
```

That path is inside `handleWireFrame` — it runs **only when a new location
frame arrives from that peer**. `EARS-LOC-10` is satisfied exactly as
written, and `test_EARS_LOC_10_receive_when_policy_fails_deletes_existing_fix`
proves it.

But the trigger is backwards for the case that matters. The user blocks a
peer *because they want that peer gone*; a blocked peer is precisely the one
who will never send another frame. So the fix that was stored while the
relationship was trusted stays in `location_fixes` — a real latitude and
longitude for a real person — until the app is uninstalled.

Three separate things then fail to catch it:
1. **Nothing hooks the relationship transition.** `deleteFix` has one caller
   (grep: `lib/features/location/domain/location_share_service.dart:370`).
   Blocking, unfriending, and `trusted → unknown` all leave the row.
2. **`E09-T04` §4 assigns the cleanup to E08** — "Retention of these rows is
   `E08`'s policy surface, not this task's." E08 has no location kind
   (`lib/core/storage/storage_item.dart:23-31`) and its executor is scoped to
   `{message}` (`storage_manager.dart:150`). The obligation has no owner; it
   only *looks* like it has one, which is worse.
3. **The row is in plaintext.** E03's retro §Open follow-ups item 4 (carried
   into this epic's ANALYZE REPORT, inherited obligation **#6**) already
   records that the Drift file has no at-rest encryption, and that row
   explicitly says E09 "widens the blast radius, because `location_fixes`
   puts peers' coordinates in that same unencrypted file." This defect is
   that widening left permanently open.

## Repro
1. In-memory `AppDatabase`. `relationships.upsert('peer-1', trusted)`.
2. `fixes.upsertFix(peerDeviceId: 'peer-1', latitude: 12.0, longitude: 34.0,
   capturedAtMs: now, receivedAtMs: now)` — or receive a real frame while the
   policy holds, which is the production path.
3. `relationships.upsert('peer-1', RelationshipState.blocked)` — the user
   blocks the peer.
4. `await fixes.readFix('peer-1')`.

## Expected
`FR-LOC-004` / epic **EARS-LOC-5**: "SHALL NOT let a blocked peer read or
write location state in either direction, and SHALL NOT accumulate a location
history." A blocked relationship holding a stored position on disk is
location state surviving the block. Step 4 must return `null`.

## Actual
Reviewer's own probe (`test/sweep_probe_test.dart`, scratch, not committed):

```
PROBE stored fix after block: LocationFixRow(peerDeviceId: peer-1,
  latitude: 12.0, longitude: 34.0, accuracyM: null,
  capturedAt: 1767268800000, receivedAt: 1767268800000)

Expected: null
  Actual: LocationFixRow:<...>
```

## Severity
**S2** — a privacy control the user explicitly exercised does not take
effect on stored data, and the data is a person's physical position sitting
in an unencrypted SQLite file. No workaround exists in the app: there is no
UI, no API and no scheduled pass that removes the row. Not S1: nothing is
transmitted, nothing is lost, and every *read* path (`LocationReadModel.read`,
`LocationShareService.share`, `handleWireFrame`) does correctly gate on the
live policy, so the stale row is not *displayed* — it is merely retained.

**Reachability, stated plainly for the 🧍 `bug_priorities` gate:** reachable
today in principle (the block path is E02's, shipped), but only after a real
fix has been received, which needs `E09-T05`'s on-device acquisition on a
peer device. No user of the current build has stored a fix. That is priority
information; the severity of the path is unchanged.

## Fix direction
Delete the fix when the relationship stops permitting, not when the next
frame happens to arrive. Two honest shapes:
- **(a)** Have `RelationshipRepository.upsert` (or the block use case) notify
  a location-side hook. Correct trigger, but it puts an E09 concern into
  **E02's file** and inverts the dependency — E02 must not learn about E09.
- **(b)** Give `LocationShareService` (or a small `LocationPrivacySweeper`)
  a `pruneFixesForNonVisiblePeers()` that re-evaluates
  `LocationVisibilityPolicy` for every row in `location_fixes` and deletes
  the ones that no longer pass, and call it from the composition root's
  existing startup path plus wherever the relationship stream (see
  **`E09-B01`**) fires. Keeps the fence inside `lib/features/location/`,
  reuses the policy rather than re-deriving a second block rule, and is
  bounded by the peer count (the same bound `readAllPeerEnabled` already
  relies on).

**(b) is advisory.** Whichever is chosen, **correct `E09-T04` §4's sentence**
— "Retention of these rows is `E08`'s policy surface" is not true and must
not be left in a scope fence for a future task to trust.

## Regression test (write it first)
`test_EARS_LOC_5_blocking_a_peer_deletes_their_stored_fix` — the repro above,
asserting `readFix('peer-1')` is `null` after the block, with **no inbound
frame** in the test at all (that absence is the point; a test that sends a
frame would pass on today's code and prove nothing). It must fail on today's
code with the exact `Actual: LocationFixRow` signature above. Add the
mirrored `trusted → unknown` and `global sharing turned off` cases.

## What this fix does NOT do
- Does **not** change `watch()`'s subscription set — that is **`E09-B01`**,
  a different defect with a different fix site and its own regression test.
- Does **not** add a `StorageItemKind.locationFix`, extend E08's inventory,
  or widen `StorageManager.runPass`'s `allowedKinds`. E08 is closed; making
  location an E08-managed retention class is new scope through
  `skills/change-impact`, and it is the wrong instrument anyway — this is a
  permission consequence, not a disk-space policy.
- Does **not** delete *stale* fixes. `E09-T04` §4's other clause stands:
  a stale fix stays stored and is reported as `lastKnown`, because deleting
  it would lose the very fallback `FR-LOC-005` permits. Only fixes whose
  **policy** no longer holds are removed.
- Does **not** add at-rest encryption to the Drift file — that is E03's
  still-unowned carry-forward (inherited obligation #6), a `spec/`-level
  rule-3 gap, and no E09 task can close it.
- Does **not** change the schema, the migration, the wire codec, or
  `EARS-LOC-10`'s existing receive-side delete.
- Does **not** touch `lib/features/trust/` if shape (b) is taken.
