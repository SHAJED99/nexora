# E09-T03 · Encrypted location share — control kind 7

## 1. Goal
Move a location fix from one device to another **encrypted end to end**, with
`FR-LOC-003`'s four-condition gate enforced independently on the send side and
the receive side — so neither an unauthorized sender nor a forged mesh frame
can put a peer's position on this device.

## 2. Business logic
- **`FR-LOC-004`: "location information shall be encrypted."** A location share
  is never sent as a cleartext control body. It goes through the **pairwise
  Double Ratchet session** (`CryptoService.encrypt`, ADR-0003), nested inside a
  `PayloadType.control` frame by `encodeCiphertextControlBody` — the exact
  discipline `GroupControlFrame` (E07-T03) and `CallSignaling` (E07-T09)
  already follow, and for the same stated reason: `RelayPacketFrame.source` is
  a field any mesh node can set to anything (E06-B04), so it is never evidence
  of who sent a frame. **The claimed sender is whichever Signal session
  decrypted the body, never `frame.source`.**
- **The gate is enforced twice, deliberately.**
  - *Send side*: `E09-T02`'s `LocationVisibilityPolicy` must return visible for
    the recipient, or nothing is transmitted. A share that should not be
    visible is not one we encrypt and hand to the mesh.
  - *Receive side*: the same policy is evaluated again for the *sender* before
    the fix is stored. `FR-LOC-004`'s "blocked users shall not be able to
    access each other's location" is a two-way statement, and a peer we have
    blocked must not be able to write a row into our database by sending us
    one. A receive path that trusts the sender's own gate has no gate.
- **`FR-LOC-003`'s conditions are evaluated at the moment of the operation**,
  not cached. A peer blocked one second ago must not have a fix stored one
  second later.
- **Storage is replace-only.** The receive path upserts on
  `location_fixes.peer_device_id` (E09-T01's PK), so accepting a fix can never
  accumulate history (`FR-LOC-004`). There is no append path to write.
- **`captured_at` comes from the sender's frame; `received_at` from this
  device's clock.** They are stored separately and neither is derived from the
  other (E09-T01 §5) — `E09-T04` needs both to discharge `FR-LOC-005`.
- **A fix whose `captured_at` is in the future is clamped-and-flagged, never
  trusted.** A sender with a skewed clock would otherwise make a stale fix look
  permanently fresh, defeating `FR-LOC-005` from the wire. Reject the frame
  rather than store a future timestamp.
- **Wire tags are explicit, never enum indexes** — the rule
  `PayloadType.tag`, `GroupControlFrame`'s `_kindTags` and `CallSignaling`'s
  own map all follow, so reordering a Dart enum declaration can never change
  the wire format.
- **Decrypt failures are caught as `CryptoDecryptFailure`** (E03-B03's
  app-owned taxonomy, resolved under E06-T02), never as `libsignal` exception
  types. An undecryptable location frame is dropped silently — it is not a
  user-facing error, and surfacing it would leak that a peer attempted a share.

## 3. What this task does
- Creates `lib/core/messaging/location_share.dart`: `kControlKindLocationShare
  = 7` (the next unused value after `kControlKindGroupMessage == 6`),
  `LocationShareFrame`, its `serialize()`/`deserialize()`, and an explicit
  `_kindTags` map for its own frame-kind byte.
- Creates `LocationSource` — the abstract port for "get this device's current
  position". **This task defines the port and uses it; it does not implement a
  real one** (see §4). Its only concrete implementation in this task is the
  test fake.
- Creates `LocationFixRepository` — the sole owner of `location_fixes`.
- Creates `LocationShareService` with a gated `share(peerDeviceId)` send path
  and a gated `handleWireFrame(frame)` receive handler.
- Registers the handler on
  `stack.inbound.registerControlHandler(kControlKindLocationShare, ...)` in
  `MessagingStack`'s **constructor body** (the established call site — not
  `create()`, not the initializer list, per that file's own header note about
  the `LateInitializationError` hazard), and adds
  `late final LocationShareService locationShareService` to the stack.

## 4. What this task does NOT do  ← the scope fence
- **Does not implement a real device location source.** No `geolocator`, no
  `location`, no platform channel, no `AndroidManifest.xml` change. Acquiring a
  real fix needs a new dependency and a new runtime permission — both rule-3
  human calls — and both belong to `E09-T05`. This task defines
  `LocationSource` and injects it; production wiring of a real implementation
  is `E09-T05`'s own contract, stated there.
- **Does not add a `PayloadType` enum value.** `PayloadType` has been frozen at
  three since E06-T02; every new sub-protocol takes a `controlKind` byte under
  `PayloadType.control`. Adding a fourth payload type would break every peer.
- **Does not write `RelayDeliveryState.failed`.** ⚠️ E04-B02's standing
  advisory (E04 retro §Open follow-ups): `failed` is declared, assigned
  nowhere, and **excluded from `reclaimPayloads()`'s reclaim set** — whichever
  task first writes it inherits exactly the retention defect B02 closed.
  Widening the terminal-state set is a rule-3 human call, so this task uses the
  existing enqueue-and-forget path unchanged and does not introduce the first
  `failed` writer. See `OQ-E09-T03-2`.
- **Does not decide staleness, or render anything.** `FR-LOC-005`'s
  live-vs-last-known reading is `E09-T04`'s; the pixels are `E06-T18`'s against
  `design/screens/chat-location.md`.
- **Does not build a settings surface or a toggle.** No design contract exists
  (GAP-005 🟡 proposed).
- **Does not modify `InboundPipeline`, `RelayPacketFrame`, `CiphertextCodec`,
  `PayloadType`, `RelayEngine` or `RoutingEngine`.** It uses their existing
  seams. If a seam looks insufficient, that is an Open Question, not an edit.
- **Does not send location to Firebase, or add any Firebase path.** `E11`'s
  `EARS-FB-1` and `FR-LOC-004` both forbid Firebase becoming a location-history
  store; an E09 task is not the place that gets revisited.
- **Does not log a coordinate, an accuracy, a peer device id, or a sharing
  state** — `E13`'s `EARS-DIAG-1`. Error paths log a reason code at most.
- Does not implement periodic/continuous sharing, a share duration, or a
  revoke message. One share = one frame, explicitly (`chat-location.md`: "live
  vs static, update frequency and share duration are E09's" — and this task
  answers *static, one shot*; anything more is new scope through
  `skills/change-impact`).

## 5. Contract

### Wire format — `LocationShareFrame`
Carried as the body of a `PayloadType.control` `RelayPacketFrame` whose first
byte is `kControlKindLocationShare` (`7`), and whose remainder is
`encodeCiphertextControlBody(ciphertext)` where `ciphertext` is the
`CryptoService.encrypt` output over `LocationShareFrame.serialize()`.

| field | wire type | notes |
|---|---|---|
| `version` | uint8 | `locationShareFrameVersion = 1`; a mismatch throws `FormatException` |
| `kind` | uint8 | explicit tag from `_kindTags`, never an enum index. `1 = share` |
| `latitudeE7` | int32 (big-endian) | decimal degrees × 1e7 — an integer wire type so no float encoding is negotiated. Valid range ±900 000 000 |
| `longitudeE7` | int32 (big-endian) | as above. Valid range ±1 800 000 000 |
| `accuracyMmm` | uint32 (big-endian) | accuracy in millimetres; `0xFFFFFFFF` is the explicit "not reported" sentinel, decoded to `null` — never `0` |
| `capturedAtMs` | uint64 (big-endian) | the **sender's** measurement time |

Same length-prefix, big-endian, exact-length-reaffirmation discipline as
`MessageEnvelope.deserialize` / `RelayPacketFrame.deserialize`. `deserialize`
throws `FormatException` on: a short buffer, a wrong version, an unknown kind
tag, an out-of-range coordinate, or trailing bytes.

> `E7` integer coordinates, not doubles, on purpose: two devices must decode
> byte-identical positions, and this is the same "explicit tag, no heuristic"
> posture `CiphertextCodec` and `RelayPacketFrame` already hold.

### Functions
`location_source.dart` declares **both** the port and the value it returns —
they have one owner and one file:

  final double longitude;

}

### `share()` — the send sequence, in order
1. `relationships.get(peerDeviceId)` → local `RelationshipState`
   (`unknown` if absent).
2. `settings.readGlobalEnabled()` and `settings.readPeerEnabled(peer)`.
3. `LocationVisibilityPolicy.evaluate(...)`. **Not visible → return
   `blockedByPolicy(reason)` and stop. Nothing is acquired, encrypted or
   sent.** In particular the device's position is not even read — a refused
   share must not turn on the GPS.
4. `locationSource.currentFix()` → `null` ⇒ return `noFix`.
5. Build + `serialize()` the `LocationShareFrame`.
6. `stack.prekeyExchange.ensureSession(peer, timeout: ...)`.
7. `stack.cryptoService.encrypt(SignalProtocolAddress(peer, 1), plaintext)`.
8. `encodeCiphertextControlBody(ciphertext)`, prepend
   `kControlKindLocationShare`.
9. Wrap in `RelayPacketFrame(payloadType: PayloadType.control, ...)` with
   `priority: RelayPriority.interactive` and a bounded TTL.
10. `stack.routingEngine.computeRoute(peer, TrafficProfile.interactive)` —
    multi-hop ⇒ `stack.relayEngine.enqueue(...)`, direct ⇒
    `stack.transport.send(...)`. This is `call_signaling.dart`'s `_sendFrame`
    sequence; follow it rather than inventing a variant.

### `handleWireFrame()` — the receive sequence, in order
1. `decodeCiphertextControlBody(frame.payload)`.
2. `stack.cryptoService.decrypt(SignalProtocolAddress(frame.source, 1), ct)`
   — catching `CryptoDecryptFailure`; on failure, **drop and return**.
   The peer identity used from here on is the address whose session
   decrypted, never `frame.source` as a claim.
3. `LocationShareFrame.deserialize(plaintext)` — `FormatException` ⇒ drop.
4. `capturedAtMs > clock().millisecondsSinceEpoch` (allowing no skew grace)
   ⇒ **drop**; a future-dated fix is never stored (§2).
5. Re-evaluate `LocationVisibilityPolicy` for that peer. **Not visible ⇒ drop,
   and additionally `fixes.deleteFix(peer)`** — if the peer is now blocked or
   sharing is off, any previously stored fix must not survive.
6. `fixes.upsertFix(...)` with `receivedAtMs = clock()`.

## 6. Risks
- **Control kind 7 must not collide.** 1–6 are taken (`prekey_exchange`,
  `delivery_ack`, `group_control`, `group_key_distribution`, `call_signaling`,
  `group_message`), and `inbound_pipeline.dart:67-72` documents a 5→6
  renumbering that already happened once. `registerControlHandler` throws
  `StateError` on a duplicate — good, but only at runtime. Grep for
  `kControlKind` before choosing.
- **Registering in the wrong place.** `MessagingStack`'s initializer list
  cannot reference `this`; the constructor *body* is where every other handler
  registers. Registering in `create()` instead would run it after
  `InboundPipeline` may already have dispatched.
- **`cryptoService.encrypt` throws `StateError` when no session exists** — it
  never auto-establishes. `ensureSession` first, or every first share to a new
  peer fails.
- **Trusting `frame.source`** is the single highest-severity mistake available
  here (E06-B04). It is a mesh-settable field. The session identity is the
  only authenticated one.
- **Evaluating the gate once and reusing it across both paths** would look
  like a tidy refactor and would silently make the receive side trust the send
  side. Two evaluations, on purpose.
- The share path acquires a position at step 4 and *only* at step 4. Hoisting
  `currentFix()` above the policy check (a natural "fetch everything first"
  instinct) turns a refused share into a GPS activation, which is exactly the
  behaviour `FR-LOC-003` exists to prevent.
- `messaging_stack_test.dart` constructs two stacks in one process; the new
  service must not assume `CryptoService.instance` — take it from the stack,
  which already supports the `cryptoService` override for that reason.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-LOC-8**: WHEN a location share is transmitted, the system SHALL
  encrypt it through the pairwise Signal session before it reaches any
  transport, and SHALL NOT place a coordinate in any cleartext frame field.
  (FR-LOC-004)
- **EARS-LOC-9**: WHEN `share()` is called for a peer whose visibility policy
  does not hold, the system SHALL transmit nothing AND SHALL NOT read the
  device's position. (FR-LOC-003)
- **EARS-LOC-10**: WHEN a location frame is received from a peer whose
  visibility policy does not hold, the system SHALL NOT store the fix AND
  SHALL delete any fix previously stored for that peer. (FR-LOC-003,
  FR-LOC-004)
- **EARS-LOC-11**: WHEN a second location frame is received from a peer that
  already has a stored fix, the system SHALL replace it, so at most one fix per
  peer is ever persisted. (FR-LOC-004)
- **EARS-LOC-12**: IF a received location frame cannot be decrypted, is
  malformed, or reports a capture time in the future, THEN the system SHALL
  drop it without storing anything and without surfacing an error.
  (FR-LOC-004)

   toggles are on and the relationship is trusted → B stores exactly one fix.
