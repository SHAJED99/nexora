# E09-T01 · Location schema migration v15

> 🧍 **This task fires the `db_schema_migration` human gate** (`harness.yaml`
> `human_gates`, rule 3). The tables and columns below are the contract the
> human approves; the builder does not add, rename or widen any of them.

## 1. Goal
Give every later E09 task one durable place to keep what the user *chose*
(global sharing on/off, and per-peer on/off) and the single most recent
location fix known for each peer — with "no permanent location history"
enforced by the schema's own shape rather than by every writer remembering.

## 2. Business logic
- **`FR-LOC-001`** needs a persisted app-wide on/off setting; **`FR-LOC-002`**
  needs an independent per-peer setting *in addition to* it (not instead of).
  Neither exists anywhere in the current schema.
- **`FR-LOC-004`**: *"Firebase shall not become a permanent location-history
  store."* The same reasoning applies locally, and it is enforced structurally
  here: `location_fixes` has `peer_device_id` as its **primary key**, so the
  table can physically hold **at most one row per peer** — the latest fix.
  There is no `location_fix_history` table and no append path. A later task
  cannot accidentally accumulate history, because the schema will not store it.
- **`FR-LOC-005`** needs a *captured-at* timestamp that is distinguishable from
  a *received-at* timestamp — staleness is a property of when the sender
  measured the position, not of when this device happened to receive the
  packet. Both columns exist for that reason; `E09-T04` is the reader that
  discharges the requirement.
- **Enums are stored as `.name` strings**, never integer indexes
  (`docs/conventions.md` "Enums") — the same rule `messages.deliveryState`,
  `relay_packets.deliveryState` and `storage_policy_settings.mode` follow.
- **Additive only** (`docs/conventions.md` "Schema migrations"): this step
  creates three tables and touches no existing table's DDL.
- **Atomic.** `database.dart`'s `onUpgrade` bumps `user_version` only after
  the callback returns; the `from < 15` step joins that existing wrapping and
  additionally wraps its own default-row insert in `m.database.transaction`,
  the precedent `E08-T01`'s `from < 14` step set for a step that inserts.
- **`location_settings` is a single-row table** (`id` always `1`), the same
  shape and for the same reason as `storage_policy_settings`: "exactly one
  global setting exists" becomes a schema invariant rather than a thing every
  reader must cope with.
- **The default is OFF.** The migration inserts `global_enabled = false`.
  `FR-LOC-003` makes location visibility conditional on four things all
  holding; a schema whose default is `true` would ship every existing
  installation into the permissive state on upgrade. Absent evidence that a
  user opted in, the honest default for a privacy control is off, and it is the
  security-restrictive one (`FR-MSG-007`'s posture).
- **An absent `location_peer_settings` row means "not enabled"**, never
  "enabled" and never "unknown". `FR-LOC-002` is an additional permission, and
  a permission nobody granted is not granted. No backfill of any kind.

## 3. What this task does
- Creates `lib/core/persistence/location_tables.dart` with three Drift tables:
  `LocationSettings`, `LocationPeerSettings`, `LocationFixes`.
- Registers them on `AppDatabase`, bumps `schemaVersion` 14 → 15, and adds the
  `from < 15` step to the existing `onUpgrade` chain.
- Inserts the single default `location_settings` row (`id=1`,
  `global_enabled=false`) on **both** `onCreate` and the `from < 15` upgrade
  path.
- Regenerates `database.g.dart` (`dart run build_runner build`).
- Extends `test/core/persistence/database_migration_test.dart` with a
  v14 → v15 additive-upgrade test in the exact shape of
  `test_EARS_STORE_3_v13_upgrades_to_v14_additively` — asserting the added
  table set and index set are **exactly** the expected ones (set equality, not
  mere existence) and every pre-existing table's `sqlite_master` DDL is
  byte-identical pre- and post-migration.

## 4. What this task does NOT do  ← the scope fence
- **Does not evaluate any permission.** No four-condition gate, no
  `isBlocked` call, no relationship lookup. `FR-LOC-003` is `E09-T02`'s
  entirely; a table is not a policy.
- **Does not encrypt, decrypt, send or receive anything.** No control-kind
  byte, no codec, no `MessagingStack` change. That is `E09-T03`.
- **Does not add a location-history table, an append-only fix log, a
  `location_fix_events` table, or a second row per peer under any name.**
  If the implementer finds themselves wanting one, that is `FR-LOC-004`
  pushing back and the answer is an Open Question, not a table.
- **Does not decide a staleness threshold** (how old is "stale"). That is a
  reader-side judgement `E09-T04` owns, and putting it in a column here would
  freeze it into the schema.
- **Does not touch `messages`, `delivery_states`, `relay_packets`, `routes`,
  `sync_cursors`, `relationships`, `storage_*` or any group/crypto table** —
  not a column, not an index, not a comment.
- **Does not add a dependency.** No location plugin, no geolocation package.
  Acquiring a real device fix is `E09-T05` and is gated on a rule-3 human
  decision; nothing in this task needs it.
- **Does not add a Firebase sync path for any of these tables.** `E11` owns
  Firebase, and `FR-LOC-004` constrains what may ever go there — an E09 schema
  task is not where that gets settled.
- Does not backfill `location_peer_settings` from `relationships`. An absent
  row is the honest reading (§2) and the one `E09-T02` is built against.

## 5. Contract

### Data
Migration step `from < 15` — three new tables, no changes to existing ones.

**`location_settings`** — `FR-LOC-001`'s global switch.

| column | type | null | notes |
|---|---|---|---|
| `id` | INTEGER | no | PK, always `1` — single-row table |
| `global_enabled` | BOOLEAN | no | default `false`; the migration inserts the row with `false` (§2) |
| `updated_at` | INTEGER | no | epoch-ms |

**`location_peer_settings`** — `FR-LOC-002`'s per-user switch.

| column | type | null | notes |
|---|---|---|---|
| `peer_device_id` | TEXT | no | PK — the same device-id string `relationships.deviceId` uses |
| `enabled` | BOOLEAN | no | default `false` |
| `updated_at` | INTEGER | no | epoch-ms |

No row for a peer means **not enabled** (§2). There is deliberately no
`unknown`/tri-state column.

**`location_fixes`** — the single latest known fix per peer.

| column | type | null | notes |
|---|---|---|---|
| `peer_device_id` | TEXT | no | **PK — this is the no-history invariant.** One row per peer, ever |
| `latitude` | REAL | no | decimal degrees, WGS84 |
| `longitude` | REAL | no | decimal degrees, WGS84 |
| `accuracy_m` | REAL | yes | metres; NULL = the sender reported none, never 0 |
| `captured_at` | INTEGER | no | epoch-ms **as reported by the sender** — what `FR-LOC-005`'s staleness is measured against |
| `received_at` | INTEGER | no | epoch-ms, this device's clock, when the fix was accepted |

Index `idx_location_fixes_captured_at` on `(captured_at)` — `E09-T04` reads
by freshness.

> `captured_at` and `received_at` are both present on purpose and are not
> interchangeable. A fix that arrives now but was measured twenty minutes ago
> is stale (`FR-LOC-005`), and a schema with only one timestamp cannot say so.

## 6. Risks
- `database.g.dart` is generated. Hand-editing it is the fastest route to a
  broken build that looks like a merge conflict; regenerate.
- A fresh install runs `onCreate`, not `onUpgrade`. The default
  `location_settings` row must exist on **both** paths, and a test must prove
  the fresh-install path too — this is exactly the case `E08-T01` §6 called
  out and it applies identically here.
- Drift's `createTable()` on upgrade does not necessarily create the same
  index set as `createAll()` on a fresh install (`E05-T01`'s review finding,
  E05 retro). Assert the index exists on the **upgraded** path specifically,
  not only the created one.
- `BOOLEAN` in SQLite is an INTEGER. A test asserting `global_enabled == false`
  must not accidentally pass because it compared against `0` in a context
  where Drift already mapped it — assert through the generated Dart type.
- Copying `E08-T01`'s migration-test shape without keeping its **exact-set**
  assertion re-opens the advisory E08 closed. Set equality, not existence.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-LOC-6**: WHEN a device on schema v14 opens the database, the system
  SHALL upgrade it to v15 by creating exactly `location_settings`,
  `location_peer_settings` and `location_fixes` plus
  `idx_location_fixes_captured_at`, leaving every pre-existing table's DDL
  byte-identical. (FR-LOC-001, FR-LOC-002)
- **EARS-LOC-3** *(epic criterion, persistence half)*: WHEN the database is
  created or upgraded, the system SHALL ensure exactly one `location_settings`
  row exists with `global_enabled == false`. (FR-LOC-001)
- **EARS-LOC-5** *(epic criterion, no-history half — the encryption and
  blocked-access halves are `E09-T03`'s)*: WHEN a second location fix is stored
  for a peer that already has one, the system SHALL replace the existing row
  rather than add a row, so that at most one fix per peer is ever persisted.
  (FR-LOC-004)
