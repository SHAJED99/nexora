# E09-T02 · Location settings + the four-condition visibility policy

## 1. Goal
Make "may this peer's location be shown, and if not, why not?" a single
answerable question with one owner — the thing `E06-T18` (location-in-chat) is
explicitly waiting on, and the thing every other E09 task consults before it
sends, stores or displays anything.

## 2. Business logic
- **`FR-LOC-003` is the epic's headline requirement** and it is a conjunction
  of exactly four conditions, all of which must hold:
  1. **connected** — the relationship permits a connection, per E02's
     `isConnectionPermitted(local, remote)`.
  2. **authorized** — the peer is not blocked and its state is `trusted` or
     `allowed`. `unknown` is not authorized.
  3. **global-on** — `location_settings.global_enabled` (`FR-LOC-001`).
  4. **per-user-on** — `location_peer_settings[peer].enabled` (`FR-LOC-002`);
     an absent row is **not enabled** (E09-T01 §2).

  *"if any condition fails, location shall be unavailable"* — so the policy is
  a hard AND, evaluated with **no short-circuit shortcut that changes the
  reported reason**: the caller needs to know *which* condition failed, because
  the design contract renders "disabled picker row" and "location unavailable"
  differently (`design/screens/chat-location.md` states 1 and 5).
- **`FR-LOC-002` is additive, not a substitute.** Per-user ON with global OFF
  is OFF. This is `FR-MSG-007`'s `LOCATION-OFF > LOCATION-ON` precedence, and
  this task **reuses `ConflictResolver.resolveLocationSharing(a, b)`
  (`lib/features/messaging/domain/conflict_resolver.dart`, E05-T05) rather
  than re-deriving it.** That function has had no production caller since E05
  shipped; this task is its first, and that is deliberate — a second, private
  copy of a security precedence rule is how the two copies diverge.
- **`RelationshipState.blocked` is checked explicitly**, not merely inferred
  from `isConnectionPermitted` returning false, so that `blocked` produces its
  own distinguishable reason (`FR-LOC-004`: "blocked users shall not be able to
  access each other's location"). Two conditions can both be false; the
  reported reason must be the most security-restrictive one, ordered
  `blocked > notConnected > notAuthorized > globalOff > peerOff`.
- **The policy is a pure function over already-fetched inputs.** It performs no
  I/O itself. The repository fetches; the policy decides. That is what makes
  every one of `FR-LOC-003`'s failure combinations testable without a database,
  and it mirrors `ConflictResolver`'s own deliberately-pure shape.
- **`FR-TRUST-006`'s location-access control is a *different* setting** and is
  not implemented here (see §4). It has no design surface (GAP-005, 🟡
  proposed) and no persisted store; conflating it with `FR-LOC-001`'s global
  toggle would silently decide a question `OQ-E02-T03-1` is still holding open.

## 3. What this task does
- Creates `LocationSettingsRepository` — **the only file that reads or writes
  `location_settings` and `location_peer_settings`** — in the exact shape
  `lib/core/storage/storage_settings_repository.dart` established: an injected
  `AppDatabase`, a `read()` that is never null, a `watch()` that emits the
  current value immediately on listen, and writes that throw rather than
  coerce.
- Creates `location_visibility.dart`: `LocationVisibility` (the decision) and
  `LocationUnavailableReason` (the enum the UI renders from).
- Creates `LocationVisibilityPolicy.evaluate(...)` — the pure four-condition
  AND, delegating the global∧per-user combination to
  `ConflictResolver.resolveLocationSharing`.
- Tests every one of the four conditions failing independently, every reason's
  precedence when two fail at once, and the all-hold case.

## 4. What this task does NOT do  ← the scope fence
- **Does not build any UI, controller, binding or route.** No settings screen,
  no toggle widget, no `SettingsController` change. The Privacy & Security
  sub-screen has **no design contract** (GAP-005 is 🟡 *proposed*, not
  approved), so per rule 2 a location-toggle screen is not shardable and
  building one here would consume a gate that has not been cleared.
- **Does not implement `FR-TRUST-006`'s location-access control.** Different
  requirement, different (undesigned) surface, tracked as `OQ-E02-T03-1`. Do
  not add a column, a flag or a parameter for it "while we're here".
- **Does not re-derive the LOCATION-OFF precedence.** Call
  `ConflictResolver.resolveLocationSharing`. If it looks wrong, that is an
  Open Question against E05-T05, not a local reimplementation.
- **Does not activate `EvaluateConnectionRequestUseCase`'s inert
  `autoAcceptSpecific` / `requireAuthForUnknown` flags** (`OQ-E02-T01-2`,
  ⚪ deferred). Read relationship state through `RelationshipRepository`;
  do not change E02's use case.
- **Does not encrypt, send, receive or acquire anything.** No `CryptoService`,
  no `RelayEngine`, no `TransportService`, no platform location call. T03 and
  T05 own those.
- **Does not read or write `location_fixes`.** That table's owner is
  `E09-T03`'s `LocationFixRepository`. A settings repository that also serves
  fixes is two repositories wearing one name.
- **Does not decide staleness.** `E09-T04` owns `FR-LOC-005`.
- **Does not add a dependency**, a Firebase path, or a log line containing a
  device id, a coordinate, or a peer's sharing state (E13's EARS-DIAG-1:
  never log sensitive location data).
- Does not register anything in `lib/app/bindings.dart`. Wiring into the
  composition root happens once, in `E09-T03`, alongside the service that
  needs it.

    remoteState: "the peer's reported state for this device (FR-TRUST-005 is two-sided). Pass RelationshipState.unknown when the remote side has not been learned — unknown is not authorized, which is the security-restrictive reading"
    globalEnabled: "LocationSettingsRepository.readGlobalEnabled()"
    peerEnabled: "LocationSettingsRepository.readPeerEnabled(peer)"
  returns: "LocationVisibility — visible, or hidden with exactly one LocationUnavailableReason"
  purpose: "FR-LOC-003's four-condition AND, as one pure function with one owner"

### Data — the decision types
```dart
enum LocationUnavailableReason { blocked, notConnected, notAuthorized, globalOff, peerOff }

class LocationVisibility {
  final bool isVisible;
  final LocationUnavailableReason? reason;   // null iff isVisible
}
```

Reason precedence when more than one condition fails, most restrictive first —
this ordering is part of the contract, not an implementation detail:

`blocked` > `notConnected` > `notAuthorized` > `globalOff` > `peerOff`

> The reason is not decoration. `design/screens/chat-location.md` renders a
> *disabled picker row* (state 1) for a policy that says no up front, and a
> *`Location unavailable` card* (state 5) for a share that stopped being
> permitted. A boolean cannot tell those apart, and the UI task is forbidden
> from deciding it (`chat-location.md` §Scope fence).

## 6. Risks
- **`readPeerEnabled` returning `true` for an absent row is the whole bug.**
  Drift's `getSingleOrNull()` plus a careless `?? true`, or a `.first` on an
  empty list, and every peer becomes shareable by default. Test the
  no-row case explicitly, first.
- `watch()` built on `watchSingle()` throws if the row is missing;
  `E09-T01`'s migration guarantees it exists, but a test that constructs an
  empty in-memory database without running `onCreate` will not have it. Build
  the test database the way `storage_settings_repository_test.dart` does.
- `isConnectionPermitted(local, remote)` is two-sided by design (E02-T01's
  `FR-TRUST-005`). Passing the same state twice makes the test pass and the
  product wrong; the remote state must genuinely come from the caller.
- `ConflictResolver.resolveLocationSharing` is `a && b`. It is trivially
  reimplementable, which is exactly why the temptation to inline it is real —
  and why §4 forbids it.
- Reason precedence is easy to get right in the four single-failure tests and
  wrong in the combinations. Test at least `blocked + globalOff` and
  `notConnected + peerOff`.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-LOC-1**: WHEN evaluating whether a peer's location may be shown, the
  system SHALL report visible only when the relationship is connected AND the
  peer is authorized AND global sharing is enabled AND per-user sharing is
  enabled for that peer; IF any condition fails, THEN it SHALL report
  unavailable with the most security-restrictive failing reason.
  (FR-LOC-003, FR-LOC-001, FR-LOC-002)
- **EARS-LOC-4** *(epic criterion — FR-LOC-002 is additive, never a
  substitute)*: WHEN global sharing is off and per-user sharing is on for a
  peer, the system SHALL report unavailable — the more restrictive state wins,
  as resolved by `ConflictResolver.resolveLocationSharing`. (FR-MSG-007,
  FR-LOC-002)
- **EARS-LOC-7**: WHEN no `location_peer_settings` row exists for a peer, the
  system SHALL treat per-user sharing as disabled. (FR-LOC-002)

## Open Questions
- **OQ-E09-T02-1 — where does the *remote* relationship state come from?**
  `FR-TRUST-005`/`isConnectionPermitted` is two-sided, but this device only
  stores its own `RelationshipState` per peer (`relationships` has one `state`
  column). Nothing in E02–E08 exchanges the peer's view of *us*. This task
  therefore takes `remoteState` as a caller-supplied parameter and documents
  `unknown` as the safe default — but the caller (`E09-T03`) has nowhere
  truthful to get it either. Does E09 need a state-exchange step, or is
  single-sided evaluation accepted for v1 with the two-sided check deferred to
  whichever epic adds relationship-state sync (`FR-TRUST-007`, E11)?
  - **Status:** 🟡 open — **important, not blocking this task.** The parameter
    exists either way; only the caller's argument changes.
  - **Answer:** Single-sided evaluation accepted for v1 — `remoteState` stays
    a caller-supplied parameter defaulting to `unknown`. Two-sided
    relationship-state exchange (FR-TRUST-007) is deferred to E11, which
    already owns Firebase/metadata sync; do not build a state-exchange step
    here.
