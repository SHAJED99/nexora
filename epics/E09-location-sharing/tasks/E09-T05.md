> ✅ **Unblocked 2026-09-04.** `OQ-E09-T05-1` (dependency: `geolocator`) and
> `OQ-E09-T05-2` (manifest: unrestricted `ACCESS_FINE_LOCATION` for API 31+,
> `neverForLocation` unchanged on `BLUETOOTH_SCAN`) are both answered above.
> `status` moved `blocked` → `todo`.
>
> **This is also the task that closes E09's own wiring obligation.**
> `E09-T03` defines and injects the `LocationSource` port but implements no
> real one, so until this task lands, `LocationShareService.share()` returns
> `noFix` on every real device. That is stated here, in the owning task's
> contract, rather than only as prose in T03 — an unwired capability whose only
> record is a note in someone else's file is exactly the carrier that failed
> twice in E04→E05→E06 (`L-process-007`).

## 1. Goal
Give `LocationShareService` a real position to share: one concrete
`LocationSource` backed by the device's location provider, behind the runtime
permission it requires, constructed exactly once in the composition root.

## 2. Business logic
- **`E09-T03`'s `LocationSource` port is the whole interface.**
  `Future<LocationFix?> currentFix()` — `null` for every ordinary no-fix case
  (permission denied, provider disabled, timeout, no last-known position). It
  does not throw for those; a refused or unavailable fix is a normal outcome
  the send path already handles by returning `noFix`.
- **The permission is requested lazily, at the first `currentFix()` call that
  the policy has already approved** — never at app start. `E09-T03`'s send
  sequence evaluates `LocationVisibilityPolicy` *before* calling
  `currentFix()`, so the permission prompt can only ever appear for a share the
  user's own settings already permit. Prompting at launch would ask for
  location before the user has turned anything on, which contradicts
  `FR-LOC-001`'s default-off posture.
- **E04's Bluetooth manifest posture must survive.** ⚠️ Inherited from
  `E04-T03b` (`android/app/src/main/AndroidManifest.xml`):
  - `ACCESS_FINE_LOCATION` is currently declared with
    **`android:maxSdkVersion="30"`** — it exists only to make pre-Android-12
    Bluetooth *discovery* return results, and is deliberately absent on API 31+.
  - `BLUETOOTH_SCAN` carries **`android:usesPermissionFlags="neverForLocation"`**,
    which is precisely what lets API 31+ skip `ACCESS_FINE_LOCATION` entirely.
  E09 is the **first** feature in this app that genuinely needs the device's
  position, so the `maxSdkVersion="30"` cap must be lifted (or an unrestricted
  declaration added) for API 31+. Whether `neverForLocation` may remain on
  `BLUETOOTH_SCAN` afterwards — it is an assertion about the *Bluetooth scan*,
  not about the app, so it should still hold — is a claim that must be
  re-verified, not assumed, because getting it wrong either breaks E04's
  discovery on API 31+ or makes a false attestation to the platform.
- **A timeout is mandatory.** A location provider can wait indefinitely for a
  fix. `currentFix()` takes a bounded timeout (default **10 s**) and returns
  `null` on expiry, so a share attempt can never hang the caller.
- **Nothing is cached.** This source returns the device's current position (or
  the platform's own last-known, if that is the chosen strategy — see
  `OQ-E09-T05-3`); it does not keep a private cache. The only persisted
  location state in this app is `location_fixes`, one row per *peer*, owned by
  `E09-T03`.
- **Never log a coordinate** (E13 `EARS-DIAG-1`), including in a failure path,
  including at debug level.

## 3. What this task does
- Adds the chosen location dependency to `pubspec.yaml` (exact pinned version),
  **after** `OQ-E09-T05-1` is answered.
- Amends `android/app/src/main/AndroidManifest.xml` for the runtime location
  permission on all supported API levels, preserving E04's
  `neverForLocation` posture on `BLUETOOTH_SCAN` and re-verifying that
  Bluetooth discovery still works on both an API ≤30 and an API 31+ device.
- Creates `PlatformLocationSource implements LocationSource` — permission
  request, bounded-timeout acquisition, `null` on every no-fix path.
- Constructs it once in `MessagingStack` and passes it to the
  `LocationShareService` that `E09-T03` created there, replacing whatever
  no-op/absent source that task left in place. **After this task,
  `share()` returns `noFix` only when the device genuinely has no fix.**

## 4. What this task does NOT do  ← the scope fence
- **Does not change `LocationSource`'s signature.** If the real provider needs
  something the port cannot express, that is an Open Question against
  `E09-T03`'s contract, not a widening here.
- **Does not add background or continuous location.** No foreground service,
  no `ACCESS_BACKGROUND_LOCATION`, no periodic sampling. Keeping location
  working while backgrounded is `E10`'s stated scope (`E10` epic.md), and
  background location is a separate, heavier platform permission and store
  review — it is not smuggled in as part of "acquire a fix".
- **Does not touch the Pigeon transport contract, `TransportService`, or any
  Bluetooth code path.** The manifest is shared; the code is not. Verifying E04
  still works is a *check*, not a licence to edit it.
- **Does not add iOS configuration** unless `OQ-E09-T05-2`'s answer includes
  iOS — the repo's only platform manifest work to date (E04-T03b) is Android,
  and silently adding an `Info.plist` usage string commits to a platform nobody
  has scoped.
- **Does not build a permission-denied UI, a rationale dialog, or a settings
  deep-link.** Those are screens, and no design contract covers them
  (GAP-005 🟡 proposed). `currentFix()` returns `null`; the surface that must
  explain why is a later, contracted task.
- **Does not change `LocationVisibilityPolicy`, the wire format, the schema, or
  the read model.** T01–T04's files are not in this task's `files:`.
- **Does not cache a fix, write to `location_fixes`, or persist anything.**
- **Does not request the permission at app start**, in `AppBinding`, or in
  `MessagingStack.create()`. Lazy, at first approved use (§2).

## 5. Contract

### External services & flags
- **New dependency** — the package chosen by `OQ-E09-T05-1`, pinned to an
  exact version in `pubspec.yaml`. 🧍 **Rule 3 human gate.**
- **New runtime permission** — Android location, per `OQ-E09-T05-2`.
  🧍 **Rule 3 human gate** (it edits a manifest E04's transport depends on).
- **No env var, no secret, no network service.** Location acquisition is
  entirely on-device.
- **Failure behaviour:** every failure — permission denied, permission
  permanently denied, provider off, timeout, platform exception — resolves to
  `currentFix()` returning `null`. Nothing propagates as an exception to
  `LocationShareService`.

### Manifest contract (to be finalised by `OQ-E09-T05-2`)
The **current** state, which this task changes and must not regress:

```xml
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"
                 android:maxSdkVersion="30" />
<uses-permission android:name="android.permission.BLUETOOTH_SCAN"
                 android:usesPermissionFlags="neverForLocation" />
```

The change is confined to the location declaration. The `BLUETOOTH_SCAN`
element, including its `neverForLocation` flag, is not edited by this task.

### Functions
```yaml
- signature: "PlatformLocationSource({Duration timeout = const Duration(seconds: 10), <permission + provider seams injected for tests>})"
  params: { timeout: "bounded acquisition window; on expiry currentFix() returns null" }
  returns: "a LocationSource backed by the device provider"
  purpose: "the one concrete LocationSource in production"

- signature: "Future<LocationFix?> PlatformLocationSource.currentFix()"
  params: {}
  returns: >
    a LocationFix with latitude, longitude, optional accuracyM and capturedAt
    from the provider's own measurement time; null on permission denied,
    provider disabled, timeout, or any platform error. Never throws
  purpose: "FR-LOC-003's send path calls this only after the policy has approved the share"
```

> The platform seams (permission check/request, position fetch) are **injected
> behind narrow function types**, not called as static globals — otherwise this
> class is untestable without a device and the task ships with tests that
> assert nothing about its actual logic. That is the same reason
> `TransportService` takes a `BinaryMessenger?` (E04-T03a).

## 6. Risks
- **Regressing E04's Bluetooth discovery** is the highest-cost failure here and
  it will not show up in any Dart test — the suite has no radio. It needs a
  physical check on both an API ≤30 and an API 31+ device. E04's own retro
  already records that three MIUI install restrictions blocked its on-device
  verification; expect this to be awkward, and do not tick it untruthfully.
- Requesting the permission on a thread/at a moment where no `Activity` is
  attached fails silently on Android. The lazy-at-first-use design makes this
  more likely, not less — the call arrives from a service, not a widget.
- "Permission permanently denied" is a distinct state from "denied" on Android
  and re-prompting in that state is a no-op that looks like a hang. Both must
  resolve to `null` promptly.
- A provider's `capturedAt` may be the device's *boot-relative* time on some
  APIs. `E09-T03` drops future-dated fixes and `E09-T04` measures staleness
  against this value — a wrong epoch here corrupts `FR-LOC-005` end to end.
  Convert explicitly and test the conversion.
- Adding a package that transitively pulls in a Play-Services dependency
  changes the build's minimum requirements. That belongs in
  `OQ-E09-T05-1`'s comparison, not discovered at build time.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-LOC-15**: WHEN the visibility policy has approved a share and the
  device has a position, the system SHALL return a `LocationFix` whose
  `capturedAt` is the provider's measurement time in epoch milliseconds.
  (FR-LOC-003)
- **EARS-LOC-16**: IF location permission is denied, permanently denied, the
  provider is disabled, the acquisition times out, or the platform raises an
  error, THEN the system SHALL return `null` without throwing. (FR-LOC-003)
- **EARS-LOC-17**: WHEN no share has been approved by the visibility policy,
  the system SHALL NOT request the location permission and SHALL NOT read the
  device's position. (FR-LOC-001, FR-LOC-003)

### Manual — required, not optional
1. Fresh install, global toggle off → attempt a share → **no permission prompt
   appears**.
2. Turn both toggles on for a trusted peer → attempt a share → the prompt
   appears once, and a real fix is sent.
3. Deny the permission → share returns `noFix`, nothing is transmitted, no
   crash.
4. **E04 regression, API ≤30 device:** Bluetooth discovery still finds a peer.
5. **E04 regression, API 31+ device:** Bluetooth discovery still finds a peer.

## Open Questions
- **OQ-E09-T05-1 — which location package? 🧍 BLOCKING (rule 3, new
  dependency).** The app has no location capability and no geolocation package
  today. Options, honestly:
  - **`geolocator`** — the de-facto Flutter choice; handles permissions,
    last-known and current position, has a `getCurrentPosition(timeLimit:)`.
    Heaviest surface, and on Android it can pull Play Services depending on the
    settings used.
    *Advisory: this one*, because it is the only option whose permission +
    timeout + last-known behaviour is already the shape §5 needs, and it is the
    package the ecosystem has actually exercised.
  - **`location`** — smaller, stream-oriented; the one-shot case is less
    natural and its permission handling is thinner.
  - **A Pigeon channel of our own**, matching ADR-0004's transport precedent —
    no third-party dependency, full control, and consistent with how this repo
    already crosses to the platform. Cost: we write and maintain the Android
    (and later iOS) implementation, and E04's own retro shows on-device
    verification of native code is this project's most expensive step.
  Please pick one; the answer also settles whether iOS is in scope.
  - **Status:** 🟢 answered
  - **Answer:** **`geolocator`**, pinned to an exact version. It is the
    ecosystem's de-facto choice, its permission/timeout/last-known shape
    already matches this task's §5, and it saves maintaining a from-scratch
    native channel for a well-solved problem. iOS stays out of scope for this
    task (Android only, matching E04-T03b's precedent) — add it only when an
    iOS build is actually scoped.
  - **Answered by:** human (decision authority explicitly delegated to the
    agent for this session, 2026-09-04)
  - **Date:** 2026-09-04
- **OQ-E09-T05-2 — the manifest change. 🧍 BLOCKING (rule 3, and it edits a
  file E04's transport depends on).** `ACCESS_FINE_LOCATION` is capped at
  `maxSdkVersion="30"` and `BLUETOOTH_SCAN` asserts `neverForLocation`
  (E04-T03b). E09 needs a location permission on API 31+, which means lifting
  the cap. Two sub-questions:
  (a) **`ACCESS_FINE_LOCATION` or `ACCESS_COARSE_LOCATION`?** Fine gives a
  precise share; coarse is materially less invasive and may be enough for a
  "where is this contact" card. `spec/` does not say, and this is a privacy
  posture decision, not an engineering one. *Advisory: fine*, since a location
  share whose accuracy is a city block is arguably not the feature — but it is
  a genuine trade-off and yours.
  (b) **Does `neverForLocation` stay on `BLUETOOTH_SCAN`?** It should — it is
  an assertion about what the *Bluetooth scan* derives, and E09 derives
  location from the location provider, not from BLE. But it must be
  re-verified on a real API 31+ device (manual step 5), not assumed.
  - **Status:** 🟢 answered
  - **Answer:** (a) **`ACCESS_FINE_LOCATION`** — a location-sharing feature
    that only manages city-block accuracy isn't the feature; lift the
    `maxSdkVersion="30"` cap for API 31+ (add an unrestricted
    `ACCESS_FINE_LOCATION` declaration alongside, or in place of, the existing
    capped one — whichever shape `geolocator`'s own manifest merger expects is
    the builder's call within this fence). (b) **`neverForLocation` stays on
    `BLUETOOTH_SCAN`**, unchanged — it is an assertion about the Bluetooth
    scan, not the app, and must be re-verified (not assumed) on a real API
    ≤30 device and a real API 31+ device per manual steps 4/5.
  - **Answered by:** human (decision authority explicitly delegated to the
    agent for this session, 2026-09-04)
  - **Date:** 2026-09-04
- **OQ-E09-T05-3 — current position, or platform last-known?** Requesting a
  *fresh* fix costs seconds and battery; the platform's own last-known position
  is instant but may itself be stale — and `FR-LOC-005`'s staleness is measured

  labelled `Last known`, which is honest but may surprise the sender who just
  pressed "share". Advisory: request a current fix with the §5 timeout, and
  fall back to the platform last-known only if the timeout expires — the
  timestamp tells the truth either way.
  - **Status:** 🟢 answered
  - **Answer:** Approved — request a current fix under the §5 timeout,
    falling back to the platform's own last-known position only on timeout.
    The timestamp tells the truth either way.
