# E03-B01 · One-time prekey ids restart at 1 after the pool drains

## Severity: S2 (major function broken, no workaround)
Not S1 only because the defect is currently **latent**: E03-T02 §4 wires
`replenishOneTimePreKeys()` to no caller, and nothing yet consumes one-time
prekeys. **E03-T03 makes it live** — `SessionCipher.decryptPreKeyMessage`
removes the one-time prekey on use. Hence `blocks: [E03-T03]`.

Priority is the human's call (`bug_priorities` gate), not the reviewer's.

## Repro (exact, from a fresh store)
1. Fresh `AppDatabase.forTesting(NativeDatabase.memory())` +
   `DriftSignalProtocolStore` + `IdentityService`.
2. `await service.replenishOneTimePreKeys(minimum: 20, batch: 5)`
   → persists one-time prekeys with ids `[1, 2, 3, 4, 5]`.
3. Record the public key stored under id `1`.
4. Simulate peers consuming every prekey (what T03's
   `decryptPreKeyMessage` does): `for (id in [1..5]) store.removePreKey(id)`
   → pool is now empty.
5. `await service.replenishOneTimePreKeys(minimum: 20, batch: 5)`.
6. Read the ids and the public key now stored under id `1`.

### Expected (E03-T02 §6, the task's own binding risk note)
> "One-time prekey id allocation must never reuse an id still referenced by
> an in-flight (not-yet-consumed) bundle handed to a peer earlier — track
> the next-free id explicitly, don't reuse gaps left by consumed/removed
> prekeys."

New ids must be `[6, 7, 8, 9, 10]` — strictly above every id this device has
ever issued.

### Actual (verified by the reviewer, run 2026-08-27)
```
first batch ids:  [1, 2, 3, 4, 5]
second batch ids: [1, 2, 3, 4, 5]     <-- ids reissued
id 1 key changed: true                <-- with DIFFERENT key material
```

## Root cause
`lib/core/crypto/identity_service.dart:85-87`

```dart
final nextId = existingIds.isEmpty
    ? 1
    : existingIds.reduce((a, b) => a > b ? a : b) + 1;
```

The next-free id is derived from the **live rows only**. `max(existing) + 1`
is correct while at least one prekey survives (which is why
`test_EARS_SEC_3c_replenish_never_reuses_a_consumed_gap` passes — it removes
id 3 out of 1..5 and the max is still 5). But when the pool drains to empty,
`existingIds.isEmpty` is true and allocation **restarts at 1**, reissuing
every id the device already handed out to peers.

This is a **specification defect as much as a coding one**: E03-T02 §6
itself suggested the flawed algorithm verbatim ("e.g. `max(existing ids) + 1`").
The builder implemented the contract as written. The contract was wrong for
the drained-pool case, and no test in §8's plan covered it.

## Why it matters
X3DH addresses a one-time prekey **by id**. A peer holding a bundle that
names prekey id 1 sends a `PreKeySignalMessage` referencing id 1. This
device looks up id 1, finds a *different* private key than the one the peer
did DH against, and the X3DH shared secret does not match — the peer's
first message is permanently undecryptable, and the session fails to
establish. Silent, per-peer, and indistinguishable from a transport fault.

## Fix direction (not prescriptive — the implementer decides within it)
The next-free id must come from a **monotonic high-water mark that survives
row deletion and app restart**, not from `max(live rows)`. Options:

1. **Persist a high-water mark** (a `next_one_time_prekey_id` counter row).
   Correct across restarts. Requires a schema change — see the gate below.
2. **In-memory-only high-water mark** on the service instance.
   Insufficient on its own: it resets every app launch, which is exactly
   when this device would re-replenish a drained pool. Do NOT ship this as
   the whole fix.

Signal's own guidance is a monotonically increasing counter, never reset;
`generatePreKeys(start, count)` wraps at `Medium.MAX_VALUE`, so wrap-around
handling belongs in whatever counter is chosen.

## 🧍 Gate — rule 3
**Resolved 2026-08-27.** The human chose Option 1, dedicated table: a new
`crypto_counters` (or equivalently-named) single-row table holding
`next_one_time_prekey_id`, over adding a column to `signal_identity` — clean
separation between identity data and allocation state. E03-T01b already
merged, so this bug now owns the schema change directly (schema v5→v6,
additive, same `onUpgrade` pattern as T01/T01b) rather than depending on an
in-flight T01b.

### What this task does
- Add a `crypto_counters` table: singleton row (fixed id, same pattern as
  `signal_identity`), `next_one_time_prekey_id INTEGER NOT NULL DEFAULT 1`.
- `DriftSignalProtocolStore` (or a small new method on it) exposes
  `allocateOneTimePreKeyIds(int count) -> Future<List<int>>` — atomically
  reads the counter, returns `count` consecutive ids starting there, writes
  the counter forward by `count`. This must never go backward and must
  survive both consumption (`removePreKey`) and app restart.
- `IdentityService.replenishOneTimePreKeys()` calls this instead of
  deriving `nextId` from `existingIds`.
- Handle `Medium.MAX_VALUE` wrap-around per the Fix direction note above —
  at minimum, don't crash; wrapping back to a low value that could collide
  with an ancient still-live id is an acceptable known edge case for v1
  given one-time prekeys are expected to be consumed/replenished long
  before ~16M ids are issued — note this assumption in the Run log, don't
  build full wrap-safety unless it's cheap.

### What this task does NOT do
- Does NOT touch `signal_identity`, `signal_signed_prekeys`,
  `signal_sessions`, or `signal_trusted_identities` — only adds the one new
  counter table.
- Does NOT change `getLocalPreKeyBundle()`'s external contract — same
  return shape, only the id-allocation source underneath changes.

## Regression test (write it FIRST, must fail before the fix)

### Reviewer fixes applied (small, scoped, inside this task's `files:`)
**R1 (the substantive one) — allocator id space was one wider than
libsignal's mintable range, breaking the "allocated id == stored id"
invariant.**
`drift_signal_store.dart` allocated over `1..Medium.MAX_VALUE` (modulus
`0xFFFFFF`), but libsignal's `generatePreKeys(start, count)` computes
`((start - 1 + i).remainder(Medium.MAX_VALUE - 1)) + 1`
(`libsignal_protocol_dart-0.8.2/lib/src/util/key_helper.dart:37`), so the ids
it can actually mint are only `1..Medium.MAX_VALUE - 1`. Probed directly with
the counter seeded to `0xFFFFFF`:
```
ALLOCATED: [16777215, 1, 2]
LIB IDS  : [1, 1, 2]          <-- 16777215 silently minted as id 1
```
Two consequences, both of them the very bug class this task exists to close:
- `IdentityService.replenishOneTimePreKeys` stores `record.id`, so the
  counter recorded a ~16M id as issued while the row actually written
  **reused ancient id 1** — allocated ≠ stored.
- A batch straddling the boundary minted id `1` **twice**, and the second
  `storePreKey(1, ...)` overwrote the first via `insertOnConflictUpdate` —
  silently yielding `count - 1` distinct prekeys while
  `replenishOneTimePreKeys` still returned `ids.length`.
This is *not* the wrap edge case the task file accepts. The accepted case is
"wrapping back to a low value that could collide with an ancient still-live
id"; this was an id the library could not represent at all, which is a
different failure and a one-token fix.
Fixed by introducing `_preKeyIdSpaceModulus = _preKeyIdMediumMaxValue - 1`
and using it for both the id sequence and the counter advance, so the
allocator's space is exactly libsignal's. Re-probed: `ALLOCATED` and
`LIB IDS` now agree (`[16777214, 1, 2]`), no duplicate across the wrap, still
no crash and still no throw at the boundary.
Locked in by a new permanent regression test,
`test_EARS_SEC_3c_allocated_ids_are_always_the_ids_libsignal_mints`
(`identity_service_test.dart`), which seeds the counter near the top of the
space so the boundary is reachable without issuing ~16M ids, and asserts
every allocated id round-trips through `generatePreKeys` unchanged.
**Falsified**: reverting the modulus makes it fail
`Expected: <16777215> / Actual: <1>`.

**R2 — migration backfill test made discriminating** (gapped pool, asserts
`MAX(id) + 1`), as described in point 5 above.

**Reviewer suite after both fixes**: `flutter analyze` → `No issues found!`;
`flutter test` → `+60: All tests passed!`.
