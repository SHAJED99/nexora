# E03-B01 · One-time prekey ids restart at 1 after the pool drains

## Severity: S2 (major function broken, no workaround)
Not S1 only because the defect is currently **latent**: E03-T02 §4 wires
`replenishOneTimePreKeys()` to no caller, and nothing yet consumes one-time
prekeys. **E03-T03 makes it live** — `SessionCipher.decryptPreKeyMessage`
removes the one-time prekey on use. Hence `blocks: [E03-T03]`.

Priority is the human's call (`bug_priorities` gate), not the reviewer's.

## Repro (exact, from a fresh store)
1. Fresh `AppDatabase.forTesting(NativeDatabase.memory())` +
   `DriftSignalProtocolStore` + `IdentityService`.
2. `await service.replenishOneTimePreKeys(minimum: 20, batch: 5)`
   → persists one-time prekeys with ids `[1, 2, 3, 4, 5]`.
3. Record the public key stored under id `1`.
4. Simulate peers consuming every prekey (what T03's
   `decryptPreKeyMessage` does): `for (id in [1..5]) store.removePreKey(id)`
   → pool is now empty.
5. `await service.replenishOneTimePreKeys(minimum: 20, batch: 5)`.
6. Read the ids and the public key now stored under id `1`.

### Expected (E03-T02 §6, the task's own binding risk note)
> "One-time prekey id allocation must never reuse an id still referenced by
> an in-flight (not-yet-consumed) bundle handed to a peer earlier — track
> the next-free id explicitly, don't reuse gaps left by consumed/removed
> prekeys."

New ids must be `[6, 7, 8, 9, 10]` — strictly above every id this device has
ever issued.

### Actual (verified by the reviewer, run 2026-08-27)
```
first batch ids:  [1, 2, 3, 4, 5]
second batch ids: [1, 2, 3, 4, 5]     <-- ids reissued
id 1 key changed: true                <-- with DIFFERENT key material
```

## Root cause
`lib/core/crypto/identity_service.dart:85-87`

```dart
final nextId = existingIds.isEmpty
    ? 1
    : existingIds.reduce((a, b) => a > b ? a : b) + 1;
```

The next-free id is derived from the **live rows only**. `max(existing) + 1`
is correct while at least one prekey survives (which is why
`test_EARS_SEC_3c_replenish_never_reuses_a_consumed_gap` passes — it removes
id 3 out of 1..5 and the max is still 5). But when the pool drains to empty,
`existingIds.isEmpty` is true and allocation **restarts at 1**, reissuing
every id the device already handed out to peers.

This is a **specification defect as much as a coding one**: E03-T02 §6
itself suggested the flawed algorithm verbatim ("e.g. `max(existing ids) + 1`").
The builder implemented the contract as written. The contract was wrong for
the drained-pool case, and no test in §8's plan covered it.

## Why it matters
X3DH addresses a one-time prekey **by id**. A peer holding a bundle that
names prekey id 1 sends a `PreKeySignalMessage` referencing id 1. This
device looks up id 1, finds a *different* private key than the one the peer
did DH against, and the X3DH shared secret does not match — the peer's
first message is permanently undecryptable, and the session fails to
establish. Silent, per-peer, and indistinguishable from a transport fault.

## Fix direction (not prescriptive — the implementer decides within it)
The next-free id must come from a **monotonic high-water mark that survives
row deletion and app restart**, not from `max(live rows)`. Options:

1. **Persist a high-water mark** (a `next_one_time_prekey_id` counter row).
   Correct across restarts. Requires a schema change — see the gate below.
2. **In-memory-only high-water mark** on the service instance.
   Insufficient on its own: it resets every app launch, which is exactly
   when this device would re-replenish a drained pool. Do NOT ship this as
   the whole fix.

Signal's own guidance is a monotonically increasing counter, never reset;
`generatePreKeys(start, count)` wraps at `Medium.MAX_VALUE`, so wrap-around
handling belongs in whatever counter is chosen.

## 🧍 Gate — rule 3
Option 1 is a **schema migration**, which AGENTS.md rule 3 reserves for the
human. Present the option + trade-offs and STOP for approval before writing
a migration. Coordinate with **E03-T01b**, which owns
`crypto_tables.dart`/`database.dart`/`drift_signal_store.dart` — this bug's
counter storage lands in that task's file fence, hence `depends_on: [E03-T01b]`.

## Regression test (write it FIRST, must fail before the fix)
`test_EARS_SEC_3c_replenish_never_reuses_a_drained_pools_ids` — the repro
above as a test: replenish, record id→key, `removePreKey` every id,
replenish again, assert the new ids are all strictly greater than every
previously issued id AND that no previously issued id reappears.

Add a second test that the high-water mark survives a service/store
re-instantiation against the same database (the app-restart case), if
option 1 is approved.
