# E03-T01b · Persist remote-peer identity trust across restarts

## 1. Goal
Close OQ-E03-T01-1 (found in E03-T01's review): make `saveIdentity` /
`isTrustedIdentity` / `getIdentity` durable, so a changed remote identity
key is still detected after the app restarts — the guarantee E03-T03's
`establishSession` depends on.

## 2. Business logic
- FR-SEC-003 (MITM resistance, protocol-level slice per epic.md scope):
  detecting that a peer's identity key changed since it was last trusted is
  the mechanism that makes X3DH's authentication meaningful. If this state
  resets on every process restart, the guarantee only holds within a single
  app session — not acceptable for a messenger that isn't kept running
  continuously.
- FR-SEC-004: still the same library's `IdentityKeyStore` contract — this
  task changes *where* the three methods keep state, not their signatures
  or semantics (trust-on-first-use, `saveIdentity` returns whether a
  previously-trusted key changed).

## 3. What this task does
- Add a `signal_trusted_identities` Drift table: `address_name TEXT`,
  `address_device_id INTEGER`, `identity_key BLOB` (serialized
  `IdentityKey`), PK on `(address_name, address_device_id)`.
- Bump the Drift schema version again (v4→v5), additive `onUpgrade`
  migration adding this one table — same pattern T01 used for its four
  tables. Write a migration test in the same hand-built-prior-schema style
  as `test/core/persistence/crypto_migration_test.dart`, this time upgrading
  from the v4 schema T01 introduced.
- Replace `DriftSignalProtocolStore`'s in-memory `_trustedIdentities` map
  (`lib/core/crypto/drift_signal_store.dart`) with reads/writes through this
  new table. `saveIdentity`/`isTrustedIdentity`/`getIdentity`'s external
  behavior (return values, trust-on-first-use semantics) does not change —
  only the storage backing does.
- Add a regression test proving the exact defect the reviewer found is
  closed: save a peer identity, simulate a restart (fresh
  `DriftSignalProtocolStore` instance over the same underlying `AppDatabase`
  connection, not a new in-memory DB), then confirm `isTrustedIdentity`
  correctly rejects a *different* key for that same address.

## 4. What this task does NOT do
- Does NOT change `IdentityKeyStore`'s method signatures or semantics —
  same three methods, same return values, only durable now.
- Does NOT add any UI to surface a "safety number changed" warning to the
  user — that's a future task once E06/E13 have a place to show it. This
  task only makes the underlying detection durable.
- Does NOT touch `signal_identity`, `signal_signed_prekeys`,
  `signal_one_time_prekeys`, or `signal_sessions` (T01's four tables) —
  those are already correctly persisted; this task adds exactly one more.
- Does NOT implement session establishment or encrypt/decrypt — still T03's
  job; this task only removes its one remaining blocker.

## 5. Contract

### Data
Migration `000X_add_signal_trusted_identities` (schema v4→v5, additive,
reversible — pre-release, no backfill needed):
- `signal_trusted_identities` — `address_name TEXT`, `address_device_id
  INTEGER`, `identity_key BLOB`, PK `(address_name, address_device_id)`.

### Functions
```yaml
- signature: "DriftSignalProtocolStore.saveIdentity(address: SignalProtocolAddress, identityKey: IdentityKey?) -> Future<bool>"
  params: { address: "remote party", identityKey: "their identity key, or null to remove the row" }
  returns: "true if this replaced a previously-persisted DIFFERENT identity key for this address; false if new or unchanged — same contract as T01, now backed by the new table instead of an in-memory Map"
  purpose: "Durable trust-on-first-use bookkeeping"

- signature: "DriftSignalProtocolStore.isTrustedIdentity(address: SignalProtocolAddress, identityKey: IdentityKey, direction: Direction) -> Future<bool>"
  returns: "true if no row exists yet for this address (trust-on-first-use) or the stored key matches; false if it contradicts a stored different key — reads the persisted table, not the removed in-memory Map"
  purpose: "Durable identity-change detection"

- signature: "DriftSignalProtocolStore.getIdentity(address: SignalProtocolAddress) -> Future<IdentityKey?>"
  returns: "the persisted identity key for this address, or null if none stored"
  purpose: "IdentityKeyStore interface method, now durable"
```

## 6. Risks
- This changes the table `DriftSignalProtocolStore` writes to but not its
  public method signatures — double-check nothing outside this class
  referenced the removed in-memory `_trustedIdentities` field directly
  (nothing should; T02 doesn't touch identity trust at all).
- The regression test is only meaningful if it genuinely exercises two
  separate store *instances* over the same persisted `AppDatabase` — a test
  that reuses the same `DriftSignalProtocolStore` object instance would
  pass even with the old in-memory bug, since the Map would still be
  populated. Construct a second instance to prove persistence, not reuse.
