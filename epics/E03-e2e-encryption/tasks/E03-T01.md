# E03-T01 · Add libsignal_protocol_dart + Drift-backed protocol store

## 1. Goal
Give the app a real, persistent implementation of the Signal protocol's
storage interfaces (identity, prekeys, signed prekeys, sessions) so T02/T03
have somewhere durable to keep key material — the foundation every later
crypto operation reads and writes through.

## 2. Business logic
- FR-SEC-004 / EARS-SEC-3: the protocol implementation must be the accepted
  X3DH + Double Ratchet family (ADR-0003), not ad hoc — this task wires the
  specific library named in OQ-E03-1 (`libsignal_protocol_dart`, resolved
  2026-08-27) into the app.
- Session/ratchet state is local-only, never synced to Firebase (`FR-FB-002`,
  epic.md "Data model") — these tables are not part of any sync path.
- Identity keys, once generated, must never be regenerated silently — a
  second call after first-run must be a no-op that returns the existing
  identity, not a fresh one (regenerating would orphan every session a peer
  has with this device).

## 3. What this task does
- Add `libsignal_protocol_dart` (mixin.dev, pure Dart, GPL-3.0 — accepted by
  the human, see OQ-E03-1) to `pubspec.yaml`.
- Add Drift tables for the four things the library's store interfaces need
  to persist: local identity (identity keypair + registration id, one row),
  signed prekeys, one-time prekeys, and sessions (keyed by remote address —
  `name` + `deviceId` per the library's `SignalProtocolAddress`).
- Implement `DriftSignalProtocolStore` — a single class implementing the
  library's `IdentityKeyStore`, `PreKeyStore`, `SignedPreKeyStore`, and
  `SessionStore` interfaces, backed by the tables above via `AppDatabase`.
  (`SenderKeyStore`/group state is explicitly out of scope — see §4.)
- Bump the Drift schema version and write a real `onUpgrade` migration
  (adding the new tables), proven by a hand-built prior-version-schema test
  in the same style as `test/core/persistence/database_migration_test.dart`.

## 4. What this task does NOT do
- Does NOT generate any actual key material or call any of the store's
  methods from application code yet — this task is the storage seam only.
  Key generation is E03-T02.
- Does NOT implement `SenderKeyStore` (group/Sender-Keys persistence) — that
  belongs to E07 when group encryption is built, even though the same
  library will provide it later.
- Does NOT touch `lib/core/crypto/crypto_stub.dart` or wire anything into
  `main.dart` — nothing calls this store yet, so nothing observable changes
  in the running app after this task.
- Does NOT add any UI, screen, or route.
- Does NOT implement encrypt/decrypt or session establishment (X3DH) logic —
  that's T03. This task only proves data survives a write→read→app-restart
  cycle correctly.

## 5. Contract

### Data
Migration `000X_add_signal_protocol_stores` (schema version bump, additive,
reversible — pre-release, no backfill needed):
- `signal_identity` — singleton row: `id INTEGER PK`, `identity_key_pair BLOB`
  (serialized `IdentityKeyPair`), `registration_id INTEGER`.
- `signal_signed_prekeys` — `id INTEGER PK` (the prekey id from the library,
  not autoincrement), `record BLOB` (serialized `SignedPreKeyRecord`).
- `signal_one_time_prekeys` — `id INTEGER PK` (prekey id), `record BLOB`
  (serialized `PreKeyRecord`).
- `signal_sessions` — `address_name TEXT`, `address_device_id INTEGER`,
  `record BLOB` (serialized `SessionRecord`), PK on
  `(address_name, address_device_id)`.

All BLOB columns store the library's own `.serialize()` bytes — this task
does not invent a serialization format.

## 6. Risks
- The library's store interfaces are `async` in `libsignal_protocol_dart`
  (unlike the original Java) — confirm exact method signatures against the
  installed package version, don't guess from the Java API docs.
- Getting the singleton-row pattern for `signal_identity` wrong (e.g.
  allowing two rows) would let a bug silently generate a second identity —
  enforce with a unique constraint or a fixed `id = 0`, not just "insert
  once and hope."
- BLOB round-tripping: write a test that serializes, writes, reads, and
  deserializes a real record object (not just raw bytes) to catch any
  library-version serialization quirk early.
