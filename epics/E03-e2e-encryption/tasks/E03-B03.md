# E03-B03 · No catchable type for the commonest decrypt failure

## Severity: S3 (broken, but there's a workaround)
Nothing is broken *today* — no caller exists yet (E03-T03 §4: the API is real
but unused until E05/E06). The defect is that the seam E03 hands to its
consumers forces one of two bad choices, in a security path:

- **catch-all** (`try { decrypt() } catch (_) { }`) — which swallows genuine
  bugs (a `StateError` from a missing `init`, an `ArgumentError` from a wrong
  message type, an `UntrustedIdentityException` that a UI *must* surface as a
  safety-number warning) alongside routine undecryptable traffic; or
- **runtime-type string matching**, the workaround already in this repo's own
  test suite (`test/core/crypto/crypto_service_test.dart:86-89`).

The workaround exists and works, hence S3 rather than S2. But it is a
string-compare against a private class name in a third-party package — it
breaks silently on any rename, and it is the pattern E05/E06 would copy.

Priority is the human's (`bug_priorities` gate). Reviewer's advisory: P3 —
this is genuinely "next epic" work, best done alongside whichever epic first
writes a `catch` around `decrypt()`.

## Repro
1. Grep the installed package barrel:
   `libsignal_protocol_dart-0.8.2/lib/libsignal_protocol_dart.dart`.
2. Note which exception files it exports.

### Expected
A consumer of `CryptoService.decrypt()` can distinguish, **by type**:
- MAC / key-derivation failure (wrong key — the routine "cannot read this"
  case, and the case both of E03-T03's strongest security proofs assert on),
- `DuplicateMessageException` (replay),
- `NoSessionException` (no session),
- `InvalidKeyIdException` (missing prekey),
- `UntrustedIdentityException` (safety-number change — must reach the user).

### Actual (reviewer-verified 2026-08-27)
The barrel exports `duplicate_message_exception` (:2),
`invalid_key_exception` (:21), `invalid_key_id_exception` (:22),
`legacy_message_exception` (:23), `no_session_exception` (:24) and
`untrusted_identity_exception` (:49) — but **not**
`src/invalid_message_exception.dart`. The one failure mode that means "the
crypto ran and the key was wrong" is the one type a caller cannot name.

Evidence that this already bit us: `crypto_service_test.dart:86-89` has to
do
```dart
final Matcher _isInvalidMessageException = predicate<Object>(
  (e) => e.runtimeType.toString() == 'InvalidMessageException', ...
```
with a comment explaining that naming the type would require an
`implementation_imports` lint violation.

## Root cause
A packaging omission in `libsignal_protocol_dart` v0.8.2 — not in NEXORA
code. But E03 owns the seam: `crypto_stub.dart` is the public
`core/crypto` API, and it currently lets the library's un-nameable exception
escape to callers unchanged.

## Fix direction (not prescriptive)
1. **A NEXORA-owned exception taxonomy** — `crypto_stub.dart` catches the
   library's exceptions inside `decrypt()`/`encrypt()`/`establishSession()`
   and rethrows small app-owned types (e.g. `CryptoDecryptFailure`,
   `CryptoReplayRejected`, `CryptoUntrustedIdentity`, `CryptoNoSession`)
   preserving the original as a `cause`. Cleanest for consumers, insulates
   the app from the library's packaging; costs a mapping layer that must not
   accidentally collapse two distinct failures into one.
2. **Re-export with a targeted lint ignore** — `// ignore: implementation_imports`
   on an import of `src/invalid_message_exception.dart` plus a re-export from
   our own file. Two lines; keeps the library's names; leaves callers coupled
   to a package-private path.
3. **Upstream** — file the export omission with the package and pin/patch.
   Right long-term answer, wrong timescale to block on.

Reviewer's advisory: **Option 1**, chosen when E05/E06's error handling is
designed rather than in isolation — the taxonomy should be shaped by what the
UI actually needs to distinguish (specifically: which failures are silent and
which must raise a safety-number warning). That is why this is a bug task and
not a two-line fix committed during the sweep.

## 4. What this task does NOT do
- Does NOT change `decrypt()`'s success-path behaviour or return type.
- Does NOT swallow any exception — every failure must still throw.
- Does NOT change the five E03-T03 proof tests' *intent*; if Option 1 is
  taken they must be updated to assert the new types (and must still fail
  against a broken implementation — re-run the E03-T03 mutation check).
- Does NOT weaken any assertion to `throwsA(isException)` or `throwsA(anything)`
  — the E03-T03 review specifically tightened one such assertion
  (`crypto_service_test.dart:388-392`); regressing it would undo that.

## Regression test
Replace the `_isInvalidMessageException` runtime-type-name predicate with a
real `isA<...>()` matcher over whichever type the approved option introduces,
and add one test asserting that a MAC failure and a replay are distinguishable
by type from the same `catch` site.
