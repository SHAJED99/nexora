# E03-T03 · Real core/crypto API — X3DH session establishment + Double Ratchet encrypt/decrypt

## 1. Goal
Replace the genesis `CryptoService` stub with the real public API every
later communication epic (E05, E06) will call: establish a session with a
remote device from its prekey bundle, then encrypt/decrypt messages through
that session — proving forward secrecy and post-compromise recovery along
the way, since this is the epic's highest-consequence deliverable.

## 2. Business logic
- FR-SEC-001 / EARS-SEC-1: only the two session endpoints can decrypt —
  proven by a two-party round-trip test where each side only holds its own
  keys.
- FR-SEC-002 / EARS-SEC-2: no third party (including this codebase's own
  test harness acting as a "relay") ever has access to plaintext or to a
  key that could derive it — ciphertext bytes handed to a simulated relay
  must not decrypt.
- FR-SEC-003 (protocol-level slice only, per epic.md scope): replay
  protection via the ratchet's message counters — a duplicated ciphertext
  is rejected or its plaintext is not re-derivable a second way that leaks
  state; MITM resistance via the identity-key-authenticated X3DH handshake,
  provided by T01b's durable `isTrustedIdentity` (T01's original in-memory
  version did not survive a restart — closed by T01b, see OQ-E03-T01-1).
- FR-SEC-004 / EARS-SEC-3: this is the library's `SessionBuilder` +
  `SessionCipher` doing X3DH + Double Ratchet exactly as specified —
  this task does not hand-roll any ratchet math.

## 3. What this task does
- `CryptoService.establishSession(remoteAddress: SignalProtocolAddress, remoteBundle: PreKeyBundle) -> Future<void>` —
  wraps the library's `SessionBuilder.processPreKeyBundle`, using T01's
  `DriftSignalProtocolStore` for all four store roles the builder needs.
- `CryptoService.encrypt(remoteAddress: SignalProtocolAddress, plaintext: Uint8List) -> Future<CiphertextMessage>` —
  wraps `SessionCipher.encrypt`; throws a clear error if no session exists
  yet (caller must `establishSession` first — this task doesn't
  auto-establish on demand, see §4).
- `CryptoService.decrypt(remoteAddress: SignalProtocolAddress, ciphertext: CiphertextMessage) -> Future<Uint8List>` —
  wraps `SessionCipher.decryptPreKeyMessage`/`decryptFromSignal` (whichever
  the installed library version names them) depending on the ciphertext's
  actual type (`PreKeySignalMessage` on first receipt vs `SignalMessage`
  thereafter) — this task must detect which and call the right one, not
  assume.
- Replace `crypto_stub.dart`'s body with the above; keep the same
  `CryptoService.instance` singleton shape genesis established so nothing
  else in the app needs to change its import.
- Write the forward-secrecy / post-compromise / replay tests named in §8 —
  these are the epic's core proof, not optional coverage.

## 4. What this task does NOT do
- Does NOT auto-establish a session inside `encrypt()`/`decrypt()` when one
  doesn't exist — callers (E05/E06) are responsible for calling
  `establishSession()` first; an implicit auto-establish would hide a
  missing-bundle bug as a silent extra round-trip.
- Does NOT implement group/Sender-Keys encryption (`SenderKeyStore`,
  `GroupCipher`) — E07's job, per epic.md scope.
- Does NOT implement any transport for exchanging prekey bundles or
  ciphertext bytes between real devices — E04's job. Tests here simulate
  both parties in-process, in the same test file, passing bytes directly.
- Does NOT wire `CryptoService` into `main.dart`, any use case, or any
  screen — no caller exists yet in this epic; the API becomes real, but
  unused, until E05/E06 call it.
- Does NOT add key rotation, session expiry, or multi-device fan-out for a
  single account — single session per `(remote name, remote deviceId)` pair
  only, matching T01's store shape.

## 5. Contract

### Functions
```yaml
- signature: "CryptoService.establishSession(remoteAddress: SignalProtocolAddress, remoteBundle: PreKeyBundle) -> Future<void>"
  params: { remoteAddress: "who we're establishing with", remoteBundle: "their published bundle (from their IdentityService.getLocalPreKeyBundle())" }
  returns: "void — a session now exists in the store for remoteAddress; throws UntrustedIdentityException if remoteBundle's identity key contradicts a previously-trusted one for this address"
  purpose: "X3DH handshake, initiating side"

- signature: "CryptoService.encrypt(remoteAddress: SignalProtocolAddress, plaintext: Uint8List) -> Future<CiphertextMessage>"
  params: { remoteAddress: "session to use", plaintext: "raw bytes to encrypt" }
  returns: "a CiphertextMessage (PreKeySignalMessage if the session is pre-confirmation, else SignalMessage) — its .serialize() bytes are what a transport actually carries"
  purpose: "Double Ratchet encrypt step; throws StateError if no session exists for remoteAddress"

- signature: "CryptoService.decrypt(remoteAddress: SignalProtocolAddress, ciphertext: CiphertextMessage) -> Future<Uint8List>"
  params: { remoteAddress: "who sent it", ciphertext: "as received (already deserialized to the correct message type by the caller)" }
  returns: "the original plaintext bytes; throws on an invalid/replayed/undecryptable message rather than returning garbage"
  purpose: "Double Ratchet decrypt step, establishes the session implicitly if ciphertext is a PreKeySignalMessage (X3DH responder side)"
```

## 6. Risks
- This is the epic's highest-consequence task — a subtly wrong wrapper
  around a correct library can still break forward secrecy (e.g. holding a
  reference to a decrypted session state longer than needed, or logging
  intermediate keys during debugging and forgetting to remove it). Grep the
  final diff for any `print`/`log` call anywhere near key material before
  calling this done.
- `PreKeySignalMessage` vs `SignalMessage` type detection: get this wrong
  and the responder can't complete X3DH — write the two-party test *first*
  so this is caught by a failing test, not by review.
- The "compromising a later key doesn't reveal earlier plaintext" test is
  easy to write in a way that doesn't actually prove anything (e.g. just
  asserting two ciphertexts differ). It must derive the *actual message
  key* the ratchet would have used for a later message and confirm it
  cannot be used to decrypt an earlier one, or equivalent library-level
  evidence — a superficial version of this test is worse than no test,
  since it gives false confidence on the epic's central claim.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-SEC-1**: The system SHALL end-to-end encrypt communication such
  that only the two session endpoints can decrypt it. (FR-SEC-001)
- **EARS-SEC-2**: A relay holding only ciphertext bytes SHALL NOT be able
  to derive plaintext. (FR-SEC-002)
- **EARS-SEC-3**: The system SHALL implement this via X3DH + Double Ratchet
  (ADR-0003), including forward secrecy and post-compromise recovery, not
  an ad hoc scheme. (FR-SEC-004)

### Tests
- `test_EARS_SEC_1_two_party_roundtrip` — Alice establishes with Bob's
  bundle, encrypts; Bob decrypts the `PreKeySignalMessage` and recovers the
  original plaintext; reply in the other direction also round-trips
- `test_EARS_SEC_2_relay_cannot_decrypt` — a third party holding only the
  serialized ciphertext bytes (no store, no keys) cannot recover plaintext
  by any means this test can exercise
- `test_EARS_SEC_3_forward_secrecy` — after N message exchanges, capture
  the *current* ratchet/message key material an attacker would obtain by
  compromising the session at that point; confirm it cannot decrypt
  messages 1..N-1 (already-consumed keys are gone, not derivable backward)
- `test_EARS_SEC_3_post_compromise_recovery` — after a simulated key
  compromise, continued ratchet steps (a fresh DH ratchet turn) produce
  message keys the compromised material cannot predict
- `test_EARS_SEC_3_replay_rejected` — decrypting the same ciphertext twice
  either throws or does not yield a second usable plaintext derivation
  (library-dependent behavior — assert whatever the library actually
  guarantees, don't assume)

## Run log
- **API correction vs task §5 sketch**: the installed `libsignal_protocol_dart`
  v0.8.2 does not have `decryptPreKeyMessage`/`decryptFromSignal` as a single
  auto-detecting call. The real API: `SessionCipher.decrypt(PreKeySignalMessage)`
  and `SessionCipher.decryptFromSignal(SignalMessage)` — two distinct methods,
  matching the task's own anticipation that names might differ.
  `CryptoService.decrypt()` type-detects via `is PreKeySignalMessage` /
  `is SignalMessage` and calls the matching one. `SessionBuilder`/
  `SessionCipher` are constructed per-call via
  `.fromSignalStore(store, address)` / `.fromStore(store, address)` —
  effectively stateless wrappers that read/write the store fresh each time,
  not long-lived session objects.
- **Two-party tests, singleton constraint**: `CryptoService.instance` is a
  true process-wide singleton, but the §8 tests need two independent
  simulated devices in one test process. Added
  `CryptoService.withStore(store)`, additive to the class, leaving
  `instance`/`init()` untouched — see §9 Deviations.
- **Each of the 5 EARS-proof tests, and what it actually demonstrates**
  (`test/core/crypto/crypto_service_test.dart`):
  - `test_EARS_SEC_1_two_party_roundtrip`: Alice establishes from Bob's real
    `PreKeyBundle`, encrypts, Bob decrypts and recovers the exact plaintext
    with zero shared state beyond the bundle; reply direction round-trips
    too, now as a plain `SignalMessage` (steady state). Proves FR-SEC-001's
    positive case with real library objects end to end.
  - `test_EARS_SEC_2_relay_cannot_decrypt`: confirms the encrypted body
    bytes of a captured ciphertext don't literally contain the plaintext,
    then hands a genuinely steady-state ciphertext to a relay store that
    has *nothing* in it (no identity, no keys, no session — the actual
    shape of "holds only ciphertext bytes"). `SessionCipher`'s own first
    check, `containsSession`, fails immediately
    (`NoSessionException`) — the relay never even reaches key material.
  - `test_EARS_SEC_3_forward_secrecy`: Bob consumes 3 messages from Alice
    in order. A snapshot of Bob's *current* session state is taken only
    after all 3 are consumed (exactly what stealing Bob's device storage at
    that instant would yield) and fed into a fresh `SessionCipher` built
    from that snapshot alone. Re-decrypting message 1 and message 2 with
    it both throw `DuplicateMessageException` — their message keys were
    already consumed and deleted from the ratchet chain (never held in the
    "skipped keys" map, since nothing was skipped), so the compromised
    *current* state genuinely cannot re-derive them. This is real key
    material from the real library's ratchet state, not a symbolic
    diff-check.
  - `test_EARS_SEC_3_post_compromise_recovery`: a 5-message exchange
    (A→B, B→A, A→B, B→A, A→B). The attacker snapshots Bob's state right
    after message 1. The attacker's stale snapshot *can* decrypt message 3
    (proving the compromise window is real, not a no-op) because deriving
    message 3's key only needs the ratchet key Bob already held at
    compromise time. But processing message 3 forces Bob's *live* session
    to mint a brand-new, randomly-generated ratchet key pair it never had
    before (`SessionCipher`'s internal `_getOrCreateChainKey`, a
    library-level fact verified by reading `session_cipher.dart`, not
    assumed) — and once Alice's side reflects that (message 4) and sends
    message 5 on the resulting new chain, the same stale attacker snapshot
    fails to decrypt message 5. This proves recovery is driven by the
    honest device's own fresh randomness after compromise, not by the
    attacker simply not trying hard enough.
  - `test_EARS_SEC_3_replay_rejected`: decrypting the identical ciphertext
    a second time throws `DuplicateMessageException` — the library's
    actual documented behavior (message keys are one-shot; a repeated
    counter with no stored skipped-key is rejected), asserted directly
    rather than assumed.
- **Confidence note**: the forward-secrecy and PCR tests are the ones the
  task's own §6 flags as easy to write superficially. Both operate on real,

  match on the attacker's *successful* attempt in the PCR case (proving the
  compromise window was genuinely exercised, not skipped past). I judge

### The library facts this task's proofs depend on (verified in source)
- `throw DuplicateMessageException` occurs at exactly **one** site in
  `session_cipher.dart:263`, inside `_getOrCreateMessageKeys`, reachable
  only when `chainKey.index > counter` **AND** `hasMessageKeys(...)` is
  false. The skipped-message-key cache is checked **first**, and a cache
  hit `return`s the key instead of throwing. So on the 1:1 path this
  exception means precisely *"the receive chain has ratcheted past this
  counter and no retained key for it exists"*. Since `ChainKey` derivation
  is a one-way KDF, that is unrecoverable — i.e. it means forward secrecy,
  not merely "already processed".
- `DuplicateMessageException implements Exception` — it is **not** a
  subclass of `InvalidMessageException`, so it is not swallowed by
  `_decrypt`'s `on InvalidMessageException` catch and propagates
  unambiguously.
- `SessionBuilder.processV3` returns early via
  `sessionRecord.hasSessionState(version, baseKey)` **before** any prekey
  load. This confirms the forward-secrecy test's attacker reaches the real
  ratchet decrypt path and does *not* fail on the snapshot's absent
  prekeys — the builder's claim here is correct.
- `_getOrCreateChainKey` calls `Curve.generateKeyPair()` and rewrites
  `rootKey` on first sight of a new `theirEphemeral`. The PCR test's
  "fresh post-compromise ratchet key" is therefore a **genuine DH ratchet
  turn with new randomness**, not counter progression.

### Mutation testing (proof the tests aren't vacuous)
Swapped `decrypt()`'s `PreKeySignalMessage` branch to the wrong library
call (`decryptFromSignal(inner)`) — a subtle, plausible wrong-path bug.
Result: **all 5 tests failed**. The suite is genuinely wired to behavior.
Mutation reverted; `crypto_stub.dart` is byte-identical to the builder's.

### Positive control (the decisive check on forward secrecy)
The stated risk was that `DuplicateMessageException` might be a
counter-artifact that fires while a skipped-key cache would still permit
decryption. I built a throwaway probe where Bob decrypts msg2 **first**,
skipping msg1 (so msg1's key IS retained), then snapshotted Bob:
```
hasMessageKeys(m1 counter=0) = true
attacker DECRYPTED skipped msg1 -> "one"
```
The attacker snapshot **succeeded**. So the exception is *not*
unconditional: it fires in the real test specifically and only because the
key material is absent. `test_EARS_SEC_3_forward_secrecy` is a genuine
proof. (Probe deleted; it was a verification aid, not a committed test.)

### Findings and fixes applied (all confined to the test file)
1. **`test_EARS_SEC_2_relay_cannot_decrypt` was materially weaker than its
   name — FIXED.** The original proof was an empty store failing at
   `containsSession` with `NoSessionException`. That proves only *"our API
   requires a session"*, which is strictly weaker than FR-SEC-002's claim.
   Added a **fully-resourced third party (Carol)** with her own real
   identity, signed prekey, one-time prekey pool, and a genuine live
   Double Ratchet session with Alice herself. Carol now fails on both
   paths: (a) running the real X3DH responder path on Alice's handshake to
   Bob — she gets through `processV3`, runs `initializeSessionBob` with her
   own valid keys, derives a real message key, and fails **MAC
   verification**; (b) intercepting the steady-state message — she passes
   `containsSession`, reaches `_getOrCreateChainKey`, derives from her own
   root key, and fails MAC. Both are now *cryptographic* failures, not
   precondition failures. Ordering matters and is commented: the X3DH
   attempt must come first, while Carol's prekey pool is intact, or she
   fails at a mere prekey-id lookup (`InvalidKeyIdException`) and proves
   much less — this is exactly what happened on my first attempt.
2. **PCR's msg5 assertion was `throwsA(isException)` — FIXED.** That would
   have passed on a broken fixture (missing prekey, absent identity, or a
   `StateError` from our own wrapper), i.e. for reasons unrelated to
   post-compromise recovery. Tightened to assert the specific
   MAC/key-derivation failure. Note: `invalid_message_exception.dart` is
   **not exported** from the library's public barrel, so this is matched by
   runtime type name via a documented `predicate` matcher rather than an
   `implementation_imports` lint violation.
3. **Strengthened two proofs against object-identity artifacts.** The
   forward-secrecy and replay tests now feed the attacker/replayer
   **re-deserialized wire bytes** (`PreKeySignalMessage(msg.serialize())`)
   rather than the sender's in-memory object, so they assert "these
   ciphertext bytes are rejected" rather than "this object is rejected".
   Also added a **direct structural assertion** to the forward-secrecy
   test: the compromised snapshot's `hasMessageKeys(...)` is false for
   msg1's and msg2's counters — proving the keys are absent from
   everything the attacker holds, independent of what any exception means.

### Non-blocking notes for the epic sweep / E05-E06
- **N-1 (forward-secrecy bound, inherent to Signal, not a defect):**
  skipped/undelivered message keys **are** retained in the session state
  (`maxMessageKeys = 2000` per receiver chain,
  `session_state.dart:34,264`) and remain decryptable from a compromised
  device until consumed or evicted. Forward secrecy as proven here holds
  for messages consumed **in order**. Standard, necessary for out-of-order
  delivery — but it bounds FR-SEC-004's claim and should be stated
  wherever that guarantee is documented for users.
- **N-2 (API ergonomics):** `InvalidMessageException` is not exported from
  the library barrel, so E05/E06 callers cannot catch the most common
  decrypt failure by type through the public API. `CryptoService.decrypt`'s
  contract says it "throws on an invalid/replayed/undecryptable message";
  a small catchable error taxonomy owned by `core/crypto` would be worth a
  task in E05.
- Neither note blocks this task; both are recorded for the sweep.
