# E03-T03 · Real core/crypto API — X3DH session establishment + Double Ratchet encrypt/decrypt

## 1. Goal
Replace the genesis `CryptoService` stub with the real public API every
later communication epic (E05, E06) will call: establish a session with a
remote device from its prekey bundle, then encrypt/decrypt messages through
that session — proving forward secrecy and post-compromise recovery along
the way, since this is the epic's highest-consequence deliverable.

## 2. Business logic
- FR-SEC-001 / EARS-SEC-1: only the two session endpoints can decrypt —
  proven by a two-party round-trip test where each side only holds its own
  keys.
- FR-SEC-002 / EARS-SEC-2: no third party (including this codebase's own
  test harness acting as a "relay") ever has access to plaintext or to a
  key that could derive it — ciphertext bytes handed to a simulated relay
  must not decrypt.
- FR-SEC-003 (protocol-level slice only, per epic.md scope): replay
  protection via the ratchet's message counters — a duplicated ciphertext
  is rejected or its plaintext is not re-derivable a second way that leaks
  state; MITM resistance via the identity-key-authenticated X3DH handshake,
  provided by T01b's durable `isTrustedIdentity` (T01's original in-memory
  version did not survive a restart — closed by T01b, see OQ-E03-T01-1).
- FR-SEC-004 / EARS-SEC-3: this is the library's `SessionBuilder` +
  `SessionCipher` doing X3DH + Double Ratchet exactly as specified —
  this task does not hand-roll any ratchet math.

## 3. What this task does
- `CryptoService.establishSession(remoteAddress: SignalProtocolAddress, remoteBundle: PreKeyBundle) -> Future<void>` —
  wraps the library's `SessionBuilder.processPreKeyBundle`, using T01's
  `DriftSignalProtocolStore` for all four store roles the builder needs.
- `CryptoService.encrypt(remoteAddress: SignalProtocolAddress, plaintext: Uint8List) -> Future<CiphertextMessage>` —
  wraps `SessionCipher.encrypt`; throws a clear error if no session exists
  yet (caller must `establishSession` first — this task doesn't
  auto-establish on demand, see §4).
- `CryptoService.decrypt(remoteAddress: SignalProtocolAddress, ciphertext: CiphertextMessage) -> Future<Uint8List>` —
  wraps `SessionCipher.decryptPreKeyMessage`/`decryptFromSignal` (whichever
  the installed library version names them) depending on the ciphertext's
  actual type (`PreKeySignalMessage` on first receipt vs `SignalMessage`
  thereafter) — this task must detect which and call the right one, not
  assume.
- Replace `crypto_stub.dart`'s body with the above; keep the same
  `CryptoService.instance` singleton shape genesis established so nothing
  else in the app needs to change its import.
- Write the forward-secrecy / post-compromise / replay tests named in §8 —
  these are the epic's core proof, not optional coverage.

## 4. What this task does NOT do
- Does NOT auto-establish a session inside `encrypt()`/`decrypt()` when one
  doesn't exist — callers (E05/E06) are responsible for calling
  `establishSession()` first; an implicit auto-establish would hide a
  missing-bundle bug as a silent extra round-trip.
- Does NOT implement group/Sender-Keys encryption (`SenderKeyStore`,
  `GroupCipher`) — E07's job, per epic.md scope.
- Does NOT implement any transport for exchanging prekey bundles or
  ciphertext bytes between real devices — E04's job. Tests here simulate
  both parties in-process, in the same test file, passing bytes directly.
- Does NOT wire `CryptoService` into `main.dart`, any use case, or any
  screen — no caller exists yet in this epic; the API becomes real, but
  unused, until E05/E06 call it.
- Does NOT add key rotation, session expiry, or multi-device fan-out for a
  single account — single session per `(remote name, remote deviceId)` pair
  only, matching T01's store shape.

## 5. Contract

### Functions
```yaml
- signature: "CryptoService.establishSession(remoteAddress: SignalProtocolAddress, remoteBundle: PreKeyBundle) -> Future<void>"
  params: { remoteAddress: "who we're establishing with", remoteBundle: "their published bundle (from their IdentityService.getLocalPreKeyBundle())" }
  returns: "void — a session now exists in the store for remoteAddress; throws UntrustedIdentityException if remoteBundle's identity key contradicts a previously-trusted one for this address"
  purpose: "X3DH handshake, initiating side"

- signature: "CryptoService.encrypt(remoteAddress: SignalProtocolAddress, plaintext: Uint8List) -> Future<CiphertextMessage>"
  params: { remoteAddress: "session to use", plaintext: "raw bytes to encrypt" }
  returns: "a CiphertextMessage (PreKeySignalMessage if the session is pre-confirmation, else SignalMessage) — its .serialize() bytes are what a transport actually carries"
  purpose: "Double Ratchet encrypt step; throws StateError if no session exists for remoteAddress"

- signature: "CryptoService.decrypt(remoteAddress: SignalProtocolAddress, ciphertext: CiphertextMessage) -> Future<Uint8List>"
  params: { remoteAddress: "who sent it", ciphertext: "as received (already deserialized to the correct message type by the caller)" }
  returns: "the original plaintext bytes; throws on an invalid/replayed/undecryptable message rather than returning garbage"
  purpose: "Double Ratchet decrypt step, establishes the session implicitly if ciphertext is a PreKeySignalMessage (X3DH responder side)"
```

## 6. Risks
- This is the epic's highest-consequence task — a subtly wrong wrapper
  around a correct library can still break forward secrecy (e.g. holding a
  reference to a decrypted session state longer than needed, or logging
  intermediate keys during debugging and forgetting to remove it). Grep the
  final diff for any `print`/`log` call anywhere near key material before
  calling this done.
- `PreKeySignalMessage` vs `SignalMessage` type detection: get this wrong
  and the responder can't complete X3DH — write the two-party test *first*
  so this is caught by a failing test, not by review.
- The "compromising a later key doesn't reveal earlier plaintext" test is
  easy to write in a way that doesn't actually prove anything (e.g. just
  asserting two ciphertexts differ). It must derive the *actual message
  key* the ratchet would have used for a later message and confirm it
  cannot be used to decrypt an earlier one, or equivalent library-level
  evidence — a superficial version of this test is worse than no test,
  since it gives false confidence on the epic's central claim.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-SEC-1**: The system SHALL end-to-end encrypt communication such
  that only the two session endpoints can decrypt it. (FR-SEC-001)
- **EARS-SEC-2**: A relay holding only ciphertext bytes SHALL NOT be able
  to derive plaintext. (FR-SEC-002)
- **EARS-SEC-3**: The system SHALL implement this via X3DH + Double Ratchet
  (ADR-0003), including forward secrecy and post-compromise recovery, not
  an ad hoc scheme. (FR-SEC-004)

### Tests
- `test_EARS_SEC_1_two_party_roundtrip` — Alice establishes with Bob's
  bundle, encrypts; Bob decrypts the `PreKeySignalMessage` and recovers the
  original plaintext; reply in the other direction also round-trips
- `test_EARS_SEC_2_relay_cannot_decrypt` — a third party holding only the
  serialized ciphertext bytes (no store, no keys) cannot recover plaintext
  by any means this test can exercise
- `test_EARS_SEC_3_forward_secrecy` — after N message exchanges, capture
  the *current* ratchet/message key material an attacker would obtain by
  compromising the session at that point; confirm it cannot decrypt
  messages 1..N-1 (already-consumed keys are gone, not derivable backward)
- `test_EARS_SEC_3_post_compromise_recovery` — after a simulated key
  compromise, continued ratchet steps (a fresh DH ratchet turn) produce
  message keys the compromised material cannot predict
- `test_EARS_SEC_3_replay_rejected` — decrypting the same ciphertext twice
  either throws or does not yield a second usable plaintext derivation
  (library-dependent behavior — assert whatever the library actually
  guarantees, don't assume)
