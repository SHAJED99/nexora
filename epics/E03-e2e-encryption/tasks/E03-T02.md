# E03-T02 · Local identity generation + prekey bundle service

## 1. Goal
On first run, generate this device's real Signal identity (identity keypair,
registration id, a signed prekey, and a batch of one-time prekeys) and expose
a `PreKeyBundle` that a remote peer needs to start an X3DH session with this
device — the material T03's session establishment will consume.

## 2. Business logic
- FR-SEC-004 / EARS-SEC-3: identity generation must happen exactly once per
  device and be idempotent thereafter (re-running app startup must not
  regenerate — see T01 §6 risk on the singleton row).
- One-time prekeys are consumable (T01's `removePreKey`) — this service is
  also responsible for noticing the pool is low and replenishing it, since
  X3DH's forward-secrecy guarantee for the *first* message depends on a
  one-time prekey being available. (E04's transport is what actually
  *carries* prekey bundles to peers — out of scope here, see §4.)

## 3. What this task does
- `IdentityService.ensureLocalIdentity()` — on first call, generates an
  `IdentityKeyPair` + random registration id via the library's helpers and
  persists them through `DriftSignalProtocolStore` (T01). On any later call,
  a no-op that reads the existing identity back.
- `IdentityService.ensureSignedPreKey()` — generates one signed prekey (id 1)
  if none exists yet; the app runs one signed prekey at a time for v1 (no
  rotation policy yet — note as a follow-up, not a gap to solve here).
- `IdentityService.replenishOneTimePreKeys({int minimum = 20, int batch = 20})`
  — counts remaining one-time prekeys in the store; if below `minimum`,
  generates `batch` more starting at the next unused id and persists them.
- `IdentityService.getLocalPreKeyBundle() -> PreKeyBundle` — assembles the
  local identity key, registration id, signed prekey (+ its signature), and
  one *unconsumed* one-time prekey into the library's `PreKeyBundle` shape,
  for a remote peer to consume via X3DH. Does not mark it consumed — the
  *receiving* side of establishment (T03) removes the one-time prekey when
  it's actually used.

## 4. What this task does NOT do
- Does NOT transmit the bundle anywhere — no mesh/network call, no Firebase
  write. `getLocalPreKeyBundle()` returns a Dart object; how a peer actually
  receives it is E04's (transport) concern.
- Does NOT implement `SessionBuilder`/X3DH session establishment on the
  *consuming* side, or `SessionCipher` encrypt/decrypt — that's T03.
- Does NOT add a prekey rotation/expiry policy (signed prekey rotation is a
  real Signal-protocol practice but not required for v1's threat model per
  the epic scope) — leave the single signed-prekey-forever behavior as is
  and note it as a follow-up in Run log, don't build rotation.
- Does NOT add any UI or expose this service to `main.dart`/app startup yet
  — that wiring happens when T03 makes the whole `core/crypto` API real and
  something actually calls it.

```yaml
  params: {}

```

## 6. Risks
- One-time prekey id allocation must never reuse an id still referenced by
  an in-flight (not-yet-consumed) bundle handed to a peer earlier — track
  the next-free id explicitly (e.g. `max(existing ids) + 1`), don't reuse
  gaps left by consumed/removed prekeys.
- `getLocalPreKeyBundle()` racing with `replenishOneTimePreKeys()` in the
  same process isn't a real concern for v1 (single-isolate, no concurrent
  callers) — don't add locking machinery for a race that can't happen yet.

**Finding 1 — S2, split out to `E03-B01`, blocks E03-T03.**
`identity_service.dart:85-87` — one-time prekey id allocation:
```dart
final nextId = existingIds.isEmpty
    ? 1
    : existingIds.reduce((a, b) => a > b ? a : b) + 1;
```
`max(live rows) + 1` is correct only while ≥1 prekey survives. When the pool
drains to empty, allocation **restarts at 1**, reissuing ids already handed
out in bundles with *different* key material. Proven empirically with a
throwaway probe test (since removed):
```
first batch ids:  [1, 2, 3, 4, 5]
second batch ids: [1, 2, 3, 4, 5]     <-- ids reissued
id 1 key changed: true                <-- different key under the same id
```
Why it matters: X3DH addresses a one-time prekey **by id**, so a peer holding
an older bundle does DH against a key this device no longer has under that
id. Its first message becomes permanently undecryptable and the session
silently fails to establish.

Note this is **as much a specification defect as an implementation one** —
§6 of this very task file suggested `max(existing ids) + 1` verbatim, and the
builder implemented the contract as written. §8's test plan never named the
drained-pool case, so nothing prompted a test for it.
`test_EARS_SEC_3c_replenish_never_reuses_a_consumed_gap` passes precisely
because it leaves id 5 alive. Not blocking this merge: the defect is latent
while §4 keeps `replenishOneTimePreKeys()` unwired and nothing consumes
prekeys. **E03-T03 makes it live** (`SessionCipher.decryptPreKeyMessage`
removes the prekey on use), hence `E03-B01 blocks E03-T03`.
