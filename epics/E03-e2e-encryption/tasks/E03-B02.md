# E03-B02 · Every peer gets the same one-time prekey

## Severity: S2 (major function broken, no workaround)
Two distinct impacts, both live today (unlike E03-B01, which was latent
until T03 landed):

1. **Functional (the severe one).** The first inbound message from every peer
   after the first is **permanently undecryptable**. `SessionBuilder.processV3`
   calls `loadPreKey(message.getPreKeyId())`, the prekey was already deleted
   when peer #1's message consumed it, and the store raises
   `InvalidKeyIdException`. The plaintext is unrecoverable — the sender's
   ratchet has already advanced. Indistinguishable at the call site from a
   transport fault.
2. **Protocol (bounded but real).** The same one-time prekey **private key**
   is used as the `DH4` input for two or more independent X3DH handshakes,
   so the "one-time" property ADR-0003 selected X3DH for does not hold. This
   does **not** let one peer read another's traffic (each session's root key
   still mixes a distinct ephemeral `EK_A` and identity `IK_A`), which is why
   this is S2 and not S1 — but it removes the initial-message
   forward-secrecy hardening that the one-time prekey exists to provide, and
   it extends how long that private key stays resident.

Severity per `skills/bug-sweep` is the reviewer's call. **Priority is the
human's** (`bug_priorities` gate, rule 3) — **resolved 2026-08-27: P1**, per
the reviewer's advisory and confirmed by the human alongside the schema
decision below. It does not leave E03; E06 (the wedge) is a multi-contact
messaging surface, and shipping this means the second contact who ever
writes to a device is silently unreachable.

## Repro (exact, from a fresh state — reviewer-verified 2026-08-27)
1. Create three independent devices, each with its own in-memory
   `AppDatabase` + `DriftSignalProtocolStore` + `IdentityService`, each having
   run `ensureLocalIdentity()`, `ensureSignedPreKey()`,
   `replenishOneTimePreKeys()` (pool = 20 prekeys). Call them Alice, Bob,
   Carol.
2. `final forBob = await alice.getLocalPreKeyBundle();`
3. `final forCarol = await alice.getLocalPreKeyBundle();`
4. Compare `forBob.getPreKeyId()` and `forCarol.getPreKeyId()`.
5. `await bob.crypto.establishSession(aliceAddr, forBob);`
   `await carol.crypto.establishSession(aliceAddr, forCarol);`
6. Bob sends: `bob.crypto.encrypt(aliceAddr, 'hi from bob')`; Alice decrypts
   it (`alice.crypto.decrypt(bobAddr, ...)`) — succeeds, and consumes the
   prekey via the library's internal `removePreKey`.
7. Carol sends: `carol.crypto.encrypt(aliceAddr, 'hi from carol')`; Alice
   attempts `alice.crypto.decrypt(carolAddr, ...)`.

### Expected
**E03-T02 §6, this epic's own binding risk note** (quoted verbatim in
`E03-B01.md:63-67`):
> "One-time prekey id allocation must never reuse an id still referenced by
> an in-flight (not-yet-consumed) bundle handed to a peer earlier — track the
> next-free id explicitly, don't reuse gaps left by consumed/removed
> prekeys."

E03-B01 fixed the *allocation* half of that invariant (the counter). The
*distribution* half was never fixed: handing prekey id 1 to Carol while
Bob's bundle naming id 1 is still in flight is precisely "an id still
referenced by an in-flight bundle handed to a peer earlier".

Also **E03-T02 §3**: `getLocalPreKeyBundle()` assembles "one *unconsumed*
one-time prekey ... **for a remote peer** to consume via X3DH" — per-peer,
singular. And EARS-SEC-3 / FR-SEC-004: X3DH per ADR-0003, whose one-time
prekey is by definition consumed by one handshake.

Step 4: the two ids must differ. Step 7: Carol's message must decrypt to
`'hi from carol'`.

### Actual (reviewer-verified, `flutter test`, 2026-08-27)
```
PROBE1 ids: bob=1 carol=1                       <-- identical id AND key material
PROBE1b prekeys left: 19                        <-- 19 unused prekeys sitting in the pool
InvalidKeyIdException - No such one-time prekey: 1
  package:nexora/core/crypto/drift_signal_store.dart 175:7   DriftSignalProtocolStore.loadPreKey
  package:libsignal_protocol_dart/src/session_builder.dart 69:38  SessionBuilder.processV3
  package:libsignal_protocol_dart/src/session_builder.dart 47:30  SessionBuilder.process
```
Note the second line: this is **not** pool exhaustion. 19 unused prekeys were
available; the selection logic simply never advanced past the first row.

## Root cause
`lib/core/crypto/identity_service.dart:119-126`

```dart
final oneTimeRows = await _db.select(_db.signalOneTimePrekeys).get();
if (oneTimeRows.isEmpty) {
  throw StateError(
    'No one-time prekeys available '
    '(call replenishOneTimePreKeys() first).',
  );
}
final oneTimeRecord = PreKeyRecord.fromBuffer(oneTimeRows.first.record);
```

`oneTimeRows.first` — an unordered, unfiltered select, take row zero. The
method is **stateless with respect to what it has already handed out**. It
advances only as a side effect of someone else's consumption (the library's
`removePreKey` during a successful inbound X3DH), so the pointer moves once
per *successful* establishment rather than once per *bundle issued*. Issue N
bundles before the first is consumed and all N name the same prekey.

### Why no task's tests caught it
This is a textbook seam. T02 owns assembly and its test
(`identity_service_test.dart:286-312`,
`test_bundle_shape_contains_current_material`) calls
`getLocalPreKeyBundle()` **exactly once** and then deliberately asserts the
prekey is still present (`:311`) — encoding the "T03 consumes it" division of
labour, which is correct, but never asking what a *second* call returns. T03
owns consumption and its tests (`crypto_service_test.dart`) give every party
its own device, so Bob's bundle and Carol's bundle come from different stores
and cannot collide. One device, two peers is the case that belongs to neither
`files:` fence.

## Fix direction (not prescriptive — the implementer decides within it)
`getLocalPreKeyBundle()` must not return a prekey it has already handed out.
Options, in the implementer's judgement:

1. **Reserve-on-issue** — add an `issued_at`/`issued` marker to the prekey row
   and select the oldest *un-issued* one, marking it issued before returning.
   Most faithful to Signal's server-side "each fetch pops a prekey" model.
   Requires a schema change → 🧍 rule 3 gate (see below).
2. **Monotonic issue cursor** — a `next_issued_one_time_prekey_id` counter in
   the existing `crypto_counters` table (E03-B01's table), selecting the
   lowest live prekey id `>=` the cursor and advancing it. Also a schema
   change, but reuses the table and the atomic-transaction pattern B01 already
   established and tested.
3. **No schema change** — select the lowest live id strictly greater than the
   highest id issued so far, where "issued so far" is derived from... nothing
   durable exists. **Do not ship an in-memory-only cursor**: it resets every
   app launch, which reintroduces the bug at exactly the restart boundary
   (same reasoning as E03-B01's rejected Option 2).

Whichever is chosen, two properties are non-negotiable:
- **Issuing must be atomic** — same transaction discipline as
  `allocateOneTimePreKeyIds` (`drift_signal_store.dart:220-241`), so two
  concurrent bundle requests cannot receive the same prekey.
- **Pool-empty must stay a `StateError`** with the existing message
  (`identity_service_test.dart:334-351` asserts on it). Note that "empty" now
  means "no *un-issued* prekey left", which is reachable much sooner than
  before — the fix should say in its Run log whether
  `replenishOneTimePreKeys()` should be invoked from `getLocalPreKeyBundle()`
  when the un-issued pool runs low, or whether that stays the caller's
  (E05/E06's) job per T02 §4. Reviewer's view: leave the call site to the
  caller, but make the exhaustion mode obvious rather than silent.

## 🧍 Gate — rule 3

Rejected: Option 1 (per-row `issued` marker) — more new state, more call

future expiry/reclaim policy) is real but not needed to close this bug;
revisit if/when that policy gets built. Rejected: Option 3 (in-memory
cursor) per the task file's own reasoning — resets on restart, reintroduces
the bug at the boundary.

### What this task does NOT do

- Does NOT touch `lib/core/crypto/crypto_stub.dart`, the store's

the caller**. The error message and the dartdoc both instruct the caller to
"call `replenishOneTimePreKeys()` first", which in precisely this state
provably does not help.

This is not the documented leak follow-up (that one is gradual capacity
loss, correctly deferred). It is a hard functional stop reachable *today*,
with no transport, by the ordinary act of adding 20 contacts before any of
them answers — and E06 is a multi-contact surface. Untreated, this task
would have traded "the second peer is undecryptable" for "the 21st bundle
never issues", same severity class, and the epic would have gone through
its human gate with it.

**Non-blocking observation, for the retro not this task.** The issue cursor
inherits B01's accepted id-space wrap edge case, and inherits it in a
harsher form: at the `_preKeyIdSpaceModulus` boundary, allocation wraps ids
back to 1 while the issue cursor stays high, so `issueOneTimePreKey()` would
find nothing at or above the cursor and issuance would raise `StateError`
permanently rather than merely reusing an id. ~16M prekeys away and
explicitly accepted for v1 in B01, so not a gate item — but whoever builds
the expiry/reclaim policy should handle wrap in the same change, since both
want the same "re-lower the cursor over still-live rows" primitive.

**Systemic note (rule 8, feeds `skills/retro`).** Three findings across
B01, B02's sweep and this review are all one root pattern: **a durable
counter was introduced, and a second reader of the same underlying data
kept deriving its answer from the live rows instead of the counter.** B01:
allocation derived from `max(live ids)+1`. B02: issuance derived from
`rows.first`. R2: pool depth derived from `rows.length`. Each fix added a
cursor without auditing the *other* readers of `signal_one_time_prekeys`
against it. The lesson is not "be careful with counters" — it is: **when a
counter becomes the authority for some property of a table, enumerate every
existing reader of that table and decide, per reader, whether it must now
consult the counter.** A grep for `select(_db.signalOneTimePrekeys)` at
B02 implementation time would have surfaced R2 immediately. Worth promoting
to a rule, and it is mechanizable as a hook.
