# E10-B11 · The listener can silently never start

## 1. Goal

A device with the app open can receive a message, without its user having
first tapped `Discover` on the Devices tab.

## 2. The defect

`BluetoothTransport.ensureListening()` opens this device's RFCOMM server
socket. It is reached only from `connect()` and `doStartDiscovery()`, and
**this is correct** — E04 documents the intent plainly and handles the
permission race on purpose (`startDiscovery()` stashes
`pendingPermissionAction = { doStartDiscovery() }`). The Dart side is what
is supposed to call `startDiscovery()` automatically. It does, but along a
path that can silently do nothing at all:

1. `BackgroundLifecycleObserver.start()` **deliberately does not** call
   `_applyPlan()` synchronously. That is intentional and right: it avoids
   acting on the optimistic `allClearPowerState()` default before a real
   reading arrives (`E10-B02`'s own reasoning, quoted in that method).
2. So the **first ever** `_applyPlan()` depends entirely on
   `_refreshPowerStateOnResume()` — whose body is wrapped in
   `try { … } catch (_) { }`. If `_service.powerState()` throws,
   `_onPowerStateChanged` is never called, `_applyPlan()` never runs,
   `transport.startDiscovery()` is never called, and **nothing listens**.
3. The catch block's comment says *"the stream subscription remains the
   fallback source of truth."* **That premise is false**, and the same file
   contradicts it twenty lines earlier: the power-state stream is *"fed by
   broadcast receivers that fire on TRANSITIONS only."* With no transition,
   nothing ever arrives. There is no fallback.
4. Independently, `_applyPlan()` latches its decision —
   `if (_discoveryAllowed == plan.discoveryAllowed) return;` — and
   `startDiscovery()`'s own failure is swallowed by
   `.catchError((Object _) {})`. So a `startDiscovery()` that failed is
   recorded as though it succeeded, and no later plan retries it.

Two independent ways to end up permanently deaf, neither of which produces
any user-visible signal. The Dashboard reads `No peers nearby`, which a user
reads as "nobody is around".

### Why S1

The device cannot receive messages at all. That is the product's primary
function, and there is no in-app indication that anything is wrong. The only
workaround — tap `Discover` — is undiscoverable, and nothing on screen
suggests it.

## 3. What this task does

1. **`_refreshPowerStateOnResume()` no longer swallows a failure into
   silence.** On failure it applies a plan from the last known power state
   rather than leaving the app in a state where no plan is ever applied.
   Doing nothing is not the safe option here: the "safe" reading was chosen
   to avoid an unbidden `startDiscovery()`, but its actual consequence is a
   device that can never receive anything.
2. **A failed `startDiscovery()` no longer latches.** `_discoveryAllowed` is
   cleared when the call fails, so the next plan retries instead of
   believing discovery is already on.

## 4. What this task does NOT do  ← the scope fence

- **Does NOT touch E04.** `BluetoothTransport.kt` is unmodified. The
  freeze-exemption request raised against it was **withdrawn** —
  `docs/E04-freeze-exemption-request-inbound-listener.md` records why.
- **Does NOT change `BackgroundPolicy`** or any tick interval, threshold or
  power band.
- **Does NOT remove `start()`'s deliberate "no synchronous `_applyPlan()`"
  property**, which exists for a good reason (`E10-B02`).
- **Does NOT add UI** telling the user the listener is down. That is a real
  gap, but a separate, design-bearing task.

## 7. Risks
- **An unbidden `startDiscovery()`** — the exact risk `start()`'s comment
  guards against. Accepted deliberately and narrowly: it now happens only
  when the one-shot read **failed**, i.e. when the alternative is applying
  no plan at all. The normal path is unchanged.

## 9. Open Questions
- **OQ-E10-B11-1 — should a device that cannot listen say so?** Right now
  the Dashboard shows `No peers nearby` whether the mesh is genuinely empty
  or this device is deaf. Those are different states and the app cannot
  currently tell the user which one it is in. Surfacing it is design-bearing
  copy, so nothing is invented here.
