# E10-B06 · Six teardown methods with no caller

## The inventory (verified at epic close, 2026-09-04)

A repo-wide grep of `lib/` for callers:

| method | file:line | caller in `lib/` |
|---|---|---|
| `CallSignaling.dispose()` | `lib/core/calls/call_signaling.dart:1093` | none |
| `PrekeyExchange.dispose()` | `lib/core/messaging/prekey_exchange.dart:663` | none |
| `GroupMembershipService.dispose()` | `lib/features/groups/domain/group_membership_service.dart:733` | none |
| `StorageNotificationSource.dispose()` | `lib/core/notifications/sources/storage_notification_source.dart:121` | none |
| `NotificationDispatcher.stop()` | `lib/core/notifications/notification_dispatcher.dart` | none |
| `BackgroundLifecycleObserver.stop()` | `lib/app/bindings.dart` (T10, new) | none |

Plus the root: `MessagingStack.dispose()`
(`lib/core/messaging/messaging_stack.dart:605`) documents itself as
*"Test-only — the app process never calls this"*, which is why none of the
six was ever going to be reached.

## The assessment this bug exists to record

The tracker carried four separate entries describing this as a growing
resource-leak pattern. At the epic sweep, with nowhere left to hide behind a
task boundary, the honest finding is: **it is not a leak, and it is not
becoming one.**

Every one of these objects is a `Get.put(..., permanent: true)` singleton
constructed exactly once, in `AppBinding`, per Dart isolate. `AppBinding`
runs from `main()`. `main()` runs once per isolate. E10-T08's engine
retention means the isolate now *outlives* the Activity rather than being
recreated with it — `MainActivity.provideFlutterEngine` returns the cached
engine and `main()` is not re-entered. So the count of each of these objects
is one, for the life of the process, and it never grows. When the process
does end, the OS reclaims everything a `dispose()` would have.

That is a materially different finding from "five instances of a leak
pattern", and it is worth writing down rather than carrying forward an
eighth time. The genuinely unbounded leak this epic *did* introduce is on the
Kotlin side and is filed separately as **`E10-B04`** — that one grows once
per app reopen and does need fixing.

So this is filed as **S4 hygiene**, deliberately: the code is correct, the
methods are unreachable dead-ish code, and the reason to close it is that a
`dispose()` nobody calls is a `dispose()` nobody maintains — the next
refactor that makes one of these load-bearing will find it untested and
never wired. It is the `L-process-007` unwired-capability shape
(`E09-B02`/`E09-B06`), which is real, just not urgent here.

## Repro
`grep -rn "\.dispose()\|\.stop()" lib/ --include=*.dart | grep -v "\.g\.dart"`
and confirm no call site resolves to any of the six rows above.

## Expected
Either a real app-lifecycle teardown path calls them, or they do not exist.

## Actual
They exist, are individually correct and idempotent, are individually
documented as unwired, and are unreachable.

## Severity
**S4** — no runtime symptom, no growth, no user impact. Correctness and
maintainability only.

## Priority
**P4** — set under the decision authority explicitly delegated by the human
for this session. Rationale: nothing is broken; the cost of the current state
is future confusion, not present failure. Explicitly **not** P2 despite four
tracker entries urging action — the entries were written from a "five
instances of a leak" reading that this sweep has now falsified. Backlog is
the honest place for it. Fix it when something makes teardown real (the
headless-entrypoint decision in `E10-B05` is the most likely trigger, since a
second composition root would make "who tears this down" a live question for
the first time).

## Fix direction
One composition-root pass, not six fast-follows. Two shapes; pick one and
say why:
- **Wire them.** Give `AppBinding` a single `Future<void> disposeAll()` that
  calls all six plus `MessagingStack.dispose()` in dependency order
  (observer → dispatcher → sources → stack), and call it from the one real
  teardown hook Flutter offers. Note there is currently **no such hook** in
  this app — that is the whole reason the gap exists — so this shape
  requires inventing app-lifecycle scaffolding, which is what every task
  correctly declined to do unilaterally.
- **Or delete them** and say plainly in each file that the process, not the
  object, is the unit of teardown — which is what
  `messaging_stack.dart:600-604` already says.

The second shape is smaller, more honest about how the app actually works,
and does not add scaffolding nothing calls. But it removes the seam a future
headless entrypoint would want. **If `E10-B05` resolves toward option (a) (a
headless Dart entrypoint), do the first shape; otherwise prefer the second.**
Sequence this after B05, not before.

## Regression test (write it first)
Whichever shape is chosen, the test is the same in structure: build an
`AppBinding`, run the teardown path (or assert none exists by design), and
assert no `StreamSubscription`, `Worker` or `Timer` created by the binding is
still active afterward. If the delete shape is chosen, the "test" is the
absence of the methods plus an updated doc comment — say so rather than
writing a test that asserts nothing.

## What this fix does NOT do
- Does **not** touch `MainActivity.kt` or any Kotlin file — the real,
  unbounded native leak is `E10-B04`'s and must not be conflated with this.
- Does **not** change what any of the six methods *do*. They are individually
  correct; only their reachability is in question.
- Does **not** add a headless Dart entrypoint or a second composition root
  (`E10-B05`, planner-owned and blocking).
- Does **not** change `MessagingCoordinator`'s tick, its interval, or the
  one-tick invariant.
- Does **not** change `Get.put(..., permanent: true)` registration for any
  object outside the six listed above.
