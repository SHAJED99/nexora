# E10-B03 · Five notification classes, two distinct strings

## The defect

```dart
// lib/core/notifications/notification_policy.dart:112-122
_Copy _copyFor(NotificationFacts facts, NotificationPrivacyLevel level) {
  switch (facts.category) {
    case NotificationCategory.message:
      if (level == NotificationPrivacyLevel.hidden) {
        return const _Copy('NEXORA', 'New message');
      }
      return _Copy(facts.peerDisplayName ?? 'NEXORA', 'New message');
    default:
      return const _Copy('NEXORA', 'Notification');   // <-- everything else
  }
}
```

E10 ships five of `FR-NOTIFY-001`'s nine classes. Exactly one of them —
`message` — has copy. The other four all fall through `default:`:

| class | task | §5 contracted copy | what actually posts |
|---|---|---|---|
| `incomingCall` | T04 | `Incoming call` / `<peerDisplayName>` \| `Someone is calling` (`E10-T04.md:108`) | `NEXORA` / `Notification` |
| `connectionRequest` | T05 | device-id short form under `senderOnly` (`E10-T05.md:105`) | `NEXORA` / `Notification` |
| `groupEvent` | T06 | `NEXORA` / `Group activity` (`E10-T06.md:108`) | `NEXORA` / `Notification` |
| `storageWarning` | T07 | `Storage almost full` / `NEXORA is running low on local …` (`E10-T07.md:107`) | `NEXORA` / `Notification` |

In the shade, an incoming call, a stranger's connection request, a group
membership change and a storage warning are the same notification. The
Android *channels* are correctly distinct (`NotificationChannels.kt`), which
is why per-category muting and importance work — but the user cannot tell
from the notification itself what happened, and an incoming call in
particular is indistinguishable from a storage warning.

## Why it survived ten task reviews

Every task did the right thing under rule 6 and the sum was still wrong.
T04 disclosed it (`E10-T04.md:288-293`, `OQ-E10-T04-2`), T06 disclosed it
(`E10-T06.md:209-216`), and both routed it forward. **T05 and T07 declare
copy in their own §5 and never disclose that it did not ship** — a minor
undisclosed contract non-delivery, transitively covered by T04/T06's
carry-forward but never stated in those two files. `notification_policy.dart`
belongs to T03, which was built before any of the four classes existed.

## Repro
1. Fresh `AppDatabase`, default settings (all categories enabled, privacy
   `hidden`).
2. `NotificationPolicy.resolve(NotificationFacts(category:
   NotificationCategory.incomingCall, ...))`.
3. Read the returned `NotificationRequest.title` / `.body`.

## Expected
`FR-NOTIFY-001` gives each class its own notification. `E10-T04.md:108`'s own
§5: title `Incoming call`, body `<peerDisplayName>` or `Unknown device`.

## Actual
`title: 'NEXORA', body: 'Notification'` for `incomingCall`,
`connectionRequest`, `groupEvent` and `storageWarning` alike.

## A second, latent defect in the same method — read this before fixing

`resolve()` downgrades `full` privacy to `senderOnly`
(`notification_policy.dart:86-92`) and `test_EARS_NOTIFY_7_full_downgrades_
to_sender_only` claims to prove it. **The sweep's own probe deleted the
downgrade line and the entire notification suite stayed green** (49/49).

The reason is structural: `_copyFor` has no `full` branch, so `full` and
`senderOnly` currently render identically and the downgrade is behaviourally
a no-op. It is safe **today** only because of that. The moment this fix adds
per-category branches to `_copyFor`, the downgrade in `resolve()` becomes the
only thing standing between `full` privacy and a decrypt path — and no test
protects it. `E06-T09.md:64-68` forbids that path by name, `OQ-E10-2` tracks
it, and `EARS-NOTIFY-2` is a `SHALL NOT`.

So this fix must land a test that actually fails when the downgrade is
removed, not just extend the copy.

## Severity
**S3** — every notification is still posted, on the right channel, at the
right importance, tappable, and privacy-correct. The content is wrong and
uninformative; the user's workaround is to open the app. Not S2: no class is
missing or misrouted. Not S4: an incoming call the user cannot identify as a
call is more than cosmetic.

## Priority
**P2** — set under the decision authority explicitly delegated by the human
for this session. Rationale: this is the epic's most user-visible shortfall,
the copy is already written down in four task files, and the fix is confined
to one method. Weighed against P1: no function is broken and `OQ-E10-1`
(no design-approved copy for any notification surface) is a standing human
gate that this fix does not close, so it is not urgent enough to preempt.
Weighed against P3: closing E10 with `FR-NOTIFY-001`'s classes
indistinguishable would make "five notification classes shipped" a claim the
build does not support.

## Fix direction
- Extend `_copyFor` with a branch per shipped category, using each owning
  task's §5 copy **verbatim** (T04:108, T05:105, T06:108, T07:107). Do not
  invent strings for the four classes E10 does not build
  (`voiceMessage`, `ptt`, `trustRequest`, `securityEvent` —
  `OQ-E10-3`/`OQ-E10-6`/`OQ-E10-7`); keep the `default:` fallback for them.
- Honour `hidden` vs `senderOnly` per class the way `message` already does:
  under `hidden`, no peer name and no group name. `NotificationFacts` carries
  no plaintext and must not gain a field that could
  (`notification_policy.dart:21-24`).
- Mark the copy **provisional**, in this file, the same way ADR-0007 §S4 and
  `NotificationChannels.kt` already mark theirs — `OQ-E10-1` is still open
  and none of this is design-approved.
- `NotificationFacts` does not carry `GroupEventNotice.kind`
  (`E10-T06.md:209`), so `groupEvent` can only render its §5 generic
  `Group activity`, not a per-kind string. Do **not** add a `kind` field to
  chase that — say so in the run log and leave it to a design pass.

## Regression test (write it first)
- One test per shipped category asserting the exact §5 title and body, at
  both `hidden` and `senderOnly`. Must fail on today's code (all four
  currently return `NEXORA`/`Notification`).
- **A falsifiable privacy test**: set privacy to `full`, resolve a
  notification, and assert the output is exactly the `senderOnly` shape.
  Then verify by hand that deleting `notification_policy.dart:91`
  (`level = NotificationPrivacyLevel.senderOnly;`) makes this test **fail**,
  and record that check in the run log. If the test still passes with the
  line gone, it is the wrong test — the sweep already proved that version
  proves nothing.
- Re-assert `test_EARS_NOTIFY_7`'s existing "the crypto double was never
  called" guarantee still holds with the new branches in place.

## What this fix does NOT do
- Does **not** add a decrypt path to `notification_policy.dart` or to any
  repository, does **not** import anything that can decrypt, and does **not**
  implement `full` privacy previews (`OQ-E10-2`, `E06-T09.md:64-68`).
- Does **not** add a field to `NotificationFacts` (in particular not
  `GroupEventNotice.kind`, and never anything holding plaintext).
- Does **not** touch any notification *source* (`sources/*.dart`),
  `notification_dispatcher.dart`, `notification_service.dart`,
  `bindings.dart`, or any Kotlin file. The copy table is one method.
- Does **not** change the foreground-service notification's provisional copy
  (`ForegroundMeshService.kt:169-170`, ADR-0007 §S4).
- Does **not** create a `design/gaps.md` entry or claim design approval —
  `OQ-E10-1` stays open and human-owned.
- Does **not** add copy for `voiceMessage`, `ptt`, `trustRequest` or
  `securityEvent`. Those classes have no producer in this build.
