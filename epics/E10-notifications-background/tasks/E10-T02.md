# E10-T02 · Notification preferences — schema + repository

## 1. Goal
Make `FR-NOTIFY-002` ("notification privacy shall be configurable") real in
the data: a per-category on/off switch and one privacy level, persisted,
defaulting to the conservative reading, so no notification can leak content
the user never opted into.

## 2. Business logic
- **FR-NOTIFY-002**: privacy is *configurable*. Three levels, closed set:
  - `full` — sender name and message preview,
  - `senderOnly` — who, not what,
  - `hidden` — neither ("New message").
  **Default is `hidden`**, and that default is load-bearing, not timid: see
  the constraint below.
- **Plaintext must not leave the screen layer.** `E06-T09.md:64-68` states
  it directly — "decryption for display happens in the screen layer …
  putting decryption in a repository that a future background job might call
  is how plaintext ends up somewhere nobody expected." E10 *is* that future
  background job. A `full` privacy level therefore has **no supported
  mechanism today** and this task stores it as a value while `E10-T03`
  refuses to act on it (`OQ-E10-2`). Storing the enum is not the same as
  honouring it, and the difference is written down rather than assumed.
- **FR-NOTIFY-001**: nine user-facing categories, each independently
  switchable, defaulting to enabled. `backgroundService` is **not** a user
  preference — Android requires that notification whenever the service runs —
  so it is deliberately absent from this table.
- ADR-0001 / `docs/conventions.md`: Drift, enums stored by `.name` string
  (never index), a versioned migration with an explicit `fromNtoM` step.

## 3. What this task does
- `notification_tables.dart`:
  - `NotificationCategorySettings` — `category` TEXT PK (the
    `NotificationCategory.name`), `enabled` BOOL NOT NULL DEFAULT true.
  - `NotificationPreferences` — `id` INT PK (always `0`, singleton row),
    `privacyLevel` TEXT NOT NULL DEFAULT `'hidden'`.
- `database.dart`: register both tables, bump `schemaVersion` **14 → 16**
  (see §6 — 15 belongs to `E09-T01`), add the `from15to16` migration step
  creating both tables and seeding the singleton row plus one row per
  user-facing category, all enabled.
- `database.g.dart`: regenerated with `build_runner`, never hand-edited.
- `NotificationSettingsRepository` — the read/write surface (see §5),
  modelled on `StorageSettingsRepository`.

## 4. What this task does NOT do
- Does **not** post, build or suppress any notification. No import of
  `lib/core/notifications/notification_service.dart` from this task's code —
  it is a settings store, and `E10-T03` is the only consumer.
- Does **not** add a settings screen, controller or binding. The Notifications
  sub-screen has **no design source** (`OQ-E10-1`); rule 2 makes it
  unshardable, so after this task the toggles exist and can only be changed
  programmatically or in the database.
- Does **not** implement quiet hours, per-conversation muting, LED/vibration
  or "silent modes". `settings.md` element 41's copy promises them; no FR
  asks for them; inventing them here would be inventing a requirement
  (rule 1).
- Does **not** decrypt anything, ever, for any reason.
- Does **not** touch any other table, migration step or existing column.
  Do not "tidy" a neighbouring migration while in the file.
- Does **not** renumber, edit or reorder `E09-T01`'s `from14to15` step.

## 5. Contract

### Data
Migration `from15to16` (schemaVersion 15 → 16), forward-only, additive:
```
CREATE TABLE notification_category_settings (
  category      TEXT    NOT NULL PRIMARY KEY,
  enabled       BOOLEAN NOT NULL DEFAULT 1
);
CREATE TABLE notification_preferences (
  id            INTEGER NOT NULL PRIMARY KEY,   -- always 0
  privacy_level TEXT    NOT NULL DEFAULT 'hidden'
);
```
Seed inside the same step: one `notification_category_settings` row per
user-facing category (`message`, `voiceMessage`, `ptt`, `incomingCall`,
`connectionRequest`, `trustRequest`, `groupEvent`, `securityEvent`,
`storageWarning`) with `enabled = 1`, and `notification_preferences(0,
'hidden')`.
No backfill of existing data (nothing existing refers to these). Reversible
by dropping both tables; no other table is altered, so a downgrade loses only
preferences.
🧍 **Schema changes are a human gate** (`db_schema_migration`) — see
`OQ-E10-T02-1`.

### Functions
```yaml
- signature: "NotificationSettingsRepository.isEnabled(NotificationCategory category) -> Future<bool>"
  returns: "the stored flag; true when no row exists (fail-open for a category added after this migration)"
  purpose: "The single question E10-T03's policy asks before posting"

- signature: "NotificationSettingsRepository.setEnabled(NotificationCategory category, bool enabled) -> Future<void>"
  purpose: "Upsert one category's flag"

- signature: "NotificationSettingsRepository.privacyLevel() -> Future<NotificationPrivacyLevel>"
  returns: "the singleton row's level; `hidden` when the row is missing — never `full` by accident"
  purpose: "Fail-safe read of the privacy setting"

- signature: "NotificationSettingsRepository.setPrivacyLevel(NotificationPrivacyLevel level) -> Future<void>"
  purpose: "Upsert the singleton row"

- signature: "NotificationSettingsRepository.watchEnabled(NotificationCategory category) -> Stream<bool>"
  purpose: "Drift-backed watch, so a future settings screen needs no polling"
```
`NotificationPrivacyLevel` (`enum { full, senderOnly, hidden }`) is declared
in `notification_tables.dart` and stored by `.name`; an unrecognised stored
string resolves to `hidden`, never throws, never guesses upward.

## 6. Risks
- **Schema-version collision with `E09-T01`, which is in flight.**
  `schemaVersion` is `14` today; `E09-T01` (a sibling epic, actively being
  built) claims `15`. This task therefore claims `16` and carries
  `depends_on: [E09-T01]` so `database.dart`/`database.g.dart` are edited by
  one task at a time. **If E09 is deprioritised or reordered, this task
  becomes `from14to15` and the dependency drops** — that is a planner
  decision at dispatch, not a builder's improvisation. Check the actual
  `schemaVersion` before writing the step.
- `database.g.dart` is generated: run `dart run build_runner build
  --delete-conflicting-outputs` and commit what it produces. A hand-edited
  `.g.dart` is a review reject.
- Fail-open vs fail-safe are *deliberately different here*: an unknown
  **category** defaults to enabled (a missing notification is worse than an
  extra one), an unknown **privacy level** defaults to hidden (a leaked
  preview is worse than a vague one). Do not unify them.
- The migration test must build the *previous* schema by hand and migrate,
  the way `database_migration_test.dart` already does — asserting on a
  freshly-created v16 database proves nothing about upgrades.
