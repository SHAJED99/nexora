# E10-T08 · Android foreground service

> ✅ **Unblocked 2026-09-04.** `ADR-0007` is `accepted` — option 1 (foreground
> service holding a retained `FlutterEngine`), exactly as this contract was
> written for. Two changes from the version originally sharded: **S3 (boot
> restart) is now in scope** (see the amended §3/§4/§5/§8 below) and **S4
> (notification copy) ships provisional, not blocking** — both resolved in
> the ADR's Decision section. `status` moved `blocked` → `todo`.

## 1. Goal
Make the mesh keep meshing when the phone is in a pocket: keep the app
process alive and legal in the background so the one existing coordinator
tick keeps running.

## 2. Business logic
- **FR-PLAT-001**: background operation — peer discovery, message
  synchronization, network maintenance — "where permitted by Android". Today
  none of it survives the app being closed (`E06-T06.md:382-384`: "with the
  app closed, nothing forwards and nothing reclaims").
- **FR-PLAT-003 + ADR-0004**: the foreground service is a system-sensitive
  native component; Flutter drives it through a Pigeon interface, never
  directly.
- **The one-tick invariant is binding.** `E08-T06.md:119-120` refused to add
  a second timer *because this epic owns background operation*, and
  `E08-T06.md:127-131` forbids changing the tick's semantics, ordering or
  re-entrancy coalescing. This task therefore adds **no scheduler at all** —
  it keeps the process alive so `MessagingCoordinator`'s existing
  `Timer.periodic` keeps firing. Any design that introduces a second driver
  is the wrong implementation of this task, whatever it scores on battery.
- **NFR-SEC-001 follows for free**: with the process alive,
  `reclaimPayloads()` — the retention guarantee — stops depending on someone
  looking at the screen. `E10-T10` proves that with a test; this task makes
  it possible.
- Android requires an ongoing notification for a foreground service.
  `E10-T01` already created the LOW-importance `backgroundService` channel,
  so this task adds no channel plumbing.

## 3. What this task does
- `pigeons/background.dart` — `BackgroundApi` host + `BackgroundEventsApi`
  flutter API (see §5), with the regeneration header, generated into both
  languages.
- `ForegroundMeshService.kt` — a `Service` that `startForeground()`s with the
  `backgroundService` notification, caches/holds the `FlutterEngine` so the
  Dart isolate survives Activity destruction, returns `START_STICKY`, and
  stops cleanly on request. Emits `onServiceStateChanged` to Dart.
- `BackgroundApiHost.kt` — `startService`, `stopService`, `isServiceRunning`.
- `MainActivity.kt` — registers the background host alongside the transport
  and notification hosts; ensures the engine is cached under a known id and
  **not** destroyed in `cleanUpFlutterEngine` while the service holds it.
- `AndroidManifest.xml` — `FOREGROUND_SERVICE`, the typed permission per
  ADR-0007 §S1, and the `<service>` element with its
  `android:foregroundServiceType`.
- `background_service.dart` / `background_stub.dart` — the Dart façade and
  its in-memory test double, mirroring `E10-T01`'s pair.
- **ADR-0007 §S3, now in scope:** a manifest-registered `BootReceiver.kt`
  (`RECEIVE_BOOT_COMPLETED`) that calls `startForegroundService()` on the
  `ForegroundMeshService` **only if** the same persisted "messaging active"
  flag that already gates the foreground-path start was on at last shutdown
  — reuse that flag; do not invent a second one. A manifest-declared
  `BOOT_COMPLETED` receiver calling `startForegroundService()` is a
  documented exemption to Android's background-service-start restriction;
  confirm this still holds for the project's target API range and verify on
  a real device per §8 Manual — if a specific OEM is observed to suppress
  it, record that honestly rather than silently dropping the feature.
- The `backgroundService` notification's copy/icon (ADR-0007 §S4) is
  **provisional**: ship the plainest possible string (e.g. "Nexora is
  running — relaying messages") and the existing app icon, and mark it in
  §9 Self-review as provisional pending a `design/gaps.md` pass on
  `settings.md`'s `Notifications`/`Battery` rows.

## 4. What this task does NOT do
- Does **not** add a `Timer`, `WorkManager` job, isolate, or any second
  periodic driver. §2, and it is the single most likely wrong turn here.
- Does **not** modify `MessagingCoordinator`, its tick, its interval, its
  ordering or its re-entrancy guard. `E10-T10` owns cadence.
- Does **not** request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` or show a
  battery-exemption prompt — ADR-0007 §S2, carried as `OQ-E10-4`. Asking for
  an exemption before there is on-device evidence the service is being killed
  is the wrong order, and it is a Play-policy-sensitive permission.
- ~~Does not add `RECEIVE_BOOT_COMPLETED` or a boot receiver~~ — **superseded:**
  ADR-0007 §S3 is now decided and in scope (see §3). `START_STICKY` still
  covers process death only, not reboot, which is exactly why the receiver
  is needed.
- Does **not** add `ACCESS_BACKGROUND_LOCATION` or keep location running in
  the background. `E09-T05.md:112-116` fenced that to E10; it is a heavier
  permission with Play review implications and it is **not built here** —
  `OQ-E10-7`.
- Does **not** change any Bluetooth permission element, `maxSdkVersion` cap,
  `neverForLocation` flag, or anything in `.../transport/`.
- Does **not** decide when to start the service. Wiring the lifecycle
  trigger is `E10-T10`; this task exposes `start()`/`stop()` and proves them.
- Does **not** implement OEM-specific autostart guidance or copy.

## 5. Contract

### Pigeon schema (`pigeons/background.dart`)
```dart
enum ServiceState { stopped, starting, running, stoppedBySystem }

@HostApi()
abstract class BackgroundApi {
  bool startService();          // false when it could not be started
  void stopService();
  bool isServiceRunning();
}

@FlutterApi()
abstract class BackgroundEventsApi {
  void onServiceStateChanged(ServiceState state);
}
```
Generated to `lib/core/background/generated/background_api.g.dart` and
`android/app/src/main/kotlin/com/nexora/nexora/background/BackgroundApi.g.kt`
(package `com.nexora.nexora.background`). **`E10-T09` extends this same
schema** — leave it extensible rather than final.

### Functions
```yaml
- signature: "BackgroundService.start() -> Future<bool>"
  returns: "false when the platform refused (missing permission, service-start restriction)"
  purpose: "The only way anything in Dart starts the foreground service"

- signature: "BackgroundService.stop() -> Future<void>"
  purpose: "Stops the service and removes the ongoing notification"

- signature: "BackgroundService.state -> Stream<ServiceState>"
  purpose: "So E10-T10 can react to stoppedBySystem instead of assuming it never happens"

- signature: "ForegroundMeshService.onStartCommand(...) -> Int"
  returns: "START_STICKY"
  purpose: "The OS re-creates the service after a low-memory kill"
```

### External services & flags
New manifest permissions: `FOREGROUND_SERVICE` + the typed permission chosen
in ADR-0007 §S1 (advisory: `FOREGROUND_SERVICE_CONNECTED_DEVICE`). No new
package, no secret. 🧍 Both the permission set and the service type are the
human's call at ADR-0007.

## 6. Risks
- **Engine lifetime is the whole task.** If `cleanUpFlutterEngine` destroys
  the engine while the service holds it, the Dart side dies silently and the
  service becomes a notification with nothing behind it. Cache the engine and
  prove it survives Activity destruction — this is the one thing a reviewer
  must see evidence for.
- Android 12+ restricts **starting** a foreground service from the
  background; `startService()` must fail loudly (`false` + a `ServiceState`
  event), never silently.
- Android 14+ requires the declared `foregroundServiceType` to match what the
  service actually does, and enforces it at runtime. A mismatch is a crash,
  not a warning.
- **OEM killers.** Three MIUI restrictions are already on record for this
  project's only physical device (`E04-mesh-routing/retro.md:86-90`).
  `START_STICKY` mitigates; it does not solve. Record honestly what was and
  was not observed rather than claiming the service "runs indefinitely".
- **Battery is measured by nobody and asserted by everyone**
  (`E06-T06.md:201-203`). This task makes the app run continuously. Do **not**
  claim an NFR-BATT-001 outcome. Record what was measured — including "no
  device was available, nothing was measured" if that is the truth.
- Double-start and start-while-stopping are real races; make both idempotent.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-PLAT-7**: WHEN `BackgroundService.start()` succeeds, the system SHALL
  run a foreground service with an ongoing notification on the
  `backgroundService` channel, and the Flutter isolate SHALL remain alive
  after the Activity is destroyed. (FR-PLAT-001, FR-PLAT-003)
- **EARS-PLAT-8**: IF the system terminates the app process, THEN the service
  SHALL be re-created (`START_STICKY`) and SHALL report its state to Dart.
  (FR-PLAT-002)
- **EARS-PLAT-9**: WHEN `stop()` is called, the system SHALL stop the service
  and remove the ongoing notification. (FR-PLAT-001)
- **EARS-PLAT-10**: WHEN the device completes a boot AND the persisted
  "messaging active" flag was on at last shutdown, THEN the system SHALL
  restart the foreground service without requiring the user to open the
  app. (FR-PLAT-001, ADR-0007 §S3)

3. Stop from the app → notification gone, ticks stop.
4. Record battery/wake observations if any tooling is available; if not, say
   so plainly. **Absence of measurement must be stated, not implied.**

**Deviations from spec/design:**
1. **The persisted "messaging active" flag, reused by `BootReceiver`, is
   newly created by this task, not reused from a pre-existing flag.**
   ADR-0007 §S3 and this task's own §3 say "reuse whatever persisted flag
   already gates the foreground-path start, do not invent a second one" —
   but nothing in this codebase persisted such a flag before this task:
   `E10-T10` (which decides *when* `BackgroundService.start()` is called)
   has not been built yet, and `MessagingStack.create()`'s own header
   explicitly documents that even `coordinator.start()`'s call site is not
   yet wired anywhere in `lib/`. `BackgroundApiHost`'s own
   `nexora_background_prefs`/`messaging_active` `SharedPreferences` pair,
   written on every successful `startService()`/`stopService()` call, IS
   therefore the one and only such flag — not a second one, since there was
   no first. `BootReceiver` reads exactly this flag. Documented here per
   `AGENTS.md`'s "small ambiguity → simplest interpretation + log it"
   guidance rather than treated as a blocking Open Question, since it
   changes no contract signature and `E10-T10` is free to keep using this
   same flag going forward.
2. **Notification copy is provisional** (ADR-0007 §S4, `OQ-E10-1`,
   confirmed by the task's own unblocking note) — shipped as "Nexora is
   running — relaying messages" with the existing app icon, not
   design-approved. Not polished; not to be treated as final copy.
3. **A real full-process kill (not just the service) followed by
   `START_STICKY`/`BOOT_COMPLETED` restart cannot revive
   `MessagingCoordinator`'s tick until the user reopens the app.** Both
   `ForegroundMeshService` and `BootReceiver` restart the *service*
   component correctly (raising process priority, showing the notification)
   in that case, but there is no cached `FlutterEngine` to find — reviving
   the Dart isolate headlessly before the user opens the app would require
   a new entrypoint wired from `lib/app/main.dart`, which is not in this
   task's `files:` list. Documented on both classes' own doc comments as a
   known limitation, consistent with the task's own instruction to "record
   honestly what was and was not observed" for OEM-killer scenarios, rather
   than silently claimed as solved.
