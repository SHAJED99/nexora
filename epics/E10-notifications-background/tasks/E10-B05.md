# E10-B05 · A permanent notification for a mesh that isn't running

**`status: done`** — architecture decision made (human, delegated via "do
what is best"), option (b)(ii) implemented. See §Resolution below.

## The defect

`ForegroundMeshService` documents this itself, honestly
(`ForegroundMeshService.kt:33-46`), and `BootReceiver.kt:24-30` repeats it:

```kotlin
// ForegroundMeshService.kt:101
retainedEngine = FlutterEngineCache.getInstance().get(ENGINE_ID)
// null after a real process kill -- MainActivity never ran in this process
```

After the whole process is killed and Android re-creates the service under
`START_STICKY` — or after `BootReceiver` starts it following a reboot (once
`E10-B01` makes that path actually reachable) — there is no cached
`FlutterEngine`, because the engine and the isolate are created by
`MainActivity.configureFlutterEngine` and no Activity has run. So:

- `MessagingCoordinator`'s `Timer.periodic` does not exist. Nothing relays,
  nothing forwards, nothing syncs.
- `reclaimPayloads()` does not run. **NFR-SEC-001's third-party-ciphertext
  TTL guarantee is not being honoured** while this state persists — the exact
  gap ADR-0007's Consequences section claimed this epic closes.
- `ForegroundMeshService.eventsApi` is null, so `emitState` returns early
  (`:132`). **`EARS-PLAT-8`'s "SHALL report its state to Dart" is unreachable
  by construction** in the one scenario it was written for.
- The service nonetheless calls `startForeground()` with
  `"Nexora is running"` / `"Nexora is running — relaying messages"`
  (`:169-170`) and holds the process at foreground priority indefinitely,
  doing nothing.

The user sees a permanent, un-dismissable notification asserting the mesh is
relaying, on a device where it is not, with no indication anything is wrong
and no way to recover except opening the app — which is the state the whole
epic exists to make unnecessary.

It is also self-perpetuating: nothing in this state will ever start an
engine, so it lasts until the user opens the app or reboots again.

## Why this matters more at epic close than it did at T08

Three things that were separate at T08's review are one thing now:

1. **`E10-B01`** — the boot receiver could never fire, so the reboot half of
   this was latent. Fixing B01 makes it live.
2. **OEM reality.** This project has three MIUI restrictions on record
   (`E04-mesh-routing/retro.md:86-90`) and ADR-0007's own constraint 4 says
   "any answer that assumes stock-Android behaviour is wrong on the only
   hardware we have". Process kill is not the rare path on that hardware —
   it is the expected one, and `START_STICKY` revival is exactly what
   Android does after it.
3. **ADR-0007's deciding argument was that option 1 needs no second
   composition root.** That is true while the process lives. The moment it
   dies, reviving headlessly requires precisely the second Dart entrypoint
   and second composition root that options 2 and 3 were rejected for. The
   decision was made on a comparison that did not price this in.

## Expected
`FR-PLAT-001` — peer discovery, message synchronization and network
maintenance continue in the background where permitted. `NFR-SEC-001`'s
retention pass runs regardless of user attention (ADR-0007 Consequences).

## Actual
After a process kill or reboot: a foreground service, a permanent
notification claiming to relay, and no messaging stack behind it.

## Severity
**S3** — reviewer's own call. There is a real, complete workaround (open the
app, which restores everything), and no data is lost or corrupted. It is a
*high* S3: the failure is silent, the notification actively misinforms, and
it occurs in the scenario the epic was built for. It is not S2 only because
the workaround genuinely restores full function; it is not S4 by any reading.

## Priority
**P2** — set under the decision authority explicitly delegated by the human
for this session. Rationale a human would apply: the decision should be made
before E10 merges, because the alternative is shipping a permanent
notification that states something false and letting it stand as the app's
background story. Not P1 because the resolution is a design conversation,
not a hotfix, and P1 preempts running work. **The gate is the decision, not
the code** — if the human chooses option (b) below, the implementation is
tiny and can land in this epic; if option (a), it is a new task and E10 can
merge with this recorded as a known limitation.

## The decision required (planner → human, rule 3)

Three coherent answers. None should be picked by an agent.

**(a) Build a headless Dart entrypoint.** A `@pragma('vm:entry-point')`
function in `lib/app/main.dart` that `ForegroundMeshService` spins up when
`FlutterEngineCache` is empty, constructing enough of `AppBinding` to run the
coordinator tick. Closes the gap fully.
*Cost:* the second composition root ADR-0007 rejected options 2/3 for, and
two ways to build the app's object graph that must not drift. Also needs a
decision about what a headless isolate may touch (Drift, transport, and
`notification_policy.dart`'s no-decrypt fence become load-bearing in a new
context — `E06-T09.md:64-68`).

**(b) Do not revive; stop lying.** Have the service detect the empty cache
and either (i) not `startForeground()` at all, stopping itself immediately so
`START_STICKY`/boot revival is a no-op, or (ii) `startForeground()` with
honest degraded copy ("Nexora is paused — open to resume") and a tap intent
that opens the app.
*Cost:* `FR-PLAT-001` is then explicitly not honoured across a process kill,
which must be recorded as a known limitation rather than implied away. (ii)
also needs copy, and `OQ-E10-1` means no notification copy in this epic is
design-approved.

**(c) Revisit ADR-0007's option 3 (hybrid).** The ADR already names it as "a
legitimate follow-up optimisation once option 1 is proven on real hardware".
A `WorkManager` job is the OS-blessed way to get *something* running after a
process kill without a permanent notification.
*Cost:* the largest, and ADR-0007 explicitly deferred it pending on-device
evidence that does not exist yet (no installable device).

**The reviewer's advisory, which is not the decision:** (b)(ii) now, (a) or
(c) as a separately-scoped follow-up epic. A notification that tells the
truth is strictly better than one that does not, costs almost nothing, and
does not commit the project to a second composition root before anyone has
been able to run this on hardware. But the copy question routes straight
back into `OQ-E10-1`, and that is a human gate already.

## What resolving this does NOT do
- Does **not** reopen ADR-0007's main choice (option 1, foreground service +
  retained engine). That decision stands; this is a gap *within* it.
- Does **not** request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — `OQ-E10-4`,
  ADR-0007 §S2, still deferred and still human-owned.
- Does **not** address `OQ-E10-8` (an open RFCOMM socket and its blocking
  read thread during Doze) — unowned, unverifiable here, and unrelated.
- Does **not** change `EARS-PLAT-8`'s text. If the decision makes
  "SHALL report its state to Dart" unsatisfiable in this scenario by design,
  that is a planner amendment at retro with disclosure, not a silent edit.
- Does **not** substitute for `E10-B01`. B01 makes the boot path reachable;
  this decides what should happen once it is.

## Resolution (2026-09-04)

**Decided by:** human, delegated via "do what is best" after reviewing the
walkthrough of options (a)/(b)/(c) above. **Chosen: option (b)(ii)** — the
reviewer's own advisory.

`ForegroundMeshService.buildNotification()` now branches on whether
`retainedEngine` is non-null (i.e. whether `FlutterEngineCache` actually has
an engine, meaning the coordinator tick is really running):
- Engine present: unchanged copy, "Nexora is running -- relaying messages".
- Engine absent (post-kill `START_STICKY` revival, or `BootReceiver` after a
  reboot): "Nexora is paused -- open to resume", with a `setContentIntent`
  tap intent that opens `MainActivity`.

`FR-PLAT-001` is explicitly NOT honoured across a process kill -- this is now
disclosed to the user via the notification text itself rather than implied
away. `EARS-PLAT-8`/`EARS-PLAT-10`'s "service SHALL be re-created" half is
still satisfied (the service still starts foreground and shows a
notification); "SHALL report its state to Dart" remains unreachable in this
scenario by construction (no Dart isolate exists to report to), same as
before -- not a regression this change introduces.

Option (a) (headless Dart entrypoint) and (c) (ADR-0007 option 3 revisit) are
not pursued here -- both require a decision and design work this task's scope
fence excludes; tracked as legitimate follow-up epics, not silently dropped.

No test infra exists in this repo for Kotlin platform classes (confirmed: no
`androidTest` directory, `ForegroundMeshService` has never had a JVM/instrumented
test) -- consistent with the project's existing pattern of verifying platform
channel code from the Dart side only (e.g. `E10-B08`'s
`background_service_test.dart`). Introducing a new Kotlin test framework is
out of this bug's scope; the change is a straightforward conditional string
swap plus a standard `PendingIntent.getActivity` call, reviewed by inspection.

## Round 2 (2026-09-04) -- Opus review REQUEST_CHANGES, addressed

**Finding:** `retainedEngine` was captured once in `onCreate` and never
re-read. On the exact recovery path this fix exists for -- process kill,
service revives with "paused" copy, user taps it, `MainActivity` creates and
caches a fresh engine, relaying genuinely resumes -- the notification stayed
stuck on "paused", permanently, because nothing re-read the cache
afterward. That is a new permanent false assertion in the opposite
direction from the one this bug closes.

**Why not hook `eventsApi`'s companion setter (the reviewer's suggested
remedy):** traced `MainActivity.configureFlutterEngine` -- `BackgroundApiHost
.attach()` (which sets `ForegroundMeshService.eventsApi`) runs *before*
`FlutterEngineCache.getInstance().put(...)` in that same method. A setter
hook on `eventsApi` would still read an empty cache at that instant.

**Fix:** `onCreate` now starts a short polling coroutine
(`watchForEngineAttach`, 2s interval, `scope`-scoped so `onDestroy`'s
`scope.cancel()` stops it for free) only when the cache is empty at start;
it re-reads the cache and re-posts the notification the moment an engine
appears, then stops itself. No-op in the common case (engine already
cached at `onCreate`). Stays entirely inside `ForegroundMeshService.kt`,
the bug's only `files:update` entry.

Re-verified: `flutter build apk --debug` compiles clean; `flutter test
test/core/background/` still 39/39.
