# E10-T07 · Storage-warning notifications

## 1. Goal
Warn the user once when local storage crosses the threshold the dashboard
already warns at — and not again on every six-hourly pass while it stays
there.

## 2. Business logic
- **FR-NOTIFY-001** lists "storage warnings" as its own notification class.
- **The producer already exists and needs no seam.**
  `StorageManager.latestPlan` is an observable `Rx<RetentionPlan?>`
  (`storage_manager.dart:82`), updated by every non-throttled `runPass`,
  which `MessagingCoordinator`'s tick already drives (`E08-T06`). This task
  observes it. That is why this task's `files:` touches **no E08 file at
  all** — the rarest and best case for a notification source.
- **Reuse the dashboard's threshold; do not pick a new one.** `E08-T08`
  built the dashboard storage warning card against a specific threshold.
  Two different "storage is full" thresholds in one app is a defect, and
  choosing a second number here is exactly the invention rule 1 forbids.
  Locate the existing constant and import it. **If it turns out to be an
  inline literal with no shared symbol, STOP and record it in §Open
  Questions rather than duplicating the number** — extracting it is an edit
  to an E08 file this task's fence does not permit.
- **Once per crossing, not once per pass.** The pass runs every six hours
  and the condition persists; re-notifying each time is how a user turns the
  channel off.

## 3. What this task does
- `storage_notification_source.dart`: observes `StorageManager.latestPlan`,
  computes the usage condition using the existing threshold, and emits
  `NotificationFacts(category: storageWarning, ...)` on a **rising edge
  only** — the first plan that is over threshold after one that was not (or
  after process start with no prior state). Falling below and rising again
  re-arms it.
- Edge state is in-memory and re-arms on process start. That is a deliberate,
  documented simplification: at most one extra warning per app launch, and no
  new table.
- `bindings.dart`: register on `E10-T03`'s dispatcher.

## 4. What this task does NOT do
- Does **not** touch `storage_manager.dart`, `storage_inventory.dart`,
  `retention_plan.dart`, `smart_mode_policy.dart`, `retention_executor.dart`
  or any other E08 file. Observation only.
- Does **not** add a second periodic timer, isolate or background service to
  drive the storage pass — `E08-T06.md:119-120` forbade itself that and named
  E10 as the owner of background operation; **`E10-T10` is where that is
  done, through the one existing tick**, not here.
- Does **not** change the storage pass's throttle, ordering, or retention
  decisions.
- Does **not** define a new threshold, percentage or denominator. `GAP-026`
  already settled that the dashboard's percentage has a specified
  denominator; this task inherits it and adds nothing.
- Does **not** offer a "free up space" action, deep link or storage screen —
  `design/screens/settings-storage.md` is E08's contract and E08's task
  (`OQ-E10-1` covers notification-side affordances generally).
- Does **not** persist the edge state.

## 5. Contract

### Functions
```yaml
- signature: "StorageNotificationSource(Rx<RetentionPlan?> latestPlan, {required bool Function(RetentionPlan) isOverThreshold}) -> NotificationSource"
  params: { isOverThreshold: "injected predicate built from E08's existing threshold symbol — never a literal written in this file" }
  returns: "Stream<NotificationFacts>, rising-edge only"
  purpose: "One warning per crossing, using the app's single storage threshold"

- signature: "StorageNotificationSource.dispose() -> void"
  purpose: "Drops the Rx worker; safe twice (bindings teardown calls it)"
```
Copy: title `Storage almost full`, body `NEXORA is running low on local
storage`. Under `hidden`, unchanged — this notification contains no personal
content at any privacy level, which is worth stating so nobody adds a figure
to it later.

## 6. Risks
- `Rx` workers (`ever`/`everAll`) leak if not disposed; `bindings.dart`
  teardown must call `dispose()`.
- The first plan after process start is not a "crossing". Treat an initial
  over-threshold reading as a crossing **once**, then latch — otherwise a
  user whose device is persistently full is never warned at all, which is
  the opposite failure and the worse one.
- `latestPlan` is null before the first pass. Null must not be read as
  "under threshold" and trigger a spurious edge when the first real value
  arrives.
- The throttle means the pass may not run for six hours after storage fills;
  this notification is therefore *late by design*. Do not "fix" that by
  running a pass — that is a second driver.

- **EARS-NOTIFY-14**: WHEN a storage pass produces a plan that is over the
  storage threshold and the previous observed state was not, the system
  SHALL post one `storageWarning` notification. (FR-NOTIFY-001)
- **EARS-NOTIFY-15**: WHILE storage remains over threshold across subsequent
  passes, the system SHALL NOT post a further notification until it has
  fallen below and risen again. (FR-NOTIFY-001)
