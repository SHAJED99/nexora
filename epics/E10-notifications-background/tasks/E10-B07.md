# E10-B07 · Five green lights with nothing wired behind them

The suite is 913/913 green and `flutter analyze` is clean. That is not in
dispute. What follows is the subset of it that would stay green with the code
it guards removed.

## F1 — `EARS-NOTIFY-14`'s null-plan guard: mutation survives the whole suite

```dart
// lib/core/notifications/sources/storage_notification_source.dart:100
if (plan == null) return;
```

`test_EARS_NOTIFY_14_null_plan_posts_nothing`
(`storage_notification_source_test.dart:146-165`) never assigns a plan at
all: `latestPlan` starts null, stays null, and the test asserts no facts were
emitted — which the `ever()` worker guarantees whether or not the guard
exists.

Mutating line 100 to `{ _wasOverThreshold = false; return; }` leaves the
**entire suite green**, yet it makes an `over → null → over` sequence
double-notify, violating `EARS-NOTIFY-15` ("stays over → no further
notification until it falls and rises again"). There is no `over → null →
over` test in the file. T07's review flagged exactly this and it is confirmed.
The rising-edge behaviour itself (`:42`, `:70`) *is* genuinely proven.

**Fix:** add an `over → null → over` test asserting exactly one post across
the whole sequence. Must fail under the mutation above.

## F2 — `EARS-NOTIFY-7`'s privacy downgrade: the sweep's own probe passed

```dart
// lib/core/notifications/notification_policy.dart:91
level = NotificationPrivacyLevel.senderOnly;   // downgrade `full`
```

The sweep deleted this line. `flutter test test/core/notifications/` →
**49/49 passed**, including `test_EARS_NOTIFY_7_full_downgrades_to_sender_only`
(`notification_policy_test.dart:103`).

It passes because `_copyFor` has no `full` branch, so `full` and `senderOnly`
render identically today and the downgrade is behaviourally a no-op. Safe
now; **not safe after `E10-B03`**, which adds per-category branches and makes
this line the only thing between `full` privacy and the decrypt path
`E06-T09.md:64-68` forbids by name. `EARS-NOTIFY-2` is a `SHALL NOT`.

**Fix:** this one belongs to `E10-B03` and is specified there — listed here
so the pattern is complete. Do not fix it twice; if B03 lands first, tick
this off and say so.

## F3 — `EARS-PLAT-11` asserts a value the test mocks in

`test_EARS_PLAT_11_missing_signal_reads_false`
(`power_state_test.dart:170-203`) installs a mock handler at `:186-193` that
returns `allClearPowerState()`, then asserts every field is `false` at
`:198-202`. It asserts exactly what it supplied. The real guard — the
API-level fallbacks in `PowerStateMonitor.kt:55-74`, where a signal
unavailable on an older API defaults to `false` — is Kotlin, is not
exercised, and could be inverted without this test noticing.

The sibling dedup test at `:136` *is* real and drives
`background_service.dart:110`. Only the missing-signal half is hollow.

**Fix:** either assert something the Dart layer actually decides (e.g. that a
platform read which *throws* still yields an all-false `PowerState` rather
than propagating), or delete the test and record the Kotlin fallback as
explicitly unverified in this environment. A test named for a guarantee it
cannot check is worse than an acknowledged gap.

## F4 — `EARS-PLAT-5` proves neither "per category" nor "idempotent"

`notification_service_test.dart:61-70` calls `ensureReady()` three times and
asserts `ensureChannelsCallCount == 3`. The criterion is *"exactly one
Android channel per category, idempotently"*. A host that created zero
channels, or ten duplicates per category, passes this test unchanged. What is
proven is that a Dart method forwards a call.

**Fix:** assert what the Dart side can actually own — that `ensureReady()` is
called before any `post()` can succeed, and that repeated calls are safe.
Then state plainly that per-category channel creation lives in
`NotificationChannels.kt` and is unverified here (the `E04-T03b`
no-mock-Kotlin limitation), rather than implying the criterion is covered.

## F5 — `EARS-PLAT-14` / `EARS-PLAT-4` never establish their own precondition

The criterion: *"WHILE the app is backgrounded AND the foreground service is
running, the system SHALL continue to run the coordinator tick, including
`reclaimPayloads()`."* This is **NFR-SEC-001's retention proof** — the whole
reason obligation #5 was raised as its own criterion with its own test, per
`epic.md:207` and the advisory's explicit instruction not to fold it into
another test.

`test_EARS_PLAT_14_reclaim_runs_while_backgrounded`
(`messaging_coordinator_background_test.dart:161-200`) sets **neither**
condition: no `AppLifecycleState`, no `ServiceState`, no
`BackgroundLifecycleObserver`. It calls `setTickInterval(120s)` and then
`stack.coordinator.tick()` **manually** (`:193`). The test's own comment at
`:165-171` concedes "MessagingCoordinator itself has no notion of
`AppLifecycleState` at all".

It proves `reclaimPayloads` runs on a tick — which
`messaging_coordinator_test.dart` already covered before E10 existed. The
task file demanded "assert `reclaimPayloads` was invoked with the app in
`paused` and the service `running`". That test does not exist.

**Fix:** drive it through `BackgroundLifecycleObserver` with a
`BackgroundStub` reporting `running` and lifecycle `paused`, let the real
timer fire, and assert `reclaimPayloads` ran without anyone calling `tick()`
by hand. This is the same composition-level harness `E10-B02`'s regression
test needs — build it once and use it for both.

## Severity
**S4** — no production defect is demonstrated by any of the five. F1's
mutation is a real latent bug but the shipped code is correct; F2 is
currently a no-op; F3/F4 are honest environment limits described dishonestly
by their test names; F5 duplicates coverage that already exists. Nothing a
user can observe is wrong. What is wrong is the evidence.

## Priority
**P3** — set under the decision authority explicitly delegated by the human
for this session. Rationale: no user impact and no merge risk today, so it
does not need to hold E10. But it should not go to P4 backlog either: F5
guards **NFR-SEC-001**, a security guarantee, and an unfalsifiable test on a
security guarantee is the kind of thing that is discovered at the worst
possible moment. Next epic, deliberately scheduled, not "someday".

## Regression test (write it first)
Each fix above *is* a test. The acceptance bar for this bug is mechanical and
must be recorded in the run log per finding: **apply the named mutation,
confirm the new test fails for the right reason, restore, confirm green.**
- F1: `{ _wasOverThreshold = false; return; }` at
  `storage_notification_source.dart:100`.
- F3: invert the API-level fallback default, or remove the throw guard.
- F5: stop the coordinator's timer and confirm the new test fails rather than
  passing on a hand-called `tick()`.
A fix whose falsification step is not recorded is not done.
