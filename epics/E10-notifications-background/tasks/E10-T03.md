# E10-T03 · Notification policy + dispatcher

## 1. Goal
Turn the first real event — a message arriving while the app is not being
looked at — into an Android notification, through one policy that every
later notification class reuses.

## 2. Business logic
- **FR-NOTIFY-001**: "new messages" is the first of the nine classes and the
  only one with a live producer today: `InboundPipeline.delivered`
  (`Stream<Message>`, `inbound_pipeline.dart:264`).
- **`E06-T05.md:124-125` is the obligation this discharges**: "Does NOT
  surface anything to the user. Counters and a stream; no UI, no notification
  (E10)." The producer exists and is live; only the consumer was missing.
  **Subscribe to the stream — do not add a hook inside the pipeline.**
  T05's fence forbids modifying it, and this task's `files:` does not list it.
- **FR-NOTIFY-002 + the plaintext boundary.** `Message` carries `ciphertext`
  and metadata only (`message.dart:48`); decryption for display happens in
  the screen layer (`E06-T09.md:64-68`). Therefore:
  - `hidden` (the default) → title "NEXORA", body "New message". No sender,
    no preview.
  - `senderOnly` → the sender's display name from the relationship/
    conversation metadata **that is already stored in the clear**; still no
    preview.
  - `full` → **not implemented.** There is no plaintext available outside the
    screen layer and this task does not create one. The policy returns the
    `senderOnly` shape for `full` and records the downgrade
    (`OQ-E10-2`). Silently doing nothing, or silently decrypting, are both
    worse than a disclosed downgrade.
- One dispatcher, one seam: every later source (T04–T07) constructs a
  `NotificationFacts` and hands it to the same `NotificationPolicy`.

## 3. What this task does
- `notification_policy.dart` — `NotificationPolicy.resolve(...)`: consults
  `NotificationSettingsRepository` for the category flag and the privacy
  level, and returns a `NotificationRequest` or `null` (suppressed). Pure,
  injectable, no I/O beyond the repository.
- `notification_dispatcher.dart` — `NotificationDispatcher`: owns the
  `NotificationService`, the policy, and a registry of sources. `register()`,
  `start()`, `stop()`. Each source is a small object exposing a
  `Stream<NotificationFacts>`; the dispatcher subscribes, resolves, posts.
  **The registry is the extension point T04–T07 use** so those tasks add a
  file rather than editing this one's logic.
- `sources/message_notification_source.dart` — subscribes to
  `stack.inbound.delivered`, maps each `Message` to
  `NotificationFacts(category: message, conversationId, senderDeviceId)`.
  Notification id derived stably from the conversation id, so a second
  message in the same thread replaces rather than stacks.
- `lib/app/bindings.dart` — construct the dispatcher, register the message
  source, `start()` it after `MessagingStack` is ready; `stop()` on teardown.

## 4. What this task does NOT do
- Does **not** modify `inbound_pipeline.dart`, `messaging_coordinator.dart`,
  `message.dart`, `conversation_repository.dart` or any messaging file.
  Subscription only.
- Does **not** decrypt, and does **not** add a decrypt path to any repository —
  `E06-T09` forbids this by name and anticipates this exact task.
- Does **not** implement the `full` privacy level (§2). Do not "just add" a
  `CryptoService` call to make it work; that is the change `OQ-E10-2` exists
  to put in front of a human.
- Does **not** notify for voice messages or PTT as distinct classes. Nothing
  in the build distinguishes them from a message without decrypting
  (`Message` has no payload-kind field), and no PTT code exists at all
  (`OQ-E10-3`). They arrive as `message` until that is resolved.
- Does **not** suppress notifications for the conversation currently on
  screen. Sensible, unspecified, and it needs an app-lifecycle/route signal
  this epic does not have until `E10-T10`. No FR asks for it; do not invent
  it (`OQ-E10-T03-1`).
- Does **not** add a second periodic driver, timer or isolate
  (`E08-T06.md:119-120`; the epic-wide invariant).
- Does **not** wire calls, requests, group events or storage warnings —
  T04–T07 own those, each through the registry this task creates.

## 5. Contract

### Functions
```yaml
- signature: "NotificationPolicy.resolve(NotificationFacts facts) -> Future<NotificationRequest?>"
  params: { facts: "category + the non-secret identifiers a source could gather" }
  returns: "a request to post, or null when the category is disabled"
  purpose: "The one place enablement and privacy are applied — no source decides for itself"

- signature: "NotificationDispatcher.register(NotificationSource source) -> void"
  purpose: "Extension point; T04-T07 add a source here rather than editing the dispatcher"

- signature: "NotificationDispatcher.start() -> Future<void>"
  returns: "resolves once NotificationService.ensureReady() has run and every source is subscribed"
  purpose: "Composition-root entry point"

- signature: "NotificationDispatcher.stop() -> Future<void>"
  purpose: "Cancels every subscription; safe to call twice"

- signature: "MessageNotificationSource(Stream<Message> delivered, {required String selfDeviceId}) -> NotificationSource"
  returns: "Stream<NotificationFacts> of category `message`"
  purpose: "Adapts E06-T05's existing delivered stream without touching it"
```
`NotificationFacts` (in `notification_policy.dart`): `category`,
`conversationId`, `peerDeviceId`, `peerDisplayName` (nullable),
`stableId` — **no field may hold plaintext, and none is nullable-because-
decryption-failed.** A source that cannot fill a field leaves it null and the
policy degrades the copy.

Copy, verbatim, per privacy level (no design contract exists for these
strings — `OQ-E10-1`; they are the minimum Android requires and are listed
here so a reviewer can check them rather than guess):
| level | title | body |
|---|---|---|
| `hidden` | `NEXORA` | `New message` |
| `senderOnly` | `<peerDisplayName>` or `NEXORA` when unknown | `New message` |
| `full` | *treated as `senderOnly`* | *treated as `senderOnly`* |

## 6. Risks
- **Re-entrancy and duplicate posts.** `delivered` is a broadcast stream; a
  hot restart or a double `start()` yields two subscriptions and two
  notifications per message. `start()` must be idempotent.
- **Notification id derivation.** Deriving from a `String` hash risks
  collisions across conversations; use a stable, documented derivation and
  say what happens on collision (worst case: two threads share a
  notification slot — acceptable; a crash is not).
- The dispatcher must never let a source's error kill the subscription —
  an exception building one notification must not stop every future
  notification. Guard per-event, log nothing sensitive.
- `bindings.dart` is edited by T03–T07 and T10 in sequence. Keep the edit
  minimal and in one place so the next task's diff is readable.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-NOTIFY-5**: WHEN `InboundPipeline.delivered` emits a message and the
  `message` category is enabled, the system SHALL post exactly one
  notification for that conversation. (FR-NOTIFY-001)
- **EARS-NOTIFY-6**: IF the `message` category is disabled, THEN the system
  SHALL post nothing and SHALL NOT throw. (FR-NOTIFY-001, FR-NOTIFY-002)
- **EARS-NOTIFY-7**: WHILE the privacy level is `hidden`, the posted
  notification SHALL contain no sender identifier and no message content;
  and the system SHALL NOT invoke any decryption path while building a
  notification. (FR-NOTIFY-002)

**Deviations from spec/design:**
- The task's contract only names `message`-category copy (§5's table). To
  keep `NotificationPolicy._copyFor`'s switch exhaustive without inventing
  copy for T04-T07's categories (none of which is design-approved,
  `OQ-E10-1`), an unrecognised category degrades to a generic, content-free
  `('NEXORA', 'Notification')` shape rather than throwing. This branch is
  unreachable in production today (only `MessageNotificationSource` is
  registered) and is not asserted on by any test for that reason — noted so
  a future reader does not mistake it for approved copy.
- `NotificationDispatcher.start()`'s fire-and-forget call in `bindings.dart`
  is wrapped in `catchError` (logging only). Without it, a test harness with
  no platform-channel mock for `NotificationApi` (`messaging_coordinator
  _test.dart`, which builds a full `AppBinding` to prove unrelated
  storage-manager wiring) surfaced the resulting `PlatformException` as an
  unhandled async error after the test had already completed — confirmed by
  running that pre-existing suite before this guard was added (3 failures)
  and after (all green). Same defensive shape `_measureDatabaseFileBytes`
  already uses in this file for the identical "platform channel unavailable
  in this test's zone" reason.
- `selfDeviceId` on `MessageNotificationSource` is used to filter out a
  delivered message this device itself authored. `InboundPipeline.delivered`
  should never emit one (every message on it came from a packet addressed to
  this device and decrypted from a peer), so this is a defensive guard, not
  a currently-reachable code path — recorded since the task's own function
  signature requires the parameter and its purpose is otherwise silent.
