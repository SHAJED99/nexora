# E10-T01 · Native notification boundary

## 1. Goal
Give the app one type-safe way to post an Android notification — a Pigeon
`NotificationApi` over a hand-written Kotlin host that owns the channels,
the runtime permission and nothing else — so every later notification task
is pure Dart logic against a stable seam.

## 2. Business logic
- **FR-PLAT-003** (non-negotiable): notifications are system-sensitive
  functionality and belong in an Android-native component, with Flutter
  communicating through a *defined interface*. ADR-0004 fixes that interface
  as Pigeon. This task is the notification twin of `E04-T03a`'s transport
  boundary and copies its shape deliberately.
- **FR-NOTIFY-001** names nine notification classes (new messages, voice
  messages, PTT, incoming calls, connection requests, trust requests, group
  events, security events, storage warnings). Each becomes an Android
  **notification channel**, created once at attach, so the user can silence
  a class from Android's own settings even before NEXORA has a settings
  screen of its own. A tenth, `backgroundService`, exists for `E10-T08`'s
  mandatory ongoing service notification — declared here so T08 adds no
  channel plumbing of its own.
- **POST_NOTIFICATIONS is a runtime permission on API 33+.** Denial must
  surface, exactly as `E04-T03b` handled Bluetooth denial: a caller that
  posts into a void with no error has no way to distinguish "denied" from
  "nothing happened".
- `docs/conventions.md`: generated files (`*.g.dart`, `*.g.kt`) are never
  hand-edited — regenerate from `pigeons/notifications.dart`.

## 3. What this task does
- `pigeons/notifications.dart` — the schema (see §5), with the same
  regeneration header comment `pigeons/transport.dart` carries.
- Generated `notification_api.g.dart` + `NotificationApi.g.kt` via
  `dart run pigeon --input pigeons/notifications.dart`.
- `NotificationChannels.kt` — creates one `NotificationChannel` per
  `NotificationCategory` on attach, idempotently. Importance per category:
  `incomingCall` HIGH; `message`, `voiceMessage`, `ptt` DEFAULT;
  `connectionRequest`, `trustRequest`, `groupEvent`, `securityEvent`,
  `storageWarning` DEFAULT; `backgroundService` LOW (no sound, no badge).
- `NotificationApiHost.kt` — implements `NotificationApi`: `ensureChannels`,
  `hasPermission`, `requestPermission`, `post`, `cancel`. Posts through
  `NotificationManagerCompat`. Holds an `Activity` reference the same way
  `TransportApiHost` does, and forwards permission results.
- `MainActivity.kt` — registers the host in `configureFlutterEngine`, tears
  it down in `cleanUpFlutterEngine`, forwards `onRequestPermissionsResult`
  (a **distinct request code** from `BluetoothTransport`'s `4200`).
- `AndroidManifest.xml` — adds `POST_NOTIFICATIONS` only.
- `notification_service.dart` — the Dart façade (`NotificationService`),
  mirroring `TransportService`: a thin, injectable wrapper over the
  generated host with a `NotificationEventsApi` implementation.
- `notification_stub.dart` — an in-memory `NotificationService` double that
  records posts. **This is what every downstream task tests against**;
  without it T03–T08 are as unrunnable-without-hardware as T03b/c.

## 4. What this task does NOT do
- Does **not** decide *when* anything is notified. No subscription to any
  stream, no policy, no copy for any real event. T03 owns the first
  producer, T04–T07 the rest.
- Does **not** read or write user preferences — no category is consulted for
  enablement here (that is T02/T03). `post()` posts what it is given.
- Does **not** create a foreground service, request `FOREGROUND_SERVICE`,
  or touch anything in `.../background/` — that is `E10-T08` and it is
  blocked on ADR-0007. Declaring the `backgroundService` **channel** is the
  only thing this task does for it.
- Does **not** add a notification package (`flutter_local_notifications` or
  similar). FR-PLAT-003 + ADR-0004 say native-behind-Pigeon; adding a plugin
  would be a new dependency (🧍 rule 3) *and* a contradiction of the ADR.
- Does **not** touch `pigeons/transport.dart`, `TransportApiHost.kt`,
  `BluetoothTransport.kt` or the Bluetooth permission elements in the
  manifest. E04's manifest posture (`maxSdkVersion="30"` caps,
  `neverForLocation`) is left byte-identical.
- Does **not** implement notification tap-through navigation beyond
  delivering the `onNotificationTapped` event to Dart. Routing on tap needs
  a design decision nobody has made (`OQ-E10-1`).
- Does **not** implement grouping, bundling, LED/vibration customisation or
  "silent modes" — `settings.md` element 41 promises "Alerts, silent modes,
  LED behaviors" behind a row that has **no destination screen**
  (`OQ-E10-1`); building the behaviour before that contract exists is
  inventing a design.

## 5. Contract

### Pigeon schema (`pigeons/notifications.dart`)
```dart
enum NotificationCategory {
  message, voiceMessage, ptt, incomingCall, connectionRequest,
  trustRequest, groupEvent, securityEvent, storageWarning, backgroundService,
}

class NotificationRequest {
  int id;                      // stable per logical notification; re-post replaces
  NotificationCategory category;
  String title;
  String body;
  bool ongoing;                // true only for backgroundService
}

@HostApi()
abstract class NotificationApi {
  void ensureChannels();
  bool hasPermission();
  void requestPermission();
  bool post(NotificationRequest request);   // false = not posted (no permission)
  void cancel(int id);
}

@FlutterApi()
abstract class NotificationEventsApi {
  void onPermissionResult(bool granted);
  void onNotificationTapped(int id, NotificationCategory category);
}
```
Generation command (record it in the file header, as `pigeons/transport.dart`
does):
`dart run pigeon --input pigeons/notifications.dart --dart_out lib/core/notifications/generated/notification_api.g.dart --kotlin_out android/app/src/main/kotlin/com/nexora/nexora/notifications/NotificationApi.g.kt --kotlin_package com.nexora.nexora.notifications`

### Functions
```yaml
- signature: "NotificationService.ensureReady() -> Future<bool>"
  returns: "true when channels exist and permission is granted; false when denied"
  purpose: "One call a composition root can await before the first post"

- signature: "NotificationService.post(NotificationRequest request) -> Future<bool>"
  returns: "false when the host refused (no permission) — never throws for denial"
  purpose: "The single seam every notification source in E10 posts through"

- signature: "NotificationService.cancel(int id) -> Future<void>"
  purpose: "Withdraw a posted notification (used by T04's call notice and T08's service notice)"

- signature: "NotificationStub.posted -> List<NotificationRequest>"
  purpose: "Test double's recording surface — downstream tasks assert against this"

- signature: "NotificationApiHost.ensureChannels() -> Unit"
  purpose: "Idempotent channel creation, one per NotificationCategory, safe to call on every attach"
```

### External services & flags
No new package, no new service, no secret. One new manifest permission:
`POST_NOTIFICATIONS` (runtime, API 33+). It is the unavoidable mechanism of
`FR-NOTIFY-001`, not a fork — but it **is** a manifest change and is listed
for the human at this epic's analyze gate.

## 6. Risks
- **Request-code collision.** `BluetoothTransport` owns `4200`
  (`E04-T03b.md`). Pick a different constant and filter on it, or the
  Bluetooth permission flow silently breaks — a regression in an epic that
  cannot be tested on hardware here.
- `MainActivity.onRequestPermissionsResult` must still call `super` **first**
  (E01's Google Sign-In depends on the plugin registry receiving results —
  `E04-T03b`'s reviewer verified this explicitly). Adding a second forward is
  additive; reordering is not.
- On API < 33 `hasPermission()` must return `true` (there is no runtime
  permission), not `false`. Getting this backwards silences every
  notification on older devices while the tests still pass.
- Channel importance cannot be raised after creation — Android ignores the
  change on an existing channel. Get the importance right the first time or
  the only fix is a new channel id.
- `NotificationManagerCompat.notify` on a channel the user disabled returns
  silently. `post()` should report the manager's own `areNotificationsEnabled()`
  rather than claiming success it cannot observe.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-PLAT-5**: WHEN the notification host attaches, the system SHALL
  create exactly one Android notification channel per `NotificationCategory`,
  idempotently. (FR-NOTIFY-001, FR-PLAT-003)
- **EARS-PLAT-6**: IF `POST_NOTIFICATIONS` is not granted on API 33+, THEN
  `post()` SHALL return `false` and SHALL NOT throw; and on API < 33 the
  system SHALL report permission as granted. (FR-PLAT-003)

### Tests
- `test_EARS_PLAT_5_channels_created_once_per_category` → the stub/host
  contract records one `ensureChannels` effect per category and repeat calls
  add nothing.
- `test_EARS_PLAT_6_post_returns_false_when_denied` → `NotificationStub`
  configured denied; `post()` resolves `false`, records nothing, throws
  nothing.
- Dart-side only. The Kotlin half is proven by `flutter build apk --debug`
  compiling plus the manual step — **do not write a Robolectric/mock Kotlin
  test that passes regardless of correctness** (`E04-T03b`'s standing rule).

### Manual

   see `E04-T03b` §Run log; if not, say so, do not claim it).
2. Fresh install on API 33+: first `requestPermission()` shows the system
   prompt; granting then denying is reflected by `hasPermission()`.
