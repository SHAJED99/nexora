# E10-B02 · Discovery runs in Doze, two ways

**EARS-PLAT-13** (`E10-T10.md:183`): *WHILE the device is in Doze or Battery
Saver, the system SHALL NOT start peer discovery, and SHALL resume it when
the condition clears.*

The criterion is law (rule 1). Two live code paths violate it.

## Route (a) — `stoppedBySystem` short-circuits the power check

```dart
// lib/core/background/background_policy.dart:85-90
if (service == ServiceState.stoppedBySystem) {
  return const BackgroundPlan(
    tickInterval: foregroundInterval,
    discoveryAllowed: true,          // <-- unconditional
  );
}
// power.deviceIdle / powerSaveMode are only consulted BELOW this return
```

The builder implemented `E10-T10.md:142`'s §5 table row exactly — *"service
`stoppedBySystem` | foreground value (nothing is running anyway) | yes"* —
and even tested this combination deliberately
(`background_policy_test.dart:156-174`). T10's reviewer correctly concluded
the code matches the table. **The table is wrong**, and its stated rationale
is factually false:

> "nothing is running anyway"

`stoppedBySystem` means the *foreground service* died, not the process. The
observer can only ever see this event because the Dart isolate is alive to
receive it (`ForegroundMeshService.onDestroy` → `emitState` → `eventsApi` →
`BackgroundLifecycleObserver._onServiceStateChanged`). The tick is still
firing and `transport.startDiscovery()` will really turn the Bluetooth radio
on — at the single worst moment, since the most likely reason the system just
killed the service is Doze or an OEM battery killer. The app's response to
being throttled is to start scanning.

## Route (b) — the power state is never seeded, so a cold start in Doze scans

```dart
// lib/app/bindings.dart (BackgroundLifecycleObserver)
PowerState _powerState = allClearPowerState();   // optimistic default
bool? _discoveryAllowed;                          // starts null

void start() {
  WidgetsBinding.instance.addObserver(this);
  _serviceStateSubscription = _service.state.listen(_onServiceStateChanged);
  _powerStateSubscription = _service.powerStates.listen(_onPowerStateChanged);
  // no powerState() read here
}
```

`start()` subscribes but never reads `_service.powerState()` once. The
`PowerState` stream is fed by `PowerStateMonitor`'s broadcast receivers,
which fire on **transitions only** (`ACTION_DEVICE_IDLE_MODE_CHANGED` et al.).
If the app cold-starts while the device is *already* in Doze or Battery
Saver, that transition happened before the process existed and no event ever
arrives. `_powerState` stays `allClearPowerState()`, `_applyPlan` computes
`discoveryAllowed: true`, `_discoveryAllowed` is `null` so the guard does not
suppress it, and `transport.startDiscovery()` is issued — with a 60 s tick
interval — for as long as Doze lasts.

The machinery to fix this already exists and is already used on the resume
path: `_refreshPowerStateOnResume()` does exactly the one-shot read that
`start()` is missing.

## Route (c) — nothing tests the seam that applies any of it

```dart
// lib/app/bindings.dart — the only place discovery is actually gated
if (_discoveryAllowed == plan.discoveryAllowed) return;
_discoveryAllowed = plan.discoveryAllowed;
if (plan.discoveryAllowed) {
  unawaited(transport.startDiscovery().catchError((Object _) {}));
} else {
  unawaited(transport.stopDiscovery().catchError((Object _) {}));
}
```

Every hit for `discoveryAllowed` in `test/` is in
`background_policy_test.dart`, asserting the pure function's returned flag.
**Deleting this entire block fails no test.** EARS-PLAT-13 says "the system
SHALL NOT start peer discovery"; what is proven is that a `bool` has the
right value, never that discovery is started or stopped. T10's own review
flagged this as an S4; combined with two live violations it is the reason
neither was caught.

## Repro
1. `BackgroundPolicy.plan(power: PowerState(deviceIdle: true, ...), service:
   ServiceState.stoppedBySystem, lifecycle: AppLifecycleState.paused)`.
   → `discoveryAllowed: true`. (Route a — already asserted as *correct* by
   `background_policy_test.dart:156-174`, which must be inverted by this fix.)
2. Construct a `BackgroundLifecycleObserver` with a `BackgroundStub` whose
   `powerState()` reports `deviceIdle: true`, call `start()`, pump. Observe
   `transport.startDiscovery()` was called. (Route b.)

## Expected
EARS-PLAT-13: no discovery while `deviceIdle` or `powerSaveMode` is true,
regardless of `ServiceState` and regardless of whether the entering
transition was ever observed. Discovery resumes when the condition clears.

## Actual
Discovery allowed in both scenarios. `BluetoothAdapter.startDiscovery()`
burns radio for results Android will not deliver during Doze — the exact
waste `E10-T10.md`'s own §2 names as "the one behavioural concession worth
making".

## Severity
**S3** — battery and radio waste in a state the device is already trying to
conserve in, with no crash, no data loss and no correctness impact on
messaging. Bounded by the duration of Doze. Not S2: nothing a user asked for
stops working.

## Priority
**P2** — set under the decision authority explicitly delegated by the human
for this session. Rationale: it is a small, well-understood fix inside a pure
function plus one one-shot read; it is a direct violation of an EARS
criterion this epic owns; and NFR-BATT-001 has never been measured by anyone,
so shipping a known battery regression on top of an unmeasured baseline is
the wrong direction to be wrong in. Not P1 — no user-visible breakage.

## Fix direction
- **Route (a):** in `BackgroundPolicy.plan`, evaluate the restricted band
  (`powerSaveMode || deviceIdle || backgroundRestricted`) **before** the
  `stoppedBySystem` short-circuit — or, if the foreground tick interval is
  genuinely wanted when the service is dead, keep the interval and force
  `discoveryAllowed: false` whenever the restricted band holds. Either
  satisfies EARS-PLAT-13; pick one and say which in the run log.
- **Correct the §5 table in `E10-T10.md`** in the same commit, including its
  "nothing is running anyway" rationale sentence, so the contract and the
  code stop disagreeing. Note in `OQ-E10-T10-2`, which already tracks the
  cadence table's unmeasured numbers, that this row was corrected — do not
  change any of the six interval numbers themselves.
- **Route (b):** have `BackgroundLifecycleObserver.start()` perform the same
  one-shot `_service.powerState()` read `_refreshPowerStateOnResume()`
  already does, with the same swallow-and-fall-back-to-the-stream error
  posture. Reuse that method; do not write a second one.
- Consider whether `_discoveryAllowed` should start as `false` rather than
  `null` so the first `_applyPlan` cannot issue an unbidden `startDiscovery()`
  before any real signal is read (T10's second S4). Seeding the power state
  makes this mostly moot; state the reasoning either way.

## Regression test (write it first)
- Invert `background_policy_test.dart:156-174`: Doze + `stoppedBySystem`
  must yield `discoveryAllowed: false`. Must fail on today's code.
- Battery Saver + `stoppedBySystem` — same assertion.
- **A composition-level test of the seam** (this is the important one, and
  the one T10 never had): drive a `BackgroundLifecycleObserver` with a fake
  `TransportService` and assert `stopDiscovery()` is called when the plan
  forbids discovery and `startDiscovery()` when it permits it, across a
  clear → Doze → clear sequence. Must fail if the `if/else` block in
  `_applyPlan` is deleted.
- A cold-start-in-Doze test: `powerState()` reports `deviceIdle: true`, no
  stream event is ever emitted, `start()` is called → `startDiscovery()` is
  never called and the interval is `restrictedInterval`.

## What this fix does NOT do
- Does **not** add a `Timer`, `WorkManager` job, isolate or second periodic
  driver, and does **not** change what the tick does or its ordering — the
  one-tick invariant (`E08-T06.md:119-120`, `EARS-PLAT-2`) is untouched.
- Does **not** change any of the six cadence *numbers* in the §5 table
  (60/60/120/300/300/300). They remain unmeasured defaults under
  `OQ-E10-T10-2`; only the `stoppedBySystem` row's `discoveryAllowed` column
  and its rationale change.
- Does **not** change `BluetoothTransport.kt`, the native read loops, or any
  transport file. What happens to an open RFCOMM socket during Doze remains
  `OQ-E10-8`, unowned and unverifiable here.
- Does **not** change the 60 s foreground floor.
- Does **not** claim any NFR-BATT-001 measurement. State plainly that none
  was possible.
