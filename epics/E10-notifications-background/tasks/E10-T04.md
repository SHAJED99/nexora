# E10-T04 · Incoming-call notifications

## 1. Goal
A ringing call the user cannot see is a missed call. Surface an inbound call
invite as a HIGH-importance notification, and withdraw it the moment the call
is answered, declined or times out.

## 2. Business logic
- **FR-NOTIFY-001** lists "incoming calls" as its own notification class, and
  `E10-T01` already created a HIGH-importance `incomingCall` channel for it.
- `CallSignaling` (`lib/core/calls/call_signaling.dart`, E07-T09) is the only
  place an inbound invite is recognised. It exposes counters and
  `pathProbeEchoes`, but **no stream of call lifecycle events** — so this task
  adds one, narrowly.
- **The seam is additive and must change no call behaviour.** The state
  machine, the ring timer, the decline path and the migration controller stay
  byte-identical in behaviour; the only change is a broadcast emission at
  points that already exist.
- A call notification is **transient**: it is cancelled on answer, decline,
  timeout or remote cancel. A stale "incoming call" notification is worse than
  none, because the user taps it and nothing is there.

## 3. What this task does
- `call_signaling.dart`: add `final StreamController<CallNotice> _notices` +
  `Stream<CallNotice> get notices`, emitting at the **existing** handling
  points for: invite received, call answered, call declined, ring timeout,
  remote cancel. `CallNotice` carries `{ CallNoticeKind kind, String callId,
  String peerDeviceId }` and nothing else. Controller closed in the existing
  dispose/teardown path.
- `call_notification_source.dart`: maps `kind == invite` to
  `NotificationFacts(category: incomingCall, ...)`; maps every terminal kind
  to a **cancel** of that call's notification id.
- `bindings.dart`: register the source on `E10-T03`'s dispatcher.
- `call_signaling_test.dart`: assert the stream emits at each point **and**
  that the existing assertions still hold (this is the regression proof).

## 4. What this task does NOT do
- Does **not** change call state, timing, framing, the migration controller,
  or `CallSignalingCounters`. If a diff line changes what a call *does*, it is
  out of scope.
- Does **not** implement a full-screen incoming-call UI, `CallStyle`
  notifications, answer/decline notification actions, or a ringtone. Those are
  a design surface (`design/screens/call.md` is E07's contract, and it draws a
  *screen*, not a notification) — `OQ-E10-1`.
- Does **not** notify for PTT. **No PTT code exists anywhere in `lib/`**
  (`OQ-E10-3`); a notification for a feature with no producer would be
  untestable theatre.
- Does **not** wake the screen, acquire a wake lock, or start a service —
  `E10-T08` owns anything that keeps the process alive, and it is blocked on
  ADR-0007.
- Does **not** touch `E10-T03`'s policy or dispatcher logic. Register a
  source; that is the whole extension point.

## 5. Contract

### Functions
```yaml
- signature: "CallSignaling.notices -> Stream<CallNotice>"
  returns: "broadcast stream; emits at invite/answer/decline/timeout/remoteCancel"
  purpose: "The only new public surface on an E07-owned class — observation, not control"

- signature: "CallNoticeKind"
  returns: "enum { invite, answered, declined, timedOut, remoteCancelled }"
  purpose: "Closed set; a new kind is a new decision, not an implementation detail"

- signature: "CallNotificationSource(Stream<CallNotice> notices) -> NotificationSource"
  returns: "Stream<NotificationFacts> for invites; issues cancels for terminal kinds"
  purpose: "Posts the ring, and — equally important — takes it away"
```
Copy (no design contract; minimum viable, listed for review): title
`Incoming call`, body `<peerDisplayName>` or `Unknown device` when the
relationship has no name. Privacy level applies exactly as `E10-T03`'s policy
defines it — under `hidden`, body is `Someone is calling`.

## 6. Risks
- `CallSignaling` is a large, heavily-reviewed file (E07-T09 + `E07-B*`).
  Touching it is where a call regression comes from. Add the emissions at
  existing branch points; do not restructure.
- Emitting **inside** a lock/critical section can re-enter through a
  synchronous listener. Emit on a broadcast controller after the state
  transition completes.
- A terminal kind that never fires leaves a permanent ring notification.
  Every path out of "ringing" must emit exactly one terminal notice — verify
  by enumerating the exits, not by testing the happy one.
- The controller must be closed on teardown or every hot restart leaks a
  subscription.

**Deviations from spec/design:**
1. **`CallSignaling.dispose()` is a NEW method, not a call added to an
   existing one.** The task's §7 checklist item ("controller closed in the
   existing teardown") assumed `CallSignaling` already had a dispose/teardown
   path to hook into; it does not — `MessagingStack.dispose()`
   (`messaging_stack.dart:605-609`) never calls anything on `callSignaling`
   today, and that file is outside this task's `files:` fence. Resolved via
   the simplest in-fence reading: added `CallSignaling.dispose()` (closes
   `_notices`, safe to call twice, mirrors `CallSession.dispose()`'s own
   discipline in the same file) without wiring any new call site — the exact
   same "no composition-root call yet" shape `E10-T03`'s own `bindings.dart`
   comment already discloses for `NotificationDispatcher.stop()`. A test
   (`dispose closes the notices stream without throwing`,
   `call_signaling_test.dart`) proves the method itself works; wiring it into
   `MessagingStack`'s real teardown is `E10-T10`'s scope (adaptive background
   policy / app lifecycle), same as the dispatcher's own `stop()` gap.
2. **`notification_policy.dart`'s `_copyFor` was NOT extended with an
   `incomingCall` case**, so a posted call notification currently reads the
   generic `('NEXORA', 'Notification')` fallback rather than §5's proposed
   copy (`Incoming call` / `<peerDisplayName>` or `Someone is calling` under
   `hidden`). `notification_policy.dart` is not in this task's `files:`
   fence, and rule 6 treats a fence violation as a stop-and-disclose matter,
   not a judgment call to make silently — even though that file's own
   existing comment ("none of which is wired to this policy by this task")
   reads as anticipating exactly this extension. EARS-NOTIFY-8/9 are
   satisfied regardless (a notification IS posted, correctly categorised,
   and IS cancelled at every terminal kind — the criteria say nothing about
   the literal copy string, and §5 itself labels the copy table "minimum
   viable, listed for review", not a tested contract). Logged as
   `OQ-E10-T04-2` below rather than expanding this task's own file scope.
3. **`CallNotificationSource` takes a second constructor parameter,
   `{required NotificationSink sink}`, beyond §5's literal
   `CallNotificationSource(Stream<CallNotice> notices)`.** There is no way
   to issue the "cancel" half of this task's own contract ("maps every
   terminal kind to a cancel of that call's notification id") without a
   handle on something that can call `cancel()` — `NotificationSource`
   (`notification_dispatcher.dart`, required context, not in this task's
   `files:`) exposes only a `facts` stream a dispatcher POSTS through; it has
   no cancel-routing concept for a source to hook into, and inventing one
   would mean editing `notification_dispatcher.dart`, which is the same
   fence problem as Deviation 2. Resolved as the simplest reading that keeps
   every other file in scope: `bindings.dart` passes
   `notificationDispatcher.service` (the same `NotificationService`
   instance the dispatcher itself posts through, never a second one) so the
   cancel bypasses `NotificationPolicy` entirely — disclosed in
   `call_notification_source.dart`'s own header and tested directly
   (`a cancel is issued even when the sink reports the category disabled`).
4. **An `async*`/`await for` implementation of `CallNotificationSource.facts`
   was tried first and abandoned** — it subscribes to its source stream on a
   later microtask rather than synchronously inside `listen()` (unlike every
   other source in this codebase) and, confirmed by a minimal repro,
   `StreamSubscription.cancel()` on the resulting stream hangs forever while
   the generator sits suspended inside `await for` over a broadcast stream.
   Replaced with the `.where().map()` idiom `MessageNotificationSource.facts`
   already establishes (`where`'s predicate carries the `sink.cancel` side
   effect and returns `false` for a terminal kind, so only `invite` reaches
   `map`) — synchronous subscription, ordinary cancellation, and one fewer
   idiom for a future reader of this codebase to learn. Not a functional
   deviation from the task's own contract (§5 does not prescribe an
   implementation strategy for `facts`), recorded because it cost real
   debugging time and the next task adding a source with a side effect
   should not have to rediscover this.
