# E10-T06 · Group-event notifications

## 1. Goal
Tell the user when something happened to a group they are in — added,
removed, renamed, ownership moved, group deleted — without telling them
about the changes they made themselves.

## 2. Business logic
- **FR-NOTIFY-001** lists "group events" as its own notification class.
- The producer exists: `GroupMembershipService.handleControlFrame`
  (`group_membership_service.dart:522`) is where an **inbound** membership
  change is applied. Locally-initiated changes go through `_perform`
  (`:287`) and its callers (`addMember`, `removeMember`, `rename`,
  `grantAdmin`, `revokeAdmin`, `transferOwnership`, `deleteGroup`, `leave`).
- **Only inbound changes notify.** A user who just renamed a group does not
  need to be told they renamed it; a notification for one's own action is
  noise that trains people to ignore the channel. The distinction is
  structural — the emission point is the inbound handler, not `_perform` —
  so it cannot drift.
- Group key rotation is **not** a group event for this purpose. It is a
  cryptographic consequence of a membership change and notifying on it would
  double every notification.

## 3. What this task does
- `group_membership_service.dart`: add `Stream<GroupEventNotice> get
  groupEvents` (broadcast), emitted from the **inbound** control-frame path
  only, after the change is applied and persisted, carrying
  `{ GroupEventKind kind, String groupId, String? groupName, String
  actorDeviceId }`. Controller closed in the existing teardown.
- `group_notification_source.dart`: maps each notice to
  `NotificationFacts(category: groupEvent, ...)`, using a stable notification
  id per `groupId` so a burst of changes to one group collapses into one
  notification rather than five.
- `bindings.dart`: register on the dispatcher.

## 4. What this task does NOT do
- Does **not** change membership logic, permission checks, key rotation, or
  any control-frame parsing. `group_permissions.dart`,
  `group_key_rotation_service.dart` and `group_control.dart` are not in
  `files:` and must not be edited.
- Does **not** emit from `_perform` or any locally-initiated path (§2).
- Does **not** notify for group *messages* — those arrive through
  `InboundPipeline.delivered` and are already `E10-T03`'s `message` class.
  Notifying twice for one group message is the obvious bug this fence exists
  to prevent.
- Does **not** notify on key rotation.
- Does **not** add group-event UI, a group activity feed, or notification
  actions (`OQ-E10-1`).
- Does **not** decrypt group message content.

## 5. Contract

### Functions
```yaml
- signature: "GroupMembershipService.groupEvents -> Stream<GroupEventNotice>"
  returns: "broadcast; inbound-applied membership/metadata changes only"
  purpose: "Observation seam on E07's service — emits after the change is durable"

- signature: "GroupEventKind"
  returns: "enum { addedToGroup, removedFromGroup, memberJoined, memberLeft, renamed, adminChanged, ownershipTransferred, groupDeleted }"
  purpose: "Closed set matched to the operations the service already performs"

- signature: "GroupNotificationSource(Stream<GroupEventNotice> events, {required String selfDeviceId}) -> NotificationSource"
  returns: "Stream<NotificationFacts>, one stable notification id per groupId"
  purpose: "Collapses a burst of changes to one group into one notification"
```
Copy: title `<groupName>` or `Group` when the name is unknown; body per kind
(`You were added to this group`, `You were removed from this group`,
`A member joined`, `A member left`, `The group was renamed`, `Admins
changed`, `Ownership was transferred`, `The group was deleted`). Under
`hidden`, title is `NEXORA` and body is `Group activity`.

## 6. Risks
- Emitting **before** the change is persisted means a notification for a
  change a later failure rolls back. Emit after the write, inside the same
  success path.
- `removedFromGroup` / `groupDeleted` may arrive after the local group row is
  gone — capture `groupName` before the deletion, or the notification reads
  `Group` for the case where the name matters most.
- A membership change that fans out to a key rotation must still produce
  exactly one notice. Count the emissions in the test, don't eyeball them.
- The self-vs-other distinction depends on `actorDeviceId` being correct;
  an inbound frame that a peer forwarded on someone else's behalf must
  attribute the originator, not the sender, or "a member joined" names the
  wrong device.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-NOTIFY-12**: WHEN an inbound group control frame applies a
  membership or metadata change, the system SHALL post one `groupEvent`
  notification for that group. (FR-NOTIFY-001)
- **EARS-NOTIFY-13**: IF the change was initiated locally, THEN the system
  SHALL post nothing; and a change that triggers a key rotation SHALL still
  produce exactly one notification. (FR-NOTIFY-001)
