# E10-B04 · The retained engine collects a set of hosts per reopen

## The defect

E10-T08's engine retention is correct and load-bearing:

```kotlin
// MainActivity.kt:84-94
override fun cleanUpFlutterEngine(flutterEngine: FlutterEngine) {
  if (ForegroundMeshService.isRunning) {
    // Leave every Pigeon host attached -- the retained engine keeps driving
    // MessagingCoordinator's tick through the exact same hosts.
    super.cleanUpFlutterEngine(flutterEngine)
    return                                  // <-- detach() deliberately skipped
  }
  transportApiHost?.detach(...)
  notificationApiHost?.detach(...)
  backgroundApiHost?.detach(...)
  ...
}
```

Skipping `detach()` is right — the hosts must keep working while the app is
closed. The defect is what happens on the way back in:

```kotlin
// MainActivity.kt:49-52  — a reopened Activity reuses the cached engine
override fun provideFlutterEngine(context: Context): FlutterEngine? =
    FlutterEngineCache.getInstance().get(ForegroundMeshService.ENGINE_ID)
        ?: super.provideFlutterEngine(context)

// MainActivity.kt:54-75  — and unconditionally builds a whole new host set on it
override fun configureFlutterEngine(flutterEngine: FlutterEngine) {
  val host = TransportApiHost(messenger, this);          host.attach(messenger)
  val notificationHost = NotificationApiHost(messenger, this); notificationHost.attach(messenger)
  val backgroundHost = BackgroundApiHost(messenger, applicationContext); backgroundHost.attach(messenger)
}
```

`configureFlutterEngine` runs on every Activity attach, including onto a
cached engine. Nothing detaches the previous set, because the previous
Activity's `cleanUpFlutterEngine` took the early return. Per close/reopen
cycle, with the service running:

1. **A second `PowerStateMonitor` and four more broadcast receivers.**
   `BackgroundApiHost` constructs its monitor as a field
   (`BackgroundApiHost.kt:60`) and `attach()` calls `register()`
   (`:79`). `PowerStateMonitor.register()`'s `if (registered) return` guard
   (`PowerStateMonitor.kt:92`) is an **instance** field, so it does nothing
   across instances. The old monitor's four receivers are never unregistered
   and stay live on the application context, forever.
2. **A leaked `Activity`.** `TransportApiHost(messenger, this)` and
   `NotificationApiHost(messenger, this)` hold a strong reference to the
   Activity (`MainActivity.kt:59,63`; `NotificationApiHost.kt:31`). The old
   instances are kept alive by their own uncancelled `eventsScope`
   (`NotificationApiHost.kt:45`, cancelled only in `detach()`), so each
   destroyed Activity and its whole view hierarchy is retained.
3. **A stale `NotificationApiHost` serving live traffic while the app is
   closed** — the Pigeon `setUp` handler registered by the *destroyed*
   Activity's host is what `post()` runs through until the app is reopened,
   so every background notification is built with
   `NotificationManagerCompat.from(destroyedActivity)`. It works (a
   destroyed `Activity` is still a usable `Context` for the notification
   manager), which is why nothing has been observed — but
   `requestPermission()` on that same object would call
   `ActivityCompat.requestPermissions` on a destroyed Activity. This is the
   T08 carry-forward about activity-detached hosts, and this is its
   mechanism.

Pigeon channel *handlers* themselves do not accumulate — `setUp` replaces the
handler on the same channel name — so the growth is in objects and
receivers, not in dispatch.

## Why this is E10's problem and not a pre-existing one

Before this epic, `shouldDestroyEngineWithHost()` was always true: closing
the app destroyed the engine, the isolate and the process, and every one of
these objects went with it. `E10-T08` is precisely the change that makes the
process outlive the Activity indefinitely. The leak has no natural bound any
more, and the epic that removed the bound is the epic that should own it.

## Repro
1. Install on any Android device. Open the app, background it so
   `ForegroundMeshService` starts.
2. Swipe the app away from recents (Activity destroyed, service alive).
3. Reopen the app. Repeat steps 2-3 ten times.
4. `adb shell dumpsys activity broadcasts | grep -c nexora` and
   `adb shell dumpsys meminfo com.nexora.nexora` (Activities count).

## Expected
One `PowerStateMonitor`, four registered receivers, one live host set and
zero retained destroyed Activities, regardless of how many times the app is
opened and closed while the service runs.

## Actual
Statically determinable: N monitors, 4N receivers, N host sets and N-1
retained Activities after N reopens. Not observable in this environment (no
installable device — the standing E04 limitation), which is why the fix must
be structural rather than measured.

## Severity
**S3** — monotonic resource growth with no functional symptom until the
process is large enough to be killed, at which point the user's workaround
(force-stop and reopen) fully resets it. Not S2: nothing is broken per
cycle, and Dart-side dedup already neutralises any duplicate power events
(T09's review). Not S4: unbounded growth in a process this epic deliberately
made permanent is a real defect, and a retained Activity per cycle is not
small.

## Priority
**P2** — set under the decision authority explicitly delegated by the human
for this session. Rationale: the fix is confined to one Kotlin file and is a
handful of lines; the leak only exists because of a change this epic made;
and this project already has three MIUI battery/memory restrictions on
record (`E04-mesh-routing/retro.md:86-90`), so a process that grows without
bound is the worst possible shape on the only hardware the project has. Not
P1 — no user-visible failure, and no device is available to demonstrate one.

## Fix direction
- In `configureFlutterEngine`, detach and null any host set that is already
  attached to this engine **before** constructing a new one — i.e. make
  configure idempotent for a reused engine. The existing `detach()` methods
  already do the right cleanup (`BackgroundApiHost.detach` unregisters the
  monitor and cancels the scope; `NotificationApiHost.detach` cancels its
  scope). The hosts are per-`MainActivity` fields today, so reaching the
  previous instance needs a small ownership change — the two candidate
  shapes:
  - hold the host set alongside the engine (a companion-object map keyed by
    engine id) so any attach can find and retire its predecessor; or
  - keep the hosts per-Activity but make `PowerStateMonitor`'s registration
    a process-wide singleton so re-registering is genuinely idempotent, and
    rebind the Activity-holding hosts' `activity` reference instead of
    reconstructing them.
  Prefer whichever keeps `ForegroundMeshService.eventsApi`'s handoff
  (`BackgroundApiHost.kt:72,88-90`) unbroken across the swap — that
  reference must never be null while the service is alive, or
  `EARS-PLAT-8`/`PLAT-9` state events are lost.
- Consider holding the `Activity` weakly in `TransportApiHost` and
  `NotificationApiHost`, or passing `applicationContext` for everything
  except the two permission-request call sites that genuinely need an
  Activity. `BackgroundApiHost` already models this correctly
  (`applicationContext`, `MainActivity.kt:67`).
- Do **not** "fix" this by removing the `cleanUpFlutterEngine` early-return.
  That guard is what makes background operation work at all (ADR-0007
  option 1); detaching there would silently kill the tick's transport path
  the moment the user swipes the app away — a far worse bug than this one.

## Regression test (write it first)
No Kotlin unit-test harness exists in this project (`E04-T03b`'s
no-mock-Kotlin rule), so the honest options, in order of preference:
- Refactor the ownership so the "retire the previous host set" step is
  reachable from a plain JVM test, and assert that attaching twice to one
  messenger leaves exactly one registered `PowerStateMonitor`. If this is
  not achievable without changing the hosts' shape more than the fix needs,
  say so explicitly rather than writing a test that asserts nothing.
- At minimum, add an assertion at the Dart boundary that a second
  `attach` cycle does not double-deliver `onPowerStateChanged`
  (`power_state_test.dart` already owns the dedup case) — and state plainly
  in the run log that the native object-count claim is **unverified in this
  environment**, per the same discipline `E10-T08` §9 used. Do not claim an
  on-device result that was not obtained.

## What this fix does NOT do
- Does **not** remove or weaken `cleanUpFlutterEngine`'s
  `ForegroundMeshService.isRunning` early-return, or
  `shouldDestroyEngineWithHost()`'s inversion. Engine retention is ADR-0007's
  chosen architecture.
- Does **not** change `ForegroundMeshService.kt`, `BootReceiver.kt`,
  `PowerStateMonitor`'s signal-reading logic, or any Pigeon schema.
- Does **not** change the `PowerState` contract, the four observed
  broadcasts, or the `RECEIVER_NOT_EXPORTED` posture.
- Does **not** add a headless Dart entrypoint (`E10-B05`).
- Does **not** touch `AndroidManifest.xml` (`E10-B01` owns the one manifest
  change this sweep files).
- Does **not** wire any Dart-side `dispose()` (`E10-B06`).

## Feedback log
- 2026-09-04 — Fixed directly, decision authority explicitly delegated to
  the agent for this session. Shape chosen: **candidate 1** — hold the
  host set alongside the engine (a `private class HostSet` + companion-
  object `attachedHosts` field on `MainActivity`, retired via the
  existing `detach()` methods before a new set is constructed). Not a
  literal "map keyed by engine id" since exactly one engine is ever cached
  (`FlutterEngineCache` under the single `ForegroundMeshService.ENGINE_ID`
  key) — a plain nullable field is the same guarantee with less
  incidental machinery, and the `HostSet` captures its own `BinaryMessenger`
  so retirement always detaches against the messenger it actually attached
  to. Rejected candidate 2 (process-wide `PowerStateMonitor` singleton +
  rebindable `activity` reference on `TransportApiHost`/`NotificationApiHost`)
  for three reasons: (a) it only closes the `PowerStateMonitor`/receiver
  half of the leak — the leaked-Activity half (item 2 in §The defect) needs
  the Transport/Notification hosts to stop holding a strong `Activity`
  reference across reopens regardless, which candidate 2 also requires via
  a *second*, separate change (rebinding `activity`) to the same two files;
  candidate 1 closes both halves as one side effect of retiring the whole
  set, because nothing is left holding the previous hosts (and therefore
  the previous Activity) once `detach()` runs and the companion reference
  moves to the new set; (b) candidate 2 needs `activity` to become a `var`
  in `TransportApiHost.kt` and `NotificationApiHost.kt` plus a process-wide
  singleton rewrite of `PowerStateMonitor.kt` — three files beyond
  `MainActivity.kt` versus zero for candidate 1, which stays inside this
  task's own `files:` fence entirely; (c) `BackgroundApiHost`'s existing
  `attach`/`detach` pair already models "one registration lives exactly as
  long as one host instance" correctly (task header, `applicationContext`)
  — candidate 1 reuses that contract as-is; candidate 2 would have
  special-cased it.

## Run log

  (`transportApiHost`/`notificationApiHost`/`backgroundApiHost` + the
  `BinaryMessenger` they were attached with) and a companion-object
  `attachedHosts: HostSet?` field. `configureFlutterEngine` now calls
  `attachedHosts?.detach()` (which runs the existing, already-correct
  `TransportApiHost.detach`/`NotificationApiHost.detach`/
  `BackgroundApiHost.detach`) and clears `attachedHosts` **before**
  constructing the new host set, then records the new set into
  `attachedHosts` after attaching it. `cleanUpFlutterEngine`'s

  itself, on this Activity's own fields) now also clears `attachedHosts`,

  detach sequence in `cleanUpFlutterEngine` run synchronously on the

  diff caused. Net effect: **every Kotlin change on `epic_10` right now
