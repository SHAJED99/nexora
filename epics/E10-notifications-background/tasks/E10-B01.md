# E10-B01 · The boot receiver can never fire

## The defect

```xml
<!-- android/app/src/main/AndroidManifest.xml:71-77 -->
<receiver
    android:name=".background.BootReceiver"
    android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>
```

`android:exported="false"` means only components running under this app's own
UID may deliver an intent to this receiver. `ACTION_BOOT_COMPLETED` is
broadcast by the system server (UID 1000), a different UID, so
`ActivityManagerService`'s broadcast dispatch skips the receiver before
`BootReceiver.onReceive` is ever reached. A manifest-declared receiver for a
system broadcast must be `android:exported="true"`; Android's own
boot-receiver documentation declares it that way.

Everything *behind* the receiver is correct and was verified in T08's review:
`RECEIVE_BOOT_COMPLETED` is declared (`AndroidManifest.xml:31`), the
`wasMessagingActive` guard is real (`BackgroundApiHost.kt:41`, set at `:110`,
cleared at `:128`), and `BootReceiver.kt:32-39` calls
`ContextCompat.startForegroundService` correctly. The one attribute in front
of all of it makes the whole path unreachable.

Note the `<service android:exported="false">` two lines above is **correct**
and must not be changed — the service is only ever started by this app.

## Repro
1. Install the app on any Android device; open it and let the foreground
   service start (so `messaging_active` persists as `true`).
2. Reboot the device. Do **not** open the app.
3. Observe the notification shade and `adb shell dumpsys activity services
   com.nexora.nexora`.

## Expected
EARS-PLAT-10 (`E10-T08.md`), ADR-0007 §S3 ("build it now, in `E10-T08`"):
`ForegroundMeshService` is restarted after boot without the user opening the
app, and the ongoing notification is present.

## Actual
No broadcast reaches `BootReceiver`, the service is not started, and the mesh
stays down until the user manually opens the app — which is exactly the state
ADR-0007 §S3 was accepted to eliminate. Statically determinable from the
manifest; not observable in this environment (no installable device — the
standing E04 limitation), which is why the regression test below is a
manifest assertion rather than an on-device check.

## Second, related defect in the same criterion — for the planner

**`EARS-PLAT-10` is defined twice, with different text**: `E10-T08.md:236`
(boot restart) and `E10-T09.md:157` (power-state emission). `epic.md:62`
lists "PLAT-10, 11" as T09's, so the boot criterion is effectively
un-indexed, and the epic's EARS-trace row looked green because **T09's**
tests cover **T09's** PLAT-10. A repo-wide grep of `test/` for
`BOOT_COMPLETED|BootReceiver|messaging_active` returns exactly one hit — a
prose comment at `background_service_test.dart:9`. Nothing would fail if
`BootReceiver.onReceive` were emptied or the guard inverted.

This is the same shape `E09-B07`'s retro lesson already named (an acceptance
criterion the task's own contract cannot satisfy), and T10's review already
flagged the DoD contradiction. Renumbering one of the two ids is a
**planner** call at this epic's retro, not part of this fix.

## Severity
**S2** — a `must`-graded, ADR-accepted feature is 100% non-functional on
every device, with the "workaround" (open the app) being precisely the thing
the feature exists to remove. Not S1: nothing crashes, no data is lost, and
the app is fully functional once opened.

## Priority
**P1** — set under the decision authority explicitly delegated by the human
for this session. Rationale a human would apply: the fix is a one-word
manifest change, it restores an ADR-accepted commitment, and shipping E10 to
`development` with its headline reliability feature silently dead would make
every later claim about background operation untrustworthy. Cheap + dead
feature + accepted ADR = do it now.

## Fix direction
- `android:exported="false"` → `android:exported="true"` on the
  `.background.BootReceiver` `<receiver>` element only. Leave the
  `<service>` element's `exported="false"` alone.
- The receiver stays safe when exported: `onReceive` already hard-filters on
  `intent.action != Intent.ACTION_BOOT_COMPLETED` (`BootReceiver.kt:34`) and
  then on the persisted flag (`:35`), so a spoofed intent from another app
  can at most start a service this app was already configured to start.
  Do **not** add a signature permission or extra guard beyond confirming
  those two lines still stand — that would be scope creep.
- Do **not** attempt to fix the headless-revive limitation here: after a
  reboot there is still no Dart isolate, so the restarted service shows its
  notification while nothing relays. That is `E10-B05`, and it is `blocked`
  on a planner decision. This fix makes the receiver fire; B05 decides what
  should happen when it does.

## Regression test (write it first)
A test that reads `android/app/src/main/AndroidManifest.xml` and asserts the
`BootReceiver` `<receiver>` element carries `android:exported="true"` while
the `ForegroundMeshService` `<service>` element carries
`android:exported="false"`. This is the only layer at which this defect is
assertable in this environment, and it is the layer the defect lives at.
Must fail on today's manifest.

Additionally assert `BootReceiver`'s guard logic is exercised at all — at
minimum that `RECEIVE_BOOT_COMPLETED` is declared and the receiver's
intent-filter names `android.intent.action.BOOT_COMPLETED`.

## What this fix does NOT do
- Does **not** change `BootReceiver.kt`, `ForegroundMeshService.kt`,
  `BackgroundApiHost.kt` or any other Kotlin file. The Kotlin is correct.
- Does **not** change the `<service>` element, any permission, or any other
  manifest entry.
- Does **not** add a headless Dart entrypoint or touch `lib/app/main.dart`
  (`E10-B05`, planner-owned).
- Does **not** renumber the duplicated `EARS-PLAT-10` id — planner, at retro.
- Does **not** request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (`OQ-E10-4`,
  ADR-0007 §S2 — still deferred).
