# E10-B10 · `ensureReady()` doesn't honor its own `Future<bool>` contract

## The defect

`NotificationService.ensureReady()`'s doc comment states the contract
plainly: "Returns true when channels exist and permission is granted;
false when denied." Two real ways it could instead throw or hang forever,
both confirmed by probe:

1. **`_api.ensureChannels()` throwing.** With no host attached yet (the
   window before `NotificationApiHost.attach` runs), the real generated
   Pigeon call throws a `PlatformException`/`MissingPluginException`
   rather than returning. `ensureReady()` had no `try`/`catch` at all, so
   this propagated straight to the caller.
2. **`permissionResults.first` never resolving.** If the OS never
   delivers `onPermissionResult` -- reachable in production, since
   `NotificationApiHost.requestPermission()` can be called against a
   destroyed `Activity` while `ForegroundMeshService` keeps the engine
   alive (the exact "no Activity, revived engine" shape `E10-B05` already
   found on the neighboring foreground-service-notification path) -- the
   `await` on that stream's first event had no bound and hung forever.

`notification_dispatcher.dart`'s `start()` sets `_started = true` before
awaiting `ensureReady()` and only subscribes its notification sources
after it returns, so either failure mode silently disabled every E10
notification source (message, call, connection request, group event,
storage warning) for the rest of the process, with nothing surfaced to
the user and no way to recover short of restarting the app.

## Severity

**S2** -- a real failure mode reachable via a documented, adjacent
lifecycle interaction (`E10-B05`'s own finding), with a total,
process-lifetime loss of every notification source and no user-visible
signal that anything went wrong. Not S1: the app itself keeps running
normally; only notifications stop. Not S3: the blast radius is total
(every category, not one) and the recovery (restart) is not obvious to a
user who has no idea notifications silently stopped.

## Fix direction

Wrap the whole method body in `try`/`catch`, returning `false` on any
exception -- matching the already-documented "false when denied"
contract rather than distinguishing "denied" from "couldn't determine."
Bound every awaited step (`ensureChannels`, `hasPermission`,
`permissionResults.first`, `requestPermission`) with a `.timeout(...)`,
matching this codebase's existing best-effort-platform-call convention
(`FirebaseMetadataService`/`SyncCursorService`, both a 10s default).

## What this fix does NOT do

- Does **not** change `post()`'s or `cancel()`'s own contracts -- both
  already correctly never throw.
- Does **not** distinguish "permission denied" from "couldn't determine
  readiness" in the return value -- both collapse to `false`, matching
  the method's own pre-existing, unchanged doc comment.
- Does **not** touch the tap-delivery gap -- that is `E10-B09`, a
  separate finding on the same task, filed and fixed independently.

## Regression test (write it first)

Two new tests in `notification_service_test.dart`:
- `test_EARS_PLAT_5_ensureReady_returns_false_not_throws_when_the_host_channel_is_unavailable`
  -- no mock handler registered for `ensureChannels`, confirming
  `ensureReady()` returns `false` rather than propagating the resulting
  `PlatformException`.
- `test_EARS_PLAT_5_ensureReady_returns_false_rather_than_hanging_when_the_permission_result_never_arrives`
  -- `hasPermission` reports `false`, `requestPermission` completes
  normally, but no `onPermissionResult` event is ever sent; confirms
  `ensureReady()` returns `false` after the (test-injected, short) timeout
  rather than hanging. `NotificationService`'s constructor gained an
  optional `readyTimeout` parameter so this test doesn't need to wait the
  real 10s default.

Both confirmed failing on pre-fix code (the first with the exact
predicted `PlatformException`; the second by genuinely hanging, caught
only by the test runner's own 30s cap) and passing post-fix.
