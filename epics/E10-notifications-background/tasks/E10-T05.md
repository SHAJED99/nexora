# E10-T05 · Connection-request notifications

## 1. Goal
Tell the user when an unknown device wants to talk to them — the one
notification class that is a *decision prompt* rather than an update.

## 2. Business logic
- **FR-NOTIFY-001** lists "connection requests" as its own class.
- The producer already exists: `PrekeyExchange` calls
  `EvaluateConnectionRequestUseCase` when an inbound session request arrives
  (`prekey_exchange.dart:413` and `:483`) and receives back a `Relationship`
  whose `state` is one of `trusted | allowed | unknown | blocked`
  (`relationship.dart:11`).
- **Only `unknown` is notifiable.** `trusted`/`allowed` peers are already
  connections — a notification adds nothing. **`blocked` must never notify**:
  E02's whole point is that a blocked device cannot reach the user, and a
  notification is reach. This is the security-relevant half of the task.
- The seam is additive and changes no evaluation, acceptance or session
  behaviour.

## 3. What this task does
- `prekey_exchange.dart`: add `Stream<ConnectionRequestNotice> get
  connectionRequests` (broadcast), emitted at the two existing evaluation
  sites **after** the relationship resolves, carrying
  `{ String peerDeviceId, RelationshipState state }`. Controller closed in the
  existing teardown.
- `connection_request_notification_source.dart`: filters to
  `state == RelationshipState.unknown`, maps to
  `NotificationFacts(category: connectionRequest, peerDeviceId: ...)`,
  de-duplicates per peer within the process so a retrying peer does not
  produce a notification per attempt.
- `bindings.dart`: register on the dispatcher.

## 4. What this task does NOT do
- Does **not** change connection evaluation, auto-accept behaviour, session
  establishment or prekey consumption. No behavioural line in
  `prekey_exchange.dart` moves.
- Does **not** activate `EvaluateConnectionRequestUseCase`'s inert
  `autoAcceptSpecific` / `requireAuthForUnknown` flags (`E02-T01`'s
  `OQ-E02-T01-2`, ⚪ deferred). They stay exactly as inert as they are.
- Does **not** notify for **trust requests**, the class `FR-NOTIFY-001` lists
  next to connection requests. **No inbound trust-request frame exists in the
  build** — there is no control kind for it and no producer — so building a
  notification for it would mean inventing the protocol first. `OQ-E10-6`.
- Does **not** add accept/decline actions to the notification, or a
  connection-request screen. No design contract covers either (`OQ-E10-1`).
- Does **not** notify for a blocked peer, under any privacy level, ever.
- Does **not** touch the dispatcher or policy from `E10-T03`.

## 5. Contract

### Functions
```yaml
- signature: "PrekeyExchange.connectionRequests -> Stream<ConnectionRequestNotice>"
  returns: "broadcast; one event per inbound session request that reached evaluation"
  purpose: "Observation seam; emits for every state so the filter lives in the source, testably"

- signature: "ConnectionRequestNotice"
  returns: "{ String peerDeviceId, RelationshipState state }"
  purpose: "Carries the decision the use case already made — this task re-decides nothing"

- signature: "ConnectionRequestNotificationSource(Stream<ConnectionRequestNotice> requests) -> NotificationSource"
  returns: "Stream<NotificationFacts>, `unknown` only, de-duplicated per peerDeviceId"
  purpose: "Where the blocked/known filter is applied and proven by test"
```
Copy: title `Connection request`, body `An unknown device wants to connect`.
Under `senderOnly`/`full` the body may name the device id's short form only
if a display name exists in the clear; an unknown peer has none by
definition, so in practice this class reads the same at every privacy level.

## 6. Risks
- **Emitting before the filter is the design.** The stream deliberately emits
  every state so the "blocked never notifies" rule is asserted in a test on
  the source, rather than being invisible because the event never existed.
  Do not "optimise" by filtering at the emission site — that moves a
  security rule into a file this task must not change the logic of.
- A peer retrying a handshake can emit many times per minute; without the
  per-peer de-dup the user gets a notification storm from a device they have
  not accepted. That is both annoying and an amplification vector.
- `prekey_exchange.dart` participates in E03's crypto path. Nothing here may
  read, log or store key material — the notice carries a device id and a
  state, and that is all.

**Deviations from spec/design:**
1. **`PrekeyExchange.dispose()` added, not wired anywhere.** Same shape as
   `CallSignaling.dispose()` (E10-T04): `PrekeyExchange` had no dispose
   method before this task. `_connectionRequests` needs somewhere to be
   closed per §7's checklist item ("controller closed in the existing
   teardown"), but `PrekeyExchange` had no existing teardown path of its
   own — `MessagingStack.dispose()` (`messaging_stack.dart:605`) never calls
   anything on `prekeyExchange` today, and wiring that cross-file call site
   is outside this task's `files:` fence. A narrow `dispose()` method was
   added (closes `_connectionRequests` only) so a future task (or a test)
   has a well-defined place to call into; it is not invoked from any
   composition-root path by this task. Mirrors E10-T04's own disclosed
   deviation for `CallSignaling.dispose()` exactly.
2. **`connectionRequests` emitted from two call sites whose only shared
   line is `_evaluateConnectionRequest(...)`.** Task file §3 describes "the
   two existing evaluation sites" as a pair; both are one-line insertions
   (`_emitConnectionRequestNotice(peerDeviceId, relationship)`) placed
   immediately after the relationship resolves and before any
   `if (relationship == RelationshipState.blocked)` branch, so the emission
   itself never influences which branch executes. No behavioural line
   moved.
