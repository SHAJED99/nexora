# E06-T16 · Finish `FR-UI-005` — migrate the remaining views

> `E06-T15` built the mechanism (`AppStrings`, `context.l10n`) and migrated two
> views. This migrates the remaining **eight settings sub-screens**, all of
> which pass `make design-verify` at 100% today, so the gate can prove no
> rendered string changed.

## 1. Goal
Every visible string in the settings area comes from `context.l10n.<key>`, and
every settings view uses logical directional geometry.

## 2. Business logic
Same as `E06-T15` §2, unchanged: `FR-UI-005`, the `context.l10n` shape from
`documentation/Design.md` §111, logical insets from §112, **no new package**,
and **not one rendered string may change**.

## 3. What this task does
- Migrates the eight remaining settings sub-screen views onto `AppStrings`.
- Adds their strings as getters, reusing an existing getter wherever the copy
  is already present (`EARS-UI-14`).
- Converts literal directional geometry in those files.
- Extends `_migratedViews` in the test so the existing literal-scan and
  geometry-scan tests cover them automatically.

## 4. What this task does NOT do  ← the scope fence
- **Does NOT migrate `dashboard`, `conversations`, `chat` or `devices`.** All
  four currently **fail** the design gate, so a copy regression there would be
  invisible — the gate cannot distinguish a new failure from the existing one.
  They belong after **P9** triages those deltas
  (`docs/product-completeness-audit.md`). This is the whole reason they are
  excluded, and it is not an arbitrary boundary.
- **Does NOT migrate `welcome` or `login`.** Both are registered in
  `design/sources.yaml` but have **no Flutter probe dump**, so
  `make design-verify … IMPL=flutter` cannot gate them at all. Migrating copy
  with no gate is exactly the situation `E06-T15` had a safety net for and
  these do not.
- Does NOT add a second locale, `intl`, `flutter_localizations`, `.arb` files
  or `l10n.yaml` — each is a rule-3 `new_dependency` call.
- Does NOT reformat or tidy beyond the substitutions.

## 5. Contract

### UI
- **Gate:** all ten settings screens must report `PASS … match 100%`.
  Note the percentage alone is **not** sufficient evidence: a copy mismatch is
  reported as its own hard failure while the element-match percentage can stay
  at 100%. Read the report, not the number (`E06-T15` proved this by
  falsification).

### External services & flags
None. **No new dependency.**

## 6. Risks
1. A single altered character fails an approved contract. Move the literal
   verbatim; never retype it.
2. `fromLTRB(l, t, r, b)` → `fromSTEB(start, top, end, bottom)` is not a
   rename. Under LTR they coincide, so the design gate cannot catch a swap.
3. Copy already present in `AppStrings` must reuse its getter, not gain a
   second one.
4. Some views hold strings in top-level `final` collections or `static const`
   fields with no `BuildContext` (this is what made `E06-T15` larger than it
   looked). Those need a context-taking builder, not a substitution.

**EARS-UI-12**, **EARS-UI-13** and **EARS-UI-14** — by extending their existing
tests to the eight further views. No new EARS id: the behaviour asserted is
identical, and a second id for the same criterion would inflate the count
without proving anything new.

### Tests

- `test_EARS_UI_13_migrated_views_use_no_literal_directional_geometry` → same.
- `test_EARS_UI_14_shared_strings_resolve_to_one_key` → grows with the table.
