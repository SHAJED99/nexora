# E06-T13 · Design gap pass for the rich message types

## 1. Goal
Produce the human-approved design contracts that voice messages, PTT,
attachments and location-in-chat need **before** any of them is sharded —
so the second half of FR-COMM-001 is built against a contract instead of
against taste.

## 2. Business logic
- **FR-COMM-001 is bigger than text:** "personal communication via text,
  voice messages, PTT, voice calls, attachments, and location sharing."
  (Voice *calls* are E07's; the rest are E06's.) E06's own §Risks
  mitigation is the reason text shipped first: *"Sub-shard text-only first;
  voice/PTT/attachments/location as follow-on tasks within the epic rather
  than one giant task."* This task is the hinge between the two halves.
- **Rule 2 makes this a prerequisite, not a nicety.** A frontend task
  without a `design_contract:` is not shardable
  (`skills/task-sharding` §Precondition; `make validate` enforces it). The
  design source draws an `add` button, a `mic` button and one
  file-transfer bubble — and **no** recording UI, no PTT interaction, no
  attachment picker, no voice-message bubble, no location bubble. Sharding
  four frontend tasks today would mean four tasks pointing at contracts
  that do not exist.
- **GAP-010 already records this**, with E06-T11 rendering `add` and `mic`
  as inert affordances in the GAP-004 precedent. This task converts that
  placeholder into real, derived, approved contracts.
- **Derived, not invented** (`skills/design-fidelity` §3): each contract is
  built from the primitives `design/screens/chat.md` already measures —
  the bubble geometry and fills, the `r12px`/`r9999px` radii, the
  `rgb(53,37,205)` accent, the 12/14/16/22/24px type scale, the existing
  `Material Symbols Outlined` glyph set. Every one is marked
  `source: derived` and traced to an SRS id. Nothing new is introduced
  without the human seeing it.

## 3. What this task does
- A gap-pass over the four journeys, each producing a `design/gaps.md`
  entry (GAP-014…) with spec id, what the design shows, what it omits, the
  primitives the derivation reuses, and a concrete proposal:
  - **Voice message** — the record interaction on the `mic` button
    (press-and-hold vs tap-to-toggle is a real product choice, not a detail
    — put both to the human), the recording indicator, cancel, and the
    playback bubble (duration, waveform or plain progress, play/pause).
  - **PTT** — walkie-talkie behaviour is a *mode*, not a bubble: where it
    is entered from, what it looks like while transmitting and receiving,
    and whether it produces a message in the thread at all. This is the
    least-specified of the four and the most likely to need the human
    rather than a derivation.
  - **Attachments** — the picker entry from `add`, the in-progress bubble
    (the design's own `troubleshoot` / `Backup: Family Photos` /
    `In progress... 78%` treatment is the primitive to derive from), and
    the completed/failed states the design does not draw.
  - **Location in chat** — the share entry point, and the received bubble.
    Note the interaction with FR-TRUST-006's location-access control and
    FR-MSG-007's `LOCATION-OFF > LOCATION-ON` conflict precedence: location
    is already a governed capability in this product, and E09 owns location
    sharing — so this contract must not quietly redefine it.
- Three hand-written contracts marked `source: derived`
  (`chat-voice.md`, `chat-attachment.md`, `chat-location.md`), each with
  its element checklist, verbatim copy, and the tokens it reuses **by name
  from the chat contract's measured table**. PTT is deliberately *not*
  given a contract yet — see `OQ-E06-T13-1`.
- `design/gaps.md`'s gate line reset to ⏳ for the new entries, per
  `skills/design-fidelity` §Recording the gate.
- `epic.md` §Tasks updated with the follow-on tasks this pass makes
  shardable, listed but **not** sharded — sharding them is a separate
  planning pass once the contracts are approved.

## 4. What this task does NOT do
- Does NOT write any Dart, and does NOT build any screen.
- Does NOT shard the follow-on frontend tasks. They become shardable when
  their contracts are approved, and a contract approved and a task written
  in the same breath skips the gate that makes the approval mean anything.
- Does NOT regenerate or hand-edit `design/screens/chat.md`'s generated
  tables. The new contracts are separate files (rule 1 of design-fidelity).
- Does NOT decide voice codecs, file size limits, storage policy, or
  transport chunking. Those are engineering decisions for the tasks that get
  sharded from these contracts, and several belong to E08 (storage) and
  E09 (location).
- Does NOT approve its own gaps. Every entry lands 🟡 with an empty
  `approved by:` line (L-process-002 — an agent-approved gap was already a
  lesson in this project once).

## 6. Risks
- **The strong pull here is to design the feature rather than derive it.**
  Four journeys with no design source is a blank canvas, and a planner
  filling it produces a product nobody agreed to. Every proposal must be
  traceable to an existing primitive plus a spec id; where neither exists —
  PTT's interaction model, most obviously — the honest output is a
  question, not a mockup.
- Location overlaps E09 and attachments overlap E08. Deriving a contract
  that presumes a retention policy or a permissions model those epics have
  not decided creates a cross-epic conflict that only surfaces when they are
  built. Reference their scope explicitly and stop at the boundary.
- Do not let the contracts grow into a design system. Three focused
  contracts beat one sprawling "rich messaging" document nobody reads to
  the end.

### Tests
No automated test — this task's output is documents. Its verification is
mechanical and is performed by the reviewer:
- every new `design/screens/*.md` carries `source: derived` and a spec id;
- every token named in a derived contract appears in `chat.md`'s measured
  token table (grep each value — a value that is not there is an invented
  token and a finding);
- every gap entry has an **empty** `approved by:` line;
- `make validate` passes, and the `design_contract_approval` gate line reads
  ⏳ AWAITING HUMAN.

## Open Questions
- **OQ-E06-T13-1 — PTT has no design source and no derivable primitive, so
  it gets a question rather than a contract.** Push-to-talk is a *mode*
  (hold to transmit, release to listen, near-real-time), not a message
  bubble, and `design/screens/chat.md` draws nothing that implies one: the
  `mic` button reads as voice-message recording, and there is no
  transmitting state, no channel indicator, no listening state anywhere in
  the design source. Deriving one from bubble primitives would be inventing
  an interaction model, which rule 2 forbids as squarely as dropping an
  element does. The real questions for the human: is PTT a live half-duplex
  stream (which is closer to E07's voice-calls work than to messaging), or
  a fast voice-message loop? Does it appear in the thread afterwards? Is it
  per-conversation or a separate surface? **Advisory recommendation: park
  PTT until E07's voice-call work settles the real-time transport
  question**, because a half-duplex live stream shares E07's problems and
  almost none of E06's — then design it once, against a transport that
  exists. Recorded here with an owner so it is not silently dropped from
  FR-COMM-001's scope.
