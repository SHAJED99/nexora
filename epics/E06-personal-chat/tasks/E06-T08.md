# E06-T08 · Delivery acknowledgements

## 1. Goal
Make the tick marks the design draws mean something: give
`Accepted`/`Delivered`/`Read` an actual producer, so a sender learns what
happened to their message instead of the state machine stopping at `Sent`
forever.

## 2. Business logic
- **The gap, found by applying E04-B03's union-sufficiency check
  (L-process-005) to E06's own scope.** `DeliveryState` has seven states
  (`delivery_state_machine.dart:13`). E05-T02 writes `queued`/`sent`/
  `failed`; E05-T03 writes `accepted` on the **receiving** device.
  **Nothing ever tells the sender.** `delivered` and `read` have no
  producer anywhere, on any device, and never have.
- **The design assumes otherwise.** `design/screens/chat.md` draws three
  distinct tick treatments — `check` (element 25), grey `done_all`
  (element 22), green `done_all` (element 14). Two of the three have no
  data source without this task. GAP-009 records the mapping; this task is
  what makes two-thirds of it real.
- **E05-B03's resolution constrains the vocabulary.** The human resolved
  (Option A) that `Sent` means *durably enqueued locally* — it is applied
  on an INSERT that cannot fail, so it says nothing about the radio. That
  makes the *remote* states the only ones carrying real information, which
  is precisely why this task matters more than it looks.
- **Acknowledgements are metadata about ciphertext, never content.** An ack
  carries a message id and a state, both of which a relay already sees in
  the frame header (FR-ROUTE-004). It must not carry, and must not require,
  anything derived from plaintext — FR-ROUTE-003.
- **Read receipts are a privacy choice, not a technical default.** Sending
  "I read your message" tells someone when you looked at your phone. Every
  serious messenger makes this a setting. There is no spec id and no design
  source for that setting — see `OQ-E06-T08-1`; until it is answered this
  task builds the *mechanism* and leaves `read` acks **off**.

## 3. What this task does
- **The ack control sub-protocol**, as `PayloadType.control` frames
  (E06-T02) over `InboundPipeline`'s `ControlHandler` seam (E06-T05):
  `deliveryAck { messageId, state, observedAtMs }` where `state` ∈
  `{accepted, delivered, read}`.
- **Producing acks on the receiving device:**
  - `accepted` — emitted when `ReceiveMessageUseCase` persists a new
    message (it already writes `accepted` locally; this sends the same fact
    back). Not emitted for a duplicate.
  - `delivered` — emitted at the same point. On this app `accepted` and
    `delivered` collapse: there is no separate "handed to the UI layer"
    moment, and inventing an artificial delay between them to justify two
    states would be fiction. **Both are sent; the sender records the higher
    one.** This is stated here rather than left implicit because a future
    reader will otherwise assume a step is missing.
  - `read` — the mechanism exists and is **disabled** pending
    `OQ-E06-T08-1`. Behind a single named constant, not scattered `if`s.
- **Consuming acks on the sending device:** validate that the ack's
  `messageId` belongs to a message this device sent to *that* peer, then
  transition via `DeliveryStateMachine` (never a raw enum write) and append
  the `delivery_states` row through `MessagingCoordinator.recordStored`'s
  existing path. An ack for an unknown or foreign message id is dropped and
  counted — an unvalidated ack lets any peer rewrite any message's state.
- **Monotonic only.** `DeliveryStateMachine` already rejects backward
  transitions (`accepted → sent` throws). A late or out-of-order ack must be
  a no-op, not an exception that kills the pipeline: check
  `canTransition` before `transition`.
- Registered as a control handler in `messaging_stack.dart`.

## 4. What this task does NOT do
- Does NOT enable read receipts (`OQ-E06-T08-1`).
- Does NOT define what `Stored` means or produce it — that is
  `OQ-E06-T11-2`, inherited from OQ-E05-T03-1, and it is a UI-semantics
  question this task deliberately does not pre-empt.
- Does NOT retry, re-request or reconcile missing acks. If an ack is lost,
  the message simply stays at its last known state. Building a
  reconciliation protocol here would be the gap-fill protocol wearing a
  disguise (see OQ-E06-T06-2, owned by E11).
- Does NOT write `RelayDeliveryState.failed` or introduce a delivery
  timeout that fails a message. If a future task adds one, OQ-E06-T06-3's
  reclaim-set constraint binds it.
- Does NOT modify `DeliveryStateMachine`, `ReceiveMessageUseCase`,
  `SendMessageUseCase`, or the `messages`/`delivery_states` schema.
- Does NOT render anything. T11 reads the state; this task produces it.

## 5. Contract

### Functions
```yaml
- signature: "DeliveryAck.serialize() -> Uint8List"
  purpose: "{messageId, state, observedAtMs} as a control-frame body, same framing idiom as the rest"

- signature: "DeliveryAck.deserialize(Uint8List bytes) -> DeliveryAck"
  raises: "FormatException; an unknown state value is rejected, never coerced"

- signature: "DeliveryAckService.onMessageStored(Message message, String senderDeviceId) -> Future<void>"
  purpose: "receiving side — emits accepted + delivered acks back to the sender; never for a duplicate"

- signature: "DeliveryAckService.handleControlFrame(RelayPacketFrame frame) -> Future<void>"
  purpose: "sending side — validates ownership, then advances state through DeliveryStateMachine"

- signature: "DeliveryAckService.markRead(String messageId) -> Future<void>"
  purpose: "emits a read ack IF read receipts are enabled; a no-op while OQ-E06-T08-1 is open. Called by T11 when a message is displayed."

- signature: "DeliveryAckService.counters -> DeliveryAckCounters"
  returns: "{sent, accepted, rejectedForeign, rejectedUnknownMessage, staleIgnored}"
  purpose: "so 'why is this message still on one tick?' is answerable"
```

### Data
No schema change — `delivery_states` (E05-T01) is the existing sink and
finally gets its second writer.

## 6. Risks
- **An unvalidated ack is a state-injection primitive.** Any peer could mark
  any message `read`. The ownership check (this device sent it, to that
  peer) is the security control, not a sanity check — test it as such.
- Ack storms: two acks per message doubles mesh traffic for text chat, and
  NFR-BATT-001 asks for less, not more. Keep acks small, do not ack an ack,
  and never ack a duplicate.
- `accepted` and `delivered` arriving in either order over a mesh: the
  transition guard must make the later-and-lower one a no-op. Test with the
  acks deliberately reversed.
- The `read`-disabled constant must genuinely gate the *emission*, not just
  the UI. A disabled feature that still puts frames on the wire has leaked
  the exact information it was meant to withhold.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-MSG-7**: WHEN a recipient persists a new message, the sender SHALL
  observe that message advance from `Sent` to `Delivered`. (FR-MSG-002)
- **EARS-MSG-8**: IF an acknowledgement refers to a message this device did
  not send, or did not send to that peer, THEN the system SHALL ignore it
  and SHALL NOT change any delivery state. (FR-MSG-002, NFR-SEC-001)
- **EARS-MSG-9**: IF acknowledgements arrive out of order, THEN the system
  SHALL never move a message backwards through the state machine.
  (FR-MSG-002)

## Open Questions
- **OQ-E06-T08-1 — should read receipts be sent, and is that a user
  setting?** Nothing in `spec/` mentions read receipts; `FR-MSG-002` lists
  `Read` as a state but never says the *sender* learns about it, and
  `design/screens/chat.md` draws a green `done_all` (element 14) that
  strongly implies they do. FR-TRUST-006 enumerates the privacy toggles the
  product offers and read receipts are not among them, so adding one is new
  scope, not an omission. Options: (a) always send — matches the design's
  implication, simplest, and tells every contact when you opened your
  phone; (b) never send — the green `done_all` then never appears and the
  design element is permanently unreachable, which is a design-fidelity
  finding, not a neutral choice; (c) a per-account setting defaulting to
  off, added to the Settings screen — the standard answer, and it needs an
  SRS amendment plus a `design/gaps.md` entry because there is no design
  source for the row. **Advisory recommendation: (c), defaulting to off**,
  with the setting sharded into E02's settings surface rather than invented
  inside a chat task. Until then the mechanism ships disabled and GAP-009
  records that the green `done_all` is unreachable, so the gate reports it
  honestly rather than the state being hidden.
