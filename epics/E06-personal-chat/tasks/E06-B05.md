# E06-B05 · Devices and Settings screens' bottom nav is a dead end

## The defect

`devices_view.dart`'s `_BottomNav` and `settings_view.dart`'s `_BottomNav`
each render the same four-tab row every other screen does (Dashboard /
Conversations / Devices / Settings), but only the currently-active tab's
`onTap` is a no-op by *intentional* convention (re-tapping the screen
you're already on shouldn't do anything) — the other three should call
`Get.toNamed(...)`, exactly as `dashboard_view.dart` and
`conversations_view.dart` already correctly do for their own non-active
tabs. On Devices and Settings, **all four** items were `onTap: () {}`,
including the three that should navigate away.

Both files carried the same doc comment, word for word: *"the other three
route to screens not yet built by their owning feature epics, so they are
present and tappable but intentionally do nothing yet."* That was true when
this pattern was first written (`devices_view.dart` predates
Dashboard/Conversations/Settings all existing as real screens) — but
nothing ever revisited it once those screens shipped. `settings_view.dart`'s
own comment even says, explicitly, "same pattern as devices_view.dart's
`_BottomNav`" — confirming it was copied forward with the same now-false
premise, not independently discovered twice.

## Why this is a real, live defect (not theoretical)

Found live, on two physical Android devices, while completing a
human-directed two-device Bluetooth mesh test this session (discovery →
mutual trust verification → attempting to reach Conversations to send a
real message). Landing on Devices to verify mesh trust between the two
phones, then trying to return to Conversations via the bottom nav,
**silently did nothing** — repeated taps at the correct on-screen
coordinates (confirmed via fresh `uiautomator` dumps before and after each
tap) produced no screen change, no log line, no exception. Only Android's
own back button escaped. The exact same symptom reproduced on Settings.

## Severity: S2

Not S1: no crash, no security/privacy exposure, no data loss — the app is
still usable via the system back gesture. Not S3/S4: this is not a cosmetic
issue or a documented workaround — it is a genuine, silent navigation dead
end on two of the app's four primary tabs, discoverable by any real user
within seconds of visiting either screen, with no in-app affordance
hinting that back-gesture is the only way out.

## Fix

`devices_view.dart`'s `_BottomNav`: `Dashboard`/`Conversations`/`Settings`
now call `Get.toNamed('/dashboard')` / `Get.toNamed('/conversations')` /
`Get.toNamed('/settings')` respectively; `Devices`' own active-tab item
stays `onTap: () {}` (correct, unchanged).

`settings_view.dart`'s `_BottomNav`: `Dashboard`/`Conversations`/`Devices`
now call `Get.toNamed('/dashboard')` / `Get.toNamed('/conversations')` /
`Get.toNamed('/devices')` respectively; `Settings`' own active-tab item
stays `onTap: () {}` (correct, unchanged).

Both files' stale doc comments (claiming the no-op was deliberate) were
corrected to record what actually happened and why, rather than deleted.

## What this fix does NOT do

- Does **not** touch `dashboard_view.dart` or `conversations_view.dart` —
  both already wire their non-active tabs correctly; this bug never
  affected them.
- Does **not** change the active-tab convention itself (re-tapping the
  current screen stays a no-op on all four screens, matching the existing,
  correct pattern).
- Does **not** add a "start new conversation" affordance anywhere — a
  separate, real observation from the same live testing session (see
  Run log), but out of this bug's own scope: this bug is specifically
  about existing, already-built screens being unreachable from two other
  existing, already-built screens, not about a screen that doesn't exist
  yet.
- Does **not** touch `design/screens/devices.md` or `settings.md` — the
  design contract's own elements table already specifies all four nav
  items as present; this fix makes three of them on each screen actually
  do what a bottom nav item is for, it does not change what's drawn.

### Findings (both non-blocking)

1. **`devices_view_test.dart:229-236` / `settings_view_test.dart:164-171`
   (nit, no action required)** — the active-tab tests assert
   `expect(find.byType(DevicesView), findsOneWidget)`. That assertion would
   *also* pass if someone wrongly wired the active tab to
   `Get.toNamed('/devices')`, since the destination is the same widget type.
   It is therefore a weak guard against a future regression *in the opposite
   direction*. Not a defect in this PR: the tests are explicitly named
   "no-op by convention, **not a regression target**", the active tabs are
   unchanged by this diff, and the behaviour is correct as shipped. Recorded
   so a future task tightening the nav convention knows the guard is soft.

2. **Carried-forward observation independently confirmed as accurate.** The
   Run log's claim that there is no UI path to start a brand-new conversation
   with an already-trusted peer checks out: `conversations_view.dart` has no
   `FloatingActionButton`, no `Icons.add`/`Icons.edit`, and no
   `Get.toNamed('/chat...')` call anywhere in the file; `devices_view.dart`'s
   per-row actions are limited to `Verify` (`:270`) and `Block` (`:240`,
   `:365`). The PR does **not** attempt to silently address it — no
   affordance is added anywhere in the diff. Correctly disclosed and
   correctly left out of fence. Belongs in the epic tracker's
   §Carried-forward observations as its own item.
