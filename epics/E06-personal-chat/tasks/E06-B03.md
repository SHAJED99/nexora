# E06-B03 · The conversations list's delivery tick silently drops GAP-009's mapping

## The defect
`design/gaps.md`'s GAP-009, approved at sharding and implemented identically
in two of the epic's three screens, defines a six-state glyph mapping:

```dart
// chat_view.dart:503-509 and dashboard_view.dart:559-566 (byte-for-byte identical)
IconData _tickIconFor(DeliveryState state) => switch (state) {
      DeliveryState.queued => Icons.radio_button_unchecked,
      DeliveryState.sent || DeliveryState.accepted || DeliveryState.stored => Icons.check,
      DeliveryState.delivered => Icons.done_all,
      DeliveryState.read => Icons.done_all,
      DeliveryState.failed => Icons.error_outline,
    };
```

`chat_view.dart`'s and `dashboard_view.dart`'s copies are in sync — both
files' own header comments say the duplication (forced by Dart's
file-private visibility, per T12's task file §6 named risk) is deliberate,
and the bug sweep confirmed both copies are byte-identical.

The **third** place a delivery tick renders — `conversations_view.dart`'s
`_ConversationRow` (built by T10, merged before T11 existed and before
GAP-009 had a real implementation to copy from) — never adopted the
mapping. Its inline logic (`conversations_view.dart:341-352`) is:

```dart
if (tile.lastMessageIsMine) ...[
  Icon(
    Icons.check,
    size: 16,
    color: tile.lastMessageState == DeliveryState.read
        ? NexoraColors.devicesTrustedGreen
        : NexoraColors.devicesMuted,
  ),
  const SizedBox(width: 4),
],
```

This renders `Icons.check` for **every** `DeliveryState` value — `queued`,
`sent`, `accepted`, `stored`, `delivered`, and `failed` are all the same
grey check mark, and only `read` gets a different (green, not a different
shape) treatment. A message that is still locally queued (no route yet), a
message that failed outright, and a message the peer has actually seen are
all visually identical or near-identical on this screen, while the exact
same `ConversationTile.lastMessageState` field renders correctly
distinguished on Chat and Dashboard.

## Why this is a seam bug, not a T10 defect in isolation
T10's own review (round 1 and round 2, `tracker.md` §Review log) never
flagged this because at T10's build time GAP-009 was an approved *design
gap entry*, not yet a concrete implementation anywhere in the codebase —
T10 had nothing to diverge from except the gap's prose description, and its
own reviewer's job was T10's own scope, not a mapping that would only be
implemented twice more, later, by different tasks. T12's reviewer explicitly
named this as a *latent* risk ("the delivery-tick glyph mapping is now
duplicated in three places ... flagged as a latent drift risk") without
being able to say whether it had already happened, because checking all
three at once was out of any single task's fence. This sweep is the first
point where checking them side by side was in scope.

## Repro (verified 2026-08-30 on `epic_06` @ `3eefe2b`, direct code comparison)
1. `grep -n "_tickIconFor" lib/features/chat/presentation/chat_view.dart lib/features/dashboard/presentation/dashboard_view.dart lib/features/conversations/presentation/conversations_view.dart`
   → only two files define the function; `conversations_view.dart` has no
   such function at all.
2. Read `conversations_view.dart:341-352` (`_ConversationRow.build`) —
   confirms `Icons.check` is a literal, not a `switch` on `DeliveryState`.
3. Compare against `chat_view.dart:503-510` / `dashboard_view.dart:559-566`
   — both implement the full six-state GAP-009 switch.

**Expected** (GAP-009, and the FR-COMM-001 delivery-status promise it
derives from): a `Queued`, `Delivered`, `Read` or `Failed` outbound message
in the conversations list renders the same glyph shape as it does on Chat
and Dashboard for that same message.

**Actual:** every state except `read` renders identically as a plain grey
check on the conversations list — a user cannot tell a queued message from
a failed one from this screen at all, only from Chat.

## Severity: S3 (broken but there's a workaround)
Nothing crashes, no data is lost or exposed, and the accurate state is
always one tap away in the Chat screen (which does implement GAP-009
correctly) — that is the workaround. But it is a real, user-visible
correctness defect in a promise the epic's own gap explicitly made
(GAP-009 exists specifically because "the delivery-glyph mapping" was
called out at sharding as needing one consistent, approved answer), and a
`Failed` message showing as an ordinary grey check on the list screen is
actively misleading, not merely incomplete.

Severity is the reviewer's call. **Priority is the human's**
(`bug_priorities` gate, rule 3) — left `TBD-human`.

## Proposed fix direction (builder to confirm; not prescriptive)
Duplicate `_tickIconFor`/`_tickColorFor` into `conversations_view.dart` the
same way `dashboard_view.dart` already duplicates them from `chat_view.dart`
— consistent with the project's own stated reason for the existing
duplication (Dart file-private visibility) rather than introducing a new
shared-widgets file this task's fence doesn't include. A regression test
should pump `_ConversationRow` (or the full `ConversationsView`) with one
tile per `DeliveryState` value and assert the rendered `Icon`'s `icon`
property matches GAP-009's mapping for each — the same shape as whatever
test already exists (if any) for `chat_view.dart`'s `_tickIconFor`.
