# E06-T02 · Relay wire-packet framing + ciphertext type tag

## 1. Goal
Give the mesh an actual wire packet: bytes a receiving device can read well
enough to know *who a packet is for and what kind of ciphertext is inside*,
without being able to read the payload — closing the two-epics-old gap where
`RelaySendFn` puts an opaque blob on the radio and no receiver can do
anything with it.

## 2. Business logic
- **FR-ROUTE-004** enumerates exactly what relay-held data carries: "packet
  id, destination, priority, size, creation time, expiration time, and
  delivery state". `RelayEngine.enqueue(destination, payload, priority,
  ttl)` (`relay_engine.dart:106`) stores all of that in `relay_packets` —
  and then `RelaySendFn(nextHopId, payload)` (`relay_engine.dart:71`) puts
  **only the payload** on the wire. A relay that receives those bytes has no
  destination, no id, no expiry: it cannot forward, cannot dedup, cannot
  expire. This task puts the same fields FR-ROUTE-004 already names into the
  frame.
- **FR-ROUTE-003 is the constraint on that:** the header must be readable by
  a relay; the payload must not be. The frame is therefore
  `clear header || opaque payload`, and no field derived from plaintext ever
  enters the header. A relay learns routing metadata and nothing else — the
  same guarantee E04-T04 already enforces at the storage layer, now enforced
  at the wire layer.
- **OQ-E05-B01-1, the second half.** `ReceiveMessageUseCase.call` takes a
  `CiphertextMessage` (`receive_message_use_case.dart:102`); the transport
  carries `Uint8List`. `libsignal_protocol_dart` 0.8.2 gives no
  type-discriminating reconstructor — a `PreKeySignalMessage` and a
  `SignalMessage` read the same version byte, and the library relies on an
  out-of-band type tag it does not itself define. E05-B01's reviewer named
  the cheapest correct fix: **carry `CiphertextMessage.getType()`'s tag in
  the relay framing.** This task is where that tag lives. The rejected
  alternative — a try-PreKey-then-Signal heuristic — is rejected here too:
  it mis-parses silently, and a garbage parse whose garbage id evicts a real
  message through dedup is the worse failure E05-B01 already documented.
- **E03-B03**, deferred by E03's retro "to whichever of E05/E06 first wraps
  a `catch` around `decrypt()`": `InvalidMessageException` is not exported
  from the `libsignal_protocol_dart` barrel, so the commonest decrypt
  failure has no catchable type. E06 is that epic — T05 wraps the catch, and
  this task defines what it catches.

## 3. What this task does
- **`RelayPacketFrame`** — the wire frame, with `serialize()` /
  `deserialize()`. Layout, big-endian, matching `MessageEnvelope`'s existing
  style (`message_envelope.dart:43-117`) so there is one framing idiom in
  this codebase, not two:

  ```
  [u8  frameVersion=1]
  [u8  payloadType]          # see PayloadType below
  [u32 packetIdLen][packetId bytes]        # RelayEngine's packet id (FR-ROUTE-004)
  [u32 destinationLen][destination bytes]  # final destination device id
  [u32 sourceLen][source bytes]            # originating device id
  [u8  priority]                           # FR-ROUTE-004
  [u64 createdAtMs][u64 expiresAtMs]       # FR-ROUTE-004 creation/expiration
  [u32 payloadLen][payload bytes]          # OPAQUE — never inspected here
  ```
- **`PayloadType`** — a closed enum serialized as its integer tag, never its
  index-by-accident: `preKeySignalMessage(1)`, `signalMessage(2)`,
  `control(3)`. `control` is reserved for the non-message envelopes later
  tasks add (prekey bundles in T07, acks in T08) so those tasks extend a
  declared point instead of re-versioning the frame; **this task defines the
  tag and nothing that uses it.**
- **`CiphertextCodec`** — the two functions E05-B01 said nobody owned:
  `encode(CiphertextMessage) -> (PayloadType, Uint8List)` (tag from
  `getType()`, bytes from `serialize()`), and
  `decode(PayloadType, Uint8List) -> CiphertextMessage` (dispatching to
  `PreKeySignalMessage(bytes)` / `SignalMessage.fromSerialized(bytes)`).
  No heuristic, no try-both: an unknown tag throws, loudly.
- **`crypto_failures.dart`** — the exception taxonomy E03-B03 asked for:
  a small sealed/`Exception` set (`CryptoDecryptFailure` with a reason enum
  covering at minimum `invalidMessage`, `noSession`, `untrustedIdentity`,
  `duplicateMessage`) plus a `mapSignalException(Object)` translator. This
  is the only place `libsignal_protocol_dart`'s unexported exception types
  are matched, so the string/type matching that E03-B03 forces exists once
  and is tested, rather than being re-improvised at each `catch`.
- **`crypto_stub.dart` (update)** — `decrypt()` and `establishSession()`
  throw the new typed failures instead of raw library exceptions. `encrypt`
  keeps throwing `StateError` for "no session" **only if** changing it would
  break `send_message_use_case.dart:124-130`, which catches exactly
  `StateError`; if it is changed, that catch is outside this task's fence,
  so **do not change it** — map at the call site in T05 instead and say so
  in §Deviations.

## 4. What this task does NOT do
- Does NOT send, receive, forward, schedule or store anything. This task is
  pure codec + types, with no I/O and no `AppDatabase` access.
- Does NOT modify `RelayEngine`, `RoutingEngine` or `TransportService`.
  `RelaySendFn`'s signature stays `(nextHopId, payload)`; the *caller*
  (T05/T06) is what passes a serialized frame as `payload`. Changing E04's
  engine from here would be an out-of-fence edit to a merged epic.
- Does NOT define the prekey-bundle or ack envelope bodies — it only
  reserves `PayloadType.control`. T07 and T08 define their own bodies.
- Does NOT touch `MessageEnvelope` (E05-T03). The two framings nest:
  `RelayPacketFrame.payload` is the ciphertext of a serialized
  `MessageEnvelope`. Do not merge them, and do not "simplify" one into the
  other — the outer frame is relay-readable and the inner one must not be.
- Does NOT add a MAC, signature or header-integrity check. That is a real
  security question (a relay can rewrite a header today) — raised as
  `OQ-E06-T02-1`, not silently invented.
- Does NOT catch anything anywhere. Defining the exception types is this
  task; wrapping `decrypt()` in a `catch` is T05's.

## 5. Contract

### Functions
```yaml
- signature: "RelayPacketFrame.serialize() -> Uint8List"
  returns: "the byte layout in §3, big-endian"
  purpose: "one wire format for every relayed packet"

- signature: "RelayPacketFrame.deserialize(Uint8List bytes) -> RelayPacketFrame"
  returns: "the frame; throws FormatException naming the field that failed"
  raises: "FormatException on a short buffer, an unknown frameVersion, an unknown payloadType, or any length prefix that exceeds the remaining buffer"
  purpose: "a relay reads the header without ever touching the payload"

- signature: "CiphertextCodec.encode(CiphertextMessage message) -> (PayloadType, Uint8List)"
  returns: "the tag from message.getType() and message.serialize()"
  purpose: "the producer half of OQ-E05-B01-1"

- signature: "CiphertextCodec.decode(PayloadType type, Uint8List bytes) -> CiphertextMessage"
  returns: "PreKeySignalMessage or SignalMessage per the tag"
  raises: "CryptoDecryptFailure(invalidMessage) on unparseable bytes; ArgumentError on a tag that is not a ciphertext tag (e.g. control)"
  purpose: "the consumer half — explicit tag dispatch, never a try-both heuristic"

- signature: "mapSignalException(Object error) -> CryptoDecryptFailure"
  returns: "a typed failure with a reason; unrecognised errors map to a distinct `unknown` reason carrying the original as `cause`"
  purpose: "E03-B03 — the one place libsignal's unexported exception types are matched"
```

## 6. Risks
- **Length-prefix parsing is where wire codecs get CVEs.** Every `u32`
  length must be validated against the *remaining* buffer before it is used
  to slice. `MessageEnvelope.deserialize` (`message_envelope.dart:117`)
  already has a reviewed version of this discipline including the fix from
  E05-B01 — read it and match it rather than re-deriving it, and note in
  §Run log that you did.
- E05-B01's regression story is the warning here: the first fix passed a
  test that *did not discriminate* — the crafted buffer threw pre-fix too,
  for the wrong reason. When writing a malformed-input test, prove it fails
  for the reason you claim by mutating the fix and watching *that* assertion
  move.
- `CiphertextMessage.getType()` returns an int whose values come from the
  library; do not assume they equal your `PayloadType` tags. Map explicitly
  in one switch, and test both directions round-trip.
- Do not let `payload` be inspected, logged, or length-validated against
  anything content-derived. FR-ROUTE-003 is the epic-level guarantee E04
  spent a whole task on; the easiest way to break it is a debug `print`.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-3**: WHEN a relay packet is serialized and deserialized, the
  system SHALL recover the packet id, destination, source, priority,
  creation and expiration times, and the payload byte-for-byte.
  (FR-ROUTE-004)
- **EARS-COMM-4**: IF a relay packet's bytes are malformed, truncated, or
  carry an unknown frame version or payload type, THEN the system SHALL
  throw a `FormatException` and SHALL NOT return a partially-parsed frame.
  (FR-ROUTE-004, FR-MSG-003)
- **EARS-COMM-5**: WHEN a `CiphertextMessage` is encoded and decoded, the
  system SHALL reconstruct the same concrete Signal message type it started
  from. (FR-MSG-003, NFR-SEC-001)

## Open Questions
- **OQ-E06-T02-1 — the frame header has no integrity protection, so a
  relay can rewrite it.** The payload is authenticated by Signal, so a
  relay cannot forge *content*; but destination, priority and expiry are
  cleartext and unsigned, so a malicious relay can redirect, deprioritize
  or prematurely expire a packet it is asked to forward. Options: (a) leave
  it — a relay could equally just drop the packet, so the added power is
  bounded and denial-of-service is already possible; (b) sign the header
  with the sender's identity key, which every relay must then verify (cost:
  a signature per packet per hop, and relays must know sender identity
  keys — they currently do not); (c) MAC the header into the Signal
  payload's AAD so only the *destination* detects tampering, after the
  fact. Advisory recommendation: **(a) for v1, revisit at the security-lens
  pass before release**, and record it as a known bound on NFR-SEC-001
  rather than an oversight — the threat is degradation, not disclosure, and
  (b)'s key-distribution cost is exactly the problem E06-T07 is already
  wrestling with. Not blocking: every option keeps this frame layout.
