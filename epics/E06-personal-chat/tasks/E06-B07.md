## What's actually wrong, as measured (not yet root-caused past this)
`test/design/design_probe_test.dart`'s `chat` fixture (`setUp`) seeds one
trusted peer (`device-trusted`) with **5** plain-text messages, deliberately
undecryptable in the test environment (no real Signal session is ever
established between the probe's synthetic device ids) — per that fixture's
own comment, the resulting `(unable to decrypt this message)`/`(empty)`
placeholder text is treated as an accepted, disclosed limitation, not
something to fake around. Two things beyond that comment's own disclosure
are NOT yet explained and are this task's job to run down:
1. `design/screens/chat.md`'s golden capture shows **8** message-area
   elements (10-25), including a file-transfer bubble (elements 16-18,
   `troubleshoot`/`Backup: Family Photos`/`In progress... 78%`) that this
   screen's own `GAP-010` already establishes is data-driven content this
   codebase doesn't build — so golden vs. build were never going to line up

   explained: the golden's `more_vert`, `add`, and `mic` icons — real,

   mismatches" table as `absent` (not merely mismatched), meaning the probe

   probe's fixed `390×844` test viewport, combined with the 5-message

2. Whether seeding the fixture with 8 messages (matching golden's count,
   including a stub/placeholder file-transfer row if one can be built
   without faking GAP-010's own already-accepted non-rendering) changes the
   missing-element count at all, isolating whether root cause #1 is really

## Run log

### 1. Root-causing the `more_vert`/`add`/`mic` absence
The task's own leading hypothesis (fixed 390×844 viewport + 5-message
thread height pushing header/composer content out of the probe's walked
bounds) was checked directly and **refuted**:
- `chat_view.dart`'s `Scaffold.body` is `SafeArea > Column [ _Header,
  Expanded(_MessageArea), _Composer ]`. `_Header` and `_Composer` are
  laid out by the `Column` at a fixed height regardless of the message
  list's content height — `_MessageArea`'s `ListView(reverse: true)`
  scrolls *within* its own `Expanded` slot; growing the message count
  cannot push the header or composer outside the 390×844 viewport, since
  they are never inside the scrollable region at all.
- Confirmed empirically: dumping `build/design-probe/chat.json`'s raw
  element list shows the header's `more_vert` button-wrapper element at
  box `{x:346,y:5,w:40,h:46}` and the composer's `add`/`mic`
  button-wrappers at `{x:8,y:772,...}`/`{x:334,y:772,...}` — all fully
  inside the 390×844 viewport, with valid non-null boxes. The button
  ELEMENTS are present; only their nested icon glyphs are absent.
- Real root cause: `test/design/flutter_probe_dumper.dart`'s `_walk`
  function (lines ~552-613) emits exactly ONE `button`-role element for
  any `_isInteractive` widget (here, the `InkWell`s `_IconTapTarget`/
  `_RoundIconButton` build), with `text` from `_collectText` — which only
  ever collects `Text` descendants, never `Icon` ones. The function then
  recurses into that widget's children with `insideInteractive: true`,
  and the `Icon` branch (line 642) only emits a probe element when
  `!insideInteractive` — so an icon nested inside an interactive wrapper
  is walked, but never added to `elements`. `arrow_back`, `more_vert`,
  `add`, `mic` are all bare `Icon`s inside exactly this shape
  (`_IconTapTarget`/`_RoundIconButton` → `Material` → `InkWell` →
  `SizedBox` → `Center` → `Icon`), so all four are swallowed identically —
  `arrow_back`'s absence is masked in the report only because the
  comparator's list-based pairing happens to pair the golden's
  `arrow_back` slot against a nearby, unrelated build element ("DE", the
  avatar initials) and reports it as a copy "change" rather than
  "absent"; `more_vert`/`add`/`mic` have no such nearby candidate left and
  report as flatly "absent".
- This is the exact, already-documented capability gap in
  `L-frontend-001` (`agent/memory/lessons/frontend.md`, added 2026-08-30
  from E06-T10): "`_isInteractive` classification... treats any
  `GestureDetector`/`InkWell`/button widget as one opaque element,
  swallowing everything nested inside it (icons, labels)". This task is
  the first to root-cause a CONCRETE instance of it down to the exact code
  path and confirm it with a raw dump, rather than inferring it from score
  deltas — recorded as a dated addendum to that lesson, not a new lesson
  (same underlying gap, first time fully nailed down).
- A SECOND, narrower and distinct probe-tooling gap was found while
  investigating the delivery-tick copy mismatches (`done_all`/`check`
  reporting as `(empty)`): `flutter_probe_dumper.dart`'s `_iconNames` map
  (lines 97-128) never includes `Icons.check` or `Icons.done_all` — the
  two icons `chat_view.dart`'s own `_tickIconFor` uses for the
  Sent/Delivered/Read delivery states. Unlike the button-swallowing gap
  above, these ticks ARE bare `Icon`s outside any interactive wrapper, so
  they ARE walked and DO get a probe element — it just carries empty
  `text` because `_iconName()` returns `null` for an unmapped
  `IconData.codePoint`. Also out of this task's `files:` fence to fix;
  disclosed here as a second, separate cause, and included in `E06-B08`'s
  scope alongside the button-swallowing fix.
