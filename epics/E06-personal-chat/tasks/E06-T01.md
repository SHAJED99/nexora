# E06-T01 · Flutter-capable design-fidelity gate

## 1. Goal
Make `make design-verify SCREEN=<id>` actually able to judge a built Flutter
screen, so E06's three screens are gated by measurement instead of by a
reviewer's eyes — which is how two real UI misses were caught in E02, and
how the third one would have shipped.

## 2. Business logic
- **Rule 2 is unenforceable today.** `design/tools/verify.mjs:27-48` loads
  the implementation as a URL in a headless browser
  (`design/sources.yaml` → `impl: {kind: url}`). A compiled Flutter/Android
  build has no DOM, so every UI task since E00 has recorded
  `design gate n/a` and substituted a manual diff (E00-T05, E02-T02,
  E02-T03). That is exactly the review-by-eye failure mode
  `skills/design-fidelity` opens with — a build that is 0.04% different by
  pixels and wrong in four places.
- E02's retro raised this from "open follow-up" to a named
  recommendation: *"Recommend prioritizing a Flutter design-verify gate …
  before E06 (the wedge) reaches review — that epic has 3 real screens with
  much higher complexity than a static menu."* E06's own `epic.md` §Risks
  says the same: build it as this epic's first task, **not** an afterthought.
- FR-UI-001 (Material 3 exclusively, no competing visual language) and
  FR-UI-002 (seeded ColorScheme, light/dark/system) are unfalsifiable
  without a measuring gate — this task is what makes them checkable.
- The gate's output must be the **same report shape** the DOM path already
  produces, so `design/screens/*.md` contracts, `design/golden/*/probe.json`
  and `design/thresholds.yaml` are all reused unchanged. A second, parallel
  fidelity system would be worse than none.

## 3. What this task does
- **`test/design/flutter_probe_dumper.dart`** — a widget-test-only helper
  that pumps a screen widget under `flutter_test` and walks the render
  tree, emitting a JSON file with the **same field names and units** as the
  DOM probe writes into `design/golden/<screen>/<state>@<vp>/probe.json`.
  Per element: `role` (derived from the `Semantics` node / widget type),
  `text` (the exact rendered string), `rect` `{x,y,w,h}` in logical pixels
  at the contract's viewport, and `styles` `{color, backgroundColor,
  fontSize, fontWeight, fontFamily, borderRadius, borderColor}` read from
  the resolved `TextStyle` / `BoxDecoration` / `RenderBox`, never from the
  source constants.
- **`test/design/design_probe_test.dart`** — the runner: for each screen
  registered in it, pumps that screen at 390×844 with
  `tester.view.physicalSize`/`devicePixelRatio` pinned, dumps to
  `build/design-probe/<screen>.json`. Registers **`devices`** (E02-T02,
  already built and already contract-checked by hand) as the proving
  screen. E06's own screens are added by their own tasks.
- **`design/tools/lib/flutter_probe.mjs`** — normalizes that dump into the
  internal shape `design/tools/lib/probe.mjs` produces from a DOM, so
  `compare.mjs` is untouched. Colour values normalize to the `rgb(r, g, b)`
  / `rgba(…)` strings the contracts already carry; radii to `Npx`.
- **`design/tools/verify.mjs`** — accepts a probe file instead of a URL:
  `--impl-probe <path>` (and `IMPL=flutter` resolving to
  `build/design-probe/<screen>.json`). Pixel comparison is **skipped, and
  reported as skipped**, on this path — there is no screenshot; the element,
  copy, style and token checks (all four hard checks) run in full.
- **`design/sources.yaml`** — a second impl entry `kind: flutter-probe`
  with its dump directory. The existing `url` entry stays for the design
  source itself.
- **`Makefile`** — `design-verify` passes `IMPL` through unchanged (it
  already does); add a `design-probe` target that runs the dumper test
  (`flutter test test/design/design_probe_test.dart`) so the two-step is
  one documented command pair.
- **`docs/design-gate-flutter.md`** — how to run it, what it can and cannot
  see (see §6), and the exact procedure for adding a screen to the runner.
- **`epics/E00-genesis/epic.md`** — flip OQ-E00-3 to 🟢 with the answer and
  a pointer to this task. Nothing else in that file changes.

## 4. What this task does NOT do
- Does NOT build any E06 screen, route, controller or binding — T10/T11/T12
  own those, and each adds *its own* screen to the runner inside its own
  `files:` fence.
- Does NOT change `design/thresholds.yaml`. Loosening a threshold to make a
  build pass is the one change that silently disables this subsystem
  (`skills/design-fidelity` rule 2) and is a 🧍 `design_threshold_relaxation`
  gate, not this task's call.
- Does NOT hand-edit any `design/screens/*.md` table, and does NOT
  regenerate the contracts or goldens — the design source has not changed.
- Does NOT add a pixel/golden-image (`matchesGoldenFile`) comparison. Pixels
  are the eyeball backstop and never the gate; adding a golden-image suite
  here would double the maintenance surface for the check that catches
  least. If the human wants one later it is its own task.
- Does NOT add font assets to the app or change any token (see
  `OQ-E06-T01-1` — that is a dependency decision, rule 3).
- Does NOT retro-fix `welcome`/`login`/`devices`/`settings` fidelity
  findings the new gate surfaces. Run it on `devices`, **record the
  findings verbatim in §Run log**, and let the sweep triage them. Fixing
  E02's screens from inside an E06 infrastructure task is exactly the
  scope creep rule 6 exists to stop.

## 5. Contract

### Functions
```yaml
- signature: "dumpScreenProbe(WidgetTester tester, {required String screenId, required Widget screen, Size viewport}) -> Future<void>"
  params:
    screenId: "the design contract id — the dump is written to build/design-probe/<screenId>.json"
    screen: "the fully-wired widget, pumped by the caller's own test setup"
    viewport: "defaults to Size(390, 844) — the viewport every contract in design/screens/ was measured at"
  returns: "nothing; writes the JSON dump as a side effect"
  purpose: "the Dart half of the gate — one call per screen, so adding a screen is one line"

- signature: "loadFlutterProbe(dumpPath: string) -> NormalizedProbe"
  params: { dumpPath: "path to the JSON written by dumpScreenProbe" }
  returns: "the same normalized structure design/tools/lib/probe.mjs returns for a DOM page"
  purpose: "so compare.mjs, the contracts and thresholds.yaml are all reused unchanged"
```

### UI
- **Design contract:** n/a — this task builds the gate, it does not build a

- Gate: this task's own proof is `make design-probe && make design-verify

  drift-injection check in §8.

## 6. Risks
- **The honest limit of a widget-test probe:** it measures the *widget
  tree*, not a rendered device frame. Platform text shaping, real font
  metrics, and OS-level insets can differ. Say this plainly in
  `docs/design-gate-flutter.md` rather than implying the gate proves more
  than it does — an overstated gate is worse than a missing one, because
  people stop looking.
- Rect units: contracts measure CSS pixels at 390×844; Flutter logical
  pixels at the same viewport are directly comparable **only if
  `devicePixelRatio` is pinned**. Pin it in the runner and assert the
  pinned value, or every geometry check drifts silently.
- Role mapping is where this can quietly go wrong: the contracts use DOM
  roles (`button`, `heading:1`, `textbox:multiline`, `generic`, `image`,
  `link`). Map from `Semantics` flags, not from widget class names, and
  put the mapping table in `docs/design-gate-flutter.md` so the next
  screen's builder can predict what the gate expects. A wrong map makes
  every element "missing" and the first reaction will be to loosen the
  gate — which is forbidden.
- Do not let the gate pass by matching nothing. The proving screen
  (`devices`) must produce a **non-trivial** element count in the report;
  a report that says `0 elements compared` is a broken harness reporting
  success, and §8's drift-injection check exists precisely to falsify that.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-UI-1**: WHEN the Flutter design gate runs against a built screen,
  the system SHALL report missing elements, changed copy and off-token
  styles against that screen's `design/screens/<id>.md` contract.
  (FR-UI-001)
- **EARS-UI-2**: IF a built screen drops an element, rewrites a string, or
  uses a colour or radius outside the contract's measured tokens, THEN the
  gate SHALL fail. (FR-UI-001, FR-UI-002)

### Tests
- `test_EARS_UI_1_flutter_probe_dumps_every_visible_element` — pumps a
  fixture screen with a known element set; asserts the dump contains each
  one with its text, rect and resolved styles (not the source constants).
- `test_EARS_UI_2_drifted_fixture_fails_the_gate` — the falsification test,
  and the one that matters. Four separate mutations of a fixture that
  otherwise matches its contract: (a) delete one element, (b) change one
  string by one character, (c) change one colour by one channel, (d) change
  one radius by 4px. Each must produce a **hard** finding. A mutation that
  still passes is a hole in the gate, not a tolerable margin.
- `test_EARS_UI_2_faithful_fixture_passes_the_gate` — the same fixture,
  unmutated, passes with a non-zero compared-element count.

### Manual
1. `make design-probe && make design-verify SCREEN=devices IMPL=flutter`
   → a real report at `design/reports/devices/…/report.md`. Paste it into
   §Run log **including the findings**, whatever they say.
2. Temporarily delete one element from `devices_view.dart`, re-run, confirm
   red, restore, confirm the tree is byte-identical afterwards.

## Open Questions
- **OQ-E06-T01-1 — the app ships none of the three fonts the contracts
  measure, and adding them is a dependency decision.** Every E06 contract
  measures `Inter`, `JetBrains Mono` and `Geist`
  (`design/screens/chat.md:62-64`, `conversations.md:64-67`,
  `dashboard.md:63-66`); the build uses the platform default everywhere —
  recorded in E02's retro as an S3 bug-sweep item explicitly needing "a
  font-asset dependency decision (rule 3) before it can be fixed". The
  moment this gate is live, **every text element on all three screens
  reports an off-token `font-family` finding**, on every screen, forever.
  There are only three honest outcomes and two of them are the human's:
  - **(a) Add the font assets** (bundle the three families under
    `assets/fonts/`, declare them in `pubspec.yaml`, theme them). New
    assets + a licence review = rule 3. Cost: ~1-2 MB of APK, one small
    task. Result: the gate is green on its own terms.
  - **(b) Accept the drift with a scoped threshold relaxation** — exclude
    `font-family` from the hard style check for these screens. This is
    explicitly a 🧍 `design_threshold_relaxation` gate
    (`skills/design-fidelity` rule 2) and is the single change that can
    silently disable this subsystem, so it must be scoped to `font-family`
    only and dated, never applied globally.
  - **(c) Change nothing and let three screens sit permanently red.** Not
    recommended: a permanently-red gate is one people learn to ignore, and
    then it stops catching the findings it exists for.
  - **Advisory recommendation: (a).** It is the only option that leaves the
    gate meaning what it says, the cost is bounded and one-time, and the
    contracts were measured from a design that genuinely uses those fonts —
    the drift is real, not a measurement artefact.
  - **This blocks the UI tasks, not this one.** T01 can be built and proven
    against `devices` regardless. T10/T11/T12 need the answer before their
    gate result means anything.
  - **Status:** 🟢 answered
  - **Answer:** **(a) — add the font assets.** Bundle Inter, JetBrains Mono
    and Geist under `assets/fonts/`, declare in `pubspec.yaml`, theme them.
    All three are permissively licensed for embedding (Inter and
    JetBrains Mono: SIL Open Font License 1.1; Geist: MIT) — the human
    should still confirm the exact license files are bundled per each
    font's terms (typically requiring the license text alongside the
    font, not just permission to embed) as part of reviewing this task's
    diff, since that's a factual license-compliance check, not a product
    decision. Cost: ~1-2 MB of APK, one small task, gate becomes green on
    its own terms rather than permanently red or scoped-relaxed.
  - **Answered by:** orchestrator, applying the task file's own advisory
    recommendation, per the user's explicit standing instruction to
