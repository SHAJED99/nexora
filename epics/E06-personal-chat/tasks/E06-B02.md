# E06-B02 · A second `TransportService` instance silently hijacks every native transport event app-wide

## The defect
`lib/features/devices/presentation/devices_controller.dart:31` still constructs
its own fallback `TransportService()` whenever `DevicesBinding` does not
inject one — and `DevicesBinding.dependencies()`
(`lib/features/devices/presentation/devices_binding.dart:16-19`) never does:

```dart
Get.lazyPut(
  () => DevicesController(
    Get.find<RelationshipRepository>(),
    Get.find<BlockUseCase>(),
  ),
);
```

Both positional-arg-only — `transportService` is left at its default, so
`DevicesController`'s own constructor runs `_transportService = transportService
?? TransportService()` (`devices_controller.dart:31`) and allocates a **brand
new** `TransportService`.

This was flagged as a carry-forward observation by E06-T03's reviewer
(`tracker.md` §Carried-forward observations, first bullet) with an explicit
recommendation: *"T04 should either wire `DevicesBinding` to inject the
shared instance or confirm the fallback path is dead code."* Neither
happened. T04 (link-quality wiring) registered its own consumer through
`lib/app/bindings.dart` specifically to avoid colliding with the
`messaging_stack.dart` chain (epic.md's own Collision matrix note) and never
touched `devices_binding.dart`. No task since has either.

`TransportService`'s constructor is not a lightweight facade — it is where
the Pigeon event boundary is claimed:

```dart
TransportService({BinaryMessenger? binaryMessenger, String messageChannelSuffix = '',})
    : _api = TransportApi(binaryMessenger: binaryMessenger, messageChannelSuffix: messageChannelSuffix) {
  TransportEventsApi.setUp(_EventsHandler(this), binaryMessenger: binaryMessenger,
      messageChannelSuffix: messageChannelSuffix);
}
```
(`lib/core/transport/transport_service.dart:63-75`)

`TransportEventsApi.setUp` (generated Pigeon code,
`lib/core/transport/generated/transport_api.g.dart:366-…`) registers a
`BasicMessageChannel.setMessageHandler` on five fixed, unsuffixed native
channel names (`onDeviceDiscovered`, `onDeviceLost`,
`onConnectionStateChanged`, `onIncomingData`, `onLinkQuality`). A platform
channel has exactly one Dart-side handler per channel name — a second
`setUp` call on the same channel **replaces** the first handler; it does not
add a second listener. Both `MessagingStack`'s `TransportService`
(`messaging_stack.dart:378`, created once at composition-root time in
`main.dart:48`) and `DevicesController`'s fallback instance use the default
`messageChannelSuffix: ''`, so they collide on the exact same five channels.

## Why it matters — this is not theoretical, and it is not confined to devices
`DevicesController` is a `GetX` `lazyPut` — it is **not constructed at app
startup**. It is constructed the first time the user navigates to
`/devices` (`app/routes.dart:59`, `DevicesBinding()`). `MessagingStack`'s
`TransportService`, by contrast, **is** constructed at startup, before
`runApp` (`main.dart:48`), so it is always first.

The consequence: the very first time a user opens the Devices screen (a
normal, expected action — Devices is one of the four bottom-nav
destinations reachable from Dashboard and Conversations, and is the *only*
screen where they can add or verify a peer), `DevicesController`'s
constructor runs `TransportEventsApi.setUp(...)` a second time and silently
overwrites the handler registration `MessagingStack`'s `TransportService`
installed at startup. From that moment on:
- `onIncomingData` events (every inbound relay/message packet) route to
  `DevicesController`'s instance instead of `MessagingStack`'s — the
  inbound pipeline (T05), the coordinator (T06), prekey exchange (T07) and
  delivery acks (T08) stop receiving any wire traffic, with **no exception,
  no log line, no user-visible error**. `EARS-COMM-1` (send/receive in a
  1:1 conversation) silently stops working for the rest of the app session.
- `onLinkQuality` events stop reaching `MessagingStack`'s consumer, silently
  breaking T04's link-quality wiring the same way (T04's own EARS-ROUTE-11
  regression test never exercises this cross-controller scenario, so it
  stays green while the real app breaks).
- `onConnectionStateChanged` events are similarly redirected, so any
  in-flight `TransportService.connect()` future owned by the messaging
  stack's instance never settles.
- `DevicesController`'s own discovery/connection flows keep working
  (it now owns the only live handler) — which is exactly what makes this
  easy to miss in manual testing: the screen you're looking at still works.

There is no recovery within the running session: the handler stays
overwritten until the app restarts, and it breaks again the next time the
user revisits Devices in the new session. A user who never opens Devices
never sees it — but Devices is a primary nav destination, not an edge case.

## Repro (verified 2026-08-30 on `epic_06` @ `3eefe2b`, static + code reading — no device needed)
1. `grep -n "TransportService()" lib/features/devices/presentation/devices_controller.dart lib/core/messaging/messaging_stack.dart`
   → two independent, unsuffixed construction sites.
2. Read `DevicesBinding.dependencies()` — confirms neither
   `transportService` nor a channel suffix is ever passed.
3. Read `TransportEventsApi.setUp` in
   `lib/core/transport/generated/transport_api.g.dart:366-…` — confirms
   `BasicMessageChannel.setMessageHandler` is called per channel name with
   no compositing; the second call for the same channel name replaces the
   first (this is `flutter/services.dart`'s own documented single-handler
   contract for `BasicMessageChannel`, not app code).
4. Confirm ordering: `main.dart:48` constructs `MessagingStack` (and its
   `TransportService`) before `runApp`; `DevicesBinding` is a route
   `Bindings` with `Get.lazyPut`, only instantiated on first navigation to
   `/devices` (`app/routes.dart:59`) — always strictly after step 3's
   registration.

**Expected** (FR-COMM-001 / FR-PLAT-003 / ADR-0004's single transport
boundary): exactly one live `TransportService` per app process, so every
native transport event reaches the one component set that's supposed to
consume it, regardless of which screens the user has visited.

**Actual:** a second instance is created on ordinary navigation and wins
the platform channel, silently detaching the messaging stack from all
native transport events for the rest of the session.

## Severity: S1 (silent, total loss of the epic's core function, no workaround, no error surfaced)
This is not a crash and nothing is corrupted — messages composed while
detached still queue durably (E05's guarantee holds) — but inbound
delivery, link-quality feedback and connection-state resolution for the
*entire messaging stack* stop working the moment an ordinary nav action
occurs, with zero user-visible signal that anything is wrong. That is
exactly the "total blocker" shape S1 describes for this codebase: the
epic's own `## User-visible outcome` — "a user opens a conversation, sends
a message ... and it arrives" — stops being true, silently, for any user
who also uses the Devices screen (the only place to add or verify a
contact, so effectively every real user).

Severity is the reviewer's call. **Priority is the human's**
(`bug_priorities` gate, rule 3) — left `TBD-human`.

## Proposed fix direction (builder to confirm; not prescriptive)
The shape matches what the original T03 reviewer already recommended:
either (a) have `DevicesBinding` inject the single shared
`TransportService` instance `MessagingStack` already owns (requires
threading it from the composition root through `Get.find`/permanent
registration, the same pattern `app/bindings.dart` already uses for
`RelationshipRepository`/`BlockUseCase`), or (b) prove the fallback path is
provably dead and remove it, replacing it with a hard failure
(`throw StateError`) if `DevicesBinding` ever fails to inject — never a
second live instance. (a) is very likely the correct answer since
`DevicesController` needs live discovery, which only the shared instance
can offer without the collision. A regression test should construct both
`MessagingStack` and `DevicesController` in the same test and assert an
event delivered on the (mocked) `onIncomingData` channel reaches
`MessagingStack`'s consumer even after `DevicesController` has been
constructed — the exact ordering that breaks today.
