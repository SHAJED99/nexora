# E06-T12 · Dashboard screen

## 1. Goal
The app's front door: tell the user in one line whether they are connected,
put the technical detail exactly one tap away, and show what they were last
talking about.

## 2. Business logic
- **Rule 2.** `design/screens/dashboard.md` is law: 46 checklist elements,
  37 verbatim strings. `Network Status`, `Primary Node Connection`,
  `Connected`, `Encryption`, `Secure`, `Latency`, `Local Storage`,
  `45% used`, `Smart Mode - Older than 10 days`, `Recent Conversations`,
  `Message queued — will send when connected.` and the four nav labels are
  copy and are exact — including the em dash in the queued line.
- **EARS-COMM-2 / FR-UI-004** is this screen's reason to exist: *"The
  default view SHALL communicate connectivity simply ('You're connected');
  route/transport detail SHALL be one tap away."* The design supplies the
  simple half; GAP-012 supplies the other half by making the Network Status
  card navigate to `/devices`, a surface that already exists and already
  shows peers and transports — rather than inventing a screen.
- **`Latency` / `24ms` is real, or it is nothing.** Its only honest source
  is E06-T04's link-quality feed. E04-B03's standing prohibition applies at
  the UI layer too: *"do not synthesize fake measurements … strictly worse
  than one that honestly returns null."* With no measurement, show the
  neutral placeholder GAP-013 describes — never `24ms` as if it were
  measured.
- **`Connected` is one of three readings, not a constant** (GAP-013):
  connected, no peers, no route to the selected peer. This app is
  offline-first; "not connected" is a normal state, and FR-ROUTE-009 makes
  route failure an expected condition.
- **`Local Storage 45% used` has no data source until E08** (GAP-011).
  Render the card with its measured labels; use the real on-disk figure if
  it is cheaply available from the Drift file, otherwise a placeholder
  **disclosed in §Deviations and in GAP-011** — never a fabricated
  percentage presented as measured.
- **Recent Conversations** comes from `ConversationRepository`
  (T09) — the same read model as T10, so the two screens cannot disagree
  about recency or about who is blocked.
- The `Message queued — will send when connected.` row (elements 33-34) is
  a real state this epic finally produces: a `Queued` message, rendered
  with `radio_button_unchecked` exactly as measured — and it is the design's
  own evidence that GAP-009's glyph mapping for the Chat screen is drawn
  from the design rather than invented.

## 3. What this task does
- `/dashboard` route + `DashboardView` + `DashboardController` +
  `DashboardBinding`, three-file GetX pattern. `/dashboard` supersedes the
  genesis placeholder `/home` as the post-login destination.
- Network Status card: connection reading (GAP-013), `Encryption` /
  `Secure` from `MessagingStack.status` (T03) — `Secure` only when crypto
  actually initialized, `Latency` from T04's most recent measurement or the
  GAP-013 placeholder. The whole card is the tap target for `/devices`
  (GAP-012).
- Local Storage card per GAP-011.
- Recent Conversations: the top N summaries from
  `watchConversations()`, rendered with the contract's row treatment
  including the three distinct state glyphs the design draws
  (`check_circle`, `lock`, `radio_button_unchecked`). Tapping a row opens
  `/chat/<id>` (T11).
- Bottom nav with `Dashboard` active (elements 35-45).
- Registers the screen in `test/design/design_probe_test.dart`.
- Loading / empty / error states, including `MessagingStack.status ==
  unavailable` — the screen must render honestly when the stack failed to
  come up (T03 §3 built that path specifically so this screen could).

## 4. What this task does NOT do
- Does NOT implement storage management, retention, or Smart Mode (E08 —
  GAP-011). The card's labels are static copy until then.
- Does NOT build a new route-detail screen. GAP-012 routes to `/devices`
  deliberately; inventing a screen is the thing rule 2 forbids most
  directly.
- Does NOT change the Devices screen, or fix any E02 finding the new design
  gate surfaces there — that is a bug-sweep item, not this task's.
- Does NOT synthesize a latency, a battery figure, a storage percentage, or
  a peer count.
- Does NOT touch `lib/app/bindings.dart` or any backend file.
- Does NOT implement notifications, background status, or connectivity
  change alerts (E10).

## 5. Contract

### UI
- **Design contract:** `design/screens/dashboard.md`
- **Route:** `/dashboard`, added to `lib/app/routes.dart` and
  `docs/routes.md`; becomes the post-login destination in place of `/home`.
  Nav to: `/devices` (the Network Status card, GAP-012), `/chat/<id>`
  (a recent row), and the three other nav targets.
- **States required:** loading · data · empty (no conversations yet — reuse
  GAP-007's approved treatment rather than inventing a second one) · error

- **Gate:** `make design-probe && make design-verify SCREEN=dashboard
  IMPL=flutter` **green before the PR** (rule 2).

## 6. Risks
- The temptation to make the screen look like the mockup by filling
  `24ms`, `45% used` and `Connected` with plausible constants is enormous,
  and every one of those is the exact failure E04-B03's human decision
  prohibited. A screen that shows confident invented numbers is worse than
  one that shows a placeholder, because nobody can tell it is lying.
- Three glyph states in the Recent Conversations rows must map to the same
  delivery states as the Chat screen's ticks (GAP-009). Two screens with two
  mappings is exactly the "state name defined in two documents" problem
  E05-B03 was. Read the mapping from one place — the shared
  `ConversationTile` view model T10 defines.
- `/dashboard` replacing `/home` touches the post-login flow. Verify the
  login journey end to end; a broken redirect here breaks the app's entry.
- Expect gate iteration, as with T10 and T11. Never loosen the threshold.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-2** *(epic-level)*: The default view SHALL communicate
  connectivity simply, and route/transport detail SHALL be one tap away.
  (FR-UI-004)
- **EARS-COMM-26**: IF no link measurement exists, THEN the screen SHALL
  NOT display a latency value. (FR-ROUTE-007, FR-UI-004)
- **EARS-COMM-27**: WHEN the messaging stack is unavailable, the Dashboard
  SHALL still render and SHALL say so. (FR-COMM-001)

### Tests
- `test_EARS_COMM_2_status_card_shows_a_simple_reading` — one word, no
  route/transport detail on the default view.
- `test_EARS_COMM_2_status_card_taps_through_to_devices` — one tap, the
  `/devices` route (the FR-UI-004 assertion).
- `test_EARS_COMM_26_no_measurement_shows_no_latency` — with an empty link
  feed, `24ms` and any other numeric latency is absent (assert the absence
  of a digit-bearing latency string, not just of the literal `24ms`).
- `test_EARS_COMM_26_real_measurement_is_displayed` — feed a measurement;
  that value appears.
- `test_EARS_COMM_27_unavailable_stack_still_renders` — `status ==
  unavailable`; the screen pumps, says so, and does not throw.
- `test_recent_conversations_use_the_shared_read_model` — assert the same
  ordering and blocked-exclusion as T10's list for identical data.
- `test_dashboard_view_matches_contract_elements` — the in-suite contract
  check.
