# E06-B04 · `frame.source` has no cryptographic binding, and T08's ack ownership check trusts it anyway

## The defect
`DeliveryAck.handleControlFrame` (`lib/core/messaging/delivery_ack.dart:377-402`)
is the only gate standing between an inbound delivery-ack control frame and
advancing a message's `DeliveryState`:

```dart
// Ownership (EARS-MSG-8): this device must have authored the message,
// AND authored it for the peer this ack claims to be from. See this
// file's header for why `conversationId == frame.source` is the right
// check for the only conversation shape this schema supports today.
if (row.senderDeviceId != _stack.selfDeviceId ||
    row.conversationId != frame.source) {
  counters.rejectedForeign++;
  return;
}
```

`frame.source` is the relay-frame header's claimed logical sender — set by
whichever device injected the frame into the mesh, never verified against
who actually delivered the bytes to this device's transport. `inbound_
pipeline.dart:325-329` constructs the inner control frame by copying
`frame.source` straight through from the outer frame with no signature
check anywhere in the chain (T02's frame format, `OQ-E06-T02-1`, records
the header as unsigned by design for v1). Control frames specifically
(`payloadType == PayloadType.control`) carry no additional authentication
beyond that unsigned header — unlike message payloads, which are
individually AEAD-sealed and only decrypt under a real Signal session with
the claimed sender, a delivery ack's `messageId`/`state` body has no
sender-binding cryptographic material at all.

Net effect: any node participating in the mesh that already knows (a) a
target device's id and (b) a `messageId` that device sent to some peer —
both values that travel in cleartext in every relay frame header and
control-frame body respectively, so they are observable by any relay hop
along the path, not secret — can construct and inject a `DeliveryAck`
frame with `frame.source` set to the real recipient's device id, and the
ownership check above will accept it as genuine.

## Why this is now a live, reachable finding, not a purely theoretical one
This was first flagged by E06-T08's reviewer (`tracker.md` §Carried-forward
observations, second bullet) as a real but not-fixable-in-one-task's-fence
finding, at a point when T11 (the chat screen) had not yet merged and there
was no real user-facing journey that would ever construct or receive a
message a hostile ack could target. As of this sweep, **T11 is merged and
is the epic's proven, real end-to-end send/receive/encrypt/decrypt loop**
(tracker.md, T11 round-2 review) — a real user composes a real message,
gets a real `messageId`, and watches its tick advance on the Chat screen
using exactly the `DeliveryState` this control frame drives. The
precondition the earlier finding was missing — "a real user could receive
acks" — is now met. The blast radius is unchanged from what T08's reviewer
already scoped (re-verified directly in this sweep by reading
`delivery_ack.dart:394-402` and `inbound_pipeline.dart:308-343` again): a
forged ack can only ever move a message that (a) this device authored
**and** (b) claims to be from the correct peer for that conversation — it
cannot forge acks on other people's conversations, cannot read or alter
message content, cannot affect encryption or trust state, and the
`DeliveryStateMachine`'s monotonicity guarantee (EARS-MSG-9, `delivery_
ack.dart:404-…`) still prevents a forged ack from moving a message
*backwards*. The exposure is confined to a hostile node making a real,
legitimate message's tick marks advance early or falsely (e.g. showing
`Delivered`/`Read` on a message the real peer never received) — a UI
integrity issue, not a confidentiality or content-integrity one.

## Repro (verified 2026-08-30 on `epic_06` @ `3eefe2b`, code reading — no live mesh needed)
1. `lib/core/messaging/delivery_ack.dart:394-402` — the ownership check
   quoted above; confirm it reads only `frame.source` and `row.
   conversationId`/`row.senderDeviceId`, never anything cryptographically
   bound to the actual sender of the wire bytes.
2. `lib/core/messaging/inbound_pipeline.dart:308-343` — confirm the control
   branch passes `frame.source` through unchanged from the outer relay
   frame into the inner frame handed to `DeliveryAck.handleControlFrame`,
   with no signature/MAC check anywhere between the transport read and the
   handler call.
3. `epics/E06-personal-chat/tasks/E06-T02.md`'s own `OQ-E06-T02-1` — confirms
   the frame header was deliberately shipped unsigned for v1, accepted as a
   known risk at sharding time, revisit deferred to "the pre-release
   security-lens pass."

**Expected** (NFR-SEC-001, and EARS-MSG-8's own "this device must have
authored the message, AND authored it for the peer this ack claims to be
from" ownership intent): the "claims to be from" half should be
cryptographically true, not merely internally self-consistent.

**Actual:** "claims to be from" is exactly that — a claim, trusted at face
value once the coarse ownership filter passes.

## Severity: S3 (broken but there's a workaround)
Not S1/S2: no content, key material, trust state, or cross-conversation
data is exposed or corrupted, and the monotonicity guard bounds the damage
to premature/false tick advancement on messages the victim device itself
already sent. Not S4: this is a genuine, exploitable integrity gap in a
security-sensitive control path in an encrypted-messaging product, not a
cosmetic issue — a workaround exists only in the weak sense that the
underlying message content and delivery are never actually compromised,
which is why this stays S3 rather than S2. This assessment matches the
bounded blast-radius already worked out by T08's reviewer; this sweep's
contribution is confirming the trigger precondition (a live send/receive
journey) is now met, which is why the observation graduates from a
carried-forward note to a scheduled bug.

Severity is the reviewer's call. **Priority is the human's**
(`bug_priorities` gate, rule 3) — left `TBD-human`.

## Proposed fix direction (builder to confirm; not prescriptive)
🧍 This is a protocol-shape decision (rule 3), not a pure bug fix — signing
control frames touches T02's frame format, T05's inbound pipeline, T07's
prekey exchange and T08's delivery acks all at once, exactly as the earlier
carried-forward note said. Options to present to the human, honestly, at
whatever epic picks this up (E06-T02's own `OQ-E06-T02-1` already names the
"pre-release security-lens pass" as the intended venue):
- (a) sign control-frame bodies with the sender's existing Signal session
  MAC/AEAD tag (reuses machinery already present for message payloads;
  requires a real session to exist, which acks currently do not assume);
- (b) add a lightweight per-control-frame HMAC keyed off material already
  established at prekey-exchange time, cheaper than a full AEAD envelope;
- (c) accept the risk permanently for v1 given the bounded blast radius,
  and close this as a documented, accepted risk rather than a bug — a
  legitimate outcome if the human judges UI-only tick spoofing acceptable
  for the product's threat model.
A regression test (once a direction is chosen) should construct a
`DeliveryAck` control frame with a forged `frame.source` matching a real
conversation's peer id but not actually originating from that peer's
session, and assert it is rejected post-fix (and, falsified against
today's code, accepted pre-fix — proving the gap is real, not assumed).
