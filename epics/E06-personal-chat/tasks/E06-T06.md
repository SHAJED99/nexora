# E06-T06 · MessagingCoordinator

> ⛔ **This task carries a 🧍 blocking Open Question (`OQ-E06-T06-1`).**
> The *trigger model* — when the relay queue runs — is an application
> architecture and battery/OS-lifecycle decision, which rule 3 reserves for
> the human, and E05-B02's own §Proposed-fix-direction says so explicitly:
> *"🧍 This one needs a human decision before code … Present the options
> with trade-offs and stop."* Everything else in this file is concrete and
> ready. **Do not start implementation until `OQ-E06-T06-1` is 🟢.**

## 1. Goal
Give the mesh a heartbeat: something in the running app that actually calls
the lifecycle methods E04 built and E05 never scheduled, so a message
composed offline leaves the device when a route appears.

## 2. Business logic
- **E05-B02, deferred to E06 by an explicit human decision (2026-08-29):**
  *"E06 is the first epic with a real running app/UI and foreground
  presence — the coordinator belongs where app-lifecycle and Android
  background policy naturally live … E06's planner must carry this file
  (and E05-B01's send/receive wiring, and `SyncCursorService.recordLocalProgress`'s
  uncalled state) into E06's task sharding as a named dependency, not
  rediscover it."* This task is that carry.
- **The EARS criterion with no mechanism.** `EARS-MSG-1`: *"WHEN a message
  is created offline, the system SHALL queue it locally **and send once a
  route is available**."* E05-T02 delivers the first half honestly. The
  second half is `RelayEngine.processQueue()`, which has **zero call
  sites** — verified by exhaustive grep in E05-B02 §Repro. As merged,
  every message on every device queues forever.
- **E04-B02's retention guarantee is unscheduled too.** Its approved review
  advisory: the retention *mechanism* is delivered and proven, while the
  retention *guarantee* "only becomes real once … both [are wired] onto a
  scheduler". `reclaimPayloads()` nulls out third-party ciphertext past TTL
  — the concrete basis of the NFR-SEC-001 argument in E04's §Data model —
  and it has never run. Ordering established by E04-B02's review:
  `processQueue()` → `sweepExpired()` → `reclaimPayloads()`, correctness-
  neutral but one cycle better for reclaim latency.
- **`SyncCursorService.recordLocalProgress` has no caller, and its doc
  comment lies about it.** `sync_cursor_service.dart:113-114` claims it is
  *"called whenever a message is stored (T02 on send, T03 on receive)"*.
  Nothing calls it; neither use case even imports the service. E05's retro
  named this the same false-comment shape as E05-B01's root cause, in a
  second file. **This task both wires it and corrects the comment** — the
  comment fix is not cosmetic, it is the removal of a false claim that has
  already caused one production bug in this codebase.
- **`delivery_states` has no writer either** (E05-T02 review, non-blocking
  observation 2). The table exists (E05-T01) and records one row per
  transition. The coordinator is the one component that observes every
  transition, so it is the honest owner.
- **A queued row that nothing reconciles** (E05-T02 review, observation 3):
  a crash between a successful `enqueue` and the `sent` UPDATE leaves a
  `queued` message whose relay packet is already durably enqueued. Correct
  per E05-T02's fence, and startup is the natural place to reconcile it.
- **NFR-BATT-001 binds here and is the reason this is the human's call:**
  "minimize unnecessary network scanning, GPS, synchronization, CPU and
  traffic — but battery efficiency shall never override reliability or
  communication requirements." A tick interval is exactly that trade-off,
  in one number.

## 3. What this task does
- **`MessagingCoordinator`** — owns the running loop:
  - `start()`: calls `InboundPipeline.start()` (**this is T05's obligation
    discharged here, stated in this task's own binding contract**), then
    begins driving the relay queue per the trigger model chosen in
    `OQ-E06-T06-1`.
  - one **tick**: `relay.processQueue()` → `relay.sweepExpired()` →
    `relay.reclaimPayloads()`, in that order, never overlapping with
    itself (a re-entrancy guard — a slow pass must not be re-entered by the
    next trigger), with every exception caught so one bad pass never kills
    the loop.
  - `stop()`: cancels everything, awaits an in-flight tick.
- **Sync-cursor advance at the store point.** On every message durably
  stored — outbound via `SendMessageUseCase`'s result, inbound via
  `InboundPipeline.delivered` — call
  `syncCursors.recordLocalProgress(conversationId, senderDeviceId,
  sequenceNumber)`. E05-T04's implementation is a monotonic guarded upsert
  and never throws (EARS-MSG-5/6), so a failure here must not fail the
  message.
- **`sync_cursor_service.dart:113-114` corrected** to describe reality:
  named as called by `MessagingCoordinator`, not by T02/T03. **This is the
  only change to that file** — no behaviour change.
- **`delivery_states` writer.** Every transition the coordinator observes is
  appended as `(messageId, state, changedAt)`. It writes through
  `DeliveryStateMachine` (E05-T01) and never writes `messages.delivery_state`
  directly.
- **Startup reconciliation**, once per `start()`: for each `messages` row
  still `queued` whose relay packet exists in `relay_packets`, transition it
  to `sent`. This closes the crash window, and only that — it does not
  re-send, re-encrypt or re-enqueue anything.
- **Registration** in `messaging_stack.dart`: the coordinator is
  constructed and exposed on the stack. `start()` is called from the app's
  lifecycle at the point the chosen trigger model implies.

## 4. What this task does NOT do
- Does NOT implement Android background execution, a foreground service, a
  `WorkManager` job, or wake locks **unless `OQ-E06-T06-1` is answered that
  way** — and if it is, that answer names a new dependency and a new
  manifest permission, which is itself a 🧍 gate. E10
  (Notifications & Background) is the epic that owns background policy;
  this task must not annex it.
- Does NOT send acknowledgements or advance a message past `Sent` on its
  own. `Accepted`/`Delivered`/`Read` need a peer to say so — E06-T08.
- Does NOT implement the multi-device **gap-fill protocol** — see
  `OQ-E06-T06-2`.
- Does NOT write `RelayDeliveryState.failed` — see `OQ-E06-T06-3`.
- Does NOT modify `RelayEngine`, `RoutingEngine`, `SendMessageUseCase`,
  `ReceiveMessageUseCase` or `InboundPipeline`. It calls them.
- Does NOT retry, back off, or re-order the relay queue. `processQueue()`
  owns queue semantics (E04-T04); this task owns *when it runs*.
- Does NOT touch `lib/app/routes.dart`, `bindings.dart`, or any UI file.

## 5. Contract

### Functions
```yaml
- signature: "MessagingCoordinator({required MessagingStack stack, required InboundPipeline inbound, required Duration tickInterval, DateTime Function() clock})"
  params:
    tickInterval: "the value settled by OQ-E06-T06-1; injected, never hard-coded at a call site"
  purpose: "the one component that drives the messaging loop"

- signature: "MessagingCoordinator.start() -> Future<void>"
  returns: "completes once the inbound pipeline is subscribed and startup reconciliation has run"
  purpose: "CALLS InboundPipeline.start() — E06-T05 deliberately calls it nowhere, and this line is that obligation's owner. Also runs reconcileQueuedMessages() exactly once. Idempotent."

- signature: "MessagingCoordinator.tick() -> Future<void>"
  returns: "one full pass; never runs concurrently with itself"
  raises: "never — every failure is caught, counted and logged as metadata"
  purpose: "processQueue -> sweepExpired -> reclaimPayloads, in E04-B02's established order"

- signature: "MessagingCoordinator.reconcileQueuedMessages() -> Future<int>"
  returns: "count of messages moved queued -> sent because their relay packet already exists"
  purpose: "closes E05-T02 review observation 3's crash window at startup"

- signature: "MessagingCoordinator.recordStored(Message message) -> Future<void>"
  purpose: "advances the sync cursor and appends the delivery_states row; the single store point E05-B02 asked for"

- signature: "MessagingCoordinator.stop() -> Future<void>"
  purpose: "cancel the trigger, await an in-flight tick, stop the inbound pipeline"

- signature: "MessagingCoordinator.counters -> CoordinatorCounters"
  returns: "{ticks, forwarded, swept, reclaimed, tickFailures, reconciled}"
  purpose: "so 'is the loop alive?' is answerable without a debugger"
```

## 6. Risks
- **Re-entrancy.** `processQueue()` does I/O over a radio; a 5s tick over a
  12s pass produces overlapping passes forwarding the same packet twice.
  Guard with a simple in-flight flag and test it with a deliberately slow
  fake.
- **The counter/cursor class, recurrence 5, is directly in scope.**
  `recordLocalProgress` was E05-T04's lost-update defect (read → await →
  write), fixed with a guarded upsert. This task adds *more concurrent
  callers* to it — inbound deliveries and outbound sends can interleave.
  `implement/SKILL.md` §6 now requires both halves: audit every other
  reader, **and** write the two-concurrent-call falsification test. Do both,
  and put the audit in §Run log. If this class recurs a sixth time, E05's
  retro says that is the evidence a real analyzer is warranted — so a
  recurrence here is worth more than a fix, it is worth recording.
- **Battery is measured by nobody and asserted by everyone.** Whatever the
  chosen interval, do not claim an NFR-BATT-001 outcome that has not been
  measured. Record what was and was not measured in §Run log.
- The startup reconciliation reads two tables and writes one; it must be
  idempotent (running it twice must reconcile zero the second time) and must
  not run concurrently with the first tick.
- Do not let `recordStored` failures propagate. E05-T04's contract is
  never-throws; if it ever does, a message must still be delivered.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-MSG-1** *(the epic-level criterion E05 could not satisfy)*: WHEN a

  system SHALL retire it and reclaim its stored payload on the same
  schedule. (FR-ROUTE-004, NFR-SEC-001)

  SHALL continue driving subsequent passes. (FR-MSG-001)

## Open Questions
- **OQ-E06-T06-1 — 🧍 BLOCKING. What drives the relay queue?** E05-B02 left
  this for E06 by explicit human decision, and E05-B02 §Proposed fix
  direction names it rule 3 territory: application architecture plus
  battery/OS-lifecycle policy. The options, honestly:

  | Option | How it behaves | Cost / risk |
  |---|---|---|
  | **(a) Periodic timer, foreground only** | a `Timer.periodic` while the app is in the foreground; nothing runs when backgrounded | Simplest, zero new dependencies, zero permissions, fully testable on a fake clock. But: a queued message does **not** leave the phone until the user next opens the app, and `reclaimPayloads()` — the NFR-SEC-001 retention guarantee — only runs while someone is looking. |
  | **(b) Event-driven: on route/connectivity change** | tick when `RoutingEngine` learns a route or the transport reports a new peer | Best latency-per-battery: work happens exactly when it can succeed, which is what NFR-BATT-001 asks for. But: no event ⇒ no sweep, so TTL expiry and payload reclaim have no guaranteed schedule at all — the retention guarantee becomes conditional on traffic. |
  | **(c) (a) + (b): timer floor plus event triggers** | events tick immediately; a slow timer (e.g. 60 s) guarantees sweeps happen | Covers both failure modes. Slightly more machinery, one re-entrancy guard, one interval to justify. Still foreground-only, still no new dependency or permission. |
  | **(d) (c) + Android background execution** | a `WorkManager` job and/or a foreground service so the mesh runs with the app closed | The only option where the mesh behaves like a mesh when the phone is in a pocket — arguably the product's whole point. But: a new dependency, a new manifest permission, a persistent notification, OEM battery-killer behaviour (this project has already hit three MIUI restrictions), and it overlaps E10's declared scope. |

  - **Advisory recommendation: (c) now, with an interval of 60 s, and (d)
    shaped as an E10 task.** (c) is the smallest option that makes **both**
    EARS-MSG-1 and E04-B02's retention guarantee real, needs no new
    dependency or permission, and is fully testable on a fake clock. It is
    also the option that does not quietly annex E10's scope: background
    execution is a policy decision with a user-visible notification and
    OEM-specific behaviour, and doing it as a side effect of a chat task is
    how it ends up unowned. The honest cost of choosing (c): with the app
    closed, nothing forwards and nothing reclaims — **say so in the release
    notes rather than implying the mesh is always-on.**
  - Whatever is chosen, the answer must also fix the **interval number**,
    because `tickInterval` is injected and the test asserts the contract,
    not a guess (E05-B02: *"the test must assert the chosen contract, not a
    guessed one"*).
