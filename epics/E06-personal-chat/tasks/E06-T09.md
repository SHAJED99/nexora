# E06-T09 · Conversation read model

## 1. Goal
Give the three screens one query surface to read from — a conversation list
with its last-message preview, and a paged thread — so no controller
assembles its own SQL and no two screens disagree about what a conversation
is.

## 2. Business logic
- **There is no `Conversations` table and this task deliberately does not
  add one.** `messages.conversationId` is a bare `TextColumn` with no parent
  (`message_tables.dart:29`). Adding a table means a schema migration, which
  is a 🧍 human gate; the list is fully derivable from `messages` +
  `relationships`, so E06 stays off that gate. If a later epic needs
  per-conversation state (mute, pin, archive), that epic adds the table with
  the gate it requires.
- **Conversation identity for 1:1 is the peer's device id.** This is the
  one definition this task fixes, and everything downstream depends on it:
  `conversationId == peerDeviceId`. It follows from the data that exists
  (`relationships.deviceId` is the only peer key in the schema) and it makes
  the list ↔ trust join a plain equality. Group conversations (E07) will
  need a different id space; that is E07's problem and this task's
  `conversationId` is documented as opaque to callers so E07 can widen it
  without rewriting the screens.
- **Trust decides who appears (FR-TRUST-003, FR-BLOCK-001).** A blocked
  peer's conversation is excluded from the list. The states come from
  `RelationshipRepository` (E02-T01); this task joins, it does not
  re-implement trust logic.
- **The preview is metadata, and the ciphertext is not.**
  `messages.ciphertext` is opaque at this layer (E05-T01 §4). The list
  screen needs a preview string, which means someone must decrypt — and it
  is **not** this repository. The repository returns the last message's
  *identity and metadata*; decryption for display happens in the screen
  layer with the stack's `CryptoService`. Putting decryption in a repository
  that a future background job might call is how plaintext ends up
  somewhere nobody expected.
- **Keyset pagination, per `docs/conventions.md` and E05-T01 §2:**
  `WHERE created_at < :cursor ORDER BY created_at DESC LIMIT :n`. Never
  offset. The `(conversation_id, created_at)` index exists for exactly this
  query — E05-T01's review had to add it to the upgrade path after finding
  upgraded installs had no index at all.

## 3. What this task does
- **`ConversationSummary`** — `{conversationId, peerDeviceId,
  relationshipState, lastMessageId, lastMessageAt, lastMessageIsMine,
  lastMessageState, unreadCount}`. Metadata only; **no preview text**, by
  §2.
- **`ConversationRepository`:**
  - `listConversations()` — one row per `conversation_id` that has at least
    one message, joined to `relationships`, blocked peers excluded, ordered
    by `lastMessageAt DESC`. Written as a single grouped query, not
    N+1 per conversation.
  - `watchConversations()` — the same as a drift `watch()` stream, so the
    Conversations screen updates when a message arrives instead of polling.
    `RelationshipRepository` currently exposes only one-shot futures and
    `DevicesController` polls; this task does **not** change that repository
    (out of fence) — it watches the `messages` table and re-reads
    relationships on each emission.
  - `messagesPage(conversationId, {before, limit})` — keyset-paginated,
    newest-first, returning domain `Message` objects.
  - `watchConversation(conversationId)` — a stream of the newest page, for
    the live chat view.
  - `unreadCount(conversationId)` — messages from the peer not yet `read`.
- Everything returns domain types (`Message`, `ConversationSummary`), never
  drift rows, so the presentation layer never imports `database.dart`
  (ADR-0002's layering).

## 4. What this task does NOT do
- Does NOT add a table, column, index or migration. **No 🧍 schema gate is
  triggered by this task, and that is deliberate.** If the query genuinely
  cannot be written without a new index, stop and raise it as an Open
  Question — do not add one.
- Does NOT decrypt anything, and does not import `CryptoService`.
- Does NOT write. Read model only — no insert, no update, no delete. A
  repository that both reads for the UI and writes for the pipeline is how
  two write paths for one table appear.
- Does NOT modify `RelationshipRepository`, `message_tables.dart`, or any
  E05 file.
- Does NOT implement search (the Conversations screen's search field is
  T10's, over the already-loaded list), mute, pin, archive, or group
  conversations.
- Does NOT define what `Stored` means (`OQ-E06-T11-2`) — it returns whatever
  `delivery_state` the row holds.

## 5. Contract

### Functions
```yaml
- signature: "ConversationRepository(AppDatabase db, {required String selfDeviceId})"
  purpose: "read model over messages + relationships; constructed once, from the stack"

- signature: "ConversationRepository.listConversations() -> Future<List<ConversationSummary>>"
  returns: "one summary per conversation with >=1 message, blocked peers excluded, ordered lastMessageAt DESC"
  purpose: "the Conversations screen's Personal section and the Dashboard's Recent Conversations"

- signature: "ConversationRepository.watchConversations() -> Stream<List<ConversationSummary>>"
  returns: "emits on every change to messages; same ordering and filtering as listConversations"
  purpose: "so the list is live without polling"

- signature: "ConversationRepository.messagesPage(String conversationId, {int? before, int limit = 50}) -> Future<List<Message>>"
  params:
    before: "keyset cursor — created_at of the oldest row already held; null for the first page"
    limit: "page size; the caller decides, the repository does not cap silently"
  returns: "newest-first; fewer than `limit` rows means the end of the thread"
  purpose: "the Chat screen's scrollback. Keyset, never offset (docs/conventions.md)"

- signature: "ConversationRepository.watchConversation(String conversationId, {int limit = 50}) -> Stream<List<Message>>"
  purpose: "live newest page for the open chat"

- signature: "ConversationRepository.unreadCount(String conversationId) -> Future<int>"
  returns: "messages from the peer whose delivery_state is not `read`"
  purpose: "list badge; 0 for a conversation with no incoming messages"
```

## 6. Risks
- The "last message per conversation" query is the classic
  greatest-n-per-group problem, and the naive version is N+1. Write it as
  one grouped query and **assert the query count in a test** — a list screen
  that fires one query per conversation is the performance bug NFR-PERF-001
  would eventually be blamed for.
- `watchConversations()` re-reading relationships on each emission can
  amplify a chatty stream into a query storm. Debounce or coalesce, and test
  that a burst of ten inserts does not produce ten full re-reads.
- Ordering ties: two messages with the same `created_at` (plausible on a
  fast device) must have a deterministic order or the list flickers. Break
  the tie on `id`, and test it — this is the kind of thing that looks fine
  until a user watches a list re-order itself.
- Do not let `ConversationSummary` grow a `previewText` field "just for
  convenience". The moment it exists, someone fills it, and plaintext is in
  the read model. §2 is the reason; keep it.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-17**: WHEN the conversation list is read, the system SHALL
  return one entry per conversation with at least one message, ordered by
  most recent activity, excluding blocked peers. (FR-COMM-001,
  FR-TRUST-003, FR-BLOCK-001)
- **EARS-COMM-18**: WHEN a message thread is paged, the system SHALL return
  messages in a deterministic logical order using keyset pagination.
  (FR-MSG-004)
- **EARS-COMM-19**: WHEN a message is stored, the conversation list stream
  SHALL emit an updated list without the caller polling. (FR-COMM-001)

### Tests
- `test_EARS_COMM_17_one_entry_per_conversation_ordered_by_recency`
- `test_EARS_COMM_17_blocked_peer_is_excluded` — a conversation with
  messages whose peer is `blocked`: absent from the list, and its messages
  still present in the table (excluded from the view, never deleted).
- `test_EARS_COMM_17_list_is_a_single_query` — instrument the database and
  assert the query count does not grow with the number of conversations
  (10 conversations → the same count as 2).
- `test_EARS_COMM_18_keyset_paging_walks_the_whole_thread` — 120 messages,
  pages of 50, no duplicates, no gaps, terminating.
- `test_EARS_COMM_18_equal_timestamps_have_a_stable_order` — three messages
  with an identical `created_at`; the same order across repeated reads.
- `test_EARS_COMM_19_stream_emits_on_insert` — insert; the stream emits with
  the new message reflected.
- `test_no_ciphertext_is_decrypted_by_the_repository` — construct with a
  `CryptoService` that fails the test if invoked (it should not even be a
  constructor parameter — the assertion is that the file does not import it).
