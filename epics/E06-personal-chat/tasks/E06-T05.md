# E06-T05 · Live inbound pipeline

## 1. Goal
Turn bytes arriving on a radio into either a decrypted message in this
device's database or a packet queued for another device — the receive half
of the wedge, which has never existed in any form.

## 2. Business logic
- Today `TransportService.incomingData(deviceId)` yields `Uint8List` and
  **nothing subscribes to it**. `ReceiveMessageUseCase.call(senderDeviceId,
  CiphertextMessage)` (`receive_message_use_case.dart:102`) has no caller.
  E05's whole receive path is reachable only from tests.
- **Two dispositions, decided by the frame header alone** (E06-T02):
  - `frame.destination == selfDeviceId` → this packet is for us: decode the
    ciphertext by its `payloadType` tag, decrypt, hand to
    `ReceiveMessageUseCase`.
  - otherwise → **FR-ROUTE-002 store-and-forward**: hand the whole frame to
    `RelayEngine.enqueue(frame.destination, frameBytes, frame.priority,
    remainingTtl)` and never look inside. FR-ROUTE-003 is absolute here: a
    relay processes routing information and delivery metadata and **shall
    not be able to access plaintext**. The relay branch must not call the
    codec, must not call `decrypt`, and must not construct a `Message`.
- **Dedup is already correct and must not be re-implemented.**
  `ReceiveMessageUseCase` returns `null` for a duplicate (FR-MSG-003) and
  E05-T03 owns the ordering logic (FR-MSG-004). This pipeline's only job is
  to deliver each inbound packet to it exactly once and to treat a `null`
  return as a normal outcome, not an error.
- **The catch that E03-B03 was deferred to.** E03's retro deferred the
  exception taxonomy "to whichever of E05/E06 first wraps a `catch` around
  `decrypt()`". This is that `catch`. It uses T02's typed failures, and its
  policy is: **a bad packet must never take the pipeline down.** A malformed
  frame, an undecryptable ciphertext, or an unknown sender is logged
  (metadata only) and dropped; the subscription survives. A single
  malformed packet that kills the receive loop is a trivial remote
  denial-of-service.
- Deliberately **not** a security decision made here: an undecryptable
  message from a *trusted* contact may indicate a session break worth
  surfacing to the user. This pipeline records the reason; deciding what
  the UI says about it is `OQ-E06-T05-1`.

## 3. What this task does
- **`InboundPipeline`** — subscribes to `TransportService.incomingData` for
  every connected peer (and to newly-connected peers as they appear), and
  for each buffer:
  1. `RelayPacketFrame.deserialize` → on `FormatException`, drop + count.
  2. Expiry check against `frame.expiresAtMs` → past-TTL packets are
     dropped, not forwarded (FR-ROUTE-004).
  3. `destination == selfDeviceId` ?
     - **yes** → `CiphertextCodec.decode(frame.payloadType, frame.payload)`
       → `ReceiveMessageUseCase.call(frame.source, ciphertext)`;
       `null` result = duplicate, counted as such.
       `payloadType == control` → routed to the registered control handler
       (T07's prekey bundles, T08's acks) via the extension point below;
       **with no handler registered, a control frame is dropped and
       counted, never guessed at.**
     - **no** → `RelayEngine.enqueue(frame.destination, originalBytes,
       frame.priority, remainingTtl)`. Note it re-enqueues the **original
       bytes**, not a re-serialized frame, so a forward is byte-preserving
       and a relay cannot alter what it did not read.
  4. Every failure path increments a named counter exposed on the pipeline
     (`malformed`, `expired`, `undecryptable`, `duplicate`, `forwarded`,
     `delivered`, `unhandledControl`) so a bug sweep and the Dashboard have
     something real to look at instead of silence.
- **The control-frame extension point:**
  `registerControlHandler(ControlHandler)` — a single named registration
  T07 and T08 use. This task defines the seam and registers **nothing**.
- **A stream of delivered messages** (`Stream<Message> get delivered`) so
  T09's read model and T11's chat screen have a live signal rather than
  polling. Broadcast, and it must not hold the pipeline open when nothing
  listens.
- `InboundPipeline.start()` / `stop()`. **Nothing in this task calls
  `start()`** — E06-T06 owns that, and states it in its own §3 and
  `functions:` so the obligation lives in a binding contract and not in a
  sibling's prose (L-process-006).

## 4. What this task does NOT do
- Does NOT decide when `processQueue()`/`sweepExpired()`/`reclaimPayloads()`
  run — that is E06-T06 and it carries a 🧍 blocking decision.
- Does NOT construct or register itself in `messaging_stack.dart` or
  `bindings.dart`. It touches **no** shared file, deliberately, so it can be
  built in parallel with T04 and T09.
- Does NOT define the prekey-bundle body (T07) or the ack body (T08). It
  reserves the handler seam and nothing more.
- Does NOT modify `ReceiveMessageUseCase`, `RelayEngine`, `CryptoService`,
  `MessageEnvelope`, or anything E02-E05 merged. If the receive use case
  cannot be driven as documented, that is an Open Question.
- Does NOT advance a message past `Accepted`, send an acknowledgement, or
  write `delivery_states` rows — T06 and T08.
- Does NOT advance sync cursors (T06 owns `recordLocalProgress`).
- Does NOT decrypt, inspect, log, re-frame or measure the payload of a
  packet destined elsewhere. FR-ROUTE-003 — this is the single most
  important prohibition in the task.
- Does NOT surface anything to the user. Counters and a stream; no UI, no
  notification (E10).

### Functions
```yaml
- signature: "InboundPipeline({required MessagingStack stack, DateTime Function() clock})"
  purpose: "the receive loop; takes the whole stack because it needs transport, relay, receive-use-case and selfDeviceId"

- signature: "InboundPipeline.start() -> void"
  returns: "nothing; idempotent — a second call must not double-subscribe"
  purpose: "begin consuming incomingData. CALLED BY E06-T06, which declares this in its own contract"

- signature: "InboundPipeline.stop() -> Future<void>"
  purpose: "cancel every subscription; required for test isolation"

- signature: "InboundPipeline.delivered -> Stream<Message>"
  returns: "broadcast; one event per message newly persisted by ReceiveMessageUseCase (never for a duplicate)"
  purpose: "live update signal for the read model (T09) and the chat screen (T11)"

- signature: "InboundPipeline.registerControlHandler(ControlHandler handler) -> void"
  params: { handler: "handles a PayloadType.control frame; T07 (prekey bundles) and T08 (acks) register here" }
  raises: "StateError if two handlers claim the same control sub-type"
  purpose: "the declared extension point, so later tasks extend a seam instead of editing this file"

- signature: "InboundPipeline.counters -> InboundCounters"
  returns: "{malformed, expired, undecryptable, duplicate, forwarded, delivered, unhandledControl}"
  purpose: "so silent drops are countable — the bug sweep's only handle on this loop"
```

### Data
None — no schema change. Rows are written only through
`ReceiveMessageUseCase` and `RelayEngine.enqueue`, both already owning their
own tables.

## 6. Risks
- **The forwarding branch is where FR-ROUTE-003 gets broken by accident.**
  A debug `print(frame)` whose `toString()` includes the payload, a
  "helpful" `payload.length` log, an early `CiphertextCodec.decode` before
  the destination check — any of these is a real breach of the guarantee
  E04 spent a task proving. Write the destination check **first**, before
  the payload is bound to a local variable at all, and assert it with a test
  that fails if decode is reachable on the relay branch.
- Subscription lifecycle: peers connect and disconnect constantly. A
  subscription per peer that is never cancelled leaks; a single subscription
  that misses newly-connected peers loses messages. Test both.
- `start()` idempotency matters more than usual here: T06 may call it from a
  lifecycle callback that fires more than once, and a double subscription
  delivers every packet twice — which dedup would hide, making it invisible
  until a counter is read.
- E05-B01's lesson applies directly: when writing the "malformed frame is
  rejected" test, prove it fails *for the reason claimed* by mutating the
  guard. The original E05-B01 regression test threw pre-fix for the wrong
  reason and looked green.
- Do not treat `ReceiveMessageUseCase` returning `null` as an error. It is
  the documented duplicate signal (FR-MSG-003) and will be the common case
  in a mesh that forwards the same packet down two paths.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-8**: WHEN a relay packet addressed to this device arrives, the
  system SHALL decrypt it and persist it exactly once. (FR-MSG-003,
  NFR-SEC-001)
- **EARS-COMM-9**: WHEN a relay packet addressed to another device arrives,
  the system SHALL queue it for forwarding without accessing its payload.
  (FR-ROUTE-002, FR-ROUTE-003)
- **EARS-COMM-10**: IF an inbound packet is malformed, expired, or cannot be
  decrypted, THEN the system SHALL drop it, count it, and continue
  processing subsequent packets. (FR-MSG-003)

### Tests
- `test_EARS_COMM_8_addressed_packet_is_delivered` — the **end-to-end seam
  test this epic exists for**: build a frame through T03's real
  `MessageEncryptFn` on a "sender" stack, feed the bytes to a "receiver"
  stack's pipeline, assert a decrypted row lands with the right
  conversation, sender and sequence number. If E05-B01's producer/consumer
  gap ever reopens, this test is what catches it.
- `test_EARS_COMM_8_duplicate_packet_persists_once` — same bytes twice; one
  row; `counters.duplicate == 1`; `delivered` stream emits once.
- `test_EARS_COMM_9_foreign_packet_is_forwarded_unread` — a frame for
  another destination; assert `RelayEngine.enqueue` got the **identical**
  byte buffer, assert a row in `relay_packets`, and assert the decrypt
  function was **never invoked** (inject a decrypt that fails the test if
  called — the FR-ROUTE-003 assertion).
- `test_EARS_COMM_9_expired_foreign_packet_is_dropped_not_forwarded` —
  `expiresAtMs` in the past; nothing enqueued; `counters.expired == 1`.
- `test_EARS_COMM_10_malformed_packet_does_not_stop_the_loop` — a bad
  buffer followed by a good one; the good one is delivered;
  `counters.malformed == 1`.
- `test_EARS_COMM_10_undecryptable_packet_is_dropped_typed` — decrypt throws
  the mapped `CryptoDecryptFailure`; counted as `undecryptable`, loop alive.
- `test_control_frame_without_a_handler_is_counted_not_guessed` —
  `unhandledControl == 1`, nothing decoded as a message.
- `test_start_is_idempotent` — two `start()`s, one delivery per packet.
- `test_peer_connected_after_start_is_subscribed` — the lifecycle case that
  silently loses messages if missed.

## Open Questions
- **OQ-E06-T05-1 — an undecryptable message from a trusted contact is
  currently indistinguishable from noise, and that may be a safety signal
  the user should see.** E03's retro notes that a broken session (a
  reinstall, a device change, or an attack) produces exactly this symptom,
  and Signal-family apps normally surface it as a safety-number warning.
  This pipeline counts it and drops it. Whether E06's UI should show
  anything — a per-conversation banner, nothing at all, or a Devices-screen
  prompt to re-verify — is a product decision, not a builder's.
  **Advisory recommendation: count it now, show nothing in E06, and shard
  the surface in the epic that owns safety numbers** — showing a scary
  warning for what is usually a benign reinstall is its own harm, and there
  is no design source for the treatment (a `design/gaps.md` entry would be
  needed first). Not blocking: the counter and the failure reason are
  recorded either way, so the answer changes UI, not this pipeline.
