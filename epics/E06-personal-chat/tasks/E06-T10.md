# E06-T10 · Conversations screen

## 1. Goal
The list a user actually opens the app to see: their real conversations,
ordered by recency, with the Groups section honestly empty until E07.

## 2. Business logic
- **Rule 2.** `design/screens/conversations.md` is law: 45 checklist
  elements, 32 verbatim strings, measured tokens. Every string is
  character-for-character (`Personal`, `Groups`, `Search conversations...`,
  `Dashboard`, `Conversations`, `Devices`, `Settings`). The design's example
  data (`Ahmed`, `Rahim`, `Sounds good, see you then!`, `10:42 AM`) is
  **data, not copy** — it is replaced by real values; the gate's copy check
  treats those as dynamic per the contract's ignore rules, and the
  *structure* around them must match exactly.
- **Data comes from `ConversationRepository.watchConversations()`** (T09)
  — live, not polled. Blocked peers are already excluded there
  (FR-TRUST-003); this screen does not re-filter.
- **The preview text requires decryption, and this screen is where it
  happens** (T09 §2 deliberately excludes it from the repository). Decrypt
  the last message via the stack's `CryptoService` for display only.
  Plaintext lives in the controller's ephemeral state and **is never
  persisted, logged, or written back**. If decryption fails, show the
  contact and timestamp with no preview rather than an error row — a broken
  session must not make a conversation disappear.
- **Approved gaps that bind this screen:** GAP-006 (Groups heading rendered,
  its three rows knowingly absent until E07), GAP-007 (empty Personal
  state). Both are 🟡 pending the human's sign-off; **this task may not
  build until `design/gaps.md`'s new entries are approved** — that is the
  `design_contract_approval` gate, and it is the cheapest one in the system.
- **The design element that must not be deleted:** the `Groups` heading
  stays even with nothing under it. `skills/design-fidelity` rule 3 —
  never delete a design element to satisfy the data layer.
- FR-UI-005 (all strings from localization resources, RTL-safe logical
  padding) applies to every string added here; follow whatever
  `lib/features/devices/presentation/` already does, and if it does not do
  it, match the existing pattern and note the divergence rather than
  starting a second convention inside one epic.

## 3. What this task does
- `/conversations` route + `ConversationsView` + `ConversationsController` +
  `ConversationsBinding`, following the three-file GetX pattern
  `lib/features/devices/presentation/` established.
- Renders, per the contract: header (`hub`, `NEXORA`, `search` action),
  search field, `Personal` section from real data, `Groups` section heading
  with GAP-006's empty treatment, and the bottom nav with `Conversations`
  active (elements 34-45) routing to `/dashboard` (T12), `/devices`,
  `/settings`.
- Row content per conversation: avatar or initials (`MS`-style, element 15,
  when there is no image — there is no avatar column, GAP-003), peer name,
  relative timestamp, decrypted preview, the delivery tick, and the `lock`
  glyph.
- Search filters the already-loaded list client-side. No new query, no
  server round trip, no history search — the contract shows a field, not a
  search results screen.
- Tapping a row navigates to `/chat/<conversationId>` (T11's route, added
  by T11 — until then the tap is inert and the task says so in §Deviations
  rather than inventing a destination).
- Registers this screen in `test/design/design_probe_test.dart` (T01's
  runner) so the gate can see it.
- Loading, empty and error states — all three, per the template and
  GAP-007.

## 4. What this task does NOT do
- Does NOT build the Chat screen (T11) or the Dashboard (T12).
- Does NOT populate Groups, create a group, or read any group data (E07).
- Does NOT add rows, buttons, menus or filters the contract does not draw.
  A real workflow that needs one is a new `design/gaps.md` entry for human
  approval, not an invented control (the E02-T02 precedent).
- Does NOT change tokens, `design/thresholds.yaml`, or any generated table
  in the contract.
- Does NOT touch `lib/app/bindings.dart` — the stack is already registered
  permanently by T03, and leaving that file alone is what lets this task run
  in parallel with the backend chain.
- Does NOT write to the database, send a message, or drive the messaging
  loop.
- Does NOT implement message search, mute, pin, archive or swipe actions.

## 5. Contract

### UI
- **Design contract:** `design/screens/conversations.md` — build from this,
  not from the screenshot.
- **Route:** `/conversations`, added to `lib/app/routes.dart` and
  `docs/routes.md`. Nav from: bottom nav on `/dashboard`, `/devices`,
  `/settings`. Nav to: `/chat/<id>` (T11), and the three other nav targets.
- **States required:** loading (first stream emission pending) · data ·
  empty (GAP-007) · error (repository or stack `unavailable` per T03's
  `MessagingStackStatus` — an honest message, not a blank screen).
- **Gate:** `make design-probe && make design-verify SCREEN=conversations
  IMPL=flutter` **green before the PR** (rule 2). Extra or missing elements
  must each trace to an approved `design/gaps.md` entry; anything else is a
  hard finding and blocks the PR.

## 6. Risks
- **This is the first screen the new gate has ever judged, so expect the
  first run to be red for gate reasons rather than build reasons** —
  role mapping, font-family (`OQ-E06-T01-1`), and geometry. Iterating
  against the gate is the job (2-4 rounds is normal on a first screen).
  **Do not loosen `thresholds.yaml`; do not "fix" the contract.** If the
  gate is wrong, that is a T01 bug and a finding, not a threshold change.
- `OQ-E06-T01-1` (fonts) is **blocking for this task's gate result**. If it
  is unresolved when this task starts, the gate will report a font-family
  finding on every text element. Do not start until it is answered, or the
  first PR is unreviewable.
- Decrypting a preview per row on every stream emission is real work on the
  UI thread and NFR-PERF-001 lives here. Cache by message id; decrypt only
  what changed.
- Two sources of "who is this person": `relationships` has no display-name
  column (GAP-003), so names are device ids or initials today. Do not invent
  a name, and do not silently show a raw device id where the design shows
  `Ahmed` — follow GAP-003's already-approved treatment.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-20**: WHEN the Conversations screen is opened, the system
  SHALL display every non-blocked conversation with at least one message,
  most recent first. (FR-COMM-001, FR-TRUST-003)
- **EARS-COMM-21**: WHEN a message arrives while the screen is open, the
  list SHALL update without user action. (FR-COMM-001)
- **EARS-COMM-22**: IF there are no conversations, THEN the screen SHALL
  show the approved empty state and still render the section headings and
  navigation. (FR-COMM-001, GAP-006, GAP-007)
