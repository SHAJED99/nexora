# E06-T14 · Add a Message entry point to Trusted/Allowed device rows (GAP-030)

## 1. Goal
Give a user an actual way to start a conversation with an
already-trusted device — the one missing piece found during live
two-device on-hardware testing this session, after real Bluetooth
discovery and mutual trust verification worked end-to-end but nothing in
the app could then reach `chat.md` for that peer.

## 2. Why this had no owner until now
`ChatController`'s own `conversationId == peerDeviceId` convention, and
`Routes.chat` (`/chat/:id`) being a real, already-working, already-bound
route, both existed from `E06-T11` onward — but no screen ever called
`Get.toNamed(Routes.chat)` for a device with no prior conversation.
`conversations.md`'s own empty state (`GAP-007`) never proposed a compose
affordance; `devices.md`'s rows offered only the kebab menu's `Block`
action. This is a genuine design-contract gap (`GAP-030`,
`design/gaps.md`), not an oversight inside an already-approved contract —
building UI for it needed human sign-off on the entry point itself
(rule 2), obtained 2026-09-08 in direct response to a question about
whether to build this now to complete real hardware verification of the
underlying mesh transport (`OQ-E06-T04-2`).

## 3. What this task does
Adds a `Message` icon-button (`Icons.chat`) to each `Trusted`/`Allowed`
row on the Devices screen, positioned before the existing kebab menu.
Tapping it navigates to `Routes.chat` with that row's own `deviceId` as
the route parameter — no new screen, no change to `chat_view.dart`/
`chat_controller.dart`, which already handle a conversation with zero
prior messages correctly (`GAP-008`'s own empty-state coverage).

## 4. What this task does NOT do
- Does **not** add the button to `Unknown` rows (no session exists yet —
  messaging one would either silently no-op or require inventing new
  first-contact UI, neither of which this task's scope covers) or
  `Blocked` rows (must not gain a new way to reach a blocked peer).
- Does **not** add any compose/add affordance to `conversations.md`
  itself — `GAP-030`'s own proposal deliberately anchors this to
  `devices.md`, where a trust decision about a specific device is already
  being made, not a new list-level "add contact" flow.
- Does **not** change `chat_view.dart`, `chat_controller.dart`, or
  `Routes.chat`'s own binding — all three already work correctly for a
  brand-new, empty conversation; this task only adds a way to reach them.
- Does **not** implement multi-device disambiguation (an account with
  more than one trusted device showing up as more than one row) — out of
  scope, unrelated to this gap.

## 5. Contract
- **Changed:** `devices_view.dart`'s `_DeviceRow` — one new conditional
  `IconButton` (`Icons.chat`, tooltip `'Message'`), gated on
  `relationship.state == RelationshipState.trusted || .allowed`, calling
  `Get.toNamed('/chat/${relationship.deviceId}')`.
- **New design record:** `design/gaps.md` GAP-030 (human-approved
  2026-09-08); `design/screens/devices.md`'s own Journey gaps section
  cross-references it.

## 6. Risks
None new — this reuses an existing, already-tested route
(`Routes.chat`) and an existing button treatment
(`OnProcessButtonWidget`'s trailing-position convention, though this
specific control is a plain `IconButton` matching the kebab's own
`IconButton`-family treatment rather than the `Verify` row's filled
button, since this is a single glyph action not a labeled CTA).
