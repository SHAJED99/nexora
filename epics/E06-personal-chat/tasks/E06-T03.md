# E06-T03 · Messaging composition root

## 1. Goal
Construct, exactly once per app launch, the objects E02-E05 built and nobody
ever instantiated — so that from this task on, "the messaging stack" is a
thing that exists at runtime instead of a set of classes that only tests have
ever seen.

## 2. Business logic
- **The finding this task exists for:** `SendMessageUseCase`,
  `ReceiveMessageUseCase`, `SyncCursorService`, `ConflictResolver`,
  `RelayEngine` and `RoutingEngine` have **zero construction sites anywhere
  in `lib/`**. `lib/app/bindings.dart` registers only `AppDatabase`,
  `DeviceIdentityRepository`, `SignInUseCase`, `RelationshipRepository`,
  `BlockUseCase` and three controllers. Four epics of correct components,
  no composition layer — the root cause E05's bug sweep named behind both
  E05-B01 and E05-B02.
- **Single instance is a correctness requirement, not tidiness.** E05-T02's
  review recorded that `SendMessageUseCase._generateId`
  (`send_message_use_case.dart:212`) is unique **per instance**, and that two
  instances sharing one `AppDatabase` collide on `messages.id` — the
  reviewer reproduced `SqliteException(1555): UNIQUE constraint failed`. The
  same review established that the sequence-number guarantee rests on
  drift's per-`DelegatedDatabase` lock, which **does not hold across two
  `AppDatabase` connections**. So: one `AppDatabase`, one
  `SendMessageUseCase`, one `RelayEngine`, app-wide, permanently. This task
  is where that becomes structurally true rather than a comment.
- **Startup order matters and is currently absent.** `lib/app/main.dart`
  does `ensureInitialized → Observability.init → Firebase.initializeApp →
  runApp`. `CryptoService.init(store)` is never called; `IdentityService`'s
  `ensureLocalIdentity` / `ensureSignedPreKey` / `replenishOneTimePreKeys`
  are never called. Without them `CryptoService.encrypt` throws
  `StateError` on the first message and there is no local identity to
  publish a bundle from (T07's whole premise).
- ADR-0002 (GetX + MVC + Clean Architecture) and ADR-0005 (device identity
  and session are fully local; Firebase Auth is a thin account pointer) both
  bind here: the stack is constructed locally, needs no network to come up,
  and must build correctly with Firebase absent.

## 3. What this task does
- **`MessagingStack`** — a plain Dart class (not a GetX controller) that
  owns the graph and exposes each member as a `final` field:
  `db`, `identityService`, `cryptoService`, `transport`, `routingEngine`,
  `relayEngine`, `sendMessage`, `receiveMessage`, `syncCursors`,
  `selfDeviceId`. Construction is via a static async factory because
  crypto/identity init is asynchronous.
- **The adapters, which are the actual work.** Each is a small named
  function inside this file, not a lambda buried in a constructor call:
  - `MessageEncryptFn`: `(recipientDeviceId, envelopeBytes) ->`
    `CryptoService.encrypt(SignalProtocolAddress(recipientDeviceId, 1),
    envelopeBytes)` then `CiphertextCodec.encode(...)` (T02) and
    `RelayPacketFrame(...).serialize()`. **This is the producer half of the
    wire format** whose absence was E05-B01. The `deviceId: 1` constant
    matches `receive_message_use_case.dart:61`'s `_localSignalDeviceId` —
    use the same constant, do not re-declare it.
  - `MessageEnqueueFn`: the tear-off of `RelayEngine.enqueue`. E05-T02's
    review verified positional order, arity and return type already match
    exactly (`relay_engine.dart:106-111` vs
    `send_message_use_case.dart:69-74`) — no adapter shim, and if one seems
    necessary, something has drifted and that is a finding, not a fix.
  - `RelaySendFn`: `(nextHopId, payload) -> TransportService.send(nextHopId,
    payload)`.
- **Startup sequence in `lib/app/main.dart`**, before `runApp`, in this
  order and with each step's failure handled explicitly:
  `AppDatabase` → `DriftSignalProtocolStore` → `CryptoService.init(store)` →
  `IdentityService.ensureLocalIdentity()` → `ensureSignedPreKey()` →
  `replenishOneTimePreKeys()` → `MessagingStack.create(...)`.
- **`lib/app/bindings.dart`** — `Get.put(stack, permanent: true)` plus
  `permanent` registrations for the members screens will resolve. Every
  registration in this task is `permanent: true`; nothing messaging-related
  is `lazyPut` at app scope, because a lazily-created second instance is the
  exact defect §2 describes.
- **A failure that does not brick the app.** If crypto init fails, the app
  still launches and the messaging stack reports itself unavailable — the
  Dashboard and Conversations screens must be able to render an honest
  "messaging unavailable" state rather than the process dying at startup.
  Expose this as a single `MessagingStackStatus` (`ready` / `unavailable`
  with a reason), and let T10/T12 read it.

## 4. What this task does NOT do
- Does NOT start anything. No timer, no stream subscription, no
  `processQueue()`, no `incomingData` listener. Construction only. Starting
  the inbound pipeline is T05's and the queue driver is T06's — and T06 is
  where the 🧍 trigger-model decision lives.
- Does NOT wire link quality (T04), prekey exchange (T07), acks (T08), or
  any UI.
- Does NOT modify `SendMessageUseCase`, `ReceiveMessageUseCase`,
  `RelayEngine`, `RoutingEngine`, `SyncCursorService` or `CryptoService`.
  If an adapter cannot be written without changing one of them, **stop and
  log an Open Question** — that is a contract mismatch between merged
  epics, not something to patch from the composition root.
- Does NOT add a service locator of its own, a DI package, or a second
  registration mechanism. GetX is the accepted pattern (ADR-0002).
- Does NOT call `establishSession`. Sending will still fail with
  `messaging.no_session` until T07 lands — that is the honest state, and
  §8's test asserts it rather than papering over it.
- Does NOT touch `lib/app/routes.dart` — no route changes here, so the UI
  tasks own that file uncontested.

## 5. Contract

### Functions
```yaml
- signature: "MessagingStack.create({required AppDatabase db, required String selfDeviceId, TransportService? transport, DateTime Function() clock}) -> Future<MessagingStack>"
  params:
    db: "the single app-wide AppDatabase already registered in bindings.dart"
    selfDeviceId: "from DeviceIdentityRepository — the local device identity (ADR-0005: local, not Firebase-derived)"
    transport: "injectable for tests; defaults to the app's single TransportService"
  returns: "a fully-constructed stack with status ready, or a stack with status unavailable and every member still non-null-safe to reference"
  purpose: "the one place the messaging graph is assembled — rule: exactly one call per process"

- signature: "MessagingStack.status -> MessagingStackStatus"
  returns: "ready | unavailable(reason)"
  purpose: "so a screen can render an honest degraded state instead of throwing in a build method"

- signature: "MessagingStack.dispose() -> Future<void>"
  purpose: "closes transport subscriptions and the database in tests; the app process does not call it"
```

### Data
None — no schema change, no migration. (Deliberate: the read model T09
builds is derived, precisely so E06 does not need a 🧍 schema gate.)

### External services & flags
No new dependency, no new secret, no new env var. Firebase is already
initialized by `lib/app/main.dart`; this task must work when
`Firebase.initializeApp()` has failed (offline-first, ADR-0005) — assert it
in a test.

## 6. Risks
- **The first real end-to-end construction will surface contract drift
  between merged epics.** Expect at least one signature that does not line
  up as documented. The right response is an Open Question naming both
  sides, not a silent shim in the adapter — a shim here is invisible to
  every future reader and is how "two callers mean different things by one
  method" (L-backend-003, five recurrences) starts again.
- Startup latency: identity + prekey replenishment on a cold start does DB
  and crypto work before the first frame. Do it after `runApp` if it costs
  visible startup time, but then the stack's `status` must be `unavailable`
  until it completes and the UI must handle it — do not race.
- `Get.put(..., permanent: true)` in tests leaks between test cases. Use
  `Get.testMode = true` and reset in `tearDown`, following
  `test/features/devices/presentation/devices_controller_test.dart`.
- Do not construct a second `AppDatabase` for the stack. §2 explains why
  precisely; a test that constructs two and asserts the collision is worth
  more than a comment.

**Deviations from spec/design:**
- **`_localSignalDeviceId` (value `1`) is re-declared in `messaging_stack.dart`
  rather than imported from `receive_message_use_case.dart:61`.** The task
  file's own instruction says to reuse that constant "do not re-declare it",
  but it is `library`-private (leading underscore) — Dart's own privacy model
  makes literal cross-file reuse impossible, and every other private
  per-device/per-instance constant in this codebase (`identity_service.dart`'s
  `_localDeviceId`, `relay_engine.dart`'s `_generateId`,
  `send_message_use_case.dart`'s `_generateId`) is independently declared per
  file for the same reason. Re-declared here with an explicit cross-reference
  comment (`messaging_stack.dart`'s header, judgment call 1) rather than left
  unexplained. Not treated as an Open Question: it is a language constraint,
  not a mismatch between what two epics built.
- **The wire frame's `packetId` is the message's own envelope `id`, not
  `RelayEngine`'s local `relay_packets.id`.** `relay_packet_frame.dart`'s
  header comment calls the field "RelayEngine's packet id", but the encrypt
  adapter (which builds the frame) necessarily runs BEFORE
  `SendMessageUseCase` ever calls `relayEngine.enqueue` — the call that mints
  that local id (`relay_engine.dart:113`) — so it provably does not exist yet
  at the point the frame is built. Re-reading FR-ROUTE-004 and
  `relay_engine.dart`'s own comments confirms each hop's `relay_packets.id`
  is that hop's own local queue-row key, never shared across hops — so the
  wire frame's `packetId` was always going to be a *different*, originator-
  minted identifier regardless. Used the message's own envelope `id`
  (`MessageEnvelope.deserialize(envelopeBytes).id`, already unique per
  `SendMessageUseCase._generateId` and already available to the adapter as
  the plaintext it is about to encrypt) instead of inventing a second
  id-generation scheme. Full reasoning in `messaging_stack.dart`'s header,
  judgment call 2, and proven by
  `test_EARS_COMM_6_encrypt_adapter_produces_a_parseable_frame`'s
  `expect(frame.packetId, message.id)`. Treated as a judgment call within the
  documented adapter shape (§3 only says "then `RelayPacketFrame(...)
  .serialize()`", not how each field is populated), not an Open Question — no
  signature changed, nothing is blocked.
- **`selfDeviceId` may be `''` at cold boot on a fresh install, and
  `MessagingStack.create` degrades to `unavailable` rather than crashing or
  inventing a placeholder id.** E01-T01's device identity
  (`device_identities.device_id`) is generated and persisted only inside
  `LoginController._signIn` — never before a user's first sign-in
  (`login_controller.dart:41-58`). `lib/app/main.dart` runs before any UI, so
  on a fresh install there is no `selfDeviceId` yet the very first time this
  composition root runs. `main.dart` passes
  `db.latestDeviceIdentity()?.deviceId ?? ''` unconditionally (never skips
  calling `create()`, per task file §5's "always returns a valid object"
  contract), and `MessagingStack.create` treats an empty `selfDeviceId` as one
  more `unavailable` reason, structurally identical to a crypto-init failure
  — not a special case any caller has to know about. Full reasoning in
  `messaging_stack.dart`'s header, judgment call 3. **Not fully resolved by
  this task** — see the non-blocking Open Question below; recorded as a
  Deviation because it does not change any given signature and every one of
  §8's tests still passes (none of them exercises the pre-first-sign-in
  state, since every test supplies a concrete `selfDeviceId`).

## Open Questions
- **OQ-E06-T03-1 — a first-time user has no live messaging in their very
  first app session, only after restarting post-sign-in.** E01-T01's device
  identity (`device_identities.device_id`) is generated only inside
  `LoginController._signIn`, never before. `lib/app/main.dart` runs the
  messaging composition root once, at process start, before any UI —
  including before a fresh install's first sign-in. `MessagingStack.create`
  handles this honestly (degrades to `unavailable('no local device identity
  yet (sign in required)')` rather than crashing — see §Self-review's third
  Deviation), but the practical consequence stands: this session's
  `MessagingStack` was built with `selfDeviceId: ''` and stays `unavailable`
  for the rest of that process's lifetime, even after sign-in completes a
  moment later in the same session — nothing re-runs composition
  mid-process. A user only gets working messaging after killing and
  reopening the app once, post-sign-in. Not blocking for THIS task: nothing
  in E06-T03's own scope starts or exercises live messaging within a running
  session anyway (task file §4 — no timer, no queue driver, no UI). Worth a
  human/planner decision before T05/T06/T09 land, since those tasks are
  exactly where this would first become user-visible. Options: (a) leave
  it — messaging becomes available on next launch, a one-time first-run
  quirk; (b) have `LoginController._signIn` (or a listener on it) trigger a
  second `MessagingStack.create()` call and re-`Get.put` it once sign-in
  completes, replacing the `unavailable` instance in place; (c) re-order
  E01's flow so a local device identity is generated at first app launch
  (independent of sign-in) rather than during it, which ADR-0005 already
  treats device identity as (local, not account-derived) — arguably the
  cleanest fix, but changes E01-T01's own flow, which is outside E06-T03's
  `files:` fence. Advisory recommendation: (c), decided at the human gate,
  since it also simplifies away this whole class of "identity not ready at
  boot" question for every future epic — but E06-T03 does not act on that
  itself.
