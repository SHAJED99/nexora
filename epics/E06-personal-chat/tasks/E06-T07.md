# E06-T07 · Prekey-bundle exchange

> ⛔ **This task carries a 🧍 blocking Open Question (`OQ-E06-T07-1`):
> where prekey bundles come from.** It is a protocol-and-trust
> architecture choice (rule 3), it interacts with ADR-0005's
> "Firebase is a thin account pointer, identity is local" stance, and it is
> the difference between a mesh that works with no internet and one that
> does not. **Do not start implementation until it is 🟢.**

## 1. Goal
Make it possible to send a first message to someone. Today it is not:
`CryptoService.establishSession` has zero callers, there is no way to obtain
a peer's `PreKeyBundle`, and every first send fails with
`AppFailure('messaging.no_session')`.

## 2. Business logic
- **OQ-E05-T02-1, verbatim:** *"How does a device obtain a recipient's
  `PreKeyBundle` to establish a session in the first place? No task in
  E01-E04 builds a prekey-bundle exchange mechanism … real sending is
  impossible end-to-end until this is answered. Flagging for the planner —
  likely belongs to E06 (first real chat UI, where 'start a conversation'
  naturally needs this)."* E06 is that epic and this is that task.
- **What exists:** `IdentityService.getLocalPreKeyBundle()`
  (`identity_service.dart:120`) produces an in-process `PreKeyBundle`;
  `DriftSignalProtocolStore.issueOneTimePreKey()` (`:260`) hands out a
  one-time key; `CryptoService.establishSession(address, bundle)`
  (`crypto_stub.dart:67`) runs X3DH via `SessionBuilder`. **What does not
  exist:** any serializer, any transport frame, any directory, any caller.
  A `PreKeyBundle` has never left a process.
- **ADR-0003** (Signal, X3DH + Double Ratchet) makes bundle exchange
  mandatory, not optional — X3DH *is* a bundle exchange. So this is
  implementation inside an accepted ADR; what is **not** settled by any ADR
  is *the channel* the bundle travels over, which is `OQ-E06-T07-1`.
- **Trust gates the exchange, and this is a security boundary, not a
  convenience.** FR-TRUST-005: "a connection is permitted only when both
  sides allow it." A bundle request from a `blocked` peer is refused; from
  an `unknown` peer it follows whatever the trust layer already decides
  (`EvaluateConnectionRequestUseCase`). This task **calls** the existing
  trust logic; it does not restate or reinvent it.
- **The identity-key trust decision is where this could go quietly wrong.**
  `establishSession` throws `UntrustedIdentityException` when a peer's
  identity key changes. Auto-trusting on change would silently defeat the
  end-to-end guarantee the Chat screen literally prints on itself
  ("End-to-end encrypted"). **This task never auto-trusts a changed
  identity key**; it surfaces the failure, and E02's Devices screen remains
  where verification happens.

## 3. What this task does
- **`PreKeyBundleCodec`** — `serialize(PreKeyBundle)` / `deserialize(bytes)`
  over the fields X3DH needs: registration id, device id, prekey id +
  public key, signed-prekey id + public key + signature, identity key.
  Framing follows the same big-endian length-prefixed idiom as
  `MessageEnvelope` and `RelayPacketFrame` — one idiom in this codebase.
  Every field is a **public** key or a public id; assert in a test that no
  private key material is reachable from a serialized bundle.
- **The control sub-protocol**, carried as `PayloadType.control` frames
  (E06-T02's reserved tag) through `InboundPipeline`'s `ControlHandler`
  seam (E06-T05):
  - `bundleRequest` — "send me a bundle for a session with you"
  - `bundleResponse` — a serialized bundle
  - `bundleUnavailable` — an explicit refusal/exhaustion, so a requester
    fails fast rather than waiting on silence
- **`PrekeyExchange`** — the component:
  - `ensureSession(peerDeviceId)`: if a session exists, return; else check
    trust, send a `bundleRequest`, await a response with a bounded timeout,
    `establishSession`, return. Concurrent calls for the same peer
    **coalesce onto one in-flight request** — otherwise opening a chat and
    sending in the same second burns two one-time prekeys and races two
    `SessionBuilder`s.
  - handles inbound `bundleRequest`: trust check → `issueOneTimePreKey()` →
    `getLocalPreKeyBundle()` → `bundleResponse`. A blocked peer gets
    nothing (not a refusal — silence, so blocking is not probeable).
  - handles inbound `bundleResponse`: only for a request this device
    actually made, and only from the peer it was sent to. An unsolicited
    bundle is dropped and counted.
- **Wiring** in `messaging_stack.dart`: registered as a control handler,
  and `SendMessageUseCase`'s no-session failure path becomes recoverable —
  the caller (T11's chat controller) calls `ensureSession` first. **This
  task does not change `SendMessageUseCase`**; it makes the precondition
  satisfiable.

## 4. What this task does NOT do
- Does NOT auto-trust a changed identity key, and does NOT catch
  `UntrustedIdentityException` and continue. It propagates as a typed
  failure (E06-T02's taxonomy). Silently re-trusting is the single change
  that would make "End-to-end encrypted" a false statement.
- Does NOT implement a Firebase-hosted bundle directory **unless
  `OQ-E06-T07-1` resolves that way** — and that answer brings a new
  external-service surface, which is a 🧍 gate of its own.
- Does NOT implement one-time-prekey pool expiry or reclamation — see
  `OQ-E06-T07-2`.
- Does NOT implement safety numbers, a verification UI, or QR exchange.
  E02 owns trust surfaces; there is no design source for any of it.
- Does NOT modify `IdentityService`, `DriftSignalProtocolStore`,
  `CryptoService` or `SendMessageUseCase`.
- Does NOT retry forever. A bundle request that times out fails the send
  honestly; the message stays queued and the chat screen says so.
- Does NOT touch any UI file, route or binding.

```yaml
  returns: "{requestsSent, requestsServed, requestsRefused, responsesAccepted, responsesUnsolicited, timeouts}"
  purpose: "so a failed first message has a diagnosable reason"
```

## 6. Risks
- **One-time prekeys are consumed by requests, so this is a spendable
  resource an attacker can drain.** `countIssuableOneTimePreKeys()` exists;
  serving a bundle to every requester with no rate limit lets an
  unauthenticated peer exhaust the pool, after which sessions degrade to
  the signed prekey only (weaker forward secrecy) or fail. Serve only
  trust-permitted peers, and count refusals.
- **Coalescing is not an optimization here, it is correctness.** Two
  concurrent `ensureSession` calls burn two one-time prekeys and run two
  `SessionBuilder`s against one store — the same shared-mutable-state shape
  as L-backend-003 (five recurrences). Write the two-concurrent-call
  falsification test, per `implement` §6.
- The X3DH initiator/responder asymmetry: whoever sends first is the
  initiator, and the first message is a `PreKeySignalMessage` — which is
  exactly why E06-T02's type tag exists. Test the full loop *through* the
  frame, not just through `CryptoService`.
- Do not log a bundle, even though it is public. Bundles identify devices,
  and a log line with an identity key is a privacy fingerprint.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-COMM-14**: WHEN a user sends a first message to a permitted peer
  with no existing session, the system SHALL obtain that peer's prekey
  bundle and establish a session before encrypting. (FR-COMM-001,
  FR-MSG-001)
- **EARS-COMM-15**: IF the peer is blocked or trust does not permit it,
  THEN the system SHALL NOT serve a prekey bundle and SHALL NOT establish
  a session. (FR-TRUST-003, FR-TRUST-005)
- **EARS-COMM-16**: IF a peer's identity key has changed, THEN the system
  SHALL fail the session establishment and SHALL NOT silently trust the new
  key. (NFR-SEC-001)

## Open Questions
- **OQ-E06-T07-1 — 🧍 BLOCKING. Over what channel does a device obtain a
  peer's prekey bundle?** Nothing in `spec/` or any accepted ADR settles
  this, and the answer changes the product's offline story, its Firebase
  dependency, and its privacy surface.

  | Option | How it works | Trade-offs |
  |---|---|---|
  | **(a) Inline over the mesh, on first contact** | a `control` frame asks the peer directly; the peer answers with a freshly-issued bundle | Works with **no internet at all**, which is the product's premise (FR-MSG-006: "continue functioning without Firebase"). Consistent with ADR-0005 (identity is local; Firebase is a thin account pointer). But: **both devices must be reachable at the moment of first contact** — you cannot start a conversation with someone who is currently offline, which is a real user-visible limitation for an offline-first messenger. Also spends a one-time prekey per request, so it needs the trust gate and rate limiting §6 describes. |
  | **(b) Published to Firebase, fetched when online** | each device publishes its bundle under its account; a sender fetches the peer's | You can start a conversation with an offline peer, which is what users expect. But: it makes first contact **require internet**, contradicting the mesh premise for exactly the case the mesh exists for; it puts device public keys and the device→account mapping in a hosted database (a metadata/privacy surface the project has not yet accepted anywhere); and it expands ADR-0005's "thin account pointer" into a key directory, which is arguably a superseding-ADR-sized change. |
  | **(c) Both: (a) preferred, (b) as fallback** | try the mesh; fall back to Firebase when the peer is unreachable and the internet is up | The best user outcome and the honest engineering answer. But it is both mechanisms, both test surfaces, and both privacy stories — roughly double this task, and it drags E11's Firebase scope forward into E06. |

  - **Advisory recommendation: (a) for E06, with (c) planned as an E11
    task.** (a) is the only option that keeps the wedge epic self-contained,
    needs no new external-service surface or ADR amendment, and proves the
    mesh premise end to end — which is what this epic exists to prove. Its
    limitation (both devices must be present for first contact) is real and
    should be **stated in the UI and the release notes**, not hidden: a chat
    with a never-contacted, currently-offline peer fails with a clear reason
    rather than a spinner. E11 already owns Firebase synchronization and is
    the right place to add (b) as a fallback with its own privacy review.
  - Whichever is chosen, say explicitly whether **bundles may be cached**
    and for how long — a cached bundle whose one-time prekey was already
    consumed elsewhere fails at `establishSession` in a way that is very
    hard to diagnose later.
  - **Status:** 🟢 answered
  - **Answer:** **Option (a) — inline over the mesh, on first contact.**
    Keeps E06 self-contained, adds no new external-service surface or ADR
    amendment, and proves the mesh premise end to end. Option (c)'s
    Firebase fallback is explicitly deferred to E11 (which already owns
    Firebase synchronization) as its own task with its own privacy
    review, not built here. The real limitation — both devices must be
    reachable at the moment of first contact — must be surfaced honestly
    in the chat UI (a clear failure reason, not a spinner) when the
    intended recipient is unreachable, and stated plainly in release
    notes. Bundles are **not cached** across requests — each
    `ensureSession` call that needs one issues a fresh request; a cached
    bundle whose one-time prekey was already consumed elsewhere would
    fail unpredictably at `establishSession` later, which is worse than
    the extra round trip.
