# E06-T11 · Chat screen (text-only)

## 1. Goal
The screen the whole product exists for: type a message, watch it encrypt,
queue, route and arrive — and see the other person's arrive back.

## 2. Business logic
- **Rule 2.** `design/screens/chat.md` is law: 31 checklist elements, 23
  verbatim strings, measured tokens. `Ahmed`, the bubble texts and the
  timestamps are **data**; `End-to-end encrypted`, `Today`, `Secure
  message...`, `arrow_back`, `lock`, `more_vert`, `add`, `mic`, `check`,
  `done_all` are **copy and chrome** and are exact.
- **Sending** goes through the real stack, in this order:
  `PrekeyExchange.ensureSession(peer)` (T07) → `SendMessageUseCase.call`
  (E05-T02) → the message is persisted `queued` then `sent` → the
  coordinator's tick (T06) forwards it when a route exists. The screen never
  encrypts, frames or enqueues anything itself.
- **Receiving** is live from `ConversationRepository.watchConversation`
  (T09), which reflects what `InboundPipeline` (T05) persisted. Logical
  ordering is E05-T03's `sequence_number` (FR-MSG-004), **not** arrival
  order and **not** wall-clock — clock drift across devices is exactly what
  E05-T01 §2 warns about. The screen orders by what the read model gives it
  and does not re-sort.
- **Delivery ticks, mapped in GAP-009** — `Queued` →
  `radio_button_unchecked`, `Sent` → `check`, `Delivered` → grey
  `done_all`, `Read` → green `done_all`. Two constraints on this mapping,
  both inherited:
  - **E05-B03's human resolution:** `Sent` means *durably enqueued
    locally* — not "the radio sent it". So `check` appears with no route
    and no radio, and the UI must not imply otherwise. This is why
    `Queued`'s distinct glyph matters: it is the only honest signal that
    nothing has left the device.
  - **`OQ-E06-T11-2`** (inherited OQ-E05-T03-1): `Stored` has no agreed
    meaning, so it gets no distinct glyph and is rendered as `Delivered`
    until it does.
  - `Failed` has no design source at all — `OQ-E06-T11-1`.
- **Decryption for display only.** Plaintext lives in the controller's
  ephemeral state, is never written back, never logged, and never leaves
  the widget tree. NFR-SEC-001.
- **Approved gaps binding this screen:** GAP-008 (empty thread), GAP-009
  (delivery-state glyph mapping), GAP-010 (`add`/`mic` present but inert;
  the transfer-progress bubble is data-driven and simply absent). All three
  are 🟡 pending sign-off, and this task may not start until they are
  approved.

## 3. What this task does
- `/chat/:id` route + `ChatView` + `ChatController` + `ChatBinding`, same
  three-file GetX pattern.
- Header per the contract: back button, avatar, peer name, `lock` +
  `End-to-end encrypted`, `more_vert` (present, per the contract; its menu
  is not drawn, so it follows the GAP-004 precedent — present, tappable,
  explicitly not-yet-available).
- Message list: incoming and outgoing bubble treatments exactly as measured
  (elements 10-25), day dividers (`Today` pill), per-message timestamp, tick
  glyph per GAP-009, keyset scrollback via `messagesPage` on scroll.
- Composer: multiline `Secure message...` field, `add` (inert, GAP-010),
  `lock` glyph, `mic` on the accent fill (inert, GAP-010). Send is by the
  field's submit action, since the contract draws no send button — the
  `mic` button is a voice affordance, and repurposing it as Send would be
  inventing a control the design does not have.
- Send flow with honest failure states: no session
  (`messaging.no_session` / `bundle_unavailable` / `peer_blocked` /
  timeout from T07) each produces a specific, non-fatal message; the
  composed message is **not** silently dropped.
- `DeliveryAckService.markRead(messageId)` (T08) called for displayed
  incoming messages — a no-op while read receipts are disabled
  (`OQ-E06-T08-1`), wired now so enabling it later is one constant.
- Registers the screen in `test/design/design_probe_test.dart`.
- **Starts the messaging coordinator, once, app-wide (OQ-E06-T06-4).**
  `MessagingCoordinator.start()` has no caller anywhere in the running app —
  E06-T06 built it, correctly did not wire it (out of that task's own
  `files:` fence), and its independent reviewer flagged the obligation as
  unowned. This task adds exactly one call —
  `messagingStack.coordinator.start()` — at the point `bindings.dart`
  already permanently registers `MessagingStack` (T03's registration site).
  This is a lifecycle call, not new architecture: no new binding, no new
  singleton, no behavior change to anything `bindings.dart` already
  registers. Without it, EARS-MSG-1 stays true only in E06-T06's own tests,
  never in the app a user runs.

## 4. What this task does NOT do
- Does NOT implement voice messages, PTT, attachments, or location. The
  `add` and `mic` buttons render exactly as measured and are inert
  (GAP-010). **Do not implement "just the simple version" of any of them** —
  the epic's own §Risks mitigation is text-first, and E06-T13 produces the
  design contracts the rest need before anything is built against them
  (rule 2: no contract, not shardable).
- Does NOT render the file-transfer bubble (`troubleshoot` /
  `Backup: Family Photos` / `In progress... 78%`, elements 16-18) — it is
  data-driven content for a feature this task does not build. GAP-010
  records it; the gate will report it missing and that finding traces there.
- Does NOT invent a `Failed` glyph or a new error colour
  (`OQ-E06-T11-1`) — the first off-palette token in the app would be a hard
  gate finding and a real visual-language fork.
- Does NOT define what `Stored` means (`OQ-E06-T11-2`).
- Does NOT implement message editing, deletion, reactions, replies,
  forwarding, or a `more_vert` menu — none is drawn.
- Does NOT drive the messaging loop, call `processQueue()`, or subscribe to
  the transport. It reads the read model and calls the use case.
- Does NOT touch `lib/app/bindings.dart` beyond the single
  `coordinator.start()` call named in §3 (OQ-E06-T06-4) — no new
  registration, no reordering of existing `Get.put` calls, no other backend
  file.

## 6. Risks
- **This screen is where an honest UI matters most.** `Sent` does not mean
  sent (E05-B03), and with `OQ-E06-T06-1` resolved to a foreground-only
  trigger model, nothing forwards while the app is closed. A single `check`
  that a user reads as "delivered" is a product lie built from four correct
  components. Render `Queued` distinctly, and if the recommended
  foreground-only model is chosen, say so in the copy the human approves —
  do not paper over it.
- Decrypting a whole thread on open is the NFR-PERF-001 hot path. Decrypt
  the visible page, cache by message id, decrypt older pages lazily.
- The `mic` button is on the accent fill and looks exactly like a primary
  action. Making it inert will feel wrong — that is the correct outcome for
  text-first, it is recorded in GAP-010, and it must not be quietly turned
  into a Send button.
- `ensureSession` can block for seconds (a bundle round trip over a mesh).
  Do not block the composer. Show the message as `Queued` immediately and
  resolve the session in the background — the message row exists either way.
- Expect gate iteration, as in T10. Never loosen the threshold.

**Deviations from spec/design** (each with its spec/ADR reason):
- **Message ordering is `sequenceNumber` within the SAME sender, `createdAt`
  only to interleave the two different senders.** `sequence_number` is
  monotonic per `(conversationId, senderDeviceId)` (E05-T01's own schema,
  `message.dart`'s dartdoc) — it has no cross-party correlation, so a pure
  "sort by sequenceNumber" cannot totally order two different people's
  messages. `ChatController._orderForDisplay` compares by `sequenceNumber`
  when both rows share a sender (correcting exactly the out-of-order-arrival
  hazard `test_EARS_COMM_1_incoming_message_renders_in_sequence_order`
  falsifies) and by `createdAt` only across senders. This is an inherent
  property of E05-T01's per-sender counter, not a defect introduced here —
  flagged so it does not get silently assumed away by a later task.
- **`ChatController`'s constructor omits `selfDeviceId`** relative to the
  task's own §5 contract sketch, which lists no such parameter either —
  `ConversationRepository` (one of the contract's own required params)
  already exposes `selfDeviceId` as a public field, read via a private
  getter instead of adding a redundant constructor parameter the contract
  never asked for.
- **Design-fidelity gate is not green — traced findings, not fixed by

  `radio_button_unchecked` (the dashboard's queued glyph) so a failed
  message is visually "not sent" — honest, no new token, but conflates two

### Fix — review finding: composer showed nothing for up to 20s during first-contact `ensureSession`
First-pass review (commit `766107d`) returned CHANGES on exactly one
blocking finding: `ChatController.send()` awaited `_sessions.ensureSession`
(up to `prekey_exchange.dart`'s own 20s `_defaultEnsureSessionTimeout`)
BEFORE calling `SendMessageUseCase.call` — the only thing that ever
persisted a row and thus the only thing `_onMessages`' DB stream had
anything to render. Since `messages` was mutated ONLY from that stream, the
message list stayed empty for the entire `ensureSession` round trip on
exactly the first-contact scenario (EARS-COMM-23) that method exists for —
directly contradicting task file §6 Risks' explicit, twice-stated
instruction: *"Show the message as `Queued` immediately... the message row
exists either way."* Confirmed against the actual code before touching
anything (`chat_controller.dart`'s pre-fix `send()`, `ensureSession`'s real
20s default in `prekey_exchange.dart`) — the finding was accurate.

**Fix**, scoped to `lib/features/chat/presentation/chat_controller.dart`
only:
- `send()` now synthesizes a local `ChatBubble` (`Queued`, a synthetic
  `local-N` id, this device's own text) and inserts it into `messages`
  BEFORE `ensureSession` is even awaited — via a new `_pendingOptimistic`
  map and `_renderPending()` helper that merges pending entries with the
  last-known DB rows (`_lastRows`, now the single source `_onMessages`,
  `loadOlder` and `send` all render from, so none of the three can
  silently drop what another just added).
- On success, the optimistic entry is dropped and the just-returned real
  `Message` is folded into `_lastRows` directly (`_mergeLocalRow`) in the
  SAME synchronous step — no `await` between removing the synthetic bubble
  and having the real one available to render, so there is never a frame
  with zero bubbles and never a frame with two.
- On any failure (no session / bundle unavailable / peer blocked / timeout
  / untrusted-identity or other crypto failure) the optimistic entry is
  simply dropped (`_dropOptimistic`) and `sendError` is set exactly as
  before. Chosen over rendering it as `Failed` because no row was ever
  durably reserved for the cases `send()` can actually catch (a blocked
  peer is refused before `SendMessageUseCase.call` even runs) — and where
  `SendMessageUseCase.call` itself does leave a real `Failed` row behind
  (its own file header's documented encryption-failure case), that row
  arrives via the live stream on its own merit, not as a stale local
  duplicate. This also keeps `test_EARS_COMM_25_blocked_peer_shows_a_reason
  _and_keeps_the_text`'s pre-existing `expect(controller.messages,
  isEmpty)` assertion true, unchanged.
- No new delivery state, no new colour — `DeliveryState.queued` is the
  same state GAP-009 already mapped to `radio_button_unchecked`; `Failed`
  still renders exactly as GAP-009 resolved it (`error_outline` at the
  existing muted grey token) wherever a real `Failed` row is ever the
  live-stream state, which this fix does not touch.
- `loadOlder` was updated to fold its paged-in rows into `_lastRows` too
  (previously it merged directly into `messages`, which `_renderPending`
  would otherwise silently clobber on the next stream emission or send).
