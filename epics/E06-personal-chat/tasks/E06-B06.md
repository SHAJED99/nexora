# E06-B06 · ChatView composer dead to touch on Redmi 10 2022 (MIUI)

## 1. How this was found
Human report, live: "I can not send any message to the other device." Asked
a clarifying question (`AskUserQuestion`) — the human confirmed: **"Keyboard/
compose never opens."** Not a send-path failure, not a delivery failure — the
compose surface itself never activates.

Reproduced independently via ADB on the physical Redmi 10 2022 (`e4813f500601`,
MIUI, `21121119SG`/`selene_global`), inside a real chat opened against peer
`B8:DB:38:7C:D4:BF`:

- Tapped the message `TextField` at 6 different coordinates spanning its
  full visible bounds (both loosely and tightly targeted, cross-checked
  against the real screenshot resolution/scale). `dumpsys input_method`
  showed `mInputShown=false` after every single one — the keyboard never
  requested to open.
- Tapped the `+` icon (`_RoundIconButton`, left of the field) and the mic
  button (`_RoundIconButton`, right of the field) — both should fire
  `Get.snackbar('Not available', ...)` per `chat_view.dart`'s own GAP-010
  comment. Neither produced a visible snackbar, at 0.3s or 1s post-tap.
- Ruled out "wrong coordinates" / "ADB can't reach this device": the same
  session's tap on the header back-arrow (`_IconTapTarget`, `onTap: () =>
  Get.back<void>()`) worked immediately and navigated correctly, and
  `logcat`'s `MIUIInput` tag confirmed genuine down/up `MotionEvent`
  delivery to `com.nexora.nexora/MainActivity` for the mic-button tap
  specifically — the touch reaches the app's window; something after that
  point in the composer's specific row never resolves to a tap.
- Ruled out touch-exploration/accessibility interception:
  `touch_exploration_enabled` and `accessibility_enabled` are both `0` on
  this device.
- Ruled out an invisible overlay window stealing input:
  `dumpsys window windows` shows only the expected stack (status bar, nav
  bar, IME, `MainActivity`, launcher, wallpaper) — no unexpected window
  above `MainActivity`.

**Cross-checked on the Pixel 8 Pro (`192.168.0.108:9999`, stock Android)
with the identical build and the identical widget tree**: the same tap
sequence opened the keyboard on the first attempt (`mInputShown=true`),
accepted typed text (`adb shell input text`), and a real send completed
(local echo appended, queued-delivery icon shown). **This bug is
device/MIUI-specific, not a universal defect in this file** — but it fully
blocks sending on at least this one real test device, which is exactly the
UX the human hit.

## 2. What's already ruled out
- Not the previously-documented, separate MIUI/ADB `TextField`-focus quirk
  from `E04-B09`'s own on-device verification (a spurious `KEYCODE_BACK`
  firing on tap, navigating back to Devices) — this session's repro shows a
  **fully inert** tap: no keyboard, no snackbar, no navigation, nothing.
  Different symptom; may or may not share a root cause. Do not assume they
  are the same bug without checking.
- Not an app-wide input freeze — the header's own `InkWell` (back arrow)
  responded instantly in the same test window.
- Not a coordinate-mapping mistake in this investigation — six different
  coordinates across the full composer row, cross-validated against the
  header/mic controls at the same time, all behaved identically.
- Not the message-delivery path (Bluetooth/bonding) — this is upstream of
  that entirely; the compose surface never activates regardless of
  peer/bonding state.

## 2a. A related, separately-tracked finding from the same session
While diagnosing the delivery side (unrelated to this bug, filed against
`E04-B10`): the two physical test devices currently have **zero real OS-level
Bluetooth bond** between them (`Redmi: Bonded devices:` empty), and the
Redmi's own native Bluetooth Settings inquiry — independent of this app
entirely — found a nearby PC but never found the Pixel even at <30cm with
both devices actively discoverable. That is a Bluetooth/radio-layer issue,
wholly separate from this bug, and does not explain or excuse this bug: the
composer must be tappable regardless of any peer's bonding state, since
composing a message has no dependency on delivery succeeding.

## 3. Hypothesis (not yet root-caused — this is the task)
Not diagnosed to a specific line yet. `chat_view.dart`'s `_Composer` (§405-468)
is a plain `TextField` inside `Row`/`Container`/`Expanded`, no `GestureDetector`,
`Listener`, `IgnorePointer`, or `AbsorbPointer` anywhere in its ancestry or
siblings that would explain swallowing all three composer-row controls'
gestures identically. Candidate directions for the assigned agent to
investigate — **not a prescribed fix, verify from scratch**:
- A MIUI-specific `Scaffold`/`SafeArea` bottom-inset or IME-inset
  recalculation issue that shifts the composer's actual hit-testable region
  away from where it is painted, specifically on devices with MIUI's
  gesture/3-button nav quirks.
- A raw Flutter engine/gesture-arena interaction specific to this device's
  Android/MIUI version that this repo hasn't hit before in a bottom-docked
  `Row` of this shape.
- Something MIUI-version-specific in `AndroidManifest.xml`/theme config
  that alters touch dispatch for views anchored to the bottom inset.

## 3a. Root cause (this session's on-device investigation)
Full methodology and raw evidence live in the Run log below; summary here.

Live-instrumented the running Redmi (`e4813f500601`) both cold (`am start`,
matching the original human repro's launch path) and warm (`flutter run -d
e4813f500601` attached, for hot-reload iteration), adding temporary
diagnostic prints to `ChatView`/`_Composer` (removed before commit — never
shipped) that read `MediaQuery`/`PlatformDispatcher.views.first` and the
Composer's own `RenderBox` global position on every frame, cross-checked
against `dumpsys window windows`, `dumpsys input_method`, and `uiautomator
dump` (which — surprisingly, since `touch_exploration_enabled=0` — DOES
return real Flutter semantics/bounds during the dump itself; useful as an
independent second measurement of the composer's real screen position).

**The measured anomaly:** on this device, `MediaQuery.padding.bottom` (what
plain `SafeArea` consumes) is exactly `0` — the OS's own 3-button nav bar is
already excluded from the canvas Android hands to Flutter, so `SafeArea`
sees nothing further to guard against. That leaves the Composer's `+`/mic/
textfield controls sitting with their bottom edge **exactly flush** against
this device's reported canvas boundary — measured via `uiautomator dump`
pre-fix as bounds `[18,2168][126,2191]` (`+`, only 23 *physical* px tall —
its real design height is 48px), `[153,2159][873,2191]` (textfield, 32px),
`[954,2168][1062,2191]` (mic, 23px) — a sliver, not their true size, with
**zero cushion** from the device's absolute edge. This device's ROM also
confirms edge/gesture input-suppression machinery is present at all
(`horizontal_edge_suppression_size`/`vertical_edge_suppression_size` system
settings exist, even though currently `-1`/inactive for this 3-button-nav
configuration) — this ROM treats screen-edge-adjacent touches specially,
and the composer sits precisely in that zone with no margin at all.

**Honesty about what this session's ADB testing could and couldn't prove**
(this is the load-bearing caveat — read it before trusting the fix):
`adb shell input tap` at the *mathematically correct* composer coordinates
(derived from the live `RenderBox`/`MediaQuery` measurements above)
reliably **succeeded** on this device, both cold- and warm-launched —
`mInputShown` flipped `false`→`true`, `+`'s `onTap` fired, real text was
typed into the field. That means this session could **not** reproduce the
human's exact "fully inert tap" symptom via synthetic ADB taps at this
build/commit, on this device, right now. Two honest readings of that:
(a) a synthetic zero-area, zero-jitter `input tap` may simply not trigger
whatever edge/gesture-suppression path a real, larger-contact-area finger
touch does on this exact screen sliver — a known class of gap between
injected and physical touches on edge-suppression-capable ROMs; or (b) the
original repro's tap coordinates were themselves slightly off (this
session independently mis-tapped the very same composer by ~500px on its
own first attempt, purely from eyeballing a downscaled screenshot instead
of measuring — see Run log — which shows how easy that specific mistake is
to make blind). This session cannot fully distinguish (a) from (b) without
a real finger on the glass.

**The fix, chosen to be correct under EITHER reading:** `ChatView`'s
`SafeArea` now takes `minimum: EdgeInsets.only(bottom: 16)`, forcing a
16-logical-px (~36-physical-px on this device) floor under whatever
`SafeArea` would otherwise compute (zero, here) — moving every composer
control a fixed, real distance off the device's absolute bottom edge and
out of any edge-adjacent input handling, regardless of the exact mechanism.
Verified via `uiautomator dump` post-fix: the same three controls now
measure `[18,2132][126,2191]` (59px), `[153,2123][873,2191]` (68px),
`[954,2132][1062,2191]` (59px) — each roughly back to its true design
height, with real headroom instead of zero. This is a pure floor/minimum on
top of `SafeArea`'s own computation: on any device that already reports a
non-zero bottom inset (the Pixel 8 Pro, confirmed unaffected either way),
`minimum:` is a no-op — it only engages where the platform reports less
than 16px, which is exactly the gap this device had.

`OQ-E06-B06-2` (below) asks the reviewer/human to confirm with one real
finger tap on the physical unit, since that is the one thing this session's
tooling cannot simulate.

## 3b. Related, disclosed finding (not this task's to fix)
Flutter's own internal metrics (`PlatformDispatcher.views.first.physicalSize`
= `1080×2294`, matching `dumpsys window`'s `MainActivity` app-bounds
`Rect(0,103 - 1080,2294)`) disagree with what `uiautomator dump`'s
accessibility bridge reports as the app's root content bounds
(`[0,0][1080,2191]`, i.e. 103px — exactly this device's status-bar height —
short of Flutter's own number), on this device specifically, at every
measurement taken in this session, before and after the fix. Functional
testing (real taps at physical y up to 2294, beyond the 2191 the
accessibility bridge implies) shows the true touchable region matches
Flutter's own number (2294), not the accessibility bridge's, so this reads
as a MIUI accessibility-bridge/`uiautomator` reporting quirk rather than a
real second window boundary — but it's a genuine, reproducible, unexplained
discrepancy on this ROM worth a future investigator knowing about before
they trust `uiautomator dump` bounds at face value on this device. Not
actioned here — out of this task's scope (`chat_view.dart` only) and not
demonstrated to affect real touch delivery.

## On-device verification (rule 7 evidence)
Device: Redmi 10 2022, `21121119SG`/`selene_global`, serial `e4813f500601`,
MIUI, 3-button nav, 1080×2400 physical, devicePixelRatio 2.25.

**Composer hit-region measurement, `uiautomator dump` (physical px), same
conversation (`B8:DB:38:7C:D4:BF`), same three composer controls:**

| control | before (this commit's parent) | after (this commit) |
|---|---|---|
| `+` button | `[18,2168][126,2191]` — 23px tall (design: 48px) | `[18,2132][126,2191]` — 59px tall |
| message `TextField` | `[153,2159][873,2191]` — 32px tall | `[153,2123][873,2191]` — 68px tall |
| mic button | `[954,2168][1062,2191]` — 23px tall (design: 48px) | `[954,2132][1062,2191]` — 59px tall |

Every control's *top* edge moved ~34-36 physical px further from the
device's absolute bottom edge post-fix (matches the intended 16-logical-px
`minimum:` × 2.25 devicePixelRatio ≈ 36 physical px), with no visual
regression (screenshots taken before/after — composer still renders
correctly-positioned, correctly-styled, immediately above the OS nav bar).

**Functional test, post-fix, on the physical unit:**
- `dumpsys input_method` before tapping the message field: `mInputShown=false`.
- `adb shell input tap` at the field's measured center →
  `mInputShown=true`, `mServedView=...FlutterView...` (keyboard genuinely
  requested and shown).
- `adb shell input text "hello_from_redmi"` → text appeared in the field
  (screenshot captured).
- `+` button tap → its `onTap` fired (verified via temporary instrumentation
  during the investigation phase, before it was reverted for commit).

**What this does NOT claim**: this session's synthetic ADB taps also
succeeded at the *pre-fix* build, at the mathematically correct
coordinates (see §3a) — meaning the before/after table above demonstrates
a real, measured geometry change (controls moved off the edge), not a
before-fails/after-succeeds ADB-tap contrast. `OQ-E06-B06-2` asks the
reviewer/human to close that gap with one real finger tap, which this
