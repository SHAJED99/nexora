# E06-T04 · Link-quality wiring

## 1. Goal
Make `RoutingEngine.computeRoute()` return a route on a real device, by
feeding it the measurements the Pigeon contract has declared and nobody has
ever produced.

## 2. Business logic
- **This obligation has now been dropped twice, and this task is the third
  attempt.** E04-B03 extended the Pigeon contract on the human's explicit
  decision (option 2, 2026-08-27): `int? rssi` on `TransportDevice`
  (`pigeons/transport.dart:45,57`) and
  `void onLinkQuality(String deviceId, int latencyMs, double lossRate)` on
  `TransportEventsApi` (`:102`), **deliberately left unfed**, with E05 named
  as the wiring owner. E05 never mentioned it. E05's own retro found it
  again and escalated: *"🔴 E04-B03's link-quality wiring is still unwired
  and now twice-dropped … This must enter E06's sharding as a named
  dependency, not a retro line."* It is that named dependency.
- **The consequence is total, not marginal.** `RoutingEngine._knownLinks` is
  populated exclusively by `recordLinkMeasurement(neighborId, {latencyMs,
  lossRate, batteryDrain})` (`routing_engine.dart:151`). With no producer,
  `computeRoute()` returns `null` for **every** destination on a real device
  — so `RelayEngine.processQueue()` has no next hop, so nothing this epic
  builds ever leaves the phone. Every other E06 task is downstream of this
  one being true.
- **FR-ROUTE-007** names the cost inputs (battery, latency, reliability,
  bandwidth, hops, congestion, stability, loss). E04-T02 already implements
  the formula; this task's job is only to supply real values for the three
  the transport can actually observe, and to be explicit about the ones it
  cannot.
- **FR-UI-004** depends on this too: the Dashboard's `Latency` / `24ms` row
  (`design/screens/dashboard.md` elements 12-14) has no honest value
  without it — see GAP-013.
- **E04-B03 §3's standing prohibition still binds: do not synthesize.** *"Do
  not synthesize fake measurements to make the engine appear live … That
  would produce a routing engine that computes confident routes from
  invented data — strictly worse than one that honestly returns `null`."*
  A measured value or no value. Never a default.

## 3. What this task does
- **Kotlin — emit what the radio actually knows.** In `BluetoothTransport.kt`:
  - populate `TransportDevice.rssi` from the scan result's RSSI at discovery
    (the value is already in the Android scan callback and is currently
    dropped on the floor);
  - call `TransportEventsApi.onLinkQuality(deviceId, latencyMs, lossRate)`
    from the existing send/receive path, where `latencyMs` is a real
    round-trip observation and `lossRate` is a real ratio over a bounded
    window of send attempts. `LoopbackTransport.kt` emits deterministic
    values so the loopback path stays testable end to end.
  - **If a value cannot be measured on a given path, emit nothing for it.**
    Do not emit a placeholder; do not emit `0`.
- **`TransportService.onLinkQuality` stops being a no-op.**
  `transport_service.dart:188` is currently `void onLinkQuality(String
  deviceId, int latencyMs, double lossRate) {}` with a comment saying the
  consumer is E05's job. Replace the body with a broadcast into a new
  `Stream<LinkQuality> get linkQuality`, and **delete the stale comment**
  (`:178-187`) rather than leaving a second false "someone else does this"
  comment in the codebase — that comment shape is the documented root cause
  of E05-B01 and of `sync_cursor_service.dart:113-114`.
- **`LinkQuality`** — a small value type `{deviceId, latencyMs, lossRate,
  rssi?, observedAt}`. `rssi` is folded in from the most recent
  `TransportDevice` for that id, and is nullable because the contract
  declares it nullable and a device may genuinely have none.
- **`LinkQualityFeed`** — the subscription that closes the loop:
  `TransportService.linkQuality` → `RoutingEngine.recordLinkMeasurement`.
  It owns the one translation decision this task must make and must
  document in code: `batteryDrain` is **not observable from the transport**,
  so the feed passes the engine's documented neutral input for it and says
  so in a comment naming this task — see `OQ-E06-T04-1`.
- **Registration** in `lib/app/bindings.dart`: the feed is constructed from
  the already-registered `MessagingStack`'s `transport` and `routingEngine`
  and started once, `permanent: true`.

## 4. What this task does NOT do
- Does NOT change `pigeons/transport.dart` or regenerate the Pigeon
  bindings. The contract was settled by E04-B03 at a 🧍 human gate and is an
  ADR-0004 boundary — changing it here would re-open a decision the human
  already made. If the existing contract genuinely cannot carry a needed
  value, that is an Open Question, not an edit.
- Does NOT touch `RoutingEngine`. `recordLinkMeasurement` already exists and
  is tested; this task supplies its input. Adding a parameter to it would
  be an out-of-fence edit to a merged epic.
- Does NOT change the cost formula, the migration threshold
  (`kMigrationImprovementThreshold`), or `RouteCostCalculator`.
- Does NOT drive `processQueue()` (T06) or render latency anywhere (T12).
- Does NOT invent a battery-drain measurement, and does NOT read the Android
  battery API to manufacture one. That is real scope with real permissions
  implications — see `OQ-E06-T04-1`.
- Does NOT smooth, average or debounce measurements beyond the bounded
  window §3 names. An EWMA is tempting and is a routing-behaviour change;
  E04-T02 owns routing behaviour.

## 5. Contract

### Functions
```yaml
- signature: "TransportService.linkQuality -> Stream<LinkQuality>"
  returns: "broadcast stream, one event per native onLinkQuality callback, rssi folded in when known"
  purpose: "the producer side of E04-B03's declared-but-unfed contract"

- signature: "LinkQualityFeed({required TransportService transport, required RoutingEngine routing})"
  purpose: "the subscription E04-B03 named and E05 never wrote"

- signature: "LinkQualityFeed.start() -> void"
  purpose: "subscribe; idempotent — calling twice must not double-record"

- signature: "LinkQualityFeed.stop() -> Future<void>"
  purpose: "cancel the subscription; required so tests do not leak between cases"
```

Kotlin side (no new Pigeon symbols — these already exist and are generated):
`TransportEventsApi.onLinkQuality(deviceId, latencyMs, lossRate)` invoked
from the transport's send/ack path; `TransportDevice(..., rssi = <scan
result RSSI>)` at discovery.

### External services & flags
No new dependency, no new Android permission. **If emitting RSSI or a
round-trip measurement turns out to need a permission the app does not
already hold, stop — that is a 🧍 human gate (rule 3), not a manifest edit.**

## 6. Risks
- **This is Bluetooth code with no hardware in CI.** E04's retro records
  three independent MIUI install-restriction confirmations and an emulator
  with no Bluetooth radio; T03b/T03c's own files state plainly that no
  meaningful hardware-free test exists for real socket I/O. So: put every
  decision that *can* be tested on the Dart side (the feed, the stream, the
  translation) and keep the Kotlin change as thin as it can be. Prove the
  Dart half exhaustively; be explicit in §Run log about exactly which lines
  rest on review and reasoning alone. See `OQ-E06-T04-2`.
- `LinkQualityFeed` writes into `RoutingEngine`'s shared link map, which
  `RelayEngine` and (later) the Dashboard also read. This is precisely the
  shape of L-backend-003 (five recurrences, most recently E04-B01, where
  `setActiveRoute` meant two different things to two callers). Before
  writing a line: list every current reader of `_knownLinks` and confirm
  each one means the same thing by a measurement arriving. Record that audit
  in §Run log — an unwritten audit is an unperformed one.
- Loopback and Bluetooth must not diverge in units. `latencyMs` is
  milliseconds, `lossRate` is a 0.0-1.0 ratio (not a percentage) — assert
  the bounds in the Dart feed and reject out-of-range values loudly rather
  than passing nonsense into the cost formula.
- The stream must be broadcast and must survive having no listener before
  `LinkQualityFeed.start()` runs, or the first measurements after launch are
  silently lost.

## Open Questions
- **OQ-E06-T04-1 — `batteryDrain` has no producer and this task will not
  invent one.** `recordLinkMeasurement` requires `batteryDrain`
  (`routing_engine.dart:151`) and FR-ROUTE-007 lists battery as a cost
  factor with the explicit constraint that it "shall never be the sole
  routing criterion". Nothing in the transport observes it. Options:
  (a) pass a documented neutral constant so battery contributes equally for
  every neighbour and the *other* factors decide — no behaviour is faked,
  the formula degrades to a battery-blind ranking; (b) read the local
  device's battery level via a new plugin and attribute it to every link —
  wrong on its face (it measures *this* device, not the link), plus a new
  dependency; (c) exchange battery level in the frame header so each peer
  reports its own — real, correct, and a protocol change touching
  E06-T02's frame and every relay. **Advisory recommendation: (a) now,
  (c) if and when battery-aware routing is actually exercised** — and (c)
  should then be its own task in the epic that needs it, not a smuggled
  addition here. Not blocking: (a) is implementable today and this task's
  test asserts the constant is named so (c) changes one line.
  - **Status:** 🟢 resolved
  - **Answer:** Option (a) — pass a documented neutral constant for
    `batteryDrain` so it contributes equally for every neighbour and the
    other measured factors (latency, loss, rssi) decide the ranking; no
    behaviour is faked. Name the constant (e.g.
    `kUnmeasuredBatteryDrainNeutral`) and reference it from
    `test_no_default_battery_drain_is_invented` per this task's own test
    plan. Option (c) — real per-peer battery reporting in the frame header —
    is deferred to whichever future epic first exercises battery-aware
    routing; it must land as its own task, not be smuggled into this one.
  - **Answered by:** orchestrator, applying the task file's own advisory
