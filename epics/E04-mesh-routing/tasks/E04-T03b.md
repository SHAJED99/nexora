# E04-T03b · Real Bluetooth Classic discovery + connect

## 1. Goal
Replace T03a's loopback discovery/connect with real Android Bluetooth
Classic (`BluetoothAdapter`/`BluetoothDevice`) — nearby devices actually
appear, and connecting establishes a real `BluetoothSocket` — proven on the
physical Wi-Fi/Bluetooth-capable device, since this cannot be meaningfully
unit-tested without real hardware.

## 2. Business logic
- FR-DISC-001/002: discover nearby devices via Bluetooth; surface them
  through the same `TransportEventsApi.onDeviceDiscovered`/`onDeviceLost`
  contract T03a already defined — this task only changes what's behind it,
  not the Dart-facing shape.
- FR-PLAT-002: Android 12+ requires `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT`
  runtime permissions (not just manifest declarations) — the app must
  request them before starting discovery and handle denial gracefully
  (surface an error, don't crash, don't silently no-op forever).

## 3. What this task does
- `BluetoothPermissions.kt`: checks/requests `BLUETOOTH_SCAN` and
  `BLUETOOTH_CONNECT` (API 31+) or legacy `BLUETOOTH`/`BLUETOOTH_ADMIN`/
  `ACCESS_FINE_LOCATION` (API <31, Bluetooth discovery historically needs
  location permission) depending on `Build.VERSION.SDK_INT`.
- `BluetoothTransport.kt` implements the Pigeon host's `startDiscovery`/
  `stopDiscovery`/`connect`/`disconnect` using `BluetoothAdapter.startDiscovery()`
  + a `BroadcastReceiver` for `ACTION_FOUND`/`ACTION_DISCOVERY_FINISHED`,
  and `BluetoothDevice.createRfcommSocketToServiceRecord()` for connect
  (a fixed, app-defined UUID for the RFCOMM service — document the UUID
  choice in the Run log).
- `TransportApiHost.kt` (from T03a) now delegates to `BluetoothTransport`
  instead of `LoopbackTransport` for these four methods — `send`/receive
  (still loopback-shaped for now) stay on the existing path until T03c.
- `AndroidManifest.xml`: add the Bluetooth permissions above.

## 4. What this task does NOT do
- Does NOT implement real data send/receive over the connected
  `BluetoothSocket` — `send()` still routes through T03a's loopback for
  this task; only discovery and connection-establishment become real.
  T03c wires the socket's actual I/O streams.
- Does NOT implement Bluetooth LE (BLE) — Classic only for v1, per the
  epic's own "Bluetooth-only first" mitigation; BLE is a later-wave
  decision if needed, not built here speculatively.
- Does NOT implement pairing-dialog UX beyond what `createRfcommSocketToServiceRecord`
  triggers by default (Android's system pairing dialog) — no custom
  pairing screen.
- Does NOT change the Devices screen — that's T05, which consumes whatever
  `TransportService.discoveredDevices` now emits.
- Does NOT implement Wi-Fi Direct or Internet-assisted discovery.

## 5. Contract

### Functions
```yaml
- signature: "BluetoothTransport.startDiscovery() -> Unit"
  purpose: "Requests permissions if needed, then BluetoothAdapter.startDiscovery(); emits onDeviceDiscovered per ACTION_FOUND, filtered to a stable de-dup window (don't re-emit the same device every scan cycle)"

- signature: "BluetoothTransport.connect(deviceId: String) -> Boolean"
  params: { deviceId: "the Bluetooth MAC address used as the device id" }
  returns: "true if the RFCOMM socket connected; emits onConnectionStateChanged either way"
  purpose: "Establishes a real BluetoothSocket, run on a background thread (never the main thread — connect() blocks)"

- signature: "BluetoothTransport.disconnect(deviceId: String) -> Unit"
  purpose: "Closes the socket for deviceId if one is open"
```

## 6. Risks
- `BluetoothSocket.connect()` is a **blocking** call — must run off the
  main thread (a dedicated executor/coroutine), or the app hangs/ANRs.
  This is the single most common Bluetooth-on-Android mistake.
- Permission denial must produce a clear, catchable failure through the
  existing Pigeon error path (or an explicit `onConnectionStateChanged(...,
  failed)`), not a silent no-op — a caller with no discovered devices and
  no error has no way to know whether nothing is nearby or permissions
  were denied.
- This cannot be verified by `flutter test` — Bluetooth requires two real
  radios. The manual step is not optional decoration here; it's the actual
  proof this task works. If only one Bluetooth-capable device is available
  this session, note in the Run log exactly what was and wasn't provable
  (e.g. "discovery started without crashing, no peer device available to
  confirm ACTION_FOUND fires for a real neighbor") rather than claiming a
  full round trip that wasn't actually observed.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-DISC-1**: WHEN Bluetooth discovery starts, the system SHALL
  request the required runtime permissions if not already granted.
  (FR-PLAT-002)
- **EARS-DISC-2**: A discovered nearby Bluetooth device SHALL be surfaced
  via `onDeviceDiscovered`. (FR-DISC-001)

### Tests
No meaningful unit test exists for real `BluetoothAdapter` behavior without
hardware mocking that would prove nothing real — do not fabricate a
Robolectric/mock test that passes regardless of correctness. Coverage here
is the manual verification below; say so explicitly rather than padding
with a hollow test.

### Manual
1. Install on the Wi-Fi device. Trigger discovery. Confirm the permission
   prompt appears (fresh install) and discovery proceeds after granting.
2. If a second Bluetooth device is available: confirm it appears via
   `onDeviceDiscovered` within a reasonable scan window, and `connect()`
   against it succeeds (socket opens, `onConnectionStateChanged(connected)`
   fires).
3. If no second device is available: note this explicitly, confirm at
   minimum that discovery starts without crashing/hanging and permission
   handling works — this is a real, disclosed test-coverage gap, not a
   pass.
