# E04-B39 · The idle-link check for E04-B36 has never been run

## 1. Why this exists, stated plainly
E04-B36 shipped adapter-off teardown, proven on hardware (EARS-TRANSPORT-8,
teardown at T₀+262 ms) and approved. Its §8 check 3 — *idle link for 3 minutes,
no false teardown, a message afterwards still arrives* — was **never executed
on any build**, across three live sessions:
- 2026-09-16 10:33: the session ended before check 3.
- 2026-09-18 01:49: after the stimulus the link did not re-establish
  (`k36-t4` sent 01:52:21, both phones still `links=0 openSockets=0` at
  01:52:46), so there was no link to idle.
- 2026-09-18 05:59: the stimulus consumed the link, and by then the
  `NexoraKA` logging had been stripped.

It is split here rather than left as an open box inside a merged task, the same
way §8 check 2 went to E04-B38 — an obligation with no named owner is one that
gets dropped (`L-process-007`/`-017`).

## 2. The risk this leaves open — the reason this is P2, not P3
Check 3 is not a formality. It is the check that guards against **E04-B36's own
mechanism misfiring**: tearing down a link that is alive but quiet.

The argument that it is safe is *reasoning, not evidence*:
- E04-B35's watchdog fires when `state.armed && silentMs > deadlineMs`.
- Keepalives are written every `KEEPALIVE_INTERVAL_MS` (10 s), and a
  keepalive-capable peer's `silent` therefore never approached the 30 s
  deadline in any observed run (max seen: 19,965 ms).
- So an idle link between two keepalive-capable peers should never trip it.

**That reasoning has not been tested against three minutes of real idling.**
This bug family has already punished exactly this pattern twice — E04-B35's
design and E04-B36's first root cause were both stated ahead of evidence and
both were wrong (see E04-B36 §6, which forbids ticking anything without a
quoted log line). The honest position is: *probably fine, unverified.*

## 3. What this task does
1. Restores diagnostic visibility for the run. The `NexoraKA` logging was
   stripped from `BluetoothTransport.kt` at E04-B36's merge, so an idle check
   on the shipped build can only be evidenced from the UI. Either re-add
   temporary logging for the run (and strip it again), or accept weaker
   evidence and say so.
2. Opens a link, idles it for **at least 3 minutes**, and records whether
   either side tears it down.
3. Sends a message afterwards and records whether it arrives.
4. If a false teardown occurs, files the fix against `keepaliveTick()`'s
   deadline logic — that would be a real S2 defect in shipped code.

## 4. What this task does NOT do
- Does not change the teardown mechanism unless step 2 shows it misfiring.
- Does not re-run adapter-off (E04-B36 check 1, already passed) or
  out-of-range (E04-B38 owns it).

## 5. Practical preconditions (learned the hard way, 2026-09-18)
- A reinstall signs both apps out and re-triggers `E01-B01`'s identity latch
  (force-stop + relaunch clears it). Budget for it.
- The Google account picker offers two of the owner's accounts — **the human
  chooses; the agent must not pick.**
- The Devices screen has **no connect affordance**: `TransportService.connect()`'s
  only production caller is `ConnectionEnsuringSender`, so a link opens when a
  message is SENT. Verify the peer first (its row must read *Allowed*), then
  use the row's message icon.
- Per `L-process-018`: clear buffers and start a raw per-device
  `logcat -v time > <file>` BEFORE the stimulus; keep the files; quote from them.

## 6. Acceptance criteria
- **EARS-TRANSPORT-11**: WHILE a link is open and idle, the system SHALL NOT
  tear it down, and a message sent after the idle period SHALL still be
  delivered. (FR-ROUTE-009)

## 7. Definition of Done
- [ ] Idle check run for ≥3 minutes, result recorded pass or fail with evidence
- [ ] Post-idle message send recorded
- [ ] If a false teardown is found: fix implemented, tested, reviewed by a
      different model than `executed_by` (rule 5)
- [ ] E04-B36's §8 check 3 line updated to point at this task's result
