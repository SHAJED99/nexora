# E04-B02 · Forwarded relay packets are retained forever

## What this bug is NOT
The T04 reviewer flagged `forwarding` as a possible "dead-end terminal
state" where a packet is stuck forever if the next hop silently fails. The
sweep investigated that specific concern and **it is not a defect.** Read
against `relay_engine.dart:190-196`, once `_send` succeeds this device has
genuinely completed its one physical hop, and the next hop is a different
device running its own `RelayEngine`. Retrying from here without an ack or
dedup mechanism would risk duplicate delivery, and ack/dedup is explicitly
E05's job per `E04-T04.md` §4. The code's own reasoning at
`relay_engine.dart:41-43` is correct and the state machine is right.

## The actual defect: nothing ever reclaims those rows
`sweepExpired()` (`relay_engine.dart:212-224`) filters on
`deliveryState.equals(RelayDeliveryState.queued.name)`. Nothing in
`RelayEngine` — or anywhere in the repo — ever deletes a `relay_packets`
row, in any state. So every packet this device ever relays leaves a
permanent row **including its full `payload` BLOB**: another peer's
encrypted message bytes, held on this device forever.

`epic.md:39-42` (§Data model) states the relay store is *"local only,
**ephemeral**"*. As merged, it is local only and permanent. No task owned
retention: T04's §3 says rows are "kept as a row for diagnostics per a later
epic's needs (E13)" — a reasonable decision about *state*, silently extended
into an unbounded-retention policy about *payloads*.

Two consequences:
1. **Storage growth (unbounded).** A device that relays for a busy mesh
   accumulates one full message payload per relayed packet, forever, with no
   cap, no eviction, and no user-visible way to reclaim it.
2. **Data retention (NFR-SEC-001).** A relay hop is a party that was
   supposed to hold someone else's ciphertext *temporarily*. Indefinite
   retention of third-party ciphertext at rest widens the blast radius of a
   device compromise well beyond what the epic's own data model promises.
   This is not a confidentiality break — FR-ROUTE-003 / EARS-ROUTE-3 holds,
   the payload is never decrypted or inspected — it is a retention-window
   defect.

## Severity: S3 (broken, but there is a workaround)
Nothing malfunctions today, and a later epic *can* add cleanup, which is the
workaround — so this is not S2. It is not S4 because it is neither cosmetic
nor minor: it is unbounded on-device storage growth plus indefinite
third-party-ciphertext retention, in direct contradiction of a written
data-model guarantee. Cheap to fix now; progressively more awkward once E05
is generating real relay volume against a schema whose retention semantics
nobody has decided.

Severity per `skills/bug-sweep` is the reviewer's call. **Priority is the
human's** (`bug_priorities` gate, rule 3) — left `TBD-human`.

## Repro (exact, from a fresh state — reviewer-verified 2026-08-27)
Verified with a throwaway probe test on `epic_04` at commit `cbc2efd`.

1. `RoutingEngine(selfId: 'A')` with links A→B and B→D recorded, so the
   route to D is 2 hops (`hops.length == 2`) and the forward is therefore
   marked `forwarding`, not `delivered`.
2. `RelayEngine(selfId: 'A', db: <in-memory>, routingEngine: <that engine>,
   send: (hop, bytes) async => true, clock: () => now)` with an injectable
   `now`, starting at `2026-01-01`.
3. `await enqueue('D', <3 bytes>, 0, Duration(minutes: 1))`
4. `await processQueue()` → the row's `delivery_state` is `forwarding`. ✅
   correct so far.
5. Advance the injected clock by **365 days** — far past the 1-minute TTL —
   and `await sweepExpired()`.

**Expected** (FR-ROUTE-004's expiry semantics; `epic.md`'s "ephemeral"):
a packet past `expires_at` is no longer retained in a form that holds its
payload. At minimum the TTL applies to the payload regardless of which
non-`queued` state the row reached.

**Actual:** probe output —
`swept=0 state=forwarding payload_still_present=3 bytes`.
The sweep returns 0, the state is unchanged, and the payload BLOB is still
there a year after a one-minute TTL expired. The same holds for `delivered`
and for rows already marked `expired`.

## Root cause
`relay_engine.dart:212-218` — `sweepExpired()`'s `where` clause is scoped to
`queued` only:
```dart
..where((t) =>
    t.deliveryState.equals(RelayDeliveryState.queued.name) &
    t.expiresAt.isSmallerOrEqualValue(now))
```
That scoping is correct for its stated job (take expired packets *out of the
active queue*). The gap is that no second mechanism exists for the other
half of the lifecycle: reclaiming storage from rows that have left the queue
by any route — `forwarding`, `delivered`, or `expired`.

## Proposed fix direction (builder to confirm; do not treat as prescriptive)
The diagnostics need (T04 §3 / E13) and the retention need are separable —
E13 wants to know *that* a packet passed through, not *what was in it*.

- Add a payload-reclaiming pass, e.g.
  `RelayEngine.reclaimPayloads({Duration retainFor})`, that nulls or empties
  the `payload` BLOB for any row past `expires_at` in a terminal state
  (`forwarding` / `delivered` / `expired`) while leaving the id,
  destination, size, timestamps and state intact for diagnostics. This
  requires making `payload` nullable — a schema change (v9→v10) and
  therefore additive-migration work with a prior-version test, per
  `docs/conventions.md` "Schema migrations" and the pattern now in
  `test/core/persistence/routing_migration_test.dart`.
- Alternatively, if the human decides diagnostics do not justify keeping
  terminal rows at all, delete them outright past a retention window — a
  smaller change with no schema impact. **This is a data-retention policy
  choice, so it is the human's call (rule 3), not the builder's.** Present
  both options and stop, rather than picking one.
- Either way, write the chosen retention window down in `epic.md`'s §Data
  model so "ephemeral" becomes a number instead of an adjective.

**🧍 Resolved, 2026-08-27:** reclaim (null the `payload` BLOB), not delete
— keep the row (id/destination/size/timestamps/state) for E13 diagnostics.
**Retention window: reclaim as soon as a terminal-state row (`forwarding` /
`delivered` / `expired`) passes its own `expires_at`** — no additional
grace period beyond the TTL the packet was originally enqueued with, since
that TTL is already the caller's stated "how long is this worth keeping"
signal. `epic.md`'s §Data model must record this exact rule as the
"ephemeral" definition. Requires the nullable-`payload` schema change
(v9→v10, additive) per the proposal above.
