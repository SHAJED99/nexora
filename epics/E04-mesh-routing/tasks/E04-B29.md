# E04-B29 · Back off automatic re-pairing after a failed pairing

## 1. Mechanism

`BluetoothTransport` keeps an in-memory, per-address backoff:

- **Recording a failure.** A failed or rejected bond records a failure. That means `BOND_NONE` while waiting on that address, or `createBond()` refusing to start. The next attempt is allowed only after 2 minutes, doubling per consecutive failure up to 30 minutes.
- **While backed off.** `connect()` for a not-yet-bonded address inside its backoff window emits `FAILED` and returns immediately, without calling `createBond()`. That is the same outcome as any other unreachable connect, so the packet simply stays queued.
- **Reset.** A successful bond (`BOND_BONDED`) clears the backoff for that address.

## What this task does NOT do

- Does not change connecting to an already-bonded peer; the backoff applies only to the pairing path.
- Does not change `RelayEngine`, `ConnectionEnsuringSender` or the relay tick interval.
- Does not distinguish a relay retry from a deliberate user tap. Both call the same `connect()`, so a user who re-taps a contact right after rejecting its pairing prompt also waits out the backoff (OQ-E04-B29-1).
- Does not persist the backoff; an app restart resets it.
- Does not add a Kotlin test harness (none exists in this project).

## 2. Definition of Done

- [x] A failed or rejected pairing records an exponential per-address backoff; a successful bond resets it
- [x] `connect()` to an unbonded address inside its backoff fails fast without calling `createBond()`
- [x] `flutter build apk --debug` compiles clean (commit `54d17eb`, branched from development `9d37dfc`, which includes E04-T07 and E04-B28)
- [x] Live: after a rejected pairing, no new pairing prompt appears on the next relay ticks; one appears again after the backoff (2026-09-15 22:15–22:23, doubling also observed; see run log)
- [x] Independent review (claude-sonnet-5, APPROVE WITH NITS, PR #268)

## Open Questions

- OQ-E04-B29-1: an explicit user action (for example tapping Connect on the Devices screen) is throttled the same as a relay retry. Telling them apart needs a `connect` API change (a "user-initiated" flag through Pigeon), which is outside this task's fence.

- OQ-E04-B29-2 (review nit, accepted): the backoff entry is cleared only by a `BOND_BONDED` this app was waiting on. A bond made outside the app (OS Settings) bypasses the backoff correctly, since `isBonded` is checked first, but does not clear the stale entry. If that peer is later unpaired and fails again inside the old window, it inherits the longer backoff instead of restarting at 2 min.
