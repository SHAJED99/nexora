# E04-B04 · Bluetooth discovery's own broadcast receiver is registered with the wrong export flag

## The defect

`BluetoothTransport.registerReceiverIfNeeded()`
(`android/app/src/main/kotlin/com/nexora/nexora/transport/BluetoothTransport.kt:429-449`)
registers a `BroadcastReceiver` for `BluetoothDevice.ACTION_FOUND` with
`ContextCompat.RECEIVER_NOT_EXPORTED`, reasoning in its own code comment
that "ACTION_FOUND is a protected system broadcast, so RECEIVER_NOT_EXPORTED
(no other app can spoof it) is correct and still delivers the real system
broadcast."

That reasoning is wrong. `ACTION_FOUND` is sent by `com.android.bluetooth`
(the OS Bluetooth stack process, its own separate app/uid) as an explicit,
package-targeted `Intent` addressed directly to the discovering app
(`pkg=com.nexora.nexora`) — not as a same-app broadcast, and not as an
untargeted system-wide broadcast either. `RECEIVER_NOT_EXPORTED` means
"only deliver broadcasts sent by processes running as this app's own uid" —
the exact opposite of what's needed for a genuinely cross-process,
different-uid system broadcast like this one. Android's own broadcast
dispatcher silently drops the intent rather than delivering it or raising
any exception the app could catch.

## Repro (confirmed on two real devices)

1. Build and run on a real Android device (`flutter run -d <device>`),
   navigate to the Devices screen, tap **Discover**.
2. Watch `adb logcat` filtered for `BroadcastQueue` while a second nearby
   Bluetooth-enabled device is also actively discoverable/scanning.
3. Confirm via `adb logcat` that native discovery genuinely finds the
   other device (`BluetoothRemoteDevices: deviceFoundCallback: Remote
   Address is: ...`), but the app's UI never lists it, and the system log
   shows:
   ```
   W/BroadcastQueue: Exported Denial: sending Intent { act=android.bluetooth.device.action.FOUND
     flg=0x10 pkg=com.nexora.nexora (has extras) }, action: android.bluetooth.device.action.FOUND
     from com.android.bluetooth (uid=1002) due to receiver ProcessRecord{... com.nexora.nexora/...}
     (uid 10258) not specifying RECEIVER_EXPORTED
   ```
   Confirmed reproducing on a real MIUI/Android 13 (API 33) device across
   two separate discovery attempts. (Also attempted on a stock Android 17
   (API 37) device in the same session — the native scan found a remote
   device there too, but the export-denial line itself did not appear in
   that capture window; not yet independently confirmed whether that
   device's broadcast dispatcher logs the denial differently or whether
   the broadcast happened to succeed there. Either way, the API-33 device's
   evidence alone is unambiguous and the fix is correct on Android's own
   documented broadcast-receiver-export semantics regardless.)

## Expected

Discovering a real nearby Bluetooth device causes it to appear in the
Devices screen's discovery results.

## Actual

Native Bluetooth discovery succeeds (the OS finds the other device), but
the app's own `ACTION_FOUND` receiver never fires — `handleDeviceFound()`
is never called, so no discovered device is ever surfaced to Dart, no
matter how close or discoverable the peer is. Every previous test of this
feature (per this app's own test suite, which cannot exercise a real
Android broadcast-receiver-export enforcement decision — no mocked-Kotlin
capability exists for this, the standing `E04-T03b` limitation already
noted by prior tasks touching this same file) reported success because it
never ran against two real devices with a real, cross-process
`ACTION_FOUND` broadcast in flight.

## Severity

**S1** — this is a total, silent failure of a core, must-have feature
(peer discovery, `FR-DISC-001`/`FR-DISC-002`) on real hardware. No
exception is thrown, no error surfaces anywhere in the app, so a user
sees only "No devices yet" with no indication anything is wrong at all.

## Fix

Change `ContextCompat.RECEIVER_NOT_EXPORTED` to
`ContextCompat.RECEIVER_EXPORTED` at
`BluetoothTransport.kt:447`. This remains safe: `ACTION_FOUND` is declared
a protected system broadcast in the Android platform's own manifest
(`<protected-broadcast android:name="android.bluetooth.device.action.FOUND"/>`),
which means only the OS Bluetooth stack itself can ever actually send one
— no third-party app can forge or spoof it regardless of the exported
flag. `RECEIVER_EXPORTED` only widens WHO this receiver will accept
broadcasts from; it does not weaken what `ACTION_FOUND` itself can mean.

## What this fix does NOT do
- Does NOT change the discovery mechanism itself (still Bluetooth Classic
  `startDiscovery()`/`ACTION_FOUND`, per ADR-0004's already-accepted
  design) — this is a receiver-registration bug, not an architecture
  change.
- Does NOT touch `ACTION_DISCOVERY_FINISHED` handling, `handleDeviceFound`,
  connection/pairing logic, or anything downstream of the receiver firing
  — those are unaffected; they simply never ran due to this bug.
- Does NOT add any new permission — `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT`
  are already declared and were already confirmed granted on both test
  devices; this is purely a broadcast-receiver registration flag.
- Does NOT attempt automated regression coverage — `flutter test`'s VM
  cannot exercise real Android broadcast-receiver export enforcement
  (the same standing limitation already carried by every prior
  `E04-T03b`-adjacent task touching this file). Verification is a real
  on-device re-test, recorded in this file's own Run log, not a
  `flutter test`/`flutter analyze` pass.
