# E04-B27 · Small defects from the audit and live testing

## 1. What each fix does

| # | Defect | Fix |
|---|---|---|
| 1 | **Stale Dashboard latency** (live, Pixel 8 Pro): `_latestLatencyMs` was set on every link-quality event and never cleared, so a vanished peer's reading stayed next to "No peers nearby". A device reporting link quality through an accepted/bonded connection (no discovery event) also left the reading at "No peers nearby". | Remember which device produced the latency and clear it when that device is lost. A device reporting a live link measurement is added to the known nearby peers. |
| 2 | **Re-delivered PreKey message counted as undecryptable** (audit finding 1): the same session-establishing message arriving over a second mesh path fails at the already-consumed one-time prekey (`InvalidKeyIdException`), which mapped to `unknown` and inflated `undecryptable`. | New `CryptoDecryptFailureReason.consumedOneTimePreKey`, used ONLY for the one-time-prekey variant (the message text is written by this codebase's own `DriftSignalProtocolStore.loadPreKey`). A missing SIGNED prekey still maps to `unknown`. The pipeline counts the new reason as `duplicate`. |
| 3 | **`stop()` race** (audit finding 2): `stop()` closes `_deliveredController` while an in-flight handler can still be past its last await, so its `add` threw `StateError`. | Both `add` sites check `isClosed` first. The row is still persisted; only the event is skipped. |
| 4 | **Silent startup-task failures** (audit finding 5): `_seedKnownDevices` and `_reconcileOrphanedMessagesByIdentity` were `unawaited`, so a throw became an unhandled async error with no trace. | Both are wrapped with `catchError`, which increments a new `counters.startupTaskFailed`. They stay fire-and-forget (`start()` is synchronous by contract) and still self-heal on the next `start()`. |
| 5 | **Non-atomic prekey replenish** (audit finding 3): the id cursor advanced in its own transaction and each row was stored separately, so a crash in between wasted allocated ids. | Allocation and storage run inside one outer `_db.transaction`; the inner transaction nests as a savepoint. |

## What this task does NOT do

- Does not change what a relay forwards or how dedup by message id works.
- Does not delete stale `relationships` rows (audit finding 7). Those rows hold trust state, so removing them is a design decision, not a small fix.
- Does not address group-message blocking via `frame.source` (audit finding 6). That is inherent to Sender Keys chain selection.
- Does not call `PrekeyExchange.dispose()` (audit finding 4). That is a documented deviation with no production effect.
- Does not redesign the Network Status card or add new reading states.
