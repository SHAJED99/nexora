# E04-B26 · File inbound 1:1 messages under this device's own conversation id

## 1. Goal

Fix the root cause E04-B24 only heals after the fact (its `OQ-E04-B24-2`,
and E04-B23's unowned "inbound-first conversation keyspace divergence"
note): at receive time, after a successful decrypt, map the envelope's
sender-minted conversation id to this device's own id for that sender.

## 2. Mechanism

Inside `ReceiveMessageUseCase.call`'s existing transaction,
`_resolveConversationId(envelope.conversationId, senderDeviceId)`:

1. If a relationship row (any state) already has
   `deviceId == envelope.conversationId`, keep the envelope id. A
   conversation that already belongs to a relationship on this device (for
   example a blocked peer's) is never pulled into another contact's thread.
   This is E04-B24's round-2 F5 lesson applied to the receive path.
2. Otherwise look up relationships with
   `remoteSelfDeviceId == senderDeviceId` and `state IN (trusted, allowed)`.
3. Exactly one match: use its `deviceId`. Zero or several: keep the
   envelope id (today's behavior).

The persisted row and the returned `Message` carry the same id.

### Security note

`senderDeviceId` is `frame.source`, a claimed field. But this code runs only
after the ciphertext decrypted successfully under the Signal session for
that address, so the claim is session-authenticated (TOFU, like the rest
of the 1:1 path). The target must already be independently
`trusted`/`allowed`. At worst a message is filed into a thread that is
already trusted: the remap never grants trust and never makes an untrusted
device dialable. `remoteSelfDeviceId` is still peer-announced
(`IdentityAnnounceService`, E04-B12), which is why ambiguity or a
pre-owned envelope id falls back to today's behavior rather than guessing.

## What this task does NOT do

- Does not change the `MessageEnvelope` wire format, and does not make senders mint a shared id.
- Does not touch the group-message path (`InboundPipeline.handleGroupMessage`).
- Does not modify `inbound_pipeline.dart` or remove E04-B24's startup reconciliation, which still heals legacy data.
- Does not change dedup, ordering, `createdAt`, `plaintextPayload`, or delivery-state logic.
- Does not migrate `sync_cursors`.

## Open Questions

- OQ-E04-B26-1 — **RESOLVED 2026-09-15 00:02.** Post-merge live check with development dc0f05a on the Pixel 8 Pro and the Redmi:
  - Pixel to Redmi `postmerge-1` was persisted on the Redmi under `B8:DB:38:7C:D4:BF` (its own id for the Pixel).
  - Redmi to Pixel `postmerge-2` was persisted on the Pixel under `00:00:46:00:00:01` (its own id for the Redmi).
  - Each device has exactly one conversation (Redmi 21 messages, Pixel 22), no ghost thread, and 0 `E flutter` log lines.
- OQ-E04-B26-2: the lookup matches on `senderDeviceId`. It relies on `frame.source` equalling the peer's announced self id, which the live DBs show it does today (`sender_device_id` = 66-hex identity). If a future transport change makes `frame.source` a MAC address again, the remap silently stops matching and behavior reverts to today's (safe, not wrong).
- OQ-E04-B26-3 (review finding, S3, accepted with the same posture as E04-B24; owner: a future project-wide TOFU / IdentityAnnounceService trust-boundary task, see E04-B12 and E09-B09): the remap runs on every inbound message, not once per launch. An attacker who learns a trusted contact's announced remoteSelfDeviceId and is the FIRST to establish a Signal session under that address string (TOFU: isTrustedIdentity accepts an unrecorded address) could get messages filed into that contact's visible thread. Bounded: it needs a first-contact race before the real peer's session exists, never grants trust, and never changes the dial target. Not reproduced.
