# E04-B15 · Extend E04-B13's outbound-identity-resolution fix to the other control protocols

## 1. Why this task exists
`E04-B13` fixed the raw-Bluetooth-MAC-vs-real-`selfDeviceId` addressing
mismatch (root-caused in `E04-B12`) for exactly two `RelayPacketFrame`
construction sites: `PrekeyExchange._sendControlFrame` (session
bootstrap) and `MessagingStack`'s own `encryptAdapter` (1:1 text chat —
the literal feature the original human bug report, "I can not send any
message," was about). That task's own reviewer confirmed via a full grep
that **13 `RelayPacketFrame(` construction sites exist in `lib/`** —
meaning at least 11 more sites were not touched, deliberately, to keep
`E04-B13` at a reviewable `size: M`.

Every one of those other sites almost certainly has the IDENTICAL defect:
addressed by Bluetooth MAC, which can never match a real peer's
`InboundPipeline._handleBuffer` `isForUs` check on real, independently
provisioned hardware, for exactly the same reason `E04-B12`'s own root
cause explains. Candidate features affected (confirm each individually,
do not assume the list is complete or that every guess below is
correct): `DeliveryAckService` (read receipts/delivery ticks — E06-T08),
`CallSignaling` (E10), `GroupMembershipService`/`GroupCryptoService`
group messaging (E07), `LocationShare` (E09). Each of these features
likely appears to "work" in this codebase's own existing test suite
(mocked transport, no real addressing mismatch possible in a test
double) while being silently broken on two real physical devices — the
exact same gap class `E04-B11`→`E04-B13` spent a full session finding for
1:1 chat, now suspected across the rest of the app's real-device surface.

## 2. What this task does
1. **Enumerate every `RelayPacketFrame(` construction site in `lib/`**
   (re-run the grep `E04-B13`'s reviewer used, don't trust this task
   file's own guess-list above) and classify each: already fixed
   (`E04-B13`'s two sites), needs the identical fix, or is a relay/forward
   site that legitimately never constructs a frame (like
   `RelayEngine`/`ConnectionEnsuringSender`, already confirmed clean by
   `E04-B13`'s reviewer).
2. **Apply the same fix pattern `E04-B13` established** to every
   remaining real construction site: resolve `Relationship.
   remoteSelfDeviceId` for the target Bluetooth MAC when known, fall back
   to the raw MAC when not yet announced — reuse `E04-B13`'s own
   `resolveOutboundDestination` helper (or an equivalent already-reviewed
   function) rather than re-deriving the logic independently per call
   site.
3. **Write a test per affected feature** proving the fix, following
   `E04-B13`'s own established test shape (a real two-`MessagingStack`
   integration test over the actual transport boundary, not a mock that
   would hide the exact defect being fixed).
4. If real hardware is available at implementation time, attempt live
   verification for at least one non-chat feature (e.g. a delivery ack
   round trip) to build additional confidence beyond the Dart-level
   proof — but per `E04-B13`'s own precedent, a genuine hardware
   unavailability is an acceptable, honestly-disclosed limitation, not a
   reason to block this task indefinitely.

## 3. What this task does NOT do
- Does NOT touch 1:1 chat's own two already-fixed sites

- Does NOT fix `E04-B14`'s own bundle-response-provenance gap — separate,

- Does NOT add new features to calls/groups/location — this is purely an

## Open Questions
- **`DeliveryAckService._sendAck` and `CallSignaling`'s
  accept/decline/ring reply path (in response to an inbound `invite`)
  have a DEEPER, related gap this task's own `files:` fence cannot
  close.** Investigated while implementing this task, not anticipated by
  its own §1/§2: both are REPLY-shaped call sites (their own
  `peerDeviceId`/`session.peerDeviceId` argument is always a value
  LEARNED from a previously-received frame's `frame.source` — i.e.
  already a logical `selfDeviceId`, never a Bluetooth MAC), unlike the
  six sites this task fixed (all locally-initiated sends addressed by a
  MAC the user/system already holds, e.g. `Relationship.deviceId` /
  `GroupMembers.deviceId`). This task's own `resolveOutboundDestination`
  fix for these two sites is a real, harmless, but STRUCTURALLY INERT
  no-op for the frame's `destination` field (the lookup key is never
  MAC-shaped, so it can never match a `relationships` row and always
  falls back to itself, which happens to already be the correct logical
  destination) — the actual remaining defect is the TRANSPORT DIAL,
  which still attempts to connect/enqueue using that same logical id,
  never a MAC. On real hardware this means: (a) `DeliveryAckService`'s
  own ack replies, and (b) `CallSignaling`'s own accept/decline/ring
  replies to an inbound invite, likely still fail to physically leave
  the device. Unlike `PrekeyExchange._handleBundleRequest` (fixed in
  this same task), neither `DeliveryAckService.handleControlFrame` nor
  `CallSignaling.handleWireFrame` receives a `linkDeviceId` at all — both
  are registered on `InboundPipeline`'s SHARED, generic `ControlHandler`
  typedef (`Future<void> Function(RelayPacketFrame)`), not a dedicated
  link-bound slot the way `E04-B14` built for `PrekeyExchange`. Widening
  `ControlHandler` itself to carry link data would force editing all
  five of its sharers (`delivery_ack.dart`, `group_membership_service.dart`,
  `group_crypto_service.dart`, `call_signaling.dart`,
  `location_share_service.dart`) just to keep them compiling — exactly
  the blast radius `E04-B14`'s own Deviations explicitly investigated and
  declined to take on, for the identical reason. Recommend a dedicated
  follow-up bug task (mirroring `E04-B14`'s own dedicated-slot pattern,
  scoped to `inbound_pipeline.dart` + `delivery_ack.dart` +
  `call_signaling.dart` + `messaging_stack.dart`'s wiring) rather than
  silently leaving this undiscovered or forcing it into this task's own
  fence. Not fixed here: out of `files:` (would require editing
  `inbound_pipeline.dart`/`messaging_stack.dart`, neither fenced by this
  task), and a real, separate design decision (a third dedicated
  `ControlHandler`-alternative slot, or something else) that should not
  be made silently inside an addressing bug-fix task.

  reported** — same environment constraint every task in this chain has
  disclosed. `adb devices -l` at dispatch time and at completion time

## Carried forward from E04-B14's own review (opus, 2026-09-13)
`PrekeyExchange._handleBundleRequest` (`prekey_exchange.dart:688-723`)
replies to an inbound bundle REQUEST via `_sendControlFrame(frame.source,
...)` → `directSend`, keyed by the REQUESTER's logical `selfDeviceId` —
not a dialable Bluetooth MAC on real hardware. This is the mirror-image
of the exact bug `E04-B13` fixed for OUTBOUND requests, on the RESPONSE
leg instead. Untouched by `E04-B13`/`E04-B14` (out of both tasks' own
fences), but means the response leg of a first-contact bundle exchange
may still not complete on real devices even after this whole chain's
fixes. **This task's own §1 enumeration should confirm whether this is
already covered by its own scope, or needs to be named as its own,
narrower fix inside this task.**

**Also carried forward, a future-hazard note for whoever implements
this task**: if this task's own fix changes what value any
`ensureSession` caller captures as its own outbound `linkDeviceId` (see
`E04-B14`'s own `_ensureSessionUncoalesced` capture point), that same
change must be made consistently — `E04-B14`'s new link-binding check in
`_takeMatchingCompleter` depends on the captured value continuing to
match the link a response actually arrives on. Do not change one without
the other.

**Resolved (this session).** Confirmed real, and fixed:
`_handleBundleRequest` now receives `linkDeviceId` (threaded through
`handleControlFrame`'s existing switch, already parameterized by
E04-B14) and uses it as `_sendControlFrame`'s new `transportTarget` —
the physical dial target — while the frame's own `destination` field
stays keyed by `peerDeviceId` (`frame.source`, unchanged, since that
was already correct: `resolveOutboundDestination`'s lookup on a claimed
logical id can never match a MAC-keyed `relationships` row, so it
always fell back to the claimed id itself, which is exactly the right
`destination` value). Trust evaluation
(`_evaluateConnectionRequest`)/the E10-T05 notice are now keyed by
`linkDeviceId` too, closing a latent, related bypass: before this fix
they were keyed by the claimed logical id, which can never match a
MAC-keyed `relationships` row either, so a `blocked` peer's request
could never actually be evaluated against its real stored relationship
row.

**This did NOT change what `_ensureSessionUncoalesced` captures as
`outstanding.linkDeviceId`** (the future-hazard note above) — that
capture point is untouched; only `_handleBundleRequest`'s own reply
path changed. Proven, not just asserted:
`test_E04_B14_forged_bundle_response_on_wrong_link_is_rejected`
(pre-existing, unmodified) still passes, and this task's own
`test_E04_B15_bundle_request_reply_uses_physical_link_not_claimed_source`
explicitly asserts `responsesUnsolicited == 0` on the legitimate,
correctly-addressed reply — proving E04-B14's link-binding check still
accepts a real reply after this fix, not merely that it still rejects
a forged one.

## Deviations
- **`PrekeyExchange._sendControlFrame` gained a new optional
  `transportTarget` named parameter**, not named in this task's own §2 —
  needed once implementation revealed that the reply leg's frame
  `destination` (correctly `frame.source`, the claimed logical identity)
  and its physical transport dial (needed to be `linkDeviceId`, the
  request's real arrival link) are two DIFFERENT values, unlike every
  other call site this task fixed (where one raw MAC serves both roles).
  Reusing `_sendControlFrame` with a second, optional parameter — rather
  than duplicating its resolution/framing logic at the
  `_handleBundleRequest` call site, or forcing the reply through the
  same single-argument shape and accepting a broken transport dial —
  keeps E04-B13's own established `resolveOutboundDestination` reuse
  discipline intact. `transportTarget` defaults to `null`, so the
  outbound-request call site (`_ensureSessionUncoalesced` →
  `_sendControlFrame(peerDeviceId, ...)`, no `transportTarget`) is
  byte-for-byte unchanged.
- **`DeliveryAckService._sendAck` and `SendGroupMessageUseCase.send`'s
  per-recipient loop had their new `resolveOutboundDestination` call
  moved inside their own existing `try`/`catch`**, discovered via a real
  test failure (not by inspection alone): the full suite run together
  with `messaging_coordinator_test.dart` intermittently failed with
  `Bad state: Can't re-open a database after closing it`, traced to
  `DeliveryAckService._sendAck` — called fire-and-forget, `unawaited`,
  from `MessagingStack`'s own `inbound.delivered` subscription
  (`messaging_stack.dart:363-366`), with no catch at that call site
  either. The new `await resolveOutboundDestination(...)` line, first
  written OUTSIDE the method's existing `try` block, could throw after a
  test (or, in production, `MessagingStack.dispose()`) had already
  closed the underlying database, escaping as an unhandled async-zone
  error this method's own doc comment already promises never happens
  ("Never throws"). Moved inside the `try`, mirroring every other fixed
  call site (`call_signaling.dart`, `group_membership_service.dart`,
  `group_crypto_service.dart`, `location_share_service.dart` all already
  had their construction site naturally inside an existing `try` that
  wraps the whole send). `send_group_message_use_case.dart`'s own loop
  got the identical treatment even though its symptom was not directly
  observed failing (its own `try` only wrapped `_enqueue`) — the same
  reasoning applies: a resolution failure for one recipient must not be
  allowed to abort the whole fan-out loop, matching this file's own
  explicit "one unreachable/failing recipient must never abort another"
  contract. Full suite re-run twice after the fix, clean both times.
- **Investigated and disclosed, not fixed: `DeliveryAckService`'s and
  `CallSignaling`'s own reply-shaped transport-dial gap** — see Open
  Questions above for the full reasoning. Out of this task's own
  `files:` fence (would require editing `inbound_pipeline.dart`'s shared
  `ControlHandler` typedef or adding new dedicated slots, plus
  `messaging_stack.dart`'s wiring), and the exact blast-radius shape
  `E04-B14`'s own Deviations already investigated and declined for the
  identical reason. Recommending a follow-up task rather than silently
  fixing or silently ignoring it.
