# E04-B15 · Extend E04-B13's outbound-identity-resolution fix to the other control protocols

## 1. Why this task exists
`E04-B13` fixed the raw-Bluetooth-MAC-vs-real-`selfDeviceId` addressing
mismatch (root-caused in `E04-B12`) for exactly two `RelayPacketFrame`
construction sites: `PrekeyExchange._sendControlFrame` (session
bootstrap) and `MessagingStack`'s own `encryptAdapter` (1:1 text chat —
the literal feature the original human bug report, "I can not send any
message," was about). That task's own reviewer confirmed via a full grep
that **13 `RelayPacketFrame(` construction sites exist in `lib/`** —
meaning at least 11 more sites were not touched, deliberately, to keep
`E04-B13` at a reviewable `size: M`.

Every one of those other sites almost certainly has the IDENTICAL defect:
addressed by Bluetooth MAC, which can never match a real peer's
`InboundPipeline._handleBuffer` `isForUs` check on real, independently
provisioned hardware, for exactly the same reason `E04-B12`'s own root
cause explains. Candidate features affected (confirm each individually,
do not assume the list is complete or that every guess below is
correct): `DeliveryAckService` (read receipts/delivery ticks — E06-T08),
`CallSignaling` (E10), `GroupMembershipService`/`GroupCryptoService`
group messaging (E07), `LocationShare` (E09). Each of these features
likely appears to "work" in this codebase's own existing test suite
(mocked transport, no real addressing mismatch possible in a test
double) while being silently broken on two real physical devices — the
exact same gap class `E04-B11`→`E04-B13` spent a full session finding for
1:1 chat, now suspected across the rest of the app's real-device surface.

## 2. What this task does
1. **Enumerate every `RelayPacketFrame(` construction site in `lib/`**
   (re-run the grep `E04-B13`'s reviewer used, don't trust this task
   file's own guess-list above) and classify each: already fixed
   (`E04-B13`'s two sites), needs the identical fix, or is a relay/forward
   site that legitimately never constructs a frame (like
   `RelayEngine`/`ConnectionEnsuringSender`, already confirmed clean by
   `E04-B13`'s reviewer).
2. **Apply the same fix pattern `E04-B13` established** to every
   remaining real construction site: resolve `Relationship.
   remoteSelfDeviceId` for the target Bluetooth MAC when known, fall back
   to the raw MAC when not yet announced — reuse `E04-B13`'s own
   `resolveOutboundDestination` helper (or an equivalent already-reviewed
   function) rather than re-deriving the logic independently per call
   site.
3. **Write a test per affected feature** proving the fix, following
   `E04-B13`'s own established test shape (a real two-`MessagingStack`
   integration test over the actual transport boundary, not a mock that
   would hide the exact defect being fixed).
4. If real hardware is available at implementation time, attempt live
   verification for at least one non-chat feature (e.g. a delivery ack
   round trip) to build additional confidence beyond the Dart-level
   proof — but per `E04-B13`'s own precedent, a genuine hardware
   unavailability is an acceptable, honestly-disclosed limitation, not a
   reason to block this task indefinitely.

## 3. What this task does NOT do
- Does NOT touch 1:1 chat's own two already-fixed sites
  (`E04-B13`'s own `files:` fence) — this task is purely the remaining
  sites.
- Does NOT fix `E04-B14`'s own bundle-response-provenance gap — separate,
  already-filed task.
- Does NOT add new features to calls/groups/location — this is purely an
  addressing-correctness fix to features that already exist in this
  codebase.

## Definition of Done

- [ ] Every site needing the fix has it, using the same resolution

## Carried forward from E04-B14's own review (opus, 2026-09-13)
`PrekeyExchange._handleBundleRequest` (`prekey_exchange.dart:688-723`)
replies to an inbound bundle REQUEST via `_sendControlFrame(frame.source,
...)` → `directSend`, keyed by the REQUESTER's logical `selfDeviceId` —
not a dialable Bluetooth MAC on real hardware. This is the mirror-image
of the exact bug `E04-B13` fixed for OUTBOUND requests, on the RESPONSE
leg instead. Untouched by `E04-B13`/`E04-B14` (out of both tasks' own
fences), but means the response leg of a first-contact bundle exchange
may still not complete on real devices even after this whole chain's
fixes. **This task's own §1 enumeration should confirm whether this is
already covered by its own scope, or needs to be named as its own,
narrower fix inside this task.**

**Also carried forward, a future-hazard note for whoever implements
this task**: if this task's own fix changes what value any
`ensureSession` caller captures as its own outbound `linkDeviceId` (see
`E04-B14`'s own `_ensureSessionUncoalesced` capture point), that same
change must be made consistently — `E04-B14`'s new link-binding check in
`_takeMatchingCompleter` depends on the captured value continuing to
match the link a response actually arrives on. Do not change one without
the other.
