# E04-B20 · Fix the same double-decrypt defect in group messaging E04-B18 fixed for 1:1 chat

## 1. Goal

Apply E04-B18's same fix shape (persist the plaintext this device already
legitimately decrypts once, at receive/send time; never re-derive it by
decrypting stored ciphertext a second time) to group messages, closing the
identical defect class in the group-conversation preview path (and any
other place group ciphertext is decrypted more than once per message).

## 2. Background (why this is filed, not silently skipped)

Found during `E04-B18`'s independent review (round 1, `claude-opus-5`,
2026-09-13). `E04-B18`'s own task file originally claimed group messaging
"use[s] a completely different mechanism (Sender Keys, not 1:1 Double
Ratchet) and were never the subject of this bug" as the reason to defer
it — the reviewer found that claim factually wrong and asked for a
correction plus this follow-up task, rather than leaving it as an
untracked, incorrect assumption. See `E04-B18.md` §4's corrected wording
for the full context.

The repo's own code comment already states the mechanism is NOT safer in
the relevant way: `inbound_pipeline.dart:1020-1021` — `GroupCipher.decrypt`
(E07-T04) "discards a message key once used, **exactly like the pairwise
Double Ratchet**." The same two-decrypts-of-one-ciphertext shape is
present:

- **Receive time**: `inbound_pipeline.dart`'s `_handleGroupMessageWireFrame`
  calls `_stack.groupCryptoService.decryptFromGroup(...)` (`:1002`) to
  recover `GroupMessageEnvelope` metadata; only the ciphertext bytes are
  persisted afterward (`:1089-1098`) — the decrypted plaintext is
  discarded, same pattern `E04-B18` fixed for `ReceiveMessageUseCase`.
- **Preview time**: `ConversationsController._resolveGroupPreview`
  (`conversations_controller.dart:496-524`) independently calls
  `decryptFromGroup` AGAIN on that same stored ciphertext, gated only by
  `_groupPreviewCache` (`:310`) — a per-`ConversationsController`-instance
  map with the exact same lifetime problem `_previewCache`/
  `_plaintextCache` had before `E04-B18`.

`E04-B18` was deliberately NOT widened to cover this: different crypto
service (`GroupCryptoService`, Sender Keys key management — membership,
epoch rotation, per-sender chains — none of which `E04-B18` touched or
was scoped to reason about), and the live symptom that triggered the
whole investigation was a 1:1 conversation. This task is that deliberate
deferral, made a tracked obligation instead of a dropped one.

## 3. What this task does

- Confirm the defect with the same rigor `E04-B18` used for 1:1 (live
  two-device group-chat repro if hardware access allows; at minimum a
  real-crypto unit test proving `decryptFromGroup` throws/fails on a
  second call against the same stored ciphertext, mirroring
  `E04-B18`'s own falsification method).
- Apply the equivalent fix: persist the plaintext `handleGroupMessage`
  already legitimately decrypts at receive time (a new column, or reusing
  `messages.plaintext_payload` if group messages share that table --
  confirm the actual group-message storage location first, this task's
  own investigation, not assumed here) instead of discarding it.
- Update `ConversationsController._resolveGroupPreview` (and the group
  chat screen's own display path, if one independently decrypts too — an
  audit this task should do, not assumed complete by this filing) to read
  that persisted value first, falling back to `decryptFromGroup` only for
  a pre-fix row, mirroring `E04-B18`'s `_resolvePlaintext`/
  `_resolvePreview` pattern exactly.
- Add regression tests mirroring `E04-B18`'s own (a second controller
  instance against deliberately-unusable ciphertext must still show the
  correct preview/message).

## 4. What this task does NOT do

- Does NOT change `GroupCryptoService`'s Sender Keys key management,
  membership/epoch rotation, or any group-crypto internals beyond what's
  needed to stop the redundant decrypt.
- Does NOT touch `E04-B18`'s own 1:1 fix, already merged and live-proven.
- Does NOT assume the fix is a drop-in reuse of `messages.plaintext_payload`
  without first confirming group messages are stored in that same table
  with the same shape -- if group messages have their own table/model,
  this task designs the equivalent column there instead.

## 5. Definition of Done

- [x] Defect confirmed by falsification. The group preview test stores deliberately unusable ciphertext, so with the fix reverted the preview degrades to empty (`Expected: 'persisted group body'`, `Actual: ''`), i.e. a second `decryptFromGroup` on stored bytes cannot recover the text. (Commit `bbccce3`.)
- [x] Fix implemented. `messages.plaintext_payload` already existed and group messages use the same `messages` table, so no schema change was needed:
  - `InboundPipeline.handleGroupMessage` persists `envelope.body`, which the wire handler already decrypted once.
  - `SendGroupMessageUseCase` persists `body` alongside the ciphertext.
  - `ConversationsController._resolveGroupPreview` reads it first, falling back to `decryptFromGroup` only for pre-fix rows.
  - Audit: no group chat thread view exists yet (GAP-020), so there is no other group decrypt-for-display site.
- [x] Regression tests:
  - `test_E04_B20_group_preview_uses_persisted_body_without_a_second_decrypt`
  - `test_E04_B20_received_group_message_persists_its_decrypted_body`
  - a `plaintextPayload` assertion added to `test_EARS_COMM_29_one_ciphertext_and_n_frames`

  Falsified three ways, each mutation restored from HEAD afterwards:
  - receive insert without the body: only the received-body test fails
  - send without the body: only the send test fails
  - preview ignoring the persisted body: only the preview test fails
- [x] Full `flutter test` 1563/1563. `flutter analyze`: the same 3 pre-existing infos, none new.
- [x] Independent review (claude-sonnet-5, APPROVE, PR #263: membership check confirmed before the body is persisted; no other group decrypt-for-display site)
