# E04-B36 · Arm the silence watchdog on any received frame

## 1. Goal
E04-B35's promise — a vanished peer is noticed within a bounded time — actually holds on hardware, including for a link that dies in its first seconds.

## 2. Root cause
Two independent mistakes in E04-B35, both mine:

1. **Arming depended on the peer.** `peerSendsKeepalive` gates the silence check, and it is set only on a received zero-length frame. Both sides refresh `lastSentAtMs` on any write, so a link carrying data early sends its first keepalive later than 10 s after open. A link that dies inside that window is never armed, so it is never closed — forever, not just late.
2. **A successful keepalive write was treated as meaningful.** It is not. `sendKeepalive`'s failure path only fires on a write error or timeout, and RFCOMM accepts a 4-byte write into its buffer for minutes after the peer's radio is off (observed: zero write failures across 2 min 41 s with the peer powered down).

The plan review (PR #283) and the code review (PR #284) both missed this, because each traced the arming rule as written rather than asking what happens when the peer never sends a keepalive at all.

## 3. What this task does
- `LinkLiveness.armed`, set by ANY frame received on that link (data or keepalive). It is what starts the silence clock.
- Two deadlines instead of "no deadline":
  - `LINK_SILENCE_TIMEOUT_MS` (30 s) once the peer has sent a keepalive, so a current build is detected fast;
  - `LINK_IDLE_NO_KEEPALIVE_TIMEOUT_MS` (120 s) when the peer has only ever sent data, which covers both an older build and a current one whose first keepalive had not gone out. Closing an idle older peer's link costs only a reconnect on the next send.
- `peerSendsKeepalive` now only SELECTS the deadline; it never decides whether one applies.
- Documents on `sendKeepalive` that a successful write is not evidence of liveness.
- Temporary `NexoraKA` diagnostic logging in the tick, the keepalive write and the keepalive receive path, so the live re-test proves what actually happens instead of inferring it. Removed before merge.

## 4. What this task does NOT do
- Does not change the wire format, the keepalive interval, or `send()`/`writeFrame`'s framing and locking.
- Does not add a Dart-side ping, a Pigeon change, or any `kControlKind`.
- Does not add a Kotlin test harness (none exists in this project).
- Does not keep the diagnostic logging: this project's native layer logs nothing, and that stays true after this task.
- Does not change E04-B28's scan-based lost events or E04-B34's Dashboard handling.

```yaml
  purpose: "silence deadline for a peer that has sent frames but never a keepalive"

  purpose: "set by any received frame; the silence clock only applies to an armed link"
```

## 6. Risks
- **Closing an idle old-build peer.** After 2 min of true silence its link closes and reconnects on the next send. Acceptable, and self-healing; the alternative is the defect this task fixes.
- **A peer that never sends anything at all** (connects, stays mute) is still never armed, so its link is never closed. Bounded by the fact that Nexora peers announce identity on connect.
- **Diagnostic logging must not ship.** It is removed in this task's own final commit, and the reviewer is asked to confirm no `NexoraKA` string survives.
