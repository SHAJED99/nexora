# E04-B36 · Silence is not observable on a dead RFCOMM link; detect the adapter/link going down instead

## 1. Goal
A peer that disappears is detected from a signal the platform actually gives, rather than from an absence of traffic that never materialises.

## 2. Root cause (corrected — the first version of this task was wrong)
This task originally claimed E04-B35's watchdog "never armed" because arming required a received keepalive. That diagnosis was **wrong**, and the diagnostic build disproved it: the Pixel logged `armed=true ka=true` continuously, with the peer's Bluetooth off.

The real finding: **turning the adapter off does not close the app's RFCOMM socket, and does not stop reads from completing.** Both apps continued to write keepalives successfully and to *receive* keepalives from each other for at least two minutes after the Redmi's adapter reported `TURNING_OFF` and dropped all of its RFCOMM servers. The bytes are coming from the stack's own buffers on each side, not over the air.

Consequences:
- `lastReceivedAtMs` is refreshed roughly every 10 s on a link that is physically dead, so `silent` never approaches any deadline. E04-B35's 30 s rule, and the 120 s variant this task first proposed, are both unreachable.
- A successful keepalive **write** proves nothing either (already documented in E04-B35): RFCOMM accepts the 4-byte write with no error.
- Therefore E04-B35, as merged (`527392b`, PR #284), is **inert on this hardware**. It ships a mechanism that cannot fire. It is not harmful — it adds one 4-byte frame per idle link per 10 s — but it does not deliver EARS-TRANSPORT-4.

## 3. What this task does
Replaces inference-from-silence with the platform's own signals, verified on hardware before any claim is made:
- Register for `BluetoothAdapter.ACTION_STATE_CHANGED` and `BluetoothDevice.ACTION_ACL_DISCONNECTED` in `BluetoothTransport`.
- On the local adapter leaving `STATE_ON`: tear down every open socket, clear liveness state, emit `DISCONNECTED` per device.
- On `ACTION_ACL_DISCONNECTED` for a device with an open socket: close that socket and emit `DISCONNECTED` for it.
- Keep E04-B35's keepalive and silence deadline as a backstop for cases those broadcasts do not cover (out of range with no ACL event), now that its limits are understood and documented.
- Re-run the live checks and record what each signal actually produces on these two phones, including the case this task was filed for.

## 4. What this task does NOT do
- Does not remove E04-B35's keepalive or change the wire format.
- Does not add a Dart-side ping, a Pigeon change, or any `kControlKind`.
- Does not add a Kotlin test harness (none exists in this project).
- Does not keep the temporary `NexoraKA` logging: it is removed before merge, and the reviewer is asked to confirm no such string survives.
- Does not claim the fix works until the §8 live checks pass on both phones. E04-B35's live box stays open until then.


## 6. Risks
- **The remote side gets no ACL event either.** If the peer's adapter dies, this device may see `ACTION_ACL_DISCONNECTED` late or not at all; that is exactly what the live checks must establish rather than assume.
- **Double emission.** `disconnect()` and the read loop already guard with a two-arg `openSockets.remove(deviceId, socket)`; the new paths must go through the same guard.
- **Receiver lifecycle.** Another unregistered receiver leak would mirror past defects; it must follow `registerReceiverIfNeeded`'s existing shape and be cleared in `release()`.
- **My own track record on this bug.** Two prior conclusions here were wrong because I reasoned ahead of evidence. No claim in this task may be ticked without a log line or a `dumpsys` excerpt quoted in the run log.
