# E04-T03a · Pigeon transport schema + Dart facade + native Kotlin skeleton (loopback)

## 1. Goal
Stand up the whole Dart↔Kotlin plumbing for the transport boundary (ADR-0004)
— Pigeon schema, generated bindings, a Dart-side `TransportService` facade,
and a native Kotlin host wired to `MainActivity` — proven end-to-end with a
**loopback** implementation (echoes bytes back in-process) so the plumbing
itself is testable without Bluetooth hardware or a real device. Real
Bluetooth is T03b/T03c.

## 2. Business logic
- FR-PLAT-003 / ADR-0004: Android-native components handle transport;
  Flutter talks to them through Pigeon-generated, type-safe bindings — not
  hand-parsed MethodChannel messages.
- This task defines the *shape* every real transport (Bluetooth now,
  Wi-Fi Direct/Internet later) will implement: discover, connect, send,
  receive, disconnect, plus a status stream. A loopback implementation lets
  every layer above (routing engine, relay, UI) be built and tested against
  a real Pigeon boundary before real radios exist.

## 3. What this task does
- `pigeons/transport.dart`: Pigeon schema defining `TransportDevice` (id,
  displayName, transportType enum: `bluetooth`/`wifiDirect`/`internet`),
  `TransportApi` (host-side, called from Dart): `startDiscovery()`,
  `stopDiscovery()`, `connect(deviceId)`, `disconnect(deviceId)`,
  `send(deviceId, bytes) -> bool`, and `TransportEventsApi` (Flutter-side,
  called from Kotlin) with `onDeviceDiscovered(device)`,
  `onDeviceLost(deviceId)`, `onConnectionStateChanged(deviceId, state)`,
  `onDataReceived(deviceId, bytes)`.
- Run Pigeon codegen (`dart run pigeon --input pigeons/transport.dart ...`
  per its documented flags), commit the generated output like any other
  reviewed generated source (same convention as Drift's `.g.dart`).
- `TransportService` (Dart, `lib/core/transport/`): thin facade over the
  generated `TransportApi`, exposing Dart-idiomatic `Stream<TransportDevice>`
  for discovery and `Stream<Uint8List>` per connected device for incoming
  data — this is what T04/E05/E06 actually import, not the generated code
  directly.
- `TransportApiHost.kt` + `LoopbackTransport.kt`: native Kotlin
  implementation of the Pigeon host interface where `connect()` to any
  device id immediately succeeds and `send()` echoes the bytes back via
  `onDataReceived` on the *same* device id after a short (real,
  `Handler.postDelayed`, ~50ms) simulated latency — enough to prove the
  round trip through the actual Pigeon/platform-channel boundary, not an
  in-Dart fake.
- Wire `TransportApiHost` into `MainActivity.configureFlutterEngine`.

## 4. What this task does NOT do
- Does NOT implement real Bluetooth discovery, pairing, or data transfer —
  `LoopbackTransport` is the only implementation this task ships. T03b
  replaces discovery/connect with real Bluetooth; T03c replaces send/
  receive.
- Does NOT request any Android permissions (`BLUETOOTH_SCAN`,
  `BLUETOOTH_CONNECT`, location, etc.) — loopback needs none; T03b adds the
  real manifest permissions and runtime permission flow.
- Does NOT implement Wi-Fi Direct or Internet-assisted transport — later
  epic waves per epic.md's own risk mitigation (Bluetooth-only first).
- Does NOT wire `TransportService` into the routing engine, relay, or any
  screen — no caller exists yet; this task only proves the boundary works.
- Does NOT add background-execution/Doze handling — that's meaningful only
  for a real radio transport (T03b/T03c's concern), not loopback.

## 5. Contract

### Pigeon schema (`pigeons/transport.dart`)
```yaml
- enum: "TransportType { bluetooth, wifiDirect, internet }"
- class: "TransportDevice { id: String, displayName: String, type: TransportType }"
- enum: "ConnectionState { connecting, connected, disconnected, failed }"
- host_api: "TransportApi"
  methods:
    - "startDiscovery() -> void"
    - "stopDiscovery() -> void"
    - "connect(deviceId: String) -> bool"
    - "disconnect(deviceId: String) -> void"
    - "send(deviceId: String, bytes: Uint8List) -> bool"
- flutter_api: "TransportEventsApi"
  methods:
    - "onDeviceDiscovered(device: TransportDevice) -> void"
    - "onDeviceLost(deviceId: String) -> void"
    - "onConnectionStateChanged(deviceId: String, state: ConnectionState) -> void"
    - "onDataReceived(deviceId: String, bytes: Uint8List) -> void"
```

### Functions
```yaml
- signature: "TransportService.discoveredDevices -> Stream<TransportDevice>"
  purpose: "Dart-idiomatic wrapper over onDeviceDiscovered/onDeviceLost"

- signature: "TransportService.connect(deviceId: String) -> Future<bool>"
  purpose: "Wraps TransportApi.connect, awaits the eventual onConnectionStateChanged"

- signature: "TransportService.send(deviceId: String, bytes: Uint8List) -> Future<bool>"
  purpose: "Wraps TransportApi.send"

- signature: "TransportService.incomingData(deviceId: String) -> Stream<Uint8List>"
  purpose: "Per-device incoming-bytes stream, wraps onDataReceived filtered by deviceId"
```

## 6. Risks
- Pigeon codegen output must be committed and reproducible — if the
  generated file drifts from what `dart run pigeon` produces from the
  schema, that's a real bug (same class as an uncommitted Drift codegen
  drift) — regenerate and diff-check before calling this done.
- Loopback's fixed device id / immediate-success behavior must not leak an
  assumption into `TransportService`'s Dart API that real Bluetooth can't
  satisfy (e.g. assuming `connect()` always succeeds synchronously) — the
  Dart facade's shape is the real contract T03b/T03c must fit, so get it
  right here, not there.
- `MainActivity.kt` is a shared file — if E01/E02 already modified it
  (they did, for Firebase), this task's diff must be additive to whatever's
  already there, not a wholesale rewrite.

**BLOCKING FINDING (fixed by reviewer, not returned as CHANGES):**
- `lib/core/transport/transport_service.dart:81-93` (pre-fix) —
  `connect()` awaited `_api.connect(deviceId)` and only *then* subscribed
  to the connection-state stream via `firstWhere`. The settled-state event
  and the host-call reply travel over **two independent channels**, so a
  transport that settles before its reply is delivered — an already-
  connected peer, a cached link, a fast failure — loses the event entirely
  and `connect()` **never completes** (unbounded hang, no timeout).
  Reproduced empirically before fixing: a mock native handler that pushes
  `onConnectionStateChanged(connected)` before returning its reply made
  `connect()` hang past a 2s timeout.
  Why it matters: this is exactly the failure §6 named as this task's job
  to prevent ("the Dart facade's shape is the real contract T03b/T03c must
  fit, so get it right here, not there"). The builder correctly avoided
  *assuming synchronous success* but introduced the mirror-image bug.
  `LoopbackTransport.connect()`'s 50ms `postDelayed`
  (`LoopbackTransport.kt:61-66`) masks it completely — no loopback test
  could ever have caught it, which is why it survived self-review.
  **Fix applied** (`transport_service.dart:81-113`): subscribe to the
  filtered state stream *before* issuing the host call, settle through a
  `Completer`, cancel the subscription in a `finally`, and complete `false`
  on `onDone` so a `dispose()` mid-connect can't hang either.
  **Regression tests added** (reviewer-authored, in the task's own test
  file): `test_connect_settles_when_state_event_precedes_host_reply` (fails
  against the old implementation, passes against the fix) and
  `test_connect_returns_false_when_native_reports_failed`. Suite 74/74.
