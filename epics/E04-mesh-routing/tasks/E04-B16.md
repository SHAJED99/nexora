# E04-B16 · Reconcile relay routing's link-id namespace with resolved-identity addressing

## How this was found
`E04-B15`'s own independent reviewer (opus), while confirming that task's
six outbound-addressing fixes, found this while checking whether any of
the fixed features route differently than 1:1 chat. Direct quote:

> On an intermediate relay, `inbound_pipeline.dart:756` re-enqueues by
> `frame.destination` — now a logical `selfDeviceId` (per E04-B12/B13/B15's
> own fix) — and `RoutingEngine.computeRoute` resolves over transport link
> ids, so it returns null and the packet sits until TTL. The fix makes
> direct-neighbour delivery work and multi-hop delivery structurally
> impossible... Not a blocker: inherited from B13, the task's §2.2
> mandated exactly this pattern, and it's currently latent
> (`link_quality_feed.dart:1-9` documents that `computeRoute()` always
> returns null on a real device today). But it becomes live the moment
> the link-quality feed lands, and fixing it needs either the reverse
> lookup B13 §1a forbids or a wire-format change — rule 3.

In plain terms: `E04-B12`/`E04-B13`/`E04-B15` correctly fixed direct
(single-hop, already-connected) message delivery by resolving a peer's
real `selfDeviceId` before addressing a frame. But `RelayEngine`'s own
multi-hop forwarding path (`inbound_pipeline.dart`'s `!isForUs` branch)
re-enqueues a frame by that SAME resolved `frame.destination` — and
`RoutingEngine.computeRoute` (the thing that decides which NEXT-HOP link
to forward a relayed packet over) has only ever known about transport
link ids (Bluetooth MAC addresses), never Signal-Protocol identity
strings. A relay device holding a queued packet addressed to a
`selfDeviceId` has no way to look up "which of my known links gets this
closer to that identity" — `computeRoute()` structurally cannot succeed
for such a packet.

**This is currently INERT, not a live bug** — `RoutingEngine._knownLinks`
is empty on every real device today (confirmed in
`link_quality_feed.dart`'s own header comment: no production populator
exists yet), so `computeRoute()` already always returns `null` for every
packet, identity-addressed or not. This task's own gap has zero
additional real-world effect until that separate, already-known
limitation is resolved. This is filed now, while the shape of the gap is
fresh and well-understood, rather than left as a note that the next
person to build the link-quality feed would have no reason to connect to
an addressing fix three epics back (`L-process-008`'s own pattern — a
cross-task seam owned by no task is exactly how a real gap sits
unaddressed across many tasks).

## What this task does
1. **Confirm the current inert state stays true** at the time this task
   is actually picked up — re-check `RoutingEngine._knownLinks`'s real
   population state and `link_quality_feed.dart`'s own status; if a
   feed has landed in the meantime, this task's own urgency changes and
   that should be reflected in a fresh priority read, not assumed away.
2. **Design a reconciliation**, presenting it as a rule-3 foundational
   choice with trade-offs to a human before implementing (per the
   reviewer's own note: "fixing it needs either the reverse lookup B13
   §1a forbids... or a wire-format change"). Candidate directions, not a
   prescribed answer:
   - Extend `RoutingEngine`'s own link/route model to track BOTH a link's
     transport address AND (once learned) its resolved `selfDeviceId`,
     so `computeRoute` can resolve a `selfDeviceId`-addressed destination
     to a next-hop link without needing a raw reverse lookup on the
     `Relationships` table (`E04-B13`'s own security precondition was
     specifically about that table, not necessarily about `RoutingEngine`
     maintaining its own, separately-scoped mapping fed by the SAME
     already-authenticated announce mechanism `E04-B12` built — but
     confirm this reasoning holds before assuming it's automatically
     safe, since it is still fundamentally a reverse-direction lookup and
     deserves the same scrutiny `E04-B13`'s own security review gave the
     forward direction).
   - A wire-format change carrying BOTH the resolved identity and a
     next-hop transport hint in a relayed frame's own header, so an
     intermediate relay never needs to resolve anything itself — it just
     reads the hint. Real scope: touches `RelayPacketFrame`'s own wire
     format, a rule-3 concern in its own right (format changes affect
     every device running an older build).
   - Something else this task's own implementer identifies once actually
     investigating the current `RoutingEngine`/`RelayEngine` code in
     detail — the two candidates above are starting points, not the only
     two real options.
3. Implement the human-chosen direction, with a test proving a multi-hop
   relay scenario (three simulated nodes, A→B→C, B relaying) can actually
   route once `RoutingEngine._knownLinks` is populated (even if by a test
   double, since the real link-quality feed may not exist yet at
   implementation time).

## What this task does NOT do
- Does NOT build the link-quality feed itself (`RoutingEngine.
  _knownLinks`'s real production populator) — that is separate,
  already-known, already-tracked work this task's own dependency should
  point to once that work is itself filed/found.
- Does NOT touch `E04-B12`/`E04-B13`/`E04-B14`/`E04-B15`'s own already-
  merged, already-reviewed single-hop fixes — this task is additive,
  fixing the multi-hop case those tasks correctly left alone (per their
  own explicit scope fences).
- Does NOT re-litigate `E04-B13`'s own forward-only security constraint
  without a fresh, explicit human decision — if this task's own design
  requires something reverse-lookup-shaped, that is exactly the kind of
  foundational call that needs to go back to a human with trade-offs, not
  be decided unilaterally by whoever implements this task.
