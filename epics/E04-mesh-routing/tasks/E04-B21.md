# E04-B21 · Stop `resolveDeviceId` from baking in this device's own masked address as a peer's identity

## 1. Goal

Harden `BluetoothTransport.kt`'s `resolveDeviceId` (and its `acceptLoop`
caller, the path this was live-confirmed through) so that a resolved
device id is never allowed to equal this device's own reported Bluetooth
address. This closes the specific mechanism by which the live-reported
"still i can not send any messages" symptom (after E04-B17/B18/B19 had
already fixed the transport handshake and the decrypt bug) turned out to
have a third, genuinely separate cause: not every failure was a decrypt
or handshake problem -- some conversations were keyed by an address that
was never dialable in the first place.

## 2. Background

Confirmed live on a Redmi (MIUI) device, 2026-09-13, via `dumpsys
bluetooth_manager` bond-state history: a real `createBond()` attempt
against `00:00:46:00:00:01` (this device's own masked address, per
`Settings.Secure.bluetooth_address`) went `BOND_STATE_BONDING` ->
`BOND_STATE_NONE` after ~35 seconds -- a genuine OS-level bonding failure
against a non-existent physical device, not a code exception or a
transient link issue. A separate, correctly-bonded relationship for the
same physical peer (Pixel, real MAC `B8:DB:38:7C:D4:BF`) exists in
parallel and shows real `BluetoothSocket` native activity when used --
proving the fix target is specifically the self-referential-address
conversation, not a general transport regression.

`BluetoothTransport.kt` already carried its own E04-B17-era comment
documenting the underlying MIUI behaviour ("MIUI reports a fixed
placeholder for an ACCEPTED connection's remote address, the same
placeholder it reports for its OWN local adapter identity") but had not
yet acted on it -- `resolveDeviceId`'s bonded-name-matching mitigation
only handles the "wrong name" ambiguity (E04-B08), not the "this is
literally my own address" case.

## 3. What this task does

- **Round 1 (superseded, see §Review):** originally added
  `unmaskIfSelfReferential`, comparing a resolved id against
  `adapter?.address` and applied inside the shared `resolveDeviceId`
  (both call sites). Review round 1 (`claude-opus-5`) found this
  compares against the wrong value in practice -- `BluetoothAdapter
  .getAddress()` returns the OS-hardened constant `02:00:00:00:00:00` to
  any app without the signature\|privileged `LOCAL_MAC_ADDRESS`
  permission (which this app does not hold, confirmed by grep), not the
  OEM-masked value (`00:00:46:00:00:01`) actually observed live -- so the
  guard would never have fired against the confirmed bug. It also
  over-applied the "peer must be bonded" reasoning to the discovery-scan
  call site, which has no such guarantee (F2).
- **Round 2 (current):** dropped the `adapter?.address` dependency
  entirely. `unmaskIfNotBonded(candidate)` instead checks bonded-set
  MEMBERSHIP (`isBonded(candidate)`, an existing helper already used
  elsewhere in this file) -- correct regardless of which placeholder
  shape any given OEM's stack reports, since it doesn't need to know the
  specific masked value at all. Applied ONLY at the `acceptLoop` call
  site (`resolveDeviceId(...).let { unmaskIfNotBonded(it) }`), the one
  place the "the real peer must already be bonded" invariant is actually
  guaranteed (this app's socket variants are both the secure flavor,
  which the platform only completes for an already-bonded pair -- see
  this file's own header and the `remoteBonded` assertion already
  present in `acceptLoop`). When the resolved id is not bonded and there
  is EXACTLY ONE bonded device to fall back to (unambiguous), that
  device's real address is used instead; any other case (candidate
  already bonded, zero bonded devices, more than one) leaves the
  candidate unchanged.
- The discovery-scan (`connect()`) call site is deliberately left
  untouched -- it has no bonded-peer guarantee, so this guard must not
  apply there (see `resolveDeviceId`'s own updated doc comment).

## 4. What this task does NOT do

- Does NOT remediate the conversation/relationship ALREADY stuck on the
  user's live Redmi device (keyed by the placeholder address before this
  fix existed) -- this task prevents the defect for NEW pairings going
  forward only. The already-stuck row is a one-off live-data fix, handled
  directly against that device's own database outside the code change
  (see Run log for what was actually done to it), not a general in-app
  feature -- building a full delete-conversation UI feature was judged
  out of scope for this bug fix (review round 1 endorsed this scoping:
  a heuristic-driven data-destructive migration shipping to every user
  to fix one row on one handset is riskier than the bug).
- Does NOT change the bonded-name-matching mitigation (E04-B08) for the
  "two same-named bonded devices" ambiguity -- untouched, still a known,
  documented, separate limitation.
- Does NOT apply the accept-path bonded-membership guard to the
  discovery-scan path -- that path has no bonded-peer guarantee, and
  review round 1 (F2) confirmed applying it there could produce a false
  "bonded peer nearby" discovery event for an unrelated, never-connected
  stranger whose randomized scan address happens to collide.
- Does NOT add a Kotlin unit-test harness for this file -- none exists in
  this project (`android/app/build.gradle.kts` has no JUnit/Robolectric
  dependency), consistent with E04-B17/E04-B19's own precedent of
  live-hardware verification for this native transport layer rather than
  mocked Android framework classes (`BluetoothAdapter`/`BluetoothDevice`
  are final, effectively unmockable without Robolectric).

## Review

### Round 1 -- `claude-opus-5`, independent review of PR #252 -- CHANGES REQUESTED

- **F1 (blocking):** the guard's entire trigger condition
  (`candidate == adapter?.address`) was unverifiable and, on real
  hardware, almost certainly false even on the exact device the bug was
  found on: `BluetoothAdapter.getAddress()` returns the OS-hardened
  constant `02:00:00:00:00:00` for any app without the
  signature\|privileged `LOCAL_MAC_ADDRESS` permission (confirmed absent
  from this app's manifest by grep) -- not the OEM-masked value
  (`00:00:46:00:00:01`) the task file's own repro actually observed via
  `Settings.Secure.bluetooth_address`. The task file's repro incorrectly
  conflated these two different APIs as interchangeable. Net effect: the
  round-1 fix was a no-op against the confirmed defect.
  **Fixed:** dropped the `adapter?.address` comparison entirely; the
  round-2 guard (`unmaskIfNotBonded`) instead checks bonded-set
  membership via the existing `isBonded` helper, which is correct
  regardless of what specific placeholder value any OEM's stack reports.
- **F2 (non-blocking but real):** the round-1 doc comment claimed the
  "peer must be bonded" precondition for BOTH call sites of
  `resolveDeviceId`, but only the `acceptLoop` (accept) path actually has
  that guarantee -- the discovery-scan path does not, and applying the
  guard there could rewrite an unrelated stranger's randomized scan
  address into a false "bonded peer nearby" discovery event if it ever
  collided.
  **Fixed:** the guard is no longer inside the shared `resolveDeviceId`
  at all -- it is applied only at the `acceptLoop` call site, where the
  bonded guarantee is real, and `resolveDeviceId`'s own doc comment now
  explicitly states why the discovery-scan path must not use it.
- Reviewer confirmed as sound and unchanged by the fix: null/throw edge
  handling (adapter null, `SecurityException`, empty/absent bonded list
  all fail safe to the pre-guard value), both call sites' coverage
  (re-verified after the redesign: `acceptLoop` now explicitly calls the
  new guard; the discovery-scan path deliberately does not), the §4
  scope-out of live-data remediation, and the "no Kotlin test harness in
  this project" framing (not counted against this PR).
- Two nits accepted: task file `status` should track review state (fixed
  above), and the Run log should record what happens to the
  already-stuck row (tracked as `OQ-E04-B21-2` until performed).

### Round 2 -- `claude-opus-5`, re-review of the F1/F2 fixes -- APPROVE WITH NITS

Independently reproduced (isolated worktree, not the shared tree):
`flutter build apk --debug` succeeds; `flutter test` -- 1539 tests, all
green (regression assurance; no Dart file is in this diff).

- **F1 confirmed resolved.** `unmaskIfNotBonded` is value-agnostic
  (bonded-set membership via the existing `isBonded` helper), catching
  `00:00:46:00:00:01`, `02:00:00:00:00:00`, or any other OEM placeholder
  identically, since none of them are ever in `bondedDevices`.
- **F2 confirmed resolved.** The discovery-scan call site's diff against
  `development` is 100% doc-comment; its body, and its call to
  `resolveDeviceId` alone (no `unmaskIfNotBonded`), are unchanged.
- **N1 (non-blocking, follow-up filed as `E04-B22`):** `bondedDevices`
  is EVERY bonded device (headphones, watch, car kit, etc.), not just
  Nexora peers -- a phone bonded to more than one non-Nexora device
  alongside the real peer has `size != 2` fail the "exactly one" check,
  and this fix no-ops for that (common) case. Narrows the fix to closing
  the reported instance, not the whole class.
- **N2 (non-blocking, logged below and in the epic tracker):** the
  fix's correctness rests entirely on "an accepted secure socket ⇒ the
  remote is already bonded." If that invariant ever breaks (an OEM
  quirk, a future socket-variant change), the guard would substitute an
  actually-unbonded stranger's id with the single bonded peer's real
  address, which then reads as `bonded = true` on the Dart side --
  same shape as this project's known `frame.source`-trust pattern.
  Contained in practice (Signal-layer decrypt still fails for a
  non-genuine peer; Dart-side reconciliation additionally requires an
  exact name match, exactly one candidate, and no existing row) -- not a
  merge blocker, but recorded as a carried-forward observation.
- **N3/N4 (cheap, fixed):** the PR body described the superseded round-1
  design; rewritten before merge. This task file's own `repro:` block
  still asserted `Settings.Secure.bluetooth_address`/`adapter?.address`
  were interchangeable -- the exact F1 error -- corrected with an
  explicit note pointing at §3 Round 2.
- Explicitly confirmed: reviewer independently reproduced the build +
  full test suite rather than taking the builder's report on faith; the
  "no Kotlin test harness" framing was reconfirmed adequate and not
  counted against this PR (same E04-B17/E04-B19 precedent).
- Reviewer's closing note, carried forward here rather than dropped:
  merging this task should NOT be read as fully closing the "still
  cannot send any messages" report end-to-end -- N1 means the fix is
  reasoned-correct but inert on any handset bonded to more than one
  device, and `OQ-E04-B21-1` (no live re-repro yet) still stands.
