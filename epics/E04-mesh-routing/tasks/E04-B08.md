# E04-B08 · Real device-to-device Bluetooth connection still fails end to end on fresh hardware

## The defect
With E04-B04/B06/B07 all merged (accept loop, connection-subscription
seeding, discovery broadcast fix), a real message send between two physical,
freshly-identified devices still fails at the Bluetooth Classic layer with
`status = Page Timeout` (`dumpsys bluetooth_manager`'s Connection Events),
confirmed on 2026-09-08 with a Redmi 10 2022 and a Pixel 8 Pro.

Two root causes, both already flagged as carried-forward observations with
no owner (`E04-B04.md` §Carried-forward #2, `E04-B06.md`'s equivalent),
plus a third, newly confirmed today:

1. **The app never makes itself Bluetooth-discoverable.** `grep -r
   "setScanMode\|ACTION_REQUEST_DISCOVERABLE\|createBond\|BOND_STATE" android/`
   returns zero hits. An idle device running the app answers no inquiry and
   opens no server socket outside an active `connect()`/discovery call.
2. **The app never bonds a peer at the OS level**, and both ends use the
   *secure* RFCOMM variants (`createRfcommSocketToServiceRecord`,
   `listenUsingRfcommWithServiceRecord`) — even once paging succeeds,
   first contact with an unbonded peer needs the OS pairing dialog accepted
   on both phones, with no prompt shown and no `BOND_STATE_CHANGED`
   observation anywhere in the app.
3. **(New, 2026-09-08) The app's own logical peer-device identity does not
   reliably correspond to the peer's real, connectable Bluetooth MAC.**
   Manually OS-bonding the two phones via Android Settings (`dumpsys
   bluetooth_manager` confirmed `B8:DB:38:7C:D4:BF [ DUAL ] SRPhone P8` newly
   bonded, `status = Success`) had **zero effect** on the app's own connect
   attempt — the very next send still timed out paging a **different**
   address, `3d:66:3d:63:21:de`, which appears nowhere else in
   `dumpsys bluetooth_manager` (never discovered, never bonded, no other
   connection event) — i.e. not a real, reachable radio at all. The app's
   own "Network Nodes" list had shown this same string as the peer's
   identity moments earlier, `Allowed`, `Last seen: Just now`. Whatever the
   app is passing to `BluetoothAdapter.getRemoteDevice(...)` in
   `BluetoothTransport.kt:334-335` for this peer is not the address a real
   OS-level pairing/connect can reach.

## Repro
1. Two physical Android devices, current `development`, both signing in
   fresh (no prior local identity).
2. Trust each other via the app's own Discover → Verify flow.
3. Send a message from either side.
4. `adb -s <id> shell dumpsys bluetooth_manager` → Connection Events shows
   `status = Page Timeout` for the peer's app-shown identity.
5. Manually OS-pair the two physical devices via Android Settings ⇒
   Bluetooth (confirms a real, different MAC bonds successfully) → retry
   the same send in-app → still `Page Timeout`, still against the
   originally-shown (unbonded, unreachable) identity string.

## Expected
FR-DISC-001 (derived — not yet a numbered SRS id at time of filing; confirm

## Actual

## Severity

this working. Not S1 only because a workaround exists today (manually pair
via OS Settings) that gets *closer* but, per finding 3, does not yet fully
resolve it either.

## Fix direction — do NOT attempt blind; diagnose in order first

**Diagnostic pass completed 2026-09-08 (code-reading only, no changes) —
ruled out the app-level identity model as the cause:**
- `BluetoothTransport.kt`'s `handleDeviceFound` (:623-647) takes
  `device.address` directly from a genuine `ACTION_FOUND` intent and emits
  it unchanged as `TransportDevice.id`; `connect()` (:317-354) passes that
  exact same string straight into `bt.getRemoteDevice()` — no
  re-derivation, no alias table, no multi-session cache
  (`discoveredAddresses` is cleared at the top of every `startDiscovery()`,
  :585).
- This device's own self-identity (`generateSecureDeviceId()`,
  `lib/features/login/presentation/login_controller.dart:91-94`) is a
  32-hex-char string with **no colons** — structurally incapable of
  producing the colon-grouped, MAC-shaped string
  (`3D:66:3D:63:21:DE`) the Devices screen displayed. No MAC-formatting
  helper exists anywhere in `lib/` (grepped) that could be reformatting a
  different id to look like one.
- **Conclusion: the app's own code is not introducing this mismatch.** The
  colon-formatted peer identity is a real, unmodified
  `BluetoothDevice.getAddress()` string, threaded through unchanged from
  native discovery to the Dart-side connect call. The mismatch happens
  *before* the app ever sees the address — most consistent with a known
  MIUI/Xiaomi behavior of returning a different (or stale/privacy) address
  on Classic discovery scan results than the device's real, bondable BR/EDR
  address. Needs on-device confirmation, not more code reading, to close.

1. **First on-device diagnostic, before writing any fix:** with the two
   phones already OS-paired via Settings, run `startDiscovery()` again and
   compare the freshly-discovered address against
   `BluetoothAdapter.getBondedDevices()`'s real, just-bonded entry. If they
   still differ, this is confirmed as an OS/OEM Bluetooth-stack quirk (not
   an app bug), and the realistic fix is: once a device is OS-bonded,
   prefer connecting via a `getBondedDevices()` lookup rather than trusting
   the raw address from a `startDiscovery()` scan result.

   **✅ CONFIRMED 2026-09-11, on real hardware (Redmi 10 2022 + Pixel 8
   Pro, both connected via adb, physically present).** Ran this exact
   diagnostic:
   - `adb -s <pixel> shell settings get secure bluetooth_address` →
     `B8:DB:38:7C:D4:BF` — the Pixel's own, real, stable adapter address.
   - `adb -s <redmi> shell dumpsys bluetooth_manager` confirmed
     `B8:DB:38:7C:D4:BF` as an already-bonded device
     (`BOND_STATE_BONDED`), listed under `Bonded devices:` as
     `[ DUAL ] SRPhone P8` — matches exactly.
   - Opened Nexora on the Redmi, navigated to the Devices screen, tapped
     **Discover** to trigger a fresh `startDiscovery()` call (confirmed
     via `logcat`: `BluetoothAdapterService: startDiscovery` fired at the
     tap). Waited the full ~12s scan window.
   - **Result: a THIRD, brand-new address appeared —
     `35:05:C1:71:3C:41`** — added to the Devices screen as a new
     "Paired locally" entry, flagged `⚠ Unknown` (unverified), distinct
     from both the previous session's stale discovered address
     (`3D:66:3D:63:21:DE`) and the real bonded address
     (`B8:DB:38:7C:D4:BF`). Different OUI vendor prefix from all of them.
   - **Further corroboration:** the Redmi's own reported local address
     (`adb shell settings get secure bluetooth_address`) is
     `00:00:46:00:00:01` — not a real hardware MAC either. MIUI is
     systematically obscuring/randomizing Bluetooth Classic addresses on
     both the local-adapter-identity side and the discovery-scan-result
     side.
   - **Conclusion: this is definitively an OS/OEM (MIUI/Xiaomi) Bluetooth
     Classic address-randomization quirk, not an app bug, and not
     resolvable by any change to this app's own discovery/connect
     code path as currently structured.** A fresh discovery scan's
     reported address for the *same, already-bonded* physical peer is
     not merely stale — it is a **different random value every scan**,
     with zero stable relationship to the real, bondable address. The
     realistic fix direction stands and is now confirmed necessary: once
     a peer is OS-bonded, the app must connect via a
     `BluetoothAdapter.getBondedDevices()` lookup (matched some other
     way — see Open Question below, since the discovery address itself
     cannot be used to recognize "this is the same bonded peer" either)
     rather than trusting any address a `startDiscovery()` scan result
     carries.
   - **New open question this raises, not previously anticipated:** if
     the discovery-scan address is randomized per-scan and bears no
     relationship to the bonded address, **the app also cannot use the
     discovered address to decide *which* bonded device a discovery
     result corresponds to** — `ACTION_FOUND`'s `EXTRA_NAME` (the
     device's Bluetooth-visible name, e.g. `SRPhone P8` above) may be
     the only correlator available pre-bond, which is weaker (names can
     collide or be blank) than an address match. This needs to be part
     of the scoped fix, not discovered again during implementation.
2. Once the identity-mapping question is answered, the remaining two gaps
   (discoverability, bonding) need one human/rule-3 decision each:
   - Add `ACTION_REQUEST_DISCOVERABLE` (time-boxed, user-visible) or a
     continuous listen-only scan mode — a product/battery tradeoff, not
     purely technical.
   - Add an explicit `createBond()` + `BOND_STATE_CHANGED` path with a
     visible pairing prompt, **or** document that manual OS pairing is a
     required precondition, **or** switch to insecure RFCOMM variants (the
     app's own E2EE makes link-layer security non-load-bearing, but that
     is a rule-3 call, not the fixer's to make silently).

## The identity-mapping fix itself
1. Confirmed in `## Fix direction` above: `startDiscovery()`'s
   `ACTION_FOUND` results carry a MIUI-randomized address with **no
   stable relationship** to the peer's real, bondable BR/EDR address —
   not merely stale, a *different* random value on every scan, even for
   an already-bonded peer.
2. Also confirmed: the discovered address therefore cannot be used to
   recognize *which* bonded device (if any) a discovery result
   corresponds to either. The only pre-bond correlator available in the
   `ACTION_FOUND` intent is the peer's Bluetooth-visible name
   (`BluetoothDevice.name`, already read into `handleDeviceFound`'s
   `name` local) — weaker than an address match (names can collide or
   be blank), but the only one that exists.
3. **The fix:** in `handleDeviceFound` (`BluetoothTransport.kt:623-647`),
   before emitting `onDeviceDiscovered`, check
   `adapter?.bondedDevices` for an entry whose `name` matches this
   scan result's `name` (both non-null, exact match). If found, emit
   the **bonded device's own real address** as `TransportDevice.id`
   (not the randomized `device.address` from this scan) — so a later
   `connect(deviceId)` call passes a real, connectable, stable address
   to `getRemoteDevice()`/`createRfcommSocketToServiceRecord()`. If no
   bonded match exists (a genuinely new, not-yet-paired peer), fall
   back to emitting the raw scanned address exactly as today — that
   peer isn't bonded yet, so there is no better address available, and
   `E04-B09`'s bonding flow is what will eventually fix that case.
4. **Required regression test** (native, or as close as this codebase's
   existing Bluetooth test seams get — check for an existing fake/mock
   `BluetoothAdapter` test harness for `BluetoothTransport.kt` first):
   prove that a discovery result whose `name` matches a bonded device's
   name emits the BONDED address, not the raw scanned one; and that a
   discovery result with no bonded-name match still emits the raw
   scanned address unchanged (the existing behavior, for the genuinely
   new-peer case). Falsify: temporarily revert to always emitting the
   raw address and confirm the new test fails.
5. **On-device verification, not just a unit test** (this bug was only
   ever reproducible on real hardware): with the two already-bonded
   physical devices, rebuild and reinstall the app on both, run the
   same Devices → Discover flow from the earlier diagnostic, and
   confirm the app now shows/uses `B8:DB:38:7C:D4:BF` (the Pixel's real
   bonded address) rather than a fresh random address for the
   already-bonded peer. If real hardware is available when this task is
   picked up, attempt an actual end-to-end message send between the two
   devices — this is the first real chance this whole bug-chain has had
   to prove messaging actually works between two real, distinct
   installs.

- Does **NOT** retune any `RouteCostCalculator` weight.
- Does **NOT** touch the Dart-side connection-subscription/accept-loop

## Open Questions
- **`OQ-E04-B08-1` — bonded-name-match path not independently confirmed

  hands directly on both devices (placed a few cm apart, screens on,
  Pixel's Bluetooth settings page left open so its own discoverable timer

  could set discoverable mode and trigger scans correctly but could not

  `firstInstallTime`/`lastUpdateTime`, app data reset), Pixel returned to
  its Bluetooth Settings screen (confirmed "Visible as 'SRPhone P8' to

  58:81:61:B0:4F:CB/HOCO ES64 Ultra]`, i.e. `resolveDeviceId`'s bonded-list
  read and name-comparison logic runs correctly on live, real hardware.**
  But across all 4 cycles, `ACTION_FOUND` never once fired for a peer
  named `SRPhone P8` — only two other, unrelated real nearby devices were
  ever reported (one unnamed, one named `SRPPC3` — this machine's own
  Bluetooth adapter), both correctly falling through to the unchanged
  raw-address path (consistent with the earlier confirmed fallback
  behavior). **Working hypothesis, not yet proven: an already-bonded
  Android device may simply not respond to a generic BR/EDR inquiry scan
  under normal conditions** (many modern stacks reserve inquiry-scan
  response for not-yet-bonded pairing scenarios, and rely on the
  connecting side already holding the bonded address for reconnection —
  which would make the original 2026-09-08 repro, where `SRPhone P8`
  *did* briefly appear under a wrong address via discovery, a
  transient, pairing-adjacent state rather than steady-state behavior).
  If that hypothesis holds, the practical rate at which this fix's
  positive branch ever fires for an already-bonded peer may be low — but
  the fix remains correct and strictly defensive either way: it changes
  nothing for a peer with no bonded-name match (the overwhelmingly common
  case, confirmed unchanged across every cycle run today), and correctly
  resolves the rarer case when a bonded peer's name does appear in a scan
  result. Not blocking merge; carried forward as a real open question
  about how often the positive branch matters in practice, for whoever
  next touches Bluetooth discovery/bonding (`E04-B09`is the obvious
  next reader, since its own bonding-flow work will interact directly
  with this exact bonded/unbonded distinction).
