# E04-B32 · Break the simultaneous-connect deadlock

## 1. Root cause

`MessagingCoordinator` retries queued packets on a fixed `Timer.periodic` tick (60 s) with no jitter. Two phones started close together tick almost in step. When both have a packet for the other, both call `BluetoothTransport.connect` → `doConnect` within about a second. Both open an RFCOMM multiplexer to the same peer at once. The Bluetooth stack resolves the multiplexer collision by rejecting one side's incoming session, which tears down both in-flight channel setups. Both `socket.connect()` calls throw `IOException`. `doConnect` treats that as terminal, and the next tick reproduces the same collision.

Earlier sends worked because only one side had anything queued, so there was no competing outbound attempt.

## 2. Fix

`doConnect` retries a failed `socket.connect()` up to `CONNECT_COLLISION_MAX_ATTEMPTS` times. Before each retry it sleeps for a **random** delay between `CONNECT_COLLISION_RETRY_MIN_MS` and `CONNECT_COLLISION_RETRY_MAX_MS`, so the two sides fall out of step. Other behavior:

- A failed socket is always closed before retrying.
- Before each retry and before emitting FAILED, it checks `openSockets`. If the peer's own attempt already arrived through `acceptLoop` (which registers it there), the attempt stops and emits CONNECTED for that accepted socket instead of dialing again (the same reuse contract as E04-B17's idempotent `connect()`).
- `SecurityException` and `IllegalArgumentException` stay immediately terminal, because waiting does not fix them.
- The randomness lives on the native side, so no Dart timing contract (`tickInterval`, E10-T10's `setTickInterval`) changes.

## What this task does NOT do

- Does not add jitter to `MessagingCoordinator`'s tick or change its interval.
- Does not add a deterministic address tie-break. Addresses are masked on some devices (the Redmi appears to the Pixel as `00:00:46:00:00:01`), so the two sides cannot reliably agree on who is "higher".
- Does not change `doConnectAfterBond`'s own retry loop or E04-B29's bond backoff.
- Does not add a Kotlin test harness (none exists in this project).

## Open Questions

- OQ-E04-B32-1: three attempts with 0.3–1.5 s random spacing makes a repeat collision unlikely but not impossible. If one still happens, the next coordinator tick retries. A later task could also jitter the coordinator tick itself if live data shows collisions persisting.
- OQ-E04-B32-2 (review nit, S3): the retry applies to every `IOException`, not only a collision. For a genuinely unreachable peer whose `socket.connect()` blocks for its full page timeout, three attempts can exceed `ConnectionEnsuringSender`'s 30 s connect timeout (`connection_ensuring_sender.dart:107`). Dart then gives up while the native thread keeps trying and may emit a late event. Worst outcome is a stray late CONNECTED/FAILED, not lost data. Candidate follow-up: cap the retry by elapsed time.
- OQ-E04-B32-3 (review, pre-existing, unchanged by this diff): a successful outbound connect writes `openSockets[deviceId]` without closing a socket `acceptLoop` may have registered for the same id a moment earlier. This fix narrows the window (failures now check for an accepted socket first) but does not close it.
