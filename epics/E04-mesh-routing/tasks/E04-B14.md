# E04-B14 · Bind bundle-response provenance to the physical link, not just a claimed identity + guessable id

## How this was found
`E04-B13`'s own independent reviewer (opus), while verifying that task's
security fix, found a second, adjacent gap while checking
`PrekeyExchange._takeMatchingCompleter`'s own provenance contract (that
file's own header comment: "only a response ... from the peer it was sent
to, is accepted"). Direct quote from the review:

> `_takeMatchingCompleter` binds a response only on `requestId` + the
> unauthenticated `frame.source`, with no physical-link binding —
> `ControlHandler` (`inbound_pipeline.dart:185`) gets only the frame, while
> `E04-B12` deliberately used a SEPARATE signature carrying `linkDeviceId`
> for its own announce handler. And `requestId` is guessable by
> construction (`'${selfDeviceId}-pkx-$counter'`,
> `prekey_exchange.dart:431`). Before this PR that check was
> unsatisfiable on hardware — fail-closed by accident. After it, it's
> satisfiable, so a forged-`bundleResponse` injection path goes live for
> the first time.

In plain terms: before `E04-B13`, `frame.source` was always this app's
own random/key-derived `selfDeviceId`, which could never match a real
peer's claimed identity anyway (the exact bug `E04-B11`→`E04-B13` fixed),
so this particular check happened to never pass — a real gap that was
accidentally masked by a different, now-fixed bug. Now that addressing is
correct, this check is REACHABLE: a device that can get bytes onto this
device's transport layer at all (a bonded peer, or potentially a relay
hop, depending on how far the mesh's own trust boundary is meant to
extend) could craft a `bundleResponse` claiming a guessable `requestId`
and an arbitrary `frame.source`, and have it accepted as if it were the
genuine response to THIS device's own pending `ensureSession` request —
potentially completing a Signal Protocol session establishment against a
bundle that did not actually come from the intended peer.

**This is the same class of risk already confirmed as a real S1 finding
in `E09-B09`** (`frame.source` trust exploit — decrypt succeeds via TOFU,
claimed address gets trusted as identity) — same root cause
(`frame.source` treated as authoritative without further binding),
different call site.

## What this task does
1. **Root-cause exactly how far this can go** before designing a fix —
   confirm precisely what `establishSession` does with a bundle accepted
   this way (does TOFU trust bind to the FIRST identity key seen, same
   shape as `E09-B09`'s own confirmed exploit? or does something else
   downstream still catch a mismatch?). Do not assume the impact without
   verifying it against the actual `CryptoService`/`DriftSignalProtocolStore`
   code.
2. **Bind `_takeMatchingCompleter`'s acceptance to the physical link the
   response arrived on**, not just the claimed `frame.source` — mirror
   `E04-B12`'s own `IdentityAnnounceService` pattern, which already
   carries a `linkDeviceId` (the Bluetooth-address-keyed connection
   identity, independently known to the receiver regardless of what the
   frame claims) through a separate handler signature for exactly this
   reason. `InboundPipeline`'s own `ControlHandler` seam may need widening
   to carry that same `linkDeviceId` to every registered handler, not just
   the identity-announce one — check whether that's a clean, additive
   change or whether it has wider blast radius across
   `DeliveryAckService`/`GroupMembershipService`/etc., and disclose either
   way.
3. **Make `requestId` unguessable**, not just correctly bound to a link —
   the current `'${selfDeviceId}-pkx-$counter'` scheme is a real,
   independent weakness even after point 2 lands (a link-bound check still
   needs the id itself to not be trivially predictable by anything sharing
   that link). A cryptographically random component is the obvious fix;
   confirm it doesn't break `_outstandingRequests`' own map semantics.
4. Write a test that specifically proves a forged `bundleResponse` (right
   `requestId`, wrong actual originating link) is now rejected.

## What this task does NOT do
- Does NOT re-open or weaken `E04-B13`'s own addressing fix — this task
  adds a stricter check on top, it doesn't touch how `destination` gets
  resolved.
- Does NOT attempt to fully re-architect trust/provenance across every
  control protocol in one pass — if point 2's `ControlHandler` widening
  turns out to have real blast radius across other handlers, that's this
  task's own scope to absorb (it's the direct fix), but do not use this
  task to fix `E09-B09`'s own already-tracked, separate call sites, or
  `E04-B15`'s own separate raw-MAC-addressing gaps in sibling protocols.

## Definition of Done
- [x] Impact confirmed against actual `CryptoService`/session-establishment
  code (not assumed). `CryptoService.establishSession`
  (`crypto_stub.dart:73-86`) wraps `SessionBuilder.processPreKeyBundle`,
  which delegates trust to `DriftSignalProtocolStore.isTrustedIdentity`
  (`drift_signal_store.dart:139-150`): `previous == null` returns `true`
  unconditionally — textbook trust-on-first-use. `ensureSession`'s own
  `containsSession` early-return (`prekey_exchange.dart:475-477`) means
  `establishSession` is reached ONLY when no session yet exists for that
  peer address, which is exactly the case `isTrustedIdentity` has no prior
  identity to compare against. **Confirmed: a forged bundle accepted via
  the pre-fix provenance gap would have been trusted outright as that
  peer's permanent identity** — the identical TOFU shape already confirmed
  as a real S1 in `E09-B09`, not a different or lesser risk class.
- [x] `_takeMatchingCompleter` (or its replacement) binds acceptance to
  the physical link a response arrived on. `prekey_exchange.dart`'s
  `_OutstandingRequest` now stores `linkDeviceId` (the raw physical link
  the outbound request left on); `_takeMatchingCompleter` requires an
  accepted response's actual arrival link to match it, in addition to the
  pre-existing `peerDeviceId`/`frame.source` check. `linkDeviceId` is
  plumbed from `InboundPipeline` via a NEW dedicated registration slot
  (`PrekeyExchangeHandler`/`registerPrekeyExchangeHandler`,
  `inbound_pipeline.dart`) mirroring the already-established
  `IdentityAnnounceHandler` pattern, rather than widening the shared
  `ControlHandler` typedef — see Deviations for why, and for the blast-
  radius check this avoided.
- [x] `requestId` is cryptographically unguessable. `_nextRequestId`
  (`prekey_exchange.dart`) now appends a 128-bit `Random.secure()` suffix;
  the monotonic counter is kept alongside it only to guarantee
  `_outstandingRequests`' own "unique per outstanding request" map
  semantics with certainty, not as part of the unguessability property.
- [x] A test proves a forged response (right id, wrong link) is rejected.
  `test_E04_B14_forged_bundle_response_on_wrong_link_is_rejected`
  (`prekey_exchange_test.dart`) — forges a `bundleResponse` with the REAL,
  captured `requestId` and a claimed `frame.source` that already passes
  the pre-existing E04-B13 check, delivered on a different physical link
  than the one the real request went out on; asserts no session is
  established, `responsesAccepted == 0`, and the real outstanding request
  still times out honestly rather than silently completing via the
  forgery.
- [x] Existing test suite green. `flutter test`: 1513/1513 passing.
  `flutter analyze`: 0 issues (2 pre-existing, unrelated infos — the same
  two E04-B13's own review already disclosed).

## Deviations
- **Did NOT widen the shared `ControlHandler` typedef.** The task file's
  own §2 anticipated this might be needed to carry `linkDeviceId` to
  "every registered handler, not just the identity-announce one," and
  asked to check the blast radius and disclose either way. Checked: five
  OTHER control sub-protocols share `ControlHandler`
  (`DeliveryAckService.handleControlFrame`,
  `GroupMembershipService.handleWireFrame`,
  `GroupCryptoService.handleWireFrame`, `CallSignaling.handleWireFrame`,
  `LocationShareService.handleWireFrame`), each in its own file, all five
  outside this task's `files:` fence — widening the typedef itself would
  have forced editing all five just to keep them compiling, a real,
  large blast radius extending outside this task's own scope, exactly the
  condition the task file names as a reason to stop rather than force a
  fix. **Avoided it entirely**: `PrekeyExchange` gets its OWN dedicated
  registration slot on `InboundPipeline`
  (`PrekeyExchangeHandler`/`registerPrekeyExchangeHandler`), mirroring the
  already-established `IdentityAnnounceHandler` precedent (E04-B12) —
  zero changes to `ControlHandler` or to any of the five other files;
  `inbound_pipeline.dart`'s own dispatch for `kControlKindPrekeyExchange`
  is checked before the generic `_controlHandlers` map is ever consulted,
  so the two mechanisms never conflict.
- **`PrekeyExchange` self-registers from its own constructor**, rather
  than via an external call in `messaging_stack.dart` (the pattern every
  other control sub-protocol, including the pre-existing
  `kControlKindPrekeyExchange` registration, uses). This task's `files:`
  fence does not include `messaging_stack.dart`, so there is no external
  composition-root call site available — the identical constraint,
  reasoning, and resolution E07-T06 already established and documented in
  `inbound_pipeline.dart`'s own header for its group-message handler.
  `messaging_stack.dart`'s pre-existing
  `inbound.registerControlHandler(kControlKindPrekeyExchange,
  prekeyExchange.handleControlFrame)` call still runs, unmodified, but is
  now provably dead in production: `InboundPipeline._handleBuffer` routes
  `kControlKindPrekeyExchange` through the new dedicated slot before the
  generic map is ever consulted. `handleControlFrame` itself keeps its
  original `Future<void> Function(RelayPacketFrame)` signature (an
  additional named `linkDeviceId` parameter is OPTIONAL, so it stays
  assignable to `ControlHandler`) purely so that dead call site keeps
  compiling — Dart's function-subtyping rules make this safe.
- **Constructor self-registration is wrapped in a `try`/`on StateError`
  no-op**, because `test/features/chat/presentation/chat_controller_test.dart`
  already constructs a SECOND `PrekeyExchange` (`_SlowPrekeyExchange`)
  against an already-wired stack, purely to override `ensureSession` for
  timing control — that file's own pre-existing doc comment already
  documented "only the ORIGINAL, registered instance's `handleControlFrame`
  is wired to `stack.inbound`" as the intended contract for the OLD
  registration mechanism. Swallowing the resulting `StateError` keeps that
  exact, pre-existing contract true for the new mechanism too, without
  editing that test file. Production only ever constructs one
  `PrekeyExchange` per `MessagingStack` (`messaging_stack.dart`'s single
  construction site), so this catch cannot mask a real double-registration
  bug there.
- **`frame.source`'s existing check is kept, not replaced**, by the new
  link check — both must now pass. The task file's own §2 asked to bind
  acceptance to the physical link "not just" the claimed identity, which
  reads as additive; a response is now rejected if EITHER check fails.
