# E04-B33 · Bound doConnect's collision retry by elapsed time

## 1. Fix

`doConnect` records `SystemClock.elapsedRealtime()` when its thread starts. After a failed attempt it only schedules another one if the retry could still begin inside `CONNECT_RETRY_BUDGET_MS` (20 s), counting the longest possible sleep (`elapsed + CONNECT_COLLISION_RETRY_MAX_MS <= budget`). Otherwise it emits FAILED at once, as it already does after the last attempt.

- The budget is 20 s, not 30 s, so a retry started just inside the budget still has room for one short `connect()` before Dart's timeout.
- A collision (the E04-B32 case) fails within about a second, so its retries all fall well inside the budget and are unaffected.
- The existing checks for a socket the peer opened meanwhile are unchanged.

## What this task does NOT do

- Does not change `ConnectionEnsuringSender`'s 30 s timeout or any Dart code.
- Does not change `doConnectAfterBond` (E04-B09 F2) or its own retry loop.
- Does not fix OQ-E04-B32-3, where an outbound socket can overwrite a socket `acceptLoop` registered for the same id. The obvious fix, keeping the first registered socket and closing the second, is unsafe: both phones apply the rule independently, so each can keep a different one of the two links and close the other, killing both. A safe fix needs a tie-break both sides agree on, and addresses are masked on some devices (E04-B32 §NOT-do). It stays an open question.
- Does not add a Kotlin test harness (none exists in this project).

## 2. Definition of Done

- [x] `doConnect` does not start a retry that could begin after `CONNECT_RETRY_BUDGET_MS`; the collision retry itself is unchanged
