# E04-B33 · Bound doConnect's collision retry by elapsed time

## 1. Fix

`doConnect` records `SystemClock.elapsedRealtime()` when its thread starts. After a failed attempt it only schedules another one if the longest sleep plus one worst-case blocking attempt still ends by the settle deadline:

`elapsed + CONNECT_COLLISION_RETRY_MAX_MS (1.5 s) + CONNECT_ATTEMPT_MAX_BLOCK_MS (13 s) <= CONNECT_SETTLE_DEADLINE_MS (28 s)`

Otherwise it emits FAILED at once, as it already does after the last attempt.

- The margin counts the duration of the attempt being started, not just the sleep before it (review round 1, F1: the first version only checked when a retry would *start*, so a slow third `connect()` could still run past 30 s).
- The deadline is 28 s, 2 s under Dart's 30 s timeout, for event delivery.
- Worst case for an unreachable peer: attempt 1 blocks up to 13 s, then a retry is allowed only if it ends by 28 s (13 + 1.5 + 13 = 27.5 s); a third attempt is not started. The native side therefore settles by about 28 s whenever each `connect()` blocks no longer than 13 s.
- A collision (the E04-B32 case) fails within about a second, so all three attempts stay far inside the deadline and are unaffected.
- The existing checks for a socket the peer opened meanwhile are unchanged.

## What this task does NOT do

- Does not change `ConnectionEnsuringSender`'s 30 s timeout or any Dart code.
- Does not change `doConnectAfterBond` (E04-B09 F2) or its own retry loop.
- Does not fix OQ-E04-B32-3, where an outbound socket can overwrite a socket `acceptLoop` registered for the same id. The obvious fix, keeping the first registered socket and closing the second, is unsafe: both phones apply the rule independently, so each can keep a different one of the two links and close the other, killing both. A safe fix needs a tie-break both sides agree on, and addresses are masked on some devices (E04-B32 §NOT-do). It stays an open question.
- Does not add a Kotlin test harness (none exists in this project).

## Open Questions

- OQ-E04-B33-1: the guarantee holds only if a single blocking `connect()` ends within `CONNECT_ATTEMPT_MAX_BLOCK_MS` (13 s). That value is an assumption: the stack's default page timeout is 5.12 s, and failed SDP lookups on these phones took about 5 s (E04-B30), but no platform API bounds `connect()` itself. If a stack blocks longer, the last attempt can still end after Dart's timeout. The effect is unchanged from before this fix (a late CONNECTED/FAILED, no data loss).
