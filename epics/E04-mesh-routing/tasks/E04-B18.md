# E04-B18 · Every incoming message is decrypted twice against one Double Ratchet chain -- the second decrypt is structurally unsafe

## 1. Goal

Stop the app from independently re-deriving a received message's plaintext
from stored ciphertext at display time, when that ciphertext was ALREADY
consumed by a real Double Ratchet decrypt at receive time -- so a delivered
message reliably decrypts, every time, not intermittently.

## 2. Root cause (confirmed by code reading + live evidence, 2026-09-13)

**Two distinct bugs were conflated under the original `OQ-E04-B17-1`
report. This task is about the real, receiver-side one. The other (sender-
side) is understood and is NOT a crypto bug — see the callout at the end
of this section.**

The receiving path decrypts every incoming ciphertext **twice**:

1. **At receive time** — `InboundPipeline._handleBuffer` calls
   `_stack.receiveMessage.call(frame.source, ciphertextMessage)`
   (`inbound_pipeline.dart:934`), which is
   `ReceiveMessageUseCase.call` (`receive_message_use_case.dart:102-174`).
   That method calls `await _decrypt(address, ciphertext)` at line 107 —
   a REAL `CryptoService.decrypt` call, which per `crypto_stub.dart`'s own
   doc comment (`crypto_stub.dart:112-130`) performs the actual Double
   Ratchet `SessionCipher.decrypt`/`decryptFromSignal` step, consuming
   that message's key from the ratchet. The resulting `plaintext` is used
   ONLY to recover envelope metadata (`MessageEnvelope.deserialize`, line
   108) — `envelope.id`/`conversationId`/`sequenceNumber` — and then
   **discarded**. Only the raw ciphertext bytes are persisted
   (`ciphertextBytes = Uint8List.fromList(ciphertext.serialize())`, line
   149; `messages.ciphertext`, line 157). Nothing about the successfully-
   decrypted plaintext survives this call.
2. **At display time** — every single row rendered in a chat, whether just
   arrived (`watchConversation`'s stream) or loaded from history,
   goes through `ChatController._resolvePlaintext`
   (`chat_controller.dart:428-454`, called from `_bubblesFor` at line 221
   and `_renderPending` at line 243, unconditionally, for every non-
   optimistic row). That method reads the STORED ciphertext back out of
   the `messages` table and calls `_crypto.decrypt(address,
   ciphertextMessage)` again (`chat_controller.dart:442`) — a SECOND,
   independent Double Ratchet decrypt attempt on the exact same ciphertext
   bytes already consumed in step 1. The only thing standing between this
   and a guaranteed failure is `_plaintextCache`
   (`chat_controller.dart:160,429-430,452`), an in-memory
   `Map<String, String?>` scoped to ONE `ChatController` instance — it
   is wiped every time a fresh `ChatController` is created, which GetX
   does on every navigation away from and back to a chat, and always on
   app restart.

`crypto_stub.dart`'s own doc comment names the exact failure mode this
produces: `CryptoDecryptFailureReason.duplicateMessage` "on a replayed
counter" (`crypto_stub.dart:123`) — this project's own crypto layer
already anticipates and detects decrypting the same message twice. Signal
Double Ratchet decrypt is a **one-time, stateful operation**: it advances
the receiving chain and (for the exact next-expected counter, the common
case) does not retain the message key for reuse — retaining it
indefinitely would itself weaken forward secrecy. Calling `decrypt()`
twice on the same wire bytes is not a "just try again" operation the way
re-reading a file is; it is architecturally adversarial to the protocol
in the SAME way an attacker's replay would be, and the protocol correctly
tries to reject it.

**Why it's intermittent rather than 100% failing**: the live evidence (3
messages sent minutes apart, only the middle one decrypted) is consistent
with a genuine race between `ReceiveMessageUseCase`'s receive-time decrypt
(running inside the async inbound-pipeline handler) and
`ChatController`'s display-time decrypt (running whenever the chat screen
is open and `watchConversation`'s stream delivers the new row) — whichever
one's session-state write (`DriftSignalProtocolStore.storeSession`,
`drift_signal_store.dart:388`) lands second effectively "wins" and
determines whether the OTHER caller's read/decrypt sees pre- or post-
advance ratchet state. This is not a guess this task needs to resolve
further to justify a fix: **regardless of which exact interleaving
produces a given pass/fail outcome, the fix is the same** — never call
`decrypt()` twice on one message's ciphertext.

**Two distinct bugs were conflated under the original report.** The
SENDING device showing "(unable to decrypt this message)" for its OWN
sent messages (observed live 2026-09-13, ALL of one device's own sent
messages, 100% of the time, after an app restart) is a **separate,
already-understood, non-crypto issue**: `_resolvePlaintext`
(`chat_controller.dart:436-438`) correctly special-cases a self-sent row
by decrypting against `_peerDeviceId` instead of `_selfDeviceId` — but
Double Ratchet sessions are asymmetric by design, so a device can NEVER
decrypt its own outgoing ciphertext at all, ever, by any method. Before
this task's investigation, the only reason a self-sent message ever
rendered correctly was `send()`'s own direct cache seed
(`_plaintextCache[message.id] = trimmed`, `chat_controller.dart:326`) —
which is populated at send time and, like every other entry in
`_plaintextCache`, does not survive a `ChatController` recreation (a
navigation or app restart). This is a real, disclosed, but MUCH smaller
gap (no persisted local echo of a sent message's own plaintext) — it does
not need a crypto fix, only a way to re-derive or re-cache a sent
message's own plaintext across `ChatController` instances. Filed as a
follow-up note below rather than its own task, since the fix is likely
the same shape as whatever this task lands on for the receiving side
(cache plaintext somewhere that outlives one `ChatController` instance).

## 3. Why this is not fixed unilaterally in this session (rule-3 stop)

This repository has an explicit, human-endorsed security architecture
decision already on record: `notification_tables.dart:9-13` cites
`E06-T09.md:64-68` for "`full` [notification privacy] has no supported
mechanism today, because **plaintext is decrypted only in the screen
layer**" — i.e., a deliberate choice that plaintext must never be
materialized anywhere outside the chat screen's own in-memory state, so
that a background dispatcher (or any other non-screen caller) can never
get at it. **Any fix for this bug changes where and how long decrypted
plaintext is allowed to live in memory** — the core question a fix must
answer is "where does the ONE legitimate decrypt's plaintext get cached so
a later display can use it without re-decrypting, and for how long", and
every candidate answer trades off against that existing security
boundary:

- **Option A — cache the plaintext from `ReceiveMessageUseCase`'s own
  (already-happening) decrypt**, keyed by message id, in a store that
  outlives one `ChatController` (e.g. a process-lifetime singleton
  service, or threaded through the same event `InboundPipeline` already
  emits on `delivered`). `ChatController` would consume that cache instead
  of ever calling `_crypto.decrypt` itself for a received row. This keeps
  "decrypt happens exactly once, ever, per message" but widens the
  existing "screen layer only" boundary to include this new cache's
  lifetime and access surface — exactly the kind of widening the cited
  ADR-level decision would need to explicitly bless.
- **Option B — make `ChatController` the ONLY decryptor**, and have
  `ReceiveMessageUseCase` stop decrypting at receive time at all (parse
  envelope metadata some other way, or accept a slightly different
  contract). This preserves the "screen layer only" boundary exactly as
  documented, but changes `ReceiveMessageUseCase`'s own contract (it
  currently *requires* decrypting to recover `envelope.id`/
  `conversationId`/`sequenceNumber` for the dedup+ordering it does at
  receive time — task file `E05-T03`'s own binding contract) and may
  affect whatever else depends on that ordering/dedup happening before the
  chat screen is ever opened (delivery-state transitions, notifications,
  etc.) — worth an independent architectural read of `E05-T03`/`E06-T09`
  before choosing this.
- **Option C — persist the plaintext at rest**, encrypted separately (e.g.
  device-keystore-backed) so a second "decrypt" is just a local unwrap,
  never a second Double-Ratchet step. Clearly a bigger, more invasive
  change and the most likely to need its own ADR.

None of these is a bug fix in the "restore previously-intended behavior"
sense — each is a genuine architecture decision about where decrypted (or
re-decryptable) plaintext is allowed to live, which is exactly what rule 3
reserves as a human call, especially given a security-relevant precedent
is already on record and any option here either widens or reinterprets it.
Per this session's own standing autonomy grant (`2026-09-06`, AGENTS.md
rule 3): this explicitly stays a genuine STOP even when told not to wait
for a response, because it is "a foundational choice with no advisory
recommendation already on record" — there IS no prior recorded human
decision to fall back on here, unlike (say) E04-B17's fixes which all
extended an already-established pattern (`resolveDeviceId`).
