# E04-B18 · Delivered messages fail to decrypt -- Bluetooth address masking may be polluting Signal Protocol identity storage

## 1. Goal

Find and fix why a message that has been transported correctly, matched
correctly through `PrekeyExchange`'s link-bound handshake, and persisted
intact on the receiving device still fails to decrypt -- so a message that
arrives is also a message the recipient can read.

## 2. Business logic

FR-SEC-001: only authorized endpoints may decrypt private communication --
implicitly, an authorized endpoint that successfully completes the Signal
Protocol handshake (X3DH via this app's own prekey-exchange control-frame
protocol, `lib/core/messaging/prekey_exchange.dart`) MUST be able to decrypt
what it receives afterward. A decrypt failure after a proven-successful
handshake is either a session-establishment defect (the two sides derive
different keys) or an identity-storage defect (the right keys exist, but are
being looked up/overwritten under the wrong identifier).

## 3. What this task does

- Investigate and fix the decrypt failure described in `repro`/`actual`
  above. Concretely:
  1. Confirm or refute the hypothesis recorded in E04-B17's Open Questions
     (`OQ-E04-B17-1`): that `00:00:46:00:00:01` -- observed as BOTH a
     device's own `Settings.Secure` `bluetooth_address` value AND the id
     `resolveDeviceId` resolves a bonded peer to -- is Android's generic
     "no `LOCAL_MAC_ADDRESS` permission" sentinel rather than a real,
     globally-unique per-device MAC. (The commonly-cited default sentinel
     on stock AOSP is `02:00:00:00:00:00`; this OEM pairing consistently
     returns a different fixed value instead, but the structural risk --
     non-uniqueness -- is the same either way.) A `run-as` pull of the
     receiving device's `nexora.sqlite` after a live 2026-09-13 re-test
     showed `signal_trusted_identities` holding the SAME public key under
     TWO different keys for what should be one peer (the peer's real,
     long-form `selfDeviceId` hex string, AND this masked-looking BT
     address) -- worth checking whether that duplication, by itself
     (rather than a wrong key), is enough to make `CryptoService`'s lookup
     path pick the wrong stored identity/session on a given decrypt call.
  2. Trace every call site that persists to `signal_sessions` /
     `signal_trusted_identities` / `signal_identity` (see
     `crypto_stub.dart`'s -- or the real, non-stub `CryptoService`
     implementation's -- `DriftSignalProtocolStore`) and confirm each one
     is keyed by a `resolveDeviceId`-resolved identity (or the peer's real
     `selfDeviceId`, once known), never by a raw, potentially-masked
     Bluetooth address read directly from a platform channel event.
  3. Reproduce with a genuinely clean pairing (fresh install, fresh Signal
     identity keys on both sides, or at minimum cleared
     `signal_sessions`/`signal_trusted_identities` rows for this specific
     pairing) to isolate "stale session state accumulated across today's
     many test iterations" from "the code re-derives mismatched keys even
     on a clean run." OQ-E04-B17-1 was never independently confirmed this
     way (Google Sign-In could not be automated past the account picker in
     the investigating session's environment) -- if hands-on device access
     is available, do this first; it is the fastest way to know which of
     the two this bug actually is.
  4. Fix whichever is confirmed. If it is identity-key duplication/misuse,
     the fix likely belongs alongside `resolveDeviceId`
     (`BluetoothTransport.kt`) and/or wherever `CryptoService` resolves an
     address to a `SignalProtocolAddress` -- ensure exactly one canonical
     identifier per peer is ever used for crypto storage, matching
     `E04-B08`'s existing "resolve once, use everywhere" discipline for
     the transport layer.
  5. Add a regression test proving a peer's crypto identity is never
     stored or looked up under a raw, unresolved address once
     `resolveDeviceId` (or the peer's own announced `selfDeviceId`) is
     available.

## 4. What this task does NOT do

- Does NOT touch `E04-B17`'s own transport-layer fix (accept-path address
  resolution, the `bonded` gate, `_reconcileStaleRelationship`, or the
  `openSockets` liveness fix) -- all four are live-proven working as of
  2026-09-13 (see `E04-B17`'s Run log) and are out of this bug's scope
  unless this investigation finds a genuine interaction.
- Does NOT redesign the prekey-exchange control-frame protocol
  (`prekey_exchange.dart`'s link-binding / provenance-matching logic) --
  that also proved correct live (`matched=true`) in the same re-test; this
  bug is specifically about what happens AFTER a successful handshake,
  during actual message decrypt.
- Does NOT assume the fix without first confirming which of the two
  hypotheses above is real -- do not guess and patch blind.

## 5. Definition of Done

- [ ] Root cause confirmed with file:line evidence (or a live-hardware
  repro trace), not guessed.
- [ ] Fix implemented, scoped to the confirmed root cause.
- [ ] A live two-device re-test shows a message sent after a clean session
  establishment decrypts to its real plaintext.
- [ ] A regression test exists proving crypto identity storage is never
  keyed by a raw/unresolved address.
- [ ] Existing test suite green, `flutter analyze` clean.
