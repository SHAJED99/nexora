# E04-B18 · Every incoming message is decrypted twice against one Double Ratchet chain -- the second decrypt is structurally unsafe

## 1. Goal

Stop the app from independently re-deriving a received message's plaintext
from stored ciphertext at display time, when that ciphertext was ALREADY
consumed by a real Double Ratchet decrypt at receive time -- so a delivered
message reliably decrypts, every time, not intermittently.

## 2. Root cause (confirmed by code reading + live evidence, 2026-09-13)

**Two distinct bugs were conflated under the original `OQ-E04-B17-1`
report. This task is about the real, receiver-side one. The other (sender-
side) is understood and is NOT a crypto bug — see the callout at the end
of this section.**

The receiving path decrypts every incoming ciphertext **twice**:

1. **At receive time** — `InboundPipeline._handleBuffer` calls
   `_stack.receiveMessage.call(frame.source, ciphertextMessage)`
   (`inbound_pipeline.dart:934`), which is
   `ReceiveMessageUseCase.call` (`receive_message_use_case.dart:102-174`).
   That method calls `await _decrypt(address, ciphertext)` at line 107 —
   a REAL `CryptoService.decrypt` call, which per `crypto_stub.dart`'s own
   doc comment (`crypto_stub.dart:112-130`) performs the actual Double
   Ratchet `SessionCipher.decrypt`/`decryptFromSignal` step, consuming
   that message's key from the ratchet. The resulting `plaintext` is used
   ONLY to recover envelope metadata (`MessageEnvelope.deserialize`, line
   108) — `envelope.id`/`conversationId`/`sequenceNumber` — and then
   **discarded**. Only the raw ciphertext bytes are persisted
   (`ciphertextBytes = Uint8List.fromList(ciphertext.serialize())`, line
   149; `messages.ciphertext`, line 157). Nothing about the successfully-
   decrypted plaintext survives this call.
2. **At display time** — every single row rendered in a chat, whether just
   arrived (`watchConversation`'s stream) or loaded from history,
   goes through `ChatController._resolvePlaintext`
   (`chat_controller.dart:428-454`, called from `_bubblesFor` at line 221
   and `_renderPending` at line 243, unconditionally, for every non-
   optimistic row). That method reads the STORED ciphertext back out of
   the `messages` table and calls `_crypto.decrypt(address,
   ciphertextMessage)` again (`chat_controller.dart:442`) — a SECOND,
   independent Double Ratchet decrypt attempt on the exact same ciphertext
   bytes already consumed in step 1. The only thing standing between this
   and a guaranteed failure is `_plaintextCache`
   (`chat_controller.dart:160,429-430,452`), an in-memory
   `Map<String, String?>` scoped to ONE `ChatController` instance — it
   is wiped every time a fresh `ChatController` is created, which GetX
   does on every navigation away from and back to a chat, and always on
   app restart.

`crypto_stub.dart`'s own doc comment names the exact failure mode this
produces: `CryptoDecryptFailureReason.duplicateMessage` "on a replayed
counter" (`crypto_stub.dart:123`) — this project's own crypto layer
already anticipates and detects decrypting the same message twice. Signal
Double Ratchet decrypt is a **one-time, stateful operation**: it advances
the receiving chain and (for the exact next-expected counter, the common
case) does not retain the message key for reuse — retaining it
indefinitely would itself weaken forward secrecy. Calling `decrypt()`
twice on the same wire bytes is not a "just try again" operation the way
re-reading a file is; it is architecturally adversarial to the protocol
in the SAME way an attacker's replay would be, and the protocol correctly
tries to reject it.

**Why it's intermittent rather than 100% failing**: the live evidence (3
messages sent minutes apart, only the middle one decrypted) is consistent
with a genuine race between `ReceiveMessageUseCase`'s receive-time decrypt
(running inside the async inbound-pipeline handler) and
`ChatController`'s display-time decrypt (running whenever the chat screen
is open and `watchConversation`'s stream delivers the new row) — whichever
one's session-state write (`DriftSignalProtocolStore.storeSession`,
`drift_signal_store.dart:388`) lands second effectively "wins" and
determines whether the OTHER caller's read/decrypt sees pre- or post-
advance ratchet state. This is not a guess this task needs to resolve
further to justify a fix: **regardless of which exact interleaving
produces a given pass/fail outcome, the fix is the same** — never call
`decrypt()` twice on one message's ciphertext.

**Two distinct bugs were conflated under the original report.** The
SENDING device showing "(unable to decrypt this message)" for its OWN
sent messages (observed live 2026-09-13, ALL of one device's own sent
messages, 100% of the time, after an app restart) is a **separate,
already-understood, non-crypto issue**: `_resolvePlaintext`
(`chat_controller.dart:436-438`) correctly special-cases a self-sent row
by decrypting against `_peerDeviceId` instead of `_selfDeviceId` — but
Double Ratchet sessions are asymmetric by design, so a device can NEVER
decrypt its own outgoing ciphertext at all, ever, by any method. Before
this task's investigation, the only reason a self-sent message ever
rendered correctly was `send()`'s own direct cache seed
(`_plaintextCache[message.id] = trimmed`, `chat_controller.dart:326`) —
which is populated at send time and, like every other entry in
`_plaintextCache`, does not survive a `ChatController` recreation (a
navigation or app restart). This is a real, disclosed, but MUCH smaller
gap (no persisted local echo of a sent message's own plaintext) — it does
not need a crypto fix, only a way to re-derive or re-cache a sent
message's own plaintext across `ChatController` instances. Filed as a
follow-up note below rather than its own task, since the fix is likely
the same shape as whatever this task lands on for the receiving side
(cache plaintext somewhere that outlives one `ChatController` instance).

## 3. Human decision and the fix built against it

This repository had an explicit, human-endorsed security architecture
decision already on record: `notification_tables.dart:9-13` cited
`E06-T09.md:64-68` for "`full` [notification privacy] has no supported
mechanism today, because **plaintext is decrypted only in the screen
layer**." Three candidate directions were presented (cache the receive-
time plaintext outside the screen; make the screen the only decryptor and
change `ReceiveMessageUseCase`'s contract; persist plaintext at rest under
separate encryption) and the human was asked directly, since every option
touches that recorded boundary and none is a "restore previously-intended
behavior" bug fix.

**Human decision, 2026-09-13**: decrypt once at receive/send time (already
happening) and keep that plaintext in the local DB — closest to Option A,
made concrete as a new nullable `messages.plaintext_payload` column rather
than a separate in-memory cache. The human's own reasoning, recorded
verbatim in spirit: this database already holds the device's private
Signal identity/session key material (`signal_identity`, `signal_sessions`
— neither separately encrypted either), so anyone who could read this
database could already decrypt every message, past and future, from the
keys alone; storing an already-legitimately-decrypted message's plaintext
alongside that does not cross a NEW trust boundary, it is consistent with
the same local-device trust model every other column in this schema
already relies on. This does not touch the separate, still-standing
restriction that a background dispatcher (e.g. a notification builder)
must never read plaintext — nothing outside the chat/conversations screens
reads this column.

**The fix**, built exactly on that decision:

- `messages.plaintext_payload` (`message_tables.dart`) — new nullable
  `BlobColumn`, schema v22→v23, additive migration
  (`if (from >= 11 && from < 23)`, no backfill — a pre-fix row's Double
  Ratchet key is already consumed and unrecoverable, so it simply stays
  `NULL` and keeps showing "(unable to decrypt this message)").
- `ReceiveMessageUseCase.call` (`receive_message_use_case.dart`) now
  persists `envelope.payload` — the plaintext it ALREADY decrypts at line
  107 to recover envelope metadata, previously discarded — into that
  column, alongside the ciphertext it already stored.
- `SendMessageUseCase.call` (`send_message_use_case.dart`) now persists
  the caller's own composed plaintext into the same column at phase 3
  (alongside the ciphertext write) — this device already knows it, it was
  never encrypted-then-received here.
- `Message` (`message.dart`), `ConversationRepository._messageFromRow`
  (`conversation_repository.dart`): thread the new, optional field
  through the domain model and DB row mapping.
- `ChatController._resolvePlaintext` (`chat_controller.dart`) and
  `ConversationsController._resolvePreview`
  (`conversations_controller.dart`) now read `plaintextPayload` FIRST when
  present, and only fall back to the old decrypt-from-`ciphertext` path
  for a row written before this column existed. Neither ever independently
  re-decrypts a row that already has a persisted plaintext.
- This incidentally also fixes the smaller, separate "sent message shows
  undecryptable after a restart" gap (§2's closing note): that was only
  ever a workaround (`_plaintextCache` seeded at send time, not surviving
  `ChatController` recreation) for the fact that this device could never
  decrypt its own outgoing ciphertext (Double Ratchet asymmetry) — now
  moot, since the plaintext is read back from the DB, not re-derived.

## 4. What this task does NOT do

- Does NOT touch `E04-B17`'s own transport-layer fix or `E04-B19`'s
  own-device-name feature — both are unrelated and already live-proven.
- Does NOT change how group messages (`send_group_message_use_case.dart`,
  `inbound_pipeline.dart`'s `handleGroupMessage`) or their own preview
  (`ConversationsController._resolveGroupPreview`) are decrypted — those
  use a completely different mechanism (Sender Keys, not 1:1 Double
  Ratchet) and were never the subject of this bug. `Message.
  plaintextPayload` is a new OPTIONAL field (defaults to `null`); every
  existing `Message(...)` construction site outside the two use cases
  this task touches (group messaging, delivery acks) compiles and behaves
  unchanged.
- Does NOT persist plaintext for anything other than the two production
  write paths named above — no backfill, no bulk migration of historical
  ciphertext.

## 6. Open Questions

- **`OQ-E04-B18-1`** — `OQ-E04-B17-1`'s original hypothesis (a masked
  Bluetooth address sentinel being stored as if it were a unique identity
  in `signal_trusted_identities`) is NOT disproven; the DB evidence for it
  (the same public key under two different keys in that table) is real
  and still on record in `E04-B17.md`'s Run log. It just isn't necessary
  to explain the observed intermittent-decrypt symptom, which the double-
  decrypt bug fully explains on its own. Whoever picks up the human
  decision in §3 should also decide whether that separate identity-
  duplication risk needs its own follow-up task, or whether fixing this
  task's root cause incidentally removes the conditions that produced it
  (e.g. if the fix touches how/when `resolveDeviceId` output reaches
  crypto storage). Not investigated further in this task — the fix chosen
  (persist the ALREADY-decrypted plaintext) closes the observed symptom
  regardless of whether this identity-duplication risk is separately real,
  so it did not block finishing this task, but it remains open.
- **`OQ-E04-B18-2`** — the receiving device's live decrypt of a brand-new
  message was not re-confirmed on real hardware after this fix (the two
  test devices' Bluetooth link would not re-establish in this session —
  see DoD's own note). Covered by real-crypto (not mocked) unit tests
  (`receive_message_use_case_test.dart`'s
  `test_E04_B18_persists_the_already_decrypted_payload_not_just_ciphertext`,
  `conversations_controller_test.dart`'s
  `test_E04_B18_preview_uses_plaintextPayload_without_a_second_decrypt`),
  and by the fact that `ReceiveMessageUseCase`'s own decrypt call — the
  ONE that matters — is completely unchanged by this fix (only what
  happens to its result changed). Suggested next step: whoever next has
  two-device hardware access, re-run one live send/receive cycle and
  confirm a freshly-received message decrypts correctly on first display.
