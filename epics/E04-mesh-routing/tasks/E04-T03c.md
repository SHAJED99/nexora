# E04-T03c · Real Bluetooth data transfer

## 1. Goal
Complete the Bluetooth transport: `send()` writes real bytes to the
connected socket's output stream, and a background read loop delivers
incoming bytes via `onDataReceived` — the last piece needed before T04's
relay engine can move real (encrypted) packets over an actual radio.

## 2. Business logic
- FR-DISC-001 / FR-PLAT-002: this is still discovery/connection's sibling
  concern (moving bytes once connected), not a new requirement — it
  completes what T03a's Pigeon contract already promised
  (`send`/`onDataReceived`) against T03b's real socket instead of loopback.
- A length-prefixed framing is required: raw `BluetoothSocket` streams have
  no message boundaries, so this task must frame each `send()` call as one
  discrete unit the receiving side can reassemble exactly — a 4-byte
  big-endian length prefix followed by that many payload bytes is
  sufficient for v1.

## 3. What this task does
- `BluetoothTransport.send(deviceId, bytes) -> Boolean`: writes the length
  prefix then the payload to the connected socket's `OutputStream`, on a
  background thread; returns `false` (not throws) on any I/O failure,
  triggering the same failure path T02's `onRouteFailure` will later
  consume.
- A per-connection background read loop (started when `connect()`
  succeeds, stopped on `disconnect()`): reads the 4-byte length prefix,
  then exactly that many bytes, and calls `onDataReceived(deviceId, bytes)`
  on the Flutter side via the Pigeon `TransportEventsApi`.
- `TransportApiHost.kt`: `send` now delegates to `BluetoothTransport`
  fully (no remaining loopback path once this lands, except in tests/dev
  builds that still use `LoopbackTransport` directly — do not delete
  `LoopbackTransport.kt`, it stays useful for T04's non-hardware tests).

## 4. What this task does NOT do
- Does NOT add any encryption, compression, or retry/ack logic — E03
  already encrypts the payload before it reaches this layer, and
  retry/queueing is T04's store-and-forward job. This layer moves opaque
  bytes, framed, nothing more.
- Does NOT change the framing format's *meaning* to anything other than
  "one `send()` call = one `onDataReceived` call" — no multiplexing, no
  fragmentation across multiple sends.
- Does NOT touch Wi-Fi Direct or Internet transport.
- Does NOT change `TransportService`'s Dart-facing API (T03a's contract) —
  this task is purely a native-side implementation completion.

## 5. Contract

### Functions
```yaml
- signature: "BluetoothTransport.send(deviceId: String, bytes: ByteArray) -> Boolean"
  purpose: "Length-prefixed write to the connected socket's OutputStream; false on any I/O exception, never throws across the Pigeon boundary"

- signature: "BluetoothTransport (internal) startReadLoop(deviceId: String, socket: BluetoothSocket) -> Unit"
  purpose: "Background thread: read 4-byte length prefix, read that many bytes, emit onDataReceived; loop until disconnect or IOException"
```

## 6. Risks
- The read loop must run on its own background thread per connection and
  must be reliably stopped on `disconnect()` — a leaked read thread blocked
  on a closed socket's `InputStream.read()` is the classic Bluetooth
  Android bug; confirm the thread actually exits (log or a test-visible
  flag) when disconnect happens.
- Partial reads are normal on a stream socket — `InputStream.read()` may
  return fewer bytes than requested. Use a loop that reads until the full
  length-prefixed frame is assembled, not a single `read()` call assumed to
  return everything.
- Same manual-verification caveat as T03b: this cannot be meaningfully
  unit-tested without two real radios. Be honest in the Run log about what
  was and wasn't actually observed on-device.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-TRANSPORT-3**: WHEN two devices have a connected Bluetooth
  session, `send()` on one SHALL result in `onDataReceived` firing on the
  other with the identical bytes. (FR-DISC-001)

### Tests
No hardware-free unit test proves real socket I/O — same disclosed gap as
T03b. If a second Bluetooth device is available for manual verification,
that is this task's actual proof.

### Manual
1. With two Bluetooth-capable devices connected (per T03b's manual step),
   send a real message (any payload, e.g. from a debug affordance or by
   temporarily wiring T04/E05 once they exist) from device A.
2. Confirm device B's `onDataReceived` fires with byte-identical content.
3. Confirm the reverse direction also works.
4. If only one device is available: note honestly that this step could not
   be completed, and what was verified instead (e.g. the write path
   doesn't throw against a real open socket to any reachable Bluetooth
   peer, if one exists in pairing range without a full app-level exchange).
