# E04-T03c · Real Bluetooth data transfer

## 1. Goal
Complete the Bluetooth transport: `send()` writes real bytes to the
connected socket's output stream, and a background read loop delivers
incoming bytes via `onDataReceived` — the last piece needed before T04's
relay engine can move real (encrypted) packets over an actual radio.

## 2. Business logic
- FR-DISC-001 / FR-PLAT-002: this is still discovery/connection's sibling
  concern (moving bytes once connected), not a new requirement — it
  completes what T03a's Pigeon contract already promised
  (`send`/`onDataReceived`) against T03b's real socket instead of loopback.
- A length-prefixed framing is required: raw `BluetoothSocket` streams have
  no message boundaries, so this task must frame each `send()` call as one
  discrete unit the receiving side can reassemble exactly — a 4-byte
  big-endian length prefix followed by that many payload bytes is
  sufficient for v1.

## 3. What this task does
- `BluetoothTransport.send(deviceId, bytes) -> Boolean`: writes the length
  prefix then the payload to the connected socket's `OutputStream`, on a
  background thread; returns `false` (not throws) on any I/O failure,
  triggering the same failure path T02's `onRouteFailure` will later
  consume.
- A per-connection background read loop (started when `connect()`
  succeeds, stopped on `disconnect()`): reads the 4-byte length prefix,
  then exactly that many bytes, and calls `onDataReceived(deviceId, bytes)`
  on the Flutter side via the Pigeon `TransportEventsApi`.
- `TransportApiHost.kt`: `send` now delegates to `BluetoothTransport`
  fully (no remaining loopback path once this lands, except in tests/dev
  builds that still use `LoopbackTransport` directly — do not delete
  `LoopbackTransport.kt`, it stays useful for T04's non-hardware tests).

## 4. What this task does NOT do
- Does NOT add any encryption, compression, or retry/ack logic — E03
  already encrypts the payload before it reaches this layer, and
  retry/queueing is T04's store-and-forward job. This layer moves opaque
  bytes, framed, nothing more.
- Does NOT change the framing format's *meaning* to anything other than
  "one `send()` call = one `onDataReceived` call" — no multiplexing, no
  fragmentation across multiple sends.
- Does NOT touch Wi-Fi Direct or Internet transport.
- Does NOT change `TransportService`'s Dart-facing API (T03a's contract) —
  this task is purely a native-side implementation completion.

## 5. Contract

### Functions
```yaml
- signature: "BluetoothTransport.send(deviceId: String, bytes: ByteArray) -> Boolean"
  purpose: "Length-prefixed write to the connected socket's OutputStream; false on any I/O exception, never throws across the Pigeon boundary"

- signature: "BluetoothTransport (internal) startReadLoop(deviceId: String, socket: BluetoothSocket) -> Unit"
  purpose: "Background thread: read 4-byte length prefix, read that many bytes, emit onDataReceived; loop until disconnect or IOException"
```

## 6. Risks
- The read loop must run on its own background thread per connection and
  must be reliably stopped on `disconnect()` — a leaked read thread blocked
  on a closed socket's `InputStream.read()` is the classic Bluetooth
  Android bug; confirm the thread actually exits (log or a test-visible
  flag) when disconnect happens.
- Partial reads are normal on a stream socket — `InputStream.read()` may
  return fewer bytes than requested. Use a loop that reads until the full
  length-prefixed frame is assembled, not a single `read()` call assumed to
  return everything.
- Same manual-verification caveat as T03b: this cannot be meaningfully
  unit-tested without two real radios. Be honest in the Run log about what
  was and wasn't actually observed on-device.

- **Read-side partial reads: correct.** `readFully()` loops
  `while (offset < count)` with `input.read(buffer, offset, count - offset)`,
  accumulating at the right offset and returning `null` on `-1` (EOF).
  Constructed the fragmentation scenario the §6 risk warns about: a 300-byte
  frame delivered as 2 + 2 + 100 + 200 bytes. A naive single `read(buffer)`
  would return 2 or 4, and a naive implementation would parse a truncated header
  as a whole frame and desync the stream permanently. This implementation calls
  `readFully(input, 4)` (which itself survives a header split across two reads)
  then `readFully(input, 300)` (which spans the 100- and 200-byte chunks). Frame
  boundaries hold. The `length < 0 || length > MAX_FRAME_BYTES` guard sits

  `ByteArray(count)`, not after.

  is not folklore — `BluetoothSocket.close()` is documented as immediately
  releasing resources and closing the attached streams, and is the *documented

  blocked read rather than letting it hang). `disconnect()` closing the socket
  therefore does unblock the read thread, whose `catch (e: IOException)` exits
  the loop. Reasoning accepted as sound; it remains reasoning, not a live trace
  (see the escalation below).

### Fixes applied by the reviewer (small, scoped, inside this task's two files)
1. **BLOCKING as shipped — unbounded UI-thread wait in `send()` (was
   `BluetoothTransport.kt:218`, `done.await()` with no timeout).** This does
   reintroduce T03a-class hang risk, in a narrower but *unrecoverable* form.
   Evidence: `TransportApi.g.kt:416` creates the `send` channel as a plain
   `BasicMessageChannel(binaryMessenger, name, codec)` with **no `TaskQueue`**
   (confirmed: zero `taskQueue` occurrences in the generated file, and no
   `@TaskQueue`/`TaskQueueType` in `pigeons/transport.dart:71`), so the host
   `send()` call runs on the platform/UI thread. An RFCOMM
   `OutputStream.write()` can block indefinitely under link-layer flow control
   (peer stops draining, link degrades without dropping) — and the only escape
   hatch, `disconnect()`, is *itself* a Pigeon host call on that same blocked
   thread, so the app cannot recover: guaranteed ANR, not merely a slow send.
   The builder's deviation #3 correctly identified the sync-Boolean constraint
   but treated the wait as "normally very fast" rather than bounding it. Fixed:
   `done.await(SEND_TIMEOUT_MS = 3_000L, TimeUnit.MILLISECONDS)` (under
   Android's ~5s ANR window), and on expiry the connection is torn down via
   `disconnect(deviceId)` before returning `false` — because returning `false`
   while the stuck writer might still finish a *partial* frame later would leave
   the peer's reader permanently desynced (this framing carries no resync
   marker). The teardown also closes the socket, which aborts the stuck write
   with an `IOException` and unblocks the read loop, so no thread is leaked.
   `InterruptedException` from `await` is now caught (flag restored, `false`
   returned) so `send()` still never throws across the Pigeon boundary per §5 —
   previously it could.
2. **Read loop could kill the process on a non-`IOException`.** The loop caught
   only `IOException`; any `RuntimeException` escaping the stream or
   `eventsScope.launch` would reach the default uncaught handler, and an
   uncaught exception on *any* Android thread kills the whole process. The
   `finally` did run either way, so the builder's bookkeeping claim was right —
   but the app would already be dead. Added a `catch (e: Exception)` arm.
   (Deliberately not catching `Error`: the 16MB `MAX_FRAME_BYTES` cap is the
   right guard for the allocation, and swallowing OOM is worse than dying.)
3. **`finally { readThreads.remove(deviceId) }` could de-register the *wrong*
   thread.** On a fast disconnect→reconnect for the same `deviceId`, the old
   thread's `finally` can run *after* the new thread has registered itself, and
   the unconditional single-arg `remove` then drops the live thread's entry —
   after which `disconnect()`/`release()` no longer interrupt it. Not a leak in
   practice (`socket.close()` is the real unblock mechanism and still works),
   but it breaks exactly the tracking guarantee §6 asks to be confirmed. Fixed
   with the two-arg `ConcurrentHashMap.remove(deviceId, Thread.currentThread())`
   so a thread only ever de-registers itself.
