# E04-B30 · Limit the bonded-cache refresh to devices that could run Nexora

## 1. Mechanism

`refreshNexoraCandidateUuidCaches` (E04-T07) now also requires the bonded device's Bluetooth major class to be `PHONE` or `COMPUTER` (tablets report `COMPUTER`) before calling `fetchUuidsWithSdp()`. Audio/video, imaging (printers), wearables, peripherals and any unknown class are skipped. The existing conditions are unchanged: SPP-capable, and not already advertising `NEXORA_DISCOVERY_UUID`.

Live check of the class filter against the real bonded set: Redmi 10 2022 reports class `5a020c` (major PHONE) and would still be refreshed. HOCO/soundcore/HAVIT (audio), MPT-II (imaging) and the Mi Band (wearable) would be skipped. ABGTL-DEV-00126 (`28010C`, major COMPUTER) would still be queried.

## What this task does NOT do

- Does not change `advertisesNexora`, the Discover filter, `unmaskIfNotBonded`, or which UUIDs are published.
- Does not remove the refresh. E04-T07 needs it so already-bonded peers learn the new record.
- Does not add a Kotlin test harness (none exists in this project).

## 2. Definition of Done

- [x] Refresh skips bonded devices whose major class is neither PHONE nor COMPUTER
- [ ] `flutter build apk --debug` compiles clean
- [ ] Independent review (reviewed_by != executed_by)
- [ ] Live: after a listener start, Pixel logcat shows SDP only for PHONE/COMPUTER-class bonded devices

## Open Questions

- OQ-E04-B30-1: a device whose class is missing or misreported (`bluetoothClass == null`, or a phone reporting UNCATEGORIZED) is now skipped, so its cache is not refreshed. It still gets a live SDP check when a Discover scan finds it (`handleDeviceFound`), and `unmaskIfNotBonded` keeps its raw bonded-set fallback.
