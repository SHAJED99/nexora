# E04-T06 · Filter Discover results to devices actually running Nexora (SDP UUID check)

## 1. Goal

Stop showing every nearby Bluetooth Classic device on the Discover page.
Only show a discovered device once its SDP record is confirmed to
advertise `NEXORA_SPP_UUID` — the same well-known UUID this app's own
listening socket (`listenUsingRfcommWithServiceRecord`) already
registers under (see this file's own header/`NEXORA_SPP_UUID` doc
comment). This is the only reliable, already-available signal that a
discovered device is a Nexora install and not an unrelated accessory —
there is no other cross-device "is this app installed" signal available
over Bluetooth Classic without a custom pairing/handshake protocol,
which is out of this task's scope (see §4).

## 2. Background

Human-reported directly (2026-09-14), live-observed on a real device's
Discover action: nearby headphones, a car kit, etc. all show up
alongside real Nexora peers. `handleDeviceFound` (this file) has never
filtered `ACTION_FOUND` scan results by anything other than "already
emitted this session" (`discoveredAddresses`) — every discovered address
is unconditionally forwarded to `onDeviceDiscovered`.

Android's Bluetooth Classic SDP mechanism already gives this app exactly
the signal needed: `BluetoothDevice.fetchUuidsWithSdp()` triggers an
async SDP inquiry against the remote device, and the result (delivered
via the `ACTION_UUID` broadcast) lists every service UUID that peer
advertises. Only a device actually running Nexora will have registered
`NEXORA_SPP_UUID` in its own SDP record (the exact same
`listenUsingRfcommWithServiceRecord(SERVICE_NAME, NEXORA_SPP_UUID)` call
this file already makes for its own listening socket). A generic
Bluetooth accessory will never have this UUID in its SDP record.

## 3. What this task does

- In `handleDeviceFound`, after resolving `resolvedId`/`name`/`rssi`/
  `bonded` (unchanged), gate the eventual `onDeviceDiscovered` emission
  on a Nexora-peer check instead of emitting unconditionally:
  - If the platform already has this device's UUIDs cached
    (`BluetoothDevice.uuids`, non-null — e.g. an already-bonded device,
    or one queried earlier this process's lifetime), check synchronously:
    contains `NEXORA_SPP_UUID` → emit; otherwise → drop silently (do not
    surface as a discovered device at all — this is the whole point of
    the feature, so a non-Nexora device should behave as if it was never
    found).
  - Otherwise, call `device.fetchUuidsWithSdp()` and defer the decision:
    track the pending device's id/name/rssi/bonded state keyed by
    address, and finish the decision when the corresponding `ACTION_UUID`
    broadcast arrives (new `IntentFilter` addition alongside the existing
    `ACTION_FOUND` registration) — emit only if the returned UUID list
    contains `NEXORA_SPP_UUID`.
  - Apply a bounded timeout to the pending-lookup bookkeeping (mirroring
    this file's own existing `Thread.sleep` timeout pattern used for
    `POST_BOND_CONNECT_DELAY_MS`) so a device that never answers SDP
    doesn't leak memory across a long-running discovery session — a
    timed-out lookup is simply never shown (fail closed, consistent with
    "only confirmed Nexora peers are shown").
- Registers/unregisters the new `ACTION_UUID` listening alongside this
  file's existing `discoveryReceiver` lifecycle (same receiver instance
  or a paired one, torn down at the same points `discoveryReceiver`
  already is) — no new leak surface.
- Clears the new pending-lookup bookkeeping at the same points
  `discoveredAddresses` is already cleared (`doStartDiscovery`) and torn
  down (`release`).

## 4. What this task does NOT do

- Does NOT build any general-purpose "is this app installed" protocol —
  SDP-advertised UUID is the specific, already-available mechanism this
  app's own architecture already relies on (ADR-0004), not a new one.
- Does NOT change `acceptLoop`'s own `onDeviceDiscovered` emission for an
  ACCEPTED inbound connection — that path is already guaranteed to be a
  genuine Nexora peer by construction (only a Nexora install would ever
  dial this app's own listening socket), so no SDP check is needed or
  added there.
- Does NOT change `resolveDeviceId`'s own bonded-name-matching logic
  (E04-B08) or the E04-B21 accept-path bonded-membership guard —
  unrelated, untouched.
- Does NOT add a Dart/Pigeon-visible behavior change — filtering happens
  entirely native-side, before `onDeviceDiscovered` is ever called, so
  the Dart layer's existing contract (every emitted device is shown) is
  unchanged; no `pigeons/transport.dart` or Dart-side file needs to
  change.
- Does NOT add a Kotlin unit-test harness — none exists in this project
  (`android/app/build.gradle.kts` has no JUnit/Robolectric dependency),
  consistent with every other native-transport bug/task in this epic
  (E04-B08, E04-B17, E04-B19, E04-B21). Verified via `flutter build apk
  --debug` compiling clean plus live on-device testing.

## 5. Definition of Done

- [ ] `handleDeviceFound` no longer emits `onDeviceDiscovered`
  unconditionally — gated on a confirmed `NEXORA_SPP_UUID` SDP match.
- [ ] `ACTION_UUID` broadcast handling implemented, registered/
  unregistered alongside the existing discovery receiver lifecycle.
- [ ] Pending-lookup bookkeeping has a bounded timeout and is cleared on
  both a fresh `discover()` call and `release()`.
- [ ] `flutter build apk --debug` compiles clean.
- [ ] Live-verified on real hardware: Discover no longer lists a nearby
  non-Nexora Bluetooth accessory (if one is available to test against)
  and still lists the other real Nexora-running test device.
