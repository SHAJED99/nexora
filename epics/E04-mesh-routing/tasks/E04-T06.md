# E04-T06 · Filter Discover results to devices actually running Nexora (SDP UUID check)

## 1. Goal

Stop showing every nearby Bluetooth Classic device on the Discover page.
Only show a discovered device once its SDP record is confirmed to
advertise `NEXORA_SPP_UUID` — the same well-known UUID this app's own
listening socket (`listenUsingRfcommWithServiceRecord`) already
registers under (see this file's own header/`NEXORA_SPP_UUID` doc
comment). This is the only reliable, already-available signal that a
discovered device is a Nexora install and not an unrelated accessory —
there is no other cross-device "is this app installed" signal available
over Bluetooth Classic without a custom pairing/handshake protocol,
which is out of this task's scope (see §4).

## 2. Background

Human-reported directly (2026-09-14), live-observed on a real device's
Discover action: nearby headphones, a car kit, etc. all show up
alongside real Nexora peers. `handleDeviceFound` (this file) has never
filtered `ACTION_FOUND` scan results by anything other than "already
emitted this session" (`discoveredAddresses`) — every discovered address
is unconditionally forwarded to `onDeviceDiscovered`.

Android's Bluetooth Classic SDP mechanism already gives this app exactly
the signal needed: `BluetoothDevice.fetchUuidsWithSdp()` triggers an
async SDP inquiry against the remote device, and the result (delivered
via the `ACTION_UUID` broadcast) lists every service UUID that peer
advertises. A device running Nexora will have registered
`NEXORA_SPP_UUID` in its own SDP record (the exact same
`listenUsingRfcommWithServiceRecord(SERVICE_NAME, NEXORA_SPP_UUID)` call
this file already makes for its own listening socket) -- see the
frontmatter `expected:` note above for the honest scope of what this
UUID actually distinguishes (SPP-capable, not strictly Nexora-only).

## 3. What this task does

- In `handleDeviceFound`, after resolving `resolvedId`/`name`/`rssi`/
  `bonded` (unchanged), gate the eventual `onDeviceDiscovered` emission
  on a Nexora-peer check instead of emitting unconditionally:
  - If the platform already has this device's UUIDs cached
    (`BluetoothDevice.uuids`, non-null — e.g. an already-bonded device,
    or one queried earlier this process's lifetime), check synchronously:
    contains `NEXORA_SPP_UUID` → emit; otherwise → drop silently (do not
    surface as a discovered device at all — this is the whole point of
    the feature, so a non-Nexora device should behave as if it was never
    found).
  - Otherwise, call `device.fetchUuidsWithSdp()` and defer the decision:
    track the pending device's id/name/rssi/bonded state keyed by
    address, and finish the decision when the corresponding `ACTION_UUID`
    broadcast arrives (new `IntentFilter` addition alongside the existing
    `ACTION_FOUND` registration) — emit only if the returned UUID list
    contains `NEXORA_SPP_UUID`.
  - Apply a bounded timeout to the pending-lookup bookkeeping via
    `kotlinx.coroutines.delay` (review round 1, F1: NOT the file's own
    `Thread.sleep` pattern used for `POST_BOND_CONNECT_DELAY_MS` — that
    pattern runs on a dedicated background thread; `eventsScope` here
    runs on `Dispatchers.Main`, where a blocking `Thread.sleep` would ANR
    the app and, worse, starve the very `ACTION_UUID` broadcast this
    feature depends on, since a context-registered receiver's `onReceive`
    also runs on the main thread — `delay()` suspends without blocking
    it) so a device that never answers SDP doesn't leak memory across a
    long-running discovery session — a timed-out lookup is simply never
    shown (fail closed, consistent with "only confirmed Nexora peers are
    shown"). Each pending entry carries a unique generation token (review
    round 1, F2) so a stale timeout from a superseded `discover()` cycle
    can never evict a newer, still-in-flight entry for the same address.
  - A cached `BluetoothDevice.uuids` NEGATIVE answer does not
    short-circuit to "never shown" (review round 1, F4) — that cache is
    populated at bond time, so a peer bonded before it ever installed/ran
    Nexora would otherwise be permanently invisible with no path to a
    fresh answer. Only a genuine cached UUID match short-circuits;
    everything else (no cache, or a cache with no match) falls through to
    a live SDP query.
- Registers/unregisters the new `ACTION_UUID` listening alongside this
  file's existing `discoveryReceiver` lifecycle (same receiver instance
  or a paired one, torn down at the same points `discoveryReceiver`
  already is) — no new leak surface.
- Clears the new pending-lookup bookkeeping at the same points
  `discoveredAddresses` is already cleared (`doStartDiscovery`) and torn
  down (`release`).

## 4. What this task does NOT do

- Does NOT build any general-purpose "is this app installed" protocol —
  SDP-advertised UUID is the specific, already-available mechanism this
  app's own architecture already relies on (ADR-0004), not a new one.
- Does NOT change `acceptLoop`'s own `onDeviceDiscovered` emission for an
  ACCEPTED inbound connection. CORRECTED reasoning (review round 1, F3 —
  the original wording here was factually wrong and is replaced, not
  merely appended to): it is NOT true that only a Nexora install could
  ever dial this socket, since `NEXORA_SPP_UUID` is the generic/standard
  SPP UUID (any SPP client could in principle connect). What actually
  makes this path safe without an SDP check is that both this app's
  socket variants are the SECURE flavor, which the platform only
  completes for an already-bonded pair, plus the existing
  `remoteBonded = isBonded(remoteId)` assertion and E04-B21's
  `unmaskIfNotBonded` guard already in place there. The residual case (a
  bonded, non-Nexora SPP gadget dialing in) is real but negligible and
  already fails safe downstream (no protocol handshake, no
  reconciliation) — so no SDP check is needed or
  added there.
- Does NOT change `resolveDeviceId`'s own bonded-name-matching logic
  (E04-B08) or the E04-B21 accept-path bonded-membership guard —
  unrelated, untouched.
- Does NOT add a Dart/Pigeon-visible behavior change — filtering happens
  entirely native-side, before `onDeviceDiscovered` is ever called, so
  the Dart layer's existing contract (every emitted device is shown) is
  unchanged; no `pigeons/transport.dart` or Dart-side file needs to
  change.
- Does NOT add a Kotlin unit-test harness — none exists in this project
  (`android/app/build.gradle.kts` has no JUnit/Robolectric dependency),
  consistent with every other native-transport bug/task in this epic
  (E04-B08, E04-B17, E04-B19, E04-B21). Verified via `flutter build apk
  --debug` compiling clean plus live on-device testing.

## Open Questions

- `OQ-E04-T06-1`: no live two-device (plus one non-Nexora accessory)
  re-verification has been run yet — see DoD's last box. **The specific
  thing this live run must check first** (round-2 review's top nit):
  `pendingNexoraChecks` is keyed by the *scanned* `ACTION_FOUND` address,
  but `handleUuidResult` looks up `device.address` from the `ACTION_UUID`
  intent. E04-B08 already documented that some OEM stacks (confirmed on
  MIUI/Xiaomi) randomize the `ACTION_FOUND` address per scan. If any
  platform ever delivers `ACTION_UUID` under a device's real address
  rather than the same scanned address `ACTION_FOUND` reported, the
  lookup misses and NO unbonded peer would ever appear in Discover —
  a total feature-blocker only a live run can catch. Bonded peers are
  unaffected (their cached `uuids` short-circuits before any SDP query).

## Review

### Round 1 -- `claude-opus-5`, independent review of PR #253 -- CHANGES REQUESTED

- **F1 (blocking):** the SDP-lookup timeout used `Thread.sleep` inside
  `eventsScope.launch`, but `eventsScope` runs on `Dispatchers.Main`
  (`TransportApiHost`) -- this would ANR the app (Android's own
  dispatch-timeout is 5s, well under the 8s sleep) and, far worse,
  starve the main-thread-delivered `ACTION_UUID` broadcast this very
  feature depends on, making the timeout fire before the real answer
  could ever be processed -- a genuinely new (not-yet-bonded) Nexora
  peer would never appear in Discover, ~100% of the time, not a rare
  race. **Fixed:** `Thread.sleep` replaced with `kotlinx.coroutines.delay`,
  which suspends without blocking the main looper.
- **F2 (blocking):** a stale timeout from an OLDER, already-superseded
  `discover()` cycle could remove a NEWER, still-in-flight pending entry
  for the same address (both `discoveredAddresses` and
  `pendingNexoraChecks` are cleared and re-populated on every fresh
  `discover()` call), silently dropping a real Nexora peer for the rest
  of that scan session. **Fixed:** `PendingNexoraCheck` carries a unique
  monotonic `token`; every removal is identity-scoped via the two-arg
  `ConcurrentHashMap.remove(key, value)` instead of by key alone.
- **F3 (non-blocking, wording corrected):** `NEXORA_SPP_UUID` is the
  generic/standard SPP UUID, not Nexora-specific -- the filter really
  means "SPP-capable", with a residual, accepted false-positive class
  (serial modules, OBD dongles, etc.). The task's original §1/§2 wording
  overclaimed this; corrected in the frontmatter `expected:` field and
  §2. The `acceptLoop` exemption's stated reasoning in §4 was also
  factually wrong (claimed only a Nexora install could ever dial the
  listening socket) and has been replaced with the real reasoning: the
  SECURE socket variant + existing bonded-peer assertions, not the UUID
  itself. Follow-up filed: `E04-T07` (a Nexora-specific service UUID,
  registered alongside `NEXORA_SPP_UUID`, to close this residual gap).
- **F4 (non-blocking, fixed):** a cached `BluetoothDevice.uuids` miss
  (populated at bond time) previously short-circuited to "never shown"
  with no path to a fresh answer -- a peer bonded before it ever
  installed/ran Nexora would be permanently invisible. **Fixed:** only a
  cached POSITIVE match short-circuits; a miss or absent cache now falls
  through to a live `fetchUuidsWithSdp()` query, same as a
  never-cached device.
- **F5 (nit, fixed):** the original 8s timeout is likely too short --
  `fetchUuidsWithSdp()` issued during an active inquiry scan commonly has
  its SDP transaction deferred until the ~12s inquiry completes.
  **Fixed:** widened to 15s.
- **F6 (process, fixed):** DoD was entirely unticked before human review
  was even possible to request; ticked above with round-2 changes
  reflected. Live-hardware re-verification remains genuinely open
  (`OQ-E04-T06-1`), disclosed rather than falsely ticked.
- Reviewer confirmed as already sound and unchanged: null/exception
  handling on both `device.uuids` and `fetchUuidsWithSdp()` fails closed
  in every path; pending-entry-before-query ordering (`:1136` at review
  time) can't be beaten by a fast `ACTION_UUID`; `discoveredAddresses`'
  existing per-session dedup already prevents a duplicate SDP query for
  a repeated `ACTION_FOUND` within one scan.

### Round 2 -- `claude-opus-5`, re-review of the F1/F2 fixes -- APPROVE WITH NITS

Independently reproduced (not taken on faith): `flutter build apk
--debug` succeeds; additionally forced a clean, non-cached recompile
(`./gradlew :app:compileDebugKotlin --rerun-tasks`) specifically to
prove the F2 fix's `ConcurrentHashMap.remove(key, value)` two-arg call
actually resolves to the atomic, equals-based overload rather than
silently binding something else.

- **F1 confirmed resolved.** `delay()` (a genuine suspending function,
  not a disguised blocking call) replaces `Thread.sleep`; independently
  re-confirmed `eventsScope` is `Dispatchers.Main`
  (`TransportApiHost.kt:25`), so the ordering bug (timeout firing before
  the main-thread-delivered `ACTION_UUID` can be processed) is genuinely
  gone.
- **F2 confirmed resolved.** `PendingNexoraCheck`'s five `val`s give it
  full value equality including `token`; both removal call sites
  construct their comparison value from the same local variables in the
  same call frame as the stored entry, so a stale timeout's `remove(key,
  staleValue)` correctly returns `false` (evicts nothing) against a
  newer entry with a different token.
- **No new bug from the F4 fix.** `discoveredAddresses.add(address)`
  sits above the whole UUID block, so a repeated `ACTION_FOUND` for one
  address within a session never reaches `fetchUuidsWithSdp()` twice,
  and the map key being the address means even a hypothetical second
  entry would replace, not accumulate.
- **F3/E04-T07 confirmed coherent and correctly scoped.**
- Nits (non-blocking, addressed same round): style inconsistency between
  the cached-uuids check (`it.uuid`) and `handleUuidResult` (`(it as?
  ParcelUuid)?.uuid`) — aligned to the same safe-cast style; `E04-T07`'s
  `files:` fence was empty despite the implicated file already being
  named in its own `required_context` — filled in. Two S4 items recorded
  rather than fixed: `handleUuidResult`'s own consumption
  (`pendingNexoraChecks.remove(address)`, one-arg) isn't itself
  token-scoped against a late broadcast from a superseded cycle
  (self-heals on the next scan, reviewer judged non-blocking); and the
  address-key-mismatch risk between `ACTION_FOUND` and `ACTION_UUID` on
  some OEM stacks is now named explicitly in `OQ-E04-T06-1` as the first
  thing the still-pending live run must check.
