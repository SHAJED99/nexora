# E04-T07 · Register a Nexora-specific SDP UUID for accurate Discover filtering

## 1. Goal

Close the residual gap E04-T06's review left explicitly named rather
than silently accepted: register a second, bespoke Nexora-specific
service UUID in this app's own SDP record (alongside the existing
generic `NEXORA_SPP_UUID`, which stays for the actual RFCOMM connection
itself — no change to the wire protocol or connection mechanism), and
have E04-T06's Discover-filter SDP check look for THIS UUID instead of
the generic SPP one.

## 2. Background

Filed directly from `E04-T06`'s round-1 independent review finding F3
(`claude-opus-5`, 2026-09-14): that task's Discover-page filter
correctly excludes the overwhelming majority of nearby Bluetooth
accessories (headphones, wearables, most car kits — none of which are
SPP serial devices), which is what the human asked for and is a real,
working improvement. But because `NEXORA_SPP_UUID` is literally the
generic/standard SPP UUID (not bespoke to this app), any other SPP-based
serial device would also pass the same check. The reviewer judged this
non-blocking for `E04-T06` itself (the improvement is real and the
residual class is narrow and unlikely in most home/office environments)
but asked for it to be tracked as its own follow-up rather than left as
an inaccurate "only Nexora" claim.

## 3. What this task does

- Register a second, Nexora-specific UUID (a fresh, randomly-generated
  v4 UUID, not derived from or resembling the standard SPP UUID) as an
  additional SDP service record on this app's existing listening socket
  -- investigate whether `BluetoothAdapter`/`BluetoothServerSocket`'s
  Android API supports attaching a second service record to one existing
  socket, or whether this requires a second, parallel
  `listenUsingRfcommWithServiceRecord` call under the new UUID (this
  task's own investigation, not assumed here).
- Update `handleDeviceFound`'s (E04-T06) SDP-match check to look for the
  new Nexora-specific UUID instead of `NEXORA_SPP_UUID`.
- Update `unmaskIfNotBonded`'s (E04-B21/E04-B22) Nexora-bonded-peer
  filter to the SAME new UUID — this closes the real
  wrong-device-substitution risk E04-B22's own round-2 review found
  (F4), not just Discover's over-broad list.
- Confirm the accept-path listening socket, the discovery-side filter,
  AND the accept-path bonded-peer filter all agree on which UUID means
  "this is Nexora" — a mismatch among any of these three would silently
  break connectivity, discovery, or reintroduce the wrong-device
  substitution risk.

## 4. What this task does NOT do

- Does NOT change the actual RFCOMM connection mechanism or
  `NEXORA_SPP_UUID`'s use for the real data socket — only adds a second,
  discovery-purpose-only service record.
- Does NOT change `acceptLoop`'s exemption from any SDP filter (E04-T06
  §4, corrected wording) — the accept path's safety already comes from
  the secure-socket-implies-bonded invariant, not from UUID matching, and
  stays that way.
- Does NOT add a Kotlin unit-test harness — none exists in this project,
  consistent with every other native-transport task in this epic.

## 5. Definition of Done

- [x] A bespoke Nexora-specific UUID (`NEXORA_DISCOVERY_UUID`, random v4 `6f3b2c1e-8a47-4d2b-9c5e-1b7a0d4e9f21`) is registered as a second SDP service record: `ensureListening` opens a second `listenUsingRfcommWithServiceRecord` socket that is never accepted on, and `release()` closes it. Investigation result: Android offers no API to attach a second record to an existing server socket, so a second socket is the only way. (Commit `ef0faa9`.)
- [x] All three "is this Nexora" checks now use one helper, `advertisesNexora`, which matches the new UUID in either byte order (some stacks report SDP UUIDs byte-reversed): the cached-UUID check in `handleDeviceFound`, the live SDP result in `handleUuidResult`, and the accept-path bonded-peer filter in `unmaskIfNotBonded`. The data connection is unchanged: it still dials `NEXORA_SPP_UUID`.
- [x] Existing bonded peers: their OS UUID cache predates the new record, so `ensureListening` asks bonded devices that are SPP-capable but lack the discovery UUID to refresh via `fetchUuidsWithSdp()`. Headsets and other non-SPP bonds are left alone.
- [x] `flutter build apk --debug` compiles clean, both on the task branch and after merging `development` (`92ded71`).
- [ ] Live-verified on real hardware: Discover still lists a genuine
  Nexora peer; a non-Nexora SPP-capable device (if one is available to
  test against) is now correctly excluded.
