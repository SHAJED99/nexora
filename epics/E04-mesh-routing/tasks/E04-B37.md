# E04-B37 · A disconnected peer that discovery once vouched for is never dropped

## 1. Goal
The Network Status card stops claiming "Connected" once the last link is gone,
including when the peer was found by this process's own discovery scan.

## 2. Root cause (read from source, not inferred)
`dashboard_controller.dart`:

```dart
// _watchLinkState, on disconnected/failed:
if (!_discoveredPeerIds.contains(deviceId)) {
  _knownPeerIds.remove(deviceId);      // line 373-375
}
if (_latestLatencyDeviceId == deviceId) {
  _latestLatencyMs = null;             // line 376-379  <- this half runs
  _latestLatencyDeviceId = null;
}
```
and
```dart
final reading = _knownPeerIds.isEmpty
    ? ConnectivityReading.noPeers
    : (_hasRouteToAnyKnownPeer() ? ConnectivityReading.connected : ...);
```

E04-B34 deliberately left the "discovery still vouches for it" case to
`lostDevices` (E04-B28). But `lostDevices` is emitted only by an **active
discovery scan** ageing a peer out. No scan runs while the Dashboard merely
sits open, so for a peer this process discovered, nothing ever removes it:
`_knownPeerIds` stays non-empty and the reading recomputes to `connected`
forever. The observed split -- latency cleared, status stuck -- is exactly this
branch.

This is `L-process-017`'s shape: an obligation delegated to a mechanism that
has no production caller in the relevant state.

## 3. What this task does
- Makes a link-ending event sufficient on its own to drop the peer from the
  *connectivity* reading, without depending on a scan that may not be running.
- Keeps E04-B28's behaviour intact: a peer that discovery still sees must not
  be resurrected into "Connected" by a stale entry, and a peer legitimately
  present must not be dropped early.
- Adds a regression test that fails on today's code: peer discovered, link
  measured, then `disconnected` -> reading is `noPeers`, with no `lostDevices`
  event at all.

## 4. What this task does NOT do
- Does not touch `BluetoothTransport.kt` or any Kotlin (E04-B36 owns that).
- Does not change discovery, `lostDevices`, or the scan lifecycle.
- Does not redesign the Network Status card or its design contract.
- Does not remove `_discoveredPeerIds`; it stays meaningful for E04-B28.

## 5. Contract
```yaml
- signature: "void _watchLinkState(String deviceId)"
  purpose: "on disconnected/failed, drop the peer from the connectivity set regardless of whether a discovery scan vouched for it, then recompute"
```

## 6. Risks
- **Regressing E04-B28.** That bug was the mirror image (a peer kept after a
  scan lost it). The fix must not reintroduce a peer removed by `lostDevices`,
  nor drop a peer that is genuinely still linked via a second socket.
- **Two sockets for one peer** (OQ-E04-B32-3): a disconnect on one socket must
  not clear a peer that still holds another live link.

## 7. Implementation checklist
- [ ] Peer dropped on `disconnected`/`failed` without requiring `lostDevices`
- [ ] E04-B28 and E04-B27 tests still green, unchanged
- [ ] New regression test: discovered peer + link measured + disconnected, no

  whether or not a discovery scan has vouched for that peer. (FR-UI-004)
