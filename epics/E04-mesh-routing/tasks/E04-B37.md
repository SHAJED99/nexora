# E04-B37 · The routing graph never forgets a link that has gone down

## 1. Goal
`computeRoute` stops returning a route over a link whose connection has
ended, so every caller that asks "is there a path to this peer?" — the
Dashboard's connectivity reading among them — gets an honest answer.

## 2. Root cause (read from source; the first version of this file was wrong)
The first version of this task blamed `dashboard_controller.dart:373`
(`if (!_discoveredPeerIds.contains(deviceId))`). **That was wrong** — it is a
contributing condition, not the cause. The Dashboard's reading is:

```dart
final reading = _knownPeerIds.isEmpty
    ? ConnectivityReading.noPeers
    : (_hasRouteToAnyKnownPeer() ? ConnectivityReading.connected : noRoute);
```

so even with the peer legitimately still in `_knownPeerIds`, the reading would
fall to `noRoute` — *if* `computeRoute` told the truth. It does not:

- `RoutingEngine._knownLinks` is populated **only** by `recordLinkMeasurement`,
  called **only** from `LinkQualityFeed._onMeasurement`.
- `LinkQualityFeed` subscribes to `transport.linkQuality` and **nothing else**.
  It has no `connectionState` subscription.
- `RoutingEngine.removeLink` has exactly **two** callers in `lib/`:
  `onRouteFailure` (routing_engine.dart:341, a *route failure*, not a link
  going down) and the test-only `NetworkSimulator`.

So no production path removes a link when the transport reports
`disconnected`/`failed`. `_knownLinks[self][peer]` survives, `_bestRouteToNode`
finds it, `computeRoute` returns non-null, `_hasRouteToAnyKnownPeer()` stays
true, and the card reads "Connected" forever. This is `L-process-017`'s shape:
a capability (`removeLink`) with no production caller on the path that needs it.

## 3. What this task does
- `LinkQualityFeed` subscribes to `connectionState(deviceId)` for each
  neighbour it has recorded a measurement for, and calls
  `routing.removeLink(routing.selfId, deviceId)` when that peer reports
  `disconnected` or `failed`.
- Subscriptions are keyed by device id (one per neighbour, never two) and are
  cancelled in `stop()`, so tests and `E14-B02`'s gating do not leak them.
- Lives in `start()`/`stop()`, so `bindings.dart`'s existing
  `if (!blockCommunication) linkQualityFeed.start()` gating applies unchanged
  and no binding edit is needed.

## 4. What this task does NOT do
- **Does not touch `dashboard_controller.dart`.** E04-B34's guard is correct
  once routing is honest: a still-discovered peer should read `noRoute`
  ("nearby, not connected"), not `noPeers`. Both existing E04-B34 tests must
  stay green *unchanged* — that is the check that this fix is in the right
  layer.
- Does not change `RoutingEngine`, `removeLink`, or the cost formula.
- Does not touch Kotlin or E04-B36's transport work.
- Does not add re-add logic: a peer that comes back sends a new
  `LinkQuality` measurement, which re-records the link through the existing
  path.

## 5. Contract
```yaml
- signature: "void _onConnectionState(String deviceId, ConnectionState state)"
  purpose: "on disconnected/failed, remove the self->deviceId link from the routing graph"
- signature: "Map<String, StreamSubscription<ConnectionState>> _connectionSubs"
  purpose: "one connectionState subscription per recorded neighbour, cancelled in stop()"
```

## 6. Risks
- **Removing a link that is still alive.** Only `disconnected`/`failed` may
  remove; `connecting`/`connected` must not. A transient `failed` during a
  collision retry (E04-B32) will drop the link — acceptable, because the next
  measurement re-records it, and a stale "Connected" is the worse failure.
- **Subscription leak.** One per neighbour, keyed, cancelled in `stop()` —
  the same shape `InboundPipeline` already uses (inbound_pipeline.dart:784).
- **Wrong layer.** If this were fixed in the Dashboard, every other
  `computeRoute` caller (`RelayEngine`, `CallSignaling`,
  `MessagingCoordinator`) would keep routing over a dead link. That is why
  §4 forbids touching the controller.

## 7. Implementation checklist
- [ ] `LinkQualityFeed` subscribes to `connectionState` per recorded neighbour
- [ ] `disconnected`/`failed` calls `removeLink(selfId, deviceId)`; other states do not
- [ ] Subscriptions keyed, idempotent, and cancelled in `stop()`
- [ ] Regression test: measurement -> route exists -> disconnected -> route is null
- [ ] Existing E04-B34 and E04-B27 dashboard tests green **unchanged**
- [ ] Full Dart suite green
