# E04-B22 · Narrow E04-B21's bonded-device fallback to actual Nexora peers

## 1. Goal

Filter the bonded-device set `unmaskIfNotBonded` falls back to by whether
each bonded device is actually a Nexora peer (advertises
`NEXORA_SPP_UUID` in its SDP record via `BluetoothDevice.uuids`), rather
than treating "exactly one bonded device of any kind" as the
unambiguous case. This closes the gap `E04-B21`'s own review found: the
current guard is inert the moment a phone is also bonded to a
non-Nexora accessory (headphones, a smartwatch, a car kit), which is a
common real-world case, not an edge case.

## 2. Background

Filed directly from `E04-B21`'s round-2 independent review finding N1
(`claude-opus-5`, 2026-09-13): `unmaskIfNotBonded`'s "exactly one bonded
device" narrowing uses `adapter.bondedDevices.size != 1` as its
ambiguity check, but that set contains every Bluetooth Classic AND LE
device this phone has ever bonded with, regardless of whether it speaks
Nexora's own SPP protocol at all. The reviewer judged this non-blocking
for `E04-B21` itself (it still closes the reporting user's specific
live-stuck instance, and leaving a masked value unchanged is no worse
than the pre-fix behavior), but explicitly asked for it to be tracked
as its own follow-up rather than left as an untracked review comment.

## 3. What this task does

- Add a helper (e.g. `isBondedNexoraPeer(device: BluetoothDevice):
  Boolean`) that checks whether `device.uuids` contains
  `NEXORA_SPP_UUID` -- confirm via `BluetoothDevice.fetchUuidsWithSdp()`
  or the cached `device.uuids` (whichever this file's existing patterns
  already rely on elsewhere; investigate before assuming).
- Update `unmaskIfNotBonded` to filter `bondedDevices` down to Nexora
  peers specifically before applying the "exactly one" ambiguity check,
  instead of using the raw bonded-device count.
- Keep the same conservative fallback behavior for zero or multiple
  matching Nexora peers (leave the candidate unchanged) -- this task
  only narrows WHICH set counts as "the bonded devices to disambiguate
  among," not the ambiguity-handling policy itself.

## 4. What this task does NOT do

- Does NOT change the accept-path-only scoping `E04-B21` established
  (this guard still must not apply to the discovery-scan path).
- Does NOT add a Kotlin unit-test harness -- same pre-existing gap
  `E04-B21`/`E04-B17`/`E04-B19` already disclosed (no JUnit/Robolectric
  dependency in this project).
- Does NOT retroactively re-verify `E04-B21`'s own live-repro gap
  (`OQ-E04-B21-1`) -- a separate, already-tracked open question.

## 5. Definition of Done

- [ ] `unmaskIfNotBonded`'s ambiguity check operates over Nexora-peer-only
  bonded devices, not the raw bonded-device set.
- [ ] `flutter build apk --debug` (or equivalent) compiles clean.
- [ ] Existing behavior for the already-covered single-bonded-device
  case is unchanged (no regression on `E04-B21`'s own fix).
