# E04-B22 · Narrow E04-B21's bonded-device fallback to actual Nexora peers

## 1. Goal

Filter the bonded-device set `unmaskIfNotBonded` falls back to by whether
each bonded device is actually a Nexora peer (advertises
`NEXORA_SPP_UUID` in its SDP record via `BluetoothDevice.uuids`), rather
than treating "exactly one bonded device of any kind" as the
unambiguous case. This closes the gap `E04-B21`'s own review found: the
current guard is inert the moment a phone is also bonded to a
non-Nexora accessory (headphones, a smartwatch, a car kit), which is a
common real-world case, not an edge case.

## 2. Background

Filed directly from `E04-B21`'s round-2 independent review finding N1
(`claude-opus-5`, 2026-09-13): `unmaskIfNotBonded`'s "exactly one bonded
device" narrowing uses `adapter.bondedDevices.size != 1` as its
ambiguity check, but that set contains every Bluetooth Classic AND LE
device this phone has ever bonded with, regardless of whether it speaks
Nexora's own SPP protocol at all. The reviewer judged this non-blocking
for `E04-B21` itself (it still closes the reporting user's specific
live-stuck instance, and leaving a masked value unchanged is no worse
than the pre-fix behavior), but explicitly asked for it to be tracked
as its own follow-up rather than left as an untracked review comment.

## 3. What this task does

- `unmaskIfNotBonded` now filters `bondedDevices` down to the subset
  whose (already OS-cached, from bonding-time SDP -- no live
  `fetchUuidsWithSdp()` query needed, unlike E04-T06's discovery-scan
  case) `device.uuids` contains `NEXORA_SPP_UUID`, via the same
  safe-cast pattern E04-T06 already established
  (`(it as? ParcelUuid)?.uuid == NEXORA_SPP_UUID`), before applying the
  "exactly one" ambiguity check -- instead of using the raw
  bonded-device count.
- Keep the same conservative fallback behavior for zero or multiple
  matching Nexora peers (leave the candidate unchanged) -- this task
  only narrows WHICH set counts as "the bonded devices to disambiguate
  among," not the ambiguity-handling policy itself.
- Updated `unmaskIfNotBonded`'s own doc comment to correct E04-B21's
  original "masked placeholder" framing (see `repro:` above) alongside
  documenting this fix.

## 4. What this task does NOT do

- Does NOT change the accept-path-only scoping `E04-B21` established
  (this guard still must not apply to the discovery-scan path).
- Does NOT add a Kotlin unit-test harness -- same pre-existing gap
  `E04-B21`/`E04-B17`/`E04-B19` already disclosed (no JUnit/Robolectric
  dependency in this project).
- Does NOT retroactively re-verify `E04-B21`'s own live-repro gap
  (`OQ-E04-B21-1`) -- a separate, already-tracked open question.

## 5. Definition of Done

- [x] `unmaskIfNotBonded`'s ambiguity check operates over Nexora-peer-only
  bonded devices, not the raw bonded-device set.
- [x] `flutter build apk --debug` compiles clean.
- [x] Existing behavior for the already-covered single-bonded-device
  case is unchanged (no regression on `E04-B21`'s own fix). CORRECTED
  (review round 1, F2): this is NOT automatically true merely because
  the Nexora-filtered subset is a strict subset of the full bonded set —
  a strict subset can be EMPTY, which is exactly the failure mode round
  1 shipped with (see F1 above): a single bonded peer whose `uuids`
  cache happens to miss the SPP record would have regressed from "guard
  fires" to "guard inert". Round 2's `ifEmpty { bondedDevices }`
  fallback is what makes this claim actually true — the single-bonded
  case now behaves identically to E04-B21 regardless of that peer's
  UUID cache state.
- [ ] Live-verified on real hardware on the exact device this bug was
  confirmed on (the Redmi, bonded to both the Pixel and a HOCO headset):
  **partially done 2026-09-14** — real end-to-end delivery over a fresh
  live connection confirmed, but not specifically proven to have
  exercised this task's own UUID-filter fallback code path (see
  `OQ-E04-B22-1`, updated). Left unticked honestly rather than claimed
  as fully proven; a from-scratch pairing test would close this for
  real.

## Open Questions

- `OQ-E04-B22-1`: **PARTIALLY RESOLVED, 2026-09-14.** A fresh accept-path
  connection between the Redmi and Pixel (real ACL connect/encrypt
  events observed in `dumpsys bluetooth_manager`, "Remote initiated")
  DID happen live this session, and end-to-end message delivery through
  the correct, already-resolved conversations succeeded on both devices
  with a genuine live connection (1ms measured latency). However, this
  does NOT specifically confirm this task's own UUID-filtering fallback
  code path was exercised: both real peer addresses were ALREADY known
  as bonded, correctly-resolved relationships from before this session
  (predating the self-referential-address bug entirely on this
  specific pair) — `unmaskIfNotBonded`'s own first line
  (`if (isBonded(candidate)) return candidate`) would short-circuit
  before ever reaching the Nexora-UUID filter this task added, in
  exactly this situation. So: real, successful live delivery is
  confirmed; but WHICH of the three scenarios below actually exercised
  (if any did) remains unconfirmed — that would need a fresh,
  from-scratch pairing to observe directly, which this session did not
  do. Round-1 review named two concrete ways this fix could still be
  inert on that exact hardware, both still worth checking for
  specifically in a future from-scratch pairing test:
  1. (Fixed in round 2, but confirm on-device) a null/stale `uuids`
     cache on the Pixel peer itself would have made `nexoraBondedDevices`
     empty — round 2's `ifEmpty { bondedDevices }` fallback should cover
     this, but hasn't been observed live.
  2. (Not fixable in this task, a real residual risk) the HOCO ES64
     Ultra headset may ITSELF advertise the generic SPP UUID (many BT
     audio chipsets do) — if so, `nexoraBondedDevices.size == 2` (both
     the Pixel and the HOCO match), the guard stays inert on this exact
     device even after this fix, and only `E04-T07`'s bespoke
     Nexora-specific UUID would close it.
  3. (Round-2 review, F4 — a sharper variant of #2, not just "inert"):
     if the genuine Nexora peer's own `uuids` cache misses AND the HOCO
     headset's cache hits on the generic SPP UUID, `nexoraBondedDevices
     = [HOCO]` (size 1) — the round-2 `ifEmpty` fallback does NOT
     rescue this case (the filtered set isn't empty, just wrong), and
     the headset's address gets substituted in as if it were the peer.
     Confirmed harmless on THIS hardware specifically (a headset can't
     be a Nexora peer either way, so the conversation stays undialable,
     just differently), but the general form — two real bonded Nexora
     peers, one with a cache hit and one without — is a genuine
     wrong-device-substitution risk `E04-T07` also needs to account for.
  A one-line logcat of `nexoraBondedDevices.size` (and which device(s)
  matched) on the Redmi during a live accept event would distinguish
  all three cases in minutes.

## Review

### Round 1 -- `claude-opus-5`, independent review of PR #254 -- CHANGES REQUESTED

- **F1 (blocking):** the Nexora-UUID filter's own doc-comment/DoD claimed
  behavior for the single-bonded-device case is "unchanged from E04-B21",
  but a cached `uuids` MISS (E04-T06's own already-documented case --
  populated at bond time, so a peer bonded before it ran Nexora has no
  cached SPP record) silently excluded that peer from
  `nexoraBondedDevices`, regressing the exact single-bonded-device case
  this task promised not to break: `nexoraBondedDevices.size == 0` (not
  1), guard falls through, stays inert. **Fixed:** falls back to the raw
  `bondedDevices` set (`ifEmpty { bondedDevices }`) whenever the
  UUID-filtered subset is empty -- sound under this function's own
  accept-path invariant (exactly one bonded device at all, UUID cache or
  not, is still unambiguous).
- **F2 (blocking, docs):** the task file's DoD asserted the
  single-bonded-device case behaves identically "because the filtered
  subset is a strict subset" -- true of subset-ness generally, but a
  strict subset can be empty, which is precisely F1's bug. Wording
  corrected to state the fallback (not subset-ness alone) is what makes
  the claim true.
- Confirmed as already sound: exact reuse of E04-T06's reviewed
  safe-cast pattern (`(it as? ParcelUuid)?.uuid == NEXORA_SPP_UUID`); the
  doc-comment correction (real address, not a placeholder) is purely
  documentary and doesn't change the fix's safety properties; `files:`
  fence honored.
- F3 (non-blocking, disclosed): efficacy on the exact target device
  (the Redmi) is still unproven either way -- the HOCO headset may
  itself advertise the generic SPP UUID, in which case the guard stays
  inert on that exact hardware even after this fix (only `E04-T07`'s
  bespoke UUID would close that). Recorded in `OQ-E04-B22-1` rather than
  claimed resolved.
