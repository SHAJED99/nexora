# E04-B11 · `send()` freezes the app and self-disconnects a freshly-bonded peer

## 1. How this was found
Live, hands-on diagnosis of a real user-reported send failure (the human
tried to message a peer on the Redmi 10 2022 and got "Message not sent —
Could not reach this device in time. Try again."), continuing directly from
`E04-B10`'s own investigation. Toggling Bluetooth off/on on both devices and
bringing them physically together produced, for the first time this
project, **a real, live, successful `createBond()`** (`BOND_STATE_BONDED`
observed via `dumpsys bluetooth_manager` on the Redmi, twice) — a genuine
positive result for `E04-B10`'s own primary open question. But the send
still failed, on both attempts, right after the bond completed.

`dumpsys bluetooth_manager`'s own `Connection Events` log on the Redmi
showed the real sequence both times:
```
04:50:55  CLASSICAL-CONNECTED     b8:db:38 SRPhone P   status = Success
04:51:00  CLASSICAL-DISCONNECTED  b8:db:38 SRPhone P   status = Local Terminated Connection
```
The physical radio link succeeds. ~5 seconds later, **the Redmi itself**
(not the peer, not a radio failure — "Local Terminated Connection" is an
OS-level classification for a locally-initiated teardown) closes it.
`logcat` at that exact moment shows Android's own input dispatcher declaring
the app unresponsive:
```
04:51:00.495  W InputDispatcher: Not sending touch gesture to ... ActivityRecordInputSink
              com.nexora.nexora/.MainActivity because it is not responsive
```
— read at the time as a real ANR-class main-thread freeze, timed exactly
to the disconnect. **Correction (see "On-device verification" below,
added after this section was written): this specific warning was later
shown, via a direct control test, to also appear with zero Bluetooth
activity at all — it does not reliably indicate an app freeze on this
device, and should not have been treated as confirming evidence on its
own.** The underlying code defect described in §2 below is still real and
independently confirmed a different way (thread-name + timing
instrumentation, not this warning) — only the ANR-based reasoning that
originally motivated looking for it is retracted.

## 2. Root cause
`BluetoothTransport.kt:634-674`, `send()`:
```kotlin
fun send(deviceId: String, bytes: ByteArray): Boolean {
    ...
    Thread({ result.set(writeFrame(socket, bytes)); done.countDown() }, ...).start()
    val settled = done.await(SEND_TIMEOUT_MS, TimeUnit.MILLISECONDS) // SEND_TIMEOUT_MS = 3_000L
    if (!settled) {
        disconnect(deviceId) // torn down right here, on whatever thread called send()
        return false
    }
    ...
}
```
`done.await(3_000, MILLISECONDS)` is a genuine **blocking** call. `send`'s
Pigeon interface (`pigeons/transport.dart:79`, `bool send(String deviceId,
Uint8List bytes);`) has **no `TaskQueue` annotation**, so — same class of
risk this codebase's own `E04-T03c` review already flagged once, and chose
to bound at 3s rather than eliminate — Pigeon dispatches it on the
**platform (UI) thread** by default. Whenever the write doesn't complete
within 3 seconds (measured here to be a real, reproducible condition right
after a fresh bond, before the peer's RFCOMM channel is fully settled),
`send()` blocks the entire app's UI thread for the full 3 seconds. That is
long enough, on this hardware, to produce a genuine ANR-class freeze
(confirmed live via `InputDispatcher`'s own "not responsive" warning), and
when the wait times out, `disconnect(deviceId)` runs — from that same
blocked thread — tearing the connection down. This is exactly what
"Local Terminated Connection" in the OS Bluetooth log means, and exactly
why the human sees "Message not sent."

**This is not a radio/RF/environmental issue** (that hypothesis, tracked in
`E04-B10`, is now largely superseded for this specific failure mode — the
link genuinely connects). It is a real, reproducible, fixable software
defect: a blocking wait on the platform thread with a large enough timeout
to freeze the app and self-sabotage the very connection it's trying to use.

## 3. What this task does
1. Move `send()`'s blocking wait off the platform/UI thread. The
   established, minimal-risk fix Pigeon offers for exactly this shape is a
   `TaskQueue` (`TaskQueueType.serialBackgroundThread`) on the `send` method
   in `pigeons/transport.dart`, regenerated via `dart run pigeon` (same
   process `E04-B09` used for `requestDiscoverable` — confirm byte-identical
   codegen the same way that task's review did, not hand-edited).
2. Audit `connect()` (`BluetoothTransport.kt:358`) and any other
   Pigeon-exposed method on this same interface for the identical risk —
   confirm which of them do or don't already offload their blocking work
   correctly (`doConnect`/`doConnectAfterBond`'s own socket work already runs
   on a background `Thread`, so `connect()` itself returns quickly today;
   confirm that finding on paper rather than assuming, since this task's own
   discovery method was "read the code and assume it's fine" failing once
   already for `send()`).
3. Preserve `send()`'s existing behavior and contract exactly (bounded
   3s wait, disconnect-and-fail on timeout, `writeFrame`'s framing and
   `synchronized(socket)` guard, `recordSendOutcome`/`onLinkQuality`
   reporting) — this task changes **which thread blocks**, not what the
   method does or how long it waits.
4. Verify live, on real hardware, that the exact failure sequence
   documented in §1 no longer reproduces: bond the two test devices fresh
   (or reuse the current live bond — confirm `dumpsys bluetooth_manager`
   still shows `BOND_STATE_BONDED` for the pair), send a message
   immediately, and confirm the UI never freezes (no `InputDispatcher`
   "not responsive" warning in `logcat` during the send) and the message
   actually reaches the peer's chat thread instead of erroring.

## 4. What this task does NOT do
- Does **NOT** change `SEND_TIMEOUT_MS`'s value or `send()`'s retry/error
  contract — this is a threading fix, not a tuning task. If live testing
  shows 3s is itself too short or too long, that's a separate, disclosed
  Open Question, not something to silently adjust here.
- Does **NOT** touch the bonding flow (`startBondAndConnect`,
  `doConnectAfterBond`, `handleBondStateChanged`) — `E04-B10`'s own live
  evidence shows that path now genuinely works end-to-end; this task's
  scope is strictly the send-path freeze.
- Does **NOT** re-attempt `E04-B10`'s remaining open items (F1/F2 live
  confirmation now largely done by this session's own evidence; leave that
  task's own bookkeeping to itself).
- Does **NOT** add new Pigeon methods, new UI, or new design surface.

## Risks
- A `TaskQueue` change to a Pigeon method's dispatch is a real behavioral
  change to threading — verify no other code path assumes `send()` runs
  synchronously on the calling (platform) thread before this ships.
- This may not be the ONLY main-thread-blocking call in this transport
  layer — §3.2's audit exists specifically because "assume the rest is
  fine" is exactly the assumption that let this bug ship unnoticed the
  first time.

**Self-correction, disclosed plainly (rule 7 in action):** this task's own
§1 "How this was found" cited a repeating `InputDispatcher "...not
responsive"` warning as evidence of a genuine ANR caused by `send()`'s
blocking wait. **That evidence does not hold up.** A direct control test —
opening and dismissing the on-screen keyboard on the SAME chat screen, with

`ActivityRecordInputSink` transition tied to keyboard show/hide, not a

the platform thread. The underlying code-level defect this task fixes
(`done.await(3000ms)` on the platform thread, confirmed by reading
`BluetoothTransport.kt` directly) is still real and still worth fixing —
Pigeon dispatching a bounded-blocking `@HostApi()` method on the platform
thread by default is a genuine risk regardless of what the ANR warning
did or didn't prove — but the causal chain originally drawn from "ANR
observed → therefore send() was blocking → therefore this caused the
disconnect" was not established as claimed, and is corrected here rather
than left standing.

**What IS independently, freshly confirmed, with real evidence (temporary
`Log.d` instrumentation added to `send()`/`writeFrame()`, observed live,
then fully reverted — confirmed via `git diff` showing zero trace before
this commit):**
- `send() called, thread=flutter-worker-2` — **not** the platform thread.
  The `TaskQueue` fix is genuinely engaging; Pigeon is dispatching this
  method on its own background worker as intended.
- `writeFrame OK in 0ms` — the actual native write completes essentially
  instantly once a connection is up. There is no multi-second stall in the
  raw byte transfer itself on this hardware.
- On this same attempt, the underlying Bluetooth connection **stayed up**
  afterward — `dumpsys bluetooth_manager` showed no further disconnect
  event following this send, unlike every pre-fix attempt this session
  (which reliably disconnected ~4-5s after connecting). This is real
  evidence the fix removed at least one self-inflicted-disconnect
  pathway.

**What is NOT yet resolved — the user still could not send a message
end-to-end after this fix, on the same hardware, same session:** tracing
the failure up the stack (`chat_controller.dart`'s `send()` → the
`TimeoutException` handler showing "Could not reach this device in
time.") led to `PrekeyExchange.ensureSession` — a **Signal Protocol
session-establishment round trip** that requires the peer to receive AND
respond to a bundle request, not just receive raw bytes. Checking the
Pixel's own "Network Nodes" list directly: it has no relationship entry
at all for the Redmi's real, currently-bonded address (only a stale entry
pointing at an unrelated Windows desktop, per `E04-B10`'s own earlier
finding). This strongly suggests the Pixel's `InboundPipeline` may be
silently dropping the Redmi's incoming request as unrecognized, rather
than the transport itself failing again — but this was not fully traced
to a confirmed root cause before the physical devices had to be released
(the human needed the Pixel back for other use, and an Android emulator
cannot substitute — no real Bluetooth radio, already established
precedent in this project). **Filed as `E04-B12`, distinct from this
task's own scope** (this task is specifically the `send()`
platform-thread-blocking defect; the handshake-level gap is a different
layer and a different, not-yet-root-caused mechanism).

## connect() audit
Traced `connect()` (`BluetoothTransport.kt:358`) directly: it calls
`ensureListening()` (fast after the first call — `if (acceptThread !=
null) return`), `isBonded()` (an in-memory `Set` lookup), then either
`startBondAndConnect()` (calls `createBond()`, which is itself
non-blocking/async — the OS handles pairing UI and reports back via
`ACTION_BOND_STATE_CHANGED`, not a synchronous return) or `doConnect()`
(spawns a background `Thread` and returns immediately — the actual
blocking `socket.connect()` call happens on that spawned thread, never on
the caller's thread). **`connect()` itself does not block its caller
beyond fast, in-memory work** — confirmed by tracing every statement on
its own call path, not assumed. `disconnect()` was also checked:
`socket.close()` is a plain OS call, not a designed multi-second wait like
`send()`'s `CountDownLatch.await(3000ms)` — a different risk class,
no `TaskQueue` warranted there.

  **`serialBackgroundThread` is the correct choice — falsified against
  the engine source, not the annotation name.** The generated Kotlin
  emits `binaryMessenger.makeBackgroundTaskQueue()` (no args);
  Flutter engine `shell/platform/android/io/flutter/plugin/common/
  BinaryMessenger.java:41` sets `TaskQueueOptions.isSerial = true` by
  default and `:67-68` routes the no-arg overload through
  `new TaskQueueOptions()`. So dispatch is genuinely **serial** — per-call
  send ordering is preserved exactly as it was on the platform thread,
  which a length-prefixed framing protocol with no resync marker
  requires. A concurrent queue would have been the wrong pick here even
  though `writeFrame`'s `synchronized(socket)` would have kept it safe.

  **No caller assumes synchronous-on-calling-thread completion —
  checked both sides.**
  - *Dart side:* every Pigeon host method is already `Future`-returning
    and asynchronous over the platform channel regardless of native
    thread, so no Dart caller can hold such an assumption by
    construction. Traced the real chain anyway:
    `transport_service.dart:158` (`_api.send`) →
    `messaging_stack.dart:601` →
    `connection_ensuring_sender.dart` `ensureConnectedAndSend` (awaits
    `send`, guards with try/catch, `false` on failure) →
    `RelayEngine._attempt`. All `await`-based. No change in observable
    Dart semantics.
  - *Native side (the real risk surface):* `send()`'s transitive path —
    `openSockets` (`ConcurrentHashMap`), `writeFrame`
    (`synchronized(socket)`), `recordSendOutcome`
    (`synchronized(window)` over a `ConcurrentHashMap` entry),
    `disconnect()` (atomic `ConcurrentHashMap.remove`, idempotent),
    `eventsScope.launch` — touches **no** `Activity`/UI-bound API and
    every piece of shared state it reads or writes is already
    explicitly thread-safe. `BluetoothTransport.kt:688`'s own existing
    comment ("Thread-safe: `send()` can be invoked from more than one
    caller") shows T03c already designed for this. The one new
    interleaving this fix permits — a `disconnect()` from the send queue
    racing a Dart-initiated `disconnect()` on the platform thread — is
    safe: both removes are atomic, the loser gets `null`, worst case is
    a duplicate `DISCONNECTED` event.
