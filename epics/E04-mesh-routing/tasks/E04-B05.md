# E04-B05 · `TransportService.connect()` is fully implemented, fully reviewed (E04-T03b), and never called

## The defect

`TransportService.connect(String deviceId)`
(`lib/core/transport/transport_service.dart:106-144`) is a real,
already-implemented, already-reviewed method: it subscribes to the
`onConnectionStateChanged` stream, calls the native `TransportApi.connect`,
and awaits the real settle event. Grepping the entire `lib/` tree for any
production call to it
(`grep -rn "transport.connect(\|\.connect(deviceId)\|\.connect(peer" lib/`)
returns **only the method's own definition** — nothing in production ever
calls it.

Native `BluetoothTransport.send()`
(`android/app/src/main/kotlin/com/nexora/nexora/transport/BluetoothTransport.kt:242`)
has its own hard contract: `val socket = openSockets[deviceId] ?: return
false`. A socket is only ever placed in `openSockets` by a successful
`connect()`. `RelayEngine`'s own `send:` function is wired directly to
`resolvedTransport.send` in `lib/core/messaging/messaging_stack.dart` — so
every real send this app has ever attempted against a real peer hit that
`?: return false` unconditionally. Discovery (`E04-T03a`/`E04-B04`) and
trust verification (`E02`) both genuinely work over real Bluetooth; the
actual message hand-off never could.

## Repro (confirmed on two real physical devices)

1. Two devices with the app installed, both signed in, mutual Bluetooth
   trust already established (Discover + Verify/Allow on both sides —
   this part works and was independently confirmed live).
2. On device 1, open the chat with the now-trusted peer and send a real
   message ("Hello from device").
3. The message shows as sent locally on device 1 (row inserted, queued for
   relay) but **never arrives on device 2** — Dashboard/route status on
   device 1 shows "No route to this peer" persistently, even after a
   fresh Discover pass.
4. `adb logcat` on **both** devices, filtered for any Bluetooth-transport
   tag, shows **zero** lines for the entire send attempt — confirming
   `connect()`/the native socket path was never invoked at all, not merely
   that it failed silently.

## Expected

A message queued to an already-trusted, already-discovered peer is
delivered once `RelayEngine` has a route to it — `EARS-TRANSPORT-3` (WHEN
two devices have a connected Bluetooth link, sending SHALL deliver the
identical bytes to the other) and `FR-ROUTE-003`/`FR-ROUTE-004`.

## Actual

The message is queued forever (or retried and re-queued per
`RelayEngine._attempt`'s own bounded-retry contract) because nothing ever
establishes the socket `send()` requires. This is invisible in every prior
test suite: no existing test exercised the real
`MessagingStack.create → TransportService.send` wiring against a scenario
where `connect()` mattered, because every fake/mocked transport in every
test only ever needed to simulate `send()` succeeding.

## Severity

**S1** — this is a total, silent failure of the app's core value
proposition (mesh message delivery). Every prior review of `RelayEngine`
(`E04-T04`), `RoutingEngine`, and `TransportService.connect`
(`E04-T03b`) was individually correct against its own task file's
contract; the gap is that no task's contract ever assigned anyone the job
of actually calling `connect()` before a send. Same recurring shape as
`E06-B02` ("a second live instance... silently steals... transport
events") and `E07-B03` ("the make-before-break controller is built,
tested, and never run") — an unwired capability, this project's own
`L-process-007` pattern, for a third time.

## Fix

New `ConnectionEnsuringSender`
(`lib/core/transport/connection_ensuring_sender.dart`) wraps
`TransportService.connect`/`.send` into one `RelaySendFn`-shaped function
(`ensureConnectedAndSend`): connect first (once per device, coalesced via
a `_pendingConnects` map against concurrent sends to the same peer — the
same pattern `PrekeyExchange.ensureSession`'s own `_pending` map already
establishes in this codebase), then send. A failed or throwing send drops
the device from `_connectedDeviceIds` so the *next* attempt reconnects
rather than trusting a socket that may have silently died.
`messaging_stack.dart` now constructs one `ConnectionEnsuringSender` per
stack and wires `RelayEngine(send: connectionEnsuringSender
.ensureConnectedAndSend)` instead of `send: resolvedTransport.send`
directly. `RelayEngine` itself is untouched — its own task contract
(`E04-T04`) still owns queuing/retry/expiry; this only changes what its
injected `send` function actually does underneath.

## What this fix does NOT do
- Does NOT change `RelayEngine`, `RoutingEngine`, or
  `BluetoothTransport.kt` — all three already do exactly what their own
  task files specify; the gap was purely in how they were wired together.
- Does NOT add proactive/eager connection to every discovered device —
  connection is established lazily, only when there is real data queued
  to send, matching `ADR-0004`'s "opaque, store-and-forward" framing (a
  device with nothing queued for it is never worth an open socket).
- Does NOT add a keep-alive/heartbeat to proactively detect a dropped
  connection — a stale socket is discovered the next time something is
  actually sent (this class's own connected-state bookkeeping is cleared
  on a failed send).
- Does NOT change `RelaySendFn`'s signature or any other injection point
  `RelayEngine` exposes.

## Regression note (the wide, cascading part of this fix)

Wiring `ConnectionEnsuringSender` into `messaging_stack.dart` broke 15
previously-passing tests across 6 files, because every one of those
tests' fake/mocked transports only ever simulated `send()` succeeding —
never `connect()`, since production never called it before this fix:
- 5 files use the established Pigeon-mock pattern
  (`mockSendAlwaysSucceeds(suffix)` registering a handler for
  `TransportApi.send.$suffix`): `messaging_stack_test.dart`,
  `group_crypto_service_test.dart`,
  `group_key_rotation_service_test.dart`,
  `group_membership_service_test.dart`,
  `send_group_message_use_case_test.dart`. Each got a parallel
  `mockConnectAlwaysSucceeds(suffix)` helper (mocks
  `TransportApi.connect.$suffix` to accept, then fires the real
  `TransportEventsApi.onConnectionStateChanged` settle event with
  `ConnectionState.connected` — mirroring `TransportService.connect`'s
  own real two-channel contract), called everywhere the existing
  `mockSendAlwaysSucceeds` was called.
- 2 files (`messaging_coordinator_test.dart`,
  `messaging_coordinator_background_test.dart`) instead define a
  `_ControlledSendTransport extends TransportService` fake that overrides
  only `send()`. Added `@override Future<bool> connect(String deviceId)
  async => true;` to each, since these fakes only ever needed to control
  `send()`'s own timing/count, not the connect step.
- One additional call site in `group_membership_service_test.dart` used a
  `wireSend(...)` helper that bypassed the other call sites' own
  mock-registration; fixed by adding `mockConnectAlwaysSucceeds(aSuffix)`
  immediately before that `wireSend` call.

## Review round 1 (CHANGES-REQUESTED) — findings and fixes

The independent reviewer (claude-opus-5) found the fix above genuinely
correct as far as it went, but incomplete: **F1 (blocking, S1)** — four
production call sites still called `TransportService.send` directly,
bypassing `RelayEngine`/`ConnectionEnsuringSender` entirely:
`prekey_exchange.dart:651` (first-contact bundle-request send — sits
*upstream* of every `RelayEngine` send, so this alone reproduces the
original repro identically after merge), `delivery_ack.dart:517`,
`call_signaling.dart:1055`, and
`location_share_service.dart:322`. Also two non-blocking findings: **F2**
— a doc comment claiming a failed send always tears down the native
socket, true only for the timeout branch, not a plain `IOException` write
failure; **F4** — no timeout on `TransportService.connect`'s own settle
future, so a connect that never settles at all could wedge
`ConnectionEnsuringSender._pendingConnects` forever.

**F1 fix — widened scope.** `MessagingStack` gained a new field,
`directSend` (`RelaySendFn`), set to the SAME
`connectionEnsuringSender.ensureConnectedAndSend` instance `relayEngine`
already uses. All four call sites now use `_stack.directSend(...)`
instead of `_stack.transport.send(...)`. `RelayEngine`/`RoutingEngine`
remain untouched — this only adds one new field alongside the existing
`transport` field, exposing the connect-then-send path to the sub-
protocols that intentionally bypass `relayEngine.enqueue` for a direct,
unqueued send.

**A real root-cause bug found and fixed during F1's own regression
sweep.** `PrekeyExchange._sendControlFrame` previously called
`_stack.transport.send(...)` and never checked its return value — safe
before this task, because a genuine transport failure there threw a
`PlatformException` that propagated all the way up through
`_ensureSessionUncoalesced` (which has no `catch`, only `finally`) to
`_sendOne`'s own `catch(_) {}`, failing the whole `ensureSession` attempt
immediately. `ConnectionEnsuringSender.ensureConnectedAndSend` **never
throws** by its own design contract (`RelayEngine._attempt` needs a plain
`false`, not an exception) — so once `_sendControlFrame` switched to
`directSend`, a failed send now returned `false` silently, `_sendControlFrame`
ignored it, and `_ensureSessionUncoalesced` fell through to
`completer.future.timeout(timeout)`, pointlessly waiting out the FULL
`ensureSession`/`_fanOutSessionTimeout` duration for a bundle response
that a known-failed send could never have triggered. Caught by
`group_membership_rate_limit_test.dart`'s own unreachable-member fan-out
test, which regressed from completing in under a second to hanging past
the test framework's own 30s default timeout. Fixed: `_sendControlFrame`
now checks `directSend`'s return value and throws
`AppFailure('messaging.transport_send_failed')` on `false`, restoring the
original fail-fast contract explicitly rather than relying on an
incidental exception that no longer exists.

**F2 fix** — the doc comment on `ConnectionEnsuringSender._connectedDeviceIds`
now states the real, narrower claim: a native write that TIMES OUT does
tear the socket down and emit `DISCONNECTED`
(`BluetoothTransport.kt`'s own timeout branch), but a plain `IOException`
write failure returns `false` while the socket is left open and keyed in
`openSockets`, with no event emitted — forgetting the connection here is
still the right heuristic (never trust a failed send blindly), it just
doesn't always match native reality. The native-side gap itself (a
possible stale-but-open socket, and its leaked read thread) is disclosed
as a real follow-up, out of this file's own fence.

**F4 fix** — `ConnectionEnsuringSender` gained a `connectTimeout`
constructor parameter (default 30s, matching a reasonable real-world
Bluetooth connect bound), applied via `.timeout(connectTimeout, onTimeout:
() => false)` around the connect call. New test:
"a connect() that never settles times out instead of wedging the
coalescing map forever."

**A second, unrelated bug found while testing F4's own fix.** A `ConnectFn`
test double that always throws (`(deviceId) async => throw
Exception(...)`, never returning normally) is reified by the Dart runtime
as `Future<Never> Function(String)`, not `Future<bool> Function(String)`,
despite `ConnectFn`'s own declared typedef — calling `.timeout(onTimeout:
() => false)` directly on that narrower runtime-typed future throws a
*separate*, synchronous `TypeError` from `.timeout()`'s own generic
type-check, before `.timeout()` ever subscribes an error handler to the
original future. The result: the original thrown exception has no
listener at all and is reported as a genuinely unhandled async error by
the test zone a beat later, even though the `TypeError` itself lands in a
`try`/`catch` and looks handled. Reproduced in isolation (a minimal
throwing-closure `.timeout()` repro outside this codebase, then
confirmed the same failure inside `connection_ensuring_sender_test.dart`'s
own pre-existing "a connect() that throws" test, which the F4 timeout
addition alone regressed). Fixed with a small explicit wrapper,
`_callConnect(deviceId) async => connect(deviceId)`, whose own declared
`async` return type is `Future<bool>` regardless of what `connect`'s
concrete implementation happens to infer — `.timeout()` is called on
THIS wrapper's future, never on `connect(deviceId)`'s own future
directly.

**Test-file mock updates for the widened F1 scope.** Every test exercising
`prekey_exchange.dart`/`delivery_ack.dart`/`call_signaling.dart`/
`location_share_service.dart`'s real Pigeon-mock wiring needed the same
kind of `TransportApi.connect.$suffix` mock added alongside its existing
`TransportApi.send.$suffix` mock (mirroring the original PR's own
`mockConnectAlwaysSucceeds` pattern): `prekey_exchange_test.dart`,
`delivery_ack_test.dart`, `call_signaling_test.dart` (two separate
helpers in this file), `location_share_service_test.dart`,
`chat_controller_test.dart` (chat's first-contact path goes through
`PrekeyExchange`), and `relay_priority_test.dart` (an existing
"review F6" direct-send-path test for `CallSignaling`).
`group_membership_rate_limit_test.dart` needed a *fast-failing* connect
mock instead (`accepted: false` immediately) — its own members are
deliberately never-reachable fakes, and after the `_sendControlFrame`
fail-fast fix, a mocked-to-fail connect is what makes that test's
already-established "unreachable member never blocks the local change"
assertion actually fast again.
