# E04-T01 · Route/battery/latency/partition simulator

## 1. Goal
Give every later routing task (T02's cost/migration engine, T04's relay)
something deterministic to test against — a pure-Dart, no-hardware
simulated mesh topology with controllable latency, packet loss, battery
drain, and partition/heal events — per the epic's own Test strategy note
that this is arguably its own deliverable.

## 2. Business logic
- FR-VER-004: a testing/simulation framework for route/battery/latency/
  partition behavior. This task builds exactly that framework — not a
  specific test suite, but the harness later tests are written against.
- The simulator models a directed graph of `SimulatedLink`s between named
  nodes, each with mutable `latencyMs`, `packetLossRate` (0.0-1.0),
  `batteryDrainPerMessage`, and an `up`/`down` state a test can toggle to
  simulate a partition and a later heal.
- Time does not really pass — the simulator exposes a `tick()` the test
  controls, so tests are fast and deterministic, never `Future.delayed`.

## 3. What this task does
- `NetworkSimulator`: add/remove nodes, add/update/remove `SimulatedLink`s
  between two node ids, `tick()` to advance simulated time by one step,
  `send(from, to, bytes) -> SendResult` (delivered/lost/noRoute) that
  consults the current link graph and applies loss/latency/battery cost.
- `SimulatedLink`: value object (immutable, `copyWith`) holding the four
  mutable properties above plus `up`/`down`.
- Deterministic randomness: packet loss uses a seeded `Random` the test
  constructor supplies — no real randomness, ever, so a failing test is
  reproducible.

## 4. What this task does NOT do
- Does NOT implement the routing engine itself (cost formula, route
  selection, migration) — that's T02, which consumes this simulator in its
  tests.
- Does NOT touch real transport (Bluetooth/Wi-Fi) — this is pure Dart,
  in-memory, no platform channel, no Pigeon.
- Does NOT persist anything — the simulator is test/dev-time only, never
  imported by production `lib/features/` code.
- Does NOT model application-level message semantics (delivery receipts,
  ordering, dedup) — that's E05; this only models whether bytes get from A
  to B at the transport-cost level.

## 5. Contract

### Functions
```yaml
- signature: "NetworkSimulator(seed: int)"
  purpose: "Deterministic constructor — same seed, same sequence of loss/random decisions"

- signature: "NetworkSimulator.addNode(id: String) -> void"
  purpose: "Registers a node id in the topology"

- signature: "NetworkSimulator.setLink(from: String, to: String, link: SimulatedLink) -> void"
  params: { link: "latencyMs, packetLossRate, batteryDrainPerMessage, up — directional, A->B may differ from B->A" }
  purpose: "Creates or replaces a directed link"

- signature: "NetworkSimulator.removeLink(from: String, to: String) -> void"
  purpose: "Simulates a link disappearing entirely (not just going down)"

- signature: "NetworkSimulator.tick() -> void"
  purpose: "Advances simulated time by one discrete step; link state changes scheduled via setLink take effect at the next tick a test chooses to call it"

- signature: "NetworkSimulator.send(from: String, to: String, bytes: Uint8List) -> SendResult"
  returns: "SendResult.delivered(latencyMs) | SendResult.lost | SendResult.noRoute — noRoute if no link or link is down"
  purpose: "One hop's worth of a send attempt; multi-hop path simulation is T02's job (it calls send() once per hop along the route it computed)"

- signature: "NetworkSimulator.batteryDrainedFor(nodeId: String) -> double"
  returns: "cumulative simulated battery cost, for tests asserting a route choice minimized drain"
  purpose: "Read-only accumulator, sums every successful send's batteryDrainPerMessage on the sending node"
```

## 6. Risks
- Keep this genuinely deterministic — any `DateTime.now()`/`Random()`
  without an explicit seed anywhere in this file makes every test that uses
  it flaky. Grep the diff for both before calling this done.
- Resist the temptation to model more than T02 actually needs yet (e.g.
  full multi-hop pathfinding) — this task is the *substrate*, T02 owns
  path computation.

**Assessment of the builder's disclosed sequencing deviation.**
Not a problem here, and the disclosure itself is the right behavior. The §7
red-first item is a mechanism against one specific failure mode: writing
assertions that pass against whatever the code happens to do. The
countermeasure is that assertions be independently derivable, and for a pure

§5/§8, not to reading the implementation back. I re-derived each assertion

exactly the residual this sequencing leaves behind, and it is now closed.
Honest disclosure beats a false red-first claim. No lesson file for a single
occurrence; a recurrence should promote one.

**Flags for E04-T02's builder (API shape — no change requested here):**
1. `SimulatedLink` is described as a value object and has `copyWith` but **no
   `==`/`hashCode`** (`simulated_link.dart:10-56`). `SendResult` has them; the
   link does not — which is why the copyWith test compares field by field.
   Expect `expect(sim.linkBetween(a, b), equals(link))` to fail surprisingly.
2. `tick()` is a bare counter (`network_simulator.dart:80-82`) and nothing in
   the simulator reads `_tickCount`. There is **no per-tick sampling hook** —
   no way to vary link quality by tick, and no record of which tick a `send()`
   occurred on. T02's migration stability window will have to correlate ticks
   to sends in its own scaffolding, or extend the simulator under a new scope
   note (this file's contract is closed).
3. `send()` takes `Uint8List bytes` but **ignores the payload entirely**;
   latency and battery are per-message, not per-byte. T02 must pass a dummy
   payload on every hop and cannot model size-proportional cost.
4. No reset for the battery accumulator — a fresh `NetworkSimulator` per
   scenario is the only way to zero it.
5. Multi-hop is correctly absent (§4/§6). One `send()` per hop is the intended
   shape and it composes cleanly for that.
