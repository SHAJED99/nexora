# E04-T05 · Wire real device discovery into the Devices screen

## 1. Goal
Replace the Devices screen's "Discover" no-op (built as a stub in E02-T02,
`design/gaps.md` GAP-004) with real nearby-device discovery, using T03's
`TransportService` — the screen's design/layout does not change, only what
powers the "Discover" action and the list.

## 2. Business logic
- FR-DISC-001: tapping "Discover" starts real Bluetooth discovery
  (`TransportService`'s discovery stream, T03a/T03b) instead of showing a
  "not available yet" snackbar.
- FR-UI-004: a discovered device that has no existing `Relationship` row
  shows as Unknown, per E02's existing trust-state model — this task does
  NOT invent a new state; a discovered device is evaluated through the
  same `RelationshipRepository`/`EvaluateConnectionRequestUseCase` E02
  already built.
- Discovered-but-not-yet-connected devices are additive to the existing
  relationship list, not a replacement — a device the user has already
  evaluated (trusted/blocked/allowed) keeps showing even if it's not
  currently in Bluetooth range, per the design contract's existing
  element set (no new elements this task can invent without a design gap).

## 3. What this task does
- `DevicesController.discover()`: replaces the snackbar no-op with
  `TransportService.startDiscovery()`; subscribes to
  `discoveredDevices`, and for each newly-seen device id not already in
  `relationships`, calls `EvaluateConnectionRequestUseCase` (E02) to get
  its current trust state (defaults to `unknown` for a never-seen device)
  and adds it to the displayed list.
- Stop discovery (`TransportService.stopDiscovery()`) when the controller
  is disposed (`onClose`) — don't leave a scan running after the user
  leaves the screen.
- No change to `verify()`/`block()` — those already work against
  `RelationshipRepository` per E02.

## 4. What this task does NOT do
- Does NOT change `design/screens/devices.md` or add any new UI element —
  if real discovery reveals a need for one (e.g. a "scanning..." spinner
  the current design doesn't have), log it to `design/gaps.md` and use the
  closest existing design primitive, per rule 2 (never silently invent).
- Does NOT implement `connect()`/pairing UI — discovery only, for this
  task. A discovered-but-unconnected device shows in the list as Unknown;
  actually connecting happens implicitly later (E05/E06's send flow) or in
  a follow-up task if the design calls for an explicit "connect" action —
  not decided here.
- Does NOT touch route cost/quality display — epic.md's screens table
  doesn't name a cost/quality UI element for `/devices`, and inventing one
  would be exactly the kind of silent addition rule 2 forbids. If route
  visibility (FR-UI-004's "one-tap-away" detail view) is wanted, that's a
  separate, explicitly-designed follow-up.
- Does NOT change how E02's existing relationship list loads/persists —
  `load()`'s existing behavior for already-known devices is unchanged.

## 5. Contract

### Functions
```yaml
- signature: "DevicesController.discover() -> void"
  purpose: "Starts TransportService discovery; subscribes to discoveredDevices, merges newly-seen device ids into the displayed relationships list via EvaluateConnectionRequestUseCase"

- signature: "DevicesController.onClose() -> void"
  purpose: "Stops discovery (TransportService.stopDiscovery()) — overridden GetX lifecycle hook"
```

### UI
- **Design contract:** `design/screens/devices.md` — unchanged, build
  against the existing contract, not a new mockup.
- No new route, no new states beyond what E02 already built
  (loading/empty/data are already handled).
- Gate: `make design-verify SCREEN=devices` if the Flutter-capable gate
  exists by the time this task runs (OQ-E00-3 status permitting); if not,
  manual on-device comparison against the existing golden, same as E02's
  practice.

## 6. Risks
- Real Bluetooth discovery can surface the same device repeatedly (each
  `ACTION_FOUND` per scan cycle, per T03b) — de-dup by device id before
  calling `EvaluateConnectionRequestUseCase` again for a device already in
  the list, or the list will flicker/duplicate.
- Discovery permission denial (T03b's concern) must surface as something a
  user understands, not a silently empty list forever — if
  `TransportService.startDiscovery()` fails, show whatever error affordance
  the existing design contract supports (or the closest primitive, logged
  as a gap if none fits).
