# E04-B07 · An accepted Bluetooth connection's incoming data is silently dropped unless the peer was also discovered this process run

## The defect

`InboundPipeline._onDeviceDiscovered` (`lib/core/messaging/inbound_pipeline.dart:413-421`)
is the **only** place that ever opens a per-device `connectionState(deviceId)`
subscription:
```dart
void _onDeviceDiscovered(TransportDevice device) {
  if (_connectionSubscriptions.containsKey(device.id)) return;
  _connectionSubscriptions[device.id] = _stack.transport
      .connectionState(device.id)
      .listen((ConnectionState state) => _onConnectionStateChanged(device.id, state));
}
```
That subscription is itself the *only* path to `_onConnectionStateChanged`,
which is the *only* place that opens the `incomingData(deviceId)`
subscription actually consumed by `_handleBuffer` (`inbound_pipeline.dart:423-433`).
`_onDeviceDiscovered` is wired exclusively from `_stack.transport
.discoveredDevices.listen(_onDeviceDiscovered)` in `start()`
(`inbound_pipeline.dart:389`) — driven by native `ACTION_FOUND` events
during an active discovery scan in *this* process run.

`E04-B06` (`BluetoothTransport.acceptLoop()`) now lets a **remote** device
dial into this one and complete a real RFCOMM handshake, emitting the
same `onConnectionStateChanged(remoteId, CONNECTED)` event `connect()`'s
own successful path already emits. But if this device never happened to
run a discovery scan that found that specific remote MAC *during this
same process run* (a completely realistic case: the app was just
launched, the user is sitting on a chat screen with an already-trusted
peer, no `Discover` tap has happened yet), there is no
`_connectionSubscriptions` entry for that id, so:
- the `CONNECTED` event lands on a broadcast stream (`transport_service.dart:83-86`)
  with zero listeners and is gone forever (no replay) — even a later
  discovery cannot recover it, since `TransportService.connect`'s own
  settle event doesn't fire again for an already-open socket;
- `incomingData(deviceId)` (`incomingData(` has exactly one consumer
  project-wide: `inbound_pipeline.dart:431`) is never subscribed either;
- every frame the peer sends over that very-really-open socket is
  silently discarded.

## Why `E04-B06`'s own retest will likely still fail without this

`E04-B06`'s fix makes an accepted connection reach `openSockets`/
`startReadLoop` on the native side and fire `onConnectionStateChanged`
correctly. But unless BOTH devices in a two-device retest happen to have
an active discovery scan running (or have otherwise already discovered
each other in that exact app run) at the moment the connection completes,
the accepting side's Dart layer will still never see the incoming
message — a failure that would look identical to "E04-B06 didn't work"
from the outside, without this bug's own diagnosis. Filed as its own task
(not folded into `E04-B06`) because the fix lives entirely in Dart,
outside that native-only fix's own `files:` fence.

## Expected

A remote device's `onConnectionStateChanged(deviceId, CONNECTED)` —
whether the connection was dialled out by this device or accepted in
(`E04-B06`) — always results in an active `incomingData(deviceId)`
subscription, regardless of whether `deviceId` happens to also be in
`discoveredDevices` this process run.

## Actual

Only a device this process has explicitly discovered (via an active scan)
ever gets a `connectionState`/`incomingData` subscription at all.

## Severity

**S1** — an already-trusted, already-known peer's incoming message can be
silently and permanently dropped depending purely on scan-timing luck,
with the sending side (and any relay in between) having no way to know
the accepting side never actually received it. Same `L-process-007`
("unwired capability") shape as `E04-B05`/`E04-B06`.

## Proposed fix direction (not yet implemented)

`InboundPipeline.start()` should also open a `connectionState`/
`incomingData` subscription pair for every device this app already knows
about — not only ones freshly discovered this run. `RelationshipRepository
.listAll()` (`lib/features/trust/data/relationship_repository.dart:41`)
already returns every known relationship row regardless of current
discovery/scan state; `start()` could seed `_connectionSubscriptions` from
that list (for `trusted`/`allowed` states, mirroring `E06-T07`'s own
first-contact reasoning about which relationship states are worth
acting on) in addition to the existing `discoveredDevices` listener, so an
already-known device reaching `CONNECTED` — by any means, dialled or
accepted — is never missed. This is a proposal, not a commitment; the
implementing task should re-verify against `InboundPipeline`'s own task
file (`E06-T05`) contract before committing to this shape.

## What a fix here should NOT do
- Should NOT change `BluetoothTransport.kt`/`TransportService`/
  `E04-B06`'s own accept-loop fix — this is purely about which devices
  `InboundPipeline` subscribes to, not the underlying transport contract.
- Should NOT eagerly `connect()` to every known relationship on `start()`
  — that would reintroduce the "proactive/eager connection" pattern
  `E04-B05`'s own fix deliberately avoided. This bug is about *listening*
  for a connection state that might already be settling or settle later
  (dialled by the OTHER side, or accepted in), not about this device
  initiating anything.

## Open Questions
- Should a `blocked`/`unknown` relationship also get a subscription (so a
  later state change to `trusted` doesn't need a fresh discovery either),
  or only `trusted`/`allowed` at `start()` time, with `unknown`/`blocked`
  devices still requiring a live discovery event the way they do today?
  Left to the implementing task to resolve against `E06-T05`'s own
  contract for what `InboundPipeline` is allowed to act on.
