# E04-B09 · Discoverability + app-initiated bonding, so two never-paired Nexora devices can actually connect

## The gap
Even after `E04-B08`'s identity-mapping fix, two Nexora devices that have
**never** been paired — by any means, OS Settings or otherwise — still
cannot connect:
1. **Nothing makes this device discoverable.** `BluetoothTransport.kt`
   only ever calls `startDiscovery()` (scan for others); nothing calls
   `ACTION_REQUEST_DISCOVERABLE` or any equivalent, so this device is
   invisible to a peer's own scan unless the user has separately opened
   Android's own Bluetooth Settings screen (which itself makes a device
   temporarily discoverable as a side effect on some OEM builds, but is
   not something this app does or can rely on).
2. **Nothing bonds a newly-discovered peer.** Both this app's own secure
   RFCOMM socket variants (`createRfcommSocketToServiceRecord`,
   `listenUsingRfcommWithServiceRecord`) require an OS-level bond to
   succeed — no `createBond()` call, no `BOND_STATE_CHANGED` listener,
   no pairing-confirmation UI exists anywhere in this codebase today.

Two human decisions were needed to scope a fix, both made directly by
the human on 2026-09-11 (hardware connected at the time):
- **Discoverability: time-boxed `ACTION_REQUEST_DISCOVERABLE`** (not a
  continuous listen-only scan mode) — the standard Android system
  dialog, user-initiated, reverts automatically (~120s), no background
  battery cost when the app isn't actively being used for this.
- **Bonding: app-initiated `createBond()` with a visible pairing
  prompt** (not "require manual OS pairing first", not "switch to
  insecure RFCOMM") — the full in-app pairing experience.

## What this task does
1. **Discoverability.** Add a new Pigeon method (`pigeons/transport.dart`,
   e.g. `void requestDiscoverable()`) implemented in
   `BluetoothTransport.kt` via
   `Intent(BluetoothAdapter.ACTION_REQUEST_DISCOVERABLE)` +
   `EXTRA_DISCOVERABLE_DURATION` (120s), launched via
   `activity.startActivityForResult` (wire the result callback through
   `MainActivity`, mirroring how `onRequestPermissionsResult` is already
   forwarded to `BluetoothTransport`). Regenerate the Pigeon bindings
   (`dart run pigeon --input pigeons/transport.dart`) — do not hand-edit
   the generated `.g.kt`/`.g.dart` files. Wire a UI trigger on the
   Devices screen (`design/screens/devices.md` — check whether this
   needs a new design element/gap entry per rule 2, or whether an
   existing "Discover" control can be reasonably extended; do NOT invent
   a new button without checking the design contract first).
2. **Bonding.** When the user taps a discovered-but-not-yet-bonded
   device (distinguish via `adapter?.bondedDevices` — same check
   `E04-B08`'s identity-mapping fix already added), call
   `device.createBond()` instead of (or before) `connect()`. Register
   for `BluetoothDevice.ACTION_BOND_STATE_CHANGED`
   (mirroring `registerReceiverIfNeeded`'s existing
   `ACTION_FOUND`/`ACTION_DISCOVERY_FINISHED` receiver pattern), and only
   proceed to the existing `connect()` path once `BOND_BONDED` is
   observed for that device. Android shows its own system pairing
   confirmation UI for `createBond()` automatically — this task does not
   need to build a custom pairing dialog, only trigger the OS one and
   react to its outcome.
3. Tests: a native/mock-adapter test proving `requestDiscoverable()`
   fires the correct intent and duration; a test proving `connect()` is
   deferred behind bonding for an unbonded target and proceeds once
   `BOND_BONDED` fires (and that a `BOND_NONE`/rejected pairing emits a
   `FAILED` connection state rather than hanging).

## What this task does NOT do  ← the scope fence
- Does **NOT** touch `E04-B08`'s own identity-mapping fix in
  `handleDeviceFound`'s emit logic — depends on it, does not modify it.
- Does **NOT** build a custom pairing-confirmation dialog — the OS's own
  `createBond()` system UI is used as-is.
- Does **NOT** add un-bonding, forgetting a device, or any bond-removal
  flow — bonding here is additive only.
- Does **NOT** change `RoutingEngine`/`RelayEngine` or any routing
  decision.
- Does **NOT** switch any RFCOMM socket variant to insecure — the human
  explicitly rejected that option.

## Contract

### Functions (Pigeon, `pigeons/transport.dart`)
```yaml
- signature: "void requestDiscoverable()"
  purpose: "Fires ACTION_REQUEST_DISCOVERABLE (120s), the human-decided
            discoverability mechanism. No return value -- the OS system
            dialog handles user confirmation; discoverability duration
            is fire-and-forget from the Dart side."
```

### Native (Kotlin)
```yaml
- signature: "BluetoothTransport.requestDiscoverable()"
  purpose: "Launches ACTION_REQUEST_DISCOVERABLE via
            activity.startActivityForResult, EXTRA_DISCOVERABLE_DURATION=120."

- signature: "BluetoothTransport.connect(deviceId: String): Boolean (behavior change)"
  purpose: "When deviceId is not in adapter.bondedDevices, calls
            device.createBond() first and defers the existing connect
            logic behind BOND_STATE_CHANGED -> BOND_BONDED, instead of
            attempting an RFCOMM connect against an unbonded peer
            (which fails today)."
```

## Risks
- **`ACTION_REQUEST_DISCOVERABLE`'s `startActivityForResult` needs a
  real `Activity`, not just a `Context`** — confirm `BluetoothTransport`
  already holds a usable `Activity` reference (it does, per its own
  constructor) and that the result callback path is wired all the way
  through `MainActivity` correctly, mirroring the existing
  `onRequestPermissionsResult` forwarding pattern exactly.
- **A user who denies/cancels the system pairing dialog** must result in
  a clean `FAILED` connection state, not a hang — `BOND_NONE` after a
  `BOND_BONDING` transition is the signal to watch for.
- **This is only end-to-end testable on real, physical Bluetooth
  hardware** — no emulator has a real Bluetooth radio. Two fresh,
  never-paired devices (or one freshly "forgotten"/unpaired via OS
  Settings) are needed to prove the full first-contact flow works,
  matching how `E04-B04`/`E04-B06`/`E04-B07`/`E04-B08` were all
  ultimately verified.

## On-device verification
Two physical devices, per the task's own risk note (no emulator has a real
Bluetooth radio): `e4813f500601` (Redmi 10 2022, MIUI) and
`192.168.0.108:9999` (Pixel 8 Pro, wireless adb). They were OS-bonded to
each other from prior epic testing at the start of this session.

**Setup — genuine unbonded state:** Forgot the peer on BOTH sides via
native Android Settings > Bluetooth (Pixel: gear icon -> Forget on "Redmi
10 2022"; Redmi: tapped "SRPhone P8" -> Forget), confirmed via
`dumpsys bluetooth_manager` before/after on both devices — the Pixel's
bonded-device count dropped 14 -> 13 with "Redmi 10 2022" gone, and the
Redmi's bonded list dropped to only its unrelated headset ("HOCO ES64
Ultra"), with "SRPhone P8" gone. This is a genuine, both-sides-forgotten
pair, not merely a stale one-sided record.

**Discoverability — verified working, both devices:**
- Tapped the existing "Discover" button on both apps. The real Android
  system dialog appeared on both: *"nexora wants to make your phone
  visible to other Bluetooth devices for 120 seconds."* Screenshotted on
  both devices (saved to the session scratchpad, not committed — see
  below).
- Confirmed via `adb logcat` on BOTH devices:
  - Redmi: `START u0 {act=android.bluetooth.adapter.action.REQUEST_DISCOVERABLE
    cmp=com.android.settings/.bluetooth.RequestPermissionActivity (has extras)}
    from ... callingPackage com.nexora.nexora` followed by
    `BtRequestPermission: Setting Bluetooth Discoverable Timeout = 120`.
  - Pixel: identical `REQUEST_DISCOVERABLE` intent from `com.nexora.nexora`,
    same `Setting Bluetooth Discoverable Timeout = 120` line.
  - Repeated successfully across 4 separate taps total (2 per device) over
    the session — consistent, no crashes, no ANRs.
- This directly satisfies the task's own on-device checklist item (a):
  "confirm the discoverability request fires correctly (check logcat for
  ACTION_REQUEST_DISCOVERABLE/startActivityForResult)".

**Bonding — NOT completed end-to-end this session.** Two independent,
environmental blockers, neither of which is a defect in this diff:
1. **Live discovery between the two physical devices did not succeed in
   this session.** Both apps' "Discover" (which now also requests
   discoverability) were triggered repeatedly — 6+ scan attempts across
   ~12 minutes, including simultaneous triggers on both sides — and
   neither app's discovery ever reported finding the other. Confirmed this
   is not specific to the app: the OS's own native Settings > Bluetooth
   scan (unrelated to any code in this diff) also could not find either
   device from the other's side during the same window, while each device
   *did* find other, unrelated nearby Bluetooth devices (a desktop PC, a
   headset). This points to a real-world RF/proximity condition between
   the two devices at the time of this session (they clearly could and
   did discover each other in earlier sessions, per the pre-existing
   "Allowed" relationship rows for each other's real addresses already in
   both apps' Devices lists) — not something this diff can fix or that I
   can control remotely.
2. Since discovery didn't surface the peer as a fresh row, the only other
   path to invoke `connect()` against the peer's already-known real
   address (both apps already have an `Allowed` relationship row for the
   other side, persisted from an earlier session) is the existing
   messaging feature's "Message" affordance
   (`ConnectionEnsuringSender` -> `TransportService.connect()`). I opened
   that chat screen on both devices and attempted to type and send a
   message via `adb shell input text`, but the message compose
   `TextField` never accepted synthetic focus on EITHER device
   (`dumpsys input_method` showed `mInputShown=false` /
   `mServedView=DecorView` rather than the field, across a wide sweep of
   tap coordinates, tap durations, and both a MIUI and a stock-Android
   device) — an ADB/UI-automation limitation against this particular
   compose field, not something in this task's own `files:` scope
   (the chat feature belongs to a different epic).

Given both blockers, I could not drive a real `createBond()` attempt to
completion on-device this session, and therefore could not observe
`BOND_BONDED`/`BOND_NONE` outcomes or verify E04-B08's regression (a
fresh post-bond discovery resolving to the real address) live. The
bonding code itself (`isBonded`/`startBondAndConnect`/
`registerBondReceiverIfNeeded`/`handleBondStateChanged`) is implemented
against Android's own documented `createBond()`/`ACTION_BOND_STATE_CHANGED`
contract, mirrors this file's own established patterns exactly
(`registerReceiverIfNeeded`'s lazy-registration + `RECEIVER_EXPORTED`
reasoning, `emitFailure`'s existing helper), and is covered by the
reasoning in each method's own doc comments — but it has NOT been proven
against real hardware pairing dialogs, and that gap is recorded honestly
here rather than claimed.

Screenshots and full logcat captures from this session are saved under
the scratchpad directory (`E04-B09-evidence/`), not committed to the repo
(they are session evidence, not part of the task's `files:` fence).
