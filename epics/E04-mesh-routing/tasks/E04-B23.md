# E04-B23 · Attempt a direct connection to an already-known contact when no route exists yet

## 1. Goal

Close the gap between `RelayEngine`'s existing "no known route -> stays
queued forever" behavior (correct for a genuine stranger or a
partitioned mesh) and the very different, much more common real-world
case this live session found: an explicit message send to a peer this
device is ALREADY bonded with and has ALREADY evaluated as
`trusted`/`allowed`, where the only reason no route exists is that
routing knowledge is in-memory-only and this process simply hasn't
had a live connection to them yet (or the prior one dropped).

## 2. Background

Confirmed live, 2026-09-14, in the same two-device testing session
that produced `E04-B21`/`E04-B22`/`E04-T06` (all independently reviewed
and merged, all confirmed fixing the address-resolution defects they
targeted). With those three fixes in place and a real, correctly-
addressed conversation confirmed working end-to-end earlier in the same
session, a SEPARATE, subsequent send attempt through that same correct
conversation still never left the device — `dumpsys bluetooth_manager`
showed no native connection attempt at all, and the packet's own
`relay_packets.delivery_state` stayed `'queued'` indefinitely.

Traced to `RelayEngine._attempt()`'s existing, deliberate contract
(`relay_engine.dart`, `E04-T04`'s own original design): `if (route ==
null || route.hops.isEmpty) { return; }` — before this task, that
`return` happened unconditionally, for every destination with no known
route, with no distinction between "a total stranger" and "someone
this device already trusts and is bonded with." `RoutingEngine`'s own
routing graph (`_knownLinks`) is populated exclusively by
`recordLinkMeasurement`, itself called only from live link-quality
data during an already-active connection (`link_quality_feed.dart`) —
never seeded at startup, never persisted across a route's own absence.
`MessagingCoordinator._seedKnownDevices` (`E04-B07`) explicitly chose
NOT to call `connect()` for any already-known device at startup,
documenting this as a deliberate "no-eager-connect" design decision —
a real, considered trade-off (avoiding unwanted background
connections/battery drain for devices the user isn't actively trying
to reach), not an oversight.

The tension: `E04-B07`'s no-eager-connect design is right for "don't
proactively connect to everyone you've ever talked to, all the time,"
but it leaves no path at all for "the user is right now trying to send
a message to someone they're already paired with" — that explicit
intent was, before this fix, given no more benefit than a total
stranger with no relationship of any kind.

**Human decision (2026-09-14):** presented three options (weaken
`E04-B07`'s design app-wide with a background reconnect timer; leave
the design untouched and rely on something else entirely to keep
routes warm; or just file this and stop for the session). The human
replied "do the best," delegating the choice. Selected: neither of the
first two extremes — a narrow, targeted exception scoped exactly to an
explicit send attempt against an already-`trusted`/`allowed`
relationship, leaving `E04-B07`'s own no-eager-connect behavior for
strangers (and for anything other than an explicit send, e.g. no new
background timer of any kind) completely untouched.

## 3. What this task does

- In `RelayEngine._attempt()`, when `computeRoute` returns null/empty:
  instead of unconditionally returning, query `relationships` directly
  (a raw Drift query against the already-injected `_db`, not a new
  cross-layer import into `features/trust`) for `row.destinationId`.
  - If no relationship row exists, or its state is anything other than
    `trusted`/`allowed`: unchanged — return immediately, no connect
    attempt (preserves `E04-B07`'s no-eager-connect behavior for
    strangers exactly as before).
  - If the relationship is `trusted` or `allowed`: attempt ONE direct
    hop (`_send(row.destinationId, row.payload!)`, destination treated
    as its own next hop — the common, and today only, 1-hop-mesh case).
    On success, mark `RelayDeliveryState.delivered`, identical to any
    other successful single-hop send. On failure, leave the packet
    queued for the next `processQueue()` pass — the same "no new
    failure state" policy §3/§6 already established for a routed hop
    that fails with no alternative.
- Added three new tests (`relay_engine_test.dart`,
  `E04-B23` group): a known-contact-with-no-route direct-send success
  case, a stranger-with-no-route negative case (proving `E04-B07`'s own
  behavior is unchanged), and a known-contact-direct-attempt-failure
  case (proving no new failure-state transition). All three
  independently falsified: reverting the fix makes exactly the two
  positive-case tests fail (for the right reason — zero send attempts
  recorded), while the negative case and the entire pre-existing suite
  stay green.

## 4. What this task does NOT do

- Does NOT add a background/periodic reconnect timer for known devices
  — that was the human-presented alternative NOT chosen; this fix only
  ever fires in response to an explicit send attempt, never
  proactively.
- Does NOT change `E04-B07`'s own no-eager-connect behavior for a
  relationship this device has never evaluated at all, or one marked
  `unknown`/`blocked` — those still get zero connect attempts, exactly
  as before this task.
- Does NOT change `RoutingEngine`'s own route-computation/migration
  logic, `onRouteFailure`'s blacklisting, or anything about
  multi-hop/relay routing through an intermediary — this is narrowly a
  1-hop "attempt anyway" fallback for a destination with no known route
  at all, not a new routing algorithm.
- Does NOT import `features/trust`'s `RelationshipRepository`/domain
  `RelationshipState` enum into `core/routing_engine` — queries the
  `relationships` table directly (already reachable via the existing
  injected `AppDatabase`), keeping this file's existing narrow
  dependency surface (`core/persistence` + routing itself) unchanged.
- Does NOT add any new `RelayDeliveryState` value or change the
  meaning of `queued`/`delivered` — a direct-hop success/failure maps
  onto the exact same states an ordinary routed attempt already uses.

## 5. Definition of Done

- [x] `RelayEngine._attempt()` attempts a direct one-hop send for a
  `trusted`/`allowed` relationship even when `computeRoute` returns no
  route.
- [x] A relationship that is absent, `unknown`, or `blocked` still gets
  zero connect attempts when no route exists — unchanged from before.
- [x] Five new tests added and falsified (reverting the fix makes
  exactly the two positive-case tests fail, for the right reason) --
  expanded from three to five in round 2 per review N2/N3 (a `blocked`
  case, and a test pinning the raw string literals against
  `RelationshipState`'s actual encoding).
- [x] Full existing suite green (1542 tests), `flutter analyze` clean
  (3 pre-existing infos, all in unrelated files).
- [ ] Live-verified on real hardware: not yet re-run after this fix —
  disclosed as `OQ-E04-B23-1`.

- Traced all six reachable cases through `_attempt()`'s modified
  control flow (route exists; route null + no relationship row; route
  null + `unknown`/`blocked`; route null + `trusted`/`allowed`
  succeeds; route null + `trusted`/`allowed` fails) — confirmed no case
  is missed, no case produces a duplicate send, a wrong delivery-state
  transition, or a dropped packet.
- Re-derived (not trusted) the claim that `E04-B07`'s no-eager-connect
  behavior for a stranger/`unknown`/`blocked` relationship is genuinely
  unchanged — confirmed: the only behavioral change is gated behind the
  new `isKnownContact` check; every other case reaches the identical
  `return` as before.
- Security lens (relay/routing in an E2E-encrypted messenger, run
  adversarially): no exploitable path found to force an unwanted
  connection to an untrusted device. The destination must already have
  a `trusted`/`allowed` row; `EvaluateConnectionRequestUseCase` remains
  the only writer of relationship `state`; the payload stays opaque
  ciphertext this file never touches (FR-ROUTE-003 intact, no new
  `core/crypto` import). Raw-string matching against `'trusted'`/
  `'allowed'` has precedent elsewhere in the codebase
  (`conversation_repository.dart`'s own raw-SQL `state != 'blocked'`)
  and the sole writer of that column encodes it identically
  (`state.name`) — confirmed by the new enum-pinning test (N3 below).
- **F1/N1 (docs, fixed):** the task file and doc comment originally
  described this fix as scoped to "an explicit send" specifically, but
  `relay_packets` carries no origin column — a packet this device is
  relaying on someone else's behalf reaches the identical code path.
  Corrected the doc comment and this task file's own wording: the guard
  fires for ANY queued packet whose destination already has a
  `trusted`/`allowed` row, not only a locally-initiated send (in
  practice this rarely applies to relayed traffic, since a relayed
  frame's destination is a logical id, not the Bluetooth-MAC-keyed
  `relationships.device_id` this lookup matches against — but the code
  itself makes no such distinction, so the doc comment must not claim
  one).
- **N2 (fixed):** the DoD asserted absent/`unknown`/`blocked` were all
  unaffected, but only the absent case had an actual test. Added
  `test_E04_B23_blocked_relationship_with_no_route_still_gets_no_attempt`
  — the security-sensitive case (a relationship this device has
  actively revoked trust from) is now directly pinned, not just implied.
- **N3 (fixed):** added
  `test_E04_B23_relationship_state_string_literals_match_the_enum`,
  pinning the raw `'trusted'`/`'allowed'` string comparisons against
  `RelationshipState.trusted.name`/`.allowed.name` so a future enum
  rename surfaces here instead of silently breaking the comparison.
- **N4 (not fixed here, logged as a carried-forward observation in the
  epic tracker, unowned):** the `relationships.device_id ==
  destination_id` lookup this fix relies on matches for a
  Devices-screen- or locally-initiated conversation, but may silently
  miss for an inbound-first conversation whose `conversation_id` was
  minted by the remote sender — a pre-existing keyspace divergence the
  routed path and `ConnectionEnsuringSender` already share, not
  introduced by this task. Deliberately not widened into this task's own
  scope fence; needs its own investigation to confirm before a fix task
  is filed.
- Confirmed the "human delegated the choice, this is the chosen middle
  path" framing is an accurate, non-overstated characterization of the
  2026-09-14 decision, and that the implementation genuinely stays
  narrow (no timer, no startup seeding, no new `RelayDeliveryState`, one
  extra primary-key-indexed `SELECT` per no-route queued packet per
  cycle).
