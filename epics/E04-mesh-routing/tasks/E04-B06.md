# E04-B06 · `BluetoothTransport` never accepts an incoming connection -- only ever dials out

## The defect

`BluetoothTransport.connect(deviceId)`
(`android/app/src/main/kotlin/com/nexora/nexora/transport/BluetoothTransport.kt`)
is, and always was, a pure **client-side** operation:
`device.createRfcommSocketToServiceRecord(NEXORA_SPP_UUID)` followed by
`socket.connect()`. Grepping the entire native Android source
(`grep -rn "listenUsingRfcomm\|BluetoothServerSocket\|\.accept(" android/app/src/main/kotlin/`)
returns **zero hits** anywhere in the codebase. No device ever opens a
listening socket on `NEXORA_SPP_UUID`, so no device can ever be the
target of another device's `connect()` call — both sides are permanently
client-only, and Bluetooth Classic RFCOMM requires exactly one side to be
a server.

This was invisible through `E04-B05` (which fixed a real, separate
defect: `TransportService.connect()` had zero *production callers* at
all) because `E04-B05`'s own fix, once wired in, correctly calls
`connect()` for the first time ever — and that is precisely what finally
exposed this second, independent defect underneath it: a genuine
connect *attempt* now happens, and it fails, because there is nothing on
the other end to accept it.

## Repro (confirmed on two real physical devices, immediately after E04-B05)

1. Two devices with `E04-B05`'s fix installed, both signed in, mutual
   Bluetooth trust already established (relationship state `Allowed` on
   both sides, survived the reinstall).
2. On device 1, use the Devices screen's Message button (`GAP-030`,
   `E06-T14`) to open chat with the trusted peer, compose a real message,
   and send it via the keyboard's IME send action.
3. The message renders as an optimistic local bubble for a moment, then
   disappears; the composer's draft text reappears un-sent. Querying
   device 1's own Drift database directly
   (`adb exec-out "run-as com.nexora.nexora cat
   /data/data/com.nexora.nexora/app_flutter/nexora.sqlite" > dev1.sqlite`,
   then `sqlite3 dev1.sqlite "SELECT count(*) FROM messages;"`) confirms
   **zero rows** — the message was never actually persisted at all.
4. `adb -s <device1> shell dumpsys bluetooth_manager` shows a real,
   recent connection attempt to the peer's MAC that failed:
   ```
   CLASSICAL-CONNECTED  b8:db:38  <peer>  :  status = Page Timeout
   ```
   `Page Timeout` is a genuine Bluetooth link-layer failure — the local
   radio paged the remote address and got no response within the
   protocol's own timeout, the exact symptom of paging a device with no
   open server socket listening on the target service UUID.

## Expected

Two mutually-trusted, mutually-reachable Nexora devices can complete a
real RFCOMM connection with each other in either direction —
`FR-DISC-001`/`FR-ROUTE-003`/`FR-ROUTE-004`, and the real-hardware half
of `OQ-E06-T04-2` this whole investigation exists to close.

## Actual

Every `connect()` attempt between two real Nexora installs fails with a
link-layer `Page Timeout`, because neither device ever listens. This is
a total, silent failure of the mesh's actual physical connectivity —
`E04-B05`'s fix is necessary but not sufficient; both defects had to be
found and fixed for a real message to ever have a chance of arriving.

## Severity

**S1** — total failure of the app's core value proposition on real
hardware, discovered the moment `E04-B05`'s fix made it observable. Same
`L-process-007` ("unwired capability") shape as `E04-B05`, `E06-B02`,
`E07-B03` — though here the missing half is a whole unimplemented
capability (server-side listening), not a wiring gap between two already-
implemented pieces.

## Fix

`BluetoothTransport` gains a listening half, symmetric with its existing
client half:
- `ensureListening()` — idempotent (a no-op if already listening), opens
  `adapter.listenUsingRfcommWithServiceRecord(SERVICE_NAME,
  NEXORA_SPP_UUID)` and starts `acceptLoop()` on a dedicated background
  thread. Called from both permission-gated entry points that already
  exist (`doStartDiscovery()`, `connect()`) so listening starts the
  moment permissions are actually granted, from whichever call happens
  to trigger that first — no new lifecycle hook needed.
- `acceptLoop(serverSocket)` — loops on `serverSocket.accept()` (blocking,
  background thread only), and on each accepted connection performs
  exactly the same bookkeeping `connect()`'s own successful path already
  does: `openSockets[remoteId] = socket`, `startReadLoop(remoteId,
  socket)`, `onConnectionStateChanged(remoteId, CONNECTED)`. A caller of
  `send()` cannot tell, and does not need to tell, whether a given
  `deviceId`'s connection was dialled out or accepted in.
- `release()` now also closes `serverSocket` and interrupts
  `acceptThread`, mirroring `disconnect()`'s identical reasoning for a
  client-side read loop (closing an open socket from another thread is
  what unblocks a thread parked in a blocking call).

No new Android permission required: `BLUETOOTH_CONNECT` (already
declared and requested by `BluetoothPermissions.required()` for API 31+)
covers both `connect()`/`send()` and `listenUsingRfcommWithServiceRecord()`/
`accept()` under Android's own permission model.

## What this fix does NOT do
- Does NOT make the device Bluetooth-*discoverable* (`ACTION_REQUEST_DISCOVERABLE`)
  — that is a separate, already-disclosed carried-forward observation from
  `E04-B04`'s own review ("the app never makes itself Bluetooth-
  discoverable... a real `FR-DISC` gap, outside this bug's own
  registration-only fence; needs its own task"). This fix is purely about
  *accepting an RFCOMM connection once both sides already know each
  other's address* (already-trusted/already-discovered devices, this
  bug's own repro) — it does not change how two devices first find each
  other.
- Does NOT change `connect()`, `send()`, `disconnect()`, `startReadLoop()`,
  or `writeFrame()` — every one of those already does exactly what its
  own task file specifies; this only adds the missing listening half
  alongside them.
- Does NOT add a keep-alive/heartbeat on the listening socket, and does
  NOT add any new Pigeon API surface (`TransportApi`/`TransportEventsApi`
  are both untouched) — accepting a connection reuses the exact same
  `onConnectionStateChanged(CONNECTED)` event `connect()`'s own success
  path already emits, so no Dart-side change is needed at all.
- Does NOT handle the (rare, self-resolving) case of both devices
  attempting to connect to each other simultaneously and each accepting
  the other's inbound connection while their own outbound one is also in
  flight — `openSockets[deviceId] = socket` already has "last write wins"
  semantics for a given device id from `connect()`'s own pre-existing
  contract, and this fix does not change that. Disclosed, not fixed here.
