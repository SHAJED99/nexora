# E04-B03 · The routing engine has no production data source

## The finding
`RoutingEngine` decides routes from `_knownLinks`, populated exclusively by
`recordLinkMeasurement(neighborId, {latencyMs, lossRate, batteryDrain})`
(`lib/core/routing_engine/routing_engine.dart:141-155`). Those three values
have **no producer anywhere in `lib/`**. Verified:

```
grep -rn "rssi|Rssi|latencyMs|lossRate|batteryDrain" lib/ --include=*.dart
  (excluding simulation/ and routing_engine's own definitions)  →  0 hits
```

The only thing in the repo that produces them is
`lib/core/routing_engine/simulation/simulated_link.dart` — T01's
deterministic test simulator.

The reason is upstream, in the transport contract. `pigeons/transport_api.dart`
— T03a's task was to "define the transport boundary once" (ADR-0004) —
exposes exactly four native→Dart events:

```dart
void onDeviceDiscovered(TransportDevice device);
void onDeviceLost(String deviceId);
void onConnectionStateChanged(String deviceId, ConnectionState state);
void onDataReceived(String deviceId, Uint8List bytes);
```

and `TransportDevice` carries only `id`, `displayName`, `type`
(`lib/core/transport/generated/transport_api.g.dart:132-143`). No RSSI, no
round-trip time, no loss counter, no throughput sample, no battery hint.
Android's `BluetoothDevice`/`ScanResult` can supply RSSI and the Kotlin side
can time its own round trips, but nothing in the contract carries any of it
across the boundary.

**Consequence on a real device:** `_knownLinks` stays empty →
`computeRoute()` returns `null` for every destination
(`routing_engine.dart:331-332`) → `RelayEngine._attempt` returns early at
`relay_engine.dart:163-167` → every relay packet sits `queued` until it
expires. The mesh discovers peers and can move bytes point-to-point, but
cannot route.

## Why this is a defect and not just "E05's job"
The sweep specifically checked whether this was cleanly deferred, the way
`RelayEngine`'s production wiring is. It is not:

- `RelayEngine` being unconstructed in `lib/` **is** cleanly deferred —
  `relay_engine.dart:13-17` says "Production wiring (a later epic) constructs
  `RelaySendFn` from `TransportService.send`", and `E04-T04.md` §4 fences it.
  The sweep confirms that hand-off is sound: `TransportService.send(String,
  Uint8List) → Future<bool>` (`transport_service.dart:120-121`) matches
  `RelaySendFn` exactly, and `AppDatabase` is already a permanent GetX
  singleton (`lib/app/bindings.dart:20`), so the
  `TransportService`/`RoutingEngine`/`AppDatabase` triple E05 needs is
  genuinely constructible. **No bug there.**
- The link-measurement gap is **nowhere disclosed** — not in `epic.md`, not
  in T02's §4, not in T03a/T03b's fences, not in the analyze report. E04's
  scope claims "Route cost calculation and make-before-break migration"
  (`epic.md:31`) as in-scope and delivered.

And it is not a wiring gap that E05 can absorb: fixing it means adding
methods/fields to the **Pigeon schema**, which ADR-0004 designates as the
one place the transport boundary is defined, plus regenerating bindings and
implementing the native side. The E04 analyze report's own "Contract sanity"
line rests on "One Pigeon schema (T03a) defines the transport boundary once;
T03b/T03c extend its *implementation*, never redefine the contract"
(`epic.md:104`). E05 needing to redefine that contract is exactly the
outcome that line was asserting would not happen.

## Severity: S3 (broken, but there is a workaround)
Not S2: no user-facing function regresses today, because E04 never claimed a
production-wired routing path and E05/E06 are the epics that send real
traffic. The workaround is real and available — extend the Pigeon schema in
E05.

Not S4: this is not cosmetic. It is a load-bearing hole in the epic's
headline deliverable, it invalidates an analyze-report assertion, and
discovering it mid-E05 converts a planned wiring task into an unplanned
ADR-0004 boundary change with native work on both platforms. Catching it
here costs a schema edit and a paragraph; catching it in E05 costs a
re-plan.

Severity per `skills/bug-sweep` is the reviewer's call. **Priority is the
human's** (`bug_priorities` gate, rule 3) — left `TBD-human`. Reviewer's
advisory: this is the one E04 finding where the *cheap* moment to act is
now, even though nothing is on fire.

## Repro (static, reviewer-verified 2026-08-27)
1. `grep -rn "recordLinkMeasurement" lib/` → one hit, its own definition in
   `routing_engine.dart`. No call site in `lib/`.
2. `grep -rn "latencyMs|lossRate|batteryDrain" lib/ --include=*.dart` →
   hits only in `routing_engine.dart`, `route_cost_calculator.dart`, and
   `simulation/`.
3. Read `pigeons/transport_api.dart` → no method or field carries any
   link-quality signal.
4. Therefore on a real device `RoutingEngine._knownLinks` is empty and
   `computeRoute()` returns `null` unconditionally.

**Expected** (FR-ROUTE-001, FR-ROUTE-002; `epic.md:31`): E04 delivers route
cost calculation over real links, or explicitly and visibly defers the
measurement source with a named owner.

**Actual:** neither. The cost formula, Dijkstra, migration policy and relay
queue are all implemented and correctly tested — against simulated inputs
that no production code path can supply.

## Proposed fix direction (builder to confirm; do not treat as prescriptive)
Smallest honest fix, in preference order:

1. **Minimum (documentation, no code):** add an explicit deferral to
   `epic.md` — a §Carry-forward entry naming the gap, the FR ids it blocks,
   and E05 as the owner, plus a correction to the "Contract sanity" analyze
   line noting that the transport contract will need extending. This makes
   the gap impossible for E05 to miss. If the human wants nothing else, this
   alone resolves the "silently absent" half of the defect.
2. **Preferred (small contract change now):** extend the Pigeon schema
   while it is still E04's own boundary — add an `int? rssi` to
   `TransportDevice` and a `void onLinkQuality(String deviceId, int
   latencyMs, double lossRate)` event, leaving the Kotlin side emitting
   nothing yet (a declared-but-unfed event is honest; a missing contract is
   not). Then E05's work is wiring, not redefinition. **Touching the Pigeon
   schema is an ADR-0004 boundary change — present it to the human and stop
   (rule 3) rather than deciding the shape unilaterally.**
3. **Do not** synthesize fake measurements to make the engine appear live
   (e.g. defaulting every discovered device to a constant latency). That
   would produce a routing engine that computes confident routes from
   invented data — strictly worse than one that honestly returns `null`.

## Regression test
No new unit test is meaningful for option 1 (a docs change) and option 2's
value is a contract shape, not a behavior — the existing
`test/core/transport/transport_service_test.dart` must stay green after any
regeneration. The real verification for this bug is the traceability pass:
`skills/traceability` should show `recordLinkMeasurement` with a production
caller, or the gap explicitly recorded as deferred with an owner.
