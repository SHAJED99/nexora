# E04-B13 · Wire the learned selfDeviceId into outbound addressing

**Status: done, NOT verified.** Reviewed and approved (opus, two rounds
of independent scrutiny across this task and E04-B12) on the strength of
real, adversarial Dart-level testing — but no message has yet been
observed arriving on a second real physical device. Three things must
still happen before the original human bug report ("I can not send any
message") can honestly be called closed:
1. A real, live, two-device send/receive pass — genuinely not yet done.
2. `E04-B14` (filed): a real, disclosed security gap the reviewer found —
   the bundle-response provenance check this fix makes newly satisfiable
   is bindable only to an unauthenticated claimed identity plus a
   guessable request id, not to the physical link a response actually
   arrived on (the same class of risk as a previously-confirmed S1 in
   `E09-B09`). Not a regression this PR caused (the alternative was the
   feature staying broken), but a real, live gap now that it works.
3. `E04-B15` (filed): the identical raw-Bluetooth-MAC-addressing defect
   this task fixed for 1:1 chat likely also affects delivery
   acknowledgements, calls, groups, and location sharing — deliberately
   left untouched to keep this task's own scope at `size: M`, but those
   features remain broken device-to-device until fixed separately.

## 1. Why this task exists, and why it's separate from E04-B12
`E04-B12` builds the mechanism to LEARN a peer's real `selfDeviceId` (a
new identity-announce control frame, fired automatically on connect, its
result stored in `Relationship.remoteSelfDeviceId`) but does not use that
value anywhere. On its own, `E04-B12` does not fix the actual bug this
whole investigation started from: a message sent to a peer still gets
addressed by that peer's Bluetooth MAC address
(`RelayPacketFrame.destination = "PHONE-A"`, say), which will
never equal the receiver's own `selfDeviceId`
(`InboundPipeline._handleBuffer`'s `isForUs` check), so `ensureSession`
still times out exactly as documented in `E04-B12`'s own §2.

This task is what actually closes the loop: once a peer's
`remoteSelfDeviceId` is known (via `E04-B12`), every outbound frame to
that peer must use THAT value as `RelayPacketFrame.destination`, not the
Bluetooth MAC — while `TransportService.connect`/`.send`'s own native-API
calls keep using the Bluetooth MAC exactly as today (Android's Bluetooth
APIs have no other way to open a socket; that requirement doesn't change).

## 1a. 🔒 Blocking precondition from E04-B12's own review (read this before writing any code)
`E04-B12`'s independent reviewer (opus) found and disclosed a real gap,
inert in that task but NOT inert here: **the identity announced via
`E04-B12`'s new protocol is unauthenticated.** `IdentityAnnounceService.
handleAnnounce` writes the announced string into
`Relationship.remoteSelfDeviceId` keyed by whichever link/Bluetooth
address the announce physically arrived on — which correctly prevents
device X from corrupting device Y's OWN relationship row (the
point-to-point, OS-bonded-connection reasoning in `E04-B12`'s own §3
point 3 is sound for THAT property). But nothing verifies that the
announced string is actually true — a malicious or compromised device
X can announce "my selfDeviceId is Y's-real-id" and this device will
believe it and store it.

**In `E04-B12` alone this was harmless — the reviewer verified nothing
reads the column.** This task is exactly the "something reads the
column" `E04-B12`'s reviewer warned about: if this task naively resolves
outbound addressing via a **reverse lookup** (`remoteSelfDeviceId` →
"which link reaches this identity"), a spoofed announcement becomes a
real hijack — messages meant for the real peer Y could be misdirected to
device X. **This task's own implementation MUST NOT do a bare reverse
lookup.** Before writing the resolution logic in §2, work out (and
record the reasoning here, in this section, once decided) which of these
directions — or another — actually closes the gap safely:
- **(a) Forward-only resolution, never reverse.** §2's own resolution
  direction is already forward (`Bluetooth MAC → remoteSelfDeviceId`,
  looked up FROM the connection you're already sending on, not searched
  FOR by identity) — confirm this stays true throughout implementation
  and never gets inverted into "find the link for identity X" anywhere,
  including in any future retry/reconnect logic. If this holds
  throughout, the spoofing risk may already be structurally avoided by
  this task's own natural shape — but verify this explicitly, in writing,
  against the actual implemented code, rather than assuming it from this
  description.
- **(b) If a reverse lookup turns out to be genuinely necessary anywhere**
  (e.g. re-establishing a connection to a peer identified only by their
  `selfDeviceId`, with no live Bluetooth link yet), that lookup MUST NOT
  trust an unauthenticated `remoteSelfDeviceId` alone — at minimum,
  require it to be corroborated by something already-authenticated (the
  Signal Protocol identity key from a previously-`establishSession`'d
  peer would qualify; a bare string match would not). If this situation
  arises, STOP and write it up as an Open Question rather than shipping
  an unauthenticated reverse lookup — this is exactly the kind of
  security-relevant judgment call that should not be made silently by an
  implementer alone.
- Whichever direction implementation actually takes, add a test that
  specifically proves a spoofed/incorrect `remoteSelfDeviceId` cannot
  cause a message to be misdirected to the wrong physical device.

**🔒 Resolved: option (a), forward-only, confirmed against the actual
implemented code (not assumed).** `resolveOutboundDestination(db,
peerDeviceId)` (new function, `messaging_stack.dart`) is the ONLY
resolution logic this task adds, and its single lookup key is
`peerDeviceId` — the Bluetooth-MAC-shaped id of the specific link the
caller is already using for `TransportService.connect`/`.send`
(`directSend`/`ConnectionEnsuringSender`). It is called from exactly two
sites (`PrekeyExchange._sendControlFrame`, `MessagingStack`'s own
`encryptAdapter`), and in both, the SAME `peerDeviceId` value is passed
to both the resolution call and the physical transport call immediately
after — grepped and confirmed: neither call site ever passes a
`remoteSelfDeviceId`-derived value into `directSend`/`enqueue`, and
neither ever queries the `relationships` table FOR a row matching a
claimed identity string (the reverse direction). `RelayEngine` and
`ConnectionEnsuringSender` were verified by full-file inspection to
construct no `RelayPacketFrame` at all (they only ever move opaque,
already-serialized bytes), so there was no second, hidden resolution
site to get wrong.

**Why this structurally closes the gap, not just "happens to" in
today's code:** which PHYSICAL DEVICE receives the bytes is decided
entirely by the `peerDeviceId`/MAC argument to
`TransportService.connect`/`.send` — a value `resolveOutboundDestination`
never touches or influences. A spoofed/wrong `remoteSelfDeviceId` can
only change what logical `destination` value gets stamped INSIDE the
frame the SAME physical peer already receives; at worst this makes that
peer's own `isForUs` check reject the frame (a safe, self-contained
failure — the peer just doesn't recognize the frame as theirs), never a
redirection to a different device, and never a session/message decrypted
by anyone other than whoever the crypto session (keyed by `peerDeviceId`
throughout, untouched by this task) was actually established with.

**Falsification test:**
`test_E04_B13_spoofed_remoteSelfDeviceId_cannot_misdirect_a_message`
(`prekey_exchange_test.dart`) — device A is physically connected only to
device B, but A's relationship row for that link has been corrupted to
claim the peer is a THIRD, uninvolved real device C (never wired to A at
all). Proves: C never receives anything (`c.prekeyExchange.counters
.requestsServed == 0`, and structurally cannot — there is no transport
path from A to C in this test); B receives the bytes but its own
`isForUs` correctly rejects the mis-stamped frame
(`b.prekeyExchange.counters.requestsServed == 0`); the ONLY observable
effect is `a.prekeyExchange.counters.timeouts == 1` — an honest,
bounded failure, identical in shape to an unresolved (never-announced)
peer, never a security breach. No reverse lookup was ever written, so
§1a option (b)'s Open-Question path was not needed.

## 2. What this task does
1. **Resolve the real destination id before constructing a
   `RelayPacketFrame`**, at every outbound call site that currently uses
   a raw `deviceId` (Bluetooth MAC) as `frame.destination`:
   - `PrekeyExchange._sendControlFrame` (`destination: peerDeviceId` today
     — this is the exact line whose output `E04-B12`'s own diagnostic
     instrumentation captured and confirmed was the Bluetooth MAC).
   - Any other `RelayPacketFrame` construction site this task's own
     `required_context` files reveal (`RelayEngine`'s own frame handling,
     if it constructs frames rather than only forwarding opaque bytes —
     confirm from the code, don't assume; `RelayEngine`'s own
     `files:` fence history notes it forwards ORIGINAL wire bytes for
     relayed traffic and never re-serializes, so it may turn out this
     task's real second call site is elsewhere — verify against the
     actual current code, not this description).
   - The resolution itself: look up `Relationship.remoteSelfDeviceId` for
     the target Bluetooth MAC; if non-null, use it as the frame's
     `destination`; if still `null` (peer hasn't announced yet — e.g. the
     very first frame sent before `E04-B12`'s announce has round-tripped),
     fall back to the raw Bluetooth MAC exactly as today (preserves
     current behavior for that narrow race window, never regresses it).
2. **Set `frame.source` to this device's own REAL `selfDeviceId`
   consistently** (confirm every outbound frame construction site already
   does this correctly — `_sendControlFrame` already uses
   `_stack.selfDeviceId` for `source`, per `E04-B12`'s own diagnostic
   capture; this task's job is to verify no OTHER call site got this
   wrong, not to introduce it fresh).
3. **Handle the resolution race explicitly and test it**: what happens
   when device A sends a frame to device B before B's identity-announce
   has arrived at A? Per point 1's fallback, A's frame goes out addressed
   by B's Bluetooth MAC — which will still fail `isForUs` on B exactly as
   today, UNLESS `E04-B12`'s own automatic-announce-on-connect ordering
   guarantee (fires before any application code runs) is actually
   airtight. Write a test that proves the ordering guarantee holds under
   realistic concurrency (e.g. `MessagingStack`'s own connection-state
   listener firing the announce vs. `ensureSession` being called
   immediately after `connect()` resolves) — do not assume `E04-B12`'s
   ordering claim without proving it under this task's own outbound path.
4. **Verify live, end-to-end, on real hardware**: a message composed on
   one physical device genuinely arrives, decrypts, and renders on the
   other device's chat thread — the actual, original symptom this whole
   `E04-B11`→`E04-B12`→`E04-B13` chain exists to fix. This is the
   Definition of Done this entire investigation has been building toward
   since the human's first "I can not send any message" report.

## 3. What this task does NOT do
- Does NOT re-implement or modify `E04-B12`'s own announce protocol,
  schema column, or `isForUs` bypass — this task only CONSUMES
  `remoteSelfDeviceId`, it does not change how it's populated.
- Does NOT change `Relationship.deviceId`, the Devices screen, or any UI
  file — same scope boundary `E04-B12` established.
- Does NOT add a keep-alive/re-announce/staleness-detection mechanism for
  `remoteSelfDeviceId` (e.g. re-announcing periodically, or invalidating
  a stale value) — out of scope; if a real need for this surfaces during
  implementation, log it as an Open Question, don't build it unasked.
- Does NOT touch `CryptoService`, identity-key trust logic, or anything
  in `E04-B11`'s own already-fixed `send()`/`TaskQueue` code.

#### F1 — §1a resolution is genuinely forward-only (PASS, verified by grep, not by description)

#### F2 — the two MACs are provably one value from one source (PASS)
The specific risk (two independently-obtained MACs that could diverge) does not
arise; at both call sites the resolution key and the physical transport address
are the *same local variable*:
- chat path: `lib/features/messaging/domain/send_message_use_case.dart:246`
  `_encrypt(recipientDeviceId, …)` → `encryptAdapter` resolves on that same
  `recipientDeviceId` (`messaging_stack.dart:729`); line **282** of the same

- control path: `prekey_exchange.dart:661` resolves on `peerDeviceId`;

Critically, **the physical route never reads the resolved value at all**:
`RelayEngine.enqueue` (`relay_engine.dart:119-140`) stores its own

incapable of changing which physical device receives bytes — it can only
mis-stamp a logical field inside a frame the same peer already receives. The
builder's claim 1 is upheld as written.
