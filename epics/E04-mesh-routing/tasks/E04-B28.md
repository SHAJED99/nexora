# E04-B28 · Emit onDeviceLost from the native transport

## 1. Mechanism

- **Tracking:** `BluetoothTransport` keeps the resolved ids each scan confirmed (`emitDiscoveredDevice`), plus the set from the previous completed scan.
- **Trigger:** `ACTION_DISCOVERY_FINISHED` was registered but never handled; it now runs `handleDiscoveryFinished`.
- **Grace period:** it waits `SDP_LOOKUP_TIMEOUT_MS`, because E04-T06's SDP confirmation can arrive after the inquiry ends.
- **Superseded scans:** it does nothing if a newer scan has started.
- **Emit:** otherwise it emits `onDeviceLost(id)` for every id the previous scan confirmed and this one did not.
- **Own cancels ignored** (review F1): Android also broadcasts `ACTION_DISCOVERY_FINISHED` when a scan is cancelled. This file cancels discovery itself in several places: `stopDiscovery`, the restart in `doStartDiscovery`, before `createBond`, before connecting, and after bonding. All of them now go through `cancelDiscoveryQuietly`, which marks the next finish as cancellation-caused (only if a scan was actually running), so a truncated scan is never diffed.

Only scan results take part. A peer reached through an accepted connection is never reported lost by this path.

## What this task does NOT do

- Does not change the Pigeon schema (`onDeviceLost` already exists) or any Dart code. `TransportService`, Dashboard and Network Settings already consume `lostDevices`.
- Does not report a peer lost when its RFCOMM connection drops. Connection state already travels via `onConnectionStateChanged`.
- Does not add a Kotlin test harness (none exists in this project).
- Does not touch E04-T07's UUID filter (a separate, parallel branch; no overlap in the edited regions).

## 2. Definition of Done

- [x] `onDeviceLost` is emitted on scan completion for ids the previous scan confirmed and this one did not
- [ ] `flutter build apk --debug` compiles clean
- [ ] Live: a peer found in scan 1 and absent from scan 2 is reported lost, and the Dashboard stops listing it as nearby and clears its latency
- [ ] Independent review (reviewed_by != executed_by)

## Open Questions

- OQ-E04-B28-1: a device that is simply not discoverable during the second scan (e.g. its 120 s visibility window expired) is reported lost even though it is still in range. This matches what a scan can observe; its link-quality events (E04-B27) re-add it as soon as a live link reports.

- OQ-E04-B28-2: a scan cancelled by ANOTHER app (or the system) is indistinguishable from a completed one, so its partial result set is still diffed. Only this app's own cancels are excluded.
