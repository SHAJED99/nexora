# E04-T02 · Routing engine

## 1. Goal
The decision-making core of the mesh: given known links to neighbors and
candidate multi-hop routes, compute a cost per route, pick the best one,
and migrate to a better route only when it's genuinely better and stable
(make-before-break) — tested entirely against T01's simulator, no real
transport required.

## 2. Business logic
- FR-ROUTE-001 / EARS-ROUTE-1: communication between two devices with no
  direct link works via one or more relays — this task computes *which*
  relay path, not the byte-forwarding itself (T04).
- FR-ROUTE-002, OQ-E04-1 (resolved, epic.md): cost = weighted sum of
  latency, `(1 - reliability)`, battery drain rate, and hop count, with two
  named profiles (`interactive`, `bulk`). Weights are named constants,
  explicitly flagged tunable in a doc comment — not hidden magic numbers.
- FR-ROUTE-006 / EARS-ROUTE-2, OQ-E04-2 (resolved): migrate to a better
  route only when its cost is ≥20% better AND has held that advantage for
  ≥10 consecutive cost-sample ticks (stability window) — both named
  constants. "Make-before-break": the new route must be validated (able to
  carry a test/heartbeat send) before the old route is dropped.
- FR-ROUTE-009 / EARS-ROUTE-4: on route failure (a hop reports `noRoute` or
  repeated loss), search known alternative paths; if none exist, the caller
  gets a clear "no route, queue for retry" result rather than a silent drop.

## 3. What this task does
- `routes` Drift table (per epic.md's Data model): candidate paths (as an
  ordered list of hop node ids) + last-measured cost factors per route,
  keyed by destination.
- `RouteCostCalculator.cost(factors: RouteCostFactors, profile: TrafficProfile) -> double`
  — pure function, the weighted-sum formula above.
- `RoutingEngine`:
  - `recordLinkMeasurement(neighborId, latencyMs, lossRate, batteryDrain)` —
    updates this device's view of a direct neighbor's link quality.
  - `computeRoute(destination, profile) -> Route?` — Dijkstra/best-path over
    known links using the cost calculator as edge weight; `null` if no path
    exists.
  - `considerMigration(destination, profile) -> MigrationDecision` — compares
    the currently-active route's cost against the best known alternative,
    applies the ≥20%/≥10-tick rule, returns `stay` or `migrateTo(route)`.
  - `onRouteFailure(destination) -> Route?` — marks the failed route's
    relevant link as degraded/down, recomputes; returns the next-best route
    or `null` (caller queues/retries per FR-ROUTE-009).

## 4. What this task does NOT do
- Does NOT send or receive any real bytes over Bluetooth/Wi-Fi — this
  engine only decides paths and costs. T04 (relay) and T03's transport
  tasks own moving bytes; this task's tests use T01's simulator exclusively.
- Does NOT implement store-and-forward packet queuing/TTL/priority — T04.
- Does NOT wire into the Devices screen or any UI — T05.
- Does NOT persist route history/analytics beyond the current best-known
  state per destination — no time-series table, no "route quality over
  time" reporting (out of scope for v1, not named in FR-ROUTE-*).
- Does NOT implement `make-before-break`'s actual "send a validation probe
  over the new route" as a real network operation — that requires T03's
  transport. This task's `considerMigration` returns a decision; T04/T03
  are responsible for actually probing before switching. Note this
  explicitly in the Run log as the seam between this task and its consumer.

## 5. Contract

### Data
Migration: new `routes` table — `destination_id TEXT`, `hops TEXT` (JSON
array of node ids, ordered), `last_cost REAL`, `last_measured_at INTEGER`
(epoch ms), `stable_since_tick INTEGER` (for the migration stability
window), PK `(destination_id, hops)` since multiple candidate routes to one
destination coexist.

### Functions
```yaml
- signature: "RouteCostCalculator.cost(factors: RouteCostFactors, profile: TrafficProfile) -> double"
  params: { factors: "{latencyMs, reliability (0-1), batteryDrainRate, hopCount}", profile: "interactive | bulk" }
  returns: "lower is better; weighted sum per §2's formula"
  purpose: "Pure, no I/O — the single place the cost formula lives"

- signature: "RoutingEngine.computeRoute(destination: String, profile: TrafficProfile) -> Route?"
  returns: "the lowest-cost known path to destination, or null if none exists"
  purpose: "Route selection"

- signature: "RoutingEngine.considerMigration(destination: String, profile: TrafficProfile) -> MigrationDecision"
  returns: "MigrationDecision.stay() | MigrationDecision.migrateTo(route: Route) — applies the >=20%/>=10-tick rule"
  purpose: "Make-before-break migration policy (the DECISION only, see §4)"

- signature: "RoutingEngine.onRouteFailure(destination: String) -> Route?"
  returns: "next-best alternative route, or null (caller must queue/retry)"
  purpose: "Failure recovery per FR-ROUTE-009"
```

## 6. Risks
- The migration stability window must be measured in discrete
  `NetworkSimulator.tick()`s in tests, not wall-clock time — keep the
  engine's own notion of "tick"/"sample" simulator-agnostic (an injected
  clock/counter) so production code can drive it from a real periodic timer
  later without this task's tests needing to change.
- Dijkstra/best-path over a small mesh is easy to get right and easy to
  silently get wrong on a cycle or a disconnected component — the test
  suite must include both a straightforward 3-node relay case AND a
  partitioned-graph case (T01's `noRoute`/down-link support exists exactly
  for this).
- Don't let "make-before-break" quietly become "break-then-make" by
  returning a migration decision the caller applies without validating
  first — the seam note in §4 exists so this doesn't get silently dropped
  when T04 wires this in.
