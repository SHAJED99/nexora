# E04-B12 · Message delivery still fails end-to-end after E04-B11's transport fix

## 1. How this was found
Continuing directly from `E04-B11`'s own live verification session: with
that task's fix in place (`send()` genuinely running on a background
`TaskQueue`, confirmed via live thread-name/timing instrumentation), a
real send attempt from the Redmi 10 2022 to the Pixel 8 Pro (both
genuinely bonded at the OS level, confirmed via `dumpsys
bluetooth_manager`) still failed with the same user-visible error:
"Message not sent — Could not reach this device in time. Try again."

Tracing the failure up the stack (rather than stopping at the transport
layer, which `E04-B11` already showed working):
- `chat_controller.dart`'s `send()` catches `TimeoutException` and shows
  exactly this error text.
- That `TimeoutException` can only come from
  `PrekeyExchange.ensureSession`'s own `completer.future.timeout(timeout)`
  (`_defaultEnsureSessionTimeout = Duration(seconds: 20)`) — a real Signal
  Protocol session-establishment round trip (X3DH-style bundle request/
  response), not a raw byte transfer.
- Live diagnostic instrumentation on `BluetoothTransport.send()`/
  `writeFrame()` (added, observed, then fully reverted — see `E04-B11`'s
  own Deviations entry) showed the OUTBOUND write itself succeeding
  instantly (`writeFrame OK in 0ms`) and the connection staying up
  afterward — the request genuinely leaves the Redmi's device. Something
  after that point — most likely on the Pixel's own receiving/response
  side — never produces the bundle response `ensureSession` is waiting
  for.
- Checked the Pixel's own "Network Nodes" (Devices) screen directly at
  this point: it shows exactly ONE relationship row,
  `AC:19:8E:6A:55:9E` — which, per `E04-B10`'s own earlier finding, is
  actually bonded to an unrelated Windows desktop
  (`DESKTOP-1K8PP7E`), not any phone. **The Pixel has no relationship
  entry at all for the Redmi's real, currently-bonded address.**

This strongly suggests (not yet confirmed to a specific line of code) that
the Pixel's own `InboundPipeline` — or whatever code path is responsible
for accepting/responding to an incoming prekey-exchange control frame —
silently drops or ignores a request from an address it has no relationship
record for, rather than at least classifying it as `Unknown` and
responding per whatever this app's own trust model dictates for a
never-seen sender (E02's `EvaluateConnectionRequestUseCase` territory,
same classification logic `devices_controller.dart`'s own discovery path
already uses — but `ensureSession`'s control-frame receipt path may not
route through the same classification at all, which would itself be the
bug).

**This investigation was cut short by real hardware becoming unavailable**
(the human needed the Pixel back for other use, and an Android emulator
cannot substitute — no real Bluetooth radio, an already-established
finding from earlier in this project's own history). The root cause below
is therefore a well-evidenced HYPOTHESIS, not a confirmed diagnosis — the
next session must verify it against the actual code before fixing
anything.

## 2. Working hypothesis (verify before fixing — do not assume this is right)
- The receiving device's inbound handling for `PayloadType.control` frames
  carrying `kControlKindPrekeyExchange` (see `prekey_exchange.dart`'s own
  `_sendControlFrame`/`handleControlFrame`) may not perform the same
  relationship lookup/classification that discovery and outbound sends
  already do — so a request from a genuinely unbonded-in-the-app's-own-
  relationship-sense (even though OS-bonded) sender is silently dropped
  rather than classified and responded to.
- Alternatively: the relationship classification happens correctly, but
  something about a first-contact bundle request specifically (as opposed
  to an ordinary message) short-circuits before a response is ever queued
  back to the sender.
- Alternatively: this is not a relationship/trust issue at all, and the
  Pixel's own `ensureListening()`/`acceptLoop()` path has its own,
  different defect that only manifests for an inbound connection it did
  not itself initiate (this task's own investigation never got as far as
  checking the Pixel's own native-side logs during the failed attempt —
  only the Redmi's).

## 3. What this task does
1. **Root-cause first, live, on two real physical devices with a
   genuinely fresh OS-level bond** (reuse `E04-B09`/`E04-B10`'s own
   established re-pairing procedure: forget the peer on both sides via
   native Bluetooth Settings, confirm via `dumpsys bluetooth_manager`,
   re-pair through the app's Discover/bond flow). Do **both** sides'
   diagnostics this time — the prior session only instrumented the
   sender (Redmi); this task must also check the **receiver's** own
   native and Dart-side logs during a failed attempt to see exactly where
   the incoming request stops being processed.
2. Confirm or refute the working hypothesis in §2 against actual code —
   read `handleControlFrame`'s full body and whatever classification (if
   any) gates it, on the RECEIVING side specifically.
3. Fix whatever the confirmed root cause turns out to be. This may be:
   relationship auto-classification for a first-contact control frame,
   a receive-path bug unrelated to relationships, or something else
   entirely surfaced during root-causing — do not assume the fix shape in
   advance.
4. Verify live, end-to-end, on real hardware: a message composed on one
   device genuinely arrives, decrypts, and renders on the other device's
   chat thread — not just "no error shown," an actual visible message
   bubble on the receiving side.

## 4. What this task does NOT do
- Does NOT re-touch `E04-B11`'s own fix (`send`'s `TaskQueue`) — that is
  independently verified and unrelated to this gap.
- Does NOT re-attempt `E04-B09`/`E04-B10`'s own bonding-flow verification
  — bonding itself is confirmed working; this task starts from an already
  -bonded pair.
- Does NOT assume the hypothesis in §2 is correct — verify against code
  and live behavior first per rule 7 ("done means proven"), the same
  discipline this task's own filing was built on.

  `E04-B09`/`E04-B10`/`E04-B11`/this task. Plan for the possibility this
  needs more than one session.
