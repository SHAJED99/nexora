# E04-B12 · Message delivery still fails end-to-end after E04-B11's transport fix

## 1. How this was found
Continuing directly from `E04-B11`'s own live verification session: with
that task's fix in place (`send()` genuinely running on a background
`TaskQueue`, confirmed via live thread-name/timing instrumentation), a
real send attempt from the Redmi 10 2022 to the Pixel 8 Pro (both
genuinely bonded at the OS level, confirmed via `dumpsys
bluetooth_manager`) still failed with the same user-visible error:
"Message not sent — Could not reach this device in time. Try again."

Tracing the failure up the stack (rather than stopping at the transport
layer, which `E04-B11` already showed working):
- `chat_controller.dart`'s `send()` catches `TimeoutException` and shows
  exactly this error text.
- That `TimeoutException` can only come from
  `PrekeyExchange.ensureSession`'s own `completer.future.timeout(timeout)`
  (`_defaultEnsureSessionTimeout = Duration(seconds: 20)`) — a real Signal
  Protocol session-establishment round trip (X3DH-style bundle request/
  response), not a raw byte transfer.
- Live diagnostic instrumentation on `BluetoothTransport.send()`/
  `writeFrame()` (added, observed, then fully reverted — see `E04-B11`'s
  own Deviations entry) showed the OUTBOUND write itself succeeding
  instantly (`writeFrame OK in 0ms`) and the connection staying up
  afterward — the request genuinely leaves the Redmi's device. Something
  after that point — most likely on the Pixel's own receiving/response
  side — never produces the bundle response `ensureSession` is waiting
  for.
- Checked the Pixel's own "Network Nodes" (Devices) screen directly at
  this point: it shows exactly ONE relationship row,
  `AC:19:8E:6A:55:9E` — which, per `E04-B10`'s own earlier finding, is
  actually bonded to an unrelated Windows desktop
  (`DESKTOP-1K8PP7E`), not any phone. **The Pixel has no relationship
  entry at all for the Redmi's real, currently-bonded address.**

Initially this suggested a relationship/trust-classification gap (the
Pixel not recognizing the Redmi's address). **That theory was directly
checked against the code afterward and does NOT hold up — see §2, which
replaces it with a much better-evidenced candidate found by tracing the
actual identity-matching logic.**

## 2. Root-cause hypothesis — a code-traced identity/addressing mismatch
(Superseding the relationship-classification guess from §1: read
`InboundPipeline._handleBuffer` and `PrekeyExchange._handleBundleRequest`
directly. Neither gates on relationship state except `blocked` — an
`unknown`/never-seen sender is still served a bundle response, per
`_handleBundleRequest`'s own `if (relationship == RelationshipState.blocked)
{ ...; return; }` being the ONLY early-out. `InboundPipeline._handleBuffer`
never checks relationship state at all for a control frame addressed to
this device. So a missing/wrong relationship row on the receiving side,
on its own, should NOT explain a silently-dropped bundle response.)

**What tracing the actual code turned up instead — a real, likely
architectural mismatch between two separate identity namespaces this app
uses, that nothing appears to reconcile:**

1. **The "device id" the UI, transport layer, and Devices screen all use
   is the peer's raw Bluetooth MAC address.** `chat_controller.dart:134`:
   `String get _peerDeviceId => conversationId;` — and every chat this
   session was opened by tapping a Devices-screen row titled literally by
   a Bluetooth address (e.g. `B8:DB:38:7C:D4:BF`). `TransportService.
   connect`/`.send` are called with this same string throughout
   (`ConnectionEnsuringSender`, `RelayEngine`). `Relationship.deviceId`
   (`lib/features/trust/domain/relationship.dart`) is the same
   Bluetooth-address-shaped string in every Devices-screen observation
   this session.
2. **A device's own `selfDeviceId` — the string `RelayPacketFrame.
   destination`/`.source` and `InboundPipeline`'s `isForUs` check
   (`frame.destination == _stack.selfDeviceId`) actually compare against —
   comes from a completely different source, unrelated to Bluetooth:**
   `lib/app/main.dart:106`: `final selfDeviceId = localIdentity?.deviceId
   ?? '';`, where `localIdentity` is read from this device's own
   `DeviceIdentity` row. That row's `deviceId` was chosen, at first
   sign-in, by `login_controller.dart:299-301`:
   `existingDeviceId ?? await _deriveDeviceIdFromLocalIdentity() ??
   generateSecureDeviceId()` — and both fallbacks are Bluetooth-unrelated:
   `_deriveDeviceIdFromLocalIdentity()` (`login_controller.dart:213-228`)
   returns a hex-encoded **Signal Protocol identity public key**;
   `generateSecureDeviceId()` (`login_controller.dart:91-94`) returns a
   **random 16-hex-char string**. Neither is, or is derived from, this
   device's Bluetooth MAC address.
3. **Nothing appears to reconcile the two namespaces.** `grep -rn
   "selfDeviceId" pigeons/ lib/core/transport/` returns zero hits — the
   transport/discovery/Pigeon layer never references `selfDeviceId` at
   all, so there is no announce/handshake step (that this search found)
   by which one device could learn a peer's REAL `selfDeviceId` and use
   that instead of the peer's Bluetooth address for `RelayPacketFrame`
   addressing.

**If this holds**, the failure mode is exactly what was observed: the
Redmi sends a bundle request with `destination = "B8:DB:38:7C:D4:BF"`
(the Pixel's Bluetooth address, correctly delivered at the transport
layer — `E04-B11` already proved the raw write succeeds). The Pixel's own
`InboundPipeline._handleBuffer` checks `frame.destination ==
_stack.selfDeviceId` — but the Pixel's real `selfDeviceId` is its own
random/key-derived identity string, not its Bluetooth address. `isForUs`
evaluates false. The frame is treated as a relay/forward candidate
instead of "addressed to me," `handleControlFrame` is never invoked, no
bundle response is ever sent, and `ensureSession` on the Redmi times out
waiting for a response that was never coming. This would also explain why
this bug was never caught before tonight: it requires two REAL,
independently-provisioned devices (each with their own genuinely
different random/key-derived `selfDeviceId`) to have gotten far enough
through discovery, bonding, AND a working transport (`E04-B11`'s own fix)
to even attempt this exchange — a combination this project's own history
shows was never reached until this session.

**CONFIRMED LIVE, 2026-09-12, directly — this is no longer a hypothesis.**
Added temporary diagnostic `print()` calls (added, observed, then fully
reverted — confirmed via `git diff` showing zero remaining trace) at
three points: `main.dart` right after `selfDeviceId` is computed,
`InboundPipeline._handleBuffer` right after `isForUs` is computed, and
`PrekeyExchange._sendControlFrame` right after `frame` is built. Rebuilt,
installed on both physical devices (Redmi 10 2022 `e4813f500601`, Pixel 8
Pro `192.168.0.108:9999`), force-stopped and relaunched both fresh:
```
Redmi logcat: B12DIAG selfDeviceId=65d14b4c75d6ddf5
Pixel logcat: B12DIAG selfDeviceId=aecdcd6f9b32dc0f
```
Neither value is, or resembles, either device's own Bluetooth MAC address
(the Pixel's real address is `B8:DB:38:7C:D4:BF`, confirmed independently
via `settings get secure bluetooth_address` earlier this same investigation
— see `E04-B10`). Since the Redmi's chat conversation with this peer is
titled, and addresses `TransportService.connect`/`.send` calls with,
exactly that Bluetooth-address string (confirmed by every chat screenshot
taken this entire session), `RelayPacketFrame.destination` on any message
the Redmi sends to this peer will be `"B8:DB:38:7C:D4:BF"` — a string that
can never equal the Pixel's real `selfDeviceId`
(`aecdcd6f9b32dc0f`). **This is a deterministic certainty given these two
values, not something that needed a further live send to prove — the
values alone are sufficient.** `isForUs` in `InboundPipeline._handleBuffer`
will evaluate `false` for every single message addressed this way, no
matter how many times it's retried, on any two real, independently
provisioned devices.

This explains every observed symptom in this investigation, end to end:
the raw transport write succeeds (`E04-B11` proved this), the connection
stays up, but the receiving device's own inbound pipeline never recognizes
the frame as addressed to itself, so `handleControlFrame` (and everything
downstream of it — bundle response, session establishment, message
decrypt) is never reached. `ensureSession` times out waiting for a
response that structurally cannot ever arrive. It also explains why this
was never caught before tonight: it requires two real, independently
provisioned devices (each generating their own distinct random/key-derived
`selfDeviceId` at first sign-in) to have gotten far enough through
discovery, bonding, AND a working transport (`E04-B11`'s own fix, merged
this same session) to even attempt the exchange — a combination this
project's own history shows was never reached until tonight.

**This is a foundational architecture gap, not a small bug** — the app
has always had two disconnected identity namespaces (Bluetooth MAC for
transport/discovery/UI, vs. a self-certifying string for messaging/Signal
Protocol identity) and nothing in the codebase has ever reconciled them.
Per this project's own rule 3, a foundational choice like "how should
this app's two peer-identity namespaces be reconciled" is a human call to
make with options and trade-offs presented, not something to implement
unilaterally — even under the standing extended-autonomy grant, which
explicitly does not reach "a foundational choice with no advisory
recommendation already on record." **§2a below presents that
recommendation. This task stops here, at diagnosis, pending that human
decision** — the Definition of Done reflects diagnosis-complete, not
fix-complete, for this reason.

## 2a. Fix-approach options (human decision needed — this is the actual foundational choice, not a formality)

**Option A — Announce `selfDeviceId` over the transport at first contact,
keep Bluetooth MAC only as a transport-layer routing hint.**
Add a lightweight identity-announce control frame (same `PayloadType.
control` mechanism `PrekeyExchange`/`DeliveryAckService` already use) sent
immediately after a connection opens, each side telling the other its real
`selfDeviceId`. The receiving side then re-keys that `Relationship` row
(and the Devices-screen entry, and the chat's own `conversationId`) from
the Bluetooth MAC to the peer's real `selfDeviceId`, while a SEPARATE,
internal mapping (`selfDeviceId` → last-known Bluetooth MAC) is kept
purely for `TransportService.connect`/`.send`'s own native-API
requirement (Android's Bluetooth APIs need a real MAC to open a socket,
so that mapping cannot be eliminated, only made invisible to the rest of
the app).
- *Pro*: fixes the root architecture, not a symptom — device identity
  becomes stable even across MIUI's own address randomization (the exact
  problem `E04-B08` separately worked around at the transport layer only).
  Aligns with how Signal Protocol identity is supposed to work (a stable
  identity key, not an ephemeral radio address).
- *Con*: real scope — touches discovery, the Devices screen/UI (every
  screenshot this whole project has shown a Bluetooth MAC as "the device
  id"; user-facing copy and possibly `design/screens/devices.md`'s own
  contract may need a human look), relationship storage, and adds a new
  wire sub-protocol. Not a "fix a bug" size — closer to a small feature.

**Option B — Use the Bluetooth MAC as the canonical `selfDeviceId` for
this transport, instead of a separately-generated one.**
Make Bluetooth-transport devices set their own `selfDeviceId` to their own
Bluetooth MAC address (or a stable derivation of it) rather than a random/
key-derived string, so the namespaces collapse into one by construction.
- *Pro*: much smaller change — likely just `login_controller.dart`'s
  device-id-selection logic and `main.dart`'s `selfDeviceId` wiring.
- *Con*: a Bluetooth MAC is not a stable identity in general (this
  project's own `E04-B08` exists specifically because MIUI randomizes it
  per-scan) — this could reintroduce the same instability at the identity
  layer that `E04-B08` fixed at the transport layer, and ties this app's
  core cryptographic identity to a property of a specific radio technology,
  which sits awkwardly with `FR-DISC-001`'s own multi-transport goal
  (Wi-Fi/Wi-Fi Direct/Internet-assisted transports, still unbuilt per this
  epic's own scope, would need a DIFFERENT physical address entirely —
  Option B doesn't generalize the way Option A does).

**Option C — Keep both namespaces, but do the reconciliation earlier, at
bonding time, using something already exchanged.** Investigate whether the
device's own Signal Protocol identity public key (already the fallback
source for `selfDeviceId` via `_deriveDeviceIdFromLocalIdentity`) could be
learned during the prekey bundle exchange ITSELF (the bundle already
contains an identity key) and used to re-key the relationship row
retroactively, without a NEW wire sub-protocol.
- *Pro*: no new control frame; reuses data already being exchanged.
- *Con*: the bundle exchange itself is the thing that's failing to
  complete (chicken-and-egg — `ensureSession`'s own bundle round trip
  never happens BECAUSE of this exact identity mismatch), so this option
  needs careful thought about whether reconciliation can happen on a
  DIFFERENT, more primitive exchange that doesn't depend on `isForUs`
  already working (e.g., a raw device-identity handshake immediately on
  `ConnectionState.connected`, before any `PayloadType.control` frame is
  ever sent) — which starts to look a lot like Option A with extra steps.

**Orchestrator's advisory recommendation: Option A.** It is the only one
of the three that doesn't trade one instability for another (Option B) or
have an unresolved chicken-and-egg problem (Option C), and it's the
option most consistent with `FR-DISC-001`'s own multi-transport future —
an identity-announce step keyed by `selfDeviceId` works identically
regardless of which transport carried it.

**🧍 Human decision, 2026-09-13: Option A chosen** (asked directly which
option to pick; the human said "do what is best," delegating to this
recommendation, which is itself the rule-3 foundational call being made,
not a bypass of it).

**Scope refinement made when turning this into an implementation plan
(disclosed, not silently narrower than what was presented):** Option A's
original description said the Devices screen and `Relationship.deviceId`
itself would be re-keyed to the peer's real `selfDeviceId`. That is MORE
invasive than necessary to fix the actual bug, and drags in a UI/display
convention change and a Devices-screen design-contract question that
doesn't need to be part of THIS fix. The scoped plan below instead:
- Keeps `Relationship.deviceId` as the Bluetooth-address string it already
  is, everywhere it's already used as a key (Devices screen, chat
  `conversationId`, `TransportService.connect`/`.send` calls) — **zero UI
  change, zero design-contract question, zero re-keying/migration risk to
  existing relationship rows.**
- Adds ONE new nullable column, `remoteSelfDeviceId`, to the existing
  `Relationships` table (additive migration, same shape as `E04-B02`'s own
  schema bump) — populated once a peer's real `selfDeviceId` is learned.
- The identity-announce protocol (this task, E04-B12) is responsible for
  learning and storing that value. Actually USING it to fix
  `RelayPacketFrame.destination`/`.source` addressing is `E04-B13`, a
  separate, dependent task — this split keeps each task a reviewable,
  independently-testable size (an `L`-sized single task was the
  alternative, and this project's own task-sharding discipline treats an
  `L` task as a planning failure to be split, not shipped).

## 3. What this task does
1. ~~Root-cause first, live~~ / ~~confirm the hypothesis~~ / ~~present
   fix-approach options~~ — **all done**, §2/§2a above.
2. **Add `remoteSelfDeviceId` (nullable `TextColumn`) to the `Relationships`
   table** (`relationships_table.dart` + an additive `database.dart`
   schema bump, schema version 20→21, transaction-wrapped rebuild — same
   shape as `E04-B02`'s own precedent). `null` until a peer's real
   `selfDeviceId` is learned; existing rows are unaffected (additive-only,
   no backfill needed since old rows simply haven't announced yet).
3. **Define a new identity-announce sub-protocol** in a new file,
   `lib/core/messaging/identity_announce.dart`, mirroring
   `PrekeyExchange`'s own file-header documentation style:
   - A new `kControlKindIdentityAnnounce = 8` (next unused value after
     `kControlKindLocationShare == 7`).
   - Wire body: just this device's own `selfDeviceId`, nothing else (no
     request/response pairing needed — this is a one-way, fire-and-forget
     announcement, sent by BOTH sides independently, not a request that
     expects a reply).
   - **The announce must be receivable BEFORE `isForUs` can possibly be
     true for it** (the whole reason it exists is that the receiver does
     not yet know the sender's real `selfDeviceId`, and the sender does
     not yet know the receiver's). `InboundPipeline._handleBuffer`'s
     `isForUs` check must be bypassed specifically and only for this one
     `controlKind` — justify this exception explicitly in the code
     (not just in this task file): a Bluetooth Classic RFCOMM connection
     is inherently point-to-point, and `TransportService.incomingData
     (deviceId)`'s own per-connection subscription model (established
     since `E04-B07`) means ANY frame arriving on a specific device's
     incoming-data stream is structurally known to have come from that
     OS-bonded Bluetooth address, regardless of what the frame's own
     `destination` field claims. This is NOT the same class of risk as
     `frame.source`'s own already-flagged unauthenticated status
     (`E06-T08`'s carried-forward finding) — that risk is about a
     multi-hop RELAYED frame's claimed origin being unverifiable; this
     announce is never relayed (point 4 below) and arrives directly over
     a connection the OS itself already authenticated via bonding.
   - Register the handler via `InboundPipeline.registerControlHandler`
     (the same seam `PrekeyExchange`/`DeliveryAckService`/etc. already
     use), wired in `messaging_stack.dart`'s composition root alongside
     the others.
4. **The announce frame must never be relayed/forwarded.** It is
   addressed to whichever specific device is on the other end of a direct
   connection, never a multi-hop destination — confirm (and if needed,
   guard) that `InboundPipeline`'s `!isForUs` relay branch cannot
   accidentally claim this `controlKind` before the new bypass in point 3
   gets a chance to handle it.
5. **Fire the announce automatically**, from both sides, immediately when
   a connection reaches `ConnectionState.connected` — before any
   application code (chat send, `ensureSession`) gets a chance to run, so
   the `remoteSelfDeviceId` mapping is already populated by the time
   `E04-B13`'s own outbound-resolution logic needs it. The natural place
   for this is `messaging_stack.dart`'s own connection-state observation
   (mirroring how `InboundPipeline` already reacts to
   `ConnectionState.connected` to open an `incomingData` subscription,
   per that file's own "Peer subscription lifecycle" doc comment).
6. **On receipt, store the announced value** in the matching
   `Relationship` row's new `remoteSelfDeviceId` column, keyed by the
   Bluetooth address the announce arrived on. If no `Relationship` row
   exists yet for that address (a genuinely first-ever contact), create
   one at `RelationshipState.unknown` the same way discovery already does
   elsewhere — do not invent a second code path for "create a
   relationship row," reuse whatever this codebase's own discovery/
   classification flow already does for that.
7. Write real tests for all of the above using this codebase's existing
   Dart test infrastructure (unlike the native Android transport layer,
   this is pure Dart — there is no "no test infrastructure" excuse here).
   At minimum: the new schema migration (upgrade path proven, not just
   fresh-create, per this codebase's own established migration-test
   pattern), the announce round-trip between two `InboundPipeline`/
   `MessagingStack` instances in a test harness, and the `isForUs` bypass
   applying ONLY to this one `controlKind` (a regular message/other
   control frame with a non-matching destination must still be correctly
   routed to relay, not accidentally swept into the new bypass).

## 4. What this task does NOT do
- Does NOT wire the learned `remoteSelfDeviceId` into
  `RelayPacketFrame.destination`/`.source` for OUTBOUND sends
  (`ConnectionEnsuringSender`, `PrekeyExchange._sendControlFrame`,
  `RelayEngine`) — that is `E04-B13`, a separate, dependent task. This
  task only builds and proves the announce/storage half; `E04-B13`
  consumes it to actually fix the `isForUs` mismatch end-to-end.
- Does NOT change `Relationship.deviceId` itself, the Devices screen's
  display convention, `design/screens/devices.md`, or any UI file — see
  §2a's scope-refinement note. Bluetooth-address-keyed relationships stay
  exactly as they are today.
- Does NOT re-touch `E04-B11`'s own fix (`send`'s `TaskQueue`) — that is
  independently verified and unrelated to this gap.
- Does NOT re-attempt `E04-B09`/`E04-B10`'s own bonding-flow verification
  — bonding itself is confirmed working.
- Does NOT add any new dependency, and does NOT touch
  `CryptoService`/`DriftSignalProtocolStore`/identity-key trust logic —
  this announce carries a plain string identifier, not a cryptographic
  identity claim; the untrusted-identity-key protections `PrekeyExchange`
  already has are completely separate and untouched.

## Risks
- Verifying this task's own DoD live (not just in a test harness) needs
  two real physical devices with real Bluetooth radios, available
  together at the same time — the same resource constraint that
  repeatedly interrupted this investigation across
  `E04-B09`/`E04-B10`/`E04-B11`. Since this task alone does not yet fix
  visible message delivery (that needs `E04-B13` too), the live-hardware
  proof for THIS task is narrower: confirm the announce is sent/received
  and `remoteSelfDeviceId` gets populated on both sides — not a full
  message send/receive round trip, which is `E04-B13`'s own DoD.
- The `isForUs` bypass is a genuine, narrow security-relevant carve-out
  in `InboundPipeline` — get an independent reviewer to specifically
  trace that it cannot be reached by any `controlKind` other than the
  new one, and cannot be used to spoof a relay-bypass for anything else.
