# E04-B10 · Prove E04-B09's bonding flow actually works on real hardware

## The gap
`E04-B09` implemented app-initiated `createBond()` bonding (`isBonded`,
`startBondAndConnect`, `registerBondReceiverIfNeeded`,
`handleBondStateChanged`, plus a review-round-1 fix adding a
`doConnectAfterBond` retry path) but **could not prove any of it against
real hardware**, for two independent, disclosed environmental reasons
(see `E04-B09.md` §On-device verification):
1. Live discovery between the two physical test devices did not succeed
   in that session (neither app, nor the OS's own native Bluetooth
   Settings scan, could find the other device from either side) — a
   real-world RF/proximity condition at the time, not a defect in the
   diff.
2. The chat compose `TextField` never accepted synthetic focus via
   `adb shell input text` on either device (MIUI or stock Android),
   blocking the fallback path of invoking `connect()` against an
   already-known peer address through the messaging feature.

On top of that, `E04-B09`'s own review round 1 found the bonding code
has **zero automated test coverage** (this Android module has no test
infrastructure at all — no `src/test`, no `testImplementation` deps in
`build.gradle.kts` — confirmed absent, matching `E04-B08`'s own
equivalent finding) and added two targeted fixes that are themselves
unverified on real hardware:
- **F1** — `startBondAndConnect` now cancels an in-progress discovery
  scan before `createBond()` (mirroring `doConnect`'s existing
  `cancelDiscovery()` guard).
- **F2** — post-bond connects now go through a new `doConnectAfterBond`
  (a short settle delay + one bounded retry on `IOException`), instead of
  `doConnect` firing a single attempt immediately on `BOND_BONDED`.

So today, `createBond()`, `BOND_STATE_CHANGED`, `BOND_BONDED`,
`BOND_NONE`, and both F1/F2 have **never been exercised against a real
Android bonding dialog**. This is a real functional gap, not a paperwork
one: the entire point of `E04-B09` was to make first-contact between two
never-paired devices actually work, and that has not yet been observed
to happen even once.

## What this task does
1. **Drive a real `createBond()` end-to-end between two genuinely
   never-paired (or freshly "forgotten") physical Android devices.**
   Reuse `E04-B09`'s own already-disclosed setup approach (forget the
   peer via native OS Settings on BOTH sides, confirmed via
   `dumpsys bluetooth_manager` before/after) so the starting state is
   provably unbonded, not just stale. Trigger discovery + tap the
   discovered peer from the Devices screen (or whatever UI path exists
   at the time) to invoke `connect()` against an unbonded target, and
   confirm the real Android system pairing-confirmation dialog appears
   on both devices, that accepting it transitions through
   `BOND_BONDING` -> `BOND_BONDED`, and that the app's own connection
   state ends at `CONNECTED` (not stuck at `CONNECTING`, not `FAILED`).
   Also confirm a rejected/cancelled pairing attempt reaches `FAILED`
   cleanly (not a hang) by rejecting the dialog on at least one attempt.
2. **Specifically confirm F1 and F2 hold live** — neither could be
   proven on real hardware when they were written (`E04-B09` review
   round 1, same-session fix, no device access at fix time):
   - **F1**: with an active discovery scan running, initiate a bond
     against a discovered peer and confirm (via `logcat` /
     `dumpsys bluetooth_manager`) that discovery is actually cancelled
     before `createBond()` fires, not racing it.
   - **F2**: confirm that the very first post-bond connect attempt does
     not simply fail once and report `FAILED` immediately (the pre-fix
     bug) — i.e. either the first attempt now succeeds (the settle delay
     helped) or, if it doesn't, the retry visibly fires and the second
     attempt succeeds, ending at `CONNECTED` rather than `FAILED` after
     a single failed try.
3. **Re-confirm `E04-B08`'s regression is still correct for a
   freshly-bonded peer**: once the new bond completes, trigger another
   discovery scan and confirm the newly-bonded peer is now resolved to
   its real, stable bonded address (via `resolveDeviceId`'s bonded-name
   match), not a fresh randomized discovery-scan address — the exact
   positive-branch confirmation `E04-B08`'s own `OQ-E04-B08-1` open
   question was never able to observe live.
4. **Record the result honestly** in this task file's own Run log and
   On-device verification section, whichever way it comes out — if a
   real environmental blocker recurs (radio/proximity, UI-automation
   focus, or anything else), disclose it exactly as plainly as
   `E04-B09` disclosed its own blockers, and hand off rather than
   force a claimed pass.
5. Update `E04-B09.md`'s own two currently-unticked on-device checklist
   items (bonding end-to-end; E04-B08 regression check) once genuinely
   observed — tick them there with this task's evidence, referencing
   this task's id, rather than leaving `E04-B09` permanently short of
   what it always intended to prove.

## What this task does NOT do
- Does **NOT** change any bonding/connect logic in `BluetoothTransport.kt`
  unless live evidence proves F1 or F2 themselves are wrong — if that
  happens, STOP, do not fix blind: write the finding into this task's own
  `## Open Questions`, since a code change belongs in a new, properly
  scoped bug task, not silently folded into a verification task.
- Does **NOT** add a custom pairing-confirmation dialog, un-bonding, or
  any bond-removal flow — out of scope per `E04-B09`'s own fence, and
  this task inherits it.
- Does **NOT** touch `RoutingEngine`/`RelayEngine` or any routing
  decision.
- Does **NOT** add native automated test infrastructure (JUnit/Robolectric/
  Mockito) — that would be a new-dependency, rule-3 human gate, and is a
  separate concern from proving the existing code works live.

## Risks
- **Same environmental risk that blocked `E04-B09` may recur**: two
  physical devices with real Bluetooth radios are required (no emulator
  has one), and the prior session's proximity/RF and UI-automation-focus
  blockers were real, not diff defects — this task may need to be
  attempted more than once, or by a human tester directly, if the same
  conditions recur.
- **A live finding that F1 or F2 doesn't actually fix the problem it
  targets** is a real possible outcome, not just a formality — this is
  precisely why this verification task exists rather than trusting the
  code-reading-only review that produced them.

- [ ] `E04-B09.md`'s two previously-unticked on-device checklist items

- [ ] Honest Run log entry either way (pass, or a disclosed blocker).

## On-device verification
**2026-09-12, orchestrator, ad-hoc re-attempt (not a formal task dispatch —
recorded here per disclosure discipline, since it's new hardware evidence
directly relevant to this task's own blockers):**

Prompted by a human report ("I can not send any message to the other
device"), attempted a live re-pair + send between the Redmi 10 2022 and
Pixel 8 Pro, devices physically adjacent (human-confirmed, <30cm) for the
retry. Findings:

1. **The app's own relationship rows are stale and pointing at the wrong
   real devices.** `AC:19:8E:6A:55:9E` — the address both phones' local
   relationship DBs show as an "Allowed"/"Paired locally" peer for each
   other — is, per `dumpsys bluetooth_manager` on the Pixel, actually
   bonded to a Windows desktop (`DESKTOP-1K8PP7E`), not either phone. The
   Redmi carries 5 stale relationship rows total; none resolve to the
   Pixel's real address either. These are leftovers from earlier testing
   sessions, not a fresh state.
2. **Zero real OS-level Bluetooth bond currently exists between the two
   phones.** `dumpsys bluetooth_manager` on the Redmi: `Bonded devices:`
   — empty. Confirms `E04-B09`'s "never bonded" starting condition is
   still genuinely true today, independent of the stale relationship-row
   issue above.
3. **Re-ran the app's own Discover flow (fresh `requestDiscoverable()` +
   `startDiscovery()`) on both sides, twice** — once at whatever distance
   the devices happened to be at, once after the human moved them
   adjacent. Zero `ACTION_FOUND` events either side, either time
   (confirmed via targeted `logcat` grep and `dumpsys bluetooth_manager`
   `Discovering: false` post-scan).
4. **Cross-checked with native Android Bluetooth Settings, bypassing the
   app entirely**, on the Redmi: a manual native scan (`android.settings.
   BLUETOOTH_SETTINGS`) — physically adjacent to the Pixel at this
   point — found a real nearby device (a Windows PC, `SRPPC3`) but **never
   found the Pixel**, despite `dumpsys bluetooth_manager` on the Pixel
   confirming `ScanMode: SCAN_MODE_CONNECTABLE_DISCOVERABLE` at that exact
   time. This rules out "the app's discovery code is broken" as the
   explanation — the OS's own inquiry, run directly through system
   settings, also could not see this specific peer at close range while
   it was genuinely, verifiably discoverable.

**Conclusion: this is not (or not only) the app-level RF/proximity
flakiness originally guessed at — it now looks like a genuine, reproducible
inability for these two specific physical radios to discover each other via
BR/EDR inquiry, independent of the Nexora app.** Neither swapping distance
nor going through native OS tooling changed the outcome. Possible causes
not yet isolated: one radio's BR/EDR inquiry-scan sensitivity, a MIUI-side
concurrent-BLE-scan resource conflict (this Redmi runs continuous
`MiuiFastConnectService`/system BLE scanning that could be starving classic
inquiry), or genuine hardware limitation on one side. This task cannot be
completed with these two specific units until that's resolved — a third
device, a different Redmi/Pixel pairing, or dedicated hardware debugging
(not available through ADB) is likely needed. Not closing this on a
guessed root cause; leaving it as `todo` with this evidence attached.
