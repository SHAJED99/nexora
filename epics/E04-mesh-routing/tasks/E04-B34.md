# E04-B34 · Drop a link-only peer when its connection ends

## 1. Fix

`DashboardController` now subscribes, once per device, to `TransportService.connectionState(deviceId)` for every device that reports a link measurement. It also tracks the peers a discovery scan reported and no scan has reported lost (`_discoveredPeerIds`).

When that device's connection state becomes `disconnected` or `failed`:
- its latency reading is cleared, if it produced the current one;
- the peer is removed from the nearby set, unless a discovery scan still vouches for it (losing a scan-found peer stays with `lostDevices`, E04-B28);
- the subscription is cancelled, and a later link measurement re-subscribes.

`BluetoothTransport.startReadLoop` already emits `DISCONNECTED` when a live socket's read loop ends from the remote side (E04-B17), and `disconnect()` emits it for a local close. No native change is needed.

## What this task does NOT do

- Does not change `TransportService`, the Pigeon schema, or any Kotlin.
- Does not change E04-B28's scan diff or make a dropped connection count as a scan "lost" event.
- Does not expire readings on a timer. `latencyMs` is only produced on a successful send, so an idle but healthy link would flicker to "No peers nearby".
- Does not touch `RoutingEngine`'s own link measurements. The reading falls to "No peers nearby" because the known-peer set empties, not because a route is removed.
- Does not redesign the Network Status card.
