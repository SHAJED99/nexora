# E04-T04 · Store-and-forward relay engine

## 1. Goal
When this device is a relay hop for someone else's route, temporarily hold
their encrypted packet and forward it toward its destination — using T02's
routing decisions and T03's transport, without ever touching plaintext.

## 2. Business logic
- FR-ROUTE-003 / EARS-ROUTE-3: a relay device never gains access to
  plaintext — this task only ever handles opaque `Uint8List` payloads
  (already encrypted by E03 at the origin); it must never attempt to
  decrypt, inspect, or log payload contents.
- FR-ROUTE-004: relayed packets are held with a priority, size, creation
  time, and expiry — if the next hop is unreachable, the packet waits
  (bounded by expiry) rather than being dropped immediately or forwarded
  blindly forever.
- "Make-before-break" from T02: when forwarding a packet whose route is
  mid-migration, this engine uses the *validated* new route once
  `RoutingEngine.considerMigration` says so — this task is where that
  seam (flagged as open in T02 §4) actually closes: forwarding a real
  packet over a new route IS the validation probe in practice.

## 3. What this task does
- `relay_packets` Drift table (epic.md's Data model): `id`, `destination_id`,
  `payload BLOB` (opaque, encrypted bytes — never parsed), `priority INT`,
  `size_bytes INT`, `created_at`, `expires_at`, `delivery_state` (queued /
  forwarding / delivered / expired / failed).
- `RelayEngine.enqueue(destination, payload, priority, ttl) -> String` (id)
  — persists a packet for forwarding.
- `RelayEngine.processQueue()` — for each queued packet (priority order,
  then oldest-first), asks `RoutingEngine.computeRoute` for the next hop,
  calls `TransportService.send` toward that hop; on success marks
  `delivered` (if this device is the destination's direct neighbor) or
  re-queues toward the next hop; on failure calls
  `RoutingEngine.onRouteFailure` and retries with the alternative if one
  exists, else leaves it queued until `expires_at`.
- `RelayEngine.sweepExpired()` — marks any packet past `expires_at` as
  `expired`, removes it from the active queue (kept as a row for
  diagnostics per the epic's later E13 needs, not deleted outright).

## 4. What this task does NOT do
- Does NOT decrypt, inspect, deduplicate-by-content, or reorder payloads
  by anything other than priority/age — payload is opaque bytes, full
  stop. Any code path that calls anything from `core/crypto` is out of
  scope and a violation of FR-ROUTE-003.
- Does NOT implement message-level delivery receipts, read receipts, or
  application-level dedup — that's E05. This engine's `delivered` state
  means "handed to the next hop's transport successfully," not "the
  end recipient's app confirmed receipt."
- Does NOT implement the actual make-before-break *probe* logic beyond
  "use whatever route `RoutingEngine.computeRoute` currently returns" —
  T02 already owns the migration *decision*; this task is a consumer, not
  a second implementation of migration policy.
- Does NOT add UI — no relay activity indicator, no queue-size display
  (that's a later epic's concern if ever built).

## 5. Contract

### Data

### Functions
```yaml
- signature: "RelayEngine.enqueue(destination: String, payload: Uint8List, priority: int, ttl: Duration) -> Future<String>"
  returns: "the new relay_packets row id"
  purpose: "Accepts a packet for store-and-forward"

- signature: "RelayEngine.processQueue() -> Future<void>"
  purpose: "One pass over the queue: attempt forward per packet, priority+age order, updates delivery_state"

- signature: "RelayEngine.sweepExpired() -> Future<int>"
  returns: "count of packets marked expired this sweep"
  purpose: "TTL enforcement — called periodically by whatever schedules this engine (out of scope here, see §4)"
```

## 6. Risks
- `processQueue()` must not hold a payload in memory longer than needed to
  attempt the send — no caching layer, no logging of payload bytes or even
  payload length in a way that could correlate traffic (size in the DB row
  is fine, per FR-ROUTE-004's own data model; logging every byte-length to
  an app log is not).
- Priority + age ordering interacting with T02's route-failure retry could
  starve low-priority packets if high-priority ones keep failing and
  retrying first — bound retries per packet per `processQueue()` pass
  (don't retry-loop one packet forever inside a single pass) and note the
  starvation risk as a known limitation if not fully solved.
- This task's tests should use T01's `NetworkSimulator` + T02's
  `RoutingEngine` together (not T03's real transport) — real Bluetooth
  isn't needed to prove queue/priority/expiry/retry logic, and using it
  would make this task's tests as unrunnable-without-hardware as T03b/c's.

**Deviations from spec/design:**
1. **§3's "on success marks `delivered` ... or re-queues toward the next
   hop" is implemented as: `delivered` when the next hop IS the
   destination (`route.hops.length == 1`), `forwarding` when it is an
   intermediate relay.** The schema declares 5 states including
   `forwarding`, which §3's own prose never assigns anywhere else — using
   it here for "successfully handed off to an intermediate hop, this
   device's part done" is the literal, minimal reading that makes the
   declared state meaningful rather than dead (avoiding this task's own
   `routes`-table-precedent problem from T02 §F3). A literal "re-queue and
   retry the same next hop again next pass" reading was rejected: nothing
   in the schema tracks "already forwarded to hop X", so blind re-queuing
   would resend to the same intermediate hop every `processQueue()` pass
   with no bound — a duplicate-delivery risk this task's own §4 correctly
   defers to E05 (no dedup/ack semantics here).
2. **`processQueue()` only ever attempts exactly one physical hop per
   packet** (`route.hops.first`), never walks a multi-hop route's
   remaining hops within the same call. This device cannot simulate a
   *different* device's own relay-forwarding decision — that requires that
   device's own `RelayEngine` instance, once it receives and re-enqueues
   the packet. This is the real-world-accurate reading and is what makes
   deviation 1 necessary/consistent.
3. **`failed` (one of §5's 5 declared states) is never assigned by this
   task's code.** §3's own text has every failure path (no route at all,
   or a failed send with no `onRouteFailure` alternative) "leave it queued
   until `expires_at`", never `failed`. Declared in the schema/enum (not
   silently dropped) exactly as written, but genuinely unused today — a
   later task/epic (e.g. a manual/diagnostic intervention) is free to use
   it. Documented in `relay_engine.dart`'s enum doc comment, same pattern
   T02 used for `routes.stableSinceTick`.
4. **Route-failure retry is bounded to exactly one alternative attempt per
   packet per `processQueue()` pass** (§6's starvation risk): the initial
   `computeRoute()` result, and if that send fails, one retry via
   `RoutingEngine.onRouteFailure`'s alternative — never a third attempt
   within the same pass. A packet that exhausts both stays `queued` for
   the next pass or until `expires_at`.
5. **`RelayEngine` takes an injected `RelaySendFn` (`Future<bool>
   Function(String nextHopId, Uint8List payload)`) rather than a direct
   `TransportService` dependency**, even though §3's prose names
   `TransportService.send`. Required by §6's own instruction that this
   task's tests use T01's `NetworkSimulator` + T02's `RoutingEngine`
   together, not T03's real transport — `TransportService` has no
   in-memory/deterministic test seam of its own (it talks to a Pigeon
   platform channel). The injected-function seam is the minimal shape that
   lets tests wire `NetworkSimulator.send` and lets a later epic wire
   `TransportService.send` without any change to `RelayEngine` itself.
6. **`RelayEngine` calls `RoutingEngine.setActiveRoute()` before each send
   attempt.** Not named in §5's function contract, but required for
   `RoutingEngine.onRouteFailure` to work at all — `onRouteFailure`
   blacklists the *active* route's first-hop link (per T02's own
   implementation), and if no active route was ever set, it has nothing to
   blacklist and would return the same failed route again. This is calling
   an existing, documented T02 API in the way T02's own review anticipated
   ("in production T04 would call `setActiveRoute` once it has validated a
   migration candidate" — T02 §Deviations #2), not inventing new API.
7. **Packet ids are generated locally** (`'${microsecondsSinceEpoch}-${counter}'`)
   rather than via a UUID library, since no `uuid` package is declared in
   `pubspec.yaml` and adding one is a 🧍 `new_dependency` gate this task
   does not need to clear for an internal-only identifier.
