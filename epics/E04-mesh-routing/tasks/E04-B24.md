# E04-B24 · Self-heal an orphaned conversation once its sender's real identity is already known

## 1. Goal

Close the gap `E04-B21`'s own task file explicitly disclosed and deferred
("Does NOT remediate the conversation/relationship ALREADY stuck...
handled as a one-off live-data fix outside this PR"): give the app a
safe, automatic, permission-free way to detect that an existing
conversation has no relationship row of its own, but its received
messages' sender identity is ALREADY known under a different,
correctly-resolved relationship — and migrate it there, without ever
inventing a new trust decision.

## 2. Background

`E04-B21`/`E04-B22` fixed the NATIVE accept-path bug that could
misresolve an inbound connection's remote address (including, in one
live-confirmed case, to this device's OWN address). Those fixes are
real and correctly scoped to preventing the defect for FUTURE accept
events. But a relationship/conversation that was ALREADY created by a
bad accept event, before those fixes existed, is untouched by them —
and critically, nothing in the rest of the pipeline ever re-evaluates
or corrects an EXISTING conversation's identity once messages start
arriving under it. The result, confirmed live: a real, already-trusted
peer's messages kept arriving in a conversation the user could never
reply from, because that conversation's own id was, literally, this
device's own address — Android's own OS refuses a self-connection.

This device has no reliable, permission-free way to directly ask "is
this id my own address" (`E04-B21`'s own round-1 review finding:
`BluetoothAdapter.getAddress()` returns an OS-hardened placeholder for
an unprivileged app). It does not need one. Every message this device
has ever RECEIVED already carries its sender's real cryptographic
identity (`messages.senderDeviceId`, populated from the Signal Protocol
session — never from the transport address). A `relationships` row's
own `remoteSelfDeviceId` (learned via the identity-announce protocol,
`E04-B12`) already records that same identity for whichever
conversation IS correctly keyed for that peer. So: a conversation with
no relationship row of its own, whose received messages' sender
identity unambiguously matches an EXISTING relationship, is provably
the same peer's traffic filed under the wrong key.

## 3. What this task does

- New `InboundPipeline._reconcileOrphanedMessagesByIdentity()`, called
  once from `start()` (alongside the existing `_seedKnownDevices()`):
  - Loads EVERY relationship row, any state, any (including null)
    `remoteSelfDeviceId` — used ONLY to decide whether a conversation
    already has a relationship row of its own (the orphan test). A
    SEPARATE, narrower set — non-null `remoteSelfDeviceId` **and**
    `state` is `trusted` or `allowed` — is used ONLY as migration-target
    candidates. Keeping these as two distinct sets, rather than reusing
    one filtered list for both questions, is itself a fixed defect (see
    Security note below — round-1 finding F1 introduced the filter;
    round-2 finding F5 caught that F1's filter had been applied to both
    questions at once, not just the target one).
  - Finds every DISTINCT `messages.conversation_id` that has NO
    matching `relationships` row (from the unfiltered set above) AND is
    not a `groups.id` (excludes group conversations, a completely
    different id space).
  - For each such orphaned conversation_id, looks at its RECEIVED
    messages only (`senderDeviceId != selfDeviceId` — a message this
    device sent itself says nothing about who the remote peer is).
  - If those received messages agree on exactly ONE sender identity,
    AND exactly ONE migration-target-candidate relationship's
    `remoteSelfDeviceId` matches it, migrates: `UPDATE messages SET
    conversation_id = <that relationship's device_id> WHERE
    conversation_id = <orphaned id>` — every message in the orphaned
    conversation moves together, including this device's own earlier
    (failed) sent messages, not only the received ones.
  - Any ambiguity (zero or multiple distinct senders, zero or multiple
    matching relationships) leaves the conversation untouched —
    mirrors `_reconcileStaleRelationship`'s own established
    conservative posture: never guesses, never invents a new trust
    decision, only ever corrects the KEY for a peer already
    independently trusted elsewhere.
- Ten tests (`test/core/messaging/inbound_pipeline_test.dart`, group
  `E04-B24`): the real-world migration case, three "must NOT migrate"
  negative cases (already has a relationship, no known match, ambiguous
  sender), a group-id exclusion case, a case proving a self-sent
  message is never used as the signal, a case proving a `blocked`/
  `unknown` relationship is never a valid migration TARGET (F1's own
  regression test), a case proving a mixed self-sent+received orphan
  migrates as one unit, and two F5 regression tests proving a
  conversation with its OWN `blocked` relationship, or its own
  never-announced (`remoteSelfDeviceId == null`) `allowed` relationship,
  is never treated as orphaned regardless of what an unauthenticated
  `senderDeviceId` claim inside it says. Independently falsified three
  times across two review rounds: reverting the whole fix fails exactly
  the one original positive-case test; reverting only F1's target-state
  filter fails exactly the blocked/unknown-target test; reverting only
  F5's fix (reusing the target-filtered set for the orphan test instead
  of the unfiltered one) fails exactly the two new source-side
  regression tests — each time for the right reason, nothing else
  regresses. A round-3 independent reviewer additionally probed a
  fourth combination the builder's own tests didn't cover (an `unknown`-
  state relationship WITH a non-null identity owning its own
  conversation) and confirmed the fix generalizes to the whole class,
  not just the two reported instances.

### Security note — the reverse-identity-lookup deviation (review F2/F3)

This function's core mechanism is a reverse lookup: given a claimed
sender identity (`messages.senderDeviceId`, itself sourced from
`RelayPacketFrame.source` — an **unauthenticated** claim carried in the
frame header, not a value this function can independently verify), it
searches `relationships` for a row whose `remoteSelfDeviceId` matches
that claim. `E04-B12`'s own review explicitly flagged this exact
reverse direction as unsafe in general, precisely because
`remoteSelfDeviceId` is itself peer-asserted and freely rewritable by
any device in range (`IdentityAnnounceService`) — nothing before this
task ever did a reverse lookup against it (confirmed via exhaustive
grep at `E04-B13` review time).

This task is a deliberate, narrow exception to that rule, made safe by
requiring the TARGET relationship to already be `trusted`/`allowed`
(the state filter above): the worst an adversarial or coincidental
identity match can do is misfile an orphan's messages into an
ALREADY-independently-trusted conversation — it can never grant trust
to, or make dialable, an `unknown`/`blocked` device, and it invents no
new trust decision. A round-1 review probe confirmed the pre-fix
version (matching against ANY relationship state, not just
trusted/allowed) let an orphan's messages migrate into a blocked or
never-accepted stranger's conversation — closed by the state filter,
covered by its own regression test above.

## 4. What this task does NOT do

- Does NOT require, read, or depend on this device's own Bluetooth
  address in any way — the whole point is a fix that works without
  that (unavailable) information.
- Does NOT touch `relationships` table rows at all — only migrates
  `messages.conversation_id`. A stale/orphaned relationship row, if one
  ever exists alongside orphaned messages, is out of this task's scope
  (in the live-confirmed case, no such row existed at all — the
  orphaned conversation was pure `messages` data with no relationship
  of its own).
- Does NOT change `_reconcileStaleRelationship`'s own name-based
  reconciliation (E04-B17) — unrelated, untouched, still handles its
  own different case (a relationship existing under a stale address,
  not a fully orphaned conversation with none).
- Does NOT retroactively fix a conversation whose messages come from
  MULTIPLE different, ambiguous senders, or from a sender this device
  has no OTHER already-established relationship with at all — those
  are correctly left alone rather than guessed at.
- Does NOT add a new user-facing "merge conversations" UI feature —
  this is a fully automatic, backend self-heal that runs once per
  `InboundPipeline.start()` call, same lifecycle as the existing
  `_seedKnownDevices()` it sits beside.
- Does NOT migrate `sync_cursors` (also keyed by `conversation_id`,
  `core/persistence/sync_tables.dart`) — the orphaned conversation's
  cursor row is left dangling under the old id. Disclosed, not fixed
  here: harmless today (message dedup is by `messages.id` primary key,
  `ReceiveMessageUseCase`, and the cursor's own upsert is monotonic),
  but noted as a known gap rather than silently ignored.
- Does NOT run per-message or continuously — see `OQ-E04-B24-2` below
  for the known consequence.

## Open Questions

- `OQ-E04-B24-1` — **RESOLVED 2026-09-14** by the live evidence in the DoD
  above. Original text: this fix has not yet been live-re-verified on the
  real Redmi device carrying the actual orphaned conversation this
  task was filed from. The mechanism is directly reasoned from the
  exact live-observed data shape (confirmed via direct SQLite
  inspection: the orphaned conversation's messages' `senderDeviceId`
  matches the CORRECT, already-known relationship's own
  `remoteSelfDeviceId` exactly), and is covered by a falsified unit
  test reproducing that same shape -- but "no live re-repro yet" is
  disclosed honestly rather than claimed as proven.
- `OQ-E04-B24-2` (round-1 review finding F4, disclosed not fixed): the
  reconciliation pass runs once per `InboundPipeline.start()` call, not
  per-message. A message written to an orphaned `conversation_id`
  AFTER this pass has already completed for that process lifetime
  stays split from the peer's main conversation until the next app
  launch. Self-heals on the next `start()`; not fixed here since
  running this per-message would be a materially different design
  (and a materially higher-cost one — a full relationship scan per
  inbound message) better justified by live evidence that this gap
  actually matters in practice, not built speculatively now. No owner
  assigned pending that evidence.
