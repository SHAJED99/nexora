# E04-B24 · Self-heal an orphaned conversation once its sender's real identity is already known

## 1. Goal

Close the gap `E04-B21`'s own task file explicitly disclosed and deferred
("Does NOT remediate the conversation/relationship ALREADY stuck...
handled as a one-off live-data fix outside this PR"): give the app a
safe, automatic, permission-free way to detect that an existing
conversation has no relationship row of its own, but its received
messages' sender identity is ALREADY known under a different,
correctly-resolved relationship — and migrate it there, without ever
inventing a new trust decision.

## 2. Background

`E04-B21`/`E04-B22` fixed the NATIVE accept-path bug that could
misresolve an inbound connection's remote address (including, in one
live-confirmed case, to this device's OWN address). Those fixes are
real and correctly scoped to preventing the defect for FUTURE accept
events. But a relationship/conversation that was ALREADY created by a
bad accept event, before those fixes existed, is untouched by them —
and critically, nothing in the rest of the pipeline ever re-evaluates
or corrects an EXISTING conversation's identity once messages start
arriving under it. The result, confirmed live: a real, already-trusted
peer's messages kept arriving in a conversation the user could never
reply from, because that conversation's own id was, literally, this
device's own address — Android's own OS refuses a self-connection.

This device has no reliable, permission-free way to directly ask "is
this id my own address" (`E04-B21`'s own round-1 review finding:
`BluetoothAdapter.getAddress()` returns an OS-hardened placeholder for
an unprivileged app). It does not need one. Every message this device
has ever RECEIVED already carries its sender's real cryptographic
identity (`messages.senderDeviceId`, populated from the Signal Protocol
session — never from the transport address). A `relationships` row's
own `remoteSelfDeviceId` (learned via the identity-announce protocol,
`E04-B12`) already records that same identity for whichever
conversation IS correctly keyed for that peer. So: a conversation with
no relationship row of its own, whose received messages' sender
identity unambiguously matches an EXISTING relationship, is provably
the same peer's traffic filed under the wrong key.

## 3. What this task does

- New `InboundPipeline._reconcileOrphanedMessagesByIdentity()`, called
  once from `start()` (alongside the existing `_seedKnownDevices()`):
  - Loads every relationship with a non-null `remoteSelfDeviceId`.
  - Finds every DISTINCT `messages.conversation_id` that has NO
    matching `relationships` row AND is not a `groups.id` (excludes
    group conversations, a completely different id space).
  - For each such orphaned conversation_id, looks at its RECEIVED
    messages only (`senderDeviceId != selfDeviceId` — a message this
    device sent itself says nothing about who the remote peer is).
  - If those received messages agree on exactly ONE sender identity,
    AND exactly ONE known relationship's `remoteSelfDeviceId` matches
    it, migrates: `UPDATE messages SET conversation_id = <that
    relationship's device_id> WHERE conversation_id = <orphaned id>`.
  - Any ambiguity (zero or multiple distinct senders, zero or multiple
    matching relationships) leaves the conversation untouched —
    mirrors `_reconcileStaleRelationship`'s own established
    conservative posture: never guesses, never invents a new trust
    decision, only ever corrects the KEY for a peer already
    independently trusted elsewhere.
- Six new tests (`test/core/messaging/inbound_pipeline_test.dart`,
  group `E04-B24`): the real-world migration case, three
  "must NOT migrate" negative cases (already has a relationship, no
  known match, ambiguous sender), a group-id exclusion case, and a
  case proving a self-sent message is never used as the signal.
  Independently falsified: reverting the fix fails exactly the one
  positive-case test, for the right reason (conversation_id unchanged),
  while every negative case and the full pre-existing suite stay
  green.

## 4. What this task does NOT do

- Does NOT require, read, or depend on this device's own Bluetooth
  address in any way — the whole point is a fix that works without
  that (unavailable) information.
- Does NOT touch `relationships` table rows at all — only migrates
  `messages.conversation_id`. A stale/orphaned relationship row, if one
  ever exists alongside orphaned messages, is out of this task's scope
  (in the live-confirmed case, no such row existed at all — the
  orphaned conversation was pure `messages` data with no relationship
  of its own).
- Does NOT change `_reconcileStaleRelationship`'s own name-based
  reconciliation (E04-B17) — unrelated, untouched, still handles its
  own different case (a relationship existing under a stale address,
  not a fully orphaned conversation with none).
- Does NOT retroactively fix a conversation whose messages come from
  MULTIPLE different, ambiguous senders, or from a sender this device
  has no OTHER already-established relationship with at all — those
  are correctly left alone rather than guessed at.
- Does NOT add a new user-facing "merge conversations" UI feature —
  this is a fully automatic, backend self-heal that runs once per
  `InboundPipeline.start()` call, same lifecycle as the existing
  `_seedKnownDevices()` it sits beside.
