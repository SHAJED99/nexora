# E04-B17 · Inbound delivery is silently broken end-to-end on real hardware -- a sent message never reaches the peer's Dart layer at all

## How this was found

Live, two-device verification (Redmi 10 2022, serial `e4813f500601`, and a
Pixel 8 Pro reconnected mid-session at `192.168.0.108:9999`) was run as the
gating test the entire E04-B11→B15 chain had been waiting on (see that
chain's own tracker notes: "done, NOT verified" pending exactly this). Both
devices were on a fresh debug build of `development` at commit `94ba160`
(includes B11-B15). The devices were already paired/bonded at the OS level;
a real `CLASSICAL-CONNECTED` Bluetooth Classic link between them is
independently confirmed in Android's own `dumpsys bluetooth_manager` log on
the Redmi.

A real chat message was composed and sent from the Redmi to the Pixel
(`B8:DB:38:7C:D4:BF`, the Pixel's paired Bluetooth MAC) through the actual
production UI (not a test double), repeated multiple times across several
app restarts to rule out one-off timing. **Every attempt failed** with the
user-facing message *"Message not sent -- Could not reach this device in
time. Try again."* -- `ChatController`'s own `on TimeoutException` branch,
meaning `PrekeyExchange.ensureSession`'s `completer.future.timeout(...)`
expired waiting for a bundle response that never arrived.

Direct database inspection (pulling and reading `nexora.sqlite` off both
devices via `run-as` + `base64`) confirmed, after every attempt:
- **Redmi**: `messages` table has 0 rows, `relay_packets` has 0 rows.
- **Both devices**: `relationships.remote_self_device_id` is `NULL` for
  every paired peer, on both sides -- meaning `E04-B12`'s identity-announce
  protocol has never once successfully completed between these two real
  devices, despite a live, OS-confirmed Bluetooth connection existing
  between them for the entire session.

To find the exact failure point, temporary diagnostic `print()` statements
were added (and, per this task's own discipline, reverted before this file
was written -- they are NOT part of this task's `files:` fence and were
never committed) at every hop of the send path:
`ConnectionEnsuringSender._runConnect`/`.ensureConnectedAndSend`,
`InboundPipeline._onDeviceDiscovered`/`._onConnectionStateChanged`/
`._handleBuffer`, `IdentityAnnounceService.sendAnnounce`/`.handleAnnounce`,
and `PrekeyExchange._sendControlFrame`/`._handleBundleRequest`. A fresh,
clean two-device test with PID-scoped `logcat` capture on both devices at
once produced this evidence:

**Redmi (sender) log** -- every step reports success:
```
[DIAG] PrekeyExchange._sendControlFrame: dest(resolved)=B8:DB:38:7C:D4:BF transportTarget=B8:DB:38:7C:D4:BF self=65d14b4c75d6ddf5
[DIAG] _runConnect: calling connect(B8:DB:38:7C:D4:BF)
[DIAG] _onConnectionStateChanged: B8:DB:38:7C:D4:BF => ConnectionState.connecting (already tracked=false)
[DIAG] _onConnectionStateChanged: B8:DB:38:7C:D4:BF => ConnectionState.connected (already tracked=false)
[DIAG] IdentityAnnounce.sendAnnounce: sending to B8:DB:38:7C:D4:BF, self=65d14b4c75d6ddf5
[DIAG] _runConnect: connect(B8:DB:38:7C:D4:BF) => true
[DIAG] ensureConnectedAndSend: calling send(B8:DB:38:7C:D4:BF, 184 bytes)
[DIAG] ensureConnectedAndSend: calling send(B8:DB:38:7C:D4:BF, 124 bytes)
[DIAG] ensureConnectedAndSend: send(B8:DB:38:7C:D4:BF) => true
[DIAG] PrekeyExchange._sendControlFrame: directSend => true
[DIAG] ensureConnectedAndSend: send(B8:DB:38:7C:D4:BF) => true
[DIAG] IdentityAnnounce.sendAnnounce: to B8:DB:38:7C:D4:BF => true
```
The sender believes it connected and successfully wrote both the identity
announce and the prekey bundle-request frames to the socket.

**Pixel (receiver) log, same time window** -- a grep for the SAME `[DIAG]`
tags returns **zero lines**. Not `_onConnectionStateChanged`, not
`_handleBuffer`, not `IdentityAnnounce.handleAnnounce` -- nothing. The only
Bluetooth-related activity in the Pixel's log at all is two bare
system-level lines from Android's own `BluetoothSocket` class:
```
D/BluetoothSocket(11316): acceptSocket: socket fd passed by stack fds:[...]
D/BluetoothSocket(11316): accept(), timeout (ms):-1
```
i.e. the OS-level `BluetoothServerSocket.accept()` call inside
`BluetoothTransport.kt`'s `acceptLoop` is at most only partially observed to
proceed -- there is no evidence any byte the sender wrote ever reached this
app's own Dart-visible inbound pipeline on the receiving device, not even a
raw, undecoded, malformed-frame counter increment.

## What this task does

1. **Root-cause exactly why an accepted (or dialled) real Bluetooth Classic
   connection's inbound bytes never reach `InboundPipeline._handleBuffer`
   on the receiving device**, despite the sending device's own transport
   layer reporting a successful write. Candidate areas to investigate, in
   the order this session's own evidence points to them -- not a
   prescribed diagnosis:
   - `BluetoothTransport.kt`'s `acceptLoop`/`startReadLoop`: does
     `accepted.remoteDevice.address` (the id `onConnectionStateChanged` and
     `onDataReceived` are keyed by for an INBOUND connection) actually match
     the Bluetooth MAC this app stored for the same peer in
     `relationships.device_id` when it was originally paired/discovered?
     `E04-B08` already found and fixed exactly this class of address
     mismatch for the discovery (`ACTION_FOUND`) path on MIUI/Xiaomi
     hardware (`resolveDeviceId`) -- confirm whether the SAME resolution is
     applied (or is even necessary) for an accepted RFCOMM socket's own
     `remoteDevice.address`, which this task's investigation must not
     assume is automatically safe just because B08 covers discovery.
   - `InboundPipeline._seedKnownDevices()`/`start()`: confirm this actually
     ran, and ran BEFORE the real connection settled, on the receiving
     device in a genuine two-device scenario (this session's own diagnostic
     prints in `_onDeviceDiscovered` never fired on the Pixel at all during
     the observed window, including the one-time seeding call for the
     already-`allowed` Redmi relationship -- confirm whether this is a
     timing gap, a silent early return, or the print was simply emitted
     before this session's log capture attached and the pipeline is
     actually fine).
   - Whether the native `eventsApi.onConnectionStateChanged`/
     `.onDataReceived` Pigeon calls are actually reaching the Dart
     `_EventsHandler` at all on a real device for an ACCEPTED (not dialled)
     connection -- vs. only ever being exercised, until now, by this
     project's own unit/integration tests, which use fakes for both sides
     and have never run across two physical radios.
2. **Fix the actual defect**, once located, with a regression test that
   proves it on the correct layer (a native/platform test if the bug is in
   `BluetoothTransport.kt`'s address handling or event dispatch; a Dart test
   with a corrected fake otherwise).
3. **Re-run the live two-device test** (the same Redmi + a second Android
   device) after the fix, and confirm in the DB directly:
   - `relationships.remote_self_device_id` becomes non-null on BOTH devices
     after connecting.
   - A real chat message sent from one device produces a `messages` row
     with `delivery_state = 'sent'` on the sender AND a corresponding
     decrypted, rendered bubble on the receiver -- not merely a `Queued`→
     `Failed` transition that stops erroring.

## What this task does NOT do

- Does NOT re-litigate or modify `E04-B12`/`E04-B13`/`E04-B14`/`E04-B15`'s
  own addressing logic (`resolveOutboundDestination`, the forward-only
  resolution constraint, `_takeMatchingCompleter`'s link-binding) -- every
  diagnostic trace in this task's own evidence shows the SENDER's side of
  that logic already runs and reports success. This bug is in the transport
  layer's inbound delivery path, upstream of anything E04-B12-B15 touch.
- Does NOT touch `E04-B16`'s own multi-hop routing gap -- that gap is about
  `RoutingEngine.computeRoute` once relay routing is exercised at all; this
  bug prevents even a single, direct, one-hop delivery from working, so
  E04-B16 remains correctly scoped as a separate, currently-inert follow-up.
- Does NOT assume the root cause without live-hardware re-verification --
  the candidate areas in §1 are starting points from this session's own
  evidence, not a prescribed fix. If investigation finds the true cause
  requires a wire-format or architecture-level change, that is a rule-3
  foundational call and must go back to a human with trade-offs, not be
  decided unilaterally.

## Definition of Done

- [ ] Root cause identified with file:line evidence (not guessed) for why
  the receiving device's Dart layer never observes an inbound connection
  event or inbound bytes that the sender's own log confirms were written.
- [ ] Fix implemented and covered by a regression test at the correct
  layer.
- [ ] A live two-device re-test (real hardware, not a fake/simulated
  transport) shows: `remote_self_device_id` populated on both sides after
  connecting, and a real message delivered end-to-end -- persisted `sent`
  on the sender, decrypted and rendered on the receiver. Screenshots/DB
  dumps from both devices attached to this task's own Run log as evidence,
  matching the same rigor this task's own "How this was found" section
  used to prove the bug.
- [ ] Existing test suite green.
