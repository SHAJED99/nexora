# E04-B17 · Inbound delivery is silently broken end-to-end on real hardware -- a sent message never reaches the peer's Dart layer at all

## How this was found

Live, two-device verification (Redmi 10 2022, serial `e4813f500601`, and a
Pixel 8 Pro reconnected mid-session at `192.168.0.108:9999`) was run as the
gating test the entire E04-B11→B15 chain had been waiting on (see that
chain's own tracker notes: "done, NOT verified" pending exactly this). Both
devices were on a fresh debug build of `development` at commit `94ba160`
(includes B11-B15). The devices were already paired/bonded at the OS level;
a real `CLASSICAL-CONNECTED` Bluetooth Classic link between them is
independently confirmed in Android's own `dumpsys bluetooth_manager` log on
the Redmi.

A real chat message was composed and sent from the Redmi to the Pixel
(`PHONE-A`, the Pixel's paired Bluetooth MAC) through the actual
production UI (not a test double), repeated multiple times across several
app restarts to rule out one-off timing. **Every attempt failed** with the
user-facing message *"Message not sent -- Could not reach this device in
time. Try again."* -- `ChatController`'s own `on TimeoutException` branch,
meaning `PrekeyExchange.ensureSession`'s `completer.future.timeout(...)`
expired waiting for a bundle response that never arrived.

Direct database inspection (pulling and reading `nexora.sqlite` off both
devices via `run-as` + `base64`) confirmed, after every attempt:
- **Redmi**: `messages` table has 0 rows, `relay_packets` has 0 rows.
- **Both devices**: `relationships.remote_self_device_id` is `NULL` for
  every paired peer, on both sides -- meaning `E04-B12`'s identity-announce
  protocol has never once successfully completed between these two real
  devices, despite a live, OS-confirmed Bluetooth connection existing
  between them for the entire session.

To find the exact failure point, temporary diagnostic `print()` statements
were added (and, per this task's own discipline, reverted before this file
was written -- they are NOT part of this task's `files:` fence and were
never committed) at every hop of the send path:
`ConnectionEnsuringSender._runConnect`/`.ensureConnectedAndSend`,
`InboundPipeline._onDeviceDiscovered`/`._onConnectionStateChanged`/
`._handleBuffer`, `IdentityAnnounceService.sendAnnounce`/`.handleAnnounce`,
and `PrekeyExchange._sendControlFrame`/`._handleBundleRequest`. A fresh,
clean two-device test with PID-scoped `logcat` capture on both devices at
once produced this evidence:

**Redmi (sender) log** -- every step reports success:
```
[DIAG] PrekeyExchange._sendControlFrame: dest(resolved)=PHONE-A transportTarget=PHONE-A self=65d14b4c75d6ddf5
[DIAG] _runConnect: calling connect(PHONE-A)
[DIAG] _onConnectionStateChanged: PHONE-A => ConnectionState.connecting (already tracked=false)
[DIAG] _onConnectionStateChanged: PHONE-A => ConnectionState.connected (already tracked=false)
[DIAG] IdentityAnnounce.sendAnnounce: sending to PHONE-A, self=65d14b4c75d6ddf5
[DIAG] _runConnect: connect(PHONE-A) => true
[DIAG] ensureConnectedAndSend: calling send(PHONE-A, 184 bytes)
[DIAG] ensureConnectedAndSend: calling send(PHONE-A, 124 bytes)
[DIAG] ensureConnectedAndSend: send(PHONE-A) => true
[DIAG] PrekeyExchange._sendControlFrame: directSend => true
[DIAG] ensureConnectedAndSend: send(PHONE-A) => true
[DIAG] IdentityAnnounce.sendAnnounce: to PHONE-A => true
```
The sender believes it connected and successfully wrote both the identity
announce and the prekey bundle-request frames to the socket.

**Pixel (receiver) log, same time window** -- a grep for the SAME `[DIAG]`
tags returns **zero lines**. Not `_onConnectionStateChanged`, not
`_handleBuffer`, not `IdentityAnnounce.handleAnnounce` -- nothing. The only
Bluetooth-related activity in the Pixel's log at all is two bare
system-level lines from Android's own `BluetoothSocket` class:
```
D/BluetoothSocket(11316): acceptSocket: socket fd passed by stack fds:[...]
D/BluetoothSocket(11316): accept(), timeout (ms):-1
```
i.e. the OS-level `BluetoothServerSocket.accept()` call inside
`BluetoothTransport.kt`'s `acceptLoop` is at most only partially observed to
proceed -- there is no evidence any byte the sender wrote ever reached this
app's own Dart-visible inbound pipeline on the receiving device, not even a
raw, undecoded, malformed-frame counter increment.

## Root cause (confirmed live, with file:line evidence)

Native+Dart diagnostic instrumentation across the full accept/connect/event
path (added temporarily, fully reverted before this PR — see Run log) on a
live two-device retest revealed the actual defect precisely: it is **not**
in the accept/read-loop mechanics or the Pigeon event bridge themselves —
both were confirmed working (`onConnectionStateChanged`/`onDataReceived`
both correctly reached Dart's `_EventsHandler`). The break is upstream, in
address identity:

**`acceptLoop`'s `accepted.remoteDevice.address` reports a stable but
non-bonded-looking address (`00:00:46:00:00:01` on the Redmi used for this
test) that does not match the address this app's own `relationships` table
had on file for the same peer (`DESKTOP-A`, almost certainly
inherited from a stale discovery-scan result predating `E04-B08`'s own
fix, or from before the peer was OS-bonded).** Since every Dart-side
stream (`connectionState`/`incomingData`) is filtered by exact device-id
match, and `InboundPipeline._onDeviceDiscovered` — the ONLY place a
subscription is ever created for a device id the Dart side doesn't already
have a relationship for — was never invoked at all for an ACCEPTED
connection (only for live discovery scans and for `_seedKnownDevices()`'s
own already-known relationships), the correctly-delivered native events
landed on a broadcast stream nothing was listening for and were silently
dropped, exactly matching this task's own original "How this was found"
evidence.

This is the same general class of defect `E04-B08` already found and fixed
for the discovery-scan path (an OEM Bluetooth stack presenting an address
with no stable relationship to the peer's real, bondable identity) — just
never previously exercised on the ACCEPT side, because no prior test in
this codebase's history ever ran two real, independently-installed devices
against each other long enough for one to accept an inbound connection at
all.

## The fix

Three, related changes, all confirmed necessary by live retest (each
change alone was insufficient — see Run log for the two intermediate,
still-failing states this went through):

1. **`BluetoothTransport.kt`'s `acceptLoop`**: resolves the accepted
   socket's raw remote address via the SAME `resolveDeviceId` bonded-name
   matching `E04-B08` already built for discovery, and now ALSO emits
   `onDeviceDiscovered` for the resolved peer (carrying its raw Bluetooth
   name) before `onConnectionStateChanged` — giving
   `InboundPipeline._onDeviceDiscovered` the one chance it never had to
   create a subscription and to reconcile a stale relationship (next
   point) for a connection this device did not itself dial.
2. **`InboundPipeline._reconcileStaleRelationship`** (new) + a new nullable
   `relationships.peer_name` column (additive migration, schema v21→v22):
   when a device id with no relationship of its own is discovered/accepted,
   and exactly one OTHER relationship's `peerName` matches (or, for a
   relationship that predates this column and so has `peerName IS NULL`,
   exactly one such unreconciled row exists), that relationship's
   already-evaluated trust state is copied forward to the new address —
   closing the actual gap this bug's root cause exposed (a relationship's
   stored address going stale relative to the peer's real, currently-live
   one, with previously no way to ever recover). Matches purely by name,
   never by address; deliberately inert on any ambiguous match (see that
   method's own doc comment for the full safety reasoning). `RelationshipRepository.upsert` and its one caller
   (`DevicesController.verify`) now also persist `peerName` going forward,
   so future reconciliation needs the migration fallback less often over
   time.
3. **`BluetoothTransport.kt`'s `connect()`** made idempotent when
   `openSockets` already holds a live socket for the target device id: once
   fix #1/#2 made an accepted connection's device id agree with the SAME id
   Dart later calls `connect`/`directSend` with for that peer (e.g. from
   `IdentityAnnounceService.sendAnnounce` firing right after accept), a
   genuinely NEW race became observable for the first time — the redundant
   outbound `doConnect()` this method always attempted regardless fired its
   own `CONNECTING` event, which `InboundPipeline._onConnectionStateChanged`
   treats as "no active link" and tears down the `incomingData` subscription
   the accept had JUST created, silently killing the very connection the
   call was trying to reuse. This was invisible before fix #1/#2 because
   inbound and outbound activity for the same peer never converged on the
   same device id at all.

**Live-verified end to end**: a real chat message sent from the Redmi was
observed physically arriving on the Pixel, correctly routed through
`InboundPipeline._handleBuffer` (`isForUs` true), and persisted as a real
`messages` row rendered in a real conversation — the sender showed a
genuine `Sent` checkmark (not `Queued`/`Failed`). This is the first time in
this bug's entire history that a message crossed devices at all.

**One remaining, narrower, unresolved item**: the delivered message
rendered as "(unable to decrypt this message)" — `ChatController`'s own
documented graceful-degrade path for a decrypt failure. This is very
likely explained by Signal Protocol session/one-time-prekey state on both
devices having been exercised dozens of times over this investigation's
many earlier failed send attempts (each a partial, incomplete handshake
under shifting, pre-reconciliation device-id keys) — not a new defect this
fix introduces, since decrypt happens strictly after this bug's own
transport-delivery defect and was never reachable before this fix at all.
**Not independently confirmed with a fully fresh install** (both test
devices were uninstalled and reinstalled to test this cleanly, but
automated Google Sign-In could not be driven past the account picker in
this environment, blocking that specific re-test) — logged honestly as an
Open Question below rather than assumed away.

## What this task does NOT do

- Does NOT re-litigate or modify `E04-B12`/`E04-B13`/`E04-B14`/`E04-B15`'s
  own addressing logic (`resolveOutboundDestination`, the forward-only
  resolution constraint, `_takeMatchingCompleter`'s link-binding) -- every
  diagnostic trace in this task's own evidence shows the SENDER's side of
  that logic already runs and reports success. This bug is in the transport
  layer's inbound delivery path, upstream of anything E04-B12-B15 touch.
- Does NOT touch `E04-B16`'s own multi-hop routing gap -- that gap is about
  `RoutingEngine.computeRoute` once relay routing is exercised at all; this
  bug prevents even a single, direct, one-hop delivery from working, so
  E04-B16 remains correctly scoped as a separate, currently-inert follow-up.
- Does NOT assume the root cause without live-hardware re-verification --
  the candidate areas in §1 are starting points from this session's own
  evidence, not a prescribed fix. If investigation finds the true cause
  requires a wire-format or architecture-level change, that is a rule-3
  foundational call and must go back to a human with trade-offs, not be
  decided unilaterally.
