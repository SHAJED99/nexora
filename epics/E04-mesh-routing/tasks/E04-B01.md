# E04-B01 · Relay traffic permanently suppresses route migration

## Severity: S2 (major function broken, no workaround)
`RoutingEngine.considerMigration` is the *entire* implementation of
EARS-ROUTE-2 / FR-ROUTE-006 (make-before-break) in this codebase. E04-T04's
`RelayEngine` — the only production consumer of the routing engine that E04
built — does not merely fail to gate on it (which is how the T04 reviewer
characterized the gap). It **actively destroys** the state
`considerMigration` needs, on every single forward attempt. Any device
relaying a steady packet stream to a destination can never migrate its route
to that destination, no matter how much better an alternative becomes or how
long the advantage holds.

This is S2 rather than S3 because there is no workaround available to a
caller: a future E05/E06 scheduler cannot "call considerMigration more
often" to get around it — the reset happens per relay packet, so more relay
traffic makes it strictly worse. It is not S1: nothing crashes, no data is
lost, and no plaintext is exposed (FR-ROUTE-003 / EARS-ROUTE-3 is
untouched). The mesh keeps delivering over whatever route `computeRoute`
returns; it just never performs a *validated* migration, which is the one
behavior EARS-ROUTE-2 names.

Severity per `skills/bug-sweep` is the reviewer's call. **Priority: P1
(human-resolved 2026-08-27)**, per the reviewer's advisory — this should
not leave E04, since E05/E06 are the epics that will send real traffic
through this path and would otherwise inherit a routing layer whose
migration mechanism is silently inert.

**🧍 Resolved, 2026-08-27:** fix the provable defect now (separate the two
signals per §Proposed fix direction option 1+2 below), and correct
T04/epic.md's docs to state plainly that relay forwarding uses per-packet
cheapest-path selection with no validated-migration probe for v1 —
EARS-ROUTE-2's validated-migration path has no production caller until
E05/E06 build one. A full make-before-break probe mechanism for relay
traffic is explicitly out of scope for this bug fix (option 3 below,
declined — would need `skills/change-impact`, not a bug-fix-sized task).

## Repro (exact, from a fresh state — reviewer-verified 2026-08-27)
Verified with a throwaway probe test on `epic_04` at commit `cbc2efd`.

1. Build a `RoutingEngine(selfId: 'A')` and record three links so that the
   direct path A→D is expensive and the 2-hop path A→B→D is far cheaper
   (well past the 20% improvement bar):
   - `recordLinkMeasurement('D', latencyMs: 1000, lossRate: 0.5, batteryDrain: 5.0)`
   - `recordLinkMeasurement('B', latencyMs: 5, lossRate: 0.0, batteryDrain: 0.1)`
   - `recordLinkMeasurement('D', latencyMs: 5, lossRate: 0.0, batteryDrain: 0.1, from: 'B')`
2. `setActiveRoute(Route(destinationId: 'D', hops: ['D'], cost: 999.0))`.
3. **Baseline (control):** call `considerMigration('D', TrafficProfile.interactive)`
   ten times in a row. The tenth returns `MigrationDecision.migrateTo(...)`.
   ✅ This is the documented behavior and it works.
4. **The defect:** repeat steps 1–2 on a fresh engine, construct a
   `RelayEngine(selfId: 'A', db: <in-memory>, routingEngine: <that engine>,
   send: (hop, bytes) async => true)`, then loop 60 times:
   - `considerMigration('D', TrafficProfile.interactive)`
   - `enqueue('D', <3 bytes>, 0, Duration(minutes: 5))`
   - `await processQueue()`

**Expected** (EARS-ROUTE-2, FR-ROUTE-006; epic.md OQ-E04-2's resolved
answer): the candidate route is ≥20% cheaper and holds that advantage for
far more than 10 consecutive samples, so `considerMigration` must return
`migrateTo` by the tenth sample — exactly as the step-3 control proves it
does without relay traffic. Interleaved relay activity is normal mesh
operation and must not change the migration decision.

**Actual:** `considerMigration` returns `MigrationDecision.stay()` on all 60
samples. Migration never fires. Probe output:
`DEFECT CONFIRMED: no migration in 60 samples with relay traffic`.

## Root cause
Two lines in two different tasks' files, neither wrong in isolation:

- `lib/core/routing_engine/routing_engine.dart:174-177` — `setActiveRoute`
  deliberately clears migration tracking:
  ```dart
  void setActiveRoute(Route route) {
    _activeRoutes[route.destinationId] = route;
    _migrationTracking.remove(route.destinationId);
  }
  ```
  Correct for its documented purpose ("switching routes starts a fresh
  comparison").

- `lib/core/routing_engine/relay_engine.dart:177` — `_attempt` calls
  `setActiveRoute` on **every** forward attempt of **every** packet:
  ```dart
  _routingEngine.setActiveRoute(route!);
  ```
  It does so only as a side-channel to make `onRouteFailure` blacklist the
  right first-hop link (see the comment at `relay_engine.dart:174-176`) —
  not because a route switch actually occurred. `route` here comes from
  `computeRoute` (`relay_engine.dart:162`), i.e. the current cheapest known
  path, which is usually the *same* route already active.

So a bookkeeping call intended to say "this is the link I'm about to use, so
blame it if the send fails" is read by `RoutingEngine` as "the caller
switched routes, discard the stability window." `RelayEngine` never calls
`considerMigration` at all.

Neither task's tests could catch this: T02's tests drive `considerMigration`
with no `RelayEngine` present, and T04's tests drive `processQueue` without
ever calling `considerMigration`. This is precisely a seam defect — which is
why the sweep exists.

## Proposed fix direction (builder to confirm; do not treat as prescriptive)
The bug is the conflation of two distinct signals. Separate them:

1. Give `RoutingEngine` an explicit way to record "this is the link I am
   transmitting over right now" **without** implying a route switch — e.g.
   `noteAttemptedRoute(Route)` that sets `_activeRoutes[dest]` but leaves
   `_migrationTracking` alone, keeping `setActiveRoute`'s reset semantics
   for genuine, validated switches only. Change `relay_engine.dart:177` to
   call that instead.
2. Decide, and write down, whether the relay path should gate on
   `considerMigration` at all for v1. The reviewer's read: **per-packet
   cheapest-path selection is defensible** for discrete store-and-forward
   packets (there is no established connection being torn down, so
   "make-before-break" has no literal referent), *provided* the docs say so
   plainly. If that is the chosen answer, fix (1) is the whole functional
   fix and the §2/epic.md wording must be corrected to "this task consumes
   `computeRoute` per packet and does not perform route migration;
   EARS-ROUTE-2's validated-migration path has no production caller until
   E05/E06." That is an honest, verifiable statement — unlike today's.
3. If instead a real make-before-break probe is wanted inside E04's scope,
   that is a larger change than a bug fix and should go back to the planner
   (`skills/change-impact`) rather than being improvised here.

The T04 reviewer previously wrote a guarded fix, could not prove it closed
the gap against the greedy `computeRoute` design, and reverted — correctly.
The reason it could not be proven is that the *stated* goal (relay
forwarding validates a migration) is not achievable without a probe
mechanism; the *actual* defect (the tracking reset) is small, local, and
directly provable. Fix the provable one; re-scope the other.

### 🔴 One real defect found and fixed by the reviewer
Introducing a second source of truth for "which link just failed" created
a latent wrong-link-blaming bug: `setActiveRoute` did NOT clear
`_lastAttemptedRoute`, so a stale attempt record outlived a validated
switch and won `onRouteFailure`'s `??` preference. Proven with a
throwaway probe: after `noteAttemptedRoute(['B','dest'])` →
`setActiveRoute(['C','dest'])` → `onRouteFailure('dest')`, the engine
blacklisted the **healthy A→B link** and left the **failed A→C path** as
the computed route.

Not reachable in production today (`RelayEngine` re-notes before every
attempt, and nothing calls `setActiveRoute` in production) — but it is
aimed squarely at the E05/E06 validated-migration caller that this very
fix's T04 §2 correction points at, and it would have failed silently.

Fixed in `routing_engine.dart` — `setActiveRoute` now also
`_lastAttemptedRoute.remove(dest)`, on the same reasoning as its existing
`_migrationTracking.remove`: a validated switch invalidates any earlier
attempt over a different path. Regression test added to
`relay_migration_seam_test.dart`:
`test_EARS_ROUTE_4_validated_switch_discards_stale_attempted_route`
(fails without the one-line fix, passes with it).
