# E02-B01 · No way to unblock a device from the Devices screen

## 1. Goal

Give a blocked device's row an "Unblock" action, restoring it to the
`allowed` state, so blocking is a reversible user decision rather than a
permanent dead end.

## 2. Business logic

FR-BLOCK-001: blocking prevents direct communication between two users.
Nothing in the spec makes this permanent or one-way, and the backend
already treats every `RelationshipState` transition uniformly
(`RelationshipRepository.upsert(deviceId, state, ...)` takes any target
state; `DevicesController.verify()` already proves the exact same UI
pattern -- a popup/inline action calling `upsert` with a different target
state -- for the Unknown -> Allowed transition). The only gap is that no UI
entry point ever calls `upsert` with a target state other than `blocked`
for an already-blocked row.

Unblocking restores `RelationshipState.allowed` (not `trusted`) --
mirroring `verify()`'s own choice for a freshly-approved device, so a
just-unblocked device goes through the same "Allowed" tier before a user
separately chooses to mark it "Trusted" (a distinct, stronger action
elsewhere in this screen), rather than silently restoring a higher trust
tier than a brand-new device would ever start at.

## 3. What this task does

- `devices_view.dart`: the `PopupMenuButton` for a device row already in
  `RelationshipState.blocked` offers "Unblock" instead of "Block" (a
  device NOT already blocked keeps seeing "Block", unchanged).
- `devices_controller.dart`: add `Future<void> unblock(String deviceId)`,
  calling `_repository.upsert(deviceId, RelationshipState.allowed)` --
  the same repository call `verify()` already makes, just from a
  differently-labeled entry point for a differently-starting state.
- One new controller test proving `unblock()` moves a `blocked` row to
  `allowed` and leaves every other row untouched.

## 4. What this task does NOT do

- Does NOT add a confirmation dialog before unblocking (blocking itself
  has none today -- consistent, not a new UX pattern to design here).
- Does NOT change what "Block" does for a non-blocked device, or touch
  `BlockUseCase` at all -- unblocking is a plain state restore via the
  existing repository, not routed through the block-specific use case
  (which handles block-specific side effects, e.g. group invisibility,
  that do not apply in reverse here).
- Does NOT add an "Unblock" affordance anywhere group-related
  (`FR-BLOCK-002`/`003`'s group-invisibility scope) -- this is the 1:1
  Devices screen only, matching where "Block" itself lives today.

## 5. Definition of Done

- [x] `PopupMenuButton` shows "Unblock" for a blocked row, "Block"
  otherwise.
- [x] `DevicesController.unblock()` exists and calls `upsert` with
  `RelationshipState.allowed`.
- [x] New test passes; full suite green; `flutter analyze` clean.
- [x] `make design-verify`-equivalent check: this is an additive menu
  item on an already-approved `PopupMenuButton` pattern (see
  `design/gaps.md` entry added), not a new screen element requiring a
  fresh design contract.
