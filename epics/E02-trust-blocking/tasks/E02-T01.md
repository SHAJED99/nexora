# E02-T01 · Relationship domain — trust states, connection evaluation, blocking

## 1. Goal
The data model and business logic for device relationships — Trusted /
Allowed / Unknown / Blocked — evaluated independently on each side, with
blocking as a complete, enforced boundary. No UI; E02-T02/T03 build on this.

## 2. Business logic
- FR-TRUST-003/005: each side evaluates a connection request independently
  into Trusted/Allowed/Unknown/Blocked; a connection is permitted only when
  BOTH sides independently allow it (never derive B's evaluation from A's).
- FR-TRUST-004: a device already marked Trusted by the local side
  auto-accepts a request from it, skipping normal authentication.
- FR-TRUST-001/002: relationships persist locally and survive
  uninstall/reinstall in the sense that they're stored in Drift, which the
  app's own local-first storage already protects across app-updates
  (FR-VER-003) — full reinstall-survival (e.g. cloud restore) is out of
  scope here (would need E01-T02's Firebase metadata scope extended, which
  isn't this task's job).
- FR-BLOCK-001: blocking prevents ALL direct communication in both
  directions — this task defines the single enforcement point
  (`isBlocked(deviceId)`) every later communication epic (E04+) must call.
- FR-BLOCK-002/003: full group-level invisibility and group-key exclusion
  are E07's job (groups don't exist yet) — this task only guarantees the
  underlying block-state query those features will need.

## 3. What this task does
- `relationships` Drift table: `deviceId` (PK), `state` (enum:
  trusted/allowed/unknown/blocked, stored as name string per
  `docs/conventions.md` "Enums"), `updatedAt`.
- `Relationship` domain entity + `RelationshipState` enum.
- `EvaluateConnectionRequestUseCase`: given an incoming request from a
  device, returns this side's independent evaluation (auto-accept if
  already Trusted; otherwise Unknown by default — no auto-accept-specific
  and require-auth-for-unknown *configuration* yet, that's FR-TRUST-006,
  E02-T03's gap-blocked UI; the use case itself takes those as optional
  parameters so E02-T03 can wire real config later without changing this
  task's contract).
- `BlockUseCase`: sets a relationship to Blocked; `RelationshipRepository`
  exposes `isBlocked(deviceId) -> Future<bool>` as the one enforcement
  query point.
- A connection is "permitted" only when a helper combines *both* sides'
  evaluations (`isConnectionPermitted(localEval, remoteEval)`) — modeled
  now even though there's no real remote-side evaluation to combine with
  yet (no transport/E04); this is the seam E04 wires into.

## 4. What this task does NOT do
- Does NOT build any UI (E02-T02/T03).
- Does NOT implement FR-TRUST-006's actual user-configurable rules
  (auto-accept-specific-users, require-auth-for-unknown, allow/disable
  communication, location-access toggle) — this task's use case accepts
  them as optional parameters with safe defaults, but no settings UI or
  persisted config exists yet. That's E02-T03's design-gap-blocked scope.
- Does NOT implement group-level invisibility (FR-BLOCK-002) — no groups
  exist yet (E07).
- Does NOT touch Firebase/relationship-config sync (FR-TRUST-007) — flagged
  as an open question below, not silently skipped.
- Does NOT implement real device discovery or a real remote evaluation
  exchange (E04) — `isConnectionPermitted` is a pure function ready for
  E04 to call, not a live network handshake.

## 5. Contract

### Data
Drift migration: new `relationships` table (schema version 3). Additive —
no changes to existing tables.

### Functions
```yaml
- signature: "EvaluateConnectionRequestUseCase.call(deviceId: String, {bool autoAcceptSpecific = false, bool requireAuthForUnknown = false}) -> Future<RelationshipState>"
  params: { deviceId: "the requesting device's id", autoAcceptSpecific: "FR-TRUST-006 param, default off until E02-T03 wires real config", requireAuthForUnknown: "FR-TRUST-006 param, default off" }
  returns: "the LOCAL side's independent evaluation — Trusted if already known-trusted, else Allowed/Unknown per the flags, defaulting to Unknown"
  purpose: "FR-TRUST-003/004/005 — one independent evaluation, never derived from the other side"

- signature: "BlockUseCase.call(deviceId: String) -> Future<void>"
  params: { deviceId: "the device to block" }
  returns: "void — writes state: blocked"
  purpose: "FR-BLOCK-001 enforcement entry point"

- signature: "RelationshipRepository.isBlocked(deviceId: String) -> Future<bool>"
  params: { deviceId: "the device to check" }
  returns: "true iff the local relationship state is blocked"
  purpose: "The one query every later communication epic must call before allowing any direct interaction with deviceId"

- signature: "isConnectionPermitted(local: RelationshipState, remote: RelationshipState) -> bool"
  params: { local: "this side's evaluation", remote: "the other side's evaluation" }
  returns: "true only if neither side is Blocked and both sides allow (Trusted/Allowed) — Unknown on either side means not yet permitted"
  purpose: "FR-TRUST-005 bidirectional-independent gate, the seam E04 calls once real evaluation exchange exists"
```

## 6. Risks
- Bidirectional-independent evaluation is easy to accidentally implement
  as one-sided — `isConnectionPermitted` must take two explicit evaluations
  as parameters, never look up "the" state for a pair.

## 8. Acceptance criteria (EARS) + test plan
- **EARS-TRUST-1**: WHEN a request arrives from an already-Trusted device, the system SHALL evaluate it as Trusted without requiring re-authentication. (FR-TRUST-004)
- **EARS-TRUST-2**: The system SHALL evaluate connection requests independently per side — evaluating device A's request never reads or depends on device B's own stored evaluation of A. (FR-TRUST-003/005)
- **EARS-BLOCK-1**: IF a device is blocked, THEN `isBlocked` SHALL return true and `isConnectionPermitted` SHALL return false regardless of the other side's evaluation. (FR-BLOCK-001)

### Tests
- `test_EARS_TRUST_1_trusted_device_auto_accepts`
- `test_EARS_TRUST_2_evaluation_is_independent_per_side` — construct two relationship rows for the same device pair with different states, assert evaluating one never mutates or reads the other
- `test_EARS_BLOCK_1_blocked_device_never_permitted` — parameterize over all four remote states, assert `isConnectionPermitted` is false in every case when local is Blocked
