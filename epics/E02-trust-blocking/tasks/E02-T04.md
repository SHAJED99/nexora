# E02-T04 · Allow/disable new connection requests — FR-TRUST-006's sixth rule

## 1. Goal
A user can turn off "new connection requests" on `/settings/privacy`, and from
that moment a device this phone has never had a relationship with is refused at
first contact — while every conversation the user already has keeps working
exactly as before.

## 2. Business logic

`FR-TRUST-006` lists *allow/disable communication* among six configurable
rules. Its scope was undefined and was raised as **`Q-FUNC-011`**. The human
answered it on **2026-09-27**, verbatim:

> "Disable communication" blocks **only new connection requests**. It does
> **not** suppress inbound delivery, hide existing conversations, alter
> notifications, or otherwise silence established conversations.

That answer is this task's entire specification, and both halves of it are
binding — the second half as strictly as the first.

### The structural guarantee

`EvaluateConnectionRequestUseCase.call` already distinguishes the two cases,
and the distinction is exactly the one the decision needs:

- a **stored relationship row exists** (`trusted` / `allowed` / `blocked`) →
  the stored state is returned as-is. Every established conversation is in
  this branch.
- **no relationship row at all** → `unknown`. This, and only this, is a
  genuinely new connection request.

So the gate goes **after** the `existing != null` early return, never before
it. Placing it earlier would silence established peers and is the failure this
task exists to avoid. The `existing != null` return must come out of this task
**byte-for-byte unchanged**.

### Return value when disabled

`RelationshipState.blocked`, not `unknown`. `E13-T02` already established the
reason in this same file: `blocked` is the only value every existing caller
actually refuses on (`MessagingStack`, `prekey_exchange.dart:563`, `:731`);
`unknown` lets them proceed. The rate limiter denies the same way. This task
follows that precedent rather than inventing a fourth outcome.

Like the rate-limiter denial, this **never writes a `relationships` row** — a
user who turns the setting back on has persisted no false "blocked" verdict.

### Default value

`allowNewConnectionRequests` defaults to **`true`**, on `onCreate` and on
`onUpgrade` alike. This is deliberately *not* the "privacy controls default
off" reasoning `location_settings` used, and the difference matters: the
location default withholds data that was never shared, whereas defaulting this
to `false` would silently stop every existing install from accepting anyone.
An additive migration preserves current behaviour, and current behaviour is
"new requests are accepted".

### Wiring

- `MessagingStack.create` (`messaging_stack.dart:336`) is the production
  construction site that `PrekeyExchange` — the real first-contact path —
  evaluates through. It gets the repository.
- The repository parameter on `EvaluateConnectionRequestUseCase` is
  **optional and nullable**, matching `_rateLimiter`'s existing shape. Omitted
  → the gate is skipped and behaviour is byte-for-byte unchanged. That is what
  keeps `DevicesController`'s own fallback construction site (§4) untouched.

## 3. What this task does

1. **`trust_tables.dart`** — `TrustSettings`, a single-row table
   (`id == 1`, `@DataClassName('TrustSettingRow')`) with
   `allowNewConnectionRequests` (bool, default `true`) and `updatedAt`
   (epoch-ms int). Shape copied from `LocationSettings`.
2. **`database.dart`** — `schemaVersion` 23 → 24; `onCreate` inserts the
   default row with `InsertMode.insertOrIgnore`; a `from < 24` step creates the
   table and inserts the same row. Additive only, per `docs/conventions.md`
   "Schema migrations". Regenerate `database.g.dart` with
   `dart run build_runner build --delete-conflicting-outputs`.
3. **`TrustSettingsRepository`** — `readAllowNewConnectionRequests()`,
   `watchAllowNewConnectionRequests()` (emits immediately on listen),
   `writeAllowNewConnectionRequests(bool)`. Structure and doc-comment
   discipline copied from `LocationSettingsRepository`.
4. **`EvaluateConnectionRequestUseCase`** — optional
   `TrustSettingsRepository? trustSettings`; the gate placed exactly as §2
   describes, with a comment naming `Q-FUNC-011` and both halves of the answer.
5. **`MessagingStack.create`** — passes `TrustSettingsRepository(db: db)`.
6. **`PrivacySettingsController`** — `Rx<bool?> allowNewConnectionRequests`
   (`null` = loading), `RxBool connectionSettingsError`, and
   `setAllowNewConnectionRequests(bool)` with the same
   "unknown state never writes" guard `setGlobalLocation` uses. The
   subscription is cancelled in `onClose`.
7. **`PrivacySettingsView`** — PV23 (section card), PV24 (`Connection
   requests` heading) and PV28 (row + state + the clarifying body line),
   using the existing `SettingsSectionCard` / `SettingsSectionHeading` /
   `SettingsBodyLine` / `SettingsEmptyOrErrorLine` primitives and the
   `_GlobalLocationRow` toggle-row shape. The tap target is inert (`null`)
   while the value is `null`, exactly as PV16's is.
8. **`settings_binding.dart`** — the controller gets a
   `TrustSettingsRepository` over the shared `db`, in the same `Get.lazyPut`
   block.
9. **Docs** — `settings-privacy.md` gains PV28 and its copy, and its
   §Derivation-boundary item 7 is corrected; `design/gaps.md` GAP-044 records
   the answer and which elements are now built; `spec/questions.md` moves
   `Q-FUNC-011` to Answered with the verbatim answer and date.

  path.** No protocol change of any kind.

  `evaluate_connection_request_use_case.dart`.
- **Does NOT write a `relationships` row** when refusing.
- **Does NOT add a second writer for any existing setting** — this screen
  remains the only writer of this one, and gains no others.
- **Does NOT back-fill, drop or rewrite any existing table or column.**

## 7. Risks
- **The gate drifts above the early return.** Then every existing conversation
  goes dark, with no error anywhere. The two
  `still_returns_*_for_an_established_peer` tests and the real-path delivery
  test exist for this one risk.
- **`database.g.dart` regenerated with unrelated churn.** Regenerate, then read
  the diff; it should contain the new table and nothing else.
- **A default of `false` shipped by accident.** Every existing install stops
  accepting anyone, silently. The migration tests assert the value, not merely
  the column's existence.
