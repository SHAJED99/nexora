# E02-T02 · Devices screen — real relationship list, trust/block actions

## 1. Goal
Build the real `/devices` screen against its design contract, wired to
E02-T01's relationship data — the first screen where a user actually sees
and acts on trust state.

## 2. Business logic
- Renders each known relationship with its real state (Trusted/Allowed/
  Unknown/Blocked) — matching the contract's four example rows'
  states/icons/colors exactly (design/screens/devices.md elements 13-14,
  21-22, 29-30, 37-38).
- The "Verify" button (contract element 31, shown only on Unknown-state
  rows) and the kebab (`more_vert`) menu on other rows are the entry
  points into E02-T01's `BlockUseCase` / trust actions.
- Bottom nav (Dashboard/Conversations/Devices/Settings) — Devices is the
  active tab; other tabs route to their existing/future screens per
  `docs/routes.md`.

## 3. What this task does
- Real `/devices` route, screen, controller, GetX binding.
- Reads relationships via `RelationshipRepository` (E02-T01) — no live
  device discovery yet (E04 doesn't exist), so the list is whatever
  relationships already exist locally (empty state if none).
- Kebab menu action: "Block" (calls `BlockUseCase`) at minimum — matching
  what's structurally supported by the contract's generic `more_vert`
  button without inventing new menu items the design doesn't show.
- "Verify" button on Unknown rows: promotes the relationship to Allowed
  (the only state transition FR-TRUST-006's not-yet-built config would
  otherwise gate — safe minimal behavior, logged as a deviation if it
  turns out to need more).
- The "Discover" button (contract element 6) is present and tappable but
  intentionally a no-op/disabled-with-tooltip for now — real discovery is
  E04's job. This is a real gap, logged below and in `design/gaps.md`.

## 4. What this task does NOT do
- Does NOT implement real device discovery (E04).
- Does NOT implement the group-invisibility behavior (E07/no groups yet).
- Does NOT touch the Settings screen (E02-T03).
- Does NOT add menu items or states the design contract doesn't show —
  if a real trust workflow needs more than Block/Verify, that's a new
  `design/gaps.md` entry for human approval, not an invented button.

**Deviations from spec/design** (none, or list):
1. **`lib/features/trust/data/relationship_repository.dart` touched, not in `files:`.** The task's contract only listed the three new `devices/presentation/*` files plus `routes.dart`/`bindings.dart`/`docs/routes.md`, but E02-T01's repository had no way to read back *all* stored relationships (`get(deviceId)` only, single-row). Rendering the list is the task's core job, so a `listAll()` method was added, following the existing `get()`/`upsert()` pattern (query the same `relationships` table, most-recently-updated first). No existing method's behavior changed.
2. **`lib/core/design/tokens.dart` touched, not in `files:`.** Per `docs/conventions.md` "UI widget kit"/design-system section, screen tokens live in `core/design/tokens.dart`, added incrementally per screen. Devices' tokens (colors + text styles) were added there, reusing four values that are pixel-identical to existing welcome/login tokens (documented inline) and adding only the values genuinely new to this screen.
3. **Device name and transport-type are placeholders (GAP-003).** `RelationshipRepository` stores only `deviceId`/`state`/`updatedAt` — no device name or transport metadata exists pre-E04 discovery. The row shows the raw `deviceId` as the name and a fixed `"Paired locally"` subtitle. Logged in `design/gaps.md` GAP-003, traced to FR-DISC-001.
4. **Leading device icon is not per-device-type.** The contract's four example rows show different icons (`laptop_mac`/`smartphone`/`router`/`desktop_windows`) with distinct colors, but no device-type field exists in the domain model. A single `Icons.devices` glyph is used for every row, tinted by `RelationshipState` (matching the color each state's example row happens to use in the golden capture). Logged alongside GAP-003.
5. **"Discover" is a no-op with a SnackBar acknowledgement**, per task §3/§6 and OQ-E02-T02-1 — confirmed on-device (see §Run log).
6. **Bottom nav's Dashboard/Conversations/Settings tabs are inert (`onTap: () {}`).** Their routes are not yet registered (`docs/routes.md` "Contracted, not yet wired") — navigating to an unregistered GetX route would show GetX's unknown-route fallback, which is worse than a harmless no-op. Devices (the active tab) intentionally does nothing since it's already the current screen.
