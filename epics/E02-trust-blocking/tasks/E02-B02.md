# E02-B02 · `trusted` is a state the app can read but never reach

## 1. Goal

A user who has paired, messaged and approved a peer can add that peer to a
group. Today they cannot, and no sequence of actions in the product will
ever let them.

## 2. The defect

`RelationshipState.trusted` is **never written by anything**. There are
exactly four `upsert` call sites in the entire application:

| Call site | State written |
|---|---|
| `lib/features/devices/presentation/devices_controller.dart:298` (`verify()`) | `allowed` |
| `lib/features/devices/presentation/devices_controller.dart:350` | `allowed` |
| `lib/features/trust/domain/block_use_case.dart:15` | `blocked` |
| `lib/features/trust/data/relationship_repository.dart:24` | *(the method definition)* |

Every other occurrence of `RelationshipState.trusted` in `lib/` is a
**comparison**, never an assignment. Verified by
`grep -rn "RelationshipState.trusted" lib/ --include=*.dart` — 11 hits, all
reads.

The action a user would reasonably expect to produce trust does not:
`DevicesController.verify()` is the only method wired to a trust-granting
button, and it writes `RelationshipState.allowed`.

### The dead end, precisely

`Verify` is rendered **only** when the state is `unknown`
(`devices_view.dart:251`-ish region; the `if (relationship.state ==
RelationshipState.unknown)` guard around the `Verify`
`OnProcessButtonWidget` at `devices_view.dart:310`). Tapping it writes
`allowed` — at which point the button is replaced by a `Last seen: …` label
and **never returns**.

So the single affordance that could conceivably grant trust:
- never writes `trusted`, and
- disappears permanently the moment it is used once.

### Why this is S1, not cosmetic

`group_create_controller.dart:213` filters the member list to
`r.state == RelationshipState.trusted`. With no reachable `trusted`, that
list is empty for every user forever, `group_create_view.dart:226` renders
`No trusted contacts yet`, and **the Create Group button has nothing to
create a group with.**

That is the whole of E07's group journey — creation, membership, the
sender-key path, group messaging in either direction — made unreachable by
a state machine that cannot reach one of its four states. It is not a
degraded experience; the feature cannot be entered at all.

Two further readers of `trusted` are affected and should be checked
alongside any fix, but are NOT independently diagnosed here:
- `lib/features/location/domain/location_visibility_policy.dart:71`
- the `Trusted Node` badge at `devices_view.dart:506`, which can never render.

### Spec position

`FR-TRUST-003` is explicit that a request is evaluated into **one of:
Trusted, Allowed, Unknown, Blocked**. Three of those four are reachable.
`FR-TRUST-004` ("when B has configured A as trusted, auto-accept") and
`FR-TRUST-006` ("auto-accept trusted devices") both presuppose that a user
can configure a peer as trusted. Nothing in the product lets them.

## 3. Evidence

Found on hardware, 2026-09-29, devices `e4813f500601` (Redmi 10 2022) and
`3f5f59c7` (Redmi Note 12), after a **successful** bidirectional 1:1
exchange between them (`docs/real-device-validation-1to1.md`). Both peers
were `Allowed`. `Conversations → +` showed `Members` → `No trusted contacts
yet`, and the row menu on each peer offered only `Block` — no verify, no
trust, no promote.

So this was reached from the healthiest possible starting state: bonded,
connected, session-established, messages delivered both ways.

## 7. Risks

- **Conflating "allowed" with "trusted" weakens a security boundary.**
  `FR-TRUST-004` auto-accepts trusted peers *skipping the normal
  authentication flow*. Making everything allowed also trusted silently
  widens what auto-accept covers. Any fix must be explicit about this.

## 8. Run log
- 2026-09-29 — found during real-device validation, after the 1:1 journey
  passed. No automated test caught it, because no test asserts that
  `trusted` is reachable — each side of the boundary is tested against a
  state the tests construct directly.

## 9. Open Questions

- **OQ-E02-B02-1 — how does a peer become `trusted`?** 🧍 **Rule-3 /
  Rule-2 decision, deliberately unresolved.** This changes a security
  boundary, so no option is chosen here. The three coherent options:

  1. **`verify()` writes `trusted` instead of `allowed`.** Smallest change.
     But it makes `Verify` mean "trust", collapses the distinction between
     the two states, and would leave `allowed` itself largely unreachable —
     trading one unreachable state for another.
  2. **Group membership accepts `allowed` as well as `trusted`.** Also
     small, and matches what a user who has messaged a peer probably
     expects. But it contradicts `EARS-GROUP-17` as written ("trusted
     relationships become member rows") and the `Trusted Node` row copy,
     so the requirement and the design copy would have to change with it.
  3. **Add a distinct, explicit trust affordance** — a separate action
     (plausibly an out-of-band fingerprint comparison) that promotes an
     `allowed` peer to `trusted`, available on an `allowed` row rather than
     only on `unknown`. Largest change, and the only one that makes
     `trusted` mean something stronger than `allowed` — which is what
     `FR-TRUST-004`'s auto-accept-skipping-authentication seems to assume.

  Option 3 is the executor's advisory recommendation **on the reading that
  `FR-TRUST-004` intends trust to be a stronger claim than mere allowance**;
  if that reading is wrong, option 2 is simpler and more honest than
  option 1. No copy, glyph or verification mechanism is invented for any of
  them.
